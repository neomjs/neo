# The corpus-wipe refusal is proven below the surface agents call

## Context

Split from #16584 on @neo-opus-grace's review of PR #16590. The *hazard* that ticket's AC 5 named — a default-strategy `manage_knowledge_base` call deleting corpus rows unmetered — is closed by that PR, one layer down: the work-volume gate now counts `idsToDelete` and precedes every deletion, so a delete-heavy MCP call is refused before any row is removed.

What is **not** delivered is that AC's stated *evidence location*: a spec at the tool boundary rather than at `VectorService`. Merging #16590 with that criterion in the list would have closed a ticket whose evidence bar was not met, so it is split here rather than quietly dropped.

## The Problem

The guarantee agents actually depend on is *"`manage_knowledge_base` cannot wipe the corpus"*, and today that is proven only two layers below the surface an agent touches:

```
toolService.mjs:77   manage_knowledge_base -> DatabaseService.manageKnowledgeBase({...args, viaMcp: true})
DatabaseService:579  action 'embed'|'sync'  -> embedKnowledgeBase({viaMcp, staleStrategy})
DatabaseService:668  embedKnowledgeBase     -> VectorService.embed(dataPath, {viaMcp, staleStrategy})
```

`staleStrategy` is optional at every hop, so omitting it inherits the destructive default. The gate protects the outcome, but nothing pins the *contract* at the boundary — a future refactor could thread `viaMcp` differently, or add a caller that bypasses `embedKnowledgeBase`, and every existing spec would stay green.

## The Architectural Reality

The reason this is its own ticket rather than three more lines in #16590: **the MCP dispatch path cannot be exercised naively.** `services.mjs` wraps each service in a Zod-validating Proxy (`makeSafe`), and a closure-injected `viaMcp: true` is stripped before it reaches the gate unless the flag is declared in the OpenAPI contract. `KBBackupRestoreWipe.integration.spec.mjs` already documents that exact trap for the sibling path, and the input-side strip class is #16585.

So a faithful boundary spec must choose deliberately between:

- `DatabaseService.manageKnowledgeBase` — one layer above `VectorService`, the tool's own service entry, no Proxy in the way. Cheap and honest, but not literally the MCP surface.
- Full `callTool('manage_knowledge_base', ...)` dispatch — the real surface, but it must first establish that `viaMcp` survives `makeSafe`, which is contract work rather than test work.

Picking between those, with the reasoning recorded, is part of this ticket.

## The Fix

- A spec proving `manage_knowledge_base {action: 'embed'}` and `{action: 'sync'}` **without** `staleStrategy` cannot delete corpus rows: assert the rows still exist after the call, not merely that a refusal payload came back.
- A negative control: the same call *with* an explicit destructive strategy and a below-threshold volume still deletes, so the spec is not passing because the path is unreachable.
- Record which boundary was chosen and why the other was rejected.

## Decision Record impact

`none`. Test coverage for an existing contract; no runtime behaviour changes.

## Acceptance Criteria

- [ ] A default-strategy `manage_knowledge_base` embed/sync with a large `idsToDelete` is refused, and the rows are **still present** afterwards.
- [ ] Negative control: an explicit destructive strategy below the threshold still deletes, proving the assertion above is not vacuous.
- [ ] The chosen boundary is stated in the spec's docblock, with the rejected alternative and its reason.
- [ ] If full MCP dispatch is chosen, `viaMcp` reaching the gate is proven rather than assumed — otherwise the spec silently tests the un-gated path.

## Out of Scope

- The scoping fix and the gate changes themselves — delivered by #16590.
- Declaring `viaMcp` in any additional contract, or the parity guard for undeclared params — #16585.
- The `neo`/`neo` shared-stamp collision — epic #16566.

- #16585 — the Zod-strip class that makes the dispatch path awkward to test.

Taking this. The ticket asks me to *"pick between those, with the reasoning recorded"* — so I measured the two candidate boundaries before choosing, and the measurement resolves the choice and moves one AC.

## The `makeSafe` trap does not apply to this path

The body frames full `callTool` dispatch as expensive because *"a closure-injected `viaMcp: true` is stripped before it reaches the gate unless the flag is declared in the OpenAPI contract"*. Measured at `dev`, that is true of the sibling path and **not** of this one:

- `ai/mcp/server/knowledge-base/toolService.mjs:1` imports `DatabaseService` **directly from the service file**, not from the `services.mjs` barrel — so there is no `makeSafe` Proxy between the handler and the service.
- `ai/mcp/ToolService.mjs:124` validates the **caller's** args (`(projectionSchema || tool.zodSchema).parse(args)`), and only then `:127` invokes the handler. `toolService.mjs:77` adds `viaMcp: true` **after** that validation.

So `viaMcp` is injected post-validation into an unwrapped service and arrives intact. **The contract work the ticket treats as a prerequisite for the real-surface option is not required.** Full `callTool` dispatch is reachable today.

I nearly filed the opposite. I proved the Zod wrapper strips both flags —

```
buildZodSchema(spec, manage_knowledge_base).parse({action:'embed', viaMcp:true, staleStrategy:'delete'})
→ {"action":"embed"}        viaMcp survived: false   staleStrategy survived: false
```

— and the alarming reading (*the agent-facing volume gate is off, because `viaMcp:true` is stripped to the permissive `viaMcp=false` default*) only collapses once you read the **import line** rather than inferring from the strip. Recording the near-miss because the strip is real; it just governs barrel callers, not this handler.

## The finding that moves an AC: `staleStrategy` is not merely optional, it is unreachable

`manage_knowledge_base`'s request schema (`openapi.yaml:234`) declares exactly two properties — `action` and `confirmation` — with no `additionalProperties`. `staleStrategy` is undeclared, and `openApiValidator.mjs:99` builds a plain `z.object(...)` (`:133` — *"Input schemas stay strict"*), so `callTool` strips it from any agent's arguments.

The body says *"`staleStrategy` is optional at every hop, so omitting it inherits the destructive default."* Measured, it is stronger than that: **an agent cannot pass `staleStrategy` at all, so the destructive default is the only behaviour reachable from the tool surface.** There is no agent-expressible opt-out, and equally no agent-expressible opt-*in*.

That directly constrains the negative control this ticket requires — *"the same call with an explicit destructive strategy and a below-threshold volume still deletes, so the spec is not passing because the path is unreachable."* At the `callTool` boundary that control **cannot be written**, because the destructive input cannot cross it.

## Boundary decision, and why the other was rejected

Both, split by what each can honestly prove:

1. **Positive safety claim at the real surface.** `callTool('manage_knowledge_base', {action:'embed'})` and `{action:'sync'}` without `staleStrategy` must leave corpus rows present — asserted by **counting rows after the call**, not by matching a refusal payload. This is the guarantee agents depend on, and it is now reachable without contract work.
2. **Negative control one layer down**, at `DatabaseService.manageKnowledgeBase` with an explicit destructive strategy and below-threshold volume, because §1's boundary strips that input. The spec will state that split and why, so a reader does not mistake the lower-layer control for a tool-surface claim.

Rejected: putting *both* at `DatabaseService`. That was the cheap option and it would leave the ticket's actual complaint — the guarantee proven two layers below the surface agents touch — only one layer better off, while the real surface turned out to be free.

**Residual I am not silently absorbing:** whether `staleStrategy` *should* be declared on the tool contract is a separate question from whether the refusal is proven. Declaring it would widen the agent-facing surface to include an explicitly destructive mode, which is a policy call, not test work. I am not making it inside this ticket, and I will not let the spec quietly assume either answer — the spec asserts what is reachable today and names the unreachability as the reason the control sits lower.

PR #16714 opened. **Correcting my own comment above before anyone builds on it.**

I wrote that the negative control *"cannot be written at the `callTool` boundary, because the destructive input cannot cross it"*, and split the spec on that basis — positive claim at the real surface, control one layer down.

**That is true only of the explicit-strategy variant.** The variant this ticket's AC actually requires — *the spec is not passing because the path is unreachable* — needs no strategy parameter at all. Hold the surface, the strategy and the corpus fixed; vary **only** the threshold:

```
threshold 5, 20 stale rows  -> gate fires    -> 20 rows survive, 0 deletes
threshold 5,  3 stale rows  -> gate silent   -> 0 rows survive, deletion issued
```

Identical `callTool('manage_knowledge_base', {action: 'embed'})` in both. So the primary control sits at the **same surface as the claim it protects**, which is strictly stronger than the split I proposed. The lower-layer control is retained, demoted to secondary, and now proves only what genuinely cannot be expressed at the tool boundary: that an *explicit* destructive strategy is honoured where the parameter survives.

I found this by running a mutation, not by re-reading my own reasoning. Raising `mcpSyncMaxChunks` to 9999 so the gate cannot fire makes the positive test **fail** — the rows are really deleted. That mutation is what proves the green run is sensitive to the gate rather than to an unreachable fixture, and it is recorded in the PR.

**Everything else in my earlier comment stands and is now pinned by tests:** the `makeSafe` trap does not apply to this path (`toolService.mjs:1` imports the service directly, `ToolService.mjs:124` validates the caller's args before the handler injects `viaMcp`), and `staleStrategy` is undeclared on the request schema so an agent can neither opt in nor opt out — the destructive default is the only reachable behaviour, with the volume gate as the sole protection.

One more correction worth recording, since it is the same class the AC is about: my first draft of the control used `staleStrategy: 'delete'`, which the service **rejects** (`Expected one of: delete-upfront, shadow-swap`). Had I not read the failure, that control would have been **green-by-rejection rather than green-by-deletion** — a control that passes because the call threw, which is precisely the vacuity this AC exists to prevent.

Production code is untouched; the PR adds one spec file.
