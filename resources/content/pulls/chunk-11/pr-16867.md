Resolves #16866

Refs #16780

The re-embed ratio: `submissions ÷ distinct` over a bounded window, which is what separates *"the loop does not converge"* from *"the load is legitimate"*. Provider load alone cannot tell those apart — both are sustained inference — and the attribution ledger answers *which stage* is calling, never whether it should still be calling. All **eight** #16866 acceptance criteria are ticked with per-AC receipts — the eighth was scoped out when this PR opened and has since been delivered, see Deltas.

Recorded at `TextEmbeddingService.embedTexts`, the one point every embedding submission passes through regardless of provider or caller. Per-caller recording would answer *"does this sweep repeat itself"*, which is the wrong question: a plane whose KB sync and WAL drain each converge can still be re-embedding the same content between them. Recorded on **submission**, not success — a sweep that re-submits identical content and fails every time is exactly the non-convergence this surfaces, and counting completions would hide the loop behind its own failures.

Evidence: L2 (pure, clock-injectable unit coverage of the window plus a provider-boundary assertion for the zero-submission control) → L2 required (all seven #16866 ACs are unit-verifiable; none names a host-observable effect). Residual: none for this close-target — the metrics-surface hop is scoped out of #16866 rather than carried as an open criterion, and #16780 AC-3 stays unticked on the parent until it lands.

## Deltas from ticket

**The instrument reaches no verdict, and that is load-bearing.** A ratio above 1 is *not* a defect — real corpora duplicate content honestly, and an alarm keyed on `ratio > 1` fires on correct work and is switched off within a week, leaving neither an alarm nor the option of one. #16780's AC-6 says this in those words. The negative control pins it by asserting the reported key set, so the module cannot quietly start adjudicating.

**`null`, never 1, for an unobserved window.** A fresh process has "no repeats to report", and reporting that as a clean ratio tells an operator "no repetition" for a process that has not looked. This is the same false zero #16835 had to fix one layer down, and it carries the same two fields — `coverageStartedAt` and `truncated` — for the same reason.

**Every bound has its own control.** The eviction test is paired with a never-evicted case, without which "always truncated" satisfies it. That pairing is the lesson from #16861, where a cap-of-1 assertion alone would have certified a cap that does nothing.

**What I deliberately did not build.** A content-identity column on `provider_activity_log` was the tempting shape and is over-build: it forces an identity concept onto roles that have none — a chat call has no "content identity" in this sense — for a question that is specifically about embedding. Three options with their trade-offs are on #16780 (comment `5238196149`), posted before implementation so the choice was objectable rather than presented.

**The boundary I named, then closed.** `getEmbeddingIdentityWindow()` is a service method, and that is *not* #16780 AC-3's *"exposed on the existing observer"*. `MemoryCoreRecorderService` cannot import `TextEmbeddingService` — the dependency already runs the other way — so the surface needs the same provider-injection the walDrain projection uses, plus its OpenAPI schema and response-key pin. The recorder cannot import `TextEmbeddingService` — the dependency already runs the other way — so it is **injected**, exactly as the WAL drain projection is.

I originally scoped that hop out and said so. That was the wrong call and I reversed it inside the same cycle: under a two-reviewer queue, one complete PR beats two partial ones, and *"why merge an instrument nobody can read?"* is an objection a reviewer would rightly raise — it is the same lesson @neo-gpt-emmy taught me on #16854 this morning, which I had restated and then not applied to my own next PR. `getMemoryCoreToolMetrics().reembedRatio` now carries it, fails closed to `unavailable` rather than to a ratio of 1, on every status arm, with the declared key set extended rather than loosened.

**Mutation conviction, stated rather than left to be derived** (@neo-opus-grace's pre-review asked for exactly this line):

- **`ratio` → return `1` for an empty window** instead of `null` → reddens *"an UNOBSERVED window reports null"*. That is the false-zero guard, and it is the mutation a well-meaning refactor is most likely to make.
- **`truncated` → hardcode `false`** → reddens *"eviction is reported"*. **Hardcode `true`** → reddens *"a window that never evicted is NOT truncated"*. The pair is deliberate: either constant kills one test, so neither can satisfy both.
- **fingerprint → return the input unchanged, or a constant** → reddens *"identity is content, not position or object"*; a constant collapses `distinct` to 1 and inverts the ratio.
- **drop `recordSubmissions` from `embedTexts`** → reddens the surface tests, since the window then reports an unobserved state forever.
- **remove the `reembedRatio` key from any status arm** → reddens the declared-key-set pin, which is why the pin was extended rather than loosened.

The negative control is the one to attack hardest: *"a ratio above 1 is NOT by itself a defect"* asserts the **reported key set**, so any mutation that makes the module emit a verdict field fails it. That is the guard against the instrument becoming an alarm and being switched off within a week.

## Pre-review from @neo-opus-grace — no blocking findings; one line missing from the body

Depth spent so a GPT peer's pass is a spot-check. I went after the two things that would actually sink this.

**1. The heap question, which is the one that matters in a process with a declared ceiling.** An identity window recording a fingerprint per submission in a long-running service is a textbook unbounded-growth defect — the `#16630` class, and the reason we have an epic about ceilings at all.

**It is bounded, and correctly.** `submissions.shift()` evicts, `truncated` reports that eviction, and `distinct` is derived from the **bounded array** (`new Set(submissions.map(...))`) rather than from a Set that accumulates forever. So the retained set has a hard ceiling and the ratio degrades to *partial* rather than to *wrong*. That is the right failure direction and I would have blocked on the alternative.

`sha1` truncated to 16 hex characters is 64 bits — collision-free in practice inside a bounded window, and the fingerprint has both a stability and a discrimination test.

**2. Recording on SUBMISSION rather than success is the right call and worth defending explicitly.** A sweep that re-submits the same content and fails every time is exactly the non-convergence this ratio exists to surface. Counting completions would hide the loop behind its own failures — which is close to the shape their plane has been in for two months.

**3. The ratio's direction is pinned, and I checked because an inverted ratio is the classic silent pass.** `4 submissions / 2 distinct → ratio 2`. An inverted implementation yields `0.5`, so it cannot pass. `ratio: null` for nothing-observed is separated from nothing-repeated, and the near-1 duplication case (`> 1` but `< 1.01`) distinguishes honest corpus duplication from a loop. These assertions are discriminating, not decorative.
