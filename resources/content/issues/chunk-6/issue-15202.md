# Use component class APIs across application state transitions

## Context

A repository-wide audit after the closed class-ownership refactor found six non-AgentOS application files that manually read an aggregate component **cls** array, mutate it, and assign the whole value back. These sites do not need a new class architecture: each already knows the exact old/new or Boolean class intent and can use **Neo.component.Base**'s existing public mutation methods.

The canonical methods are [addCls()](https://github.com/neomjs/neo/blob/53e9314dee5d3d9834b85b102d47d8387a9b814a/src/component/Base.mjs#L352-L360), [removeCls()](https://github.com/neomjs/neo/blob/53e9314dee5d3d9834b85b102d47d8387a9b814a/src/component/Base.mjs#L1602-L1610), and [toggleCls()](https://github.com/neomjs/neo/blob/53e9314dee5d3d9834b85b102d47d8387a9b814a/src/component/Base.mjs#L1683-L1692). Moving application consumers onto that boundary removes their dependency on today's array representation without deciding the planned future object representation.

Live latest-open sweep: checked the latest 20 open issues and the latest 30 A2A messages at 2026-07-15T19:13:56Z; no equivalent ticket or in-flight claim surfaced. Targeted issue, Discussion, Knowledge Base, Memory Core, and local-content sweeps also found no owner for this cleanup.

## The Problem

The following six files manually duplicate component class mutation:

- **apps/covid/view/MainContainerController.mjs:403-412** clones the main view's classes, scans out a theme class, adds the next theme, and reassigns the aggregate.
- **apps/sharedcovid/view/MainContainerController.mjs:597-609** repeats the same pattern across connected main views.
- **apps/devindex/view/Viewport.mjs:92-102** removes the previous size class, adds the next, and reassigns **me.cls**.
- **apps/portal/view/Viewport.mjs:95-103** performs the equivalent Portal size transition.
- **apps/portal/view/ViewportController.mjs:391-407** toggles two header state classes through a local aggregate and reassigns it.
- **apps/shareddialog/view/MainContainerController.mjs:616-621** replaces the previous theme class with the current theme through a local aggregate and reassigns it.

The semantic owner is known at every site. Reading the complete aggregate couples these applications to framework-owned, layout-owned, and other caller-authored classes that are unrelated to the transition being expressed.

## The Architectural Reality

**cls** is a reactive component config; **Neo.component.Base** owns its update path. The getter returns a copied array, and the public class methods deliberately perform add/remove/toggle operations before re-entering the config setter.

This ticket is limited to component instances. [StylingAndTheming.md](https://github.com/neomjs/neo/blob/53e9314dee5d3d9834b85b102d47d8387a9b814a/learn/guides/uibuildingblocks/StylingAndTheming.md#L105-L138) explicitly preserves direct class-array writes for descendant raw-VDOM nodes. RealWorld descendant-node updates and Dock Demo progress pips are therefore legitimate and excluded.

Workstation is also excluded. Its two writes use **setSilent()** during dock projection staging and have a batching contract that today's public class methods do not express. That seam is an explicit consumer requirement in [D#15200](https://github.com/orgs/neomjs/discussions/15200), not a mechanical cleanup.

## The Fix

Use the current public component class methods only in the six listed files:

- theme transitions remove only the known prior/theme vocabulary and add the selected theme without cloning the aggregate;
- DevIndex and Portal viewport transitions remove the previous size class and add the next;
- Portal header state uses enforced **toggleCls()** calls for **hide-sidebar** and **separate-bar**;
- SharedDialog removes **previousTheme** and adds **currentTheme** through the component API;
- remove NeoArray imports that become unused.

Preserve all existing text, icon, map-style, visibility, connected-window, and state-provider behavior. Do not broaden the patch to other **cls** assignments that replace a complete authored input without reading the current aggregate.

Because remove-then-add can enter the reactive setter more than once, focused evidence must prove that no observable intermediate class state, extra motion, or render regression is introduced. If the existing API cannot satisfy that, stop and route the missing atomic/batched primitive back to D#15200.

## Decision Record impact

None. This is an application-only consumer cleanup using an existing public API. It does not define or amend the class-config architecture.

## Premise check before implementation: the stop-condition this ticket names is LIVE

Claimed this, and ran the ticket's own gate before writing any of the six files:

> *"Because remove-then-add can enter the reactive setter more than once, focused evidence must prove that no observable intermediate class state, extra motion, or render regression is introduced. If the existing API cannot satisfy that, stop and route the missing atomic/batched primitive back to D#15200."*

**It cannot satisfy it, and the reason is structural.**

### Measured, not argued

A `Button` with `cls: ['probe-action', 'theme-a']`, instrumented on `update()`, capturing the vdom-root class list at every entry:

```
AGGREGATE (what the six files do today)
  1 update
  update 0 -> ["probe-action","neo-button","icon-left","theme-b"]   ← the final state, directly

API (removeCls + addCls)
  2 updates
  update 0 -> ["probe-action","neo-button","icon-left"]             ← NEITHER theme class
  update 1 -> ["probe-action","neo-button","icon-left","theme-b"]
```

The `cls` getter returns a **copy**, so today's read-mutate-reassign is genuinely atomic: one setter entry, one `afterSetCls`, one `update()`. `addCls()`/`removeCls()` each end in `this.cls = cls`, so the pair is **two** of everything — and the intermediate carries *no theme class at all*.

**Both final states are identical.** An AC asserting the end state is green on the regression; the defect is in the transition, not the destination.

### The part I could NOT prove, stated plainly

**Two `update()` entries are not two paints, and this harness cannot tell me which.** Spying on `updateVdom` — the real dispatch gate — every entry reports `mounted=false`, so every update defers and **nothing dispatches**:

```
API — updateVdom entries: 2
   0 cls=[…,"icon-left"]           mounted=false  deferred=true
   1 cls=[…,"icon-left","theme-b"] mounted=false  deferred=true
```

The unit harness never mounts, so it **structurally cannot** produce the evidence this ticket's AC demands. What is knowable from the source: `VdomLifecycle.updateVdom` guards with

```js
if (me.isVdomUpdating || !me.vnodeInitialized || me.silentVdomUpdate) { me.needsVdomUpdate = true; return }
```

— which **defers the second update without cancelling the first**. On a *mounted* component the first has already dispatched the intermediate. So the flash is plausible and unproven, and I am not going to assert it in either direction from a harness that answers `mounted=false` to every question.

### Why `silentVdomUpdate` isn't the escape

Wrapping the pair collapses it to one real flush — and that is **exactly the seam this ticket excludes Workstation for**: *"its two writes use `setSilent()` during dock projection staging and have a batching contract that today's public class methods do not express."* Reaching for it here would adopt the unresolved requirement while claiming to avoid it.

### Where this leaves the ticket

The premise — *"these sites do not need a new class architecture; each already knows the exact old/new intent and can use the existing public methods"* — is right about **intent** and wrong about **atomicity**. All six sites express a *single* transition (`theme-a → theme-b`, `size-x → size-y`, two header flags at once). The public API can express each **half**, and has no way to say "these halves are one change." That is not six consumers being sloppy; it is a missing primitive, and it is the same one Workstation was excluded for.

**Routing to D#15200 as the ticket instructs**, rather than shipping six transitions that each gain an intermediate frame. Two things worth deciding there:

1. **The atomic/batched multi-class primitive.** Workstation needs it, these six need it, and any future `cls`-object migration will need it. It is one requirement with three consumers, not a Workstation special case.
2. **The evidence bar.** This ticket's AC ("prove no observable intermediate class state") **cannot be met by a unit test** — nothing mounts. Either the AC needs an e2e witness on a mounted component, or it needs to be honest that the unit suite can only assert the endpoint, which is precisely the assertion that cannot see this defect.

**Not dropping the ticket** — the six sites are real and the cleanup is worth doing. It is blocked on the primitive, not on the will to do it. Un-assigning so it isn't parked under my name while it waits on D#15200.

**Verified independently against the primitive rather than inherited** (`src/component/Base.mjs`):

```js
addCls(value)         { NeoArray.add(cls, value);          this.cls = cls }   // assignment 1
removeCls(value)      { NeoArray.remove(cls, value);       this.cls = cls }   // assignment 2
toggleCls(value, add) { NeoArray.toggle(cls, value, add);  this.cls = cls }
```

**Each method ends in its own `this.cls = cls` config-setter assignment — so each publishes its own change.**

### The prescription inverts the property at 5 of 6 sites

Every site this ticket names is a **replace** (or a double-toggle), and the current code is **atomic by construction** — it builds the whole array locally and assigns **once**:

| site | intent | today | after this ticket |
|---|---|---|---|
| `apps/covid/.../MainContainerController.mjs:403-412` | theme replace | 1 published change | **2**, intermediate root has *no* theme class |
| `apps/sharedcovid/.../MainContainerController.mjs:597-609` | theme replace | 1 | **2** |
| `apps/devindex/view/Viewport.mjs:92-102` | size replace | 1 | **2**, intermediate has *no* size class |
| `apps/portal/view/Viewport.mjs:95-103` | size replace | 1 | **2** |
| `apps/portal/view/ViewportController.mjs:391-407` | two header toggles | 1 | **2** |
| `apps/shareddialog/.../MainContainerController.mjs:616-621` | theme replace | 1 | **2** |

**The "manual duplication" this ticket removes is the thing making the transition atomic.** The aggregate read isn't sloppiness — it's how the site expresses *one* semantic change as *one* published change. The public methods express add / remove / toggle; **none expresses replace**, and replace is what every one of these sites does.

**Its own framing carries the tell:** *"each already knows the exact **old/new** or Boolean class intent."* **Old/new is a replace.** There is no `replaceCls`, so old/new must decompose into two calls — and the decomposition is the defect.

### Not a criticism of the ticket's premise

The premise is right: these sites shouldn't depend on today's array representation, and the exclusions (Workstation's `setSilent()` batching per `D#15200`, RealWorld descendant nodes, Dock Demo pips) are carefully drawn. **The ticket is well-built and that's exactly why it's dangerous unassigned** — it reads as a clean mechanical cleanup with the line numbers already found, so the next agent ships six diffs and five regressions, each one green (no test asserts *"one published change"*), each one visible only as a one-frame flash of an unthemed root.

**Blocked on the same boundary as `#15201`: an atomic replace/batch seam through `D#15200`.** Once `replaceCls(old, new)` (or a batch boundary) exists, this cleanup is correct and worth doing — the sites keep their semantics and lose the representation coupling, which is the whole point.
