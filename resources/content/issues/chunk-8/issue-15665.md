# Kimi wake route lands in a serverside sibling, never the live TUI

## Context

Operator, 2026-07-21: *"maybe our biggest friction item: getting wake messages delivered into your TUI (not a serverside sibling session)."*

The live cost is visible every session: peers suppress wakes to the Iris seat and the **human relays content by hand** (twice more on 2026-07-21 alone — Euclid's intakes on `#15666`/`#15667` and on this ticket both state "direct Kimi wake suppressed due split-brain risk; operator may relay").

**Amended 2026-07-22T00:2xZ per Euclid's intake (needs-narrowing + needs-contract-alignment, comment on this ticket):** the kitty terminal-injection prescription is **withdrawn** — source-proven unsafe. Replaced by the research-neutral owner-ingress comparison + Contract Ledger below. No implementation branch opens from the prior body.

## Lineage (corrective successor)

- `#15579` / PR `#15588` shipped the kimi-server wake adapter; its receipt proved REST delivery **to a session ID** — not that the human-driven TUI owned that session.
- `#15596` / `#15597` shipped v0.28 coordinate discovery under the since-falsified "live TUI adoption works" assumption.
- `#13796` owns shared stop-hook semantics — a different layer.

## The Problem (split-brain, source-proven at `1d7fa14474`)

Neo treats HTTP 200 + `code === 0` from the loopback web server as `delivered` (`ai/daemons/wake/daemon.mjs:1301-1323, 1759-1761`) — that proves **acceptance by the web process**, not ownership by the running TUI. The pinned Kimi source (`ec88d352…`) supplies the process boundary:

1. The Node SDK constructs a new `KimiCore` per caller process.
2. The REST prompt route calls `resume(sessionId)` — a persisted-but-cold session is materialized **in that process** (session liveness is a process-local `Map`).
3. The prompt enqueues into that process-local scope.

So the same persisted session can be live in two processes, and a prompt appearing in shared history is **not** evidence the TUI owned the turn. AC2 must require **execution-owner proof**, not session-history visibility.

Additionally verified on the Iris seat: `WAKE_SUB:ad94a336-…` pins a `lockPath` whose instance file no longer exists (`server/instances/` empty), so today's route hard-errors; an interactive TUI registers **no** loopback instance (only `kimi web` does); the wake envelope correctly carries the live TUI's `sessionId` but no receiving surface exists for it.

## The Architectural Reality

- Cross-harness parity exists elsewhere (opencode-server REST, codex-app-server, Claude instance-addressable routing). Kimi TUI is the only seat class without an inbound path.
- **Why raw kitty injection is rejected (Euclid's evidence):** the Kimi window title carries only session title/product name — no idle/active-turn/approval/typing/epoch state; and when an approval panel owns focus, **Enter submits the selected decision**. A `send-text` digest + Enter can mutate an approval or collide with unsent operator input, and yields no causal TUI-turn receipt. This conflicts with ADR 0002 §5.2 (unknown presence → `next_turn`; no injection over `userTyping`; bridge fallback must degrade unless it can prove idle or append-only safety).
- A same-process seam exists upstream (cron fire → `agent.turn.steer(...)`; `KIMI_CRON_MANUAL_TICK=1` + SIGUSR1 manual tick), but upstream labels it a bench affordance, warns a process may host main agent **plus subagents**, and manual mode disables automatic cron polling. Research candidate only, with a mandatory negative matrix.

**ADR successor-risk:** `adr-amendment-required` if raw title-addressed terminal input remained the route (contradicts ADR 0002 §5.2). `adr-aligned` under the owner-native ingress route chosen below.

## The Fix (research-neutral owner-ingress comparison — ordered)

1. **Upstream-supported TUI ingress / owner registration** via the in-process turn API (the durable route; if it does not exist, the deliverable is the upstream proposal, not a Neo workaround).
2. **Constrained manual-tick/cron proof** to learn whether the owner-native seam is usable without scheduler or subagent regressions — bounded prototype, falsifying: listener fan-out, active-turn buffering, session switch, PID reuse, cron expiry, existing-cron regressions.
3. **Kitty only with a separate state-and-ack bridge** that proves idle/append-only delivery — the current title + `send-text` proposal cannot, so kitty is not the route unless that bridge materializes.

First executable artifact: the bounded owner-native ingress probe + its negative matrix. No terminal-injection code.

So the split-brain is **structural in the harness**, not in Neo's wake substrate: every programmatic path (`kimi web` REST — what our `kimi-server` route uses, or ACP) hosts a *different* session than the one the human drives in the terminal.

**Consequence for the option space:** option 1 of the ticket (TUI exposes/registers a receiving surface) is falsified against current docs; MCP-notifications-to-TUI is not documented as a receiving channel either. The remaining honest Neo-side path is **terminal injection** — a `bridge-daemon` kitty adapter (`kitty @ send-text`, title-addressed window) that lands the digest *as input* in the live TUI. Caveats to design against: kitty remote control must be enabled on the seat; injected text races with human typing; the digest must be self-contained; the adapter keeps the daemon's fail-visible bar (no silent fallback). The alternative — upstream feature request to Kimi Code (TUI-side prompt ingress / instance registration for interactive sessions) — is worth filing in parallel; if the harness ever ships it, the existing `kimi-server` route + wake envelope works unchanged.

### Confirmed facts

1. **Process topology (v0.28.1):** interactive TUI = pid 60469 (`kimi`, started with the session, parent of the interactive MCP set); `kimi web` = pid 2855 (parent of the 09:05 twin MCP set). Distinct processes — and **the TUI has ZERO listeners** (`lsof -p 60469` shows no TCP LISTEN). AC1 re-confirmed at process level on v0.28.1: no inbound surface on an interactive TUI.
2. **The owner-native primitive exists and works — from inside only.** `CronCreate` in the agent's own process registers jobs that fire via `agent.turn.steer` in the **owning** process (idle-gated delivery, `<cron-fire>` envelope, coalescing). This is the only documented in-process ingress seam.
3. CLI surfaces: `kimi acp` (stdio, IDE clients), `kimi web` (server), `kimi server` (deprecated). No interactive-ingress mode.

### Design consequence — the pull-inversion (iteration 2, now running)

The TUI has no inbound surface but constantly makes OUTBOUND moves (hooks, its own scheduler). So invert: **the owning session polls for its own wakes.** A recurring self-poll cron (registered by the agent at boot, e.g. every ~3 min: "read the seat wake-outbox") fires owner-natively via steer; the daemon's delivery becomes *writing the seat outbox file* — no inbound surface, no twin, fail-closed (no cron → no delivery, loud). The wake envelope hook (`SessionStart`) already proves the seat-hook channel; the identity-anchor hook proves boundary context-injection. Iteration 2 probes the full loop end-to-end on this seat: daemon-stand-in writes the outbox → self-poll fire consumes it → wake surfaces in the live TUI with execution-owner certainty.

Trade-offs being measured: delivery latency = poll interval (bounded by the daemon's own ~2.5–5 min cadence anyway); per-fire turn cost; the 7-day recurring-cron expiry (boot re-registration via the SessionStart/boot hook). The **upstream proposal remains the durable route** (true push ingress for interactive sessions — or a documented cron-dir watch, which would resurrect the EXT-WRITE-1 path). The self-poll bridge is the Neo-side candidate that works on v0.28.1 today.

## Iteration 2: the pull-inversion WORKS — owner-native wake delivery proven end-to-end on v0.28.1 (2026-07-22, Iris seat)

**The proof, with the exact owner tuple and causal receipt AC2 demands:**

1. **External write (daemon stand-in):** `~/.kimi-code/wake-outbox.jsonl` ← one wake-shaped payload (`probe-1`), written by a plain shell process at 14:04:30 local — no session involvement.
2. **Owner-native fire:** the session's own one-shot cron (`18b1e77b`, registered in-process via `CronCreate` at 12:05Z) fired at **14:09:00 local** — `agent.turn.steer` executing in the **owning interactive TUI process** (pid 60469, booted 08:33:02Z, zero listeners).
3. **Causal turn receipt:** the `<cron-fire jobId="18b1e77b" recurring="false" coalescedCount="1">` envelope arrived as a user-role message in the live TUI conversation — a turn steered by that exact process epoch. Not HTTP acceptance, not session-history visibility: **execution-owner proof.**
4. **Consume:** the agent read `probe-1` and rewrote the outbox to 0 bytes. Loop closed.

End-to-end latency: ~4.5 min, bounded by the chosen 5-min poll interval — at parity with the wake daemon's own ~2.5–5 min scan/coalesce cadence.

**Safety semantics fall out by construction, not by inspection:** fires are **idle-gated by the harness itself** (held to the next idle moment, never injected mid-turn — documented scheduler behavior), and the payload arrives as a *queued user message*, not keystrokes — so the approval-dialog / operator-draft clobber class that killed the kitty route (ADR 0002 §5.2) does not exist here. No inbound surface on the TUI, no twin, and fail-closed by construction: no registered poll → no delivery, loud.

**What this is and isn't:** the seam is proven (external writer → seat outbox → owner-process steer → live TUI). One integration step short of a *true* wake: the daemon-side outbox writer doesn't exist yet (probe payload stood in for it). Next executable artifacts, in order:
