# fix(ai): file-system MCP server tools missing x-pass-as-object -> object-handler arg-shape mismatch

## Problem

Every argument-taking tool of the **file-system MCP server** fails at call time. Only `healthcheck` (no arguments) succeeds.

Verified against the published npm packages `neo.mjs@13.0.0` and `neo.mjs@13.1.0`, by starting `ai/mcp/server/file-system/mcp-server.mjs` and connecting a real MCP client over stdio (`@modelcontextprotocol/sdk`):

```
tools/list -> healthcheck, read_file, write_file, list_directory, check_syntax, run_playwright_test

healthcheck          isError=false  {"status":"healthy"}
read_file            isError=true   Error executing read_file: The "paths[0]" argument must be of type string. Received undefined
list_directory       isError=true   (same)
write_file           isError=true   (same)
check_syntax         isError=true   (same)
run_playwright_test  isError=true   (same)
```

Stack trace from the server process:

```
BaseServer.mjs:341            dispatch
  ToolService.mjs:74          callTool           -> tool.handler(...handlerArgs)
    FileSystemService.mjs:54  checkSyntax
      FileSystemService.mjs:16 ensureSandboxed   -> TypeError (ERR_INVALID_ARG_TYPE)
```

## Root cause

Same defect class as #8332, #9545 and #14542.

`ToolService` dispatch branches on `x-pass-as-object` (`ai/mcp/ToolService.mjs`):

```js
if (tool.passAsObject) {
    return tool.handler(validatedArgs);              // pass the single validated object
}
const handlerArgs = tool.argNames.map(name => validatedArgs[name]);
return tool.handler(...handlerArgs);                 // else: spread positionally
```

All `FileSystemService` handlers destructure a single object:

```js
static async readFile({absolutePath})            { ... }
static async writeFile({absolutePath, content})  { ... }
static async listDirectory({absolutePath})       { ... }
static async checkSyntax({absolutePath})         { ... }
static async runPlaywrightTest({absolutePath})   { ... }
```

…but `ai/mcp/server/file-system/openapi.yaml` declares `x-pass-as-object` on **none** of its operations, so the positional branch is taken and the handlers receive a bare string. Destructuring it yields `absolutePath === undefined`, and `path.resolve(undefined)` throws.

Declaration counts per server (13.0.0):

| server | operations | x-pass-as-object |
|---|---|---|
| github-workflow | 23 | 16 |
| gitlab-workflow | 13 | 12 |
| knowledge-base | 9 | 8 |
| memory-core | 29 | 28 |
| neural-link | 37 | 32 |
| **file-system** | **6** | **0** |

## Suggested fix

Add `x-pass-as-object: true` to the five argument-taking operations in `ai/mcp/server/file-system/openapi.yaml`:

```yaml
  /read_file:
    post:
      operationId: read_file
      x-pass-as-object: true
```

(same for `write_file`, `list_directory`, `check_syntax`, `run_playwright_test`)

Locally patching just `check_syntax` this way makes the tool return `Syntax OK` through the same MCP client, so the one-line annotation is sufficient.

## Why it went unnoticed

No test exercises these tools through the real `ToolService` dispatch. `FileSystemPolicy.spec.mjs` substitutes `callTool` with a mock, and the `FileSystemService` unit specs call the service methods directly with an object. A dispatch-level test for one file-system tool would have caught this, and would guard the other servers too.

Related: PR #10873 review already flagged that `x-pass-as-object` lacks a discoverable definition in the docs surface, which is likely why the annotation keeps getting missed.

## Environment

- neo.mjs 13.0.0 and 13.1.0 (npm)
- Node.js 22
- @modelcontextprotocol/sdk 1.27.x

### Generalizing the existing guard was the right call

> *"I generalized the existing #14542 recurrence guard in `OpenApiValidatorCompliance.spec.mjs` rather than adding a parallel one, since that test is already this assertion narrowed to neural-link."*

That is the better judgment and worth naming, because the tempting move was a new file. A parallel guard would have left two tests asserting one invariant over different subsets — and the next server added would have landed in whichever subset its author happened to notice. Widening the existing one means the invariant has a single home and new servers are covered by construction rather than by remembering.

### Your two extra findings outrank the original

This is the part I want to be direct about: **both are more dangerous than the bug you filed.**

The reported defect crashes. `path.resolve(undefined)` throws, the call returns `isError=true`, and a caller cannot proceed on a wrong answer. Loud failures are the cheap kind.

Yours are silent:

- **`knowledge-base.get_ingestion_progress`** — `{staleAfterMs = 60000} = {}` absorbs the positional call and applies the default. The caller's value never lands and nothing says so, so a deliberately narrowed staleness window reads as if it were honoured.
- **`github-workflow.get_pull_request_diff`** — a bare `pr_number` survives, but `file`, `sha` and `files_only` are dropped by arity. **A request for one file's diff returns the whole diff.**

The second one matters here beyond correctness of the tool: agents on this project use `get_pull_request_diff` during review, and "asked for one file, silently received everything" is precisely the failure a reviewer would not notice — you get *more* than you asked for, which reads as thoroughness rather than as a bug. That is a real review-integrity issue and it was invisible until you wrote a test that enumerated the whole surface.

**Recording them with a reason rather than fixing them in this PR was the correct instinct.** They are a different defect class — the annotation is missing in the same way, but the symptom is a wrong result rather than a refusal, so they need their own falsifiers and their own scope.

One ticket covering both, not two: they are two instances of one class (*"unannotated operation degrades silently instead of failing"*), and the fix and the guard are shared. Splitting per-server would fragment a single invariant across two tickets.
