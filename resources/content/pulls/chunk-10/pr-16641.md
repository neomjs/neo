Resolves #16488

The `ai/services.mjs` barrel is the canonical SDK entry point, and it could not be loaded in the Body install tier: two of its eagerly-imported leaves reached `chromadb`, which ships only in the Brain tier. Merely *importing* the SDK required a package that is only needed once something talks to Chroma. That took the hourly Data Sync stage down for twelve consecutive runs with `ERR_MODULE_NOT_FOUND`, froze `resources/content/issues` and `resources/content/discussions`, and was bridged by a deliberately temporary, self-expiring SDK-boundary exception (#16495 / PR #16496).

**This removes the reason that exception existed, and retires it.**

Evidence: L2 (spec-driven; the repo's own sunset guard is the class assertion) → L3 required (a scheduled Data Sync run postdating the merge, which is the only thing that can confirm the pipeline stays green without the exception). Residual: pipeline confirmation [#16488].

## What shipped

- `chromadb` is no longer imported at module scope anywhere under `ai/services/`. Both `ChromaManager`s build their client in `initAsync()` with `await import('chromadb')`; `chromaClientPrimitives` pulls the registry symbols on first registration.
- `registerNeoChromaEmbeddingFunctions` is **async**, and its 7 call sites await it. Registration is a connection-time concern, not a load-time one.
- Every direct reader of `.client` asserts readiness at **its own entry**.
- The SDK-boundary exception in `syncGithubWorkflow.mjs` is retired — the import block is byte-identical to its pre-exception form — and its sunset spec is deleted, exactly as that spec's own failure message instructs.

The barrel's export surface is unchanged, and no consumer of `ai/services.mjs` was modified.

## The class assertion came from the repo, not from me

`syncGithubWorkflowImportException.spec.mjs` was built to fail the moment the barrel stops reaching `chromadb`. It fired:

> `ai/services.mjs` NO LONGER reaches chromadb, so the Body tier can import the barrel again. […] **This failure is the exception expiring on schedule, not a regression.**

That is the AC *"the same walk from `ai/services.mjs` itself reaches no `chromadb`"*, proven by a guard written before the fix existed and observed rather than asserted. Retiring the exception and deleting the spec are what that message prescribes.

## Deltas from ticket

1. **The ticket's own table was wrong, and it mattered.** It lists `chromaClientPrimitives.mjs` as *"deferrable as-is, cleanly"* because the symbols are used inside a function. They are — but **both managers called that function at module scope**, so the barrel still reached `chromadb` through it. Deferring required making the function async and awaiting it at all 7 sites. Measured before implementing: no caller reads the return value, and all 4 script call sites are module-scope ESM where top-level `await` is legal.
2. **The premise had decayed and the ticket was corrected before this work started.** Its title claimed Data Sync *"still cannot run"* with 12 consecutive failures; the pipeline had been green for days behind the #16495 exception. Body and title were truth-folded in place with a marked correction; the architectural defect was unchanged.
3. **The AC's named risk materialised, and it was not a race.** Moving client construction into `initAsync()` broke six **capture-and-restore** sites across four specs — `const originalClient = ChromaManager.client` taken synchronously, then restored. A capture landing before the microtask snapshots `null` and the restore writes that null back *permanently*, so later readers see null even after awaiting `ready()`. Established by instrumentation (`isReady: true` with `client: null`), not inference. `cleanupChromaManager`'s truthiness guard had the same root cause and was **silently skipping cleanup**.
4. **7 pre-existing trailing-whitespace lines** stripped in `smart-search.mjs`; the whitespace lint is file-scoped, so touching the file surfaced them. `git diff -w` confirms that hunk is whitespace-only.
5. **The managers' own `this.client` reads were NOT safe by construction, and integration CI caught it — not me.** An earlier revision of this body asserted they were. They are not: they sit in *public* methods (`getCollection`, `getMemoryCollection`, `deleteCollection`, `checkConnectivity`) that nothing stops a caller invoking during boot; it held only while the client was built in `construct()`. Three Dockerized KB specs failed with `TypeError: Cannot read properties of null (reading 'getCollection')`. **The enumeration missed them for a structural reason worth recording: readers were found by grepping `ChromaManager.client`, so every internal `this.client` read was invisible to the search that was supposed to be exhaustive** — the population was inferred from the shape of the query rather than from the code. Eleven public entry points across both managers now assert readiness; `connect()` is excluded because it runs *from* `initAsync` and would deadlock.

## The Body-tier claim, verified against the whole Brain-only population

The sunset guard only ever tested `chromadb`. This PR claims something broader — *the Body tier can import the barrel again* — so that claim was checked against every Brain-tier-only package, derived from the manifests rather than from memory:

```
brain-only = package.brain.json devDependencies − (package.json deps + devDeps)
           = chromadb, better-sqlite3, @chroma-core/default-embed
```

Static import walk:

| entry | modules walked | chromadb | better-sqlite3 | @chroma-core/default-embed |
|---|---|---|---|---|
| `ai/services.mjs` | 267 | not reached | not reached | not reached |
| `ai/scripts/maintenance/syncGithubWorkflow.mjs` | 269 | not reached | not reached | not reached |
| **positive control** — `defragChromaDB.mjs` | 39 | **REACHED** | not reached | not reached |

The positive control matters: a "not reached" from a walker never observed detecting anything proves nothing. `defragChromaDB.mjs` statically imports `chromadb` and the walk finds it, so the negatives above are meaningful. `better-sqlite3` was the one worth checking beyond the obvious — it has many direct importers elsewhere in `ai/`, and none is reachable from the barrel.

## Evolution

**The mechanism was established by instrumentation after two hypotheses died.** `await ready()` did not fix it, and `resetMemoryCoreLifecycle` proved not to touch `.client`. Reading `core.Base:305-317` showed `#readyPromise` cannot resolve before `initAsync` completes — which meant the reasoning was still guesswork, so the next step was to print what the assertion actually saw. `isReady: true` with `client: null` killed every remaining hypothesis in one line and pointed straight at a post-init writer.

**Readiness is asserted at each reader's entry rather than traced through the call graph.** Reachability reasoning is exactly what has been wrong repeatedly in this area; an entry-point assertion is locally provable and survives a caller being added later.
