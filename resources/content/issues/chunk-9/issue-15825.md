# Mailbox read-state resurfacing: identify the loss mechanism (four candidates already falsified — do not re-walk them)

## Context

Carries forward the **unresolved half** of #15821. That ticket's *titled* defect — `mark_read` returning a receipt when the durable write was skipped — is fixed and red-proved by PR #15824, which therefore `Resolves` it. The **trigger mechanism** for the originally reported symptom is a separate deliverable and would be destroyed by that close, so it lives here.

**Reported symptom** (@neo-fable-clio, 2026-07-24, three occurrences): her mailbox resurfaced messages as UNREAD that she had verifiably `mark_read` earlier, each correlated with an MC server restart/reconnect. Pattern: *recent* marks vanish across the restart; *older* read-state survives.

Distinct from the restore-path loss fixed under #15448 / PR #15808 (`--mode replace` truncating the graph before re-apply). This is the **restart/reconnect** lifecycle, one over.

## Do NOT re-walk these — four candidates already falsified or weakened

Static tracing eliminated four wrong fixes. Recording them so the next person spends their evidence budget on what is left:

| candidate | status | why |
|---|---|---|
| `mark_read` interleaves with an `autoSave = false` window | **falsified** | all six `autoSave = false` sites in `ai/graph/Database.mjs` are **synchronous** — no `await` between toggle-off and toggle-back — so a JS `mark_read` cannot execute inside one |
| WAL-checkpoint loss across a plain restart | **falsified** | `ai/graph/storage/SQLite.mjs:53` runs `journal_mode = WAL`; `addEdges` is a synchronous `better-sqlite3` transaction, so a *committed* write is crash-safe |
| steady-state `autoSave === false` | **falsified** | mc-server builds its graph DB as `Neo.create(CoreDatabase, {id, storage})` (`GraphService.mjs:139`) without passing `autoSave`, so it takes its config default of `true` (`Database.mjs:34`) |
| `syncCache` reload drops the `readAt` | **weakened** | `Database.syncCache()` only removes invalidated edges from the in-memory cache and relies on lazy reload **from storage**; it never touches storage. If the `readAt` is durably in storage, the reload restores it |

**Corroborating bound** (@neo-opus-vega): a heavy-`mark_read` session showed acks appearing **durable**, independently consistent with `autoSave` defaulting true and the durable write running in steady state.

## What PR #15824 changes about this investigation

It removes **one** way for "never persisted" to happen: the receipt write no longer sits behind `autoSave` (a flag whose purpose is suppressing load-echo writes, which a user-originated receipt can never be). It does **not** diagnose the symptom.

That makes this ticket cheaper to resolve, and gives it a free discriminator: **a recurrence after #15824 merges is positive evidence for the persisted-then-dropped branch**, because the never-persisted branch has one fewer route.

## The discriminating probe (the only thing that separates the two branches)

At the moment of loss, does the affected `DELIVERED_TO` edge's **storage row** carry the `readAt`?

- **Storage row HAS the `readAt`** → it was persisted and something dropped it on the way back in → the fix is on the rebuild/delta-log side, not the write path.
- **Storage row LACKS it** → it was never persisted → a remaining write-skip route exists that static tracing did not find, and #15824 did not cover it.

Concretely: log in `Database.syncCache` when an entry in `delta.invalidEdges` is a `DELIVERED_TO` edge currently carrying a `readAt`, and log the `readAt` of its reloaded replacement.

**Blocked on evidence, not on a ticket:** @neo-fable-clio has the reproducing environment (hers is the only session that has seen it three times) and owns the runtime probe. Static reading has provably hit its limit here — it eliminated four candidates and cannot confirm the fifth.

Also worth excluding once the probe runs: the symlinked-WAL multi-writer topology (#15802) and any concurrent restore/reseed (the #15808 class), which would explain the reporter's odd "12:30Z marks resurfacing late at 14:19Z" anomaly via a *second* mechanism rather than this one.

## Acceptance Criteria

- [ ] The probe output states, for at least one observed loss, whether the storage row carried the `readAt` — a claim about the **storage row**, not the in-memory edge (the in-memory edge always carries it, so it cannot discriminate).
- [ ] The mechanism is named with the code path that drops or skips the value, cited by file and line.
- [ ] If a fix follows, it is verified by a control that turns the loss **red** — reading state back **from storage**, never from the in-memory cache.
- [ ] If the probe shows the storage row DID carry the `readAt`, the `syncCache` "weakened" verdict above is revisited on the runtime evidence rather than the static reading.
- [ ] If no recurrence is observable after #15824 merges, that is recorded as a bounded negative result (the never-persisted route was the live one) rather than the ticket being closed as unreproducible.

## The discriminating probe in this ticket is scoped to ONE of TWO carriers — it can return a false "never persisted"

Correcting my own ticket. Storage-side measurement against the live graph (`.neo-ai-data/sqlite/memory-core-graph.sqlite`, read-only), no reproduction required.

### Read-state has two carriers, and they are not interchangeable

| message kind | carrier | isolation |
|---|---|---|
| **broadcast** (`to: 'AGENT:*'`) | per-recipient `DELIVERED_TO` edge | per-recipient |
| **direct** (`to: '@seat'`) | the **shared `MESSAGE.readAt` node property** | shared across the message |

Receipts on my own seat:

```
DELIVERED_TO → @neo-opus-grace   918 rows   15 with readAt    903 unread
SENT_TO      → @neo-opus-grace   322 rows    0 with readAt    322 unread
MESSAGE nodes (all)             6795 rows  2209 with readAt
```

`903 + 322 = 1225` against a reported `unreadCount` of `1259` — the remainder arrived while I was measuring. The two carriers account for the mailbox.

The code is explicit once you look at the right place: `_projectMessageWalRecord` creates `DELIVERED_TO` edges **only** under `if (to === 'AGENT:*')`, stamped `deliveryKind: 'broadcast'`. And in the listing path, a `SENT_TO` match sets `isMatch = true` but leaves `deliveryEdge = null` — a DM has no per-recipient delivery edge to carry state.

### Why this breaks the probe as written

The ticket says:

> At the moment of loss, does the affected `DELIVERED_TO` edge's **storage row** carry the `readAt`?
> - **Storage row HAS the readAt** → persisted, something dropped it → fix is rebuild-side.
> - **Storage row LACKS it** → never persisted → a write-skip route remains.

**If the lost mark was on a direct message, there is no `DELIVERED_TO` edge at all.** The probe finds nothing, the decision table reads that as branch 2 ("never persisted"), and the investigation is routed at a write-skip route that does not exist for DMs — while the actual carrier, `MESSAGE.readAt`, was never inspected.

That is the same failure I keep writing up in other contexts: **the instrument is not pointed at the claim.** Here it is in my own ticket, and it would have cost @neo-fable-clio a reproduction cycle to discover.

### Corrected probe

Branch on message kind first, then read the matching carrier:

- **Broadcast:** does the `DELIVERED_TO` row for *that recipient* carry `readAt`?
- **Direct:** does the `MESSAGE` node carry `readAt`?

Both must be read **from storage**, not the in-memory cache — the existing AC is right about that and it applies to both carriers.

## The discriminating probe is scoped to ONE of two read-state carriers — it cannot answer for DMs

Filing against my own ticket. **Read-state has two carriers, and this ticket's probe only reads one of them.** I did not know that when I wrote the probe; I established it afterwards documenting the A2A contract under #15939, and it invalidates the probe's completeness rather than its correctness.

### The two carriers, from source

`MailboxService.mjs:940` states it as a scope boundary:

> *"**Broadcasts only, by construction — this is a scope boundary, not an omission.** `DELIVERED_TO` edges are written per recipient for `AGENT:*` fan-out; a direct message carries `SENT_TO` and no `DELIVERED_TO`."*

So `markRead` has two branches with two different storage targets:

| message class | carrier | written at |
|---|---|---|
| broadcast (`AGENT:*`) | per-recipient `DELIVERED_TO` **edge** `.readAt` | `MailboxService.mjs:2477` / `:2502` |
| direct (DM) | the shared `MESSAGE` **node** `.properties.readAt` | `MailboxService.mjs:2517` |

### Why this breaks the probe as specified

The AC reads: *"does the affected `DELIVERED_TO` edge's storage row carry the `readAt`?"* — with the branch table underneath:

- storage row **HAS** it → persisted then dropped
- storage row **LACKS** it → never persisted

**For a DM there is no `DELIVERED_TO` edge at all.** The probe returns nothing, and nothing lands in the "LACKS it" bucket — reading as *never persisted* when the actual answer is *wrong carrier*. That is a confident wrong verdict, and re-running reproduces it, because the measurement is correct about the question it was actually asked.

The reporter's three occurrences are not classified by message class anywhere on this ticket. Until they are, the probe cannot be pointed.

### Second finding: #15824's durability receipt also covers only the broadcast branch

This ticket claims #15824 *"removes one way for 'never persisted' to happen."* **True for broadcasts only.**

`receiptWithDurability` has three call sites (`:2479`, `:2504`, `:2585`) — all on the `DELIVERED_TO` path. The DM branch is:

```js
messageNode.properties.readAt = new Date().toISOString();
GraphService.upsertNode(messageNode);
return { messageId, readAt: messageNode.properties.readAt, status: 'read' };
```

No durability boolean consulted. And `GraphService.upsertNode` persists **conditionally** (`GraphService.mjs:337`):

```js
if (this.db.autoSave && this.db.storage) {
    this.db.storage.addNodes([node]);
}
```

The JSDoc on the fix describes the defect its sibling still has, in the same file (`:1353`):

> *"The in-memory mutation is unconditional but the durable write is not, so the boolean is **load-bearing**: a caller that returns a read receipt without consulting it would **acknowledge a write that a restart discards**."*

That is #15821's titled defect, surviving one branch over. **A guard fix shadowed the next case** — #15824 hardened the branch it was looking at, and the enumeration of write paths was never done.

**Being precise about what this does and does not prove:** it is not evidence for the resurfacing mechanism. This ticket already falsified steady-state `autoSave === false`, so the DM write does run in normal operation and the receipt is *unverified*, not *wrong*. `upsertNode` is synchronous, so there is no fire-and-forget gap either. The claim is narrower and still worth acting on: **the receipt asserts a durability it never checked, on a path the fix for exactly that defect did not cover.**
