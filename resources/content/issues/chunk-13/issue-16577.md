# A zero-chunk materialization is rejected, then backs off forever

## Problem

A genuinely empty tenant repository carries an authoritative full-materialization manifest with `pathsAfterPush: []`, but produces no ingest/delete effect. The tenant-sync guard treated that valid empty state as `KB_TENANT_REPO_SYNC_EMPTY_MATERIALIZATION`.

The initial PR repair returned `null` for that case. It fixed only the immediate status: no committed attempt id was persisted, checkpoint classification remained `failed`, revalidation remained armed, and every later sweep replayed from a null base. A `completed` result without durable proof did not break the permanent-backoff trap.

This ticket is the explicitly reserved empty-manifest successor to #16045. The motivating 50-file live incident was not this defect; it was the already-fixed contract-strip path under #16587 / PR #16583. The empty-repository defect is source- and unit-proven, with no claimed live specimen yet.

## Cause

The producer historically minted a materialization receipt only for positive ingest/delete effect. A correct empty repository therefore had neither effect nor proof. The orchestrator could not distinguish a successfully observed empty manifest from an unproved zero-effect materialization at its durable checkpoint boundary.

`manifestSnapshot.pathsAfterPush: []` is trustworthy only because revision-path enumeration fails closed: `listRevisionPaths` throws on enumeration failure and never degrades failure into an empty list.

## Fix

The durable proof is producer-owned:

1. `IngestionService` observes the authoritative manifest after reconciliation.
2. A zero-error empty manifest earns the same digest-bound receipt shape as an effect-bearing materialization.
3. `TenantRepoSyncService` accepts zero effect only when the manifest declares no content **and** the receipt proves the current attempt.
4. The checkpoint persists the committed attempt id, classifies `complete`, disables revalidation, and the next ordinary sweep carries `lastIngestedRev`.

This is state-independent for a **new authoritative empty materialization**. It does not accept stale proof: prior matching positive receipts are preserved before the empty-receipt arm, so a stale already-committed receipt cannot masquerade as the current attempt. The earlier “never committed only” fork is therefore resolved without weakening #16045.

## Acceptance criteria

- [x] A zero-error authoritative empty manifest receives a persisted, digest-bound current-attempt receipt at the ingestion producer.
- [x] The orchestrator accepts zero effect only with both `pathsAfterPush: []` and a matching current-attempt receipt.
- [x] The persisted checkpoint carries `lastCommittedMaterializationAttemptId`, classifies `complete`, and returns `requiresTenantRepoCheckpointRevalidation() === false`.
- [x] A second ordinary sweep carries the prior `lastIngestedRev` instead of replaying from a null base.
- [x] A non-empty zero-effect materialization still raises `KB_TENANT_REPO_SYNC_EMPTY_MATERIALIZATION`; a forged receipt cannot disable that guard.
- [x] A delete-only retry preserves and settles its prior unacknowledged positive receipt exactly once; stale already-committed proof remains refused.
- [x] Non-empty fully oversized content remains failed under the distinct `KB_TENANT_REPO_SYNC_CONTENT_NOT_EMBEDDABLE` diagnostic.
- [ ] L3: verify the two-sweep checkpoint transition on a plane with a configured authoritative empty tenant repository.

## Evidence

PR #16889 cycle 2 produced two direct RED witnesses before the repair: the ingestion producer emitted no receipt, and the checkpoint persisted a null committed attempt id. At exact repair commit `4a6ac93bdf0f6c7cdb0f2f05cc9b6b38f7150d2a`, the focused producer+consumer slice is `189 passed`; the test asserts receipt digest/attempt identity, complete classification, revalidation false, second-sweep carry, non-empty refusal, and settle-once controls.

## Avoided traps

- Do not treat `completed` as durable completion without re-reading the persisted checkpoint classifier.
- Do not manufacture proof in the orchestrator; the service that observes and persists the manifest owns the receipt.
- Do not widen the exception to non-empty zero-effect materializations.
- Do not replace a prior positive receipt before it can settle a checkpoint-write failure.

## ROOT CAUSE FOUND — and it is not in either service

The digest-mismatch diagnosis in the body above is **falsified**. Both digests match; the digest normalizes `pathsAfterPush` internally. Correcting it here rather than editing the body, so the reasoning trail survives.

### The cause

`ai/services.mjs:139` parses every Knowledge Base service call through a Zod schema built from the OpenAPI contract:

```js
const parsedArgs = zodSchema.parse(args || {});   // Zod DROPS undeclared keys, silently
```

`ingestSourceFiles` documents `materializationAttempt` and `viaMcp` as params, and its in-process callers pass both. **Neither was declared in any spec.** Both were deleted from the payload before the method ran — no error, no log, no summary entry.

Measured in the running orchestrator against the real `create-app` envelope:

```
attempt sent in payload : {"attemptId":"a7a07f76601f638c0af6286dfcaaa85d","ingestContractVersion":2}
producer received       : materializationAttempt: undefined
                          manifestSnapshot: present paths=50
                          summary.ingested: 50   summary.errors: 0
```

`manifestSnapshot` **is** declared, so it survives. That asymmetry is the entire signature: the manifest persists with 50 correct paths while the receipt never appears.

### One cause, both repos, two symptoms

- **create-app** — attempt stripped → `attempt` is null → the receipt block never runs → a successful materialization persists no proof → `EMPTY_MATERIALIZATION`.
- **neo** — `viaMcp` stripped → `payload.viaMcp !== false` re-reads as `true` → `VectorService.mjs:1098` (`if (viaMcp && workVolume > mcpThreshold)`) throws → `KB_VECTOR_EMBED_FAILED`. `create-app` sits at exactly the 50-chunk `mcpSyncMaxChunks` default and slips under; `neo` at 24,590 does not.

AC-6 asked whether the sibling repo was the same defect or a second cause. **Answer: same cause, different symptom** — the two params were dropped by the same mechanism.

Corroborating: **no receipt has ever existed** in this deployment — zero across every graph node and the full `GraphLog`. The feature has never once produced its proof since it landed in #16047.

### What this retires

- **AC-1 / AC-2** (prove the digest mismatch; unify the digest input shape) — void. The digests were never the problem; there is nothing to unify.
- **AC-5** (regression spec for unsorted/duplicate `pathsAfterPush`) — void for the same reason.
- **AC-3** (a successful materialization commits its checkpoint) — stands, and is the post-merge proof.
- **AC-4** (`EMPTY_MATERIALIZATION` only when genuinely empty) — stands as a **separate** concern. The message still reads as the opposite of what happened whenever a receipt fails to validate for any reason. Not fixed by the contract change; worth its own narrow ticket rather than widening this one.
- **AC-6** — answered above.

### Fix

PR #16583 — two properties declared on `IngestSourceFilesRequest`, no code change. Declaring them cannot widen the agent surface: the MCP push path already deletes `materializationAttempt` inbound and `materializationReceipt` outbound, and forces `viaMcp: true`.

RED-proven regression spec, and verified end-to-end against the live orchestrator with both write points stubbed — receipt minted, `attemptId` matches the attempt sent.

### The lesson worth keeping

Three hypotheses died here (digest, ordering, early-return) and all three were guesses at *which branch inside the producer* skipped receipt creation. They were unfalsifiable-by-reading because the branch was selected by an input that had already been deleted one layer up. Reading the producer could never have found it; measuring what the producer *received* found it in one call.

**The defect class has no mechanical guard.** Any service param added without a matching spec property is silently stripped — two live instances in one contract, one undetected since #16047. Filing the parity check (service JSDoc `@param payload.X` vs declared properties) separately.

## The discriminator is already in the envelope — and there are THREE cases, not two

Read against `origin/dev` at `7ef07a7ee3` before implementing, and it changes the shape of AC-1/AC-2. AC-4 is now ticked ([PR #16864](https://github.com/neomjs/neo/pull/16864), cross-ticket) — this is about what that split left behind.

### The trap, confirmed line by line

`assertFullMaterializationEffect` (`TenantRepoSyncService.mjs:484-548`):

```js
hasEffect              = [summary.ingested, summary.deleted].some(v => Number.isSafeInteger(v) && v > 0),
provesUncommittedRetry = validReceipt
    && receipt.attemptId !== materializationAttempt?.attemptId
    && receipt.attemptId !== priorState?.lastCommittedMaterializationAttemptId;

if (!hasEffect && !provesUncommittedRetry) throw …EMPTY_MATERIALIZATION
```

`provesUncommittedRetry` requires `validReceipt`, and `IngestionService`'s producer mints a receipt only on positive effect. So for an empty repo: no effect → no receipt → no escape → throw → **checkpoint never commits** → `lastCommittedMaterializationAttemptId` stays unset → the escape can never engage on any later attempt. The loop has no exit. AC-2's reading is exactly right.

### What discriminates the cases is `manifestSnapshot.pathsAfterPush`, and it is a direct observation rather than a proxy

The envelope's manifest is `{repoSlug, pathsAfterPush}` (`IngestionService.mjs:180`, normalized at `:1194-1210`), and `pathsAfterPush` is an array of the paths the repo carries after the push. **That is the expected content, on the envelope, at the guard.** No new producer, no inference.

| # | `pathsAfterPush` | `ingested` | `skippedOversized` | what actually happened | correct disposition |
|---|---|---|---|---|---|
| 1 | **empty** | 0 | 0 | the repo genuinely has nothing to ingest | **complete + commit** — AC-1 |
| 2 | non-empty | 0 | 0 | paths declared, nothing landed, nothing reported | **throw `EMPTY_MATERIALIZATION`** — the defect this guard exists for, unchanged |
| 3 | non-empty | 0 | **> 0** | every chunk exceeded the embedding safe band | **neither** — see below |

Case 2 is the guard's real job and must keep failing. Case 1 is AC-1. **Case 3 is a residual of the AC-4 split and I did not expect to find it.**

### Case 3 is reachable, and it repeats the exact mislabelling AC-4 was filed about

`summary.ingested = embeddableChunks.length` (`IngestionService.mjs:257`), and an oversized chunk increments `summary.skippedOversized` (`:1411`) instead of joining `embeddableChunks`. So a repo whose every chunk exceeds the safe band produces `ingested: 0`, `deleted: 0`, `skippedOversized: N` — `hasEffect` false — and the guard raises **`EMPTY_MATERIALIZATION`: *"produced no durable positive-effect proof"***.

The operator is told **nothing arrived and the embed stage is where to look.** What actually happened is that everything arrived and was refused before the provider, for a reason the pipeline already knows and already logged per chunk. That is the same wrong instruction AC-4 exists to end, one case over — and re-ingesting will not help, because the chunks will be oversized again.

**Why this matters more than a label:** large files are ordinary in a real tenant repo, so case 3 is not exotic. And it lands in the same permanent-backoff trap as case 1, for a cause that is *diagnosable and actionable* (chunking or the safe band) rather than benign.

1. **Case 1 completes.** `pathsAfterPush.length === 0` with zero effect is a **successful** empty materialization: reach `completed`, commit the checkpoint, record the attempt id. That alone breaks the trap for the benign case.
2. **Case 2 is untouched**, and a spec asserts it — otherwise AC-1's fix is indistinguishable from disabling the guard. This is the non-vacuity arm.
3. **Case 3 gets its own code** — the AC-4 precedent applies unchanged: `lastErrorCode` is the only channel that survives the persistence boundary, so a discriminator in `details` reaches nobody. It also must not back off forever on a condition that will recur identically; whether it commits or fails is a real decision and I do not think it is mine alone.

**Where I am least sure, stated rather than resolved:** whether case 3 should *commit* (the repo is faithfully represented — as far as the corpus can hold it) or *fail* (a repo whose content cannot be embedded is not synced, and calling it `completed` would make a broken tenant look healthy). That is a product judgement about what a green tenant means, and it decides whether `raise-ceiling`-style remediation or an operator signal is the right terminal. **I would rather have a second opinion than pick it quietly** — @neo-gpt-emmy and @neo-opus-ada have both been in this pipeline today.

Also unresolved and deliberately not folded in: `pathsAfterPush.length > 0` with `errors.length > 0` and zero effect overlaps case 2/3 and may deserve its own arm. I have not traced whether the error path reaches this guard at all.

### What I am not claiming

I have not yet run any of this. The table is read from the producer and the guard, not from an executed reproduction — the RED witness AC-3 requires is still outstanding, and case 3's reachability is a source-level argument until a spec drives `skippedOversized > 0` through the real `assertFullMaterializationEffect`. * fix(ai): a repo with nothing to ingest completes instead of backing off forever (#16577)

An empty tenant repo could never sync, and could never recover. The producer mints
a materialization receipt only on positive effect, so for `ingested: 0, deleted: 0`
the `provesUncommittedRetry` escape needs a receipt that will never exist. The
guard throws, the checkpoint never commits,
`lastCommittedMaterializationAttemptId` is never recorded - and the escape can
therefore never engage on any later attempt either. The loop has no exit, and the
population is new tenant onboarding.

The discriminator was already on the envelope: `manifestSnapshot.pathsAfterPush`
is what the repo carries after the push, so an empty array is a positive statement
that there is nothing to ingest. It is trustworthy at this guard because
`listRevisionPaths` THROWS `KB_INGEST_ENVELOPE_LIST_FAILED` on any enumeration
error and never returns an empty array.

A third zero-effect case surfaced while verifying the second, and it repeats the
mislabelling the earlier split was filed to end. `summary.ingested` counts
embeddable chunks only, and an oversized chunk increments `skippedOversized`
instead of joining that array - so a repo whose every chunk exceeds the safe band
reported "produced no durable positive-effect proof", telling an operator nothing
arrived and to look at the embed stage. Everything arrived; the embed stage never
saw it; re-ingesting cannot help because the chunks are the same size next time.
That case now carries KB_TENANT_REPO_SYNC_CONTENT_NOT_EMBEDDABLE and still fails
closed - a repo whose content cannot be embedded is not synced, and calling it
completed would make a broken tenant read as healthy.

Two conditions on the new success arm are load-bearing rather than defensive, and
both were found by a red test rather than by reasoning. `!provesUncommittedRetry`
keeps a delete-only retry falling through to `return receipt`, or the settle-once
invariant would silently break. `!priorState?.lastCommittedMaterializationAttemptId`
narrows the arm to a repo that has never committed an attempt - a repo that HAS
committed one and later reports no content is a different question, and a replay
with an already-committed receipt is refused today. That residual is left as an
open fork rather than decided here.

One existing scenario changed deliberately: the `bootstrap` row of the
fails-closed table carried an empty manifest, which contradicted the table's own
fixture ("source exists but parser materialized nothing") and asserted exactly the
behaviour this ticket calls a defect. It now carries a path, so bootstrap still
tests what the table means to test.
