# Tear-out vessel renders its pane unstyled — the popout shell drops the workstation theme

## Context

Operator glitch-review of the first film draft (v0 cut from take-14, film lane `#15252` → `#15912`) called it directly: "popup window misses styling." The take-14 footage shows it unambiguously — the in-window metrics pane is the fully styled card (dark panel, LIVE badge, chart glyph, type hierarchy), while the SAME live pane inside its tear-out vessel renders as bare unstyled text lines ("LIVE METRICS / 99.9 / System Metrics / system envelope stableLIVE") on a default background. Worker-truth is intact (the pane is the same live instance — object-permanence assertions pass, the feed keeps streaming); only the vessel DOCUMENT's presentation layer is missing.

## The Problem

The `?popout=` vessel shell is a pure-pane-host: it deliberately owns no workspace document and hosts the traveling pane bare. But "bare of workspace chrome" must not mean "bare of THEME." A newborn vessel window is a fresh browser document — the workstation main window carries its theme class(es) (`neo-theme-neo-dark` at minimum) plus the app's SCSS on its own document, and whatever propagates that onto vessel windows is not doing so for the workstation's tear-out flow. Every publishable film take is blocked behind this: the tear-out is the film's money shot, and the vessel is the thing it births.

Not yet root-caused (deliberately): candidate layers, in the order I would falsify them —
1. the vessel viewport/shell never applies a theme class to its body/root (dockdemo's `?popout=` shell may apply themes via a path the workstation composition doesn't exercise);
2. theme CSS files load per-window and the vessel document's stylesheet set is incomplete (dev-mode per-window CSS loading);
3. `DockVesselEmbodiment` mounts the pane before/without the theme wrapper the pane's SCSS scopes under.

## The Architectural Reality

- `apps/workstation/view/Viewport.mjs` — the `?popout=` vessel-shell mode (workstation side, shipped on PR `#15840`).
- `src/dashboard/DockVesselEmbodiment.mjs` — carries the live pane into the vessel.
- `apps/workstation/view/Workspace.mjs` `setWorkspaceTheme` — the main-window theme path (scene-1's flips); whatever it writes never reaches vessel documents.
- Sibling precedent: dockdemo's popout shell + DemoB vessel flows (`apps/dockdemo`) — verify whether they exhibit the same gap or carry a theme-propagation step the workstation composition missed.
- Evidence: take-14 footage frames (film lane production record; worker-truth green during the take — presentation-only defect).

## The Fix

Falsify the three candidates in order; the likely shape is the vessel shell applying the host's CURRENT theme at embodiment time (and tracking subsequent theme changes — a theme flip while a vessel is open must reach every connected window, which is exactly the multi-window claim the film makes in its theme beat).

## Root cause — and it is none of the three candidates

**It is not a theme-propagation defect at all. The theme propagates correctly. It is a design-token *bridge scope* defect.**

Receipts below are from a live two-window run against the dev server on `dev@a47edbdf3b`, not from reading.

### Candidates 1 and 2 are empirically falsified

Booted `apps/workstation/index.html?popout=probe` and inspected the vessel document directly:

```
bodyClass : neo-mouse neo-body neo-theme-neo-dark neo-body-viewport   ← theme class PRESENT
bodyBg    : rgb(14, 15, 13)                                           ← themed, not default
sheets    : 67  (src/Global, theme-neo-dark/Global, theme-neo-light/Global,
                 grid/Container, tab/Container, button/Base, list/Base, …)
```

- **Candidate 1 (vessel never applies a theme class) — FALSE.** `Stylesheet.addGlobalCss()` runs per main thread and does `document.body.classList.add(themes[0])`; the vessel window is a normal Neo boot and gets it.
- **Candidate 2 (per-window stylesheet set incomplete) — FALSE**, and I tested the case that would most plausibly break it. Re-ran with the vessel as the **second** window joining an already-booted app (`cssMap` is keyed per `windowId`, so a late joiner starts empty): **67 sheets, `hasGrid: true`, `hasTab: true`, body themed.** Late-join loads fine — `afterSetWindowId` → `insertThemeFiles` fires for the traveling component, and `container/Base.mjs:317` (`item.windowId = value`) cascades it to descendants.
- **Candidate 3 (mounted without the wrapper its SCSS scopes under) — closest, but the wrapper is not a theme wrapper.** `DockVesselEmbodiment.mjs` has zero theme references; nothing about the embodiment is wrong.

### What is actually broken

The workstation's tokens live in **two layers at two different scopes**:

```scss
/* resources/scss/theme-neo-dark/apps/workstation/Viewport.scss:1 */
:root .neo-theme-neo-dark {          /* GLOBAL — reaches the vessel */
    --workstation-panel: #141a23;
    --workstation-line : #262f3d;
    …
}

/* resources/scss/src/apps/workstation/Workspace.scss:5-168 */
.workstation-workspace {             /* ← the vessel has NO such ancestor */
    --grid-container-cell-background-color: var(--workstation-panel);
    --grid-header-button-background-color : var(--workstation-panel-2);
    --tab-strip-background-color          : var(--workstation-panel-2);
    …~30 declarations
}
```

The second block is the **bridge**: it translates the app palette into the component tokens `grid.Container` / `tab.Container` actually read. It is scoped to `.workstation-workspace`.

The vessel hosts the pane under `.workstation-viewport.workstation-popout-host` — `Viewport.mjs:51-53` adds the popout cls and returns **without mounting `Workspace`**, by design. So there is no `.workstation-workspace` ancestor, the bridge never applies, and every grid/tab token falls back to its stock Neo default.

**This predicts the footage exactly:** structure and layout survive (those CSS files are loaded — confirmed, 67 sheets), while all colour/background/border values revert to defaults. "Bare unstyled text lines on a default background" is what a correctly-loaded component looks like with its token bridge missing. A missing *theme* would have produced a light-themed card; a missing *stylesheet* would have produced no layout at all. Neither matches; a missing *bridge* does.

### Fix shape

Hoist the bridge block from `.workstation-workspace` to **`.workstation-viewport`**. Both boot modes carry that class (`Viewport.mjs:31`), so the layering becomes coherent — global palette (`:root .neo-theme-*`) → viewport-level bridge → component consumption — and the vessel inherits it without pretending to be a workspace. Adding `workstation-workspace` to the popout host would also work but conflates "is a workspace" with "provides tokens", and the vessel deliberately is not one.

AC2 (theme flip reaches all windows) should follow for free once the bridge is viewport-scoped, since the palette is already keyed on the per-window body theme class — but that is a claim I will prove, not assume.

### On the ACs I can and cannot close

AC3 is delivered above. AC4 (spec-side tripwire) is mine and lands with the PR — a computed-style assertion on a vessel-hosted pane, which is strictly better than a class check: a class check would have passed throughout this entire bug, since the theme class was never missing.

**ACs 1 and 2 require headed verification under the film profile, which I cannot produce headless.** I will hand the branch over green on everything else rather than claim a ceiling I did not reach.

The `.workstation-workspace` scope was correct when the workspace was the only host; the vessel is the first consumer that is deliberately *not* a workspace, which is exactly the kind of thing that only shows up once frames exist.
