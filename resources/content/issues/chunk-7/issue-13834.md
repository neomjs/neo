# Idle-window starvation: per-message concept-extraction fires ungated gemma4 calls in parallel with exclusive-heavy tasks

## Context

Operator-flagged live reality (2026-06-21): *"the current scheduling is NUTS. there are no free slots and gemma4 gets hammered all the time… we NEED an idle window where gemma4 does not get hammered with other tasks in PARALLEL."* The idle window is the prerequisite for clean REM extraction **and** for any benchmarking/experiments (the gemma4-rem-benchmark + keep-alive-probe can't get a clean read while gemma4 is saturated). Sub of #13624 (orchestrator heavy-maintenance).

## Root Cause (V-B-A'd against `dev`)

`MailboxService.mjs:677` fires concept-extraction **fire-and-forget on every A2A message**:

```js
// 4. Auto-emit TAGGED_CONCEPT edges asynchronously without blocking delivery
SemanticGraphExtractor.extractMessageConcepts(body).then(concepts => {…});
```

And `extractMessageConcepts` (`SemanticGraphExtractor.mjs:403-441`) is a **gemma4 chat call** — `resolveGraphModelProvider(aiConfig)` + `provider.generate(messages)`, the *same* model as the tri-vector extraction, up to **2 calls/message** (maxRetries).

**Consequence:** the registry heavy tasks (summary / memory-summary-backfill / dream / golden-path) are all `exclusive-heavy` (serialized, one at a time, lease-gated). But this per-message path **bypasses that entirely** — no lease, no throttle, no backpressure — so it spawns gemma4 inference in **parallel** with whatever heavy task is running. The result is exactly the operator's symptom: gemma4 hit constantly, no idle gap.

**Vicious cycle:** the load scales with swarm A2A traffic — the more the maintainers coordinate (the entire point of the swarm), the more gemma4 calls fire. A single active session can fire dozens.

## The Fix (direction)

Move per-message concept-extraction **out of the fire-and-forget hot path** into a **scheduled, backpressure-aware registry task** (a `concept-extraction` lane alongside dream/summary): batch the unprocessed messages' extraction in a controlled window that respects `exclusive-heavy`. Then gemma4 runs one thing at a time **with gaps** — the idle window exists by construction.

Open design choices (for the implementation, not blocking the contract): batch trigger (count vs interval), a `conceptExtracted` marker on the MESSAGE node (mirror `graphDigested`), and whether to keep a fast non-LLM path (embedding/tag) for delivery-time and defer only the LLM concept-mining.

## Acceptance Criteria

- [ ] Per-message `extractMessageConcepts` no longer fires an unbounded gemma4 call from the `addMessage` hot path.
- [ ] Concept-extraction runs as a backpressure-aware scheduled task respecting `exclusive-heavy` (no parallel gemma4 with a running heavy task).
- [ ] A `conceptExtracted` (or equiv) marker prevents re-extraction; pending messages are batch-processed.
- [ ] Measurable idle gap in gemma4 utilization between heavy tasks (the operator's "free slot").
- [ ] No loss of `TAGGED_CONCEPT@0.8` auto-edges — they land on the scheduled pass instead of inline.

## Out of Scope

- The REM extraction input-shape (chunk-the-raw — #12439's OQ3, resolved separately).
- The tri-state digest-state-machine (#12839 → #13624 sub).
- Secondary parallel hitters (ask-synthesis) — separate audit if the idle gap doesn't materialize after this.
