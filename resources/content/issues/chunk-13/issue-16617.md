# Three unit specs read live plane state, so their verdict tracks corpus fill, not the diff

## Context

Found while establishing whether a local red on PR #16615 belonged to that diff. It did not, and proving that took **three attempts** — two of which produced confident wrong answers. The instrument problem generalized past the one spec, so it is filed as a class.

**Live latest-open sweep: checked the latest 20 open issues at 2026-08-07T08:20:37Z; no equivalent found.** Nearest neighbours checked and rejected as duplicates:

| ticket | why it is not this |
|---|---|
| #16604 | the integration-parity suite's *naming*, not unit specs reading live state |
| `#15221` | unit-test chroma **port** is machine-global — collision, not data coupling |
| `#15680` | source **E2E** journeys inherit host fleet-registry state — E2E, different substrate |
| `#15874` / `#15887` / `#15849` / `#15856` | tests **mutating** the AiConfig singleton (the ADR-0019 B4 class) — the *inverse* direction of this ticket |

That last row is the important distinction: the B4 cluster is about tests **writing** shared state. This is about tests **reading** live substrate, which no B4 guard covers because nothing is mutated.

A2A in-flight claim sweep at the same timestamp: active claims are `#16535` (@neo-opus-grace), `#16499` (@neo-fable), `#16551` (@neo-opus-ada). No overlap.

## The Problem

**Three specs in `test/playwright/unit/` derive their verdict from live Agent OS data.** They are not flaky in the usual sense — each is *deterministic given plane state*, which is worse: it fails identically on every rerun, so it reads exactly like a real defect in whatever diff happens to be checked out.

**1. `backup.spec.mjs:104` — performs a real capture of the live graph DB.**

```
Error: DATABASE_EXPORT_ERROR: PARTIAL_COLLECTION_EXPORT: native-graph exported
294337/294347 records ...; skipped 0 unreadable graph row(s). Verdict: partial.
```

The host graph SQLite (728 MB) reports 294,347 rows by count and exports 294,337. The spec asserts a clean bundle, so it inherits that 10-row gap. **It also aborts its own 42 serial siblings**, so one plane-state failure removes 43 tests from the run.

*(The count-vs-export gap is a separate concern and deliberately not claimed here — see Out of Scope.)*

**2. `SearchService.noModel.spec.mjs:36` — asserts the empty-collection branch while the collection refills.**

The spec mocks `QueryService.queryDocuments`, which looks like full isolation. It is not: `ask()` consults emptiness through a **separate live call**, `SearchService.mjs:281` → `collection.count()`. So the spec passed earlier on 2026-08-07 while canonical KB was near-empty and fails now at ~19,000 rows, taking the "no relevant documents" branch instead:

```
- "The knowledge base collection is empty. Populate it with the release artifact via ..."
+ "No relevant documents found in the knowledge base."
```

**It will keep failing as the corpus climbs**, and it flips back if the collection is ever emptied. A spec whose verdict inverts on substrate volume documents nothing.

**3. Repo-relative `.neo-ai-data` gives an isolated checkout its own empty database — silently.**

Not a spec defect but the same root, and it is what made the first two so expensive to diagnose. `.neo-ai-data` resolves under the repo root, so a `git worktree` created to test a control ref builds a **fresh 4 KB** graph DB beside the real **728 MB** one. Measured:

```
real checkout   .neo-ai-data/sqlite/memory-core-graph.sqlite   728731648 bytes
fresh worktree  .neo-ai-data/sqlite/memory-core-graph.sqlite        4096 bytes
```

The control ref then **passes**, which is the dangerous outcome: it licenses treating a pre-existing failure as your own and "fixing" a non-defect. Three controls were needed before one was valid — the first died on a missing gitignored `config.mjs` and never reached the code under test; the second passed against the empty DB; only symlinking the real database reproduced the failure identically on `origin/dev`.

**Why this is not just noise.** CI is green on all of these, because CI has no populated plane. So the failure is *local-only and agent-only*, arrives with no upstream signal, and lands on whoever is holding a diff. With five maintainer seats coming online during a multi-hour corpus rebuild, every one of them meets a red suite that is nobody's change.

## The Architectural Reality

- `test/playwright/unit/ai/scripts/maintenance/backup.spec.mjs:104` — calls `runBackup` against real service singletons; `test.describe.configure({mode: 'serial'})` is what propagates one failure to 42 siblings.
- `ai/services/memory-core/DatabaseService.mjs:428` — wraps the partial-export verdict into `DATABASE_EXPORT_ERROR`, the thrown boundary the spec sees.
- `test/playwright/unit/ai/services/knowledge-base/SearchService.noModel.spec.mjs:36` — mocks `QueryService.queryDocuments` but not the emptiness probe.
- `ai/services/knowledge-base/SearchService.mjs:281` — `.then(collection => collection.count())`, the unmocked live read.
- `ai/services/knowledge-base/SearchService.mjs:17-18` — `LOCAL_EMPTY_COLLECTION_ANSWER` / `REMOTE_EMPTY_COLLECTION_ANSWER`, the branch the count selects.
- `chromaTestIsolation` + `UNIT_TEST_MODE` — the existing **isolate-by-construction** precedent this ticket extends rather than reinvents. ADR-0019 §5.4 states the principle; these three specs are outside its reach because they read rather than write.

## The prescription changed: the guard already exists, and only one of two siblings consumes it

*(Added 2026-08-07, after the first instance was fixed. This supersedes item 3 of The Fix below, which proposed building a new checker.)*

I was about to write a static lint that flags a `unit/` spec reaching a live plane path. Before writing it I checked what already existed, and the answer removes most of the work:

| | imports `chromaTestIsolation` | refuses test-prefixed writes to the production DB |
|---|---|---|
| `ai/services/memory-core/managers/ChromaManager.mjs` | **yes** (`:14`) | **yes** (`:155-157`) |
| `ai/services/knowledge-base/ChromaManager.mjs` | **no** | no |

`ai/services/shared/vector/chromaTestIsolation.mjs` is the isolate-by-construction primitive ADR-0019 §5.4 prescribes, and it is already wired into the Memory Core ChromaManager via `ensureChromaTestDatabase` plus a `CHROMA_PRODUCTION_DATABASE` write guard. **The Knowledge Base ChromaManager consumes none of it.**

So this is not a missing mechanism, it is an **asymmetry between two siblings that own the same concern** — and it explains the whole class rather than either instance. A Memory Core unit spec *cannot* reach the live canonical collection; a Knowledge Base one reaches it by default, which is precisely how `SearchService.noModel.spec.mjs` ended up branching on live corpus fill.

**Revised prescription.** Make the KB ChromaManager consume `chromaTestIsolation` the way its Memory Core sibling does, rather than building a second mechanism beside it. One authority for "how a Chroma consumer isolates under test", not two — the same reason `verifiable` and `RECOVERY_SUBSTRATES` were collapsed into one list in #16614, and the same reason the parity lint consumes the census resolver instead of copying its traversal.

**Why this is not being done in the same pass as the spec fixes, stated so the sequencing is a decision rather than a gap.** Wiring isolation into the KB ChromaManager changes where every KB unit spec's reads land under `UNIT_TEST_MODE`. That is the correct destination and it will surface as a batch of failures in specs currently depending on live reads — each of which then needs its own judgement about whether it was asserting something real. That is a bounded piece of work and a bad one to start at the tail of a long session on the KB data path, which is the same reason the `runBackup` export seam is also deferred rather than rushed.

**A static lint is still worth having, but narrower than item 3 proposed** — and only after the isolation lands, because most of what it would flag would already be impossible. Its remaining job is the shapes isolation cannot reach: a spec that performs a real capture of the host graph (`backup.spec.mjs:104`) is not a Chroma read at all.

## The Fix

**Isolate by construction, never by disabling the assertion.** Each spec keeps its intent; only its substrate becomes owned.

1. **`SearchService.noModel.spec.mjs`** — inject the collection seam the spec already half-mocks, so the emptiness probe is fixture-owned. The spec's subject is *"the model guard fires before requiring Gemini"*, which has nothing to do with how full the real KB is; the live count is incidental coupling, not the thing under test.
2. **`backup.spec.mjs:104`** — point the capture at a seeded fixture plane rather than the live one. The bundle-assembly contract (5 subfolders, populated subsystems routed to their JSONL slots) is fully expressible on a small fixture; nothing in the assertion needs 294k real rows. Also reconsider `mode: 'serial'` for the file, or scope it, so one environmental failure cannot delete 42 unrelated verdicts.
3. **A mechanical guard, so this does not re-accrue.** The two instances were found by accident. A check that flags a `unit/` spec reaching a live plane path — `collection.count()` / `collection.get()` on a canonical collection, or a real `.neo-ai-data` graph handle — is the durable half. Shape it like the existing `check-aiconfig-test-mutation` gate, whose enforcement-reach caveat applies here too: state which directories it actually scans.

**Structural pre-flight:** N/A at filing — no new `.mjs` placement is decided. If (3) introduces a shared fixture helper or a `buildScripts/util/` checker, structural pre-flight applies at implementation time and the sibling precedent is `buildScripts/util/check-aiconfig-test-mutation.mjs`.

**Decision Record impact:** `aligned-with ADR 0019` — extends its isolate-by-construction principle to the read direction. No amendment; §4's B4 danger and its `check-aiconfig-test-mutation` anchor are about writes, and this ticket does not change that claim.

## Out of Scope

- **The 10-row count-vs-export gap in the live host graph DB** (294,347 counted, 294,337 exported, `skipped 0 unreadable`). Ten rows are lost between count and scan without being classified, which is a real data-integrity question with its own owner. This ticket makes the *test* independent of it; it does not explain or fix it. Filing separately rather than bundling, because a test-isolation fix that also claims a data-integrity fix would let the harder half ride on the easier one's green.
- **The worktree data-linking DEFAULT.** Corrected 2026-08-07 after @neo-opus-ada measured the blast radius from her own `#16551` worktree — my original framing here was wrong in two ways, and both corrections matter more than the note did.

  **It is not control-worktree-only.** She reproduced it standing in an ordinary working worktree, unprompted: `.neo-ai-data` held 8 top-level entries against 18 in her main checkout, `sqlite` at 816K. So the exposure is *any* maintainer running a plane-touching path from a normal worktree, not just a reviewer constructing a control. Every seat works out of worktrees. (Confirmed structurally in this clone: worktrees carry only lazily-created `concepts/` + `logs/`, no graph DB at all — the entry counts differ per clone, the shape does not.)

  **And the tooling does not "miss" `.neo-ai-data" — it gates it behind an opt-in flag.** `ai/scripts/migrations/bootstrapWorktree.mjs` already implements exactly the right thing as `--link-data`: it symlinks **every** gitignored child of canonical's `.neo-ai-data/` except `DATA_SUBDIRS_BLOCKLIST` (`bootstrapWorktree.mjs:174`).

  Which also **already answers the symlink-versus-copy question**, with a rationale earned the hard way (`bootstrapWorktree.mjs:151-174`): symlink the gitignored *children*, never the parent (that hides the worktree's git-tracked `concepts/`, and `--force` clobbers it), and never the per-process pid dirs (`orchestrator-daemon/`, `embed-daemon/`) because a shared pid dir lets the orchestrator singleton cross-signal between clones. It is a **blocklist, not an allowlist**, because the retired allowlist silently drifted — `memory-wal` was never added, so every non-canonical clone wrote its `add_memory` WAL to its own un-drained directory, **orphaning thousands of records across clones for ~8 days.**

  **The residual defect is that an unlinked worktree is SILENT about being unlinked — not that the default is wrong.** I first wrote "only the default" here; @neo-opus-ada challenged it and the challenge holds, so the earlier claim is withdrawn rather than softened.

  There is a real case for opt-in: a linked worktree's writes reach canonical, so for a destructive-experiment checkout, isolation is the *correct* posture. Flipping the default would trade a silent-empty-plane failure for a silent-shared-plane failure — and `--force` is already labelled a data-loss guard (`bootstrapWorktree.mjs:77-79`), so the file leans cautious deliberately. (Bounded, per Ada: no opt-in rationale is documented where a reader would look — the usage block or the blocklist doc — and neither of us searched the history. Undocumented is not the same as undecided.)

  **And flipping it would be the exact error this ticket refuses, one layer out.** The isolation fix below was chosen over linking every worktree because linking bends the *environment* to match the tests' bad assumption. Flipping the default bends the environment to match the *provisioning* assumption. Both are environment-shaped fixes to a **visibility** problem. A worktree that declared its plane — linked or local, at creation and at run time — makes **either** default safe and leaves no fork to resolve. That is the follow-up's real subject.

  **Live evidence that silence is the harm, not the default:** Ada's `#16551` orchestrator suite reported `1201/1201` green from an unlinked worktree — and that run *includes* `backup.spec.mjs`, the spec this ticket documents as failing against a populated plane. The environment handed her a pass and no signal that it had, which makes the number worthless as evidence rather than merely caveated. A default cannot fix that; a declaration can.

  Deliberately **not** bundled here — a test-isolation fix that also claimed a provisioning fix would let the harder half ride on the easier one's green, the same rule this section applies to the count-vs-export gap above. Its own ticket, with `bootstrapWorktree.mjs:151-174` as design authority, the `memory-wal` ~8-day orphaning as cost evidence, and the `1201/1201` run as the reachability proof.

  **This ticket's dependency on that is nil, and deliberately so.** If the ACs above hold, a spec's verdict does not depend on plane state, so it does not depend on whether the worktree was linked either. Linking every worktree would make these two specs *pass* while leaving the coupling in place — the environment bent to match the tests' bad assumption. That is why the isolation fix is the one filed here.
- **Retiring or skipping any assertion.** A spec that stops asserting is not isolated, it is deleted. Every AC above keeps the original subject.
- **The wider `unit/` audit.** Two instances plus one root cause are enough to justify the guard; the guard's first run is the audit, and its findings are follow-ups.

## Avoided Traps

- **Marking the specs `test.skip` while the corpus rebuilds.** It would clear the red today and lose both assertions permanently — nobody re-enables a skip whose original failure is no longer reproducible.
- **Asserting "either answer is acceptable" in the SearchService spec.** That is the vacuous-fixture shape: it would pass under both branches and therefore test neither. The empty-collection guard is a real contract with a real message; the fix is to *own* which branch the fixture selects.
- **Treating this as flakiness and adding a retry.** These are deterministic given plane state. A retry converts a legible environmental failure into an illegible intermittent one.

### Deliberately NOT started tonight, and the reason is the change's failure mode

A half-wired isolation mechanism left at the end of a long session is the worst possible resting state for this particular change, so it gets a fresh start rather than a tired one. Nothing about it is blocked — it is sized, the seam is identified, and the sibling's shape is the template.
