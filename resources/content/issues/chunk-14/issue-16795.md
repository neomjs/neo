# SyncService Stage 2 fails silently, so a green sync can mean a frozen graph

Related: #16794

## Context

`SyncService.sync()` runs two stages. Stage 1 emits the markdown mirrors and pushes them; **Stage 2** ingests them into the Native Graph. Stage 2 is wrapped in a `try/catch` that logs and continues:

```js
} catch (error) {
    logger.error(`[SyncService] Stage 2 Ingestion failed: ${error.message}`);
}
```

`ai/services/github-workflow/SyncService.mjs:571-584`.

The sync then computes `finalStats` and returns success. **Stage 1's outcome is the only thing that reaches the caller.**

This is the narrow, fork-free half of the defect measured in #16794. *Where* Stage 2 should run is a genuine design question with a divergence matrix and lives there. *That Stage 2 can fail without anyone learning* is wrong under every option on that matrix, and is why the defect went unnoticed.

Live latest-open sweep at 2026-08-09T14:1xZ: checked the latest 20 open issues; no equivalent found. A2A in-flight claim sweep: no claim on this scope.

## The Problem

**A pipeline whose success signal comes from its first stage cannot report the failure of its second.**

Observed on the local plane 2026-08-09: the hourly `chore(data): Hourly data sync pipeline update` commits land on time (13:38Z most recently) — Stage 1 is healthy and visible. Meanwhile the Native Graph has not ingested issue state for weeks: `issue-14613` reads `state: "OPEN"` in the graph while GitHub closed it 2026-07-18, and `issue-16630` has no node at all. Four of the six top-weighted Golden Path targets are closed issues.

Nothing surfaced this. The commits kept arriving, so the sync read green the entire time. It was found only by asking why the Golden Path was recommending finished work.

**The severity is the invisibility, not the outage.** A stale forecasting surface does not throw; it quietly recommends the wrong lanes, and every consumer downstream inherits that silently — the same shape as `#16208`'s *"reports healthy, serves empty collections"*.

## The Architectural Reality

- `ai/services/github-workflow/SyncService.mjs:571-584` — the swallowing `catch`; the three ingestion calls it guards are `IssueIngestor.ingestIssueStates()`, `.ingestDiscussionStates()`, `.ingestPullRequestFeedback()`.
- The dynamic `import()` inside the `try` is deliberate and documented: it keeps the `github-workflow` MCP server from loading SQLite/Chroma at boot. **That rationale is sound and must survive this fix** — the guard exists so a missing DB does not crash the server, which is a different concern from a *silent* ingestion failure.
- `finalStats` is assembled after the `catch` with no field describing Stage 2.

**The distinction this ticket rests on:** *non-fatal* and *unreported* are different properties. Stage 2 should stay non-fatal — a graph-ingestion failure must not lose the emitted markdown. It must stop being unreported.

## The Fix

Give Stage 2 an outcome the caller can see, and make it loud when it fails.

1. Record Stage 2's result in `finalStats` — attempted, succeeded, or failed with its reason.
2. The sync's returned status must not read as unqualified success when Stage 2 failed.
3. Keep the failure non-fatal and keep the dynamic import.

## Acceptance Criteria

- [ ] **A forced Stage-2 throw does not produce a success verdict.** Red witness: stub the ingestor to throw, run the sync, assert the returned status is not unqualified success. This test fails against current `dev`.
- [ ] **Stage 1's work is preserved when Stage 2 fails** — the emitted/pushed markdown is not rolled back or suppressed. Asserted as a control, so the fix cannot be "make it fatal".
- [ ] **Never-attempted is distinguishable from failed.** A sync that did not reach Stage 2 must not report the same shape as one whose ingestion threw — collapsing them recreates the ambiguity this ticket removes.
- [ ] **The dynamic import stays inside the guard**, and a spec pins it — the boot-isolation rationale at `:576-578` must not be lost to a refactor that hoists it.
- [ ] **Evidence level: L2.** Unit receipts close this; no live-deployment reading is required, because the property is about the return value rather than about any plane's state.

## Out of Scope

- **Where Stage 2 should run, and how the container gets fresh content** — #16794's divergence matrix. This ticket does not move Stage 2 or change its trigger.
- **Making Stage 2 fatal.** Explicitly rejected: a graph-ingestion failure must not cost the emitted markdown.
- **Backfilling the stale graph.** Running the ingestion is an operation, not a change.

## Avoided Traps

- **Deleting the `catch`.** It would make Stage 2 fatal and lose Stage 1's push — trading a silent failure for a louder, worse one.
- **Hoisting the dynamic import.** The comment at `:576-578` explains it prevents the `github-workflow` MCP server from loading heavy DB dependencies at boot. A fix that "cleans that up" reintroduces a crash-on-boot path.
- **Asserting only that the logger was called.** `logger.error` already fires today and the defect persisted for weeks — nobody reads it. The AC must bind to the **returned value**, which callers actually consume.

## ⚠️ Premise correction — my causal claim was wrong. @neo-gpt falsified it within the hour

**The defect this ticket fixes is real and the ACs stand. The reason I gave for why it went unnoticed is false**, and it is in the body above, so it needs correcting here before anyone builds on it.

I wrote that Stage 2 *"needs SQLite + Chroma, which a CI runner does not have, and it is wrapped in a `try/catch` that logs and swallows"* — i.e. that CI runs Stage 2, it fails, and the catch hides it.

@neo-gpt's D#16794 input states Stage 2 is **absent by design** in CI. Verified at source before accepting:

```
ai/scripts/maintenance/syncGithubWorkflow.mjs:56
  "The scheduled Data Sync pipeline invokes this CLI with `--emit-only`"
:134   emitOnly ? <emission path> : <full sync>
```

**CI never reaches Stage 2 at all.** The catch does not fire there, because the code path that contains it is never entered.

### What that changes, and what it does not

**Does not change — the ticket is still valid.** A Stage-2 failure that cannot be seen by the caller is wrong on its own terms, for any invoker that runs the full `sync()`. Every AC above holds unmodified, and the red witness (stub the ingestor to throw, assert the verdict is not success) still fails against current `dev`.

**Does change — the severity story.** I claimed the swallowing catch is *"why this went unnoticed for weeks."* It is not. The real reason is that **nothing invokes Stage 2 anywhere**: CI deliberately emits only, and the container that owns the graph never calls it. The catch is a latent hazard that would hide a *future* failure; it did not hide this one.

So this ticket is **preventive, not causal**. It should be picked up on that basis — and anyone triaging the stale Golden Path should not expect fixing this to explain, or repair, the incident that surfaced it. That repair lives in D#16794.

### Why I am flagging rather than quietly editing

The distinction matters for whoever takes it: a preventive fix and a causal fix carry different urgency, and a wrong causal story would make this look like the whole answer. It is not the whole answer — it is the half with no fork in it.
