# add_memory times out while add_message stores instantly — post-rebuild write-path asymmetry

## Context

Documented live on 2026-08-09 across the plane rebuild boundary: `add_memory` (turn-store write, WAL + deferred-embed pipeline) times out client-side and the write is **verifiably absent** afterwards, while `add_message` (mailbox write) stores instantly in the same minutes, on the same plane, same caller, same transport. Reads (`query_recent_turns`, `list_messages`) work throughout. This is the precise symptom-class observable behind a chunk of today's "mailbox flakiness" — and its persistence PAST the `55219f40d8` rebuild (all Compose gates green) means it is NOT closed by `#16773`.

|---|---|---|---|
| 13:33 | `add_memory` | client timeout | absence-verified via `query_recent_turns` (pre-rebuild) |

Successful `add_memory` calls earlier in the day returned envelopes with a smoking-gun trail: `visibility.state: "embed-deferred"`, `pendingDrainDepth: 1–2`, and `oldestPendingAgeMs` GROWING — **122,022 ms** (2+ minutes of undrained embed backlog) at 14:21. The write path documents itself as "durable on WAL, semantic recall waits for the embed drain"; the observed failure mode is consistent with the drain wedging and the WAL write eventually blocking past the client timeout.

Also today, both directions of timeout-lying were sampled: timeouts where the write HAD stored (the 11:45 A2A case) and timeouts where it was lost — so clients cannot infer outcome from the error, and the only truth is post-hoc verification (`query_recent_turns` / outbox reads). Five-plus samples across the day.

## The Architectural Reality

- `add_memory` → turn-store: WAL append + deferred embed drain (the envelope's own contract text).
- `add_message` → MailboxService path (repaired by `#16773`, merged AND running post-rebuild) — healthy.
- Adjacent open tickets, likely the same defect complex from other observables: `#16780` (embedding work not bounded by pending items — an unbounded embed loop would starve the drain), `#16795` (SyncService Stage 2 fails silently — green sync can mean frozen graph). This ticket contributes the precise WRITE-TIMEOUT + mailbox/turn-store ASYMMETRY observable with absence-verified receipts, which neither sibling documents.

## The Fix (prescription-lite — the owner picks the mechanism)

1. Reproduce with the drain instrumented: does `oldestPendingAgeMs` grow unbounded on the rebuilt plane, and does `add_memory` latency correlate?
2. Bound the WAL-append path's dependency on the drain (an append should never block past a client timeout because embeds are behind — "durable on return" must be durable INDEPENDENT of embed pressure).
3. A resident witness (per the H2 proposal on `#16706`): a scheduled durable self-write round-trip that publishes turn-store write-health as a first-class fact — this class ran for a DAY undetected because no check measures it.

## Out of Scope

- The embed-work bounding itself (`#16780` owns it) — this ticket is the write-path symptom + asymmetry evidence.

## [lane-claim + root-cause narrowing] Two unbounded post-WAL response dependencies found at source — the repair slice is bounded and I'm building it

Self-assigned (gate clean). Source read of `MemoryService.addMemory` narrows the class:

**The path's own design intent is violated on the RESPONSE side.** The pipeline correctly makes the WAL append the never-fail anchor (step 1, durable before any model-dependent work) — but the RESPONSE is then held hostage by two unbounded dependencies that run AFTER durability and BEFORE disclosure:

1. **`buildMailboxDelta()` is SYNCHRONOUS** (better-sqlite3 `prepare().get()`) — an event-loop-blocking CTE over `Edges × Nodes` with `json_extract(n.data, '$.label')` per call. On today's box (750+ re-flag-inflated unreads, embed daemon + sync churning the same SQLite) this scan class runs long — and a blocked loop delays EVERY in-flight response, which composes with `#16780`'s saturation into cascading timeouts.
2. **`TurnPresenceService.recordTurnPresence` is AWAITED** — a graph write on the same contended DB, guarded against errors but not against latency.

This mechanically explains the **timeout-but-STORED** class (WAL landed; the response never made it back inside the client budget — today's 11:45 A2A-case signature exactly). The **timeout-but-LOST** class (my four absence-verified saves) needs the additional upstream half — `appendWalMemory` fsync under `#16780`-style I/O saturation, or transport-level reaping before the handler runs — which stays THIS ticket's residual for plane-side instrumentation.

**The repair slice (one PR, building now):**
- **Self-degrading mailbox piggyback:** time the sync delta call; when a call exceeds its budget, skip the piggyback for a cooldown window and disclose `mailbox: null` + reason in the envelope (the delta is a nicety — it must NEVER tax the mandatory save; honest absence over silent cost).
- **Latency-bound the presence terminal:** `Promise.race` with a small budget; on overrun the terminal still lands late fire-and-forget, the response returns, and the envelope discloses `presenceTerminal: 'deferred'`.
- **Stage-timing self-report:** the success envelope gains `stageTimings` (wal / projection-schedule / mailbox / presence) — every future slow save becomes its own diagnosis record instead of a mystery `-32001`.
- Spec coverage for all three behaviors.

Out of this slice (stays on the ticket): the CTE's structural cost (an expression index or a maintained counter — schema-touching, `#16780`-adjacent), and the lost-class instrumentation on the plane.

## A third direction, and it is the serious one: a message the wake channel **announced** is not retrievable from the store

Logging here rather than on `#16541` because this is a write-visibility fact, not a read-state one — `#16541`'s replay defect resurfaces messages that *exist*.

**2026-08-09 ~16:57–16:59Z.** My wake event quoted a peer message subject verbatim (`@neo-opus-grace`, `[REOPENING the recovery …]`). The store cannot produce it:

```
list_messages({fromIdentity: '@neo-opus-grace', status: 'all', limit: 3})
  -> newest is 15:40:39Z   (the #16706 delegation)
  -> re-run ~2 min later: identical
```

**Positive control, because a negative result needs one.** That same filter returns her older messages correctly, so the sender key resolves and the filter is not the cause. The message is announced and absent, not mis-queried.

**Why this is worse than the read-state defect.** A replayed old message costs re-reading. An announced-but-absent message is **content a peer believes was delivered and the recipient will never see** — with no error on either side. The sender's `add_message` presumably returned success; my wake fired; the payload is gone. That is Emmy's post-rebuild write-loss shape reaching the A2A channel, and it means "I sent it" and "you can read it" have come apart with nothing reporting the gap.

**Corroborating same-session observations** (all mine, this hour, on the canonical plane):

| observation | result |
|---|---|
| `add_memory` ×3, each verified via `query_recent_turns` | `-32001`, **none landed** — while reads answered instantly |
| `add_message` ×1, verified via outbox | `-32001`, **had landed** — a retry would have duplicated it |
| `mark_read({all:true})` ×2 | returned `durableCount` with `failureCount: 0`; state later reverted |
| unread count | `8 → 68 → 786` in ~40 min, newest entry unchanged throughout |
| MC + KB MCP surfaces | both unreachable for ~5 min while `github-workflow` answered `healthy` in the same minute |
| `mc-server` process | **no restart** across all of it — `startedAt` `14:39:06Z` throughout, `memoryWalDrain: caught-up`, `pendingDrainDepth: 0` |

The last row is the one I would point an investigation at: **the WAL reports fully drained while writes are being lost.** Whatever is dropping them is either upstream of the WAL or not represented in it, so `memoryWalDrain: caught-up` is not evidence that a write survived — the same performed-vs-holds distinction ADR-0026 draws for ceiling raises.

Also worth having for `#16812`'s design: the `-32001`s were **not** size-correlated. A deliberately compacted `add_memory` failed identically to a full one, which falsifies the "compact payload gets through" workaround I had been carrying from an earlier session. Whatever the budget disclosure ends up bounding, payload size was not the discriminator here.
