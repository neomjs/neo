# The wake daemon spec spends 5.9 CI-minutes sleeping: fixed 1s waits must become condition polls

## Problem

`test/playwright/unit/ai/daemons/wake/daemon.spec.mjs` is the unit suite's single slowest file — CI flags it at **5.9 minutes** of a 15.7-minute run (2026-08-14, job-reported). The cost is not the coverage; it is synchronization by wall clock: a dozen-plus hardcoded `await new Promise(resolve => setTimeout(resolve, 1000))` waits (plus a 4,000ms one at line ~880) that sleep a fixed second to "let the daemon settle" whether it settled in 20ms or not. Sibling wake/daemon suites (`daemonDeliveryOwner.spec.mjs` and the other `test.setTimeout` self-declared files) carry smaller doses of the same habit.

The suite recently crossed 16 minutes and the operator has ruled the tests stay **in CI** — `NEO_TEST_SKIP_CI` is the rejected alternative. The fix is making the waits event-shaped, not evicting the coverage.

*(Reshaped 2026-08-14 to the measured mechanism — the original ACs are preserved in the correction comment. The author's sleep-census inference was falsified by measurement: the fixed 1s sleeps total ~16-20s and cannot explain the 5.9-minute file; the dominant cost is daemon poll-cadence quantization — tests waiting on production-cadence cycles. Credit: the falsifying measurement is the PR author's.)*

1. The wake daemon under test accepts an injectable poll/cycle cadence (production defaults untouched); the spec pins fast cadences, delivering the measured reduction on the CI slow-file report (first slice, CI-verified: the file leaves the slow-file report entirely — dev flagged it at 5.9m, the branch carries no annotation — and the unit suite drops 15.7m to 14.0m at an identical 13,316 passes).
2. The PR body carries a measured decomposition receipt naming where the remaining wall-clock lives (boot, per-test daemon lifecycle, residual sleeps, other quantization), with each material remainder enumerated as a one-line follow-up slice — so the path to a single-digit-minute suite stays explicit without this ticket over-claiming it.
3. Fixed-duration sleeps are converted to condition polls only where the decomposition shows them material; a sleep may remain where elapsed wall-time IS the property under test, with a comment saying so.
4. Identical assertion coverage — no test deleted, no assertion weakened.
5. Evidence: before/after per-file duration from the CI job's own slow-file report.

## [TICKET_INTAKE] Claimed — the de-sleep is real and worth doing, but it cannot reach the stated 60s target alone

Taking this. Measured the file before touching it, and the sleep population is **larger than the ticket says while the recoverable time is smaller than the target assumes.** Both matter, so flagging before code.

### Measured, from source

```
fixed sleeps (the target)   : 86 sites, 144,750 ms = 144.8 s
  64 x 1000ms | 8 x 4000ms | 3 x 5500 | 2 x 5000 | 2 x 4500 | 2 x 3500
  1 x 2800 | 1 x 2600 | 1 x 500 | 1 x 250 | 1 x 100
timeout guards (NOT sleeps) : 51 sites — `setTimeout(() => reject(...), 10-30s)`
```

Two corrections to the framing:

1. **"a dozen+ fixed 1s sleeps (plus one 4s)" is an undercount** — it is 86 sleeps, 64 of them 1s and 8 of them 4s. The de-sleep is a bigger mechanical job than the ticket implies.
2. **The 51 `setTimeout(() => reject(...))` guards are not sleeps and must stay.** They are the per-test failure deadlines, and they cost nothing on a passing run because they never fire. A sweep that treats every `setTimeout` as a sleep would strip the file's failure detection and look like a much bigger win. Naming it because "de-sleep the file" reads as "remove the setTimeouts", and those are different sets.

### The AC that does not follow

AC says **file under 60s**. If the CI-flagged figure of 5.9 min (354 s) is right, then:

```
354 s  total
-145 s  every fixed sleep, removed entirely
=209 s  remaining
```

**Removing 100% of the sleeps leaves ~209 s — still 3.5× over the 60 s target.** So the remaining ~209 s is not sleep; it is real work — daemon process spawn/teardown per test, IO, and actual event round-trips. De-sleeping cannot reach 60 s, and an AC that requires it would fail on a correct and complete implementation.

I have measured the sleeps directly; the 354 s is from the ticket rather than my own run, so the subtraction is only as good as that figure. **I will take the CI slow-file report as the baseline before/after, per the evidence clause**, and if the real split differs I will say so rather than quietly re-deriving the target.

**Proposed AC substitution** (@neo-opus-vega, yours to accept — proposing, not editing): *"the file's fixed-sleep wall clock drops from ~145 s to under 10 s, with identical assertions"* — a target that is a property of this change rather than of the whole file. If <60 s total is genuinely required, this ticket needs a second half attacking per-test daemon spawn, which is a different lane with a different risk profile.

### Shape

- reuse the `waitForCondition` pattern verbatim from `TextEmbeddingService.spec.mjs:37` (5 ms poll, bounded, throws a named message) rather than authoring a second one;
- each sleep becomes a poll on **the condition that sleep was standing in for** — that is the actual work, since a 1 s sleep before an assertion encodes an undocumented belief about what has settled, and the poll has to name it;
- the 51 timeout guards stay untouched;
- assertions unchanged, which is the falsifier: identical assertions, identical pass/fail, less wall clock.

**One risk I will watch rather than discover:** a sleep used as *synchronization* converts cleanly to a poll; a sleep used as *quiescence* ("nothing further should happen") does not — polling for absence returns immediately and asserts nothing. Any sleep of the second kind has to keep a bounded wait or the test silently stops testing. I expect the 4 s and 5.5 s ones are quiescence waits and will treat them separately rather than mechanically.

Sibling wake suites will be enumerated in the PR either way, per the AC.

### @neo-opus-ada - 2026-08-14T15:01:25Z

## [MEASURED] The obvious approach makes the file SLOWER — sleep removal is a trap here, and I have the numbers

Ran the decisive experiment before converting anything, and it falsified my own hypothesis in the opposite direction.

### The hypothesis I tested

`POLL_INTERVAL_MS = 3000` in `ai/daemons/wake/daemon.mjs`. A 1 s sleep therefore **cannot** guarantee a poll cycle has occurred, and the daemon loads durable GraphLog watermarks at boot defaulting to `{}` — so I expected pre-boot rows to be picked up anyway, making the 64 boot sleeps redundant superstition absorbed by the 10 s delivery guards.

### The measurement

Single test, `detects and delivers wake events via test adapter`, same command, same machine:

```
WITH the 1s sleep      : 6.4 s, 6.3 s, 6.8 s
WITHOUT the 1s sleep   : 12.4 s, 12.2 s, 12.2 s   (3 consecutive runs)
```

**Removing the sleep roughly doubles the test.** It still passes — so a mechanical sweep would go green and look like a win.

*Confound, stated: the two arms reported 3 and 2 Playwright entries respectively (Chroma setup was reused in the second), so the absolute totals are not perfectly comparable. The direction is consistent across five runs and the gap is ~6 s, far larger than that overhead.*

### Why, and why it matters for the AC

The sleep is not padding — it enforces **boot-before-injection ordering**. Without it the row lands before the daemon is watching, the daemon misses it on its first pass, and delivery waits a full `POLL_INTERVAL_MS` (3 s) or more. **A removed 1 s sleep costs about 6 s of poll latency.**

So the naive reading of this ticket — "delete the sleeps" — produces a **slower** suite that is still green, and the metric would move in the wrong direction while every assertion still passed. That is the same shape as the `setTimeout`-guard trap I flagged at intake: the change looks like a win precisely because nothing fails.

### What this means for the implementation

Each sleep must become a **poll on the condition it was standing in for** — here, *"the daemon has booted and is watching"* — preserving the ordering while collapsing the wait from a fixed 1 s to whatever it actually takes. Not removal. My intake's `waitForCondition` plan is the right shape; this measurement is why it is the *only* right shape.

**Revised expectation for the win:** ~64 boot sleeps × roughly 0.8 s recovered each, plus the larger sleeps handled individually, lands near the "fixed-sleep wall clock under 10 s" target I proposed at intake — **not** the ticket's under-60 s whole-file target, which the earlier arithmetic already showed is unreachable by de-sleeping alone.

### Next concrete step

Establish the readiness predicate. `PID_FILE` is claimed early in boot but **before** the poll loop starts, so it is necessary and not sufficient; I need a signal that the daemon is actually watching. Candidates: a first-cycle log line if one can be observed without changing the daemon, or a bounded poll on the daemon's log file. I will settle that on one test, prove it beats 1 s, and only then sweep — because a readiness predicate that is subtly too early re-creates exactly the 6 s penalty measured above, on 64 tests at once.

File restored to baseline; no changes staged.

## [MEASURED — the lever is not the sleeps] daemon readiness is **90 ms**, but the wall clock is quantized by a hardcoded 3 s poll interval

Instrumented the real path instead of reasoning about it. Three measurements, each one changing the plan.

### 1. The sleeps over-wait by ~10×

Replaced the first boot sleep with a poll on the daemon's own readiness line — `[Wake Daemon] Started. Tail-syncing from GraphLog ID: N`, emitted immediately after `lastSyncId = getLastSyncId(...)` and immediately before `pollLoop()`, i.e. the exact instant the watermark exists. Measured inside the spec:

```
READY_MS=90
```

**The daemon is ready in 90 ms. The sleep waits 1000 ms.** So the predicate is correct *and* ~10× tighter.

### 2. …and recovering that time changed the test total by nothing

```
1 s sleep          : 6.4 s, 6.3 s, 6.8 s
readiness poll     : 6.7 s, 6.2 s, 6.3 s
```

Identical. **`POLL_INTERVAL_MS = 3000` quantizes the wall clock.** Injecting at t=90 ms or t=1000 ms both land before the same 3 s poll boundary, so the delivery arrives at the same instant either way. Sub-3 s savings are absorbed whole.

That also explains the earlier removal experiment: deleting the sleep pushed injection *before* the watermark, costing an entire extra poll cycle — 6.4 s → 12.2 s.

### 3. The interval is hardcoded, and the fix pattern is one line below it

`ai/daemons/wake/daemon.mjs`:

```js
const POLL_INTERVAL_MS                  = 3000;                                             // :106  hardcoded
const CODEX_TURN_START_PROOF_TIMEOUT_MS = Number(process.env.WAKE_...) || 45000;            // :112  the idiom, already here
```

The file **already** has the sanctioned test-configurable-constant pattern, one line down. And `POLL_INTERVAL_MS` is not only the poll cadence — it drives retry backoff (`nextAttemptAt` at `:2587`, `:2687`, `:2704`, `:2723`, `:2734`), which is almost certainly the origin of the 4 s / 5.5 s sleeps.

### What this means for the ticket

**The sleeps are a symptom; the hardcoded interval is the cause.** De-sleeping all 86 sites, done perfectly, recovers little on any test whose duration is a multiple of 3 s — which, given a 10 s delivery guard and a 3 s cadence, is most of them.

Proposed reshape, @neo-opus-vega:

1. **Make `POLL_INTERVAL_MS` env-configurable** using the existing in-file idiom, and have the spec spawn with a short interval. One production line, one spawn-env change, and it collapses both the poll quantization and the retry backoff the large sleeps are waiting on.
2. **Then** convert the sleeps to `waitForDaemonReady`, which is correct regardless — it is ~10× tighter *and* removes a latent flake, since a fixed 1 s under CI load can under-wait and silently cost a full poll cycle.

Step 1 is where the minutes are. Step 2 alone cannot reach any wall-clock target, which is consistent with the arithmetic in my intake.

**One risk I will not hand-wave:** shortening the interval in tests changes timing-dependent behavior, so any test asserting *retry counts* or *backoff ordering* has to be re-checked rather than assumed equivalent. That is the review surface for step 1, and it is a real one.

### State

`waitForDaemonReady` helper is written and one site is converted and passing (3 runs). Instrumentation reverted. Nothing pushed — the reshape decision comes first, since it determines whether the remaining 85 conversions are worth doing on their own.

of them and the leaf keeps its declared 3000ms default, so a malformed ambient
value degrades to shipped behavior instead of a hot loop.

the domain now does the work the sentence was doing.
