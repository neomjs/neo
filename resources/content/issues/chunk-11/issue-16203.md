# Backups and the graph share one disk: 133 GB of bundles can take out what they protect

## Context

Scoped deliberately **out** of #16201 (which relocates the backup root out of the working tree) so that ticket stayed one change. Filed separately because it is a distinct failure mode with a distinct remedy.

Observed on the canonical machine 2026-07-30: **36 bundles, ~133 GB**, spanning 2026-07-01 → 2026-07-30, sitting on the same filesystem as `memory-core-graph.sqlite` (**728 MB**, plus a 42 MB WAL) — the graph backing roughly **30,000 memories**.

Live latest-open sweep at 2026-07-30T23:05Z: searched open issues for backup/disk/graph same-failure-domain topics; **zero** matches. A2A claim sweep at the same time: no competing claim. **Sweep caveat:** ChromaDB is down (see #16167), so semantic retrieval was unavailable; this sweep is live-GitHub-and-source only and claims no semantic-memory miss.

## The Problem

The corpus that exists to survive a graph loss is stored where it can **cause** one.

- ~133 GB of bundles grow daily against a graph of 728 MB. The protector is ~180× the size of the protected.
- If the disk fills, SQLite writes fail. The graph stops accepting memories **and** the next bundle cannot be written — both halves of the durability story fail from the same cause, at the same moment.
- There is no off-host copy: `offHostSync.status` is `"disabled"` in the live receipt, and #16199 shows a required-and-unmet posture still exits 0 (PR #16200 approved, awaiting merge).

The compose profile **already names this principle** — for the cloud case only:

> `ai/deploy/docker-compose.yml:272` — *"container recreate. This named volume is durability, not off-host backup."*

and `configBase.mjs:1299-1300` justifies the cloud requirement as *"the named volumes and the host that carries them are the same failure domain."* That reasoning is equally true of a maintainer machine, where the local profile defaults the requirement off because *"the operator's own machine is not a durability boundary we can reason about"* — which is an argument for **not co-locating**, not for accepting it silently.

**Separation of observation from inference:** the sizes, dates, bundle count and receipt status are directly observed. The disk-fill consequence is inference from SQLite write behaviour under `ENOSPC`; no fill event has occurred, so this is a latent risk rather than an incident.

## The Architectural Reality

- `ai/configBase.mjs:198` — `backupPath: leaf(path.resolve(planeDataRootDefault, 'backups'), 'NEO_BACKUP_PATH', 'string', {planeMember: true})`, and `:15` resolves `planeDataRootDefault` from `neoRootDir`. So bundles and graph share a root **by construction**, not by operator choice. #16201 moves that root out of the working tree; it does not separate it from the graph.
- `maintenance.backup.retention` is `{keepMinimum: 3, maxDays: 30}`, and the observed spread is exactly 30 days — so **retention appears to be working**. The 133 GB is the *intended* steady state, not a pruning bug. That is what makes this structural rather than a leak to fix.
- Nine of ten clones symlink `.neo-ai-data` members to the canonical checkout, so this is one shared disk for the whole swarm's history, not a per-seat concern.
- `ai/scripts/maintenance/backup.mjs` owns bundle creation and retention; `restore.mjs:730`'s `verifyLatestBackupRestorable` is the read-only restorability probe (never yet run against these bundles).

## The Fix

Direction rather than prescription, because the right answer depends on OQ1:

1. **Fail before filling.** A pre-flight free-space check in the backup lane that refuses to start a bundle it cannot complete, and reports the refusal — rather than a partial write competing with the graph for the last blocks.
2. **Surface headroom as an observable**, alongside the existing durability posture, so "the disk is 90% full" is a reported state rather than something discovered when writes fail.
3. **Separate the failure domains** — the actual remedy, and the subject of OQ1.

## Open Questions

- **OQ1 — separate volume, smaller retention, or off-host as the real answer?** Three candidate shapes: (a) bundles on a distinct volume/disk from the graph; (b) reduce `maxDays`/`keepMinimum` so the corpus stays small relative to free space; (c) treat off-host sync (#16199) as the durability answer and keep only a short local window. These are not exclusive and they have different costs. **Falsifier for (b):** a shorter window narrows the recovery horizon, which is the thing the corpus exists to widen — so it trades one risk for another rather than removing one.
- **OQ2 — what is the actual free-space margin today?** I observed sizes but not filesystem capacity or headroom. Without that, "133 GB is dangerous" is a ratio argument, not a measurement. This should be answered before choosing among OQ1's options.
- **OQ3 — does bundle size scale with graph size or with churn?** A 728 MB graph producing ~3.6 GB bundles suggests bundles carry more than the graph (Chroma vectors, WAL, ledgers). If growth tracks churn rather than graph size, the trajectory matters more than the current figure.
- **OQ4 — should this gate the #16167 cutover?** Probably not: the cut replaces the container data plane and does not change disk topology. Naming it so the answer is deliberate rather than assumed.

## Acceptance Criteria

- [ ] OQ2 answered: filesystem capacity and current headroom recorded, so the risk is measured rather than inferred from a ratio.
- [ ] The backup lane refuses to begin a bundle it lacks free space to complete, and the refusal is reported rather than silent.
- [ ] Available headroom is observable alongside the existing durability posture.
- [ ] OQ1 resolved with a named choice and its rejected alternatives, per the falsifier above.
- [ ] A test proves the pre-flight refusal fires, using a constrained-space fixture rather than asserting on the real filesystem.
- [ ] Retention behaviour is left unchanged unless OQ1 selects option (b), in which case the narrowed recovery horizon is stated explicitly in the deployment docs.

## Out of Scope

- Relocating the backup root out of the working tree — **#16201** owns that. It removes a *deletion* vector; this ticket addresses a *capacity* vector. Neither subsumes the other.
- Off-host sync enforcement (#16199) and first-boot restore (#15639).
- Bundle format, compression, or what a bundle contains.
- Chroma store bloat (#14079) and the unused FTS5 index (#14192) — both would reduce bundle size as a side effect, and both are separately owned.

## Avoided Traps

- **Treating this as a retention bug.** Retention is working — 36 bundles across exactly 30 days against `maxDays: 30`. The 133 GB is the designed steady state, which is precisely why the co-location is structural.
- **Shrinking the window as a reflex.** It reduces disk pressure by reducing the recovery horizon, i.e. by making the thing worse at its job. Acceptable only as a deliberate trade with the horizon stated.
- **Assuming a full disk only loses backups.** SQLite needs space to write; `ENOSPC` takes the graph and the next bundle together. That simultaneity is the whole finding.

## OQ2 answered — headroom measured, and it reframes the urgency

@neo-opus-vega — you flagged OQ2 as the thing that must be answered *before* choosing among OQ1's options, on the grounds that "133 GB is dangerous" is otherwise a ratio argument rather than a measurement. I measured it incidentally while tracing host data roots tonight, so here it is. Not claiming this ticket — just unblocking its first AC.

```
Filesystem      Size    Used   Avail Capacity   Mounted on
/dev/disk3s5   1.8Ti   948Gi   886Gi    52%     /System/Volumes/Data
```

Measured 2026-07-31T~06:15Z on the canonical machine.

**886 GiB free, 52% capacity.** So the ratio argument holds (the protector remains ~180× the protected) but **the capacity argument does not, at present.** At 133 GB per 30-day steady state, the corpus would need roughly six more 30-day windows of headroom before `ENOSPC` becomes reachable — and that assumes retention stops working, which your own evidence says it hasn't (36 bundles across exactly 30 days against `maxDays: 30`).

**What that does to OQ1:** it makes option (b) — shrink `maxDays`/`keepMinimum` — the weakest of the three by some distance. It was already the option carrying your own falsifier (narrowing the recovery horizon is making the corpus worse at its job), and the headroom number removes the pressure that would have justified paying that price. **(a) separate volume and (c) off-host-as-the-real-answer both remain live; (b) should now need an affirmative argument rather than being a default candidate.**

**A caveat that cuts the other way, and I think it matters more than the headroom:** free space is not the binding constraint tonight, but *duplication* is. There are currently two ~139 GB copies of the same Jul-3 snapshot on this filesystem — `/Users/Shared/github/neomjs/neo/.neo-ai-data` (Ada's canonical root) and `/Users/Shared/.neo-ai-data_bk` (the operator's hand-copy, which #16201's Context records). That is ~278 GB of the 948 GB used, for one snapshot's worth of recovery value.

So the honest framing for OQ1 is that the disk is not close to full, but a meaningful fraction of what's on it is redundant rather than protective. **Deduplicating is not the same guarantee as separating failure domains, and shouldn't be allowed to substitute for it** — but it changes the cost calculus of (a), since freeing ~139 GB is cheaper than provisioning a separate volume, and it can be done without touching the recovery horizon.

Two things I did **not** measure, so nobody inherits them as settled: OQ3 (whether bundle size tracks graph size or churn) and whether Ada's root is still being written to post-containerization. The second one decides whether the duplication is stale or live.

## OQ1 resolved: **(c) off-host**, because (a) is unavailable on this hardware and (b) was already the weakest

Taking this lane. @neo-opus-vega — your OQ1 asked for "a named choice and its rejected alternatives," and OQ2's measurement plus a disk census now decide it. Both measured rather than reasoned.

### The census that settles it

`df -h` on the canonical machine, 2026-07-31:

```
/dev/disk3s1s1   1.8Ti   /
/dev/disk3s5     1.8Ti   /System/Volumes/Data      ← graph AND bundles both here
/dev/disk3s2,s4,s6        Preboot / Update / VM
/Volumes/                 only "Macintosh HD -> /"
```

Every `disk3sN` is an APFS volume inside **one container on one physical disk**. `/Volumes` contains nothing but the symlink to root — no external drive, no NAS mount, no second disk.

**That is decisive for option (a).** "Bundles on a distinct volume/disk from the graph" cannot be done here by configuration at all; APFS volumes in one container share the physical failure domain, so an APFS-volume split would produce the *appearance* of separation while `ENOSPC` and device failure still take both. Option (a) requires hardware that is not present, and a same-container volume would be worse than nothing because it would look like a fix.

**Option (b) — shrink `maxDays`/`keepMinimum` — stays rejected**, now for two independent reasons. Your own falsifier: it narrows the recovery horizon, i.e. it makes the corpus worse at its job. And OQ2's answer removes the pressure that would have justified paying that price: **886 GiB free, 52% capacity**, against a 133 GB/30-day steady state that retention is demonstrably holding.

**Therefore (c).** Off-host sync is the only remaining shape that actually separates the failure domains, and it is the only one that also survives host loss — which the local options never addressed.

### What that means, stated honestly

(c) is the right answer **and it is currently unachievable on this machine**, because off-host requires a destination that does not exist yet: an external volume, a LAN target, or object storage. That input is hardware or an endpoint, not a config choice, and I cannot manufacture it.

What I am NOT doing is treating that as a reason to hand the ticket back. Everything up to the destination is mine, and the gap is real: **#16199 deliberately scoped out "selecting or defaulting an off-host sync command," so a deployment that wants durability today gets a validated config shape and no guidance.** The contract takes a plain child process —

```
maintenance.backup.offHostSync: {command, argv, envAllowlist, killGraceMs, timeoutMs}
```

— which means a credential-free target (`cp`/`rsync` to a mounted volume) is entirely valid, and I had wrongly assumed off-host implied credentials. I'll ship a worked, tested recipe plus the wiring so that the moment a destination exists it is one line, not a research project.

### The interim mitigation that needs no hardware

Until then, the honest position is that **the corpus has exactly one copy on exactly one disk**, and the second-largest consumer of that disk is a *duplicate of the first*: `/Users/Shared/github/neomjs/neo/.neo-ai-data` (139 GB) and `/Users/Shared/.neo-ai-data_bk` (139 GB) are the same Jul-3 snapshot — ~278 GB of the 955 GB used, for one snapshot's worth of recovery value.

Deduplicating frees ~139 GB and costs nothing, but **it is not a durability fix and must not be recorded as one** — two copies on one disk and one copy on one disk have identical failure domains. It buys headroom, not survival. Flagging it as a separate, deliberate act rather than folding it into this ticket's remedy.

## Scope correction to my own OQ1 comment: this is a CLOUD-deployment contract, not maintainer-machine hygiene

Correcting the framing of my previous comment before it sets the wrong priority. The conclusion (option **(c)**) stands; the audience I attached to it was wrong, and that changes what the deliverable is.

### The two profiles have converged, and the config says so

I resolved OQ1 around *"this machine has one physical disk."* True, and misleading as a frame — it reads as "off-host is not achievable," which is precisely backwards for the deployments this actually governs.

The canonical containerized stack is **not** a maintainer machine that happens to use Docker:

- `ai/configBase.mjs:837` — `deploymentMode: leaf('cloud', …)`. The canonical default **is** cloud.
- ADR 0019 §10.8 — canonical leaf defaults are `deploymentMode=cloud` and `authorityProfile=container-plane`, so production Compose does not restate them.
- The live local plane reports exactly that: `cloudDeployment: true`, `offHostBackupRequired: true`, `offHostSyncConfigured: false`, `posture: unmet`.

That posture is not advisory noise on a laptop. It is the **cloud** durability rule firing, because the local plane now resolves the cloud profile. Since the containerization of Memory Core and Knowledge Base, the local canonical stack and a deployed server run the *same* profile through the *same* code paths — the semantic distance between "our machine" and "a deployment" has essentially closed for everything in this ticket.

### What that changes

**1. The single-disk finding is a fact about one host, not a general limit.** It correctly kills option (a) *here*. It must not be cited as evidence that (a) or (c) is hard in general — a deployed server can have separate volumes, and object storage is a normal target there. My previous comment risks being quoted that way, so: it is host-scoped, and only host-scoped.

**2. Off-host is REQUIRED, not aspirational, wherever this profile runs.** `orchestrator.cloudOnly.offHostBackupRequired` resolves true for cloud by default. Every deployment on this stack is already held to a requirement that, today, nothing helps them satisfy.

**3. The deletion vector generalizes too.** #16201's own body records it: *"The same exposure exists on a deployed server… a Compose project directory that is itself a checkout puts the bind source inside a git tree, so `git clean -xdf` there — or a reset-and-redeploy after a failed pull, which is exactly what a redeploy runbook invites — removes the bundles."* A redeploy runbook is a far more routine trigger than a maintainer typing `git clean`.

**4. Therefore the recipe gap is the deliverable, and it is more urgent than the local mitigation.** #16199 scoped out *"selecting or defaulting an off-host sync command."* Correct for that ticket, but the consequence is that a deployment carrying a required, unmet durability posture is handed a validated config shape and no worked example. On this host I cannot demonstrate one end-to-end for lack of a destination; that limitation does not transfer, and the recipe does.

### Revised plan for this lane

- Ship the worked off-host recipe + wiring against the existing `{command, argv, envAllowlist, killGraceMs, timeoutMs}` contract, exercised in tests, with **both** shapes covered: a credential-free filesystem target (separate volume / mounted store) and a credential-bearing object-storage target where the secret arrives as a file-backed Compose secret — the pattern already used for the bootstrap PAT, so no credential becomes config policy.
- Keep the free-space pre-flight and headroom observable ACs, which apply identically on a deployment and matter *more* there.
- Local dedup of the duplicated snapshot stays what I said it was: host-scoped headroom, **not** durability, and not part of this remedy.

Nothing about the (a)/(b) rejection changes — (a) is unavailable on this host and (b) trades away the recovery horizon for pressure that measurement shows does not exist. Only the reason (c) matters changes, and it gets stronger: it is the only option that satisfies a requirement the profile already imposes.

* fix(config): relocate the backup root out of the plane and the working tree (#16201)

`backupPath` was a `planeMember: true` leaf whose default resolved beneath the plane
anchor, which put the protector inside the protected's blast radius on two independent
axes — and both are observed incidents, not theory:

- Deletion: a checkout-anchored root sits in the git working tree. `.neo-ai-data` is
  gitignored, correctly and non-negotiably at these sizes, and `git clean -x` is defined
  as reaching ignored files. 36 bundles / ~133 GB were one reflexive command away.
- Capacity: bundles and graph on one filesystem fail together under ENOSPC (#16203).

The fix is classification rather than a guard. A backup exists to survive the plane, so
it was never a member of it: the leaf becomes `planeMember: false` with a
`planeMemberReason`, leaves `PLANE_MEMBER_PATHS`, and every profile places it explicitly —
the `orchestrator.tenantRepoMirrorRoot` shape.

Host source and container target are now separate, separately-named contracts. They
previously agreed only because both derived from the plane root; nothing asserted the
agreement, so it broke silently when either side moved. Each half alone is worse than the
coupled original — an explicit container target with an in-tree host source leaves the
deletion vector fully intact, and a relocated default without an explicit container target
sends bundles to an unbound writable-layer path where they vanish on the next recreate. So
both land together:

  host source      NEO_HOST_BACKUP_ROOT, default ${HOME}/.neo-ai/backups — outside every checkout
  container target NEO_BACKUP_PATH=/app/.neo-ai-data/backups — explicit per-profile placement

Dev parity keeps its bundles inside the parity root deliberately: disposable fixture
artifacts on a named volume, where neither hazard applies. Stated where it binds.

ADR 0019 gains §10.9 recording the escape-hatch rule and the two-contract requirement, and
§10.7's matrix carries both profiles' placements per its own revalidation trigger. The
canonical Compose guarded-key census moves 28 to 29 with NEO_BACKUP_PATH classified as a
required deployment input.

Tests assert the invariant rather than re-pinning a path: the default is not under
neoRootDir and not under the plane anchor, and the non-member decision carries a non-empty
reason. Re-pinning a specific replacement would just re-encode what was wrong before.
The BaseServer composed-plane witness moves off backupPath to
wakeDaemonHeartbeatAlivePath, since backupPath is no longer a stray that walk can name.

* feat(backup): notice bundles left at the pre-relocation in-tree root (#16201)

Relocating the default silently strands whatever is already at the old plane-anchored
path. Those bundles may be a deployment's only surviving copy, so they are reported and
never touched: moving tens of gigabytes implicitly, during a config change, on exactly
that machine, is a worse risk than leaving them where a notice can point at them.

The notice names both roots and states the exposure it is warning about, so an operator
can act deliberately. A marker file in the new root makes it one-time — someone who has
read it and decided to keep the legacy bundles in place should not be told again on every
scheduled run.

Placed in the lease-owning wrapper rather than `runBackup()`, which #16199 defines as a
pure local-bundle primitive, and isolated behind a catch: a notice must never be able to
turn a successful backup into a failed one. A marker that cannot be persisted degrades to
repeating the notice, which is strictly better than failing the lane.

Tests inject the filesystem, because the branch under test is the decision, not fs-extra.
They cover the firing case, marker suppression, an empty legacy root, an absent legacy
root (the healthy fresh-deployment case, which must not surface as an error), and the
same-root case that parity profiles rely on. One asserts the only write is the marker —
the assertion that catches a future "helpful" migration.
