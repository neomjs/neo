# Restore scheduled corpus publication through the Data Sync Publisher identity

## Context

This ticket originally concluded that the corpus generator had never had an automated publisher. Live history falsifies that premise:

- automated `chore: ticket sync [skip ci]` commits advanced `resources/content/**` until 2026-07-17;
- the default-branch ruleset then began rejecting the local orchestrator's pushes with `GH013`;
- the existing Data Sync workflow now has a working Publisher App identity and continues to advance `dev`, but its generated-path allowlist excludes `resources/content/**`;
- the canonical long-running checkout therefore keeps regenerating the corpus locally without a delivery path. On 2026-07-28 it held 794 modified or untracked generated outputs.

This is a publication regression, not a missing-design investigation.

## The Problem

The corpus currently has two incomplete halves:

1. `githubWorkflowSync` still runs every two hours in a local maintainer checkout. It can emit issues, pull requests, discussions, and release notes, but its checkout credential cannot bypass the current `dev` ruleset.
2. `.github/workflows/data-sync-pipeline.yml` already possesses the sanctioned Publisher App credential and successfully pushes generated data, but `buildScripts/dataSyncPipeline.mjs` neither runs the corpus generator nor stages `resources/content/**`.

Moving the existing generator into CI exposes two recovery edges:

- the first discussion bootstrap has no `updatedAt` high-water mark and its `first: 50` GraphQL query exceeds GitHub's resource limit; a measured outer page size of 30 succeeds while retaining complete cursor pagination;
- `GH_SyncService` deliberately preserves successful facet output when another facet fails, but an ephemeral runner currently exits before that progress can be published.

## The Fix

Extend the existing Data Sync pipeline as the sole scheduled corpus publisher:

- run the canonical corpus generator in an emission-only mode under the workflow's read identity;
- allowlist `resources/content/**` and publish it through the pipeline's existing Publisher App push;
- cap the outer discussion bootstrap page at the measured safe size while retaining full pagination;
- if one corpus facet fails, publish only the integrity-checked progress from successful facets, then fail the workflow loudly;
- disable local scheduled corpus generation by default while retaining the manual `syncGithubWorkflow` entry point.

No second publisher identity or new ADR is needed: this extends the already-sanctioned Data Sync ownership and credential split.

## Contract Ledger Matrix

| Target Surface | Source of Authority | Required Behavior | Failure Behavior | Evidence |
|---|---|---|---|---|
| `resources/content/**` on `dev` | `GH_SyncService` generators | advances from the scheduled Data Sync workflow | failed facet rolls back; successful facets may publish; workflow remains red | focused unit tests + scheduled-run commit |

## Acceptance Criteria

- [ ] Data Sync runs the canonical corpus generator in emission-only mode; that mode cannot commit or push.
- [ ] The workflow grants only the read scopes required for pull requests and discussions in addition to its existing read scopes.
- [ ] `resources/content/**` is part of the generated-data allowlist and is delivered only by the existing Publisher App final push.
- [ ] A no-high-water discussion bootstrap uses an outer page size no larger than 30 and still follows every outer cursor.
- [ ] When one corpus facet fails after another succeeds, integrity-checked successful-facet output is staged and pushed before the workflow reports the original failure.
- [ ] Local scheduled `githubWorkflowSync` is disabled by default; the guarded manual maintenance command remains available.
- [ ] [L4-deferred — operator handoff needed] An actual post-merge scheduled run advances `resources/content/**` on `dev` and the existing per-facet watchdog reports all facets fresh.
- [ ] [L4-deferred — operator handoff needed] The canonical checkout's generated backlog is discarded only after the published commit proves that no generated data was lost.

## Decision Record impact

None. The implementation extends the Publisher App / reader identity split already established by #15744 and the existing Data Sync pipeline.

## Out of Scope

- Discussion comment/reply completeness (#16016).
- Corpus schema or rendering-format changes.
- Any non-generated file cleanup in the canonical checkout.

## Avoided Traps

- Do not give the generator a write credential or let emission invoke its legacy nested push path.
- Do not treat a green Data Sync run as corpus freshness until `resources/content/**` is in its allowlist.
- Do not hide a partial facet failure merely because successful-facet progress was published.
- Do not reset the canonical dirty checkout before the CI-published commit exists.

## AC-1 discharged — the volume number exists, and it does not kill Option A

Claimed this lane. AC-1 gates every other decision here (*"no option may be adopted without it"*), so it is the only thing this comment does. Measured, not estimated.

### The numbers

| Measurement | Value | Method |
| --- | --- | --- |
| Corpus size on `dev` | **15,807 files / 100.7 MiB** (mean 6.5 KiB/file) | `git ls-tree -r -l origin/dev -- resources/content/` |
| Diff churn | **~1.08 MiB/day** (34,062,592 bytes / 30d) | `git log -p --since=30.days -- resources/content/ \| wc -c` |
| Commits/day, current hand cadence | **8.0/day** (167 commits over 21 active days of 30) | `git log --format=%ad --date=short`, grouped |
| Commits/day, 90-day view | 4.3/day (384 commits) | same, 90-day window |
| **Delta-bearing 2h windows** | **65 of 84 = 77%** | GitHub artifact `updated_at`, bucketed into 2h |

### What that projects for a 2h publishing cadence

12 runs/day × 77% delta-bearing = **≈ 9.3 commits/day**, against a current baseline of **8.0/day**.

That is **+1.3 commits/day, roughly +16%** — not a step change. The reason is the finding I did not expect: hand-committing was *already* landing at near-2h effective granularity. The corpus was not being batched into infrequent large commits; it was being committed often and irregularly, and the nine-day gap that surfaced this ticket was an outage rather than the normal rhythm.

Bytes/day is **cadence-invariant to first order** — the churn is driven by GitHub activity, not by how often we commit it. A finer cadence splits the same ~1.08 MiB/day into more, smaller commits.

### The falsifier, answered

Option A's recorded falsifier: *"measure the commit volume a 2h cadence produces over 30 days; if repository growth is unacceptable, A dies."*

**A does not die.** At +16% commits over what is already happening and no change in byte volume, the cadence shift is marginal. Annualised raw diff content is ~394 MiB/year, which git packs well below that — and critically, that cost is being paid **today**, just with a human as the scheduler.

This also reframes C. C exists to solve A's volume problem, and there is no volume problem to solve. C's own falsifier (*"if a slower cadence cannot keep the watchdog's per-facet thresholds green"*) now bites harder than A's, because slowing publication is the thing that produced a 233-hour staleness alarm in the first place. I am not adopting anything in this comment — AC-2 wants the adoption with its falsifier recorded, and B's environment question is untested — but the discriminator AC-1 was built to provide now points at A.

### Instrument limitations, stated rather than buried

Four, and none of them changes the conclusion's direction:

1. **Diff bytes overstate content bytes.** `git log -p` output includes diff headers and context lines, so ~1.08 MiB/day is an upper bound on pure content change. The conclusion is "volume is acceptable", and an upper bound is the safe side for that.
2. **The 77% is a floor, not a point estimate.** It comes from `search/issues`, which covers issues and pull requests but **not discussions** — a facet this corpus carries. Including discussions can only raise the fraction, which raises projected commits/day toward the 12/day ceiling. Even at 100% the projection is 12/day versus 8.0 today: +50%, still not a step change.
3. **Amplification from intermediate revisions is real but small here.** A finer cadence commits successive states of the same file where a batch would commit one. At 8 commits/day the corpus is already near 2h granularity, so there is little batching left to lose — but this is the term that would grow if the cadence were pushed below 2h, and it is the number to re-measure if anyone proposes that.
4. **Repository pack size was not measured.** This session runs in a git worktree, so `du -sh .git` reports 4.0K rather than the real object store. The byte-churn figure above is the honest substitute; a true pack-growth number needs the main checkout.

### One correction to my own first attempt

My initial delta-bearing measurement bucketed **corpus commit timestamps** into 2h windows and got 37 of 168 (22%). That number is wrong for this question and I nearly recorded it: commit timing reflects *when a human chose to commit*, not when a delta existed. It would have understated the delta-bearing fraction by 3.5× and made a 2h cadence look far cheaper than it is. The corrected instrument reads artifact `updated_at` from GitHub, which is the thing the generator actually responds to.

## AC-3 — the authority analysis inverts AC-1's implication: A is cleared on volume and killed on authority

AC-1 cleared Option A's cost falsifier. AC-3 kills A anyway, for a reason the ticket's option table did not anticipate. Recording both halves so the adoption in AC-2 rests on the pair rather than on the cheaper number.

### What a corpus publisher must actually get past

Pushing `resources/content/**` to `dev` means pushing to `~DEFAULT_BRANCH`, which is governed by ruleset **`19087298` "code scanning merge protection"** — rules `code_scanning` **and** `required_status_checks`, the latter requiring `integration-parity`.

A freshly generated corpus commit carries **no status checks at all** — checks attach to commits that CI has run against, and a generated commit pushed directly has none. So `required_status_checks` blocks it by construction. A corpus publisher therefore needs **one of**:

1. ruleset bypass, or
2. to route through a PR and wait for checks, or
3. an explicit ruleset exemption.

This is not hypothetical: the existing Data Sync publisher pushes `chore(data)` commits straight to `neo:dev` on a schedule, so option 1 is the mechanism already in use.

### The bypass exists and its holder is not auditable from my credential

| Probe | Result |
| --- | --- |
| REST `repos/neomjs/neo/rulesets/19087298` | `bypass_actors` key **absent entirely** — reads as "no bypass" |
| GraphQL `ruleset.bypassActors.totalCount` | **1** |
| GraphQL `bypassActors.nodes { bypassMode actor { … } }` | `bypassMode=null`, `actor=null` — **not disclosed** |

So: **a bypass exists on the ruleset governing `dev`, and I cannot enumerate who holds it or what it covers.** REST would have told me there is none; only the GraphQL count contradicts that, and the count is all it will give me.

That is the AC-3 answer, and it is stronger than the principle the AC was written around. The AC asks that the publisher's authority be "named and least-privilege… so a content publisher does not silently acquire the ruleset-bypass credential." **You cannot grant least-privilege against an authority you cannot enumerate.** Reusing the existing publisher identity would inherit a bypass whose scope is invisible to inspection — which is the definition of acquiring it silently, regardless of intent.

### Why this kills A rather than merely constraining it

Option A is *"the `githubWorkflowSync` lane commits + pushes its own output after a successful run."* That lane is an **orchestrator lane running on a developer seat** — `orchestrator.localOnly`, gate `githubWorkflowSyncEnabled` resolving to enabled on a local profile.

So A requires putting **ruleset-bypass push authority to `dev` onto a per-developer machine**, replicated to every seat that runs the orchestrator. That is a categorically worse grant than the same authority held by a CI-scoped App:

- it is per-seat rather than singular, so revocation is per-seat too;
- it lives on machines the swarm does not control the lifecycle of;
- and it couples corpus publication to whichever seat happened to be awake — the exact per-seat coupling `#15744` split two identities to avoid.

A's recorded falsifier was volume, and AC-1 cleared it. **The falsifier the option table was missing is authority**, and A fails it. Recording that explicitly, because "A is the smallest change" remains true and is now beside the point — smallest-diff is not a reason to distribute a bypass credential.

### Where that leaves the options

| Option | Volume (AC-1) | Authority (AC-3) |
| --- | --- | --- |
| **A — orchestrator publishes** | **passes** (+16% commits) | **fails** — bypass authority onto per-developer seats |
| **B — CI publishes** | passes (identical volume; cadence-invariant) | **plausible** — one CI-scoped App identity, the pattern the Data Sync publisher already runs |
| **C — cadence-decoupled** | passes, but solves a problem that does not exist | same authority question as B, unimproved |

B is now the leading option, on authority rather than on convention. Its own recorded falsifier is still live and untested: *"the sync is dev-branch-guarded and heavy-lease-bound; if it cannot run under a runner's constraints, B dies."* Both halves are checkable — `syncGithubWorkflowBranchGuard.mjs:57-61` for the branch guard, and the heavy-maintenance lease work in `#16027` / PR `#16030` for the lease binding, which has moved since this ticket was written.

**I am not adopting B in this comment.** AC-2 requires the adoption to carry its falsifier discharged, and B's runner-environment falsifier is exactly what I have not yet tested. Testing it is the next step on this lane.

### Two items that need the operator, and are not mine to do

1. **Naming the bypass holder.** Repository ruleset bypass actors are visible in repo settings but not through my credential. AC-3 cannot be *fully* closed by an agent — the least-privilege reconciliation needs someone who can read the bypass list to confirm which identity holds it and whether it spans more than `code_scanning`. Flagging rather than assuming a benign answer.
2. **A second direct-push exception is a `§critical_gates` question.** Gate 3 forbids direct commit/push to `dev` with *"the data-sync pipeline is the explicit exception."* Whichever option lands here becomes a **second** exception, which is substrate-level and wants explicit operator direction plus an ADR answer under AC-6 — not an implementation detail decided inside this leaf.

### Instrument note

If any future work reads ruleset bypass state, **REST is not a valid probe** — it omits App-type entries silently, so `bypass_actors: absent` and `bypass_actors: []` are indistinguishable from a real empty list. Use the GraphQL `bypassActors.totalCount`. I published a wrong claim from the REST reading earlier this cycle and it took a peer's falsifier to catch; the count is the only reliable existence check available, and even it will not name the holder.

## AC-2 — adopting B′, a refinement none of the three options captured: ride the sanctioned publisher instead of becoming a second one

AC-1 gave the volume number, AC-3 gave the authority analysis. Together they select **B over A**, and then they select something better than B.

### The refinement, and why it is not just "B with extra steps"

The option table framed B as *"a scheduled workflow runs the sync on a runner and pushes, like the Data Sync pipeline does for its own paths."* Reading that phrase literally is what produced the refinement: the Data Sync pipeline **is already** a scheduled runner that pushes to `dev` under the publisher identity with the ruleset bypass, and it is the **single explicit exception** to `§critical_gates` #3's no-direct-push rule.

So B has two very different implementations:

- **B (as written)** — a *new* scheduled workflow that also pushes to `dev`. That creates a **second** direct-push exception, a second identity question, and a second bypass grant.
- **B′ (adopted)** — the corpus becomes **additional stages and paths inside the existing pipeline**. No new exception, no new identity, no new bypass, no new schedule.

B′ is strictly smaller in authority surface while being slightly larger in diff. The option table ranked by diff size (*"A is smallest"*), which is the axis AC-3 showed does not matter here.

The mechanism is already declarative, which is what makes B′ cheap:

```js
// buildScripts/dataSyncPipeline.mjs — stages are {args, label, tokenScope}
{args: ['run', 'devindex:update', '--', '--limit=200'], label: 'DevIndex Updater', tokenScope: 'intake'}
```

A corpus stage is one more entry of that shape, plus adding `resources/content/**` to `GENERATED_DATA_PATHS` (currently four `apps/**` entries, with the corpus deliberately excluded — that exclusion is the defect this ticket names).

### The two rejected options, with the evidence that killed them

**A — orchestrator publishes: DEAD on authority.**

Its recorded falsifier was volume, and AC-1 **cleared** it (+1.3 commits/day, ~+16%, bytes cadence-invariant). It dies on the falsifier the table was missing. The `githubWorkflowSync` lane runs under `orchestrator.localOnly` on developer seats, so A requires ruleset-bypass push authority to `dev` **replicated onto every seat that runs the orchestrator** — per-seat rather than singular, revocable only per-seat, on machines whose lifecycle the swarm does not control, and coupling corpus publication to whichever seat is awake. That is the precise per-seat credential coupling `#15744` split two identities to prevent. Smallest-diff is not a reason to distribute a bypass credential.

**C — cadence-decoupled publish: DEAD twice over.**

C exists to solve A's volume problem. AC-1 established there is no volume problem, so C's reason to exist is gone. Worse, its own recorded falsifier — *"if a slower cadence cannot keep the watchdog's per-facet thresholds green, C dies"* — is not hypothetical: slowing publication is exactly what produced `#15972`'s **233-hour** staleness alarm. C proposes more of the mechanism that caused the defect.

### B′'s own falsifiers — stated, and both are live

Adopting an option means owning its kill conditions, not retiring them.

**1. Permission grants are missing.** The pipeline currently grants exactly:

```yaml
permissions:
  contents: read
  issues: read
```

The corpus sync emits issues, PRs, discussions and release notes. `issues: read` is present (added for `#16007`), but **`pull-requests: read` and `discussions: read` are not granted**. B′ dies unless those are addable — they are additive least-privilege reads of the same class as the `issues: read` addition, so I expect them to be fine, but **this is untested and it is the first implementation step, not an assumption.**

**2. The per-run GraphQL budget.** The sync's own JSDoc scopes it at *"~8.5k issues + ~2.8k PRs + ~165 discussions + ~166 release notes."* A full traversal against a 5,000-point hourly limit — with the DevIndex stages already spending a measured `953` points per run — would exceed the window. That is not speculative: it is the `Resource limits for this query exceeded` failure that opened this whole investigation.

**This is why B′ is only affordable now.** `#16001` merged at `2026-07-26T22:27:49Z` (`b67e208115`), making the discussion delta cutoff actually engage — so a normal run fetches a handful of changed discussions rather than the full history. **`#16001` is a hard prerequisite for B′, and it landed twelve minutes before this comment.** Before tonight, B′ would have failed falsifier 2 on every run. The measurement that must exist before implementation is the per-run corpus GraphQL cost *with* the delta engaged, added to the DevIndex `953`, against 5,000.

### What B′ dissolves

The `§critical_gates` #3 concern I raised in AC-3 — that any option here becomes a *second* direct-push exception needing operator direction — **does not apply to B′.** It adds paths to the one existing sanctioned exception rather than creating another. That was the single strongest argument against doing this in CI at all, and the refinement removes it rather than seeking a waiver for it.

The AC-3 item that **remains** operator-owned: the ruleset bypass holder is not enumerable from my credential (`bypassActors.totalCount=1`, `actor=null`, REST omits the key entirely). B′ does not *widen* that bypass — it publishes more paths under the identity that already holds it — but confirming what that identity's bypass actually spans still needs someone who can read repo settings.

### AC-6 — does B′ need an ADR? Answering explicitly: no.

An ADR would be warranted for *creating* a scheduled committer of generated content, which is what A and B(as-written) do. B′ creates no publisher, no exception, no identity and no schedule; it extends the path set and stage list of an existing sanctioned publisher whose architecture an ADR already governs. The decision worth recording is *"the corpus joins the existing publisher rather than becoming a second one"*, and this comment plus AC-2's falsifier record is the right weight for it. If a reviewer reads B′ as constituting a new publisher, that is the disagreement to have before implementation, and I would rather have it here than after a PR.
