# Cross-harness wake Tier-1: outbound authenticated wake-stream + per-harness re-invoke sidecar (event-driven; honors the wake-after-state invariant)

## Problem

Tier-0 polling (the self-timeout recipe) is a cheap bridge but burns an empty turn per cadence. The event-driven successor: the agent dials **OUT** to an authenticated wake-stream (over the MCP ingress + PAT); a thin per-harness sidecar/hook re-invokes the local harness headlessly when the awaited state is reached.

Honors the load-bearing invariant (@tobiu): **peers are woken after the state they wait for is reached — especially when wake-notifications are deactivated.**

## Fix shape

- Outbound wake-stream subscription (rides the existing `WAKE_SUBSCRIPTION` / `CoalescingEngineService` `ns` target; the agent dials out vs the daemon dialing in — the direction-flip).
- A per-harness re-invoke sidecar (block-termination hook → headless resume).
- The state-transition emits the wake even with notifications off (the invariant guard).

## Acceptance Criteria

- [ ] An agent subscribes to an outbound wake-stream for a named awaited-state.
- [ ] Reaching that state re-invokes the parked harness headlessly (per-harness sidecar).
- [ ] The wake fires even when wake-notifications are deactivated (invariant guard + test).

## Missing AC: seat-exclusive delivery. The stream answers *when*, nothing answers *which machine*.

Surfaced while the operator and I worked the local↔cloud parity consequence — a containerized Agent OS cannot host wake delivery (no desktop session to `osascript`/`tmux` into), so a host-side deliverer is permanent, and this ticket is its design. Adding the gap here rather than filing a duplicate.

**What this ticket already gets right** and I would not change: the direction-flip. The agent dials **out** to the wake-stream instead of the daemon dialing in. That is the property that makes it work for real operators — outbound-only survives NAT, corporate firewalls, laptop sleep/resume, and IP changes with no reconnect story, and the cloud never needs to reach anyone's machine. Webhooks die on developer desktops; this does not.

**The gap: the ACs stop at *when*, never *where*.**

> - [ ] An agent subscribes to an outbound wake-stream for a named awaited-state.
> - [ ] Reaching that state re-invokes the parked harness headlessly.

Both hold perfectly with **two deliverers subscribed for the same seat**, and both then fire. `WakeSubscriptionService` today records presence — `harnessPresenceFreshMs` 5 min, `harnessPresenceTtlMs` 10 min — which detects a deliverer that *vanished*, but nothing prevents two that are simultaneously alive.

**This is not hypothetical.** We hit exactly this locally on 2026-07-26: two wake-daemon PIDs on one machine produced duplicate delivery, and it took an operator observation to find. On one host it is a bug. Across ten operators it is the **default state** — any seat that moves machines, any operator running two harnesses, any stale sidecar after a laptop wakes up.

And duplicate is the worse failure direction: a late wake costs latency, a duplicate wake burns an agent turn re-handling a message already handled, at exactly the moment the swarm is under budget pressure.

### Proposed AC to add

- [ ] Delivery subscription is an **exclusive lease per seat**, not a registration. A second claimant for a live lease is either an explicit takeover or is refused — never a silent second deliverer.
- [ ] Lease expiry uses the existing presence TTL, and an expired lease **queues** wakes rather than delivering into the void (a closed laptop must not lose wakes).
- [ ] Seat migration is a first-class transition: the new machine takes the lease, and the previous holder's delivery attempt is **refused**, not duplicated.
- [ ] Test: two subscribers, same seat, one state transition → exactly one re-invoke.

That last one is the whole ticket in a single assertion, and it is the one that would have caught our live bug.
