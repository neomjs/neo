# KB release artifact is 583MB (was 2.3MB): raw embedding vectors dominate the JSONL

## Context

Observed live during the v13 cut (step 5.5, `uploadKnowledgeBase.mjs`): the packaged artifact hit **583.17 MB** vs **2.27 MB** for the 12.1.0 asset (verified via `gh release view 12.1.0 --json assets`) — ~256×. Operator (mid-cut): "this needs work post release… way more code, maybe 20MB. it MUST not include MC and Graph."

`Release classification:` post-release (operator's explicit word; the upload itself succeeds — GitHub's per-asset limit is 2GB — so the cut is not blocked).

## The Problem

**The MC/Graph-leak hypothesis is falsified**: the script is deliberately collection-scoped and its leak-guard ("fails loudly if any Memory Core collection or a `sqlite/` payload leaks") passed — the log confirmed `28398 'neo-knowledge-base' chunks, no Memory Core collections, no sqlite/`. The bloat driver is the artifact FORMAT: the JSONL is a **raw-vector round-trip** (`uploadKnowledgeBase.mjs:50`) — every chunk carries its full embedding vector as JSON-serialized floats. At 28,398 chunks × ~1536 dims × ~13 chars/float, vectors dominate by orders of magnitude, and float text compresses poorly. The 12.1.0 artifact predates either the vector round-trip shape or this cycle's KB growth (or both).

## The Architectural Reality

- `ai/scripts/maintenance/uploadKnowledgeBase.mjs` — collection-scoped export via `KB_DatabaseService.manageDatabaseBackup({action: 'export'})`; emits `knowledge-base-backup-<ts>.jsonl` (raw vectors) + `kb-artifact-meta.json` (embeddingProvider + dimension provenance for download-side compatibility).
- The download-side consumer imports the JSONL to reconstruct the collection — the vectors exist so consumers don't need the embedding provider to rebuild. That trade-off (no-reembed convenience vs 256× size) is the design decision to revisit.

## The Fix (options to weigh, not prescribed)

1. **Split artifact**: canonical text+metadata JSONL (small, ~the operator's 20MB intuition) + an OPTIONAL vectors sidecar for no-reembed consumers.
2. **Binary vector packing** (Float32 base64 or a columnar format): ~4 bytes/dim vs ~13 chars/dim → ~170MB — better but still heavy; combines with (3).
3. **Chunk census**: is 28,398 the honest corpus size, or do stale/duplicate chunks inflate it? (The KB grew enormously this cycle; a dedup/staleness pass may pay for itself.)
4. **Size tripwire in the script**: warn/fail above a budget so the next 256× surprise is caught at package time, not at upload-watch time.

## Acceptance Criteria

- [ ] Artifact size returned to the operator's expected order (~tens of MB) OR the size explicitly justified + budgeted with the tripwire in place.
- [ ] Download-side import path verified against the new shape (round-trip test).
- [ ] Size tripwire in the script.

## Out of Scope

- Memory Core / Graph export policy (not implicated — the guard held).
- The middleware deploy pipeline (#12964, separate).
