# Use toggleCls for single-class AgentOS Fleet markers

## Scope Correction — atomicity gate applied

The original six-primitive prescription was falsified before implementation. Sequential `removeCls(old)` + `addCls(new)` calls publish two reactive `cls` changes and an intermediate state carrying neither semantic class. That is the exact stop condition the original ticket named, and D#15200 still has no graduated atomic replace/batch primitive.

This leaf is therefore narrowed to the two Fleet mutations that already map to **one** public class-API call:

- `StateDot.afterSetLive` → enforced `toggleCls('fm-live', value)`
- `HealthBar.updateAnimateCls` → enforced `toggleCls('fm-animate-counts', this.animateCounts)`

The four old→new replacement hooks (`EventChip.afterSetKind`, `StateDot.afterSetState`, `HealthSwatch.afterSetState`, and `FamilyRail.afterSetFamily`) remain on their current single aggregate assignment. `SourceHealthMarker.applyHealth` remains on its coherent `set({cls, text})` batch. Their future representation-independent cleanup belongs after D#15200 resolves atomic class replacement; no successor micro-ticket is created now.

The evidence trail is explicit:

- [Fleet intake falsifier](https://github.com/neomjs/neo/issues/15201#issuecomment-4998493057)
- [Cross-app independent measurement](https://github.com/neomjs/neo/issues/15202#issuecomment-4998832975)
- [D#15200 atomicity finding](https://github.com/neomjs/neo/discussions/15200#discussioncomment-17668527)

## Context

Both remaining sites read the aggregate component `cls` array only to enforce one Boolean class. `Neo.component.Base#toggleCls(value, add)` already owns that exact boundary in a single reactive assignment, so these two migrations remove representation coupling without changing transition atomicity.

This is an app-only consumer cleanup. It does not define the future `cls` / `wrapperCls` representation and introduces no new core API.

## The Problem

- `apps/agentos/view/fleet/StateDot.mjs#afterSetLive` copies `this.cls`, adds or removes `fm-live`, and reassigns the aggregate.
- `apps/agentos/view/fleet/HealthBar.mjs#updateAnimateCls` filters `this.cls`, optionally appends `fm-animate-counts`, and reassigns the aggregate.

Each intent is a single enforced Boolean membership. Reading unrelated classes is unnecessary.

## The Fix

Use the existing enforced toggle form at both sites:

```js
component.toggleCls(className, shouldExist)
```

Preserve all state, token, Store, motion, and rendering behavior. Do not migrate any old→new replacement or multi-class batch under this ticket.

## Decision Record impact

None. The change consumes the existing component API and leaves D#15200 fully open.

## Acceptance Criteria

- [ ] `StateDot.afterSetLive` uses one enforced `toggleCls` call and no aggregate `cls` read/reassignment.
- [ ] `HealthBar.updateAnimateCls` uses one enforced `toggleCls` call and no aggregate `cls` read/reassignment.
- [ ] Both true→false and false→true transitions publish exactly one effective `cls` change when membership changes.
- [ ] Unrelated caller-authored and base classes survive both directions.
- [ ] Repeating the same state is idempotent and creates no duplicate class.
- [ ] Focused unit evidence covers both sites and the one-change invariant.
- [ ] The four old→new replacement hooks and `SourceHealthMarker.applyHealth` remain unchanged.

## Out of Scope

- `EventChip.afterSetKind`, `StateDot.afterSetState`, `HealthSwatch.afterSetState`, and `FamilyRail.afterSetFamily`
- `SourceHealthMarker.applyHealth`
- An atomic `replaceCls` / class transaction primitive
- D#15200’s object-shaped `cls` / `wrapperCls` design
- Core, VDOM, SCSS, token, visual-design, State Provider, Store, or Model changes
- Non-AgentOS applications and Workstation

## Avoided Traps

- No sequential remove-then-add for one semantic replacement.
- No aggregate spread/filter/reassign replacement under another local helper.
- No `silentVdomUpdate` or app-local batching seam.
- No new micro-ticket for the deferred atomicity work.

## Ticket intake — the atomicity gate tripped

**Decision: stop before claim.** I did not assign the ticket, create a branch, or modify tracked files.

To assert whether the existing component methods can preserve the ticket's single-assignment behavior, I ran the same `StateDot` transition through both paths under the standard unit-test runtime and observed the reactive `cls` config with `observeConfig()`. A caller-authored class was seeded as a preservation control.

### Falsifier result

Current aggregate transition (`wedged → ok`):

```text
1 cls event:
["caller-authored", "fm-state-dot", "fm-state-ok"]
```

Prescribed public-API sequence:

```text
removeCls("fm-state-wedged")
addCls("fm-state-ok")

2 cls events:
["caller-authored", "fm-state-dot"]
["caller-authored", "fm-state-dot", "fm-state-ok"]
```

The first API event is an observable intermediate state containing neither the old nor the new semantic state class. This is not merely an Effect scheduling concern: each method performs its own `this.cls = cls`, and each assignment reaches `afterSetCls()` / `update()`.

`SourceHealthMarker` makes the contradiction stronger: its existing regression test requires class and text to publish as one coherent reactive batch. Replacing its current `set({cls, text})` with a series of removals/additions would expose several partial class states while text still carries the previous fact.

### Intake verdict

The ticket's prescribed implementation cannot satisfy its current acceptance criteria using only `addCls()`, `removeCls()`, and `toggleCls()`. This is exactly the stop condition already named in the body.

The consumer cleanup remains directionally sound, but it needs an atomic replace/batch primitive resolved through D#15200 first. After that boundary exists, this ticket can resume without an app-local workaround. A separately scoped Boolean-only cleanup could use one enforced `toggleCls(name, state)` call, but it would not satisfy this ticket's six-site contract.
