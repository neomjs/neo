# miniSummary backfill retries silently-empty generations forever, burning the provider for nothing

## Context

Found 2026-07-31 during a remote diagnosis of a CPU-only cloud deployment, corroborated on the local canonical plane. Plan-Authority: INDEPENDENT — runtime defect, no governing epic; sibling of the #16222 failure-handling family.

## The Problem

`MemoryService.backfillMiniSummaries` retries items whose generation returns empty, forever:

- On the cloud deployment: ~43 pending memories × ~20s of 26B CPU generation each, every ~19 minutes, around the clock — supervisor logs show `0 updated, 30 deferred` per pass, then the same set restarts ~35s later. ~2.3 CPU-cores average burned for days, producing zero summaries.
- **Mechanism (corrected after code trace): the OUTPUT is cheap, the INPUT is unbounded.** `buildMiniSummary` feeds the RAW `prompt` + `response` into the summary prompt (`MemoryService.mjs:1628`) — real agent turns run 10-50KB — under `generateMiniSummaryTimeoutMs = 20000` (`ai/configBase.mjs:757`). CPU prefill of a multi-KB turn cannot finish in 20s, so each big item times out at exactly the cap (matching the observed ~20s/item cadence to the second), returns null, defers — and the abandoned request keeps computing on the model server. The tweet-size output would cost ~70 tokens; the untruncated input costs minutes.
- The timeout's own calibration comment records it was tuned on GPU hardware (5.3s warm for ~5k chars). Measured corpus sizes (n=300 sample, document text as proxy for prompt+response): p50 1.9KB / p95 4.8KB / max 7.2KB — on GPU the whole distribution fits the 20s cap; on CPU-only hardware the whole distribution STRADDLES it (matching the observed ~100% deferral at ~20s each). Local constant-pending is therefore likely transient provider-saturation windows, not structural — to be confirmed by a drain observation on an idle provider; the CPU deployment's loop is structural.
- Evidence correction from the first filing: "zero warns" was stream-scoped — the inner timeout warn goes through the MC logger, not the supervisor tail that was captured. The timeout path is the coherent explanation, not silent-empty extraction.
- The pending set grows with inflow (observed 41→43), so the loop is permanent.
- Side effects: the loop occupies the heavy-maintenance mutex, starving REM/dream/tenant-sync; and the generation runs `priority: 'interactive'`, queue-jumping real interactive traffic from a batch job.

## The Architectural Reality

- `ai/services/memory-core/MemoryService.mjs` — `buildMiniSummary` (:1611, fail-soft null paths; its own comment documents the prior null-drain incident and a timeout calibrated on GPU hardware) and the backfill loop (:1856 `deferred++` on falsy).
- The escape-hatch pattern already exists in the same loop: structurally-un-summarizable rows are archived with `reason: 'no-content'` precisely so they "leave the pending set AND count as progress" (:1840-1846). Repeated-empty rows lack the same exit.
- Third instance of one defect family observed the same day: healthcheck canary (retries with no backoff, #16222), tenant repo sync (backs off with no retry), miniSummary (retries with no budget).

## The Fix

*(Operator framing, two constraints: the summary input must stay COMPLETE — prompt, thought, response; cutting it loses the most important content. And a hardware-dependent constant must never need a human recalibration: detecting "too little processing time" and adjusting the window until it fits is exactly what the self-diagnostics/self-healing daemons were built for — the two-ADR immune system.)*

1. **PRIMARY — homeostatic timeout via the immune system (ADR 0025 detect → ADR 0026 config-tier actuation)**: a detector for generation-timeout starvation (a backfill pass whose timeout-rate ≈ 100% and `updated = 0`), consumed by a config-only actuation that widens the generation window — bounded maximum, rate-limited, anti-thrash per the §2.5 envelope, heal-ledger event per adjustment, reversible when measured latency recovers. This is the first concrete instance of the phase-2 homeostatic controller D#13873 anticipated behind ADR 0026's controller-agnostic interface. Input stays complete; the window adapts to the hardware.

   ⚠️ **The window is TWO nested leaves, and the actuation must move both.** Verified at source 2026-08-02: `generateMiniSummaryTimeoutMs` = **20000** sits *inside* `buildMiniSummary`, whose `try/catch` swallows its rejection → `null` → the loop's **falsy** branch (`deferred++`). `miniSummaryTimeoutMs` = **30000** sits at `MemoryService.mjs:1850-1853`, wrapping `summarize(...)` from *outside* the guard → its rejection **escapes** → the sweep's **`catch`** branch. Consequences the controller must respect: (a) widening only the inner leaf becomes a **silent no-op at 30s** — the outer timeout fires first, and the controller reads "widening stopped helping" against a ceiling it never touches, then bounds out or thrashes; (b) crossing 30s **flips every item from the falsy path to the thrown path**, so any detector keyed to one branch goes blind exactly when the actuation is working hardest. The widening bound must therefore be expressed against the **outer** leaf, with the inner held strictly below it.
2. **Complete the input**: the summary prompt currently feeds only `prompt` + `response` (`MemoryService.mjs:1628`) — include `thought` when the node carries it; the reasoning is often the summary's real substance. ~~*(Shipped by #16313.)*~~ **→ SHIPPED THEN WITHDRAWN. Still open, and it needs more than a one-line input change.**

   > **Why it was withdrawn (@neo-opus-ada, corrected by @neo-gpt-emmy's review of PR #16314):** `thought` is private. `queryRecentTurns` forces `projection: 'public'` for any peer read precisely so it never crosses the MCP boundary. But the resulting `miniSummary` is returned **ungated by both public shapes** — the full projection emits it *before* the private-projection gate, and the summary projection takes no projection argument at all. So feeding `thought` to the summarizer laundered private reasoning into a public field as derived text, defeating that gate instead of passing through it. Derived text cannot launder the boundary.
   >
   > **The requirement is not wrong — the operator framing above stands.** Satisfying it safely needs a **private summary tier** the public shapes can withhold: either a second `miniSummary` variant returned only on the authorized `'private'` projection, or a per-row marker that makes a `thought`-derived summary public-ineligible.
   >
   > **Correction (@neo-opus-ada, after reading the seam):** I originally wrote that this "is an architecture change, and it also doubles generation cost on a loop that is being bounded *because* it burns CPU". **The cost claim is wrong** and I am retracting it rather than leaving it to deter the work — a single summary carrying a visibility marker costs nothing extra to produce. There is no second generation pass.
   >
   > **The actual enabling gap is one argument at one dispatch site** (`MemoryService.mjs:1478-1480`):
   >
   > ```js
   > const turns = detail === 'full'
   >     ? await this._hydrateRecentTurnContent(rows, effectiveProjection)   // ← projection-aware
   >     : await this._hydrateRecentTurnSummaries(rows);                     // ← projection-BLIND
   > ```
   >
   > `effectiveProjection` is already computed and in scope. The `full` path receives it and gates `thought` on it (`:1551`); the `summary` path never receives it. **That asymmetry is why `miniSummary` reaches a public peer read ungated**, and it is the root of the leak withdrawn from `#16313`. The tier is therefore: (1) thread `effectiveProjection` into `_hydrateRecentTurnSummaries`, (2) mark rows whose summary consumed private input, (3) withhold-or-fall-back on the public branch.
   >
   > **Still a real design question, just a smaller one:** what a public reader sees when a summary is withheld (raw fallback / nothing / a cheaper public-input summary). That decision is independent of the generation-window work below.
3. **Cancel timed-out requests provider-side** — an abandoned request must not keep computing (that orphaned compute is most of the observed burn).
4. **Safety net — attempt budget + reason ledger**: after N consecutive failures *at the maximum window*, archive the row reversibly (`reason: 'generation-timeout'`, mirroring the `no-content` exit) and tally it — no future variant of this class may loop forever. **Split at #16313 (deliberate, author-accepted):** the pre-controller half shipped without the *maximum window* qualifier, because no maximum window exists until item 1 lands. It therefore archives at the FIXED window and can park rows a widened window would have summarized. Accepted because the burn is live and the archive is reversible and reason-tagged — but the restore is now item 1's obligation, not a hope (AC below).
5. Drop `priority: 'interactive'` from the batch path. *(Shipped by #16313.)*

## Intake amendment — four LIVE specimens from 2026-08-01, and the falsifier frame they fix

This ticket's class ("retries silently-empty generations forever") turned out to be one face of a broader defect family observed live across one day: **health/liveness instruments that cannot distinguish LOAD from DEATH, and retry/lease machinery that cannot distinguish EMPTY-PROGRESS from NO-PROGRESS.** Whoever builds this: the four specimens below are the acceptance surface.

**Specimen 1 — busy-read-as-dead (the wedge, 10:28Z):** a summarize-sessions child ran 27 min at ~84% CPU with the orchestrator state-file mtime stale past the 10-min threshold → `inspect_deployment` classified it as a crash and RECOMMENDED A RESTART that would have killed legitimate work. The probe read mtime; the truth was in the child's CPU + the absence/presence of work receipts.

**Specimen 2 — dead-read-as-alive (the stale lease, 12:07Z):** the pre-stop orchestrator's heavy-maintenance lease (acquiredAt 11:48) survived the 12:03 boot because old and new daemon are both in-container pid 1 — same-pid liveness passed vacuously and the lease blocked the post-restoration backup until a manual operator-approved rm. (The cross-pid half landed as #16262/#16266; the PROGRESS half — a lease holder that is alive but doing nothing — is this ticket's territory.)

**Specimen 3 — the misread pattern generalized:** two independent seats (audit 09:56Z, correction 12:39Z) each initially read orchestrator health labels as death and had to self-correct to "stale-state false-negative; summarizer live." The instrument's word keeps beating the process's behavior — that asymmetry is the defect.

**Specimen 4 — the POSITIVE control (23:0xZ, must be preserved):** the first N=1 tenant sync ran multi-hour whole-tree ingestion by holding the heavy lease in windows and cooperatively yielding to session-summarization and REM extraction between rounds — `Refreshing` entries without completion lines LOOKED like a silent-failure loop, and the falsifier was a MOVING work-product count (KB 61,206 → 60,711). **The falsifier frame for the build:** (a) liveness verdicts must incorporate a PROGRESS signal (work receipts / product deltas), never mtime or pid alone; (b) an empty generation repeated N times is a TERMINAL outcome for the item, not a retry ticket — bound it and surface it (the original miniSummary case); (c) never cache liveness across writers (the #16260 retrospective's do-not-cache constraint applies here verbatim); (d) specimen 4 is the regression guard — a healthy long-runner cycling the lease must still read healthy. ## Implementation-shape correction from the ADR-0019/0025/0026 gate — this ticket is smaller than its own body, and it has an unrecorded dependency

Ran the mandatory `§critical_gates` 10 read (ADR-0019) before touching any `ai/` config surface, then followed it into ADR-0026. Two things changed, and the second is a blocker worth naming before anyone builds.

### 1. The Fix section over-describes this ticket's scope

Item 1 currently reads as though this ticket builds the actuation ("a config-only actuation that widens the generation window — bounded maximum, rate-limited, anti-thrash per the §2.5 envelope, heal-ledger event per adjustment").

**ADR-0026 §2.4 says the actuator already exists and is controller-blind:**

> `diagnosis → [controller selects action] → actuator.apply(serviceKey, action) within the §2.5 envelope → outcome → re-observe`
>
> *"Phase-2 (#13873) swaps in a **homeostatic** controller against the same `apply` interface and the same envelope. **No actuator rewrite** is the binding constraint — the phase-2 controller cannot widen the action set or bypass the envelope."*

This ticket **is** that phase-2 homeostatic controller. So the correct scope is a **diagnosis** (ADR-0025 detect half: generation-timeout starvation, sustained + multi-fact, false-positive-safe) plus a **controller** that selects an action — and explicitly **not** a new actuator, envelope, anti-thrash ledger, or heal-event emitter. Those are `RecoveryActuatorService`'s, already shipped. A bespoke actuator here is an ADR-0026 anti-anchor by name.

Also binding, from ADR-0019 §3 **B4 (safety-critical)**: **never mutate the `AiConfig` singleton at runtime.** Whatever widening means, it is not `AiConfig.memoryService.generateMiniSummaryTimeoutMs = X`. I would have written that.

### 2. The blocker — `reconfigure` is specified but not implemented

ADR-0026 §2.4 fixes the action set as `{restart, recycle, throttle, reconfigure(knownKey), shed}`.

`ai/daemons/orchestrator/services/RecoveryActuatorService.mjs:19`:

```js
const DEFAULT_ACTIONS = Object.freeze(['restart', 'redeploy', 'warm-provider']);
```

`apply()` rejects anything outside that set (`:250`). So **the action this controller needs does not exist**, and three of the ADR's five actions are absent while two shipped actions (`redeploy`, `warm-provider`) are not in the ADR's list. The action set has drifted from its own ADR **in both directions**.

That leaves a real constraint: this controller requires `reconfigure(knownKey)`, and ADR-0026 forbids a phase-2 controller from widening the action set. **Implementing `reconfigure` is therefore actuator work, not controller work** — and it is ADR-sanctioned rather than a widening, since it closes a specified-but-missing action. It is a separate deliverable with a separate owner surface (`RecoveryActuatorService`, ADR-0026's territory).

### What I am doing

Building the **diagnosis half only** for now — generation-timeout starvation, counting a timeout as a timeout on **both** branches per the outer-leaf AC, since which branch a failure takes is a function of the window the controller moves. That half is fully unblocked, is what ADR-0025 owns, and is what any controller consumes regardless of how the `reconfigure` gap resolves.

The controller half stays unwritten until the action exists. Raising the gap to @neo-opus-grace as ADR-0026's author rather than unilaterally extending her actuator.

**No AC changes** — the ACs are still correct about *outcomes*. This corrects the prescription, not the goal.
