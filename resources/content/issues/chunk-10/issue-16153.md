# Cross-window dock exposes a cleared Workstation body

## Context

#15955 deliberately treats appearance as a hypothesis until a current presented-frame witness names the exercised boundary. Its prior Take-17 claim was withdrawn because the MOV came from an older head, and retired `#16152` must stay closed.

A fresh headed run now reproduces the class on current `origin/dev` head `a500254d4fe480cd3fe4667d8a1c121a42843194`. The production tree is unchanged from that head; the only delta is the focused CDP witness in `WorkstationFiveBeatNL.spec.mjs`.

```bash
env -u NEO_FILM_TAKE -u NEO_E2E_ENGINE_PROFILE \
  npx playwright test test/playwright/e2e/workstation/WorkstationFiveBeatNL.spec.mjs \
  -c test/playwright/playwright.config.e2e.mjs --headed --workers=1 --retries=0 \
  --grep 'candidate 2 red control'
```

The witness attaches a minimum frame which preserves the Workstation header while the dense dock body is almost entirely black. Its JPEG SHA-256 is `643961bd63838a095bc73a40363e55fb56a1f7a367600961e0350a8303cb0f6c`.

An independently isolated first-tear-out control stays continuous: baseline `5.3616986832011975`, minimum `4.855493229069374`, floor `3.4851041440807786`. The defect therefore belongs to the second popup's cross-window composition / source-retirement leg, not popup birth or the first detach commit.

Live latest-open sweep: checked the latest 20 open issues immediately before creation; no equivalent found. The latest 30 A2A messages contained no competing claim.

## The Problem

`executeCrossWindowDockStep()` succeeds semantically while at least one consecutive compositor frame presents a cleared main dock body. Worker truth, the remote dock receipt, and popup retirement are therefore insufficient to prove the visible transaction.

The exact current source exposes a structurally capable interval in `Neo.dashboard.DockProjectionReconciler.reconcileProjection()`:

- `src/dashboard/DockProjectionReconciler.mjs:329-339` inserts and commits the visibility-hidden staged shell;
- `src/dashboard/DockProjectionReconciler.mjs:377` moves retained tab chrome;
- `src/dashboard/DockProjectionReconciler.mjs:448-464` physically removes and inserts retained containers;
- `src/dashboard/DockProjectionReconciler.mjs:385-392` swaps old/new shell visibility and commits afterward.

That ordering is the leading mechanism, not yet a license to patch the first plausible line. The minimum frame must first be correlated to the current transaction phase so the repair targets the actual compositor-visible boundary.

## The Architectural Reality

- `DockProjectionReconciler` owns identity-preserving projections for multiple dock consumers; a Workstation-local cover would repair the demo while leaving the framework transaction broken.
- The dock document commits before render effects. A visual repair must not weaken model-first transfer or source/target ownership.
- Surviving `tab.Container`, toolbar, button, pane, store, and DOM identities are the permanence contract. Cloning content to cover the gap is not equivalent.
- `captureWorkspaceContinuity()` is the existing consecutive CDP presented-frame oracle. It crops the real `.workstation-dock-host`; sampled screenshots, DOM presence, and a decoded MOV are weaker evidence.

## The Fix

1. Use the focused cross-window red control to correlate the minimum-entropy frame to the current projection phase.
2. Make the convicted ownership/visibility handoff compositor-safe in `DockProjectionReconciler`; keep the old visible shell populated until the staged shell can become visible with its retained descendants in the same presented boundary.
3. Flip the red control to the positive continuity contract and keep the minimum-frame attachment on failures.
4. Preserve exact component/DOM identity, overflow projection, `DockMotionSignal`, model-first transfer, remote-preview identity, and source-vessel retirement order.
