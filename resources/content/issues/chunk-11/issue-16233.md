# Nothing generates the wake-receiver route manifest, so the host edge cannot be provisioned without hand-authoring secrets

## Context

`ai/daemons/wake/receiver.mjs` refuses to start without a route manifest. `loadWakeReceiverManifest` requires the file to be mode `0600` and every route to carry a `signingKey` of at least 32 characters, an `agentIdentity`, `harnessTargetMetadata`, and a positive `adapterConfig.attemptTimeoutMs`.

The routes correspond to live `WAKE_SUB` subscription records, which are available from `manage_wake_subscription list`.

Part of #16167 — gap 2 names *"routes.json manifest = WAKE_SUB ids + host-held signing keys"* as a deliverable.

## Problem

Nothing produces that manifest. Verified: no generator exists anywhere in `ai/`.

Provisioning the host edge therefore means hand-authoring a file that contains secrets, by copying subscription records out of a tool response, inventing a signing key, remembering to `chmod 0600`, and then discovering the shape rules one `throw` at a time when the daemon refuses to boot.

That was done by hand while proving delivery on this machine, and it cost several round trips. The rules are not discoverable without reading `receiver.mjs` — for example a numeric `schemaVersion` is rejected where the string `"1.0"` is accepted, and the failure surfaces as `409 signed-route-mismatch` rather than anything naming the field.

Two consequences beyond the inconvenience:

- **A hand-written manifest is only validated by the daemon failing to start.** There is no way to check one before deploying it.
- **Rebuilding by hand rotates the signing key**, which silently breaks the container side that signs with the key it was provisioned with. Nothing warns about this; wakes simply stop being accepted with `401`.

## Architectural Reality

The receiver deliberately imports no graph, SQLite, Memory Core config, or database path — it "owns only the local final mile". A generator must respect that boundary or it re-couples the host edge to the container plane it is being wired to. Subscription records should therefore arrive as plain data, not be fetched through a graph import.

The receiver is also the authority on manifest validity. A generator that re-implements those rules creates a second copy that will drift from the daemon that actually enforces them.

## Fix

A generator that maps active `WAKE_SUB` records onto receiver routes, and:

1. validates its output **through the receiver's own loader** before publishing, so a manifest the receiver would reject never reaches the target path;
2. reuses supplied signing keys rather than rotating them, so a rebuild does not break an already-provisioned container;
3. never writes a signing key to stdout or a log, reporting a short fingerprint per route instead so both sides can be compared without either printing the secret;
4. excludes retired subscriptions rather than refusing the build over them.

## Out of scope

- The container-Memory-Core → host-receiver leg. This produces the host side of the shared secret; wiring the sender is separate.
- A managed `ai:host-edge` entrypoint with a `requiredFor` guard — #16229.

## Acceptance criteria

1. A manifest built from live subscription records starts the receiver without hand editing.
2. A manifest the receiver would reject is never published: neither the target file nor any staging file survives the attempt.
3. Rebuilding with existing keys supplied produces byte-identical signing keys for unchanged routes.
4. No signing key appears in any returned summary or log line; a fingerprint is available instead.
5. Retired subscriptions produce no route, and a set containing only retired subscriptions fails loudly rather than writing an empty manifest.
