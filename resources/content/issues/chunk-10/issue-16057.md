# Corpus logical-identity guard: nothing should be able to commit two artifacts that claim the same logical name

## Context

A knowledge-base sync on a remote deployment fails outright with:

```
PullRequestSource: pull request 11982 has more than one local artifact
(resources/content/archive/pulls/v13.0.0/chunk-1/pr-11982.md and
 resources/content/archive/pulls/v13.0.0/chunk-10/pr-11982.md)
— refusing to embed duplicate evidence under one logical name. Repair the corpus first.
```

The refusal is correct. The corpus is not.

## The Problem

`resources/content/archive/pulls` currently holds **27 duplicated logical PR names**, each appearing under two different chunk directories. The `pr-11982` pair has **divergent md5s** (`9263d3f3…` vs `ca5ce901…`), so these are two *different documents* asserting the same identity — not harmless copies. Embedding either one silently would attach one PR's evidence to another's logical name, which is why `PullRequestSource` refuses instead.

Consequences:

- **The full-corpus sync aborts on the first duplicate.** Enumeration never completes, so KB document count stays 0 and `get_ingestion_progress` reports all-null timestamps. A deployment in this state has a Knowledge Base server of zero value.
- **This very likely affects our own KB sync**, which needs verifying as the first act of this ticket. Our KB still answers queries from previously embedded content, so a frozen sync would be invisible — the failure mode is silent staleness, not an error anyone sees.

**The guard never existed** — nothing prevents a duplicate logical name from entering the corpus, and nothing detects one until an embed attempt refuses it, potentially long after the commit that caused it.

## The Architectural Reality

`PullRequestSource` already owns the invariant and enforces it at the right moment — at embed time, fail-closed, with a precise message. The gap is that the invariant is enforced **only** at the point of consumption, by a component that runs on a schedule, possibly on someone else's host, days after the commit that broke it. By then the author is gone and the failure surfaces as "the client's KB is empty."

The invariant is a property of the committed corpus, so it should be checked where the corpus changes. This is the same shape as the config-leaf parity manifest: an invariant a lint asserts at commit time rather than one a runtime discovers later.

## The Fix (one PR)

- **Repair the 27 existing collisions.** Each pair needs a decision, because the contents diverge — this is not a mechanical dedupe. Determine which artifact is authoritative for its logical name (or whether one is misfiled into the wrong chunk) and reconcile.
- **Add the guard**: a lint that fails when two artifacts under `resources/content/archive/**` claim the same logical name, wired into the existing lint surface so it runs pre-commit and in CI.
- The guard must land **with** the repair — added first, CI goes red on `dev`.

## Acceptance Criteria

- [ ] First, verified and reported on this ticket: whether our own KB sync is currently blocked by the same duplicates. That determines whether this is a client-only outage or a silent internal one.
- [ ] All 27 duplicated logical names reconciled, with the basis for each choice recorded — divergent content means a judgement per pair, not a script.
- [ ] A lint fails on any two artifacts sharing a logical name under the archived-content tree; it fails on a deliberately reintroduced duplicate, asserted by a fixture.
- [ ] The guard covers the *class*, not just PR artifacts — any archived-content family keyed by a logical name.
- [ ] A full-corpus sync completes past source enumeration after the repair, evidenced by a non-zero document count.
- [ ] The chunking step that produced two homes for one logical name is identified and named on this ticket, so the guard is a backstop rather than the fix. A guard that only catches recurrences leaves the generator free to keep producing them.

## `[AC1 CLOSED — internal outage confirmed]` + the repair rule is ADR-determined, not mtime-determined

### AC1: yes, our own KB sync is blocked too

Replicated `PullRequestSource`'s exact id-derivation against our real tree rather than reasoning about it:

```
resources/content/_index.json entries: 15,549
markdown files scanned:                 4,351
COLLISIONS:                                27
first throw: id 11982
  a: archive/pulls/v13.0.0/chunk-1/pr-11982.md
  b: archive/pulls/v13.0.0/chunk-10/pr-11982.md
```

The nuance worth measuring: `id` resolves from `indexMap` **first** and only falls back to the basename on a miss, so a populated index could have disambiguated these. It doesn't — both paths miss, both derive the same basename id, and the source throws.

**So this is an internal outage, not a client-only one.** Our full-corpus sync has been aborting at the first collision, invisibly, because the already-embedded corpus keeps answering queries. Every `ask_knowledge_base` answer is served from a snapshot frozen at whenever these landed. That outranks the client-facing symptom, which is only how we noticed.

Also noted: `resources/content/pulls/_index.json` (the type-index tier) is **absent** — only the root index exists. Not the cause, but it means this tree leans entirely on the fragile basename fallback.

### The 27 are one mechanism, not 27 accidents

| property | result |
|---|---|
| pairs | 27 |
| divergent content | 27 / 27 (zero identical) |
| **`chunk-1` on one side** | **27 / 27** |
| `chunk-1` `updatedAt` newer | 27 / 27 |
| `chunk-1` has `contentTrust:`, sibling lacks it | 27 / 27 |
| stale sibling contains the word "client" | **27 / 27** |
| `chunk-1` copy still contains "client" | **6** |

Sibling distribution: chunk-10 (×10), chunk-12 (×4), chunk-2 (×3), chunk-11 (×3), chunk-6 (×2), and one each in chunk-4/5/7/8/9 — all inside `v13.0.0`.

A representative diff shows the delta is small and systematic: newer `updatedAt`, an added `contentTrust` block, and body text where **"client" became "tenant"**. So the newer rendering carries a deliberate terminology correction, and **every stale copy preserves the pre-correction wording**.

### ADR 0004 is the authority, and it names the mechanism

ADR `0004-github-content-architecture.md` establishes a **single universal ordinal-100 chunking primitive** for all tiers and types, and its own Considered-Alternatives section records the footgun by name:

> **Migration footguns** (`migrate-pr-archive-ac8.mjs --fallback-version v13.0.0`) pre-staged 195 PRs into a **sealed-chunk-violating bucket** before v13 was cut

All 27 collisions sit in `v13.0.0`. That is the generator this ticket's last AC asked us to name.

### Which corrects the repair rule I was about to propose

My first instinct was "keep the newer copy" — and that is **wrong**, because it conflates two independent axes:

1. **Location correctness** — determined solely by ADR 0004's ordinal-100 rule. With >100 PRs in the `v13.0.0` bucket they distribute across `chunk-1..N` by ordinal; `chunk-1` legitimately owns ordinals 1–100 and nothing else.
2. **Content freshness** — which rendering has the corrected text.

A file being newer says nothing about whether it is in its ADR-correct chunk. So the repair is: **compute each PR's ADR-correct chunk, keep that path, and ensure the content there is the corrected rendering** — re-rendering if the surviving path holds stale text. Deleting by mtime would satisfy the guard while leaving files in ADR-violating locations, which is how this recurs.

**Do not skip step 2 for the six.** Six `chunk-1` copies still contain "client" even in the corrected rendering, so the sanitization pass was incomplete. Whatever survives the dedupe must be checked for that term rather than assumed clean.

### Revised plan

1. Compute the ADR-correct ordinal chunk for each of the 27.
2. Reconcile so the surviving path is both ADR-correct **and** carries the corrected text.
3. Add the commit-time guard on duplicate logical names.
4. Confirm a full sync completes past enumeration; confirm our own KB ingests again.
5. Separately: the incomplete "client" → "tenant" sweep, and the absent type-index tier.

> A divergent pair cannot be resolved locally. That is a better rule than mine and it is already reviewed and merged. Choosing the "newer" local copy — which is what `contentTrust` presence and mtime would have led me to — is precisely what it exists to prevent. Recording the refutation rather than the conclusion, since the wrong rule is the reusable hazard here.

### Scope correction: the 27 are a subset of 202

The duplicates are the visible symptom of a mis-chunked bucket. Computing ADR 0004 §2.2's ordinal (`floor(itemIndex / 100) + 1`) with §2.5's ordering — *"Archive tier by ascending GitHub ID within each version-folder bucket"* — against complete on-disk membership per §2.2.1:

| Bucket | Unique | Correct shape | Duplicates | Misplaced |
|---|---|---|---|---|
| `issues/v13.0.0` | 1713 | `chunk-1..18` | 0 | 26 |
| `pulls/v13.0.0` | 1445 | `chunk-1..15` | **27** | **146** |
| `pulls/v13.1.0` | 746 | `chunk-1..8` | 0 | 30 |

**202 misplaced artifacts across three buckets**, and two buckets with zero duplicates are also non-conformant — so a duplicate-only guard would leave most of this invisible. `pulls/v13.0.0` currently has `chunk-1` holding 205 files and `chunk-2` holding 142, both spanning the full ID range, while `chunk-3`…`chunk-13` are clean contiguous 100-blocks. That shape is the signature ADR 0004 line 31 already names: `migrate-pr-archive-ac8.mjs --fallback-version v13.0.0` pre-staging into a sealed-chunk-violating bucket — a partial-membership ordinal collapsing everything into the first chunk, exactly §2.2.1's failure mode.

My earlier comment on this ticket asserted that `repairDuplicateArtifacts` "has no scheduled invoker at all — only the `ai:sync-github-workflow` CLI and release-time `publish.mjs`". That is **false**, and the operator caught it.

The orchestrator schedules it:

| Coordinate | Value |
|---|---|
| task | `githubWorkflowSync` — `ai/daemons/orchestrator/taskDefinitions.mjs:427` |
| interval | default **2h** — `configBase.mjs:906`, `NEO_ORCHESTRATOR_GITHUB_WORKFLOW_SYNC_INTERVAL_MS` |
| enablement | `configBase.mjs:1161` `localOnly`, `null` ⇒ profile default: **enabled local, disabled cloud** — correct, a tenant deployment must never sync this repo |
| guard | `syncGithubWorkflowBranchGuard.mjs` refuses unless the working tree is on `dev` |

**Why my search could not find it:** I grepped for `runFullSync` callers. The orchestrator spawns the CLI *script by path* (`args: [path.join(scriptDir, 'maintenance', 'syncGithubWorkflow.mjs')]`), so no reference to the method exists. I searched for the method and concluded about the capability — the same shape as attributing a producer's behaviour by association, which I have been correcting elsewhere all day.

### The corrected mechanism is worse than the one I claimed

Stage 7-b runs the repair. Stage 7-d takes the integrity verdict **after** it and throws while the corpus is unclean; the aggregate verdict then fails the run **before** the generated-content commit. So a corpus with one duplicate repairs itself on disk every two hours and the fix is **never delivered**.

Verified on the canonical clone — on `dev`, so the branch guard passes:

- working tree: **0** duplicate logical names
- committed `dev` at the time: **27**
- **488** uncommitted files under `resources/content`, plus 17 under `apps/portal`

The repair has been succeeding and failing to deliver for weeks. That also explains how ADR 0004 §2.2.1 could record this repair as complete while both of its numbers were still outstanding on `dev`: it was true of a working tree nobody committed.

### What this changes

- **AC6 answer is sharper, not different.** The generator is still `migrate-pr-archive-ac8.mjs --fallback-version v13.0.0`. But the reason its output survived is *delivery*, not a missing repair and not a missing schedule.
- **The guard's value is unchanged and better founded.** "Nothing repairs this" was wrong; "a repair that cannot be delivered leaves every consumer reading the broken state, silently" is the real hazard, and CI-on-push-to-`dev` is what makes it loud.
- **The residual risk is named and is not mine:** the next divergence will again repair on disk and stall before the commit. Delivery is #16002 (facet isolation / all-or-nothing) and #15993 (SEO credential scope).
