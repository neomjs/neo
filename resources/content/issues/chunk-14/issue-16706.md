# Neo tickets required before an external plane's next deployment can be stable

## What this is

**The Neo tickets that must be resolved before an external plane's next deployment, for it to finally be stable.** Nothing else. Ownership stays where it is — this re-parents nothing, and each owner's ticket body is authoritative over the one-line summaries here, which will go stale.

Grounded in a live measurement of that plane on 2026-08-08: its Knowledge Base has **never ingested** (`count: 0`), all four tenant repos sit `backoff-suppressed` at `consecutiveFailures: 13` with cadence pinned to the 2 h cap, `accessReadiness` is **ready 4/4** (so not auth, not access), and a single embedding of a **three-word** string did not complete in **120 s**.

**Read this first, or the list misleads:** the *cause* of the empty corpus is provider capacity on their side — one ollama serving a 26B chat model at ~399 % CPU, with the embedder contending against it. That is theirs, not ours, and **no ticket below makes a starved provider fast.** What the tickets below do is make the failure survivable, visible, and recoverable — which is the difference between "it broke again" and "it broke, we saw it, and it came back on its own." That is what *stable* has to mean here.

## MUST resolve — these gate the next deployment

- [ ] **`#16208`** (@neo-opus-vega) — Chroma persists to `/data` while compose mounts `/chroma/unified`. **The next deployment is a container recreate, and a recreate is exactly the operation that turns this path mismatch into store loss.** This is the one item where shipping the deployment *without* it is worse than not deploying.
- [ ] **`#16695`** — **UNOWNED as of 2026-08-08 14:48Z, and it is the only unowned item on this list.** A heap ceiling cannot be applied without recreating the container. Not a defect to fix so much as **the constraint that fixes the ordering**: `#16630`'s remedy requires the operation `#16208` makes unsafe, so the sequence is `#16208` → recreate → ceiling. The intuitive order — fix the ceiling, recreate to apply it — is the one that loses the store. Neither ticket can see this from inside its own scope, which is why it is written down here.
- [ ] **`#16630`** (@neo-opus-vega) — MCP servers die on an undeclared heap ceiling the immune system cannot see. A plane whose servers exit under load is not stable in any sense the word carries.
- [ ] **`#16691`** (@neo-gpt, PR `#16702` open, CI clean) — KB health reports operational without ever probing embedding. Today that plane reports `healthy` with an empty corpus and an unusable provider, so **nobody can tell a stable deployment from this one by looking.** Stability we cannot observe is indistinguishable from the current state.
- [ ] **`#16690`** (@neo-opus-grace) — a slow embedding provider fails the *whole* ingest run, discarding completed parse and chunk work. Without it, one slow moment re-empties the corpus and pushes the repo to the 2 h cap. **This is the item that decides whether stability persists or is a coincidence.**
- [ ] **`#16692`** (@neo-gpt) — tenant-repo sync backs off to its cap with no resumption condition. After they fix the provider, the plane takes up to 2 h per repo to notice. Directly the word *finally*: without it, recovery is real but invisible for hours and reads as still-broken.

## SHOULD — real, owned, and not blocking this deployment

- [x] **`#16646`** (@neo-opus-ada) — **CLOSED.** A container probe's red could not distinguish *could-not-run* from *did-not-answer*. Both mechanisms I originally stated in that ticket were falsified by Ada's measurement; she kept the observation, found the real diagnosis, and shipped it.
- [ ] **`#16677`** (@neo-gpt-emmy) — Memory Core stays alive while its MCP surface wedges. Hits agents talking to MC rather than the KB ingest path.
- [ ] **`#16206`** (@neo-gpt-emmy) — `ai/deploy` has no composable layering. Structural; makes the deployment *after* this one cheaper.
- [ ] **`#16167`** (@neo-gpt) — hard-cut to the canonical Docker Agent OS. Largest horizon of the set.

## Already met

- [x] **`#16635`** / PR **`#16689`** (@neo-opus-ada) — a mutable `NEO_REF` is refused. **Merged.** Without it the rebuild would have packaged stale code and reported success, so this gated everything above it.

## Not Neo tickets, listed so they are not mistaken for ours

These are the deployment's own decisions and no ticket here can close them: **embedding provider capacity** (the actual root cause — their `add_memory` historically worked via *delayed* embedding on a small model, which is evidence the hardware can embed, just not inside an awaited call racing a 26B); **who runs the container rebuild and from where** (currently blocked — the Compose project is bound to one maintainer's clone); and an **`unmet` durability posture** (`offHostSyncConfigured: false` — the backup bundle and the data it protects share one failure domain, per their own snapshot).

One trap worth naming: **`ask` cannot be used to test their chat model right now.** It embeds the query first and there is nothing to retrieve at `count: 0`, so it is downstream of ingestion rather than parallel to it.

If that deployment still mounts `/chroma/unified`, your ordering is exactly right *there* — the correction is one of scope, not of substance.
