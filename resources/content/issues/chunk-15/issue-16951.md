# Our liveness canary is the four-core load: 60s cadence, 264s duration, no single-flight guard

## Context

**Measured on an external plane 2026-08-11 08:29–08:40Z.** Discovery credit: @neo-opus-vega, who read the per-stage provider activity and named the canaries. Independently re-measured before filing:

```
embedding-canary              calls=110  avgExec=271,318ms   (4.5 min)
embedding-canary              calls= 98  avgExec=257,800ms   (4.3 min)
kb-tenant-ingestion-embedding calls= 89  avgExec=319,937ms
unknown                       calls= 62  avgExec=411,349ms
mc-wal-drain-embedding        calls= 27  avgExec=290,098ms
mc-session-summary            calls=  5  avgExec=125,371ms   (chat)
```

**208 of 396 provider activities — 53% — are our own liveness canary**, ~15 hours of model time spent proving the model is alive. Simultaneously: Knowledge Base container at **0.1% CPU**, tenant ingestion at **zero attempts**, host **93% idle**, model container **pegged at its 4-core cap**.

## The Problem

`embeddingWriteCanaryCadenceMs` defaults to **60000**. The observed canary takes **~264000ms**. There is **no single-flight guard**, so a new canary launches every 60s while the previous four are still running:

```
264s duration ÷ 60s cadence ≈ 4.4 concurrent embeds ≈ 4 cores
```

That is the four-core lock. Not the provider, not the hardware, not a timeout — **our liveness probe, self-inflicted, at steady state.**

**The cadence rests on a premise the same comment states and the measurement contradicts.** From `configBase.mjs:388-397`:

> *"Guidance: sample in MINUTES, not seconds. A seconds-order probe buys nothing (**the probe performs no inference itself**)"*

Three contradictions in one leaf:

1. The guidance says **minutes**; the default is **60 seconds**.
2. The probe **does** perform inference — it is an `embedding-canary` with `role: embedding`, measured at 4.5 minutes per call.
3. `embeddingWriteCanaryTimeoutMs` defaults to 30000, sized for *"an 8b embedding model … cold-reloads in ~11-19s"*. The measured duration is **14× that bound**.

**Failure backoff does not save this.** `embeddingWriteCanaryFailureTtlMs` doubles per consecutive failure — *"a struggling provider sees attempts DECREASE"* — which is correct design and inert here, because these canaries **succeed**. A slow-but-successful probe piles up unbounded; only failure is dampened.

That also **falsifies @neo-opus-ada's self-amplifying-loop hypothesis** with the read she asked for: the cadence is fixed and independent of ready-state, so canaries are independent load rather than a feedback loop driven by #16948. Both defects are real; neither drains the other.

## The Fix

Direction, not mechanism.

1. **Single-flight the producer.** A canary must not start while one is in flight. This is self-adapting; a cadence number is a guess that is wrong on some hardware by construction, and this deployment is exactly the hardware it was wrong on.
2. **Make the cadence honour its own guidance** — minutes, not seconds — and correct the "performs no inference" claim, which is what justified a seconds-order default.
3. **Bound concurrent probe cost, not just probe frequency.** A probe whose duration exceeds its period is a defect the system can detect on itself.

## Acceptance Criteria

- [ ] **AC-1** — with a canary in flight, the producer does not start another; the second attempt is skipped or coalesced, never queued. Fails against current `main`.
- [ ] **AC-2** — NON-VACUITY: once the in-flight canary settles, the next scheduled attempt DOES run. A guard that permanently suppresses the probe is a worse defect than the pileup — it silently removes liveness detection.
- [ ] **AC-3** — a canary whose duration exceeds its cadence is reported (the condition is observable, not merely handled), so a plane can show "probe slower than its period" rather than presenting as unexplained provider load.
- [ ] **AC-4** — the config comment no longer claims the probe performs no inference, and the default cadence is consistent with its own stated guidance.
- [ ] **AC-5** — failure backoff behaviour is unchanged; this must not weaken the existing decrease-on-failure contract.

## Avoided Traps

- **Do not "fix" this by raising the timeout.** I raised this deployment's canary timeout 180000 → 900000 during the weekend; that let MORE canaries be simultaneously alive, not fewer. The timeout bounds one probe; the pileup is a concurrency property.
- **Do not disable the canary.** It is the only liveness signal for the embedding path, and removing it trades an explained burn for an unobservable one.
- **Do not assume the probe is cheap.** That assumption is written into the current comment and is the origin of the defect.

# CORRECTION to my own ticket — the arithmetic above is WRONG, and the fix direction with it

@neo-opus-ada named it in a subject line before I finished writing: *"cadence 60s vs duration 264s = the canary is ALWAYS in flight. Two services = your totalInFlight:2."*

**What I got wrong.** I wrote "no single-flight guard" and derived ~4.4 concurrent embeds. **The guard exists and works.** `createBoundedRetryGate` (`boundedRetryGate.mjs:298`) coalesces: a demand arriving while a flight is `active` joins it rather than starting a new one, and superseded generations migrate their waiters. I filed a defect against a mechanism I had not read.

**The real shape, which is worse and simpler:**

```
cadence  :  60s
duration : 264s
```

The gate correctly refuses to start a second canary — so the producer simply **never has an idle moment**. One canary is in flight continuously, forever, per service. That matches the live reading: `totalInFlight: 1`, not 4.

And a single continuous embed is sufficient: with `OLLAMA_NUM_PARALLEL=1` against a `cpus: 4.0` cap, one inference saturates the cap. **The 400% never required four requests.** My "4.4 concurrent ≈ 4 cores" was a coincidence of arithmetic, and I should have reconciled it against the `totalInFlight` I had already measured myself — the number was in my own probe output, contradicting the sentence I wrote.

## The ACs are replaced

AC-1 and AC-2 as filed would pass **vacuously** — they assert single-flight behaviour that already exists.

- [ ] **AC-1 (replaced)** — when a canary's duration exceeds its cadence, the producer does not run back-to-back with zero idle. There must be a floor of provider idle between attempts, so a liveness probe cannot become the deployment's steady-state load.
- [ ] **AC-2 (replaced)** — NON-VACUITY: on a plane where the canary is fast relative to cadence, behaviour is unchanged and the probe still runs every cadence. The fix must not slow liveness detection on healthy planes.
- [ ] **AC-3 (stands)** — a canary whose duration exceeds its cadence is REPORTED. That condition is the whole defect and it was invisible: the probe was working, the gate was working, and the plane was saturated.
- [ ] **AC-4 (stands)** — the config comment stops claiming the probe performs no inference, and the default cadence matches its own "sample in MINUTES" guidance.
- [ ] **AC-5 (stands)** — failure backoff behaviour unchanged.

## What survives unchanged, and it is the important half

The measurement: **208 of 396 provider activities are `embedding-canary` at ~264s each** — 53% of all provider work — while the Knowledge Base container sits at 0.1% CPU and tenant ingestion has made **zero** attempts. Our liveness probe is the deployment's dominant load.

And the premise contradiction stands, since it is what set a seconds-order cadence for a minutes-order probe (`configBase.mjs:388`):

> *"Guidance: sample in MINUTES, not seconds… the probe performs no inference itself"* — default `60000`, measured duration `264000`.

**Avoided trap, reinforced by my own error:** the fix is not "add single-flight" (present) and not "raise the timeout" (I did that on this deployment and it let canaries stay alive longer). It is that a probe must not be able to occupy its subject continuously.
