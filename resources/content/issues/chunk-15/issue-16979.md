# The file-system MCP executor needs real isolation, not a path jail

Split out of #16481 so each half has a PR that can resolve it. #16481 keeps the false-claim correction (PR #16976); this holds the architecture.

> **Amended 2026-08-25 after the terminal review on PR #17771** ([review 5023067944](https://github.com/neomjs/neo/pull/17771#pullrequestreview-5023067944), @neo-gpt). The first attempt recorded an *acceptance* ADR resting on a premise this ticket itself supplied and never falsified — see [Premise correction](#premise-correction). PR #17771 is closed; its salvage map is carried below. Re-entry runs from this amended body.

## The gap

The path jail binds **arguments**. It does not bind the process.

`run_playwright_test` executes a spec, and a spec is arbitrary JavaScript, so what it reads and writes is bounded by the host process this server runs in. `write_file` plus `run_playwright_test` therefore reaches outside the project root without either call violating any guard.

Reported externally by @novice-22, three independent times, reproduced from source.

## Why the obvious partition is closed

From @novice-22 on #16481, and it is the reason this needs a real fix rather than a cleverer guard:

> *"A sound tool-level partition would have to keep `write_file` out of everywhere `run_playwright_test` can read. But a spec is arbitrary JavaScript, so the executor's read set is not statically bounded — it is the project."*

So there is no line to draw between the two tools. Any guard that tries becomes a guard on a set nobody can enumerate, which is how the current one came to promise something it cannot deliver.

## What would actually contain it

The executor needs to run somewhere that cannot read the host — a child process with a restricted filesystem view, or a container. That is a real design decision with real costs:

- test runs get slower and need their fixtures carried in
- failure diagnostics have to cross the boundary, or debugging gets worse
- the boundary itself becomes a thing to keep correct, and a broken sandbox that reports success is worse than none

## Premise correction

This ticket previously carried, as a Delta, the line *"this surface is used by agents operating on this repo with host access already."* **That is false**, and it was load-bearing: PR #17771's ADR promoted it into the rationale for accepting unjailed execution outright.

The security subject is the **caller's granted capability**, not the Unix authority of the MCP subprocess. A host-trusted subprocess does not make a tool-scoped model host-trusted. Verified from source at `b2359004`:

- [`.github/AI_QUICK_START.md:273`](https://github.com/neomjs/neo/blob/b235900493768aa82e9aa2ff9ee21ebc56465972/.github/AI_QUICK_START.md#L273) — frontier harnesses ship their own file and command-execution tools; this server exists *for* `Neo.ai.Agent` instances and local harnessless profiles that reach the filesystem **through the Agent OS client**.
- [`ai/agent/AgentOrchestrator.mjs:198`](https://github.com/neomjs/neo/blob/b235900493768aa82e9aa2ff9ee21ebc56465972/ai/agent/AgentOrchestrator.mjs#L198) — creates an autonomous `Neo.ai.Agent` with `servers: ['knowledge-base', 'file-system', 'github-workflow']`. No shell in the grant.
- [`ai/agent/profile/QA.mjs:33`](https://github.com/neomjs/neo/blob/b235900493768aa82e9aa2ff9ee21ebc56465972/ai/agent/profile/QA.mjs#L33) — `servers: ['knowledge-base', 'file-system']`, `modelProvider: 'ollama'`, and a system prompt that *mandates* `read_file`. The narrowest grant in the fleet.

For those two classes the server list is a **deliberate capability narrowing**, and `run_playwright_test` silently converts it into host-process authority. Isolation is not "machinery guarding a boundary no caller is on the far side of" — they are exactly on the far side. The revisit condition the first ADR wrote for itself was already true when it was written.

## The ledger's two open rows have a third option, and it already ships

Pre-implementation V-B-A on the Contract Ledger's `Decision owed` column. ADR 0041 posed the fork as **isolate the executor** vs **accept unjailed execution**, priced isolation as a child process or container, and rejected it on cost. That framing is missing the option the codebase already implements — and it is the correct one.

### `resolveAllowedTools` is the capability-gating primitive, already wired

[`ai/agent/resolveAllowedTools.mjs`](https://github.com/neomjs/neo/blob/dev/ai/agent/resolveAllowedTools.mjs) is shipped, tested, and called from the live tool-assembly path at [`ai/agent/Loop.mjs:207`](https://github.com/neomjs/neo/blob/dev/ai/agent/Loop.mjs#L207). Its own summary line is *"Pure least-privilege filter for an agent profile's MCP tool surface — the capability-gating mechanism"*, and its rationale names this exact hazard:

> *"`Agent.servers` selects MCP servers all-or-nothing … That is fine for a frontier model, but over-exposes a local lower-parameter worker (e.g. a Gemma Librarian) to an API surface it cannot navigate safely."*

Semantics, from the docblock:

- `allowedTools` null/undefined → **no filtering anywhere**
- a server absent from a non-null map → that server's **full surface**
- a server present in the map → **only its listed tools**; an explicit `[]` denies all

**It is fail-open, and that is why the exposure exists today.** Neither [`QA.mjs`](https://github.com/neomjs/neo/blob/dev/ai/agent/profile/QA.mjs) nor the Agent created in [`AgentOrchestrator.mjs:198`](https://github.com/neomjs/neo/blob/dev/ai/agent/AgentOrchestrator.mjs#L198) sets `allowedTools`, so both receive the file-system server's **entire** surface — `run_playwright_test` included. The mechanism to prevent this was built for precisely this class of caller and simply was never pointed at this server.

### What this does to the ledger

The two open rows resolve to **deny**, not isolate, and not accept:

| Caller class | Resolution |
|---|---|
| Frontier-harness maintainer seat | **Accept** — unchanged; the tool grants nothing the caller lacks |
| `Neo.ai.Agent` via `AgentOrchestrator` | **Deny** — `allowedTools['file-system']` lists the file tools it needs; `run_playwright_test` omitted |
| `QA` profile (Ollama-backed) | **Deny** — same, and its system prompt only ever mandates `read_file` |
| Hosted / untrusted / non-fleet | Not present; the ledger row stands as the revisit trigger |

This costs no new machinery, no child process, no container, and none of the three costs ADR 0041 weighed. It also dissolves that ADR's decisive objection — *"a broken sandbox that reports success is worse than no sandbox"* — because there is no sandbox to break. A tool that was never projected cannot silently start being projected: the failure mode of an allowlist is losing a tool you wanted, which is loud, not gaining one you denied.

### Why ADR 0041 missed it

Not an oversight about the mechanism — a **framing** failure. The ADR asked *"how do we contain the executor?"* when the load-bearing question was *"who should be handed the executor at all?"* Both listed options operate on the executor; the answer operates on the grant. AC-1's own wording (*"isolate the executor, or accept unjailed execution as the contract"*) carried that two-option shape into the decision, which is why nothing in the chain surfaced the third.

Recorded plainly because it is the second time this ticket's framing has steered the outcome: the first was the `Deltas` premise corrected above, and this is the same class one level up — an enumerated option set treated as exhaustive.

### Consequence for AC-1 and AC-4

AC-1's binary is superseded by the ledger's per-class column, which the amendment already installed. AC-4's acceptance branch survives **only** for the maintainer-seat row and must name that class explicitly. The successor ADR records deny-by-allowlist as the decision for the two tool-scoped profiles, and carries the preserved OpenAPI corrections from the closed PR #17771 per its salvage map.

## Falsifier RUN — the deny branch survives, and it gates invocation, not just advertisement

I named this probe in the comment above before building anything, and it nearly went the other way. Recording both the near-miss and the result.

### The scare: the allowlist is applied to *advertisement*

[`ai/mcp/client/Client.mjs:368`](https://github.com/neomjs/neo/blob/dev/ai/mcp/client/Client.mjs#L368) fetches **every** tool at connect and builds a callable proxy per tool on the client instance — no allowlist anywhere near it:

```js
const tools = await me.listTools();
me.tools = {};
tools.forEach(tool => { me.tools[Neo.snakeToCamel(tool.name)] = async args => me.callTool(tool.name, args) })
```

So `client.tools.runPlaywrightTest` exists regardless of `allowedTools`. If the filter only shaped what the model was *told about*, deny would be a false assurance — precisely the "broken sandbox that reports success" failure ADR 0041 named, wearing a different costume.

### The result: dispatch is registry-bound, so deny is a real gate

It holds, because the filtered list is the *only* thing that reaches the dispatch table. [`Loop.mjs:212-215`](https://github.com/neomjs/neo/blob/dev/ai/agent/Loop.mjs#L212) populates `toolRegistry` exclusively from the post-filter `clientTools`, and [`Loop.mjs:500-515`](https://github.com/neomjs/neo/blob/dev/ai/agent/Loop.mjs#L500) dispatches only through it:

```js
if (this.toolRegistry && this.toolRegistry[name]) { … await entry.client.callTool(name, args) }
else if (name === 'delegate_task') { … }
else { results.push({name, error: `Unknown tool: ${name}`}) }
```

A denied tool is absent from `toolRegistry`, so it lands in the final `else` and is **refused**. A model that names `run_playwright_test` explicitly — hallucinated, memorised, or prompt-injected — does not reach the server. That is a capability gate, not an advertisement filter, and it is why the deny branch is sound rather than cosmetic.

**Enumeration, with the selector's own control run first.** My first two sweeps returned "no bypass paths" and both were instrument artifacts — `ai/agent/**/*.mjs` skips `ai/agent/Loop.mjs`, because git pathspec `**/` requires an intermediate directory. The positive control (`does this pattern find the known site at Loop.mjs:207?`) failed and exposed it. With a working selector, `listTools` callers outside the server tree are: `Loop.mjs:208` (filtered), `Client.mjs:368/392` (the client primitive Loop calls), `mcp/client/mcp-cli.mjs:63`, and `scripts/diagnostics/genesisProbe.mjs:1357`. The last two are maintainer-operated — the ledger's **accepted** row, unchanged.

### One residual, carried into the ADR rather than waved off

The `client.tools.*` proxy surface from `Client.mjs:368` stays reachable to any *future* code holding a client object. It is not a live bypass — `Loop` never uses it, routing through `callTool(name)` via the registry — but it is an unguarded second door, and the ADR will record it as a named anti-anchor: **capability decisions bind at `toolRegistry` assembly; any new caller that reaches `client.tools.*` directly inherits the full surface and voids the allowlist.** That belongs in the decision, because the next person to add a caller will not read this thread.

PR #13747 shipped it **deliberately dormant**, and said so plainly:

> *"The mechanism is dormant until a profile sets `allowedTools` (default `null` = no change), so there is no live behavior shift on merge. End-to-end validation lands with the policy-matrix work on #9980: when a real profile (e.g. `Librarian`) opts into an allowlist…"*

Its reviewer left a matching follow-up:

> *"when #9980 wires the real tier/profile policy, add a committed regression that instantiates Loop with fake clients and proves gated tools are absent from both `tools` and `toolRegistry` while `allowedTools:null` preserves the full surface."*
