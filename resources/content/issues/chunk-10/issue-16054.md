# Intra-deployment A2A trust: a private deployment's members should be able to message each other without pairwise grants

## Context

Observed on a fresh self-hosted private deployment during post-redeploy verification. The identity roster was healthy — 19 AgentIdentity nodes present, auto-provisioned from auth provenance — but **every attempt to initiate a message failed**:

```
Unauthorized: Cannot send to @<recipient>. Requires CAN_REPLY_TO permission or prior message history.
```

The gate is behaving exactly as written. The problem is that it has no bootstrap.

## The Problem

`add_message` admits a send when the sender holds `CAN_REPLY_TO` **or** there is prior message history. On a newly provisioned plane there is neither, and there is no way to obtain the second without the first. So the mailbox is installed, correctly fail-closed, and **unusable**: no member can initiate to any other member until someone grants permissions out of band.

For a deployment with ~15 members that is up to 210 pairwise grants to make a fundamental capability work at all — and every new member re-opens the problem. The result is that A2A reads as broken to the deployment's users even though identity, transport, and storage are all healthy.

**This capability never existed** — it is not a regression. There is currently no notion of "members of the same private deployment are mutually reachable by default."

## The Architectural Reality

The current model is per-pair permission with a history escape hatch. That is the right default for a **multi-tenant** plane, where two callers who share a server share nothing else. It is the wrong default for a **single-organisation private deployment**, where every authenticated member is already inside one trust boundary — the auth provider decided that at login.

So the missing concept is *deployment-scoped trust*: the admission decision belongs to the deployment's posture, not to each pair of members inside it. `autoProvisionIdentitySources` already encodes exactly this reasoning for identity creation — GitLab PAT auto-provisions because a self-hosted GitLab is a scoped caller set, while public GitHub does not. Mailbox admission needs the same distinction and does not have it.

## The Fix (one PR)

Add an AiConfig leaf governing default intra-deployment mailbox reachability, with an env binding, registered in the config-leaf parity manifest:

- Members authenticated by the **same** deployment may initiate to one another without a prior grant when the posture is private/self-hosted.
- Multi-tenant and public-identity postures keep today's pairwise behaviour.
- Explicit grants and revocations continue to work and continue to win; this changes the **default**, not the mechanism.
- Cross-deployment sends are unaffected — this is strictly intra-plane.

## Acceptance Criteria

- [ ] A new AiConfig leaf with an env binding controls default intra-deployment mailbox admission, registered in `ai/scripts/lint/config-leaf-parity.json` in the same commit.
- [ ] With the private/self-hosted posture, a member with no grant and no history can `add_message` to another member of the same deployment.
- [ ] With the multi-tenant posture the current refusal is unchanged, asserted by a test — the permissive path must not be reachable by posture drift.
- [ ] An explicit `revoke_permission` still blocks a send that the default would otherwise allow; the default is a floor, not an override.
- [ ] Cross-deployment / unknown-identity sends still refuse, asserted.
- [ ] The refusal message names the *posture* when it blocks, so an operator can tell "you need a grant" from "this deployment does not permit intra-plane initiation."

## Out of Scope

- Broadcast semantics (`AGENT:*`) — unchanged.
- Wake/subscription authorization — separate surface.
- Any change to identity auto-provisioning.

## AC1's premise is stale — the leaf exists, and the permissive default is already the library default

Read ADR-0019 as the gate before touching any `ai/` config, then went looking for where to add the leaf. It is already there.

`ai/mcp/server/memory-core/configBase.mjs:808`:

```js
defaultReplyPolicy: leaf('open', 'NEO_MAILBOX_DEFAULT_REPLY_POLICY', 'string')
```

Its own documentation describes precisely the two postures this ticket asks for:

- **`'open'`** — *"peer-trust mode… accepts any authenticated sender as a peer… Eliminates the first-message bootstrap tax."* `CAN_REPLY_TO` edges stay queryable; enforcement skips the check.
- **`'blocked'`** — *"strict-isolation default policy. Suited for multi-user / multi-tenant Memory Core deployments… Cross-tenant reach requires explicit `CAN_REPLY_TO` grants."*

It also already holds two things I was about to add as new ACs: the read paths (`CAN_READ_INBOX_OF`, `CAN_READ_MEMORIES_OF`, `CAN_READ_SESSIONS_OF`) stay strict regardless — *"Reading someone's inbox is categorically different from sending them a message; asymmetric treatment is intentional"* — and an explicit grant remains queryable and revocable either way.

So **AC1 as written ("a new AiConfig leaf with an env binding") would duplicate an existing leaf**, which ADR-0019 §3 A6 names as an antipattern outright.

### What this means for the deployment that motivated the ticket

The library default is `'open'`. A deployment whose members cannot message each other is therefore **not missing a feature** — either the env var is set to `'blocked'`, or something else is refusing. And `NEO_MAILBOX_DEFAULT_REPLY_POLICY` **is** present in that deployment's mc-server environment keys, so it is set explicitly rather than defaulted.

**That check has to happen before any code is written here**, because if the answer is `'blocked'` the whole fix is a one-line config change on their side and this ticket should be closed as premise-invalid.

### What might still be real

Two of the six ACs survive the leaf's existence, and neither needs a new leaf:

- **AC6 — the refusal names the posture.** `MailboxService.mjs:1606` currently throws `Unauthorized: Cannot send to ${to}. Requires CAN_REPLY_TO permission or prior message history.` That reads as "you need a grant" in both postures. Under `'blocked'` it should say the deployment does not permit intra-plane initiation, so an operator can tell a missing grant from a policy decision. Same class as #16056: the system knows why and does not say.
- **A posture-derived default.** `defaultReplyPolicy` defaults to `'open'` unconditionally; it does not consult `deploymentMode`. A *cloud* deployment that is nonetheless *private/self-hosted* — one operator, one org, many members — is exactly the case the binary `local`/`cloud` axis cannot express, and it is the case that motivated this ticket. Whether that wants a posture concept or just documentation is a real design question, not an implementation detail.

### Recommended disposition

Rescope to those two, or close as premise-invalid if the deployment simply has the policy set to `'blocked'`. Not proceeding with AC1–AC5 as written.

Recording rather than quietly rewriting my own ACs: the premise was wrong at filing time and the correction belongs where the next reader will see it.

## Correcting my own previous comment: the premise is VALID. Only the prescription was wrong.

I claimed above that this ticket might be premise-invalid, reasoning that `defaultReplyPolicy` cannot explain the reported "could not message anyone" because `MailboxService.mjs:1561` exempts `AGENT:*`, `role:` and `human:` targets from the gate. That reasoning was sound and the conclusion was still wrong, because I never re-ran the failing call.

Reproduced live against the deployment, two sends, two different failures:

**1. The original failed test used an unregistered recipient.**

```
add_message to: 'lme'
→ Unrecognized 'to' format: 'lme' (normalized to '@lme'). Expected '@<identity>' canonical
  form matching a registered AgentIdentity graph node, or 'AGENT:*' for broadcast.
```

`who_is_online` returns a 19-identity roster containing `@lbe` — not `@lme`. So that failure was an addressing error, and its message said so in plain words.

**2. The registered recipient hits the permission gate.**

```
add_message to: '@lbe'
→ Unauthorized: Cannot send to @lbe. Requires CAN_REPLY_TO permission or prior message history.
```

That is verbatim `MailboxService.mjs:1606`, which only executes when `strictReplyPolicy` is true. So `mailbox.defaultReplyPolicy` resolves to `'blocked'` on this deployment.

### Disposition

- **Premise: VALID.** A member of this deployment cannot DM another member without a pairwise grant. That is exactly what the ticket says, now confirmed by the refusal rather than inferred.
- **AC1: still invalid.** The leaf exists (`ai/mcp/server/memory-core/configBase.mjs:808`), carries both postures, is in the parity manifest, and defaults to `'open'` in the library. A second leaf is ADR-0019 §3 A6 duplication.
- **The real gap** is that the default is not posture-derived. `'open'` is the library default; this deployment resolves `'blocked'`. A deployment that is *cloud* **and** *private/self-hosted* — one operator, one org, many members — is precisely the case the binary `local`/`cloud` axis cannot express, and it is why an install lands on the multi-tenant-shaped default when the peer-trust one is correct.
- **AC6 survives and is worth more than it looks.** The refusal says "Requires CAN_REPLY_TO permission or prior message history" and gives no hint that a deployment-level policy decided it. An operator reading that reaches for `grant_permission` pairwise — 15 members is 210 grants — when one env var is the actual answer. Naming the posture in the refusal turns an afternoon into a one-line change.

Rescoping to: posture-derived default + the refusal naming the posture. Dropping AC1–AC5 as written.

Recording the reversal rather than editing the earlier comment: it was wrong for a reason worth keeping — I tested a mechanism against part of the evidence, concluded, and did not re-run the one call that would have settled it.
