# Tenant-repo ingestion has never produced a lastIngestedRev — the embed stage fails and the repo reports "uninitialized"

## Problem

Pull-mode tenant-repo ingestion has **never once succeeded** on the canonical local plane. The clone stage completes and the **embed stage fails**, so nothing a tenant repo contains ever becomes queryable — and the failure is not reported as a failure anywhere a human or a health gate looks.

`get_deployment_state_snapshot` → `snapshot.tenantRepoSync`:

```
status = completed          repos = 1
repos[0].lastIngestedRev                  = null
repos[0].lastOutcome.lastSourceErrorCode  = KB_VECTOR_EMBED_FAILED
repos[0].ingestContractVersion            = null
repos[0].lastAttemptedIngestContractVersion = 2
checkpointRevalidation.uninitializedCount = 1   (currentIngestContractVersion = 2)
```

Note `status = completed` alongside a null `lastIngestedRev` and an embed error. The lane reports completion, the repo reports *uninitialized* rather than *failed*, and the only field that records real progress — `lastIngestedRev` — stays null.

Corroborated independently from the corpus side. `repoSlug` counts in `neo-knowledge-base`:

| repoSlug | count |
|---|---|
| `neo` | 59158 |
| `create-app` | **0** |
| `devindex-opt-in` | **0** |
| `devindex-opt-out` | **0** |

`repoSlug=neo` accounts for the entire collection, so there is **no tenant-ingested content at all**. The query mechanism is sound — it returned 59158 for `neo` — so the zeros are real rather than a broken filter.

## Second defect: configured tenants are missing from the deployed plane

Three tenants were configured (`create-app`, `devindex-opt-in`, `devindex-opt-out`), but the snapshot reports **one** repo and `uninitializedCount = 1`. So "are the tenant repos ingested" is No for two independent reasons: the embed stage fails, *and* most configured tenants are not present on the deployed plane at all.

## Why this is the priority

Every downstream tenant capability — per-repo corpora, multi-tenant retrieval, the whole pull-mode ingestion story — is unproven end to end. Prior work on ingestion error messages and credential/scope handling did not move this, because neither touches the embed stage. There is no green path to point at, so no way to tell a configuration problem from a code problem.

## Acceptance criteria

- [ ] `create-app` ingests end to end: `lastIngestedRev` non-null AND `repoSlug=create-app` count > 0 in `neo-knowledge-base`. **This is the proof artifact** — a passing unit test is not sufficient.
- [ ] `KB_VECTOR_EMBED_FAILED` root-caused and fixed. Candidates to eliminate explicitly:
  - embedding-provider contention with a concurrently running `kbSync`
  - embedding dimension mismatch between the tenant collection and the active provider
  - an unbounded provider call: `TextEmbeddingService` accepts `options.signal`, but it is **optional per caller** — a caller that omits it has no timeout and no cancellation at all
- [ ] All three configured tenants appear in `tenantRepoSync.repos`, or the config gap is explained and closed.
- [ ] A repo whose embed stage fails reports `failed`, never `uninitialized`, and the lane does not report `status = completed` over a null `lastIngestedRev`.
- [ ] `ingestContractVersion` converges to `lastAttemptedIngestContractVersion` on success (currently `null` vs `2`).

## Out of scope

- **`branchRef` main-vs-dev selection.** `tenantRepoAccessContract.mjs:496` documents `branchRef` as "only present when configured" with no default, so an unset value follows the remote default branch — which may not be the active integration line. Real, but branch selection cannot matter while nothing ingests. Deferred until the ACs above pass.
- The mirror/round-trip cost of a first ingestion — that is #16557.
- Backoff and counter-freezing on the failing path — that is #16551.

## Mechanism for `KB_VECTOR_EMBED_FAILED`: the heavy-maintenance lease gates task START, not in-flight work

Observed 2026-08-06, and it promotes the first AC candidate (provider contention) from a guess to a mechanism with a timeline.

**The timeline:**

```
19:06:xx  kbSync starts its embedding loop (1281 batches)
20:12:40  TenantRepoSync: "Refreshing neo-shared/neo"
20:12:43  Orchestrator: "Deferring knowledge base sync; heavy maintenance task
                          tenant repo sync (cloud) is active"
20:17:27  ERROR TenantRepoSync neo-shared/neo failed:
          KB_TENANT_REPO_SYNC_SYNC_FAILED source=KB_VECTOR_EMBED_FAILED
```

Tenant sync **acquired the heavy-maintenance lease at 20:12 while kbSync's embedding loop from 19:06 was still running.** The `Deferring knowledge base sync` line proves kbSync was blocked from *starting again* — not that its in-flight batch loop had stopped. So both were embedding concurrently, and the tenant ingest failed ~5 minutes in.

**Corroborating evidence — the embedder degrades measurably under load.** Batch pacing during a single kbSync run tonight:

| batch | timestamp | gap |
|---|---|---|
| 176 | 22:54:02 | — |
| 177 | 22:54:24 | 22s |
| 178 | 22:56:33 | **129s** |
| 179 | 22:58:44 | **131s** |
| 181 | 23:02:55 | **166s** |

A 4–7x slowdown within one run. An embedding call that takes 7x longer than its baseline is exactly what turns into a timeout-shaped failure for a second concurrent consumer.

**What this changes for this ticket:**

1. The first AC candidate ("embedding-provider contention with a concurrently running kbSync") is now the leading hypothesis, with a mechanism: *the lease serialises task admission, not resource usage.*
2. The identity-collision hypothesis (`neo-shared/neo` sharing `tenantId/repoSlug` with kbSync's stamped chunks) is **not needed to explain the failure**. It remains a real design smell but should not be assumed causal here.
3. **Any attempt to prove tenant ingestion while a kbSync run is in flight will fail for this reason and teach nothing.** Sequence the proof run for an idle embedder, or fix the serialisation first.

**Suggested added AC:** either the heavy-maintenance lease must cover in-flight work rather than only admission, or the embed path must tolerate a saturated provider (bounded retry with backoff — note `TextEmbeddingService` accepts `options.signal` but it is optional per caller, so a caller that omits it has neither timeout nor cancellation).

Evidence: L1 — orchestrator logs read directly, batch pacing measured across a live run.
