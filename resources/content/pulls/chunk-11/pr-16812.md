Resolves #16808

The accepted save now discloses within budget. `addMemory`'s WAL append was already the never-fail durability anchor — but the RESPONSE was held hostage by three unbounded post-durability dependencies (the SYNCHRONOUS mailbox-delta CTE that blocks the event loop, the awaited presence-terminal graph write, and the pending-WAL visibility scan), so on a contended plane an ACCEPTED save could exceed the client's transport timeout and read as `-32001` data loss — the exact misread the disclosure machinery exists to prevent, and today's measured timeout-but-STORED signature. All three are now bounded with honest degradation, and every accepted save self-reports where its response time went via a new `stageTimings` envelope field — a slow save becomes its own diagnosis record instead of a bare timeout.

Evidence: L2 (hermetic guard spec + WriteAhead envelope assertions over the real WAL path, 27/27 scoped green) → L2 required (the delivered slice's ACs are service/spec-observable). Residual on #16808 (stays open-scoped in the ticket's Out-of-Slice list… folded into ticket residual note below): the timeout-but-LOST class needs plane-side instrumentation (`appendWalMemory` under `#16780`-style I/O saturation) and the mailbox CTE's structural cost (expression index / maintained counter) is `#16780`-adjacent schema work — both explicitly out of this slice per the claim comment.

## Deltas from ticket

- The ticket prescribed three repairs (self-degrading mailbox piggyback, latency-bound presence terminal, stage-timing self-report); implementation added the **visibility-read bound** as a fourth after the source read found `describeWriteVisibility`'s pending-WAL scan equally unbounded on the response path — same class, same budget pattern, degraded fallback mirrors the method's own catch-branch semantics (`recencyQueryable: true` stays asserted because it is true BY CONSTRUCTION post-append).
- New shared helper `ai/services/memory-core/helpers/selfDegradingSyncCall.mjs` (sibling of `withTimeout.mjs`): the retrospective budget for event-loop-blocking sync work `withTimeout` structurally cannot race — pay once, learn, skip during cooldown, resume after; errors rethrow (latency pricing never swallows failures). Async bounds reuse the existing `withTimeout` + structural `WITH_TIMEOUT_CODE` — no twin.
- Budgets are module constants, deliberately NOT config leaves: they price the transport contract (client timeouts), not a deployment choice — no `AiConfig` surface touched (ADR-0019 clean by construction).
