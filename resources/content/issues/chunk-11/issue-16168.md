# Containerize Fleet control with request-time seat identity

[PROVISIONAL_UNGRADUATED: D#16176]

## Status

Native child of #15798. This issue reserves the **outcome** of containerized Fleet control with request-scoped seat authority. It is not executable or self-assignable until successor Ideation round #16176 converges and graduates.

D#15595 settled the broad local-parity runtime tuple, but deliberately left the Fleet identity/authorization and service-boundary divergence for a successor round. D#16176 is that source of authority.

## Corrected current state

- Fleet already has a capability-gated HTTP projection facade, but `devFleetServer` resolves one viewer at boot and `fleetBridgeServer` stamps that same viewer onto every request.
- Fleet registry, tenant, and lifecycle services are process-global. Mutating their data root per request is not a safe ownership model.
- Fail-closed one-tenant/one-agent exclusivity already exists and remains the correct fallback while the shared target pins its first provider subject.
- Registry and plane credentials are stored and injected as separate classes. Repository provisioning does not yet consume the registry PAT, so the full credential-use contract is not shipped.
- Public projections and generated MCP artifacts already avoid raw bearer serialization in the covered paths. A host-actuator command/receipt surface does not exist yet.
- Fleet planning, persistence, workspace preparation, and host process effects are currently interleaved in the host process. There is no Fleet Compose service.
- ADR 0026 is security precedent, not direct authority: its daemon-core actuator explicitly excludes client-reachable Fleet lifecycle writes.

## Intended outcome

Run Fleet's cloud-capable control work in the shared Docker Agent OS while a slim local edge retains only effects the container cannot perform.

The container control plane should own authenticated desired state, credential vaults, pure plans, its command ledger, and durable receipts. The host should own unavoidable local process/session effects, host-derived paths, process handles, and replay tombstones. Request ownership must be immutable and server-resolved; operator/global views require an explicit capability.

This is one outcome with at least four prerequisite leaves, not one implementation PR:

1. request-scoped Fleet principal plus owner-scoped registry/tenant schema;
2. pure plan composition plus container service, persistence, health, and ADR 0020 amendment;
3. a separately reviewed closed host-actuator protocol, replay boundary, and one-shot secret handoff; and
4. multi-subject MC/KB admission plus a consumed two-token/two-identity isolation witness.

The exact leaves, dependency edges, storage boundary, actuator transport, secret handoff, and ADR disposition remain design output of D#16176.

## Settled constraints carried into D#16176

- No caller-supplied owner or seat authority.
- No per-request mutation of process-global config or `dataDir`.
- Repository/workflow and MC/KB plane credentials remain separate typed classes.
- A host actuator is closed and curated, never a generic command runner.
- `metadata.launch` arbitrary commands remain host-operator-only or unsupported through the container edge.
- Wake/session effects remain host-local per ADR 0014.
- First-subject pinning remains fail-closed until two distinct credentials resolve to two isolated identities through one shared stack.
- Existing unowned records require an explicit migration; the implementation may not guess ownership.

## Graduation gate

#16168 may be promoted into executable child tickets only after D#16176:

- selects and falsifies its identity/storage, service-boundary, and host-actuator options;
- defines owner principal versus launched resident identity and global/operator capability semantics;
- resolves host reachability/exposure and one-shot secret handoff;
- defines container-owned versus host-owned durable state and crash/replay behavior;
- maps the ADR 0020 amendment plus ADR 0026 disposition; and
- completes the high-blast step-back and family-keyed quorum.
