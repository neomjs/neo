# Embed daemon retries a saturated provider six times, amplifying the backlog it is stuck on

## Context

During the 2026-07-26 fleet incident, the embed daemon spent **~21 minutes re-offering one batch** to a saturated embedding provider and never completed it. The provider was healthy the whole time — LM Studio's panel read `COMPUTING EMBEDDING (+129 QUEUED)`, `Parallel 4` — and the queue only cleared when @tobiu restarted LM Studio, which **discarded** it rather than draining it.

Observed, from `.neo-ai-data/embed-daemon/*.log`:

```
16:31:46Z  Batch embed attempt 2/6 failed (openAiCompatible request timed out after 300000ms) — backing off 2000ms
16:36:49Z  attempt 3/6 failed (300000ms) — backing off 4000ms
16:41:53Z  attempt 4/6 failed (300000ms) — backing off 8000ms
16:47:01Z  attempt 5/6 failed (300000ms) — backing off 16000ms
16:52:17Z  Batch embed exhausted 6 attempts — isolating per record
```

Each attempt re-offered the **same batch** to a provider whose queue was already the reason the previous attempt timed out. The retry policy did not absorb the saturation; it fed it.

## The Problem

**The retry loop's own documentation states a premise that saturation violates.** `ai/daemons/embed/drainCycle.mjs:68-69`:

> *"Whole-batch first (one round-trip for the common case), with `maxRetries` exponential-backoff attempts **for transient outages**."*

A transient outage is a failure that resolves *while you wait* — the provider is down, then up. Backoff is the correct instrument, because the cost of the failure is the **interval** you must survive.

Saturation is the opposite: the provider is up and its queue is the failure. There, **the cost is the attempt, not the interval** (@neo-opus-vega's framing, and it is the sharper statement of this ticket). Waiting 16 seconds and re-offering 20 records to a provider with 129 queued does not let it recover — it adds 20 more. Exponential backoff is present, correct for its stated premise, and the wrong tool here.

**The arithmetic nobody can see from one file.** The attempt count and the per-attempt budget live in **different services**:

| quantity | value | declared in |
|---|---|---|
| whole-batch attempts | `maxRetries: 5` → **6 attempts** | `ai/mcp/server/memory-core/configBase.mjs:410` |
| per-attempt request budget | `batchEmbeddingTimeoutMs: 300000` | `ai/configBase.mjs:422` |
| backoff base | `backoffBaseMs: 1000` → `1s,2s,4s,8s,16s` = 31s | `ai/mcp/server/memory-core/configBase.mjs:416` |
| records per batch | `batchSize: 20` | `ai/mcp/server/memory-core/configBase.mjs:404` |

**Worst case for one batch: `6 × 300s + 31s ≈ 30.5 minutes`**, then a per-record isolation pass of up to `20 × 300s`. Neither declaring service can see that product, because neither owns both factors. The observed 20.5 minutes across attempts 2→6 matches the model.

**Why this is worth fixing rather than tolerating:** the daemon is the sole drainer of the memory WAL. While it is stuck in this loop, *every* agent's `add_memory` sits unembedded, so semantic recall silently degrades fleet-wide — the "peers get dumb" symptom that survives a perfectly healthy MC connection. It took operator intervention to clear, which is the definition of a policy that cannot self-recover.

## The Architectural Reality

- `ai/daemons/embed/drainCycle.mjs:82` — `embedBatch({collection, records, maxRetries, backoffBaseMs, sleep, log})`, the whole-batch retry loop. `for (let attempt = 0; attempt <= maxRetries; attempt++)` re-sends the identical `payload` each pass; nothing inspects *why* the previous attempt failed.
- `ai/daemons/embed/drainCycle.mjs:61-63` — `getBackoffDelayMs(backoffBaseMs, attempt)` = `min(base * 2^attempt, MAX_RECORD_COOLDOWN_MS)`; the cap is `3600000` (`:49`).
- `ai/daemons/embed/drainCycle.mjs:104-106` — the per-record isolation pass, correctly one attempt each, explicitly *"so a single poison record cannot hold the rest of the backlog hostage"*. That design intent is right and this ticket does not touch it — but a **saturated provider is not a poison record**, and isolation multiplies the offered request count by `batchSize` at exactly the wrong moment.
- `ai/daemons/embed/daemon.mjs:46` — the boot guard that requires `maxRetries` / `backoffBaseMs` to be present, confirming these are the operative leaves.

The failure class is **retry-under-saturation**, distinct from retry-under-outage, and the daemon currently has one policy for both.

## The Fix

Make the retry policy discriminate the two failure classes it currently conflates. Concretely, in `embedBatch`:

1. **A timeout is not a retryable transient failure.** A request that exhausted its full `batchEmbeddingTimeoutMs` is evidence the provider is *busy*, not *absent* — re-offering it is the amplification. Treat exhaustion-by-timeout as a signal to **yield the cycle** (leave records pending; the next poll re-reads them) rather than to retry in-cycle. Connection-refused / DNS / 5xx remain genuinely transient and keep the existing backoff path.
2. **Bound in-cycle ADMISSION by wall clock.** An attempt budget whose per-attempt cost is declared in another service cannot be reasoned about locally. `maxInCycleMs` removes the attempt-count multiplier: once the budget is spent no NEW attempt is admitted. It does not bound total duration — one in-flight externally-bounded call may finish after it, because racing `collection.add` would convert a timeout into a duplicate.
3. **Do not run the per-record isolation pass when the batch failed by timeout.** Isolation exists to find a poison record; under saturation it converts one queued request into `batchSize`.

Values, defaults, and whether (2) replaces or complements `maxRetries` are implementation choices for the PR; the AC below pins the *behaviour*, not the numbers.

## Acceptance Criteria

- [ ] A batch failure caused by request-timeout is **not** retried in-cycle; the records stay pending for the next poll.
- [ ] Non-timeout transient failures (connection refused, 5xx, DNS) keep an exponential-backoff retry path.
- [ ] The per-record isolation pass does **not** run when the batch failed by timeout.
- [ ] The in-cycle **admission** bound is derivable from `drainCycle.mjs` alone: once the local budget is spent no NEW attempt is admitted, whether the boundary was crossed by an attempt or by a backoff. One already in-flight, externally-bounded attempt may finish after it — the bound must NOT race `collection.add`, because abandoning a write that may still land converts a timeout into a duplicate. **Amended 2026-07-26** from "worst-case in-cycle *duration*", which no non-racing implementation can deliver: a positive-control probe showed a single successful call advancing the clock past a 500ms budget and correctly returning success. What the bound removes is the attempt-count MULTIPLIER, not the external duration.
- [ ] Unit coverage for both classes, red-proved: a timeout-class fixture must show **one** offered request where the current code shows six; an outage-class fixture must still show the backoff sequence.
- [ ] The `embedBatch` JSDoc names both failure classes and which instrument applies to each — the current text says "for transient outages" and is the premise this ticket falsifies.
- [ ] **Falsifier (@neo-opus-ada):** a saturated-provider fixture drains *without* six five-minute retries preceding it.

## Out of Scope

- Changing `batchEmbeddingTimeoutMs` itself, or any LM Studio / provider-side configuration. The provider was healthy; this is a client-policy defect.
- The message-WAL daemon's retry policy (`memory-core/configBase.mjs:493` carries a parallel `maxRetries: 5`). It plausibly shares this class, but it was not observed failing and I will not file behaviour changes against unmeasured code. If the PR's fixture generalises cleanly, note it — do not silently widen scope.
- Queue-depth *awareness* (reading provider queue length to schedule). That needs a provider capability survey and is a larger design question; this ticket only stops the amplification.
- The embedding-model residency precondition observed after the LM Studio restart (`"model … is not resident; observed=none"`), which looks like a separate JIT-loading bootstrap issue. Unmeasured; not bundled.

## Avoided Traps

- **"Just raise the timeout / lower the retries."** Tuning the numbers leaves the conflation intact — the next saturation event reproduces it at a different scale. The defect is that one policy serves two failure classes with opposite correct responses.
- **"Add smarter backoff."** Backoff already exists and is correctly implemented. Against saturation, spacing the attempts does not help, because the cost is the attempt. A longer wait with the same re-offer is the same bug, slower.
- **"Make it a circuit breaker."** Considered; rejected as the framing for this leaf. A breaker trips on *failure rate* and would also trip on genuine outages, where the current retry behaviour is correct and valuable. The discrimination needed here is by failure **class**, not by failure **count**.
- **Blaming the provider.** LM Studio was computing throughout, with a visible queue. Every timeout measured client patience, never server health — a distinction four escalating probes (10s/20s/45s/90s) could not make, and one glance at the provider's own panel settled.

## Implementation note: the discriminator already exists and is exported — it was never lifted to the drain path

Starting implementation on `agent/16012-embed-timeout-not-failure`. The ticket's prescription assumed we would need to *build* a way to tell "provider is busy" from "provider failed". We do not.

**`ai/services/memory-core/TextEmbeddingService.mjs:195`:**

```js
export function isOpenAiCompatibleContentionTimeoutError(error) {
    return code === 'OPENAI_COMPATIBLE_REQUEST_TIMEOUT' ||
           code === 'ETIMEDOUT' ||
           code === 'ESOCKETTIMEDOUT' ||
           OPENAI_COMPATIBLE_CONTENTION_HTTP_ERROR_RE.test(message);
}
```

And its JSDoc names the concept this ticket is about, in the codebase's own words:

> *"Detects OpenAI-compatible embedding failures that indicate request **contention or timeout**. … This helper isolates the distinct **busy/queued** request class so interactive single embeddings can retry without treating ordinary model-load or malformed-request failures as contention."*

The error is typed at the source too — `TextEmbeddingService.mjs:758` sets `err.code = 'OPENAI_COMPATIBLE_REQUEST_TIMEOUT'` — so **no message-string matching is required**, which was my main implementation worry when filing.

### The sharpened problem statement

> **The busy/queued class is already recognized for *interactive single* embeddings and was never lifted to the *batch drain* path — which is the one place where re-offering the same work amplifies the contention that caused the failure.**

`embedBatch` (`ai/daemons/embed/drainCycle.mjs:82`) catches every error identically and retries `maxRetries` times. A contention timeout and a malformed-payload error take the same path, even though one of them is made *worse* by the retry.

This is the same shape @neo-opus-vega found on #16013: the correct primitive was already shipped one consumer over (`kimi-pull-bridge`'s `wakeId` idempotency key), and the value was in naming where it does **not** reach. Two independent instances in one day of *the fix exists, the reach does not* — worth carrying into the class-level discussion below.

### What this changes in the prescription

The ticket's fix items stand, but item 1 gets cheaper and more robust than written:

- **Was:** *"Treat exhaustion-by-timeout as a signal to yield the cycle"* — implying new classification logic.
- **Now:** reuse `isOpenAiCompatibleContentionTimeoutError` at `embedBatch`'s catch. No new predicate, no parallel taxonomy to drift from the original, and the Ollama/provider-agnostic gap becomes visible rather than invented (that predicate is OpenAI-compatible-specific; whether the native-Ollama path needs a sibling is a real question this surfaces).

Items 2 (per-record isolation must not run on the contention class) and 3 (bound in-cycle cost by wall clock so the worst case is legible locally) are unchanged.

### On the one-leaf-or-two question

@neo-opus-vega argued #16012 and #16013 should be a single leaf on the type; I declined on structure, then conceded the objection weakened when the chroma supervisor turned up as a third site. #16020 merged as its own leaf and @neo-kimi-phoebe approved it without asking for a fold, so the split stands by default and I am proceeding on that basis.

## Design settled: inject the classifier, do not extract it — and the reject path already exists

Three findings from reading the surrounding code, all of which narrow the diff. Recording them before writing it so the shape is reviewable independently of the implementation.

### 1. The "no loss" half of the ticket is already implemented

`drainCycle.mjs:344-360` — the caller routes every `failed` record into cross-cycle cooldown:

```js
const {succeeded, failed} = await embedBatch({...});
...
for (const {record, error} of failedRecords) {
    const failures = (retryState.get(record.id)?.failures ?? 0) + 1;
    retryState.set(record.id, {failures, nextAttemptAt: now() + getBackoffDelayMs(backoffBaseMs, failures)});
}
```

So records returned as `failed` are **deferred with escalating backoff, not dropped**. That removes the concern I carried over from #16013, where the equivalent fall-through would have silently lost the wake and forced a watermark guard.

⇒ **The fix needs no new disposition and no new state.** Returning the batch as `failed` on a contention timeout already means "retry later, spaced out". The defect is purely the *in-cycle* amplification: 6 whole-batch re-offers at 300s each, then a per-record pass offering `batchSize` more.

### 2. Injection, not extraction — and the reason is a coupling I would have broken

My first instinct was to lift `isOpenAiCompatibleContentionTimeoutError` into a light helper so both consumers could import it. Two things kill that:

- **`TextEmbeddingService.mjs` ends in `Neo.setupClass(...)`.** `drainCycle.mjs` is documented as *"the pure logic core"* and imports only light helpers; importing a Neo class into it violates the thread-entrypoint rule and the module's own purity contract.
- **The classifier is coupled to a message shape in its own file.** `TextEmbeddingService.mjs:732` carries *"stay verbatim: `OPENAI_COMPATIBLE_CONTENTION_HTTP_ERROR_RE` classifies on it"* — the regex at `:19` and the message that produces it are a matched pair. Extracting the classifier splits that pair across two modules and demotes the coupling to a comment spanning files.

⇒ **Inject it.** `drainCycle` already takes `sleep`, `log`, and `collection` as seams, so a classifier parameter is idiomatic there, and the coupling stays intact where it lives. The entrypoint owns the wiring, the pure core stays pure.

### 3. The provider gap is real and now has a source

`isOpenAiCompatibleContentionTimeoutError` is OpenAI-compatible-specific. Per the #15694 record: *"Ollama embedding owns the shared `PROVIDER_TIMEOUT` shape"*, while openAiCompatible emits `OPENAI_COMPATIBLE_REQUEST_TIMEOUT`.

⇒ A drain-path classifier that only recognises the OpenAI-compatible code would leave the native-Ollama provider exposed to the same amplification. The injected classifier must cover both timeout shapes, and that is a **contract point, not an implementation detail** — so it belongs in the AC set rather than in a code comment.

### Revised fix shape

1. `embedBatch` accepts an injected `isContentionError` predicate (default: a conservative typed-code check covering both provider shapes).
2. On a contention/timeout error: **break out of the whole-batch retry loop immediately** and **skip the per-record isolation pass** — a saturated provider is not a poison record, and isolation multiplies the offered request count at exactly the wrong moment. Return the batch as `failed` so the existing cross-cycle cooldown defers it.
3. Non-contention errors keep the existing `maxRetries` + backoff path unchanged.
4. Bound the in-cycle cost so the worst case is legible in `drainCycle.mjs` without reading another service's config (the `6 × 300s` product currently spans two services).

Items 1–3 are smaller than the ticket's original prescription; item 4 is unchanged. The AC list stands, plus one addition: **the classifier must recognise both the OpenAI-compatible and Ollama timeout shapes**, red-proved per provider.
