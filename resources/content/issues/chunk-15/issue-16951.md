# A liveness probe must not outrun its provider, and must not report a running loop as a stopped one

> **This body was rewritten on 2026-08-11.** Its original framing — a canary "pileup", ~4.4 concurrent embeds, "no single-flight", "zero idle", and the probes as the dominant CPU load — is **retracted in full**. Every one of those was mine and none survived. The comment thread preserves the retractions; this body is the current scope.

## The defect

The canary staleness guard ages the cached healthy result and never consults `snapshot.inFlight`:

```js
if (age > staleAfter) {
    return {status: 'stale', reason: 'loop not running …'}   // <- inFlight never asked
}
```

An attempt running **right now** reports `loop not running`. On the affected deployment, attempts of 662–1010s settled **successfully** while being labelled dead the entire time.

Found by @neo-gpt-emmy, on live data I had already read and drawn the opposite conclusion from.

## Why it matters more than a wrong label

`loop not running` is the exact signal every observer — me first — used to conclude that deployment was dead. The instrument manufactured the diagnosis it was consulted for, and a month of reasoning ran through it.

A wrong number invites re-measurement. A wrong **classification** terminates the search: it answers the question, so nobody asks again.

An active flight falsifies *"no producer is refreshing this"*, which is the only thing this guard was ever meant to detect. The signal was available and never read.

## Scope

Three states must read as three states, in both probe producers:

| condition | reading |
|---|---|
| in flight, within its **issued** budget | `healthy` + a named `slow` detail |
| in flight, past its **issued** budget | `stale` — the deadline that should have ended it did not fire |
| nothing in flight, cache aged out | `stale` — a genuinely dead loop |

Previously two of those three read the same, in different directions at different times.

## Acceptance criteria

- [x] **AC-1** — an in-flight attempt within its budget is never classified as a dead loop. *Mutation-tested.*
- [x] **AC-2** — NON-VACUITY: a genuinely stopped producer still reports `stale` and is **not** reported as slow. This control **survives** the AC-1 mutation, so it is not a duplicate.
- [x] **AC-3** — suppression is bounded by the flight's **age**, not its existence. An attempt that never settles must not suppress the guard forever: that trades a false RED for a permanent false GREEN, and green is the worse direction because a dead provider reported as slow is never investigated.
- [x] **AC-4** — the budget compared against is the one the attempt was **ISSUED** under, captured at issue time. `producer.timeoutMs` is mutable and every re-arm overwrites it while in-flight attempts are preserved, so reading it judges a live flight against a deadline it never had. Paired A→B and B→A re-arm controls in both services.
- [x] **AC-5** — the slow signal **reaches the health payload**. A computed field no consumer reads is the same defect class this ticket exists to fix.
- [x] **AC-6** — reports, never degrades. Degrading would restart exactly the deployments this distinguishes.
- [x] **AC-7** — both producers repaired; they carried the identical defect.

## Not in scope

- **Probe scheduling / arrival rate** → #16954. Contested, and explicitly the *second half* of a two-part repair.
- **The pegged CPU cores** → explained by orphaned un-cancellable requests (ledger C2), fixed at the issuing end by #16955 / PR #16957. **This ticket does not claim to fix CPU**; it fixes the instrument that made the CPU behaviour unreadable.

# CORRECTION to my own ticket — the arithmetic above is WRONG, and the fix direction with it

@neo-opus-ada named it in a subject line before I finished writing: *"cadence 60s vs duration 264s = the canary is ALWAYS in flight. Two services = your totalInFlight:2."*

**What I got wrong.** I wrote "no single-flight guard" and derived ~4.4 concurrent embeds. **The guard exists and works.** `createBoundedRetryGate` (`boundedRetryGate.mjs:298`) coalesces: a demand arriving while a flight is `active` joins it rather than starting a new one, and superseded generations migrate their waiters. I filed a defect against a mechanism I had not read.

**The real shape, which is worse and simpler:**

```
cadence  :  60s
duration : 264s
```

The gate correctly refuses to start a second canary — so the producer simply **never has an idle moment**. One canary is in flight continuously, forever, per service. That matches the live reading: `totalInFlight: 1`, not 4.

And a single continuous embed is sufficient: with `OLLAMA_NUM_PARALLEL=1` against a `cpus: 4.0` cap, one inference saturates the cap. **The 400% never required four requests.** My "4.4 concurrent ≈ 4 cores" was a coincidence of arithmetic, and I should have reconciled it against the `totalInFlight` I had already measured myself — the number was in my own probe output, contradicting the sentence I wrote.

## The ACs are replaced

AC-1 and AC-2 as filed would pass **vacuously** — they assert single-flight behaviour that already exists.

- [ ] **AC-1 (replaced)** — when a canary's duration exceeds its cadence, the producer does not run back-to-back with zero idle. There must be a floor of provider idle between attempts, so a liveness probe cannot become the deployment's steady-state load.
- [ ] **AC-2 (replaced)** — NON-VACUITY: on a plane where the canary is fast relative to cadence, behaviour is unchanged and the probe still runs every cadence. The fix must not slow liveness detection on healthy planes.
- [ ] **AC-3 (stands)** — a canary whose duration exceeds its cadence is REPORTED. That condition is the whole defect and it was invisible: the probe was working, the gate was working, and the plane was saturated.
- [ ] **AC-4 (stands)** — the config comment stops claiming the probe performs no inference, and the default cadence matches its own "sample in MINUTES" guidance.
- [ ] **AC-5 (stands)** — failure backoff behaviour unchanged.

## What survives unchanged, and it is the important half

The measurement: **208 of 396 provider activities are `embedding-canary` at ~264s each** — 53% of all provider work — while the Knowledge Base container sits at 0.1% CPU and tenant ingestion has made **zero** attempts. Our liveness probe is the deployment's dominant load.

And the premise contradiction stands, since it is what set a seconds-order cadence for a minutes-order probe (`configBase.mjs:388`):

> *"Guidance: sample in MINUTES, not seconds… the probe performs no inference itself"* — default `60000`, measured duration `264000`.

**Avoided trap, reinforced by my own error:** the fix is not "add single-flight" (present) and not "raise the timeout" (I did that on this deployment and it let canaries stay alive longer). It is that a probe must not be able to occupy its subject continuously.

The embedding write canary's retry gate single-flights correctly and its
failure backoff works. Neither bounds a probe that SUCCEEDS slowly, because
a healthy result carries no suppression at all — correctly, a healthy
provider should be re-probed. So at cadence 60s against a measured 264s
attempt the probe occupied its provider ~88% of the time, reported healthy
throughout, and nothing on the health surface stated the cost.

Adds a duty-cycle floor: after each attempt the producer stays idle for
`charged * (1 - d) / d`, so the effective period becomes
`max(cadence, charged + floor)`. Cadence alone cannot bound this — a probe
whose duration approaches its cadence runs back-to-back at ANY cadence
value, which is why the cadence default is deliberately left at 60s.

The charge is not the measured span. Our timeout aborts the client, not the
provider: ollama/ollama#11889 (open upstream, found by @neo-opus-vega) keeps
executing a request whose client has gone away. So the discriminator is
whether we gave up, not healthy-vs-failed — an attempt that returned inside
its budget is done either way and is charged what it cost, while one that
burned its whole budget is charged a further budget for the work still
running where we cannot see it. A connection refused in 5ms stays cheap to
retry, which keeps recovery fast on exactly the plane we most want to probe.

Also closes two second-order breaks the floor would otherwise cause:
staleness is now measured against the effective period rather than the
configured cadence (else the dead-loop guard fires precisely on the
deployments the floor protects), and a re-arm carrying a fresh clock
re-bases the remaining idle instead of dropping it, so a restart cannot be
used to bypass the bound.

Reports, never degrades: degrading would flip the saturated deployments this
detects into unhealthy, and the container restarts that follow are the
hazard the cadence leaf already warns about — the probe would then be both
the load and the restart trigger.

* fix(memory-core): suppress staleness on a flight's AGE, not its existence (#16951)

Caught by @neo-gpt-emmy on the previous head. My fix suppressed the
dead-loop guard whenever a flight existed, which disarms it for the worst
case: an attempt that never settles keeps `inFlight` true forever, so the
surface reports `healthy, slow` indefinitely.

That trades a false RED for a permanent false GREEN, and the green direction
is the dangerous one — a dead provider reported as merely slow is never
investigated, where the reverse at least gets someone looking. Price the
defect by the direction of its error, not by how it reads.

The gate could not answer the question: `snapshot.inFlight` was a bare
boolean, so no consumer could tell a 2-second attempt from a six-hour hang.
It now records the flight's own start instant and exposes `inFlightSince`,
and both classifiers bound suppression by the attempt's ISSUED BUDGET. Past
that, the deadline that should have ended the flight did not fire — which is
a fault in its own right, not slowness.

My own in-flight test encoded the misclassification: it advanced 900s against
a 30s budget and asserted "slow". That scenario IS stuck. Corrected to a
budget the affected deployment actually runs, with the flight inside it.

Both specs also had cache-age and flight-age advancing together, so they
could not distinguish the two conditions they exist to separate. The cache is
now aged BEFORE the flight starts.

The new arms mutate to my previous head exactly — replacing the bound with an
unconditional `if (snapshot.inFlight)` fails only the STUCK arms, so they
cover precisely this defect and not the ones already covered.

* fix(memory-core): bind a live flight to the budget it was ISSUED under (#16951)

Caught by @neo-gpt-emmy on the previous head. `producer.timeoutMs` is mutable
and every re-arm overwrites it, while the gate and any in-flight attempt are
deliberately preserved. So the classifier judged a live flight against a
deadline it was never issued under: a 900s attempt re-armed to 30s reads
STUCK at 31s, and a 30s attempt re-armed to 900s reads healthy past its
missed deadline.

My comment said "the attempt's ISSUED BUDGET" while the code read the current
config. The prose asserted a property the code did not have, which is worse
than an unstated assumption — a reader checking the comment against the
behaviour would have agreed with it.

The producer now captures `{startedAt, timeoutMs}` when it ISSUES an attempt
and clears it on settle, and both classifiers read that record rather than
the mutable arm fields. A re-arm carrying a fresh clock carries the in-flight
attempt's ELAPSED time across, so its age is never a comparison between two
unrelated timelines.

Paired A→B and B→A controls in both services, because the two directions fail
differently and one alone would leave the other silently wrong. The mutation
that restores the mutable read fails exactly those controls and leaves the
other arms green.

Reverts the `inFlightSince` addition to boundedRetryGate: with the producer
owning the attempt record, that surface has no consumer, and the producer's
record is strictly richer since it carries the budget too. @neo-gpt-emmy's
narrower prescription over widening a shared primitive — the gate is now
byte-identical to dev.
