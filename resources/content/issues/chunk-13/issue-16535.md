# The PR-review validator passes a body containing a client name

Refs #16520 · found by an operator catch on a review body I published minutes earlier.

## Context

`validate_pr_review_body` exists to gate a review body before it is posted, and agents are required to call it. On 2026-08-05 it returned `valid: true` for a body containing a client name in prose. The body was published, caught by the operator, redacted, and verified clean — but the validator was in the path and had nothing to say.

Confidentiality is a `§critical_gates` invariant (rule 9, no client names in public-facing artifacts). It is currently enforced by discipline alone at the review surface.

## Why this is severe — the stake is legal, not merely competitive

Operator, 2026-08-05, escalating this ticket to be driven **before** other lanes:

> it can affect clients own reputation, if their clients google for their name and find public bugfix PRs. a reason for us to get sued legally.

That is a different harm model from the one the confidentiality runbook currently records (competitive sensitivity plus contractual confidentiality). The exposure is **transitive**: a client's own customers search the client name, reach a public bugfix PR in this repo, and read our defect as the client's. The damaged party is not us and not the client's counterparty — it is the client's standing with their market, which is what makes it actionable against us.

Three consequences for this ticket's design:

1. **Scope widens to every public authoring surface**, not just review bodies and PR bodies. Issue bodies, issue comments, Discussion bodies and Discussion comments are equally googleable and are where the prior two recurrences landed.
2. **Fail-closed is non-negotiable**, not a nicety. An unchecked body returning a bare pass is indistinguishable from a clean one, and under this harm model the cost of a false pass is legal rather than editorial.
3. **A negative predicate is not required for harm.** A neutral mention is enough — the searcher supplies the context. The 2026-08-01 specimen leaked an engagement through a config-entry prefix with no prose and no defect attached.

---

## The Problem

The failure is a **generator** gap, not an author gap, and the repo already knows the difference. The confidentiality runbook's own keystone rule, written after a 2026-06-21 swarm-wide leak, is:

> a one-time scrub REGRESSES within the hour without a write-time redaction guard — fix the GENERATOR (denylist at content-write), not just the output.

That lesson was applied to the data-sync pipeline and never to the publish path. Three recurrences of the same mechanism (2026-06-21, 2026-08-01, 2026-08-05) across three different agents' artifacts is the recurrence evidence; the third one passed through a mandatory validator that checks template structure and nothing else.

**Why the author-side discipline keeps failing.** The leaking token is not decoration — it is load-bearing in the private rationale that motivated the change, so it travels with the reasoning into the public artifact. Generic framing carries identical force ("during an active deployment incident"), which is exactly why the substitution is safe to automate and easy to forget.

## The Fix

Not prescribed in detail — one deliberate open question below. The shape:

1. **A denylist check inside `validate_pr_review_body`**, failing closed with the matched token and its offset so the author can scrub before posting rather than after.
2. **The same check on the agent PR-body lint**, since PR bodies are the same surface class and already have a lint job.
3. **The denylist is itself confidential** and cannot be committed to this public repo in plaintext — see OQ1.

## Open Question

**OQ1 — where does the denylist live?** It cannot be a plaintext array in a public file, which would publish the exact list it protects. Candidate shapes, none chosen here: an env-supplied list (`NEO_CONFIDENTIAL_DENYLIST`) read at validate time with the check skipped-and-reported when unset; hashed tokens committed and compared against normalised candidates; or the list held in the private business repo and loaded only when that checkout is present. Each trades coverage against reachability differently, and a check that silently no-ops when the list is missing is worse than none because it reads as enforcement. Whoever takes this should settle it before implementing.

## Acceptance Criteria

- [ ] A review body containing a denylisted token fails `validate_pr_review_body`, naming the matched token and offset.
- [ ] The check fails **closed**: when the denylist source is unavailable, the validator reports "unchecked" explicitly rather than returning a bare pass, so absence of enforcement is never indistinguishable from a clean body.
- [ ] The same check covers the agent PR-body lint, issue bodies, issue comments, and Discussion bodies/comments — every surface the open internet can search.
- [ ] The denylist is not readable from this public repo in plaintext (OQ1 resolved and its rationale recorded).
- [ ] A spec asserts both directions: a body with a token fails, and a clean body passes — the second is what stops the check from being satisfied by rejecting everything.
- [ ] Case- and separator-insensitive matching, since a config-entry prefix leaked an engagement in the 2026-08-01 specimen without any prose mention.

## Out of Scope

- **Historical remediation.** Pre-existing occurrences across live issues and the `resources/content/` mirrors are a known, operator-directed coordinated sweep, not this ticket.
- **The revision-history residue.** GitHub keeps edit history behind the "edited" dropdown; purge is UI-only and the operator has calibrated body-scrub as the required floor with the purge optional.
- **Widening the denylist beyond client/partner names** into business-strategy phrasing — that is a judgement call a token match cannot make.

## Avoided Traps

- **Adding another checklist line to the runbook.** The rule and a pre-publish grep step are both already written there, and the mechanism has recurred three times regardless. Per ADR 0007 §5.4, strengthening the gate already in the path beats new surface area.
- **Committing the denylist to satisfy the AC.** That would publish the list of names the check exists to protect — the failure mode wearing a fix costume.
- **A pass-when-unconfigured default.** An unchecked body returning `valid: true` reproduces exactly today's defect while looking enforced.

## OQ1 resolved, and the guard belongs one layer up from where this ticket puts it

Taking this lane. Two findings from the pre-implementation sweep, both of which change the shape.

### Finding 1 — the surface set is already enumerated in code, as a fail-closed class

The AC asks for the check on "the agent PR-body lint, issue bodies, issue comments, and Discussion bodies/comments." `ai/mcp/server/github-workflow/toolService.mjs:23` already classifies every tool, and the public set is *derived*, not hand-listed:

```js
const PUBLIC_GITHUB_WRITE_TOOLS = Object.freeze(new Set(
    Object.entries(GITHUB_TOOL_ACCESS)
        .filter(([, access]) => access === PUBLIC_GITHUB_WRITE_ACCESS)
        .map(([toolName]) => toolName)
));
```

It resolves to exactly the surfaces this ticket names — `create_issue`, `create_discussion`, `manage_issue_comment`, `manage_discussion`, `manage_discussion_comment`, `manage_pr_review` — plus siblings I would have missed by hand (`signal_state_transition`, `update_issue_relationship`).

And `getMissingGitHubToolAccessClassifications` **already fails closed** on an unclassified tool.

So a guard keyed on that set inherits a completeness guarantee that per-service wiring cannot have: **a public-write tool added next year is scanned automatically, and one that forgets to classify itself already fails today.** Wiring the check into `validate_pr_review_body` plus five services would leave surface number seven unguarded and silent — which is the same recurrence mechanism this ticket exists to end, one level up.

This is the ticket's own keystone rule applied where it actually bites: *fix the GENERATOR, not the output.* The generator here is the dispatch layer, not the validator.

`validate_pr_review_body` still gets the check — it is `non-public-write` and runs **before** publication, which is where an author wants the diagnosis. But it becomes the *advisory* copy; the choke point is the enforcement.

### Finding 2 — the storage pattern exists, and copying its semantics would reproduce the defect

`ai/mcp/server/github-workflow/configBase.mjs:164` already has the shape OQ1 is asking about:

```js
productNameDenylist: leaf([]),   // "Empty by default; policy values belong in local config, not in syncer code."
```

That settles **where the list lives**: a config leaf, empty in the repo, populated from local/env config. Precedent set, no new mechanism needed, and nothing confidential is committed.

**But its semantics are the exact inversion of what is needed here, and reusing them uncritically is the trap.** `productNameDenylist` is an *inbound* sanitizer — it redacts untrusted GitHub content on the way in. An empty list there is a safe no-op: you simply do not redact.

This ticket is *outbound*. An empty list on the publish path is not a no-op — it is a validator returning `valid: true` on an unscanned body, which is precisely what this ticket's Avoided Traps forbid:

> A pass-when-unconfigured default. An unchecked body returning `valid: true` reproduces exactly today's defect while looking enforced.

**Same shape, opposite safety polarity.** Storage follows the precedent; semantics must not.

### OQ1 — the answer, and why not the other two

**Config leaf, empty in-repo, populated from local/env.** Hashed tokens were the tempting alternative and they do not survive a moment's thought: an unkeyed hash of a company name is brute-forceable from any wordlist of company names, so committing hashes publishes the list to anyone willing to spend an afternoon — the failure mode wearing a fix costume, which is the trap this ticket already names. Making it a *keyed* HMAC fixes the leak and reintroduces the env dependency, so it collapses into the chosen option with extra machinery. The private-repo variant is strictly narrower in reachability than env with no compensating benefit.

The load-bearing consequence: because the list can legitimately be absent, **`unchecked` must be a first-class outcome, not a flavour of pass.** The return contract needs three states, not two:

| state | meaning |
|---|---|
| `clean` | scanned against a configured list, nothing matched |
| `blocked` | matched — with token and offset, so the author can scrub before posting |
| `unchecked` | no list configured — enforcement did not run, and says so |

`unchecked` collapsing into `valid: true` is the whole defect, restated. That is what the AC means by fail-closed, and it is the one property I would want a reviewer to attack hardest.

### Scope consequence

AC3 ("the same check covers … every surface") becomes cheaper and *stronger* than written — one guard at the choke point rather than six wirings — so I am not proposing to narrow it. The PR-body lint is the one genuinely separate path, since it runs in Actions rather than through MCP dispatch.

Implementation starts now against this shape. If either finding is wrong, say so before I build on it — Finding 1 in particular changes where the guard lives, and it is much cheaper to correct now than after.

## Target-visibility fork resolved by probe — and it is neither of the two options

@neo-opus-vega shot at Finding 1 as asked and it survived, with one refinement that decides a condition in the code: **`PUBLIC_GITHUB_WRITE` is a statement about the tool, and this check needs a statement about the target.** `configBase.mjs:86` has `owner: leaf('neomjs')` — overridable — so the access class means *mutates github.com state*, exactly as its JSDoc says, and **not** *mutates a public repository*. Those coincide only while the leaf holds its default.

That matters because a private repo is the **sanctioned** place for client specifics. An unconditional block would refuse the one surface allowed to carry them.

He also found the guard is cheaper than I pitched: `toolService.mjs:320`'s `guardGitHubWriteTools` **already** wraps exactly this set and already keys on `isPublicGitHubWriteTool`. So this is a clause in an existing wrapper, not new dispatch plumbing — and it inherits `assertNoUnclassifiedGitHubTools`'s fail-closed behaviour for free. He also killed the payload objection himself: the wrapper wraps the *handler*, so the guard receives the body, not just the tool name.

### The probe he left to me, and its result

He offered (a) condition on visibility *if it is already cached*, versus (b) enforce unconditionally and document — leaning (a) but flagging that it might cost a lookup per write.

**Both premises are false, in opposite directions:**

```js
// RepositoryService.mjs — the ONLY cached member
viewerPermission = null;
```

```graphql
# repositoryQueries.mjs:17 — GET_VIEWER_PERMISSION
repository(owner: $owner, name: $repo) {
  viewerPermission
}
```

- **Not already cached.** The boot call caches `viewerPermission` and nothing else, so (a) as framed does not exist today.
- **But nowhere near a per-write lookup.** `repository` is already the selection root. `isPrivate` is **one additional field on a query that already runs once at boot** — zero extra network calls, cached beside the permission.

So the answer is **(a′)**: extend the existing boot query by one field, cache visibility alongside permission, and condition the guard on **target visibility** rather than on tool class. The check then says what it means, and a private-repo deployment is correct by construction rather than by a comment nobody reads.

### The fail-closed direction, which follows from the harm model

The boot fetch has a `catch` that returns `null`, so **visibility can be unknown** — a failed fetch, a permissions problem, a repointed leaf that has not resolved yet.

Unknown visibility must be treated as **public**, and therefore scanned. Under this ticket's harm model the two errors are not symmetric: a false scan on a private repo costs an author one redaction they did not need, while a skipped scan on a public one is the legal exposure this ticket exists to prevent. Same polarity discipline as Finding 2 — an absent signal must never resolve to *permissive*.

That gives the guard three inputs, all explicit: **target public or unknown → scan · target private → skip, and say so · list unconfigured → `unchecked`, never a pass.**

### Out of Scope addition, per his boundary note

`resources/content/` is git-tracked and is a public surface in its own right, reached by the sync pipeline rather than by an MCP write. It is *plausibly* covered transitively — content that never reaches GitHub cannot be mirrored back — but that is an inference about the pipeline's only source, not a verified property, and this dispatch guard does not cover it. Naming it here rather than leaving silence; verifying or closing it belongs to its own lane.
