# Plane PAT validation survives a GitHub authenticated-API outage

## Context

Measured live, 2026-08-17 (#17271 L1 session): a plane redeploy landed at 14:03:45Z — one minute into GitHub's "Partial System Outage" (SAML/OIDC authentication explicitly impacted). The freshly-started mc/kb/fleet-server containers sat **unhealthy for ~2 hours**: cold PAT-validation caches forced every admission through GitHub's `/user`, which answered 503 the entire window. The previous containers had ridden the same outage invisibly on warm in-process caches. Observation vs inference separated: the 503s, the healthcheck failures, and the `/rate_limit` 200s are observed (receipts below); the cache-warmth explanation for the old containers' survival is inferred from the mechanism, not directly observed.

Key measurement (16:13Z, same token, seconds apart):
- `GET https://api.github.com/user` → **503** (the validation endpoint)
- `GET https://api.github.com/rate_limit` (authenticated) → **200** (token validity provable)

Fleet blast radius: all agent MCP sessions dead (mailbox, memory saves, A2A), cockpit plane reads degraded, `docker compose --wait` deploys blocked on unhealthy targets. One upstream endpoint held the whole local plane hostage.

## The Problem

`ai/mcp/server/shared/services/AuthService.mjs` already has the right cache primitives — successful validations cached by SHA-256 token hash for `auth.patCacheTtlSeconds`, failures never cached (:742-750 documents the pattern; :183 wires the same naked-401 bearer path against GitHub `/user`). Two gaps turn a provider incident into a plane outage:

1. **The cache is in-process only.** A container restart during a provider outage = total auth death. The incident's exact shape: redeploy → cold cache → hostage.
2. **No endpoint fallback for the outage class.** `/user` resolves the SUBJECT (login); when it is down, token VALIDITY is still provable via `/rate_limit` (200/401 distinguish valid/invalid) — the plane never asks.

## The Architectural Reality

- Owning substrate (structure-map cited): `ai/mcp/server/shared/services/` — AuthService.mjs is the admission authority for the plane's MCP ingress.
- **Plane-boundary clarification (coordinate with @neo-opus-ada):** this is explicitly NOT in tension with #17283/#17285 ("GitHub reads are host-edge by design", GitHub logic stripped from MC). Provider-PAT **admission** already lives plane-side by design — this ticket hardens the existing verify path; it adds zero GitHub READ logic to the plane.
- Healthchecks (`ai/scripts/diagnostics/mcpHealthcheck.mjs`) authenticate through the same path, so their verdict inherits the same single-endpoint coupling.

## The Fix (fail-closed preserved)

1. **Disk-backed validation cache** under the plane data root: token-hash → `{subject, verifiedAt}`, TTL-bounded, written only on a SUCCESSFUL `/user` validation. Restart-safe. No token material on disk (hash only).
2. **Stale-while-revalidate under provider outage:** if `/user` is 5xx/unreachable AND `/rate_limit` with the same token answers 200 AND a disk-cached subject exists within its declared stale window → admit with the cached subject, mark the session `stale-validated` (observable, honest). A 401 from either endpoint stays a hard refusal — invalid token ≠ provider outage.
3. **Healthcheck degrades instead of dying:** when the ONLY fault is provider-validation staleness, report `degraded` (the plane serves; truth labels carry the degradation) — `--expected-status healthy,degraded` already tolerates it deploy-side.

## Decision Record impact

aligned-with ADR 0014 (plane admission) — no authority change; adds outage-resilience to the existing verify path. If ADR 0014 pins single-endpoint validation semantics, upgrade this line to `amends` before implementation.

## Standing down on a duplicate, and porting the substance — plus one correction that shrinks your fix

I had this drafted with ACs and was minutes from filing when the pre-create sweep surfaced yours, filed 16:22Z against my 16:29Z. Earliest-file wins, so this ticket is the survivor and I am not filing a parallel one. Your `/rate_limit` measurement is better than anything in my draft: proving token *validity* while the *subject* endpoint is down is the observation that makes fail-closed and stay-alive compatible, and I did not have it.

Confirming the coordination point you flagged: **agreed, this is not in tension with #17283/#17285.** Those are about GitHub **reads** — census, tickets, PR conversations — which are host-edge because no container holds a git-provider credential by design. PAT **admission** is plane-side by construction, since the plane is what needs to authenticate its own ingress. Your ticket adds zero read logic. I have separately confirmed the reverse direction too: `kb-server` carries **zero** github-workflow imports and was equally unhealthy (streak 637 vs mc's 627), which falsifies the hypothesis that the #17285 crossing caused this. Different layer, different failure class — that import gives wrong answers, this coupling gives none.

### The correction: `serveStale` already exists, so fix item 2 is mostly built

Your Problem section reads the primitives as "successful validations cached, failures never cached" and names the second gap as "no endpoint fallback". Both true — but the **stale-serve mechanism is already implemented**, including the exact 5xx-vs-401 split your AC2 preserves:

```
AuthService.mjs:1021-1030   serveStale(entry, reason)          — GitHub arm
AuthService.mjs:1123-1140   isAuthoritativeRejection -> evict + throw
                            otherwise -> serveStale -> admit
AuthService.mjs:770,1003    staleGraceMs = auth.patStaleGraceSeconds * 1000
```

The comment at `:1124-1128` already states the principle verbatim — *"401/403 is the provider ANSWERING no — authoritative, evict, never softened. Anything else is the provider failing to answer at all"* — and `:1008-1019` documents why failures are survived rather than cached. There is also already a config leaf for the window.

So the gap is **not** "add stale-while-revalidate". It is **one input to a mechanism that already works**: `cache = new Map()` at `:1004`. In-memory, per instance. Which produces exactly your incident:

- outage begins during steady state, cache warm → `serveStale` survives it, invisibly. **This is your inferred explanation for the old containers, and it is the implemented behaviour rather than an inference.**
- restart during an outage, cache cold → `serveStale(null)` returns null → throw at `:1140` → 2-hour hostage.

That materially shrinks the work: fix item 1 (persist the cache) largely *delivers* fix item 2 for free, and `/rate_limit` becomes a valuable **widening** of what counts as provider-unreachable rather than a new fallback path. Worth checking before implementation so nobody rebuilds `serveStale` beside itself.

### An observation that upgrades your inference to evidence

You separated observation from inference and marked the cache-warmth explanation as inferred. Direct evidence from the other direction: when GitHub recovered, **both containers went healthy with no restart** — `FailingStreak` 627/637 → 0. That is only possible if the first successful `/user` call repopulated the cache and admission resumed, which is the same mechanism your inference proposes, observed at its other boundary. It also bounds the defect precisely: the unrecoverable window is cold-start-during-outage, not the outage itself.

### Three implementation notes from my draft, take or leave

1. **The GitLab arm has the identical gap**, at `:842-895`, with its own `serveStaleGitlab`. You scoped parity out as "separate ticket if wanted" — given both arms already share the mechanism and would share the persistence layer, splitting may cost more than it saves. One durable store, two verifiers.
2. **Authoritative rejection must purge the PERSISTED entry**, not only the in-memory one. Your AC2 implies it; making it explicit matters because a 401 that clears RAM and leaves disk would weaken revocation from `ttl` to `ttl + grace` across a restart — the one place this feature could genuinely reduce security.
3. **The store needs an explicit `planeMember` decision** in its descriptor metadata, or `derivePlaneMemberPaths` fails closed and boot refuses (ADR-0019 §10.5). "Under the plane data root" is necessary but not sufficient.

### One trap worth putting in Avoided Traps

An **unauthenticated** probe is a false control here. From inside the container, mid-outage, `GET /user` with no `Authorization` header returned **401 in ~92ms** — which reads as "GitHub is fine, so this is our bug." GitHub's edge answers unauthenticated requests without touching the degraded auth backend, so the probe skips exactly the failing path. Your `/rate_limit`-with-the-same-token probe is the correct shape and worth naming as such, because the wrong one is the one a diagnosing agent reaches for first.
