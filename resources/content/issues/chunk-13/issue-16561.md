# Backup is priority-0 and still starved 8.5h: the lease has no fairness and no signal

## Context

Observed live on the maintainer plane, 2026-08-05T18:1xZ, on an otherwise **healthy** deployment — all five containers up, orchestrator at 0 restarts / 0 OOMs since the 17:12 deploy at `5902ba0aa735`, KB restored to 62,486:

```
heavy-maintenance-lease.json
  owner        : tenant-repo-sync
  acquiredAt   : 2026-08-05T17:54:23.411Z
  staleAfterMs : 21600000            ← 6 hours
  expiresAt    : 2026-08-05T23:54:23.411Z

most recent bundle: backup-2026-08-05T09-39-56.157Z   ← 8.5 hours earlier
```

**Three distinct holders were observed starving the same task across one afternoon** — `tenant-repo-sync` (OOM-killed while holding), then `summary` (took it 8 seconds after a restart released it), then `tenant-repo-sync` again. Each hold is individually legitimate. The backup ran none of those windows.

`offHostSync` is `disabled`, so the plane holds a single copy. Memories written since 09:39Z were covered only because @neo-opus-grace took a verified host snapshot by hand.

Observation vs inference, separated: the counts, timestamps, lease owner and `staleAfterMs` above are measured. *Why* each holder held as long as it did is not established and is not this ticket's claim.

## The Problem

**The scheduler already solves the priority half, and the starvation happens anyway.**

`scheduling/pipeline.mjs:13` — `PRIORITY_ZERO_TASKS = Object.freeze(['backup'])`. Backup outranks every other candidate in the picker by construction, ahead of `stalenessRatio` (`picker.mjs:186`, `(now - lastRunAt) / cadenceMs`) even mattering. **I initially assumed the cadence normalisation deprioritised it** — a 24h-cadence backup 8.5h late scores 0.35 while a 60s-cadence task 2min late scores 2.0 — and that hypothesis is **falsified**: the priority-0 exemption means the ratio never gets to decide.

So the defect is not selection. It is that **winning selection does not get you the lease**:

1. The picker names `backup`.
2. Lease acquisition fails — `pipeline.mjs:55` `'heavy-maintenance-lease-held'`.
3. The current holder keeps it until it voluntarily releases or `staleAfterMs` (**6 hours**) expires.
4. `tenant-repo-sync` has a **60-second** cadence, so on release it can re-acquire before the next poll reaches the backup. A short-cadence holder structurally out-competes a long-cadence priority-0 task for a resource that has no queue.

**And nothing reports it.** No deferral duration is tracked anywhere — `grep` for `deferredSince` / `deferralCount` / `consecutiveDefer` across `ai/daemons/orchestrator/` returns nothing (positive control: `picker.mjs` and `remConsolidationLivenessWatchdog.mjs` both match on `starv`, so the matcher and scope work). Each deferral logs one line and forgets. A plane 8.5 hours without a backup reports `healthy`.

That is the same silent-gap shape as the unowned-`kbSync` incident (#16554): a correct-looking local decision at every step, an aggregate outcome nobody is measuring, and a health surface that reads green throughout.

## The Architectural Reality

- `ai/daemons/orchestrator/scheduling/pipeline.mjs` — `PRIORITY_ZERO_TASKS`, and the `heavy-maintenance-lease-held` / `heavy-maintenance-lease-acquire-error` outcomes (`:54-55`). The lease gate sits **after** selection, so priority cannot influence acquisition.
- `ai/daemons/orchestrator/scheduling/picker.mjs` — `stalenessRatio` and the priority-0 short-circuit. Correct as written; not the defect site.
- `ai/daemons/orchestrator/Orchestrator.mjs:1464` — `isHeavyMaintenanceLeaseActive(now)`, a boolean with no notion of *who is waiting* or *for how long*.
- `AiConfig.orchestrator.heavyMaintenanceLease.staleAfterMs` — 6h. Sized for the longest legitimate hold, which makes it useless as a starvation bound.
- The lease file itself carries `owner`, `reason`, `acquiredAt`, `expiresAt` — no waiter set, so fairness is not expressible in the current shape.

## The Fix

Not fully prescribed — one open question below. The shape:

1. **Track the wait, per task.** A deferred priority-0 task needs a `deferredSince`, so "how long has the backup been unable to run" becomes answerable at all. This is the piece with no design risk and it unblocks everything else.
2. **Report starvation as a health fact.** A priority-0 task deferred past a threshold should degrade the orchestrator's health surface rather than logging one line per poll. The threshold is a *risk* bound (unprotected-data window), not a cadence multiple.
3. **Give the lease fairness, or bound the wait.** Options in the open question.

**Not proposed:** lowering `staleAfterMs`. It is sized for the longest legitimate hold; shortening it to bound starvation would start breaking real work, which trades a silent gap for a loud corruption risk.

## Open Question

**OQ1 — fairness at the lease, or a bypass for the backup?**

- **(a) Waiter registration / handoff.** A deferred priority-0 task records intent in the lease file; a releasing holder must not immediately re-acquire while a higher-priority waiter exists. Fixes the class. Touches a primitive four other lanes depend on.
- **(b) Bounded-wait escalation.** After N minutes of deferral the backup preempts, or the holder is asked to yield at its next checkpoint. Narrower, but "preempt a heavy maintenance task" needs a safe interruption point that may not exist.
- **(c) Signal only** — implement 1 + 2, leave scheduling unchanged. Converts an invisible failure into a visible one without touching the lease. Weakest fix, smallest blast radius, and it is a strict prerequisite for (a) or (b) anyway since neither can be validated without the measurement.

Recommendation: **(c) first**, as its own deliverable, then decide (a) vs (b) against measured deferral distributions rather than against this one afternoon. Sizing a fairness policy from three observed holds would repeat the mistake #16463 documented — a threshold derived from observations taken while the system was misbehaving.

- [ ] The starvation assertion is proven **in both directions**: a starved task reports starved, and a normally-deferred task does **not**. A one-sided test passes for an always-alarm implementation.
- [ ] The threshold is expressed as an unprotected-data window, not a cadence multiple, with its derivation recorded.

## Out of Scope

- **Changing `PRIORITY_ZERO_TASKS` or `stalenessRatio`.** Selection is already correct; this was verified, and the plausible-sounding cadence-normalisation theory is falsified above.
- **Lowering `staleAfterMs`** — see The Fix.

- **The missing backups themselves.** Already mitigated by a verified host snapshot; this ticket is about the mechanism, not the recovery.
- **`offHostSync: disabled`** — single-copy posture is its own decision and not touched here.

## Avoided Traps

- **Fixing the picker.** The obvious read is "the backup is ranked too low." It is ranked *first*. A fix there would have been a no-op that looked like a repair — and would have closed this ticket while the starvation continued.
- **Sizing a fairness policy from one afternoon.** Three holds is not a distribution. #16463 is the precedent for what a threshold derived from a misbehaving system costs.
- **Treating the 6h `staleAfterMs` as the bug.** It is sized correctly for its actual job; the missing thing is fairness, not a shorter timeout.

## AC-4 derivation, from tonight's measurement — and the streak is **not** the quantity this AC asks for

AC-4 wants the threshold *"expressed as an unprotected-data window, not a cadence multiple, with its derivation recorded."* Working it against live data, the deferral streak `bf8d026ecb` now measures is **the wrong input for it**, and that distinction is the derivation.

### Two quantities, and only one of them is data risk

| quantity | what it measures | tonight's value |
|---|---|---|
| `deferredSince` streak | scheduling **fairness** — how long this task has been unable to run | backup: deferred once at `2026-08-07T13:09:23Z` |
| `now - lastSuccessful` | **unprotected data** — how much is at risk right now | **unbounded — `lastSuccessful: null`, `count: 0`** |

**They come apart in both directions, which is why one cannot substitute for the other:**

- a task deferred **briefly** can still have badly stale data (its last few runs failed, so the streak keeps resetting while nothing was ever protected);
- a task deferred **long** can be perfectly safe (it succeeded just before the holder took the slot).

**The streak resets when the task RUNS, not when it SUCCEEDS.** So a repeatedly-failing priority-0 task shows a healthy streak forever while the unprotected window grows without bound. A threshold on the streak would have reported this plane as fine.

### The derivation

> **The threshold is on `now - lastSuccessful`, and the unprotected-data window it bounds is the task's own recovery objective — the interval at which it is scheduled to protect data.** Past one interval without a *success*, the plane is by construction running on data older than the objective its own cadence encodes.

That is not a cadence multiple in the sense AC-4 rejects: the quantity being bounded is elapsed-time-since-protection, and the interval supplies the *objective*, not a multiplier on a poll rate. `24h` here is what the deployment already declared its acceptable data-loss window to be by scheduling backup daily.

**Measured basis, this plane at 2026-08-08T07:53Z:** uptime 27.7h against an 86400000ms (24h) backup interval, `lastSuccessful: null`, `count: 0`. One backup was due, was deferred once at 13:09 on 08-07, and **none has ever succeeded** — so the unprotected window is not 27.7h, it is *the entire life of the plane*, which is exactly the reading a streak-based threshold would have missed.

### Consequence for AC-2 and AC-3

- **AC-2** (health surface) should carry `now - lastSuccessful` for priority-0 tasks, with `deferredSince` beside it as the *cause* field. Fairness answers *why*; the unprotected window answers *how bad*.
- **AC-3**'s both-directions test gains a third arm that the two-arm version would pass while broken: a task **deferred briefly but never succeeding** must report starved. A test with only *starved* and *normally-deferred* arms is satisfied by a streak-based implementation, which is the wrong quantity.
- **`lastSuccessful: null` must not resolve to zero elapsed.** Never-succeeded is the *worst* case, not a fresh one — the same absent-signal-must-not-read-permissive rule this repo has been hitting in three other places today.

### AC-6: the reason `staleAfterMs` is not the lever

Two bounds exist and only one is a fairness mechanism:

| bound | value | reached by | applies to |
|---|---|---|---|
| `maxActiveHoldMs` | **30 min** (`configBase.mjs:1430`) | cooperative yield at a resumable checkpoint | the **1** holder that polls it |
| `staleAfterMs` | **6 h** (measured above) | **eviction** | the **5** that do not |

Only `ai/scripts/maintenance/syncKnowledgeBase.mjs:49` passes `maxActiveHoldMs`. The other five heavy-lease acquirers — `Orchestrator.mjs:582` (`restore-empty-target`), `TenantRepoSyncService.mjs:1178`, `backfill-memory-summaries.mjs:27`, `syncGithubWorkflow.mjs:133`, `ingestTenant.mjs:197` — do not. So for five of six holders the **de facto** hold bound is `staleAfterMs`: **12× the intended fairness bound**, reached by eviction rather than cooperation.

**Which is precisely why tuning it is the wrong move, and it fails in both directions:**

- **Lowering it** does not create fairness, it creates **eviction of live holders**. `staleAfterMs` is a liveness timeout — a holder past it is presumed dead. Shortening it to 30 min would evict genuinely-working multi-hour jobs mid-flight, and the lease contract permits release only at a torn-read-free checkpoint. Eviction has no such guarantee, so this trades starvation for corruption.
- **Raising it** widens the starvation window directly.

So `staleAfterMs` is load-bearing for a *different* property (detecting a dead holder) and is only incidentally the hold bound because the cooperative yield is unwired for five holders. **The lever is making `maxActiveHoldMs` reach those five**, not moving the liveness timeout. That is a wiring gap, and each holder needs its own resumable checkpoint before it can yield — so it is per-holder work, never a sweep.

**Eliminated:** "the holder never releases". `acquiredAt` is `09:28:50Z` and the plane was recreated at `08:51`, so the lease releases and re-acquires normally. ADR-0022's release-time staleness-ratio picker (#13586, shipped) **does** get to run — it simply cannot out-rank a starved lane more often than the lease is released, and for a non-yielding holder that is every 6 hours rather than every 30 minutes.
