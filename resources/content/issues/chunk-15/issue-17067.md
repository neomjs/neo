# Tenant-repo backoff reaches a 2h cap with no operator path to clear it, so a fixed root cause still cannot resume ingestion

## Context

External-plane tenant-sync state, 2026-08-13 19:59Z. Four configured repos, one active, three suppressed:

```json
{"identityHash":"3b6d6176e65c","status":"backoff-suppressed","lastIngestedRev":null,
 "lastSourceErrorCode":"KB_VECTOR_EMBED_FAILED","consecutiveFailures":40}
{"identityHash":"e1daf1ca9706","status":"backoff-suppressed","lastIngestedRev":null,
 "lastSourceErrorCode":"KB_VECTOR_EMBED_CONNECTION_REFUSED","consecutiveFailures":56}
{"identityHash":"0485923578f7","status":"backoff-suppressed","lastIngestedRev":null,
 "lastSourceErrorCode":"KB_VECTOR_EMBED_CONNECTION_REFUSED","consecutiveFailures":62}
```

`scheduler.backoffCapMs: 7200000` — two hours. Orchestrator log:

```text
[TenantRepoSync] apps-global suppressed by backoff
  (next ~2026-08-13T17:36:27.955Z, consecutiveFailures=40, backoffX=1099511627776, ...)
```

## The Problem

The backoff is correct as congestion control: repeated failures should not hammer a broken dependency. What is missing is the **exit**.

Every one of these failures shares a single external cause. When that cause is repaired, the three repos remain suppressed for up to two hours each, and there is **no supported way to tell the scheduler that the world changed**. The operator's only levers are to wait out the cap or restart the orchestrator — and restarting to clear a counter is exactly the reflex this incident class already suffers from.

This turns every fix into a fix-plus-a-two-hour-wait, and it makes verifying a fix expensive: you cannot distinguish "the repair did not work" from "the lane has not been allowed to try yet". During a customer-facing outage that ambiguity is costly, because the natural response to apparent non-recovery is another intervention.

There is a second, sharper edge. `consecutiveFailures` counts *attempts that failed*, not *distinct causes*. Sixty-two failures against one continuously-unavailable dependency is one fault observed sixty-two times, but the counter escalates as though the repo itself were progressively more suspect. A lane whose dependency was down for a day is punished for the duration of the outage after the outage ends.

Note the interaction with #17062: failures caused by **queue preemption** also increment this counter, so ingestion that never had a real chance still drives the lane toward the cap.

## The Fix (shape)

1. **An explicit, supported reset.** An operator (or a healed-dependency signal) must be able to clear the backoff for one repo or all repos without restarting the process. Read-only diagnosis is already exposed; this is the missing write.
2. **Cause-aware counting.** A failure attributable to a shared unavailable dependency should not escalate the per-repo counter the way a repo-specific failure does — otherwise the counter measures outage duration rather than repo health.
3. **Recovery-triggered retry.** The orchestrator already detects embedding recovery (`"Embedding recovery not yet observed (EMBEDDING_PROVIDER_ERROR; provider still failing)"` is logged on every sweep). Observing the *positive* transition should release lanes suppressed by that same cause.
4. Surface `nextAttemptAt` per repo in the deployment-state snapshot so an operator can see the wait rather than infer it from logs.

## This ticket's premise just went live, and I am retracting my own earlier assessment of it

In a prior session I assessed this as *"not a critical path blocker — latency-only"*, on the reasoning that repos were retrying every sweep and failing for embedding reasons, so nothing was stranded by backoff itself. That was true **while the root cause was unfixed**. It is exactly wrong now, and this ticket's title describes the current state precisely: *a fixed root cause still cannot resume ingestion.*

A containerized deployment had its embedding lane OOM-looping for ~14 hours; repos accumulated large failure streaks throughout. The root cause was fixed at ~10:02Z today and the lane has been healthy since — `restartCount 0`, memory below cap, embeddings landing. Measured at 11:18Z, with the cause gone:

**Case 1 — a repository succeeding cleanly is throttled 25× by a streak it can no longer earn.**

```
apps-* materialized: ingested=5916 embeddings=55 errors=0
partial-progress: slice budget reached … (streak held at 42; repo stays due)
suppressed by backoff (next ~11:42:58, consecutiveFailures=42, backoffX=4398046511104)
```

`errors=0`. Every sweep it gets, it makes clean progress. And it is suppressed for ~25 minutes between sweeps on a streak of 42 accrued during the outage, because `partial-progress` explicitly holds the streak. The log states both halves in adjacent lines — *"repo stays due"* and then *"suppressed by backoff"* — so due-ness and backoff are separate gates and backoff wins.

Cost, at the observed rate of 55 embeddings per sweep over 5,916 pending units:

| cadence | time to complete |
|---|---|
| throttled (~25 min/sweep, streak 42, capped) | **44.8 h** |
| base 60 s cadence | **1.8 h** |

A 25× penalty on a repository with zero errors. That is not latency-only by any reading I can defend.

**Case 2 — a repository has not been retried at all, and its status is therefore unknown.**

```
11:18:05Z  apps-* suppressed by backoff (next ~11:18:21, consecutiveFailures=62, backoffX=4611686018427388000)
```

Identical lines at 10:56, 11:01, 11:07, 11:12, 11:18 — all naming the same `next`. **Zero attempts in the entire log buffer.** Its 62 failures are all pre-fix. Nobody can say whether it would ingest cleanly today, because it has not been offered a chance since the cause was removed. A repo whose disposition is *unknowable* is a stronger form of "cannot resume" than one that retries and fails.

## Two mechanism notes for whoever takes this

**`partial-progress` holding the streak looks deliberate and is the wrong default here.** Holding it makes sense if partial progress means "still failing, just slower". It is wrong when the slice ended for budget reasons with `errors=0` — that is a *success* signal being scored as continued failure. The discriminator already exists in the same log line: `errors=0` versus `errors=N`. A clean partial slice should decay the streak (or at minimum not hold it), and a slice with errors should hold it.

**The multiplier overflows into float before it is capped.** `consecutiveFailures=62` prints `backoffX=4611686018427388000`; 2^62 is 4611686018427387904, so the printed value has already lost precision above `Number.MAX_SAFE_INTEGER`. The cap makes the behaviour correct, so this is not a live defect — but computing `2^62` in order to clamp it to 30 minutes is a latent smell, and the printed number in an operator-facing log is not the number the code means. Worth a guard when this area is touched.
