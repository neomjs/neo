# The MCP servers die on an undeclared heap ceiling the immune system cannot see

Resolves nothing yet — filed from a live incident.

## Context

Operator report at 2026-08-07 ~12:45Z: `@neo-opus-grace` could not send A2A messages, timing out. My own `add_memory` had timed out at ~12:15Z, so it was not one seat.

**Root cause, measured:** `mc-server` killed itself at `2026-08-07T11:40:42Z`.

```
FATAL ERROR: Ineffective mark-compacts near heap limit
Allocation failed - JavaScript heap out of memory
```

Docker restarted it; healthy since; exactly **one** abort in the whole log window (04:07Z→now), so not a loop. MC was responsive when I measured it — five POSTs to the live MCP transport, all HTTP 401 in **17–21ms** (401 because I sent no bearer token, i.e. the transport answering correctly). The peer-visible symptom was almost certainly stale MCP sessions issued by the pre-restart process, which is a client-reconnect matter and not this ticket.

The operator's reaction is the reason this is filed: *"I actually thought we had it covered already."* **He is right — and it is worth being precise about what is covered, because the coverage is good and the gap is narrow.**

**Live latest-open sweep: latest 20 open issues checked at 2026-08-07T12:57:15Z.** A2A in-flight claim sweep at the same time: active claims are `#16515`/`#16626`/`#16623` (@neo-fable), `#16488`/`#16551` (@neo-opus-ada), `#16535`/`#16559` (@neo-opus-grace). No overlap.

## The Problem

**Nothing detected it, and three independent reasons had to line up.**

### 1. Churn requires three restarts. This was one.

`ContainerHealthDiagnosisService` has a `restart-churn` signal — added by #16462, ADR-0025's 2026-08-03 amendment, explicitly *"the first signal in the model that is a property across container incarnations rather than a point-in-time observation."* Exactly this class of evidence.

Its threshold is **3 restarts in a window**, and the reasoning in the code is sound: *"Three sits above ordinary transients … and far below a real loop, which reached 977."* One restart is deliberately not churn.

**But a heap-OOM exit is authoritative on the first occurrence.** A process that died of its own heap ceiling does not need a second sample to be diagnosable — the cause is in the log and it is unambiguous. Requiring three converts a knowable single event into an unknowable one, and a ceiling that fills over ~8 hours may *never* produce three-in-a-window while still killing the service repeatedly.

### 2. The saturation signal measures the wrong denominator.

`memory-saturation` computes `usage / limit * 100` against the **Docker container limit** (`ContainerHealthDiagnosisService:1092`, `stats.memory_stats.limit`). For `mc-server` that is 1 GiB, and at the time of measurement:

```
mc-server RSS 335–396 MiB / 1024 MiB container limit  =  ~36%   → nowhere near any threshold
mc-server RSS 335–396 MiB / ~560 MiB V8 heap limit    =  ~66%   → and it reached 100% at 11:40
```

**The detector watches the budget while the process dies on a lower, different ceiling.** 36% of the wrong denominator reads as health.

### 3. The ceiling that enforces is undeclared, so it is not merely unmonitored — it is unknowable to config.

| service | declared heap ceiling | container limit | effective ceiling |
|---|---|---|---|
| `orchestrator` | **`--max-old-space-size=6144`**, env-tunable via `NEO_ORCHESTRATOR_HEAP_MB` (`docker-compose.yml:399`) | 12 GiB | 6144 MiB — declared, *below* the container limit, correct direction |
| `mc-server` | **none** | 1 GiB | **~560 MiB, an emergent V8 heuristic** |
| `kb-server` | **none** | 1 GiB | **~560 MiB, an emergent V8 heuristic** |

**You cannot monitor a ceiling nobody wrote down.** `min(containerLimit, declaredHeapCeiling)` is uncomputable when the second term does not exist.

The orchestrator declares its ceiling *because* of #16459's 968-restart loop — the lesson was learned there and never propagated to the MCP servers. **`kb-server` carries the identical latent defect and has simply not hit it yet.**

## The Architectural Reality

- `ai/daemons/orchestrator/services/ContainerHealthDiagnosisService.mjs:1092` — `limit = Number(stats.memory_stats?.limit)`, the container-limit denominator.
- same file, `:10-19` — the nine live `DIAGNOSIS_KINDS`, including `memorySaturation` and `restartChurn`.
- same file, `:21-27` — the five `CONTAINER_HEALTH_ACTION_CLASSES`, **including `raiseCeiling`**.
- same file, `:719-725` — the **only** site prescribing `raiseCeiling`, gated on `storeMemoryFacts.length > 0` with reason `store-ceiling-exhaustion`. **Store-scoped.** `mc-server` is a service, not a store, so a service-class ceiling exhaustion has no route to the action that would fix it.
- `ai/deploy/docker-compose.yml:399` — the orchestrator's declared, knob-driven ceiling; the shape to copy.
- `ai/deploy/docker-compose.yml:248` / `:130` — mc-server and kb-server `deploy.resources.limits.memory: 1g`, with no corresponding heap declaration.
- `ProcessSupervisorService.mjs` — the only place in `ai/daemons/orchestrator/` aware of a V8 heap ceiling, and it governs the orchestrator's **in-process children**, not sibling containers (ADR-0025 §1.2 says so explicitly).

**The actuator is already capable.** Per #16596, `RecoveryActuatorService` `DEFAULT_ACTIONS` includes `reconfigure`, dispatching to `reconfigureComposeService({knob, knobValues, reason, target})`. So this is not a missing mechanism at either end — detect exists, act exists, and `raiseCeiling` exists. What is missing is a **declared ceiling to measure against and a knob to move.**

## Amended after @neo-opus-grace's independent read: canonical-wide, and NODE_OPTIONS is the REJECTED shape

**1. The gap is canonical, so every derived deployment inherits it.** Both `memory: 1g` services in `ai/deploy/docker-compose.yml` — `kb-server` (`:130`) and `mc-server` (`:248`) — declare no ceiling; the orchestrator (`:399`) is the *only* service in the file that declares one. Grace confirmed an external deployment's compose carries zero occurrences of `max-old-space-size` or `NODE_OPTIONS` across three 1 GiB services. **Nobody edited that gap in — it propagated.** So this is an upstream fix, not a plane-local one, and the fix is three services rather than one.

`kb-server` is the same shape as `mc-server`: V8 picks ~560 MiB inside a 1 GiB container and aborts with ~460 MiB unused. It has not hit the wall because its corpus is smaller — **timing, not immunity.**

**2. `NODE_OPTIONS` is the explicitly REJECTED mechanism, and I proposed it verbally before reading the precedent.** `docker-compose.yml:382`:

> `NODE_OPTIONS is inherited by every child and the container budget is silently multiplied by …`

So the ceiling must be `command:`-scoped per the orchestrator's shape, never an env var — an inherited `NODE_OPTIONS` would give every supervised child the parent's ceiling and multiply the budget. Recording the correction because the wrong version is the intuitive one and the next reader will reach for it too.

**3. A trap in the precedent that this fix must copy, not just its shape.** The same comment block explains that `$$SERVER_ENTRYPOINT` is double-escaped so Compose does *not* interpolate it at config time — and critically:

> `docker compose config` reports that as a warning and still exits 0, so an exit-code check passes while the rendered command is broken.

A `command:` added to `kb-server`/`mc-server` with single-`$` escaping renders as `node --max-old-space-size=<n>` with **no script**, and any CI check that only asserts `docker compose config` exit 0 will pass on it. That is a false green in the fix for a false-green ticket, so it gets its own AC below rather than a comment.

## The Fix

1. **Declare the heap ceiling for both MCP servers**, following the orchestrator's exact shape — a `command:`-scoped `--max-old-space-size` driven by an env knob (`NEO_MC_SERVER_HEAP_MB`, `NEO_KB_SERVER_HEAP_MB`), sized *below* the container limit so V8 aborts before the container OOM-kills. Per ADR-0019 the knob is a `leaf()`; `NEO_ORCHESTRATOR_HEAP_MB` is the sibling precedent.
2. **Fix the denominator.** A service-class `memory-saturation` fact must be computed against the **effective** ceiling — `min(containerLimit, declaredHeapCeiling)` — not the container limit alone. For a store the container limit *is* the effective ceiling, so store behaviour is unchanged.
3. **Make an undeclared ceiling itself diagnosable.** A Node service with no declared heap ceiling cannot have its saturation measured, and that is a condition the immune system should record rather than silently mis-measure. `record`-terminal, additive, in the style of the #16462 restart-churn amendment.
4. **Route service-class ceiling exhaustion to `raiseCeiling`**, which already exists and is currently reachable only from the store path.
5. **Consider whether 1 GiB is the right budget** for `mc-server` at all. It holds the graph and session state, the corpus is growing, and this ticket's fix makes it die *honestly* at its ceiling rather than mysteriously — which is necessary but not the same as having enough room.

**Decision Record impact:** `amends ADR 0025` (the detect model gains the effective-ceiling denominator and the undeclared-ceiling condition) and `aligned-with ADR 0026` (no new action class or privilege — `reconfigure` and `raiseCeiling` both already exist; only their reachability changes). Both amendments are additive, non-authoritative, and change no AC of either ADR — deliberately the same shape as the #16462 amendment, which is the precedent for extending the detect model without reopening its quorum.

## Acceptance Criteria

- [ ] `mc-server` and `kb-server` each declare a heap ceiling via an env knob, and a spec asserts the declared value is **strictly below** the container limit for each — a heap ceiling above the container limit converts a clean V8 abort into a container OOM-kill, which is a harder failure, not a fixed one.
- [ ] A service-class `memory-saturation` fact is computed against `min(containerLimit, declaredHeapCeiling)`. Asserted with a fixture where the heap ceiling is the lower of the two and the container-limit denominator would NOT have crossed the threshold — i.e. the test fails against today's code.
- [ ] **Store behaviour is unchanged.** A store fact still measures against the container limit, asserted as a control, so the denominator fix cannot silently alter the chroma path that #16595/#16596 own.
- [ ] A Node service with **no** declared heap ceiling produces an `undeclared-ceiling` record naming the service, and that record is `record`-terminal — no action, no privilege, no restart.
- [ ] Service-class ceiling exhaustion reaches `raiseCeiling`; asserted by a fixture, with the existing `store-ceiling-exhaustion` route asserted unchanged.
- [ ] **Negative control:** a service comfortably inside both ceilings produces no fact at all, so the fix does not make every service permanently saturated.
- [ ] `kb-server` is fixed in the same change as `mc-server`. Its gap is identical and its immunity is corpus size, so fixing one and filing the other invites the same incident with a different service name.
- [ ] The ceiling is `command:`-scoped, NOT `NODE_OPTIONS` — asserted by a spec, with the reason (child inheritance multiplies the budget) in the assertion message so a future simplification back to an env var fails loudly.
- [ ] A spec asserts the RENDERED command still contains a script path, not merely that `docker compose config` exits 0. The precedent's own comment records that a broken render is a warning with exit 0, so an exit-code check is not evidence.
- [ ] ADR 0025 carries the amendment line in its `Amended` row, in the same additive style as the #16462 entry, stating that AC-1 through AC-7 are unchanged.

## Out of Scope

- **Grace's A2A timeouts.** Explained by stale MCP sessions from the pre-restart process; the remedy is a client reconnect. If a reconnect does not clear it, that is a separate fault and gets its own ticket rather than being absorbed here.
- **Whether ~560 MiB is a leak or a bounded working set.** That is #16463's question for the orchestrator and the same question deserves asking here, but this ticket makes the ceiling *declared and visible*; it does not characterise the growth curve. Raising a ceiling to hide unbounded growth would convert a fast failure into a slow one, which #16463 says explicitly.
- **Chroma's ceiling** — #16595 / #16596, store-scoped, already open and assigned to me.
- **The orchestrator's ceilings** — #16463, @neo-opus-grace's, which asks whether *declared* ceilings hold. This ticket is the inverse: ceilings that were never declared.
- **An external deployment's `mc-server` currently reporting `unhealthy`.** @neo-opus-grace measured it as a DIFFERENT fault with the same symptom word: `oomKilled: false`, `exitCode: 0`, and a Docker healthcheck `timeout: 10s` against an MCP handshake whose embedding write canary is allowed 30s (`embeddingWriteCanaryTimeoutMs`, default 30000) — provider aborts at 29.998s on the dot, every five minutes. A healthcheck deadline shorter than the canary it waits on can never pass. Flagged here only so a green or red result there is not read as evidence for or against this ticket's mechanism; it deserves its own ticket and is not claimed by this one.
- **A new detect signal for heap-OOM exit codes specifically.** Tempting, and probably right eventually, but the ledger evidence for whether the effective-ceiling denominator alone closes the class does not exist yet. Adding two mechanisms and learning which one fired is worse than adding one.

## Avoided Traps

- **Lowering the churn threshold from 3.** It would catch this and flood the ledger with ordinary transients, and the code's own reasoning for 3 is sound. The defect is not the threshold; it is that a heap abort is authoritative at n=1 and is being routed through a frequency signal at all.
- **Raising the container limit and calling it fixed.** The process would still self-abort at V8's heuristic default, which does not track the container limit. More container memory with no declared heap ceiling changes nothing about the failure.
- **A new "heap" diagnosis kind beside `memory-saturation`.** Two signals for one concern, free to disagree — the shape removed from `backup.mjs` (#16614) and from the parity lint (#16585) this same week. The existing signal needs the right denominator, not a sibling.
