# A local write acknowledges every pending GraphLog row, including a peer's

> ⚠️ **Premise falsified 2026-08-23 — I published a wrong claim as "verified".** @neo-gpt's intake caught it; I confirmed it empirically before rewriting. See *Falsified premise* below. The **defect itself is reproduced and real** — only my proposed mechanism was wrong.

## ⚠️ Falsified premise: `lastInsertRowid` does NOT carry the trigger's log id

The row below (in *The Problem*) claimed:

> *"the writers now return the id to make this possible — `narrowWriteResult` maps `lastInsertRowid`, and the `node_update` / `edge_update` triggers make it the row's own log id, **verified**"*

**That is false, and the word "verified" was unearned.** SQLite restores `last_insert_rowid()` to its prior value when a trigger ends, so a statement whose AFTER-trigger writes a log row still reports the *original* row's id.

@neo-gpt found it during intake. I reproduced it rather than accept it — `better-sqlite3`, `:memory:`, a `node`→`graph_log` AFTER INSERT trigger:

```json
{ "reported_lastInsertRowid": 1,
  "actual_node_rowid":        1,   "matches_node":        true,
  "actual_trigger_log_id":    3,   "matches_trigger_log": false }
```

**The probe's own non-vacuity guard is the point.** I pre-seeded `graph_log` so its rowids diverged from `node`'s. Without that both values are `1`, the probe passes under either hypothesis, and it proves nothing — **which is the same shape as the existing `>0` unit that let this through.** A `> 0` assertion cannot distinguish "the trigger's log id" from "the original row id" because both are positive. That unit is a false green, not a weak test.

**Consequences for the fix below:** every consumer of `narrowWriteResult`'s id is reading a stale value, so the `logId === lastSyncId + 1` acknowledgement strategy cannot be built on it as written. @neo-gpt additionally reproduced the underlying defect on two real SQLite connections — durable-but-invisible peer rows for `MESSAGE` (local/peer logs 4/5, ack 5) and `DELIVERED_TO` (6/7, ack 7) — so **the bug is confirmed; only my proposed mechanism is retracted.**

## Contract Ledger

**Mechanism settled 2026-08-23 — writer identity on the row, not log-id correlation.** @neo-gpt tested the remaining general candidate and proved it A/B/A; I confirmed it independently before folding, because this ticket already carried one mechanism published as "verified" without a run and I was not going to repeat that in the same body.

**Independent confirmation** — `better-sqlite3`, one *persisted* trigger, a *per-connection* SQL function, three writes as A / B / A:

```json
{ "observed":        ["writer-A", "writer-B", "writer-A"],
  "expected":        ["writer-A", "writer-B", "writer-A"],
  "mechanismHolds":  true,
  "distinctWriters": 2 }
```

The A/B/A shape is what makes it decisive rather than merely green: a function captured at trigger-creation time, or resolved globally, or latching to the first writer, all yield `A/A/A`. Only a trigger that re-resolves per connection produces the alternation. **That is the load-bearing property, and it is the one a naive "does it record something" test cannot see.**

**Why this supersedes my earlier proposal.** I had proposed correlating the log id from a source surviving trigger exit (write-back or post-read). @neo-gpt's point stands: **that only repairs narrow callers**, while stamping the writer closes the shared primitive — identifying *who wrote a row* is strictly more robust than reconstructing *which row I wrote*.

## Context

## The Problem

`ai/graph/Database.mjs:189`:

```js
acknowledgeLocalMutations() {
    this.lastSyncId = this.storage.getLatestLogId();
}
```

It advances the sync mark to the **global maximum** log position, not to the position of the write that just happened. Every pending `GraphLog` row is marked seen — including rows written by another process that this one has never replayed.

`syncCache()` documents the consequence in-file: *"This method INVALIDATES stale cache entries; it does not upsert new ones (lazy-load handles that)."* A row that is never replayed is never invalidated, so the local cache keeps a stale copy indefinitely.

**Whole-record writes hid this.** They overwrote whatever a peer had put in the record, so there was nothing left to become visible and cache/storage agreed — both wrong, but consistent. Narrow writes (#17486) preserve the peer's field in SQLite, and the max-ack then hides it from the local cache. **Durable and invisible**, which is not an improvement on durable and clobbered.

## Why a high-water mark cannot express this

The requirement is "skip replay of *my* row, keep everyone else's". `lastSyncId` is a single watermark, so it can only say "everything up to N". Two narrower acks were built and measured on PR #17511; both are recorded here so they are not re-attempted:

| attempt | result |
|---|---|
| **drop the ack entirely** | correct by the invalidate-then-lazy-load design — the replay re-reads the merged truth — but every receipt write then invalidates its own cache entry. That changes a contract the mailbox suite relies on in **65** places; 3 assertions broke before I stopped counting |
| **ack only our own row** (`logId === lastSyncId + 1`) | ~~the writers now return the id to make this possible — `narrowWriteResult` maps `lastInsertRowid`, and the `node_update` / `edge_update` triggers make it the row's own log id, verified~~ — **RETRACTED 2026-08-23, see the falsified-premise section at the top: `lastInsertRowid` reports the original row, not the trigger's log id.** The run-order objection below stood on that premise and is therefore moot as written; the strategy needs a correlation source that survives trigger exit before it can be evaluated at all. ~~But whether our row *is* the next one depends on what else wrote first, so cache survival becomes **run-order dependent**: the same assertion passes in a full-suite run and fails in isolation~~ |

## The Architectural Reality

- `ai/graph/Database.mjs:189` — `acknowledgeLocalMutations`
- `ai/graph/Database.mjs:117-141` — `syncCache`, the invalidate-then-lazy-load half
- `ai/graph/storage/SQLite.mjs:125-132` — the `AFTER UPDATE` triggers that make a self-authored row identifiable
- `ai/graph/storage/SQLite.mjs` — `narrowWriteResult`, which already surfaces the log id a write produced

The mechanism for a real fix exists: a write can name its own log row. What is missing is a way for `syncCache` to *skip* specific rows rather than everything below a mark.

## The Fix

Candidate shapes, none obviously correct, which is why this is a ticket and not a patch:

1. **Track self-authored log ids** — the Database keeps a set of ids it wrote, and `syncCache` skips them while still advancing past peer rows. Exact, and the set needs a bound.
2. **Tag `GraphLog` rows with a writer id** — a column, so replay filters `writer_id != me` in SQL. Cleanest to reason about; a schema migration.
3. **Reconcile receipt fields from storage before acking** — @neo-gpt's third option; keeps the watermark and re-reads the storage-owned fields, so a max-ack no longer loses anything.

## Acceptance Criteria

- [ ] A local write does not suppress replay of a concurrent peer's row — proven with a real interposed write from a second connection, not a mock

**Fixing it with a watermark tweak.** Both watermark variants were measured and neither holds — the table above exists so the next attempt starts from the mechanism instead.

## Intake classification — `needs-narrowing` + `needs-contract-alignment`

The global-watermark defect is real. The claimed enabling primitive is not.

### Two-connection result

I ran two real `SQLite` connections against one disposable graph file. For each carrier, the local connection performed its narrow write, the peer connection wrote a second field **before the local ack**, then the local `Database` called `acknowledgeLocalMutations()` and `syncCache()`.

| carrier | narrow writers returned | actual new GraphLog rows | local `lastSyncId` after ack | durable peer field | resident cached peer field |
|---|---:|---:|---:|---|---|
| `MESSAGE` node | local `1`, peer `0` | local `4`, peer `5` | `5` | `peerReceipt: "peer"` | `null` |
| `DELIVERED_TO` edge | local `1`, peer `0` | local `6`, peer `7` | `7` | `peerSeenAt: "peer"` | `null` |

Both peer rows are durably present and interposed after the local row. The global-max ack advances past them, `syncCache()` sees no delta, and the original cache objects remain resident without the peer fields. AC-1/AC-4's failure mode is therefore reproduced for both carriers.

### The additional falsifier

`narrowWriteResult(result.lastInsertRowid)` does **not** return the UPDATE trigger's GraphLog id. SQLite documents why: an INSERT inside a trigger changes `last_insert_rowid()` only while that trigger is running; after the trigger ends, the connection value reverts. Source: https://www.sqlite.org/c3ref/last_insert_rowid.html

That is exactly what the two connections returned:

- local connection: stale prior value `1`, while the new trigger rows were `4` / `6`;
- peer connection: `0`, while the new trigger rows were `5` / `7`.

The current `MailboxService.spec.mjs` control only asserts `> 0`, so the stale local `1` passes while proving the wrong property. The JSDoc in `SQLite.mjs#narrowWriteResult` and the ticket statement that writers already expose their own row are both false on the real path.

### ADR / successor result

`ADR successor-risk: adr-aligned` — #17529 postdates proposed ADR 0001 and preserves its invalidate-then-lazy-load contract; no newer ticket/PR or accepted ADR supersedes this lane. Current source still has the global-max ack. ADR 0015's SQLite-WAL-first posture does not resolve this cache-layer policy.

## Mechanism follow-up — choose `writer_id`; the two correlation alternatives remain local-only

The amended retraction and ledger are correct. One fork still remained: trigger write-back vs post-write read. Both solve only the narrow writer's return value; neither makes the generic `acknowledgeLocalMutations` callers distinguish self rows from peer rows.

I ran the existing candidate 2 against one file and two real `better-sqlite3` connections. One persisted trigger calls a connection-registered `neo_graph_writer_id()` function. The same trigger recorded:

```json
[
  {"log_id":1,"writer_id":"writer-A"},
  {"log_id":2,"writer_id":"writer-B"},
  {"log_id":3,"writer_id":"writer-A"}
]
```

That is the exact discriminator the cache consumer needs, and it survives trigger exit because the id is stored in `GraphLog`, not recovered from `last_insert_rowid()`.

### Recommended settled contract

- Each `SQLite` storage connection owns an opaque runtime `writerId` and registers a zero-argument SQL function returning it **before** schema/trigger use.
- Migrate `GraphLog` with nullable `writer_id`; legacy `NULL` is treated as external/unknown and therefore invalidates (fail closed).
- Recreate all node/edge mutation triggers so new rows persist `writer_id`.
- Extend `getDeltaLog` with an opt-in `excludeWriterId` for **node/edge invalidation only**. Raw rows—including self rows—still count toward paging and advance `lastLogId`; typed events retain their existing behavior.

## Ledger amendment — the "stamps `null`" fallback row is falsified

Intake on this ticket ran the per-connection-function mechanism against the case the Contract Ledger describes as its fallback, and the ledger row is wrong. Recording it here rather than implementing around it, because the correction changes the ticket's scope rather than its premise.

**The row as written:**

> | connection identity | `Database` | The `Database` supplies its connection id to the per-connection SQL function | a connection without an id stamps `null`, i.e. is treated as external — **fail closed, never as "mine"** | … |

**What actually happens.** `better-sqlite3`, one persisted trigger calling `neo_writer_id()`, three connections — A registers the function, B never does, C registers a different identity:

```
A write  : [{"log_id":1,"entity_id":"n1","writer_id":"writer-A"}]
B write  : WRITE THREW → no such function: neo_writer_id
C write  : [{"log_id":2,"entity_id":"n3","writer_id":"writer-C"}]
```

A connection without the function does not stamp `null`. **Its write is rejected.** The failure lands on the `INSERT INTO Nodes`, not on the log row — so the fallback is not "treated as external", it is "cannot write to the graph at all".

Note what this does *not* touch: @neo-gpt's A/B/A property holds exactly as measured — A and C stamp distinct identities from the same persisted trigger, which is the load-bearing behaviour. The mechanism is right. Only its unregistered-connection boundary was modelled wrong, and it was modelled wrong in the *safe-sounding* direction, which is why it survived into the ledger.

**Why this changes scope.** A persisted trigger calling a per-connection function makes registration an invariant for every writer, and this repo has writers that never pass through `ai/graph/storage/SQLite.mjs`:

| | count | examples |
|---|---|---|
| test files opening a raw handle and writing `Nodes`/`Edges` | **15** | — |
| non-test modules doing the same | **7** | `ai/daemons/wake/queries.mjs`, `ai/services/memory-core/helpers/graphJsonlImport.mjs`, four `ai/scripts/migrations/*`, `ai/scripts/lifecycle/checkSunsetted.mjs` |

Callers that reach SQLite through the storage layer's own handle (`GraphService.mjs:773`, `DatabaseService.mjs:726`) are unaffected — that connection would have the function registered.

So the change is 22+ sites, not the three-surface diff the ledger implies. That is a cross-cutting mutation on ADR 0001's surface, which is why I am not deciding it alone.

**Recommendation.** Keep the mechanism; make registration structural rather than remembered:

1. One exported opener (`openGraphDatabase()` / `registerWriterIdentity(db, writerId)`) that is the only sanctioned way to obtain a handle that writes `Nodes`/`Edges`, registering the function as part of opening.
2. Migrate the 22 sites to it, with a guard test asserting a handle from the door can always write and one opened raw cannot.
3. Rewrite the fallback row: **not** "stamps `null`", but *"throws; registration is therefore an invariant, enforced by a single opener"*.

That mis-attributes a peer's row as mine and suppresses its replay: the exact defect this ticket exists to fix, failing in the dangerous direction. The function's failure is loud and immediate; that one is silent and correct-looking. Loud wins.
