Resolves #17401

`grid.View#syncBodies` ran the scroll cycle at `updateDepth: 3`. The depth is 1-based, so it expands View → Body → Row and emits everything past that boundary as `{componentId, neoIgnore: true}` — references the vdom worker deliberately leaves untouched. Cell components sit exactly on that boundary, so a recycled row repainted its plain and renderer cells while every `grid.column.Component` cell kept the content it first rendered. Moving the boundary one level lower expands the cells themselves.

Evidence: L3 (live Chromium e2e on `examples/grid/bigData` reproducing the defect and confirming the fix, plus a tearing detector and the existing scroll-telemetry rig) → L3 required (every close-target AC is runtime scroll behaviour observable in a browser). No residuals.

## Deltas from ticket

**The ticket's stated root-cause candidate was wrong, and is corrected here.** #17401 named the `cellRenderer` short-circuit as the prime suspect. It is not implicated — a recycled row carries a different record, so the short-circuit is bypassed correctly, and the component instance rebinds. The defect is purely that the update never reaches the DOM.

**Two alternative fixes were measured and rejected.** A tearing detector ran 60 rapid wheel steps sampling `(rank, login)` pairs, where the component cell's content is derived from the row's own record — a login observed under two different ranks means the two disagree:

| approach | torn | staleness |
|---|---|---|
| `updateDepth: 4` (this PR) | **0 / 266** | fixed |
| non-silent `component.set` | 7 / 292 | fixed, but tears |
| non-silent + View pre-marked so cells merge into its cycle | 10 / 303 | fixed, but tears |

Un-silencing lets each cell update on its own schedule, so the row advances a frame before its content follows. Keeping the update silent and expanding one level further is what preserves same-cycle atomicity.

**Known limitation, disclosed rather than assumed.** Depth 4 expands the cell component; a cell component that is a **Container** has children one level further out, which still receive `neoIgnore` and would hold their last render. Every built-in cell component is flat today — `GitHubUser`, `IconLink`, `CountryFlag`, `GitHubOrgs` and `Progress` extend `component/Base.mjs`, `Sparkline` extends `Canvas` — so the fix is complete for what ships, but `grid.column.Component` places no constraint on the `module`. This is unverified in either direction: a unit fixture could not observe it (the unit path is not silent, so it passes on the defect) and was deleted rather than committed as false coverage.

**Deleted rather than shipped:** a unit spec asserting the component instance rebinds. It passed on the unfixed tree, so committing it would have advertised coverage that does not exist.

## Test Evidence

`test/playwright/e2e/grid/ComponentCellScrollSync.spec.mjs` — new, drives `examples/grid/bigData`, whose `countAction` column renders a Button with `record.firstname + ' ++'` beside the plain `firstname` cell. That pairing is self-contained: no external ground truth, and a row that never scrolled cannot satisfy it.

- Fails on the unfixed tree: `Expected "Brian ++", Received "Ashley ++"` — the row advanced, the component cell did not.
- Passes with the fix.

`test/playwright/unit/grid/ComponentColumnResizeSync.spec.mjs` — new, 4 tests. Closes a separate measured gap: no spec at any level resized a component column. It carries a component column, both axes buffered at range 1, and columns assigned after `construct()`.

```
grid unit suite            65 passed
grid e2e suite             32 passed, 1 failed
scroll telemetry           1912–1916 frames vs 1921 baseline, 0 blank, 0 jitter
tearing detector           0 / 266
```

Verified on the reporting app as well, since `apps/devindex` is not driven by a committed spec here. After a scroll, row 1 moved from rank 1 to rank 157 and every component-backed column followed it:

| column | type | before | after |
|---|---|---|---|
| User | `githubUser` | `laciferin2024Hir` | `ashkingAshwin` |
| Impact | `component` | 🔥 | ⚡🚀🛡️ |
| Top Repo | `iconLink` | `155` | `154,393` |
| Location | `countryFlag` | `Dubai, UAE` | `Bangalore, India` |

On the unfixed tree all four held their first-rendered values while `rank` advanced.

The single e2e failure is `TreeBigData › Filtering`. It is pre-existing: verified by stashing this change and re-running it on the unmodified tree, where it fails identically.
