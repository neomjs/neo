# Validate DevIndex budget across three scheduled runs

## Context

The implementation for #15745 is complete in #15747. The PR's current head `ee315206603c9a808bcb2f6cf69fabcf4b46c25d` is mergeable and all 16 reported checks pass, but its final acceptance criterion requires evidence from three scheduled Data Sync runs after the implementation reaches `dev`.

That evidence cannot exist while the implementation PR remains draft and unmerged. Neo also prevents reopening closed tickets through [`prevent-reopen.yml`](https://github.com/neomjs/neo/blob/dev/.github/workflows/prevent-reopen.yml), so the post-merge witness needs a durable leaf of its own.

## Problem

Keeping the three-run witness inside the implementation ticket creates a circular lifecycle gate:

1. #15747 cannot receive formal review while it remains draft.
2. The scheduled-run evidence cannot be collected before the PR is reviewed and merged.
3. Closing #15745 on merge and reopening it later would violate Neo's immutable issue-history contract.

## Architectural Reality

- #15745 defines GraphQL cost as the DevIndex admission currency and reserves 100 points for the downstream label-index query.
- #15747 supplies the implementation and pre-merge test evidence.
- Scheduled Actions telemetry is the only evidence surface for the remaining operational witness.
- This ticket owns observation only; it must not become a second implementation lane.

## Fix

After #15747 merges to `dev`, observe the next three scheduled Data Sync Pipeline runs that reach the DevIndex phase. For each run, record the run URL, tested head SHA, admitted-user count, observed GraphQL cost, remaining capacity, configured reserve, stop reason, and downstream label-index outcome.

Close this ticket once those three receipts demonstrate that DevIndex does not terminate on a GraphQL primary-quota or query-cost failure and that downstream work retains the declared 100-point reserve.

### Two observations the witness produced

Recording these rather than acting on them; this lane is observation-only and neither is a GraphQL-budget correctness defect.

**1. A stale-head restart doubles the DevIndex GraphQL burn.** Attempt 1 spent its full `953` points and admitted its full 200 users before being discarded. The run's true GraphQL cost was ~`1906` points, not the `953` any single checkpoint reports. Both attempts logged `Saved 0 records`, so the second attempt re-fetched the same admitted cohort. Under a tighter reserve or a busier `dev`, cost-per-run is bounded by `attempts × 953`, not by `953`. No current risk — the run ended with 3082 points spare — but the budget's headroom claim should be read per-run, not per-attempt.

**2. The rollout ceiling is triple-sourced and the config leaf is unreachable.** The `200` that bound this run has three declarations that do not agree:

| Source | Value | Effective in the pipeline path? |
| --- | --- | --- |
| `apps/devindex/services/config.mjs:85` `spider.batchSize` | `50` | **No** — never reached |
| `package.json:108` `devindex:update … --limit 200` | `200` | No — overridden |
| `buildScripts/dataSyncPipeline.mjs:92` `['--limit=200']` | `200` | **Yes** |

`Manager.mjs:61` parses this with Commander (`.option('-l, --limit <number>', …, config.spider.batchSize)`), which is last-wins for repeated scalars, so the CLI receives `--limit 200 --limit=200` and the pipeline's value binds. Behaviour is correct today because both flags happen to say `200`. The trap is that `config.spider.batchSize` reads like the SSOT for the rollout ceiling and is dead in every scripted path — tuning it from `50` would change nothing. Raising the ceiling is explicitly out of scope for this ticket; single-sourcing it is a separate concern and I am not widening this lane to do it.

Both runs executed on the same UTC day (20:13Z and 22:03Z). The backlog is scoped `pending update today`, so if run 1's 200 admitted users had been recorded as updated, run 2's baseline should have opened at `49801` and closed at `49601`. It opened at `50001` and closed at `49801` — **identical to run 1**. Paired with `Saved 0 records` in both, the admitted cohort appears not to be persisted as processed, so each run re-admits against an undrained pool.

**I am recording this as an observation, not a defect, and deliberately not acting on it.** `Saved 0 records` has a benign reading — 200 users fetched, none with changed data worth writing — and I have not established the intended semantics of `Backlog size` versus `Remaining Backlog`. What makes it worth writing down is that the identical baseline across two same-day runs is the *discriminating* datum: the benign reading explains `Saved 0`, but it does not explain the pool failing to shrink.

This is **not** a GraphQL-budget failure and does not affect either AC above. The budget mechanism did precisely what #15745 specified: admitted to the cap, spent 953 of 5000, held the 100-point reserve, and left the downstream query 3941 points of headroom. Whether admitted users durably drain the backlog is a separate concern from whether the admission currency works, and this ticket owns only the latter.
