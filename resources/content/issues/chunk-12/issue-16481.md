# fix(ai): file-system MCP sandbox is crossed by write_file + run_playwright_test

The file-system MCP server states a containment guarantee in two places. `openapi.yaml` describes it as "heavily sandboxed file system manipulation", and the guard throws `403 Forbidden: Path traversal detected. Operation jailed to <root>`.

That guarantee does not hold when `write_file` and `run_playwright_test` are used together, and neither call violates any guard.

- `write_file` accepts any path inside the project root.
- `run_playwright_test` executes a Playwright spec. A spec is JavaScript, so executing it runs whatever it contains.

Observed on current `dev`, which contains `5acc564` and #16235.

## Observed

Absolute paths are redacted to `<root>`. The canary is `/tmp/OUTSIDE_SECRET.txt`, outside the project root, containing `SECRET-OUTSIDE-THE-PROJECT-ROOT`.

**The guard works when approached directly**

```
read_file({absolutePath: "/tmp/OUTSIDE_SECRET.txt"})
  -> REJECTED
     403 Forbidden: Path traversal detected. Operation jailed to <root>
```

**Retrieval in two steps**

```
write_file({
  absolutePath: "<root>/test/playwright/exfil-canary.spec.mjs",
  content     : "import fs from 'fs';
                 fs.copyFileSync('/tmp/OUTSIDE_SECRET.txt', '<root>/exfil-landed.txt');"
})
  -> allowed (the target is inside the root)

run_playwright_test({absolutePath: "<root>/test/playwright/exfil-canary.spec.mjs"})

read_file({absolutePath: "<root>/exfil-landed.txt"})
  -> "SECRET-OUTSIDE-THE-PROJECT-ROOT"
```

The third call is an ordinary, fully permitted request, and the guard behaves correctly on it. The content it returns is the content the guard refused in the first case.

**Retrieval in one step, through the tool's own return value**

```
write_file({
  absolutePath: "<root>/test/playwright/exfil-canary.spec.mjs",
  content     : "import fs from 'fs';
                 process.stdout.write('[LEAK] ' + fs.readFileSync('/tmp/OUTSIDE_SECRET.txt','utf-8'));"
})

run_playwright_test({absolutePath: "<root>/test/playwright/exfil-canary.spec.mjs"})
  -> "Test Failed:
      [LEAK] SECRET-OUTSIDE-THE-PROJECT-ROOT
      ..."
```

`runPlaywrightTest` returns the child process's stdout to the caller, so the file contents are handed straight back. No intermediate file is needed.

**Arbitrary commands, not only file reads**

```
write_file({
  absolutePath: "<root>/test/playwright/uid-canary.spec.mjs",
  content     : "import {execSync} from 'child_process';
                 execSync('id -u > /tmp/UID_PROOF');"
})

run_playwright_test({absolutePath: "<root>/test/playwright/uid-canary.spec.mjs"})

/tmp/UID_PROOF -> "1000"
```

## Preconditions

1. The caller can invoke both `write_file` and `run_playwright_test`. Both are default tools of this server.
2. `@playwright/test` is installed. It is a devDependency of neo.mjs, so it is present in a normal development checkout of the project this server is built for. It would not be present if neo.mjs were installed as a dependency of another application.
3. The agent is induced to make both calls.

Condition 2 is a genuine constraint. This is not unconditional.

## This is separate from #16231

I re-ran the payloads from that ticket against `dev`. All are blocked. I also tried three bypasses against the new guard, all blocked:

- a filename shaped like a `node` flag — the path is always absolute, so it cannot be read as a flag
- a sibling directory whose name prefixes the root (`<root>-evil/`) — blocked by the `path.relative` containment check
- an in-root symlink pointing outside — blocked by the `realpath` canonicalization

`execFile` does what it was written to do. The behaviour described here never touches a shell, so it is not what that change was addressing.

## Which direction to fix

This reads as a policy decision rather than a defect with one obvious patch. Three options I can see:

1. Keep `write_file` out of `test/playwright/`
2. Have `run_playwright_test` refuse specs that the tool itself wrote
3. Drop the containment wording from `openapi.yaml` and the 403 message, and document the tool as executing arbitrary project code

## One further observation

`runPlaywrightTest` limits execution with `safePath.includes('test/playwright/')`. This is a substring test rather than a containment test, so a directory such as `<root>/atest/playwright/` satisfies it. It does not cross the sandbox boundary, since the jail check runs first, and it grants nothing that `write_file` into the real test directory would not already grant. Noting it for completeness rather than as a separate issue.

## Confirmed from source. The composition is real, and both guards are individually correct — which is what makes this the interesting one

@novice-22 — third report, third time the diagnosis holds. Verified rather than read:

```js
// FileSystemService.mjs:155
static async runPlaywrightTest({absolutePath}) {
    const safePath = await ensureSandboxed(absolutePath);         // path jailed
    if (!safePath.includes('test/playwright/')) throw new Error(  // narrowed further
        '403 Forbidden: Can only execute Playwright specs within the test/playwright/ directory.');
    await execFileAsync('npx', ['playwright', 'test', safePath]); // …then executes it
}
```

`ensureSandboxed` is genuinely sound on its own terms — it uses `path.relative` on a path boundary rather than a string prefix, specifically because `startsWith` once admitted `<root>-evil/x`. `write_file` is jailed the same way. Neither guard has a hole.

**The escape is that neither guard is about the same thing as the guarantee.** Both jail *path arguments*. `run_playwright_test` executes *arbitrary JavaScript*, because a Playwright spec is JavaScript — so the executed code was never inside the jail, and no amount of hardening the path check reaches it. Your two-step reproduction is the shortest possible demonstration of that, and the one-step variant through the tool's own return value is a better one, because it removes even the second `read_file`.

That is a confused deputy in the classic form: two correctly-implemented, individually-safe capabilities composing into one that neither of them authorises.

### Scope, stated so nobody over- or under-reads it

`file-system` is **not** a deployed surface. It appears in no compose file and is not a `TARGET_SERVER` image — it is a local stdio dev-tool on a maintainer machine. So this is not remote compromise, and I am not going to dress it up as one.

What it *is*: the containment an agent's tool surface promises, and does not have. The realistic threat is a prompt-injected or misbehaving agent reading `~/.ssh`, a `.env`, or another repo on the same machine — while every individual call it makes is permitted and logged as permitted. That is worth fixing on its own terms, and the `openapi.yaml` phrase "heavily sandboxed file system manipulation" is currently an overstatement I would rather correct than defend.

### Why this needs a decision before a patch

There is no small fix, and I want to be straight about that rather than promise one:

- **Narrow what may execute** — a spec is arbitrary JS; there is no subset check that survives contact.
- **Constrain the child process** — run the spec with a restricted filesystem view. Correct, and the largest change.
- **Split the trust envelope** — the capability that *writes* and the capability that *executes* should not sit behind one guard. Probably the real answer.
- **Withdraw the claim** — cheapest, honest, and fixes nothing.

That is an architecture call, not a bug fix, so I have labelled this `bug` + `architecture` and I am not going to pick the shape unilaterally in a comment.

### @novice-22 - 2026-08-05T03:20:27Z

`#16508` — please pass it on. Not my call to make on the codebase's shape either way.

On the axis: it is right, but I think the split you are reaching for cannot be drawn where you are drawing it.

A sound tool-level partition would have to keep `write_file` out of everywhere `run_playwright_test` can read. But a spec is arbitrary JavaScript, so the executor's read set is not statically bounded — it is the project. Draw the partition honestly and `write_file` has nowhere left to write. Your third objection is not a risk of that approach; it is what that approach necessarily produces.

Which is why the split that pays looks like it is between **processes**, not tools. The executor's problem is that the child inherits the parent's authority. Bound the child and the reach becomes the project instead of the account — the spec still runs, agents still write and run specs, and the tool keeps doing what it exists for.

Stated precisely, because the weaker version would be overselling it: bounding the child does not make the write side irrelevant. A malicious spec can still read whatever is inside the bound, so a checked-in secret or a `.env` still leaves. What it removes is the class my reproduction demonstrated — reaching `~/.ssh`, another repo, anything outside the project.

One thing to fold in either way: `runPlaywrightTest` returns the child's stdout to the caller, which is what the one-step variant uses. The bound has to cover what the child can **read**, not just what it can write, or everything inside it still leaves through the return value.

Cost, honestly: this is your "largest change" option and I think that was the right label. It is platform-specific, and "what a test actually needs" is its own policy question — browser, local-server network, temp dirs, the source tree is not a small surface.

And option four is not a retreat if the bound is too expensive. Documenting "this tool executes arbitrary project code, do not treat it as sandboxed" is accurate labelling. Leaving "heavily sandboxed" up while knowing otherwise is the retreat.
