# Importing the Brain barrel opens the memory-core graph database

## Context

Split from #17369 under its AC-5, which permits *"the caller … is identified and named in the PR, **or a follow-up ticket is filed if it is a separate defect**."* #17369 removes the path that made this reachable from the Playwright fixture; it does not answer the question, and the question outlives it.

**Live latest-open sweep:** checked the latest 12 open issues at 2026-08-19T09:52Z; no equivalent found.

## The Problem

`ai/graph/storage/SQLite.mjs:49` loads the native binding through a **dynamic** import, carrying a comment stating it exists *"to prevent native Node module evaluation crashes inside browser/test runtimes."*

Observed on #17369 (2026-08-19, prior session): removing `better-sqlite3` from the tree made the Playwright fixture fail **at load** with

```
ERR_MODULE_NOT_FOUND … imported from ai/graph/storage/SQLite.mjs
```

A dynamic import inside a method should not resolve at module load. Something on the barrel path was calling it during initialization, and the mitigation that exists to prevent exactly this was rendered moot by the path that reached it.

## The Architectural Reality — what this ticket narrows, and what it does not

Verified by code read at `c39a430420`, so the next investigator does not repeat it:

- **The dynamic import is method-scoped, not module-scoped.** `SQLite.mjs:47-49` sits inside `async initAsync()`, after a `dbPath` guard. Nothing evaluates it on import.
- **Neither file instantiates at module scope.** `SQLite.mjs` has no top-level `new`/`await`; `GraphService.mjs`'s only module-level construction is `const PROTECTED_EDGE_TYPE_SET = new Set(PROTECTED_EDGE_TYPES)` — constants, no storage.
- **The static half of the chain is `ai/services/memory-core/GraphService.mjs:6` → `SQLite.mjs`.** That explains how the *module* is reached. It does not explain how `initAsync()` is *called*.

**So the premise "something reaches the dynamic import during initialization" survives the narrowing but is not pinned.** Two candidate explanations, neither tested:

1. A service on the barrel path constructs a graph-backed singleton during its own init, transitively awaiting `initAsync()`. If so, **an eagerly-opened graph connection is a defect well beyond the test harness** — it would mean importing the barrel opens a database.
2. The observation is explained by something other than the import graph. `test/playwright/playwright.config.unit.mjs:24-33` carries an explicit Brain-tier presence probe naming `better-sqlite3` including its compiled artifact `build/Release/better_sqlite3.node`. **Weak but not dismissable:** the reported error names `SQLite.mjs` as the *importer*, which a config-level probe would not produce.

## The Fix

Identify the caller, then decide — this ticket is a diagnosis before it is a repair.

1. Reproduce: remove `better-sqlite3`, load the fixture, capture the **stack** rather than the message alone. The stack names the caller; the message does not, which is why the original observation could not close this.
2. If a service opens the graph during init: that is candidate (1) and the real defect. Scope its repair here or split it once named.
3. If the trigger is the config probe or another non-import mechanism: candidate (2), close this as premise-falsified and record the correction on #17369, whose body asserts the import-graph explanation.

## Decision Record impact

`none`.

## Acceptance Criteria

- [ ] **AC-1:** The caller that causes `SQLite.mjs`'s dynamic import to resolve during initialization is named with a **captured stack**, not inferred from an error message.
- [ ] **AC-2:** The verdict is recorded on #17369, since that ticket's body states the import-graph explanation as the mechanism. If falsified, it is corrected there rather than left standing.
- [ ] **AC-3:** If a graph connection is opened eagerly at import/init, that is stated explicitly as its own defect with its blast radius named — every process importing the barrel, not only test runtimes.
- [ ] **AC-4:** Red-proof: whatever mechanism is identified, a probe must distinguish it from the alternative. A reproduction that only shows "it fails" repeats the original observation and closes nothing — the control is the *other* candidate, which must be shown not to fire.

## Out of Scope

- Changing the dynamic-import mitigation at `SQLite.mjs:49`. It is correct; this asks why it was bypassed.
- #17369's fixture change, which is independent and already removes the fixture's exposure.

## Avoided Traps

- **Assuming a lazy import is inert.** It carried a comment explaining it existed to avoid exactly this crash, and the crash happened anyway. A mitigation is only as good as the paths that respect it.
- **Reading an error message as a stack.** `ERR_MODULE_NOT_FOUND … imported from X` names the *importer*, never the *caller*. The original observation stalled precisely there, and AC-1 exists so the reproduction does not stall the same way.

## Diagnosed — candidate (1), and it is worse than "the fixture pays for it"

**Importing `ai/services.mjs` opens the memory-core graph database.** Not resolves the binding — opens the file and runs `initSchema()`.

### AC-1 — the caller, with a captured stack

The message-level stack was useless: the loader rejection originates in a loader worker, and `initAsync` is scheduled through `Promise.resolve().then()`, so both truncate. Captured it at **construction** instead, which is synchronous, via a `load` hook injecting a stack capture into `src/core/Base.mjs`:

```
SQLite.construct                     src/core/Base.mjs:313
  Object.create                      src/Neo.mjs:320
    Neo.create(SQLite, {dbPath})     ai/services/memory-core/GraphService.mjs:137
      GraphService.initAsync         ai/services/memory-core/GraphService.mjs:173
        (scheduled)                  src/core/Base.mjs:316
```

The whole chain, in order:

1. `ai/services.mjs` statically imports `GraphService.mjs`.
2. `setupClass` instantiates the **GraphService singleton at module load**.
3. `Base.mjs:316` schedules `GraphService.initAsync()` on the next microtask.
4. That calls `Neo.create(SQLite, {dbPath})` at `GraphService.mjs:137`.
5. `Base.mjs:315` schedules `SQLite.initAsync()`.
6. `SQLite.mjs:49` resolves `better-sqlite3`, then `new Database(me.dbPath)` + `initSchema()`.

So the dynamic import at `:49` is not defeated by anything exotic. **The deferral is syntactic, not behavioural** — exactly the property `hostBarrelRuntimeReach.spec.mjs` was written to catch, one layer further down than it currently looks.

### AC-3 — it fires, and the blast radius is not test runtimes

```
ai/services.mjs       → === DB OPENED === .neo-ai-data/sqlite/memory-core-graph.sqlite
ai/services.host.mjs  → (no database opened)
```

Instrumented at `me.db = new Database(...)`, so this is the open itself rather than an inference from the import.

**Any process that imports the cloud barrel acquires a handle on the real memory-core graph** — a CLI, a build script, a one-off diagnostic, a test runner. It is not scoped to anything. `initSchema()` runs, and the connection sets `journal_mode = WAL` and `busy_timeout = 5000`, so this is a live handle with locking semantics, not an idle file open. It also explains the downstream `Statement::~Statement()` teardown abort concretely: the process was holding a real database it never asked for.

### AC-4 — red-proof

The host barrel is the control: identical probe, identical instrumentation, **no database opened**. So the instrument discriminates rather than reporting a generic success, and the difference is attributable to the barrel split rather than to the probe.

### AC-2 — verdict recorded against #17369

**Candidate (2) is falsified.** The unit config's `better-sqlite3` presence probe is not the mechanism; the import graph is. #17369's body asserted the import-graph explanation and was **correct** — the doubt I filed here was mine, not a defect in that ticket. Recording it on #17369 as this AC requires, so a later reader does not inherit a resolved question as open.

### What this ticket becomes

The diagnosis is complete, so the remaining work is a repair whose shape is not mine to pick unilaterally: **`GraphService` opens storage in `initAsync`, and `initAsync` is unconditional at module load.** The obvious direction is to make the connection lazy — acquired on first use rather than at construction — but that touches memory-core initialisation ordering and every consumer that currently relies on the singleton being ready after a microtask. That is a scoping conversation, not a patch I should land off my own diagnosis.

Retitling and re-scoping this ticket accordingly rather than closing it: the question it was filed to answer is answered, and what it found is bigger than what it asked.

## Blast radius, measured — so the repair decision has inputs rather than adjectives

I called this "a scoping conversation, not a patch" from instinct. Measuring it first, because that claim was itself unverified.

```
GraphService references across ai/ (excluding its own file and specs):  494
direct `.storage` touches within ai/services/memory-core/:              129
```

**And one fact that cuts the other way:** `GraphService.initAsync` is *already* memoised and idempotent —

```js
if (this.db || this._initPromise) { if (this._initPromise) await this._initPromise; return }
this._initPromise = (async () => { … })();
await this._initPromise;
```

— and it already degrades rather than throws, recording `graphInitError` and leaving `this.db = null`. So **the lazy-acquisition primitive substantially exists**; what does not exist is a safe way to move consumers off the current guarantee that `db` is populated once the post-construction microtask has run.

### Two candidate shapes, with what each actually costs

**(a) Make acquisition lazy in `GraphService`.** Keep `_initPromise` as the memo, stop calling it from `initAsync`, and route reads through an `ensureDb()`. The primitive is there and the degradation path is there. The cost is the 494/129 surface: every consumer that today touches `.db` / `.storage` synchronously after boot needs an await, or the accessor has to become async and the change stops being local. This is the shape that fixes the defect *for every importer*.

**(b) Stop the barrel instantiating the singleton at import.** `ai/services.host.mjs` demonstrably opens nothing under the identical probe, so the split already encodes a working answer to a neighbouring question. Much smaller, and it is the same move #17369 made one level up — but it fixes the *import* path rather than the *behaviour*, so a consumer that legitimately imports the cloud barrel still gets an unrequested database.

They are not exclusive: (b) is a containment and (a) is the repair. (b) alone would leave the defect true and merely harder to reach, which is the shape I would reject in review, so it should not ship as the whole answer.

### What I am not doing

Not picking between them off my own diagnosis, and not opening an Ideation Discussion off a hunch either — the numbers above are what such a round would need as input, and they now exist. My read is that (a) at 494 call sites crosses the bar for a consensus round rather than an author decision, but that is a judgement about *this* repo's tolerance for a wide mechanical change, and the peers who own memory-core init ordering should set it rather than me.

Recorded here so the decision is made from measurement whenever it is made, and so a later reader does not re-derive the 494.
