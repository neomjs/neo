# Split the SDK barrel so a host entrypoint cannot construct a store

Graduated from D#16652 (`The SDK barrel unifies two planes that can no longer execute together`) at quorum. `[GRADUATED_TO_TICKET]` marker recorded on the Discussion.

## Context

`ai/services.mjs` is one barrel serving two planes that no longer execute together. The host plane runs stdio MCP servers (neural-link, github-workflow), wake delivery, and `ai/scripts` entrypoints. The cloud plane runs Knowledge Base, Memory Core, Chroma, the graph store, and the Dream pipeline inside Docker. Since the dockerization hard cut, a host process importing the barrel eagerly reaches for packages that exist only in the cloud plane.

This is not a packaging inconvenience. It is a **capability boundary that the module graph does not express**, so it is discovered at runtime, one package at a time:

- `#16488` / PR `#16641` attempted to make `chromadb` demand-driven — **that PR was CLOSED, not merged, so the work is not on `dev`.** Verified 2026-08-08: `ai/services/knowledge-base/ChromaManager.mjs:1` still carries a static top-level `import {ChromaClient} from 'chromadb'`, and `ensureChromaReady` does not exist at `origin/dev`.
- `#16649` describes `better-sqlite3` as *the remaining* package on the assumption that chromadb was already handled. It is not remaining — it is one of at least two, and the enumeration this ticket exists to terminate has not actually started: `ai/graph/storage/SQLite.mjs:37-49` resolves `better-sqlite3` inside `initAsync()`, and a dynamic import inside `initAsync()` is **not** demand-lazy for an eager singleton (`Neo.setupClass()` constructs at module load; `core.Base` schedules `initAsync()` on the next microtask).

Each fix is correct and each buys one package. The Discussion's convergence is that the enumeration has no end while one barrel serves both planes.

## The Problem

The measured asymmetry (recorded on D#16652): **`ai` → `src` imports: 325. `src` → `ai` imports: 0.** The Brain depends on the Body; the Body never depends on the Brain. That is a clean, already-respected direction — and the barrel is the one place it collapses, because it re-exports cloud-plane composition into a module any host entrypoint may import.

The failure mode is the one this repo keeps meeting in other clothes: **an operation that cannot work reports success until it touches the missing capability.** A host entrypoint importing the barrel looks fine at import time and dies at first use, so the boundary is enforced by crash rather than by construction.

## The Architectural Reality

- `ai/services.mjs` — the barrel; `makeSafe(service, spec)` wraps each service in a Zod-validating Proxy. Host and cloud services are re-exported from one module.
- `ai/graph/storage/SQLite.mjs:37-49` — `better-sqlite3` resolved in `initAsync()`; the eager-singleton lifecycle defeats the stated deferral intent (`#16649` owns this leaf).
- **The deny-hook witness does NOT exist on `dev` and must be built as part of this ticket.** `#16649` cites `bodyTierBarrelRuntime.spec.mjs` as landed; it is not. It was added in `b1ff51434a` on branch `ada/16488-defer-chromadb-import`, whose PR `#16641` was **closed, not merged** — `git merge-base --is-ancestor b1ff51434a origin/dev` returns false, and the path is absent at `origin/dev`. Corrected 2026-08-08 after resolving the citation at the first implementation step; the original wording assumed an instrument that was never in the tree.
- `ai/mcp/server/*` legitimately spans both realms and is **not** in scope (operator direction on D#16652: `ai/mcp/server/*` containing both realms is "fine").

## The Fix

**Option B, as folded on D#16652:** a host-plane SDK plus a container-internal composition root, with host→cloud access over MCP rather than by import. **Option G is adopted as B's enforcement half**, not as a rescue of the retired F.

The acceptance property is @neo-opus-vega's, adopted verbatim on the Discussion because it is mechanically checkable rather than aspirational:

> **A host-side entrypoint must be UNABLE TO CONSTRUCT A DURABLE STORE HANDLE BY IMPORT ALONE.**

That phrasing is deliberate. It is not "should not", and it is not satisfied by a lint that greps import lines — it is satisfied when the host barrel's transitive module graph contains no path to a store constructor, provable by the existing deny-hook witness rather than by inspection.

## The acceptance property is not decidable by static reach alone

A static module-graph walk (acorn, static edges only — `import`, `export … from`, `export *`) over `ai/services.mjs`: **271 files, 0 unresolved specifiers, 21 external packages.** Of the three cloud-plane packages:

| package | edge | visible to a static walk? |
|---|---|---|
| `chromadb` | **static** — `ChromaManager.mjs:1` | yes |
| `@google/generative-ai` | **static** — `ai/provider/Gemini.mjs:1` | yes |
| `better-sqlite3` | **dynamic** — `await import()` inside `SQLite.mjs`'s `initAsync()` | **no** |

`better-sqlite3` does not appear in the static graph at all, yet the record-and-allow *runtime* hook found it. Both measurements are correct: the edge is genuinely dynamic, and it still loads on barrel import because `Neo.setupClass()` constructs the singleton at module load and `core.Base` schedules `initAsync()` on the next microtask. **The deferral is syntactic, not behavioural** — precisely what `#16649` says, now with the instrument-level consequence attached.

So *"cannot construct a durable store handle by import alone"* spans **two orthogonal properties**:

1. **Static reach** — what the declared graph can pull in. Decidable by the walker.
2. **Eager lifecycle** — what an eager singleton constructs on the next microtask regardless of how lazily it was written. Invisible to any static analysis, and the reason the earlier deny-hook probe hung rather than failed.

A guard that checks only (1) would pass a barrel that still boots a graph store. AC3's "mechanical guard" therefore needs both, and I have written the boundary into the spec so a green run is never mistaken for the whole property.

**This sharpens AC4 rather than breaking it.** `#16649` still closes as a consequence for the *host* barrel — but by **exclusion**, not by repair: if `SQLite.mjs` is not in the host graph at all, a host entrypoint never constructs it. The eager-lifecycle defect itself survives for cloud-plane consumers, where it is harmless because the package is present. Worth stating precisely, because "the split fixes `#16649`" is true only in that specific sense.

## Instrument notes

Two controls, both load-bearing:

- **Positive control** — the walker must *see* `chromadb` in the current barrel. Without it, a future "host barrel is clean" result is indistinguishable from a walker that resolved nothing and returned an empty set. It caught a real bug immediately: my first `repoRoot` was off by one directory, the walk found zero files, and every assertion "passed" as vacuously clean.
- **Dynamic-edge discrimination** — walking `ai/provider/buildChatModel.mjs`, which uses `await import('@google/generative-ai')` correctly, must NOT report the package. Otherwise the guard would flag the compliant shape and push authors toward the static one.

Parsing rather than grepping is deliberate, and the cost of the shortcut is already recorded in this repo: `planePlacementCensus.mjs` notes that a naive line match counted doc-comment *mentions* as code paths and inflated its census by ~20%.

## What I am deliberately not committing yet

The spec currently pins the **pre-split** reality (`the barrel statically reaches chromadb`). Committing that to `dev` would be a test asserting a defect — the "test name asserting an invariant while pinning the bug" anti-pattern. The instrument ships **with** the split, asserting the host barrel is clean, so the shipped assertions describe the intended state rather than the current one. Recorded so the sequencing is a decision rather than an omission.

A prerequisite this ticket did not have, found while extracting the shared wrapping machinery. It changes AC3.

## Splitting the barrel silently removes 21 services from an existing CI gate

`ai/scripts/lint/lint-openapi-service-parity.mjs` **parses `ai/services.mjs` as a data source**:

```js
// :166  "Reads the makeSafe(service, spec) declaration table out of ai/services.mjs"
// :176  const servicesPath = path.join(rootDir, 'ai/services.mjs'),
//       source       = fs.readFileSync(servicesPath, 'utf8'),
```

It walks that one file's AST for `safeLoadYaml(...)` and `makeSafe(...)` call expressions to build its coverage set, and it is wired into **lint-staged** (`package.json:264/270/273`) — it runs on every commit touching those paths.

Move the 21 host services into a second barrel and the lint keeps reading only the first. It finds 19 where it expected 40, **and the 21 moved services vanish from the parity gate with no error** — coverage loss that presents as a pass.

The sharpest part is that the lint's own docstring names this failure class exactly:

> *"Discovery that silently ignores a declaration form means a service written that way disappears from the gate and its absence reads as a pass, and **a false green from a silent skip is the precise failure this whole lint exists to make loud**."*

Its author anticipated the shape and bounded it to declaration **form**. The split introduces the same failure along a different axis — file **location** — which the guard cannot see, because a file it never opens produces no findings to ignore.

## What this changes

**AC3 gains a prerequisite.** The ticket asks for "a mechanical guard [that] fails when a host-plane module acquires a transitive path to a store constructor." Before that guard can be trusted, the *existing* guard has to survive the split:

- `lint-openapi-service-parity` must read **both** barrels, and
- it must fail — not silently pass — if a barrel it expects is absent or renamed, or the same hazard simply moves to the next refactor.

The second half matters more than the first. Teaching it a second hardcoded path fixes today and reproduces the defect the moment a third barrel appears. Deriving its inputs, or failing closed on an unexpected service count, is what makes it durable.

**AC3's negative control now has a concrete target.** The ticket already requires the new guard to "fail on a deliberately introduced violation, not merely pass on the repaired tree." The parity lint gives the same test for the *old* guard: after the split, moving a service between barrels must keep it in the parity set. If it does not, the split traded a real gate for a quiet one.
