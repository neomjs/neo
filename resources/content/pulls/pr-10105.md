## The Problem

Today's concept ontology (~59 nodes) is derived almost entirely from guide titles. That's a thin seed: architectural vocabulary emerging from actual Swarm work — session summaries, ticket discussions — is invisible to the ontology. Without a discovery channel, the only growth path is manual `nodes.jsonl` edits, which don't scale as session + issue volume grows.

#10036's intake discussion clarified the core trade-off: *both of us don't yet know for sure what qualifies as a concept, or how many there will be.* The right first-pass architecture is **low-cost deterministic extraction + conservative defaults + human review as the promotion mechanism**. No LLM, no staging file — the existing weight gate plus a new `validated` flag silence unvalidated candidates; git diff on `nodes.jsonl` is the curator's review UI.

## Architectural Reality (verified against precedent)

- `ai/daemons/services/ConceptIngestor.mjs` — additive one-way sync from curated JSONL → graph. Splitting discovery into its own service keeps that directional invariant: `ConceptDiscoveryService` is the reverse-flow proposal channel (JSONL ← discovery); `ConceptIngestor` is unchanged (JSONL → graph).
- `ai/daemons/services/GapInferenceEngine.mjs:inferConceptGraphGaps` — already iterates CONCEPT nodes with a weight gate. Adding `if (concept.properties?.validated === false) continue` at the top of the loop is a one-line explicit override that stays orthogonal to the weight gate. Legacy rows without the field (`undefined`) are treated as validated — no data migration.
- `ai/daemons/services/IssueIngestor.mjs` — established the `resources/content/issues/*.md` scanning pattern. `ConceptDiscoveryService.mineFromIssues` mirrors it without duplicating the graph-ingestion machinery (we just want vocabulary, not graph nodes).
- Memory Core summary collection via `StorageRouter.getSummaryCollection` — the existing Swarm-summary substrate. No new DB surface needed.
- `.neo-ai-data/concepts/nodes.jsonl` — 59 existing rows. Appending new rows preserves the git-diff review workflow; no row rewriting.

## Gold Standards Leveraged / Traps Avoided

- **Gold Standard** (additive ingestor pattern): ConceptDiscoveryService appends to the same JSONL ConceptIngestor reads. Next cycle auto-picks up new candidates; no special routing.
- **Gold Standard** (weight-gate reuse): candidates get tier 3 → default weight 0.3 via `ConceptService.calculateWeight` → below `guideGapWeightThreshold` default 0.8 → silenced. `validated: false` is belt-and-suspenders, not the primary silencer.
- **Gold Standard** (Hebbian floor from ticket): MIN_FREQUENCY = 3 distinct sources. A single verbose epic mentioning a term 50 times doesn't promote — cross-source recurrence is the signal.
- **Trap avoided** (dual-file staging): per the intake discussion, a `candidates.jsonl` split would duplicate the curator's review surface. Git diff on `nodes.jsonl` is simpler and matches existing curator muscle memory.
- **Trap avoided** (LLM extraction): `ask_knowledge_base` and gemma4-31b would give higher-quality semantic extraction but introduce provider dependency, ChromaDB cold-start latency (the exact KB timeout noted in the ticket body), and LLM-noise that the conservative defaults already guard against. Deterministic regex is sufficient for the first pass; if we hit precision/recall walls, revisit with KB-assisted classification (deliverable 3).
- **Trap avoided** (ingest-loop integration): wiring discovery into `processUndigestedSessions` would run it every REM cycle, flooding `nodes.jsonl` with churn. Standalone invocation lets curators decide when to run a discovery pass.
