# Reconcile GitHub issue activity exhaustively

## Context

Option H selects exhaustive resource-family reconciliation as completeness authority. This first GitHub adapter leaf also establishes the shared normalized runner and source-relative actor/trust foundation consumed by later PR and Discussion leaves; it is not a framework-only ticket.

This is one fully closeable PR leaf under Epic #15145. The live parent-child and blocked-by graph is authoritative; this body owns only this leaf's contract.

## The Problem

Current issue sync is conditional and snapshot-oriented: child exhaustion depends on root refetch, stable child revision fields are pruned, and absence cannot distinguish deletion from permission loss. Notifications and repository events are accelerators, not complete occurrence sources.

## The Architectural Reality

GitHub acquisition stays in `ai/services/github-workflow/`, matching `IssueSyncer.mjs`, `issueQueries.mjs`, and `PullRequestHistoryService.mjs`. The shared runner is earned inside this issue-family delivery. Actor kind remains independent from security/content trust; automatic normalized batches contain metadata only.

The Agent OS structure map was run on 2026-07-14. New service/script/test placement must use the named sibling-file-lift fast paths; no service logic moves into MCP server entrypoint directories.

## The Fix

Add exhaustive active+closed issue enumeration, independently exhausted comments/timelines, stable provider identities, create/edit/close/reopen/delete observations where provider evidence exists, inventory verification, explicit loss markers, source-relative collaborator/trust context, and neutral batch output for Memory Core admission.

## Operator Scope Clarification — 2026-07-14

The community substrate is **not** a mirror of every GitHub repository notification. It separates:

1. **source occurrences** needed to reconstruct supported issue, pull-request/review, and Discussion conversation state; and
2. **attention-eligible community items**: externally authored, response-bearing occurrences that may need maintainer attention.

Stars/un-stars, forks, watches, and equivalent popularity telemetry are outside the community-event source families and cannot enter Bird View, counts, wake, or Task claim. Internal/rostered actions may update or resolve the state of an existing external item without minting new community attention. First-time versus trusted-repeat external status affects trust/projection, not basic eligibility. Bot eligibility must be an explicit ADR disposition and cannot be inferred from provider actor kind or trust tier.

Attention eligibility remains zero-authority: it does not assign work, enter LifecycleFrontier, or create a Task. Only the explicit canonical claim transition owns that promotion.

## Arc ruling — one classifier, distinct production emitter

Fresh source check against ADR 0036, the merged admission contract, the classifier, and the shadow reader resolves both questions.

### 1. Confirm one classifier / three producers — with one refinement

**Confirmed.** Issue, PR/review, and Discussion adapters emit source facts; `CommunityBatchAdmissionService` owns the one attention decision through `communityAttentionClassifier`.

The production observation should carry the canonical fact inputs:

- stable `actorId` when the provider supplies one;
- normalized provider `actorKind`;
- `occurrenceKind` + stable coordinate/time;
- source-relative provider evidence such as `sourceAssociation`;
- absence/deletion evidence where applicable.

It should **not** carry connector-authored `attentionDisposition`, `eligibility`, `trustProjection`, or a policy-shaped `responseBearing` Boolean. The classifier already derives response-bearing status from the injected `responseBearingKinds` set keyed by `occurrenceKind`. Letting an adapter assert a Boolean would create a second policy input and let producer drift bypass the shared classifier.

AC10–AC12 therefore belong as adapter fixtures passed through the shared admission classifier, exactly as proposed: excluded families never produce observations; rostered actors never mint attention; external-user trust cohorts produce identical eligibility for the same response-bearing kind; bot/unknown kinds fail per the accepted v1 table.

### 2. Keep the production runner/emitter distinct from the shadow emitter

**Keep them distinct.** The shadow reader’s private `occurrence()` shape is measurement-oriented and explicitly window-bounded: `eventType`, `mutationKind`, `responseBearing`, `activityAt`, timestamp bags, lower-bound gaps. ADR 0036 forbids that probe from becoming completeness or admission authority.

#15152 should establish the canonical issue reconciliation runner + admission observation normalizer. The later PR/review and Discussion producers reuse that production contract. Reusing the whole shadow emitter would invert the authority order and couple durable completeness to a lower-bound probe.

Sharing a narrow provider-fact helper later is fine only where semantics are literally identical (for example actor-kind normalization or stable provider-id extraction). Do not share the measurement envelope.

### Trust boundary refinement

Adding `sourceAssociation` now is correct as provider evidence. Do **not** call `conversationTrust` to stamp a trust tier into the automatic batch: that helper is the explicit prose-read projection, while ADR 0036 requires automatic paths to remain metadata-only and tenant/source-relative. The batch validator also reserves/rejects connector-authored `trustProjection`.

Reuse the same source-relative collaborator inputs and underlying trust policy at explicit drill-down; keep actor kind, provider association evidence, and later server-side trust projection as three non-collapsed axes.

**Residual test implication:** add a negative witness that a connector-provided response-bearing/policy field cannot steer classification, plus a shape witness that the shadow measurement row is not accepted as the production observation contract.
