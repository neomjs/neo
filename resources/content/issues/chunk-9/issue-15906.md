# Workstation cross-window docking: conversion, arbitration, stack return

## Context

Increment 2 of the `#15252` capstone ladder, minted by the operator-directed reshape (2026-07-25): the one-PR-vehicle plan is superseded — increments merge as they green, the film iterates against merged reality. Increment 1 (PR #15840, ready-for-review) shipped the vessel shell, tear-out composition, journey executor, and the green scene-1/2 witnesses including the morph. This ticket is the remaining WIRING: the popup that knows it is a dock.

## The Problem

The workstation can tear a pane OUT into a live vessel and bring it home mid-gesture — but a vessel is not yet a dock TARGET. Scenes 3–4 of the five-beat journey are contracted `test.fixme` legs in `test/playwright/e2e/workstation/WorkstationFiveBeatNL.spec.mjs`, each naming its worker-truth receipts:

- **Scene 3:** a second pane converts to a vessel WHILE ITS DRAG CONTINUES (park-not-close lifecycle); dragged over the first popup, the TARGET popup's zones preview (remote previews rendered inside the other window); with overlapping candidates EXACTLY ONE preview claims (deterministic arbitration asserted from the claim registry, never pixels); release docks — two panes in one popup, both stores streaming.
- **Scene 4:** stack-handle drag home; the commit lands the WHOLE stack atomically (one document transaction); the emptied vessel closes itself AFTER the commit, terminal only when the runtime windowId leaves the connected topology (dispatch success is never effect proof); same-instance identity + heartbeat continuity across the return.
- **Scene 5:** the full five-beat journey in ONE run, two-take beat-log equality — the capstone determinism contract and the film's recording form.

## The Architectural Reality

- **Shipped mechanism (compose, never rebuild):** `src/dashboard/DockVesselConversion.mjs` (308 — convert-while-dragging sensor), `DockVesselPark.mjs` (391 — park/reshow/dispose lifecycle), `DockWorkspaceSet.mjs` (172 — multi-workspace registry), `CrossWindowDragTarget.mjs` (204) + `DockCrossWindowParticipation.mjs` (288 — the remote-target machinery), plus the tear-out/embodiment already composed by increment 1.
- **Sibling source (map, not verbatim lift):** `apps/agentos/childapps/dockdemo/view/DemoBWorkspace.mjs` — `executeCrossWindowStep` (:1965, the two-window transfer executor), the cross-window stage composition (:460-553), transfer commit via the atomic two-document `transferItem`/`transferNode` seams. Its app-local `DemoBCrossWindowStage.mjs` (727 lines) carries per-workspace geometry registries and hit-testing that the workstation must NOT replicate — see the binding below.
- **BINDING (production-record D-013, from the operator's `manager.Window` probe, recorded publicly on `#15895`):** the workstation consumes `Neo.manager.Window` — the live screen-space geometry authority (inner/outer/chrome rects, high-frequency updates) with `getWindowAt(x, y)` — for cross-window hit-testing and vessel-follow receipts. DemoB's parallel `hitTestWorkspace` + `crossWindowGeometry` registry pattern is explicitly rejected for this consumer: one geometry authority, less app-local state.
- The workstation remains single-document-plus-vessels; the popup workspace document (the vessel's own dock document, seeded on first dock-INTO) is new state this increment introduces — the DemoB popup-document pattern applies at workstation grain.
- **App-work gate applies** (`apps/**`): the five neo-core contracts load before authoring; `structural-pre-flight` fires for any new `.mjs` file (sibling expectation: composition stays inside `Workspace.mjs` unless the cross-window block outgrows the class — decided at authoring time).

## Integration map — 8 of 10 seams already exist in `Workspace.mjs`; 2 need new plumbing

Claimed while @neo-kimi-iris is held (her design authority stands). This is the read done once so the implementation does not have to re-derive it: every owner seam `DockCrossWindowParticipation` requires, resolved against the workstation's landed surfaces.

**Composition site:** `apps/workstation/view/Workspace.mjs:310-315`, immediately after `me.dragAffordances = Neo.create(DockDragAffordances, …)` — the same idiom the eight sibling adapters already use.

### Seams that exist today

| Adapter seam | Workstation surface |
|---|---|
| `getDocument` | `getDockZoneDocument()` — `:510` (returns the live committed `dockModel`) |
| `commitLocal` | `applyDockZoneOperation(descriptor)` — `:376`, already `{document, errors}`-shaped, the same path in-window drops ride |
| `previewToOperation` | already imported at `:20` from `src/dashboard/dockPreviewContract.mjs` — pass the import straight through |
| `previewFor` / `clearPreview` | the persistent `dock-preview` overlay, `getReference('dock-preview')` — created at `:298`, object-permanent across re-projections |
| `hitTest` | the `dock-host` container reference — `:304`; window-local, side-effect-free bounds check |
| `windowId` | `me.windowId`, used throughout the tear-out choreography (e.g. `:1263`) |
| `sortGroup` | the dock sort group already stamped by `DockTabSortZone` on drag start |
| `dragCoordinator` | leave null — the target defaults to the `Neo.manager.DragCoordinator` singleton |

### The two that do not exist — and they are what scenes 3–4 actually need

1. **`workspaceId`** — `grep workspaceId apps/workstation/view/Workspace.mjs` returns **nothing**. The workstation has no workspace-set identity, and the adapter's local-vs-foreign discrimination keys on exactly this (`dockSourceWorkspaceId` vs ours). Without it every drop looks local and a foreign transfer silently takes the wrong path. This is the first real change: mint a stable per-workspace id and stamp it where `DockTabSortZone` stamps the payload.
2. **`getForeignDocument(sourceWorkspaceId) → document`** and **`commitTransfer({sourceWorkspaceId, sourceDocument, targetWorkspaceId, targetDocument, descriptor})`** — the workstation resolves sibling windows only as *views* (`Neo.apps[windowId]?.mainView`, `:322`/`:1583`), never as a keyed set of workspace documents. Both seams need a worker-owned registry mapping `workspaceId → Workspace`, which is also what makes the atomic two-document `transferItem` publishable.

### Consequence for the film, stated plainly

Scene 3 (two panes into one popup) and scene 4 (whole-stack reintegration) are **foreign** transfers, so they depend entirely on item 2. The wiring is therefore not "add one adapter" — it is one adapter plus a workspace-set registry. That is bigger than the `test.fixme` header implies (*"the mechanics are already shipped in src/dashboard"* is true of the dashboard tier and not of the app tier), and it is the honest reason the film's three closing beats have never run.

Nothing landed yet; no half-wiring committed. Next step on this lane is the registry plus the adapter composition, and the fixme stubs become real assertions in the same change — a green suite that still skips its three closing scenes would be a false receipt, and I already had to retract one of those today.
