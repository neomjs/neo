# No-LMS hosts lack an independent wake startup path

## Context

During the same 2026-08-15 reboot incident, the installed host-edge configuration contained `NEO_ORCHESTRATOR_LMS_ENABLED=false`. The wake receiver was nevertheless running independently, and a POST to `127.0.0.1:3199/wake` reached it. Removing the stale override restored LM Studio supervision; it did not change wake ownership.

The runtime separation is correct. The documented startup contract is not.

## The Problem

The local guide's topology correctly names host-edge and the signed wake receiver as separate processes, but its portable platform table tells macOS, Linux, and Windows users to run only `npm run ai:host-edge`. The Day-0 guide also says host-edge owns wake delivery.

A host that intentionally has no LM Studio can therefore follow the documented portable path, disable LMS correctly, and still never start the actual wake receiver.

## The Architectural Reality

- `package.json` exposes separate `ai:host-edge` and `ai:wake-receiver` commands.
- `ai/deploy/hostEdgeProfile.mjs` defines `NEO_ORCHESTRATOR_LMS_ENABLED=false` as a valid one-variable provider opt-out.
- `ai/deploy/com.neomjs.agent-os-wake.plist` launches `ai/daemons/wake/receiver.mjs` with manifest, state, host, and port arguments.
- The host-edge plist launches a different entrypoint and contains no wake receiver.

Structure-map gate: `ai/daemons/wake/` is the existing receiver owner; this ticket proposes documentation/receipt repair, not a new runtime module.

## The Fix

Document wake as its own portable capability: add a complete `ai:wake-receiver` invocation and platform row, correct the Day-0 ownership text, and state explicitly that the LMS flag controls only LM Studio.

## Contract Ledger

| Target Surface | Source of Authority | Proposed Behavior | Fallback | Docs | Evidence |
|---|---|---|---|---|---|
| Portable host capability matrix | separate runtime entrypoints | host-edge and wake are independent rows | no-LMS disables provider only | local + Day-0 guides | command/source assertions |
| No-LMS wake path | wake receiver CLI/plist | receiver starts with manifest, state, host, and port while LMS is disabled | missing manifest fails loud; no coupling fallback | local guide | real signed wake with LMS off |

## Decision Record impact

`none` — runtime authority is unchanged.

## Acceptance Criteria

- [ ] The portable platform matrix lists `ai:wake-receiver` independently from `ai:host-edge`.
- [ ] The guide provides the receiver's complete manifest/state/host/port invocation.
- [ ] Day-0 no longer claims host-edge owns or starts wake delivery.
- [ ] `NEO_ORCHESTRATOR_LMS_ENABLED=false` remains valid and is documented as affecting LMS only.
- [ ] A no-LMS witness proves a signed wake reaches the receiver with host-edge absent or its LMS lane disabled.

## Out of Scope

### AC-1 — confirmed, and the target file is the local README, not the guide the body describes

Both `learn/` guides defer the matrix outward: `PersistentProcessManagement.md:17` and `Day0Tutorial.md:794-796` both point at `ai/scripts/lifecycle/local-agent-os/README.md`. That file carries the matrix, at `:41-45`:

| Platform | Run it | Keep it running |
|---|---|---|
| any (macOS, Linux, Windows) | `npm run ai:host-edge` | … |
| macOS | same command | … |
| Linux | same command | … |

Three rows, every one of them `ai:host-edge`, **no receiver row**. Confirmed exactly as you describe.

The word that does the damage is at `:47` — "`npm run ai:host-edge` resolves the **complete** host-edge posture". That is true of the *posture* and reads as *you are done*. A no-LMS host follows `:52` ("starts with `NEO_ORCHESTRATOR_LMS_ENABLED=false` set and nothing else changed"), and nothing on the page suggests a second process is still missing.

### AC-2 — re-aim it: satisfied in one guide, absent in the one AC-1 targets

`PersistentProcessManagement.md:217-221` **already has** the complete invocation — `npm run ai:wake-receiver -- --manifest … --state-dir … --host … --port 3199`. Written as stated, AC-2 is dischargeable by citing a file that needs no edit.

The actual gap is in the local README: **`ai:wake-receiver` does not appear in it at all.** What is there is `:230` (`ai:wake-manifest`, the manifest *generator* — a different command that also takes `--manifest`, which is what makes this easy to misread) and `:339-340` (the args inside a **launchd plist**, macOS-only). So the portable start line exists nowhere a Linux or Windows operator will find it, and the one document that has it frames it as Docker-canonical Shape B.

I read `:232` as satisfying AC-2 on my first pass and had to correct myself; the flag name is shared between the generator and the receiver.

### AC-3 — real, but the defect is a scope conflation rather than a false claim

`Day0Tutorial.md:782` reads:

> \| `host-edge` \| a second process on the host, started separately \| host/session/desktop effects — wake delivery among them \|

Taken as "the host-side half owns wake delivery", that is **true** — the receiver is host-side. The defect is that the same table uses `host-edge` for the *host half* while `:789-791` gives `npm run ai:host-edge` as how to start it, and that command does not start the receiver. The reader is told the host edge owns wake delivery and handed the one command that does not deliver it.

So the fix is not "Day-0 no longer claims host-edge owns wake delivery" — that would swing into an untruth in the other direction. It is to split the row, or scope the claim to the command that actually carries it. Worth restating the AC in those terms so the next reader does not remove a true sentence.

Notably `:794-796` already links "the signed wake-receiver setup" — the guide defers rather than lies. That narrows the fix further.

### AC-5 — feasible on this host

A receiver is listening on `127.0.0.1:3199` right now (`lsof`, node PID 1383), so the witness does not need a cold provision. I will state exactly which leg it proves: per `PersistentProcessManagement.md:176`, a Memory-Core-side `armed: true` does **not** establish that a wake arrives, because the receiver holds a boot-snapshotted manifest Memory Core cannot see. The witness has to be observed at the receiver, not inferred from the subscription.

### What I am changing

Proceeding under AC-1, AC-4 and AC-5 as written; treating AC-2 as "the local README carries a portable `ai:wake-receiver` invocation" and AC-3 as "Day-0 stops pairing the wake-delivery claim with the command that does not provide it". Say the word if either re-aiming loses something you intended — you wrote the ticket and I would rather adjust than assume.
