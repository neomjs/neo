* test(ai): the runtime deny-hook witness AC1 requires, with two failure directions (#16710)

The static walk states its own boundary: the acceptance property is not decidable by
static reach alone, because `better-sqlite3` is reached through `await import()` inside
`initAsync()` and still loads on barrel import — `setupClass` instantiates the singleton
and `core.Base` schedules `initAsync` on the next microtask. The deferral is syntactic,
not behavioural. AC1 asked for the runtime half; this is it.

Recovered from the closed, unmerged chromadb branch rather than rewritten. That branch's
own commit message records the mistake this file prevents, in its author's words:
"I promoted a static-walk result into a runtime claim." The loader's ERR_MODULE_NOT_FOUND
fidelity is the load-bearing part and is carried verbatim.

Three tests, and the two controls are why the first one means anything:

  HOST barrel survives with every cloud-only package denied      the AC1 property
  CONTROL: CLOUD barrel dies under the IDENTICAL denial          denial is real, and the
                                                                 split is what causes it
  CONTROL: HOST barrel dies when js-yaml, which it uses, is denied  the probe observes
                                                                    THIS module

Both controls also assert the REASON, not just the failure. A spawn that died of a bad
cwd or a missing loader would satisfy a bare `survived === false` while proving nothing,
so each control matches the specific denial marker it should have died of.

Mutation-proven rather than argued: injecting a static chromadb import into the host

* docs(ai): choose the SDK barrel by required exports, not by where the script runs (#16710)

RA-2A correction. My previous guide edit published a substitution rule keyed on
execution location — "host processes take the host barrel" — and the guides' own
examples import `KB_QueryService`. Following the published instruction turns the example
printed directly beneath it into a missing-export failure.

Measured export populations:

    host barrel   GH  GL  NeuralLink  Shared              (KB_ count: 0, Memory_ count: 0)
    cloud root    GH  GL  KB  Memory  NeuralLink  Shared

So the axis is the exports a script needs, never its physical location. A host-side
script requiring KB_ or Memory_ cannot use the host barrel at all — that is a missing
export, not a degraded mode.

Reframed rather than patched, because the stronger statement was available: the host

store. When a host-side script does need KB_ or Memory_, the friction is the architecture
speaking — those services reach a store and a host machine has only the base package
tier — so the guides now name it as a design signal rather than something to route around.

I inferred capability from location. Caught by @neo-gpt-emmy, who checked the rule against
the export population rather than against its own reasoning.
