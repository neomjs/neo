Resolves #17188

Deletes two `expect(payloadReads).toBe(1)` assertions that restated a strictly weaker form of the post-completion assertion three lines below them, while being the only part of these tests that depended on a turn budget.

Evidence: L2 (in-process spec runs, plus a mutation experiment against the production single-flight with the turn budget set to zero) → L2 required; the change is confined to one spec file with no host, UI, or deployment effect. No residuals.

## The ticket's original claim was wrong, and I proved it wrong before building on it

I filed #17188 saying these two spins **pass vacuously** and silently stop testing under contention. That is not what they do, and the correction is why this PR is a deletion rather than the arrival-anchor hunt the ticket originally prescribed.

The experiment I should have run before filing:

| run | result |
|---|---|
| turn budget `0`, single-flight intact | **passes** — the second caller joins with no wait at all |
| turn budget `0`, single-flight **disabled** | **fails** at the post-completion assertion, `Expected: 1 / Received: 2` |

**With the wait removed entirely, the defect is still caught.** Detection never lived in the spin — it lives in the deterministic post-completion assertions, which run after both callers settle and are unaffected by the budget. "One read *so far*" is strictly weaker than "one read *in total*".

The body of #17188 is corrected in place with the original claim retained under *Superseded original claim*, so nobody re-derives it.

## What the wait is actually for, and why it stays

It is a **false-failure preventer**, not a detector.

The single-flight entry is dropped when the first caller's read *resolves* (`MailboxService.mjs:1216-1220`), which happens after `releasePayloadRead()`. A second caller that only decided after that release would legitimately miss the pending promise, open its own read, and fail the post-completion check **on correct code**. The turns buy the overlap that prevents that.

So its failure mode is a **false RED**, and under `workers: 4` that surfaces as a `flaky` — which per #15861's amended AC-2 is a positive detection that **disqualifies the sample**. A false flaky here costs a probe sample exactly as much as a real defect. That is why this still blocks #15861, and why deleting the wait along with the assertion would have been the wrong move.

The comments now say this. The previous comment — *"Give the second caller several turns to reach the same id"* — read as though the wait were establishing the property under test, which is the misreading that produced the ticket's first version.

## Deltas from ticket

**Two candidate arrival anchors were falsified**, and both are recorded in the ticket body so they are not re-proposed:

1. **The marker `readFile`** — `getGraphMarkerFileStats` uses `fs.stat`, not `readFile`, and `readJsonlEntries` (the only marker path that reads) is skipped on the cache hit that two concurrent unchanged callers produce.
2. **The `readdir` in `listMessageWalSegmentKeys`** — measured: the counter is already at **2 at turn 0**, before the wait begins, while the second caller's read decision lands around turn 2. **The anchor fires two turns early**, so it cannot prove arrival.

There is a structural reason no anchor exists: **when the second caller joins, it produces no side effect.** Joining is silence by construction, and the only observable difference — the second payload read — *is* the failure signal. Once the redundant assertion is gone, nothing needs to observe arrival at all, so the ticket's route (b) (exposing an observable from production) is moot rather than deferred.

**Also checked and cleared:** `projectionStatsCache` is module-scope keyed by `dir`, which looks like cross-file worker state in the exact class #15861 hunts. It is not — `messageWal.dirTest` derives from the active test's `memoryWal.dir`, isolating the key by construction (`configBase.mjs:544-549`).
