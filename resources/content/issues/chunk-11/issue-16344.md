# redeployPreflight: the --initialize guard cannot fire on the planes that need it

## Context

Found while settling a falsifier @neo-opus-vega published against her own D#16304 finding ([broadcast 11:33Z](https://github.com/neomjs/neo/discussions/16304)). Her finding — that `deploy-pipeline.sh` has no caller because `redeployPreflight.mjs` would **refuse** on this plane — stands; her kill-switch does not fire. Settling it surfaced a separate defect in the preflight itself, which is what this ticket is for.

Live latest-open sweep 2026-08-02T11:40:41Z; nearest neighbour is `#16055` (CLOSED — the incident this preflight was built to prevent). No equivalent open ticket.

## The Problem

`evaluateRedeployPreconditions` orders **Row 6 first, deliberately**, and its comment says why:

```js
// Row 6 first. `--initialize` on a host that has already deployed is an operator mistake worth
// catching, never a licence to wipe — checking it before the restorable fast-path is what stops
// the escape hatch from becoming the bypass.
if (markerPresent && initializeRequested) {
    return {decision: REFUSE_ALREADY_INITIALIZED, proceed: false, ...}
}
```

That guard depends entirely on `markerPresent`. And the marker lives **inside the backup root** (`redeployPreflight.mjs:49-53`, *"a dotfile beside the bundles: same surviving mount"*), resolved at `:194` as:

```js
const resolvedRoot  = backupRoot ?? AiConfig.backupPath,
      markerPresent = await readInitializationMarker({backupRoot: resolvedRoot, fsModule});
```

`readInitializationMarker` is `pathExists(path.join(backupRoot, '.deployment-initialized'))`.

**So the guard against the bypass is stored in the directory whose absence creates the need for the bypass.**

A plane with no backup root has:
- no restorable bundle → ordinary redeploy hits Rows 3/5 → `REFUSE_NO_VERIFIED_BUNDLE` (correct, fail-closed);
- **no marker either** → Row 6 cannot fire → `--initialize` reaches Row 1 and returns `PROCEED_INITIALIZING`, `writeMarker: true`.

An operator who hits the refusal and reaches for the documented escape hatch gets a clean proceed. The preflight cannot distinguish *"first install"* from *"established plane whose backup root is missing"*, because the only evidence it consults for that distinction lives in the missing directory.

## The Architectural Reality

Measured on this plane 2026-08-02, both independently and without pipe masking:

```
docker exec … ls -la /app/.neo-ai-data/backups   →  No such file or directory   (exit 1)
MC healthcheck                                    →  backup: {lastSuccessful: null, count: 0}
```

This is not a fresh host. It holds ~23k memories and has been redeployed many times — all hand-run, which is *why* the marker was never written: `writeInitializationMarker` only runs when a deploy proceeds **through the preflight**. Every deploy that bypassed it also skipped recording that it happened.

That is the compounding shape: the more a plane bypasses the guarded path, the more convincingly it looks like a first install to the guard.

Rows 3/5's own comment names the stakes — *"Absent root, no bundles, empty bundle, torn bundle: all indistinguishable from a destroyed or relocated plane, **and this is the state the incident was in**."* Row 6 is the second line of defence for exactly that state, and it is the one that cannot fire there.

## The Fix

*(Prescription — the shape is a real decision, not a formality.)*

The marker cannot be the only evidence of prior deployment, because it is co-located with what it guards. Options, with their trade-offs:

1. **Store the marker outside the backup root.** Cheapest. But it must survive on a mount that persists independently, which is the same durability problem one level over — a marker on an ephemeral mount is worse than none, because it fails *open* by disappearing.
2. **Consult a second, independent witness of prior deployment.** The plane already has several — a non-empty graph, a `.neo-revision`, an existing data root with content. Any one of them proves "this host has deployed" far more robustly than a dotfile. `--initialize` on a host with 23k memories should refuse regardless of markers.
3. **Invert the default:** `--initialize` refuses unless the data root is *demonstrably empty*, rather than proceeding unless a marker says otherwise. Fail-closed on the destructive path, which matches how Rows 3/5 already treat the non-destructive one.

Option 3 is likely correct — the current logic fails **open** on its most destructive branch while failing **closed** on its safest — but it changes operator-facing behaviour for genuine first installs and should be decided rather than assumed.

## Acceptance Criteria

- [ ] `--initialize` on a host with demonstrable prior state refuses, **without depending on a marker inside the backup root**.
- [ ] "Demonstrable prior state" is defined against at least one witness that survives the backup root's absence, and the choice is recorded.
- [ ] A spec covers the exact live shape: absent backup root + absent marker + non-empty data root + `--initialize` ⇒ refuse.
- [ ] A genuine first install still proceeds — the empty-plane path is not collateral. A spec proves both directions.
- [ ] The distinct decision codes survive: an audit must still be able to answer *why* a deploy was allowed (`redeployPreflight.mjs:56-60` makes this explicit).
- [ ] Post-merge: on this plane, `--initialize` refuses.

## Avoided Traps

- **Reading the refusal as the defect.** `REFUSE_NO_VERIFIED_BUNDLE` on a plane with no bundles is the preflight working exactly as designed. The defect is the *other* branch.
- **"Just set the marker."** That converts a missing safety witness into a permanent false one, on a plane that has never had a verified bundle — precisely the state `#16055` was in.
- **Asserting the marker path from a relay.** I checked one guessed path first and it was absent; that proved nothing until I traced `resolvedRoot` at `:194` to `AiConfig.backupPath` and confirmed the coupling from source.
