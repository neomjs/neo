# Retry backoff bases are hardcoded seconds, so every retry spec pays real wall-clock — make them leaves and lint fixed sleeps out of unit specs

## Problem

`VectorService`'s retry backoff is a hardcoded `2 ** retries * 1000` at two sites (the ordinary batch retry arm and the carried-prefix write retry, `ai/services/knowledge-base/VectorService.mjs` ~1128/~1229). Any spec that exercises a retry pays a real 2s/4s per attempt — today's work-conservation falsifier arms alone added ~15-20 seconds of genuine sleep to the unit suite, and the leaseYield spec documented the same friction weeks ago ("a maxRetries-5 mutation run exhausts the 30s test timeout") and worked around it by shrinking `maxRetries` instead of fixing the cause. The unit suite has crossed 16 CI-minutes; the operator has ruled coverage stays in CI (`NEO_TEST_SKIP_CI` is the rejected alternative), so the wall-clock tax must go, not the tests.

## Acceptance Criteria

1. The backoff base becomes an ADR-0019-compliant config leaf (e.g. `kb.retryBackoffBaseMs`-class, default 1000, env-projected per the behavior-binding-clock projection contract from #17115), consumed at both VectorService sites; specs pin it to 1ms.
2. The existing retry/falsifier specs keep their exact assertion coverage and drop their real-sleep cost (the four VectorService invariant spec files' combined wall-clock drops measurably; state before/after).
3. A mechanical lint (same gate family as check-block-alignment / lint-retry-bounds) fails a unit spec containing a bare fixed `setTimeout(resolve, N)` with N >= 1000 that lacks an explicit `wall-clock-under-test:` justification comment — so the class cannot regrow silently.
4. A sweep enumerates any other production retry/backoff constants specs currently pay for real (grep receipts in the PR body), fixing or ticketing each.

- 2026-08-14T18:30:42Z @neo-opus-grace referenced in commit `eafb0d0` - "feat(build): require a fixed second-scale wait to name what it waits for (#17124)

The visible shape is a bare setTimeout in a spec and the visible cost is wall
clock, but the bare sleep is a symptom. In every censused site the spec was
out-waiting a HARDCODED PRODUCTION CONSTANT it had no way to inject - a poll
interval, a lock-hold threshold, a token TTL, a spawn startup delay. A test
cannot pin what the source does not expose, so it guesses a number larger than
the constant and pays it forever.

So the rule is not "no sleeps": a fixed second-scale wait must carry either
`wall-clock-under-test:` or `out-waits: <the constant>`. Naming it is cheap, and
the naming IS the census that finds the next non-injectable constant.

Deleting a sleep is explicitly NOT the sanctioned fix, and the failure text says
so. Measured on the wake daemon spec: readiness is 90ms against sleeps waiting
1000ms, converting a sleep to a readiness poll moved 6.4s to 6.3s, and DELETING
one moved 6.4s to 12.2s with every assertion still green - the wall clock is
quantized by the production poll interval, so removing the wait pushes injection
before the next watermark and costs a whole extra cycle. A guard that nudges
toward the wrong repair converts a visible cost into an invisible one and prints
green.

Three sites earned annotations rather than baseline rows, which is the escape
hatch working: an outbox lock-hold threshold, a token TTL boundary, and
spawnBridge's 2000ms startupDelayMs - the last named by the spec's own comment.
Each names a leaf candidate.

The remaining 83 are baselined PER SITE, not per file: these convert rather than
vanish (a sleep becomes a readiness poll), and a file count would silently
absorb a conversion that left the site present. A stale row fails too, so the
baseline may only shrink.

Controls: a new unjustified sleep fails with the site named; a baseline row
without a live site fails; the intact tree passes at 83 baselined, 0 new,
0 stale. Mirrored in CI so --no-verify cannot bypass it; guard-ci-parity green."
