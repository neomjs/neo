# Demo B: third registered claim target for the row-6 arbitration receipt

## Context

The tear-out portability matrix's row 6 (multi-window targeting / claim-protocol identity binding) is honestly blocked on a **design authority, not a test** — recorded in the living ledger (TearOutPortabilityMatrix.md footnote ⁷, 2026-07-19) after macOS row 4 landed `PASS_NATIVE` (PR #15589). The matrix will not simulate the cell; this ticket owns the production/design prerequisite.

Live latest-open sweep: newest 20 open issues at 2026-07-19T20:35Z; no equivalent. A2A in-flight sweep: no competing claim.

## The Problem

Row 6's required receipt: *with at least three windows, at most one target exposes one menu and one preview for the gesture; identity remains stable* — measured through the merged G3 workspace-set claim protocol (PR #15465). Today's Demo B topology cannot host that receipt honestly:

- Three **physical** windows exist, but only **two registered workspaces** (the main workspace + one registered popup claimant).
- The physical tear-out vessel is not a `DockCrossWindowParticipation` target; counting it as a third claimant would produce a false receipt (Emmy's preserved RED control in the ledger: two registered workspaces vs three physical windows, the vessel's live `windowId` colliding with the workspace target's).

A third page opened merely to be counted is a vacuous witness. The cell needs a third **registered** claim target — real workspace-set composition.

## The Architectural Reality

- The claim protocol itself is merged and unit-proven (PR #15465, G3 arbitration) — the missing piece is a third registered claimant, not the protocol.
- The competing-vessel composition repair belongs to #15396 (explicitly not absorbed by the matrix or this ticket).
- Demo B's workspace-set substrate: `AgentOS.childapps.dockdemo.view.DemoBWorkspace` + `DockWorkspaceSet` (merged in the vessel-conversion arc). The natural question: register a third workspace (a second popup claimant, or a workspace-set expansion) so the arbitration receipt has three real registered targets.
- Until this lands, row 6 stays `NOT_YET_MEASURED` on every platform — the honest hole is the matrix's integrity, not its failure.

## The Fix

1. Design the third registered claim target for Demo B (shape decision: a second registered popup workspace vs a workspace-set composition change), with the same fail-closed registration semantics as the existing two.
2. Land it behind the existing registration path (no new protocol; the matrix's cell must measure the MERGED protocol, not a bespoke host).
3. Hand the cell back to the matrix: row 6 executes against the three registered targets (macOS first, then Windows/Linux per their real-desktop receipts).

## Intake + design decision (author, 2026-07-20)

Lane accepted per the ownership note. Intake verified against `dev`: the registration semantics already generalize — the design blocker was never the registry, it is the demo's single-popup bookkeeping. Shape decision below.

### Verified substrate (why no protocol change is needed)

- `createDockWorkspaceSet()` is a Map keyed by **semantic** workspace id with fail-closed registration (`src/dashboard/DockWorkspaceSet.mjs:150`) — a third entry is a data fact, not a protocol change.
- A workspace becomes a claim target by mounting a `DockCrossWindowParticipation` (one per registered workspace), which registers its `CrossWindowDragTarget` with the `DragCoordinator` under the shared `sortGroup` (`DockCrossWindowParticipation.mjs:144-159`). The G3 arbiter (`manager/GestureClaimArbiter`, PR #15465) admits exactly one candidate per gesture — the protocol row 6 measures, untouched (AC4).
- Demo B's own registries are already keyed by workspace id: `crossWindowHosts`, `crossWindowParticipations`, `crossWindowGeometry` are all `Map<String,…>` — the composition points accept a third id with no shape change.
- The singleton assumption lives in the *staging bookkeeping* (`POPUP_WORKSPACE_ID` static, `crossWindowTargetWindowId`, `ensurePopupWorkspaceRegistered()`), not in the registration seam.

### Shape decision: a second registered popup workspace (`demo-b-popup-2`) — NOT a composition change

1. **Three registered claim targets:** `demo-b-main` + `demo-b-popup` + `demo-b-popup-2`, each with its own committed document, each mounting a participation on `CROSS_WINDOW_SORT_GROUP` when its window stages. A drag from main hovering the two popups gives the arbiter two remote candidates; exactly one exposes menu+preview — the honest row-6 receipt.
2. **The physical tear-out vessel stays a non-claimant** (AC2): it never registers a workspace entry or participation — the RED control (two registered vs three physical, windowId collision) holds by construction.
3. **v1 scope discipline:** the third window is staged by a dedicated demo action ("stage third window") reusing the existing popup mount path — NOT a generalization of the tour/perspective/topology machinery to N windows. Topology perspectives stay main+popup-1 scoped; the matrix cell needs the live arbitration surface, not full multi-popup perspective support. Generalizing to N is a named follow-up if the demo ever wants it.
4. **Registration identity honesty:** `demo-b-popup-2` registers through the SAME `workspaceSet.register(id, {getDocument, setDocument})` seam with its own document instance — a NEW workspace lifetime per staging, mirroring `ensurePopupWorkspaceRegistered()`'s re-registration discipline.

### Execution plan

1. Second popup stage action + `demo-b-popup-2` document + registration (same seams).
2. Participation mount for the third window (same `mountCrossWindowTarget` machinery).
3. Row-6 cell executable on macOS (headed matrix runner): drag from main over both popups → exactly one claim, identity stable.
4. Matrix lane retakes the cell once merged.
