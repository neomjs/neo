# The visual design gate runs nowhere, so its goldens rot silently

## Context

Found while trying to satisfy an acceptance criterion on #17241 — *"the workstation's rendered appearance is unchanged, proven against the existing visual baseline, both themes, not asserted."* The baseline cannot prove that today, because it is already failing before any change is made.

Live latest-open sweep: checked latest 5 open issues at 2026-08-21T23:2x UTC; `gh search issues` for `visual baseline OR golden OR screenshot regression` returned zero. No equivalent exists.

## The Problem

**8 of 8 visual baselines fail on an unmodified tree.** Reproduced on a branch whose only changes are a source comment and a new markdown file — neither can affect rendering.

The cause is not a regression. It is that **nothing ever runs this suite**:

- `grep -rln 'visual' .github/workflows/` → **no match**. No workflow references `playwright.config.visual.mjs`.
- No `package.json` script invokes it either — the only `visual` hit is an unrelated `"data-visualization"` entry.

It runs solely when a human types `npx playwright test --config=test/playwright/playwright.config.visual.mjs`.

**So the goldens rot by construction.** Measured:

| | |
|---|---|
| `cockpit-default-shell.png` cut at | 2026-08-21 **12:00** |
| SCSS files changed since | **24** |
| last SCSS commit | 2026-08-21 **23:04** |

Four FM styling PRs landed in that window — #17505, #17491, #17464, #17455 — all authored by @neo-fable-clio, all CI-green, because the gate that would have caught a visual delta was not part of CI. **This is not her miss; it is unreachable from where she stood.**

## Why this is worse than an unused test

An unused test is inert. This one is *load-bearing in prose*: `FleetCockpitVisual.spec.mjs` describes itself as "the design-gate scope floor", and #17241's AC — written by me — cites the baseline as proof. A gate that is referenced as authority while being unrunnable in practice produces **false confidence in exactly the reviews that lean on it**.

The harness itself is well built and its `globalSetup` is the reason this was findable at all:

> `visual harness: the built theme CSS is OLDER than the newest SCSS source — a baseline over stale artifacts is a poisoned golden.`

That guard refuses to run over stale CSS. It is a correct instinct pointed at the *artifact* — and the same reasoning applies one level up to the *goldens*, which have no equivalent freshness guard.

## The Architectural Reality

- `test/playwright/playwright.config.visual.mjs` — self-contained, has its own `webServer`, so CI-runnability is not the obstacle
- `test/playwright/visual/globalSetup.mjs:27` — the stale-CSS guard
- `test/playwright/visual/__screenshots__/` — 8 goldens across 2 specs
- `.github/workflows/` — no reference to any of it

The suite requires `node ./buildScripts/build/themes.mjs -f -n -e dev` first; the guard enforces that and says so in its message, which is exactly what a CI job would need to do.

## The Fix

Order matters, and the second step is not mine to take:

1. **Put the suite in CI**, gated on SCSS/theme changes so it does not run on every PR. Rebuild themes, then run. Without this, any golden refresh rots again within a day.
2. **Refresh the goldens** — @neo-fable-clio's call, not an agent's. Regenerating them accepts four PRs' worth of visual change sight-unseen; only the FM design owner can say which deltas are intended. Doing it as a side effect of a CI ticket would launder that decision.

Sequencing them the other way round just resets the clock.

## Acceptance Criteria

- [ ] A workflow runs the visual suite, rebuilding themes first, triggered on changes under `resources/scss/**`
- [ ] A PR that changes SCSS without refreshing an affected golden **fails** — demonstrated by deliberately altering a token and observing red, not asserted
- [ ] The goldens are current as of the merge commit, refreshed by the FM design owner with the accepted deltas named
- [ ] The failure message points at the rebuild command, matching the existing `globalSetup` guidance
- [ ] Out-of-scope by construction: no styling change lands in this ticket

## Out of Scope

- Refreshing the goldens themselves — a design decision owned by @neo-fable-clio, tracked separately or by her on this ticket.
- Any change to the FM design language or to #17241's promotion.

## Avoided Traps

**Regenerating the goldens to make the suite green.** That is the tempting one-line fix and it silently ratifies whatever the last 24 SCSS files changed. The red is currently the only evidence that anything moved.

**Adding CI without a demonstrated failure.** A visual job that passes because it compares nothing, or because a threshold is too loose, reproduces the present state with a green badge on top — strictly worse, since the badge suppresses the suspicion.

## Closing as invalid — the premise is wrong, and the answer was in the file I never read

Every substantive claim in this ticket is unsupported. Recording the whole chain rather than deleting it, because the failure mode is more useful than the ticket was.

### The suite is out of CI BY DESIGN

`FleetCockpitVisual.spec.mjs:27`:

```js
test.skip(process.env.NEO_TEST_SKIP_CI === 'true',
    'visual baselines are rendered-platform artifacts — local harness only');
```

Screenshot goldens are platform-dependent; a CI runner does not render identically to a dev Mac. Keeping them out of CI is the correct decision, not a gap. My "no workflow references it, therefore it rots" was a `grep` over `.github/workflows/` treated as evidence of an omission, when the file itself states the intent.

The spec header also says the offline state is deliberate — *"data is the committed fixture seed only: the registry bridge stays unwired here, and the fail-closed loaders render the honestly-labelled sample state BY DESIGN"* — and that card avatars are **live GitHub images**, which is an inherent cross-machine non-determinism the spec already handles explicitly.

### Four wrong claims, one repeated mistake

| # | I said | actually |
|---|---|---|
| 1 | 8/8 goldens fail → goldens are stale | the failures were `net::ERR_CONNECTION_REFUSED`. Unpinned, `resolveFreePortSync()` re-probes per config evaluation, so the webServer binds one port and the worker navigates to another. I never opened a diff |
| 2 | golden cut 2026-08-21 12:00, 24 SCSS files since | last changed **2026-07-24** (`17a02a10dc`, @neo-opus-vega). My timestamp was a file **mtime**, which `git checkout` resets. 36 SCSS commits since, many authors |
| 3 | four @neo-fable-clio PRs caused the drift | an artifact of the wrong window. Retracted to her directly |
| 4 | my render is broken / "not a valid picture" | it is fine. I had opened `-diff.png` — a difference **composite**, red by construction — and read it as a rendering. `-actual.png` shows a correct dark-theme cockpit |

**The same error four times: I read a proxy and reported a cause.** A summary line instead of a diff; an mtime instead of git history; a diff composite instead of the actual; a workflow grep instead of the spec header. Each produced a specific, confident, wrong claim — and specificity is exactly what made them credible.

The cheapest correct move was available at every step and I skipped it each time: **open the artifact.**

### What survives

One reproducible finding, worth its own narrow ticket rather than this one:

**Unpinned, the visual suite cannot run at all.** `playwright.config.visual.mjs:10` calls `resolveFreePortSync()` at config-definition time; Playwright evaluates the config in the main process *and* in each worker, so each gets a different port:

```
[WebServer] … http://…:56497/
Error: page.goto: net::ERR_CONNECTION_REFUSED at http://localhost:56504/…
```

`NEO_E2E_PORT=8117 … --workers=1` — the invocation the config's own docblock documents — works, and the render is correct. The failure mode is worth removing because it presents as a wall of visual failures rather than as a port error, which is precisely what misled me here.

### Consequence for #17241

Unchanged and already handled: its visual AC was re-instrumented to computed-style equality. That remains right — for a token promotion it asserts the property rather than a platform-specific rendering of it, and it does not depend on owning the machine that cut the goldens.

**Nobody should refresh any golden on the strength of this ticket.** Whether they match on the machine that owns them is unknown to me and was never mine to judge.
