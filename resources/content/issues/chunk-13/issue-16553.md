# The ticket-archaeology guard reads an all-numeric hex colour as an issue ref

## Context

Hit while committing `#16538`. Every edit to `src/component/Helix.mjs` failed the pre-commit hook on a line the change never touched:

```
check-ticket-archaeology: 1 decay-prone ref(s) in durable comments:
  src/component/Helix.mjs:29: * @member {String} backgroundColor_='#000000'
```

`#000000` is a hex colour. The guard reads it as an issue reference.

## The Problem

**The guard's own docblock claims the protection it does not provide.** `buildScripts/util/check-ticket-archaeology.mjs:22-24`:

```js
// Decay-prone tracking anchors that must not live in durable source comments. `#\d{4,}\b` targets
// issue/PR numbers (Neo tickets are 5 digits) while a trailing word boundary avoids matching hex colors
// like `#1234ff`; the named forms catch the prose variants.
export const TICKET_PATTERNS = [
    /#\d{4,}\b/,
```

The trailing `\b` does exactly what the comment says — for the example the comment picks. `#1234ff` has letters after the digits, so `\d{4,}` cannot reach a word boundary and the match fails. **An all-numeric colour has no letters to stop it:** `#000000` is six digits, `\d{4,}` consumes all six, `\b` succeeds at the string end, and the guard fires.

So the exclusion holds for `#1234ff` and fails for `#000000`, `#111111`, `#123456`, `#332211`. The prose reads as a general guarantee; it is a guarantee about one example.

**Measured blast radius** — the checker run over every tracked `src/**/*.mjs`, rather than counting pattern matches:

| file | why |
|---|---|
| `src/app/content/Component.mjs` | all-numeric hex in a durable comment |
| `src/collection/Base.mjs` | same |
| `src/component/Gallery.mjs` | same |

Three files cannot be committed without an escape marker, on lines the committing change need not touch. `src/component/Helix.mjs` was the fourth until `#16538` added the marker as a stopgap.

The cost is not the three files. It is that the escape marker is the only route, and it makes a **false statement in the source**: `ticket-ref-ok` asserts a ticket reference is deliberate, when there is no ticket reference. Every use of it here teaches the next reader that a hex colour is a tracking anchor someone chose to keep.

## The Architectural Reality

- `buildScripts/util/check-ticket-archaeology.mjs:26` — the pattern.
- `:20` — `ESCAPE_MARKER = 'ticket-ref-ok'`, matched per-line, so the marker must sit on the offending line. In a JSDoc block that means appending lint prose to an `@member` tag.
- Neo ticket numbers are 5 digits and currently in the 16000s; 6-digit hex colours collide by construction, and 4-digit numeric colours (`#0000`) would too.

## The Fix

Distinguish the two by what precedes the `#`, or by what the digits are attached to. A colour literal in Neo's comments appears as a value — `='#000000'`, `` `#000000` ``, or after a colon — while a ticket ref appears as a bare word in prose. The narrowest change that keeps every true positive:

- require a non-value context before `#` (not immediately preceded by `'`, `"`, `` ` ``, or `=`), **or**
- exclude a match whose digit run is exactly 6 or 3 and is delimited as a literal.

The first is preferable: it keys on the syntax that makes something a value, not on digit-count numerology that a future 6-digit ticket number would break.

**Whatever shape it takes, it must keep firing on a real ref in a quoted string** — `'see #16538'` in a comment is still decay-prone. The fix is about the value position, not about quotes alone.

## Acceptance Criteria

- [ ] `#000000`, `#111111`, `#123456` in a durable comment do **not** trip the guard, proven by a spec that fails against today's pattern.
- [ ] `#16538`, `#1234`, and a ref inside a quoted string in prose still **do** — the true positives are asserted alongside, or a pattern matching nothing passes the first criterion.
- [ ] `#1234ff` still passes, so the existing exclusion is not regressed while widening it.
- [ ] The docblock at `:22-24` describes the actual rule rather than one example of it.
- [ ] The three named `src/` files commit without an escape marker.
- [ ] The stopgap marker at `src/component/Helix.mjs:29` is removed.

## Out of Scope

- The other entries in `TICKET_PATTERNS` (the named prose forms) — no false positive observed, and widening the sweep would risk the true positives this guard exists for.
- Whether `ESCAPE_MARKER` should be block-scoped rather than line-scoped. Real friction — a JSDoc `@member` line is a poor host for lint prose — but a separate concern from the false positive, and fixing this one removes the reason to reach for it here.

## Avoided Traps

- **Excluding anything in quotes.** A real ref in a quoted string is still decay-prone; the discriminator is value position, not quoting.
- **Keying on digit count.** `#000000` is six digits and so is a plausible future ticket number. Numerology that works today by accident of the counter is not a rule.
- **Leaving the marker as the answer.** It unblocks and it lies: `ticket-ref-ok` asserts a deliberate ticket reference where none exists, and it accumulates one false statement per affected file.

## Still live at `dev` — and the known site was papered over rather than fixed

Re-checked while triaging the open queue. Two things changed since filing, neither of them the fix.

**1. The pattern is unchanged.** `buildScripts/util/check-ticket-archaeology.mjs` still carries:

```js
export const TICKET_PATTERNS = [
    /#\d{4,}\b/,
```

with the same docblock claiming the trailing `\b` "avoids matching hex colors like `#1234ff`". It does — for hex containing letters, where `\b` fails between `4` and `f`. It does nothing for an **all-numeric** hex colour: `#000000` matches `\d{4,}` and ends at a true boundary. The defect this ticket describes reproduces exactly as filed.

**2. The reported site now carries an escape marker instead.** `src/component/Helix.mjs:29`, and its sibling `src/component/Gallery.mjs:33`:

```
* @member {String} backgroundColor_='#000000' ticket-ref-ok: hex colour, not an issue ref
```

**That is a misuse of the relief valve, and it is the part worth recording.** `ESCAPE_MARKER` is documented one line above `TICKET_PATTERNS` as an *"inline relief valve for a genuinely load-bearing comment ref (judgment-call escape, not a blanket bypass)"* — it exists to **keep a real ref** that the author judges worth the decay risk. `#000000` is not a ref at all. Using the marker here says "this ref is worth keeping" when the true statement is "the guard is wrong."

Those two readings need to stay distinguishable, because they have opposite consequences. Measured across the tree: **55 files carry `ticket-ref-ok`, and 53 of them use it as designed** — ADR clauses that are the governing authority for the code beneath them, implementing-ticket refs on the script that implements them. Exactly **two** use it to silence a false positive, and both are this bug.

**The cost is that the guard's false-positive rate is now invisible.** The next all-numeric hex colour to enter a durable comment gets a third marker, the fix keeps not happening, and the ticket stays open while the symptom looks handled. That is the shape where a workaround outlives the thing it was standing in for — and the two markers are the only evidence it is happening, which is why they are written down here rather than left in a grep.

Not resolving this. The premise holds, the reproducer is unchanged, and the remedy is still a pattern that distinguishes a six-digit issue number from a six-digit colour — plus removing the two markers once it does, since leaving them would preserve a false claim about why they are there.

## The quoted/value-position family is closed — I nearly re-shipped it today

Picked this up as a self-chosen lane, designed a fix, broadcast a lane-claim describing it, and then found I had already tried it and closed it unmerged three weeks ago. Recording the boundary so the next pickup — quite possibly me again — does not spend a third cycle on it.

**Prior art: PR #16968, CLOSED unmerged 2026-08-11.** @neo-gpt's `CHANGES_REQUESTED` was correct and I accepted it:

> `(?<!['"`=])#\d{4,}\b` treats every immediately quoted/assigned number as a value, regardless of whether it is a colour or an issue reference.

A guard that exempts by *quoting* trades a false positive for a **false negative**. That is the strictly worse trade: a noisy guard annoys, a blind guard certifies that a decay-prone ref is absent while the comment still names one.

**Today's variant does not escape it.** I proposed narrowing the exemption with a CSS-hex-length constraint — exempt only when quoted **and** the digit count is 4, 6, or 8 — reusing the `CSS_HEX_LENGTHS` idea that shipped in `lint-guides` via PR #17747. That is strictly better than the 2026-08-11 shape, and still holed:

```
quoted `#9473`    4 digits -> EXEMPTED (silent false negative)
quoted `#16553`   5 digits -> still fires
quoted `#123456`  6 digits -> EXEMPTED (silent false negative)
```

`#9473` is a live Neo ticket cited in current substrate. And 6-digit refs stop being hypothetical the moment issue numbers cross 99999 — which the repo-split discussion made a near-term concern rather than a distant one.

I checked whether the hole is currently occupied: **0** distinct 4-digit refs appear in `src/**` or `ai/**` comments today. That count is true and it is not a defence — it is one commit from being wrong, and the failure mode is silence.

**Why `lint-guides`' answer does not transfer.** PR #17747 solved the same colour-vs-ticket ambiguity, but its discriminator is a **CSS-property anchor** (`background:`, `--custom-prop:`, `fill:`) inside code context. That works because a CSS declaration is a strong, closed context. This guard reads JSDoc prose, where the only available signal is quoting — which is precisely the signal already rejected. Same ambiguity, different context, and the context is what carried the fix.

### What is left, and the honest scoping

The measured cost today is **2 files**, both carrying a `ticket-ref-ok` marker for a hex colour (`src/component/Helix.mjs:29`, `src/component/Gallery.mjs:33`). Re-measured per-file across every tracked `src/**` + `apps/**`; the other two files this ticket originally named now fail for **genuine** refs (`#12209`, `#11595`, `#11611`) and are not this defect.

So the residual harm is the one this ticket already named precisely: the escape marker *"makes a false statement in the source"* — `ticket-ref-ok` asserts a ticket reference is deliberate when there is no ticket reference.

That points at a fix with **no guard-weakening surface at all**: leave detection maximally strict and give the escape an honest second spelling (e.g. `not-a-ticket-ref: <reason>`), so the two files stop teaching the next reader that a hex colour is a tracking anchor someone chose to keep. Zero false negatives, because nothing is exempted by pattern — a human still declares intent per line.

I am **not** claiming that as this session's lane. The operator rated this ticket ROI 1 during a live incident, I have already spent one PR on it, and two markers is not where the next hour belongs. Leaving it assigned with the boundary now written down, which is worth more than another attempt.

**Retracting the design in my `[lane-claim]` broadcast** — the quoted-value shape named there is the closed family, not a new idea.
