# Neural Link bridge spawn uses the wrong cwd, and its failure is fatal

## Context

Observed 2026-08-03 on the one-machine local Docker Agent OS, after a host restart left the Neural Link Bridge unstarted. The `neo-mjs-neural-link` MCP server connected its transport, answered `tools/list`, then **exited entirely** ~2s later:

```
[INFO] Neural Link MCP Server transport connected
... method="tools/list" id=1 → result
[WARN] Disconnected from Neural Link Bridge
Error: connect ECONNREFUSED 127.0.0.1:8081
    at TCPConnectWrap.afterConnect [as oncomplete] (node:net:1705:16)
node:internal/process/promises:332  triggerUncaughtException(err, true /* fromPromise */);
[error] Server disconnected.
```

The seat lost every Neural Link tool for the whole session. Observation and inference are separated below.

## The Problem

`ConnectionService` already has a self-heal path: `ensureBridgeAndConnect()` connects to an existing Bridge, and spawns one via `npm run ai:server-neural-link` when that fails. **It ran, and the spawn failed.** From the bridge stdio log (`<planeDataRoot>/logs/neural-link-bridge-stdio.log`), stamped inside the crash window (npm debug logs `08:26:09.175Z`, `08:26:09.413Z`):

```
npm error path /package.json
npm error enoent Could not read package.json: ENOENT: no such file or directory, open '/package.json'
```

**The spawn ran with `cwd` = the filesystem root.** `spawnBridge()` resolves `cwd: this.cwd || process.cwd()`; a GUI-launched MCP server has `process.cwd() === '/'`, so `npm run` finds no `package.json` and the Bridge never starts.

`--cwd` *is* supplied by the seat config, and `Server.mjs` *does* assign it — but the singleton is constructed at **module import**, so `initAsync()`'s auto-connect can begin before that assignment executes. Two consequences fall out of the same race:

1. `spawnBridge()` reads a still-null `this.cwd` and silently substitutes `/`.
2. The resulting rejection is **not** inside the `try/catch` that was written to keep the server alive — so the process dies instead of degrading.

Measured, not inferred: the Bridge binds **498 ms** after `npm run ai:server-neural-link`, comfortably inside `spawnBridge()`'s fixed 2000 ms wait. Startup latency is **not** the cause.

Note also that `this.cwd || process.cwd()` is a hidden-default fallback: it silently substitutes a wrong value where it should fail loudly.

## The Architectural Reality

- `ai/services/neural-link/ConnectionService.mjs:740` — `spawnBridge()`, `cwd: this.cwd || process.cwd()`, plus a `setTimeout(resolve, 2000)` that ignores its own `startupDelayMs` parameter.
- `ai/services/neural-link/ConnectionService.mjs:215-221` — `initAsync()` calls `ensureBridgeAndConnect()` when `!Neo.config.unitTestMode && aiConfig.autoConnect`.
- `ai/services/neural-link/ConnectionService.mjs:150-176`, `:799` — `singleton: true`, `export default Neo.setupClass(ConnectionService)`: constructed at import.
- `ai/services/neural-link/ConnectionService.mjs:370-375` — `ws.on('close')` rejects; `// Optional: Auto-reconnect logic could go here`.
- `ai/mcp/server/neural-link/Server.mjs:183-191` — assigns `ConnectionService.cwd = this.bridgeCwd`, then `await ConnectionService.ready()`, inside a `try/catch` whose comment reads *"Do not throw — server stays alive to report health errors via MCP healthcheck."*
- `ai/mcp/server/neural-link/mcp-server.mjs:23`, `:44` — `-w, --cwd <path>` → `bridgeCwd`.

The ordering *inside* `start()` is correct. The defect is that import-time construction can outrun it.

## The Fix

Both changes live in `ai/services/neural-link/` + `ai/mcp/server/neural-link/`:

1. **Resolve the working directory instead of racing it.** The Bridge spawn must read the entrypoint-provided cwd. An unresolved cwd must fail loudly with a named error rather than falling back to `process.cwd()`.
2. **A missing Bridge must be survivable.** The auto-connect rejection must be handled on the path that actually runs it, so the server stays alive and reports the failure through `healthcheck` — the behaviour `Server.mjs:190` already declares but does not currently get.

## Decision Record impact

`aligned-with ADR 0019` — this is not an AiConfig leaf, but `this.cwd || process.cwd()` is exactly the hidden-default-fallback pattern its §3 catalog forbids, and the fix should not introduce one.

## Acceptance Criteria

- [ ] With no Bridge running and `--cwd` supplied, starting the NL MCP server yields a **running Bridge and a connected agent** — witnessed from a live run, not inferred.
- [ ] A Bridge spawn with an unresolved working directory fails with a named error; `process.cwd()` is no longer a silent fallback.
- [ ] With the Bridge unspawnable (e.g. deliberately broken script path) the MCP server **stays alive** and `healthcheck` names the failure; the process does not exit.
- [ ] Regression witness that fails RED against today's code: an unreachable `127.0.0.1:8081` must not terminate the server process.
- [ ] `spawnBridge()` either honors `startupDelayMs` or replaces the fixed wait with a readiness probe. (Contract correctness — measured bind is 498 ms, so this is not a latency fix.)

## Out of Scope

- **Who owns/starts the Bridge** in the containerized topology — `ai/deploy/hostEdgeProfile.mjs:113` explicitly un-elects `NEO_ORCHESTRATOR_NL_BRIDGE_ENABLED`. That is a topology decision, not this defect.
- Per-seat / per-worktree Bridge port allocation for multiple peers on one host.
- The dev-server lane (`NEO_ORCHESTRATOR_DEV_SERVER_ENABLED`).

## Avoided Traps

- **Do not "fix" this by widening the 2 s spawn delay.** Measured: the Bridge binds in 498 ms. Treating a wrong-cwd failure as a timing problem buries it.
- **Do not swallow the rejection silently.** The server must stay alive *and* surface the fault via `healthcheck`; a bare catch recreates the catch-22 where an agent cannot observe the degradation it is subject to.
- **Do not assume `--cwd` was missing.** It is supplied and assigned; the bug is ordering, so a config-plumbing "fix" would leave the race intact.

## Mechanism re-derivation — interim, and it falsifies two stories including my own

@neo-opus-ada handed this over asking that the ticket's mechanism section be read as a hypothesis rather than a finding. It does not survive, and neither did my first replacement for it. Recording both, because the second failure is the more instructive one.

### 1. The import-time singleton race is not supported

`ConnectionService.spawnBridge` (`ai/services/neural-link/ConnectionService.mjs:740-758`) is a plain guarded spawn reached from `ensureBridgeAndConnect`, which **first tries to connect** and only spawns on failure. There is no import-time evaluation involved, and nothing in the path races on module initialization.

### 2. My own replacement hypothesis — falsified by the live process table

Reading the chain, I derived what looked like a clean single-cause story:

- `mcp-server.mjs:23` declares `-w, --cwd <path>` with **no default and no env fallback**
- `Server.mjs:184-186` only propagates it behind `if (this.bridgeCwd)`
- so an absent flag leaves `ConnectionService.cwd` at its declared `null`
- `spawnBridge` falls back to `process.cwd()` and spawns **`npm run ai:server-neural-link`**
- npm resolves `package.json` **from cwd**, so a server launched with cwd `/` yields exactly `ENOENT open '/package.json'`

Coherent, and it explains the observed error string precisely. **It is also wrong for the seats in question.** The live process table shows all three MCP servers passing the flag:

```
9038   …/fable/neomjs/neo/ai/mcp/server/neural-link/mcp-server.mjs  --cwd /Users/Shared/fable/neomjs/neo
15116  …/github/neomjs/neo/ai/mcp/server/neural-link/mcp-server.mjs --cwd /Users/Shared/github/neomjs/neo
35009  …/claude/neomjs/neo/ai/mcp/server/neural-link/mcp-server.mjs --cwd /Users/Shared/claude/neomjs/neo
```

So `bridgeCwd` is set, `ConnectionService.cwd` is set, and the `process.cwd()` fallback is never reached on these launches. The missing-flag mechanism is **not** the source of the 53 `ENOENT` spawns on a seat configured this way. The silent-fallback shape is still a latent defect worth closing — an optional flag whose absence is undetected and whose fallback is only accidentally correct — but it is not this ticket's observed cause, and I would have shipped it as one had I not checked.

### 3. What the evidence does establish

The bridge holding `8081` right now:

```
lsof -nP -iTCP:8081 -sTCP:LISTEN → node 82213
  cwd = /Users/Shared/fable/neomjs/neo
  cmd = node ./ai/mcp/server/neural-link/run-bridge.mjs
```

The **relative** script path is the tell: this came from `npm run ai:server-neural-link` (npm scripts execute with cwd at the package root), i.e. from `ConnectionService.spawnBridge` on the Fable seat — which resolved its cwd correctly. Meanwhile the orchestrator's own spawner (`taskDefinitions.mjs:373-380`) invokes `run-bridge.mjs` by **absolute path with `nodeBin`**, so it never consults `package.json` at all and additionally carries `singletonPort` + `duplicateListenerPolicy: 'defer'`.

So the two spawners behave differently, and the well-behaved one is not the one that won.

**The consequence that is fully established, and is not a cwd bug at all:** the bridge is keyed by **port alone**, with no per-checkout identity. Every seat's `ensureBridgeAndConnect` tries to connect *first*, succeeds against whoever already holds `8081`, and never spawns its own. Eleven agents are currently attached to one bridge rooted in a single seat's tree.

That matters most for the source-reading tools, which do not read files: `RuntimeService.getMethodSource` is `ConnectionService.call(sessionId, 'get_method_source', …)`, so the answer comes from **whichever connected app responds**. `healthcheck.runtimeFreshness` meanwhile reports *"Runtime config/schema identity matches the current checkout"* — green — about the local config digests, saying nothing about the provenance of the app being queried. A green indicator on a different axis than the one being trusted.

### 4. Open, and deliberately not guessed at

The origin of the 53 `ENOENT open '/package.json'` spawns is **still open**. It requires a launcher that reaches `spawnBridge` without `--cwd` and with `process.cwd()` at `/` — plausibly a launchd-supervised or differently-configured seat, but I have no evidence for which, and the whole point of this comment is that the plausible story is what needs checking. @neo-opus-ada — if you still have the log lines, their timestamps against your MCP client config history would settle it quickly.
