# Discussion delta cutoff never engages — `updatedAt` is never persisted, so every run re-pages the entire history

## Context

The discussion sync fails with `Resource limits for this query exceeded` and has re-paged the entire discussion history on every scheduled run. Surfaced from a live local `syncGithubWorkflow`, operator-reported.

> **Body rewritten in place 2026-07-26** per @neo-gpt-emmy's cycle-1 RA-2. It previously prescribed adaptive page-size degradation, which is **withdrawn** — see *Out of Scope*. The prior prescription and the two superseded AC sets are preserved in this ticket's comment history; this body is the live contract.

## The Problem

**The delta cutoff has never engaged.** It is computed from `updatedAt` on cached entries:

```js
const cachedDiscDates = Object.values(metadata.discussions || {})
    .map(d => Date.parse(d.updatedAt)).filter(t => !isNaN(t));
const sinceCutoff = (metadata.lastSync == null || cachedDiscDates.length === 0) ? 0 : …
```

That field was never written. `Date.parse(undefined)` → `NaN` → filtered out → the date list is empty → **`sinceCutoff` is always `0`** → the `UPDATED_AT`-descending early break can never fire. So every run re-pages all ~210 discussions and pays full GraphQL cost for a corpus that has not changed.

Measured in live `resources/content/.sync-metadata.json`:

| facet | entries | carrying `updatedAt` |
|---|---|---|
| **discussions** | 210 | **0** |
| issues | 10,380 | **10,380** |

The issue syncer has always persisted it. This is the discussion side catching up.

**The cost, measured rather than asserted.** `rateLimit(dryRun:true)` on the real query: **15 points per 30 discussions**, so a 210-discussion traversal is **~105 points, hourly, indefinitely**, against a 5,000/hour ceiling that the corpus exists to protect. The per-query cost ceiling is the *symptom*; this is why it is reached at all.

## The Architectural Reality

### Three row producers, not one

The field has to be emitted by every writer of a cache row, and there are three:

| producer | site | role |
|---|---|---|
| bulk repopulation | `DiscussionSyncer:569` | writes the row for every fetched discussion |
| **force-refetch recovery** | **`DiscussionSyncer:675`** | **OVERWRITES the row — omitting the field strips it from every discussion it repairs** |
| persistence prune | `MetadataManager:170` | decides what survives a save/load round trip |

The recovery one is the dangerous omission: a repair pass that lowers the cutoff, and zeroes it once enough rows lose the field, **reintroduces the exact defect it recovered from.**

### The matched pair — persisting the field alone is WORSE than the bug

The bulk repopulation also did `metadata.discussions = {}` and rebuilt only from what the run fetched. That is harmless **only because** the zero cutoff makes the fetch the whole corpus.

Make the delta work without converting that replace to a merge, and every entry it skips loses its `path` and `contentHash`, misses the unchanged-content shortcut, and is **rewritten on every subsequent run** — a permanently non-empty diff in a tracked generated corpus, which would look like a successful fix. **The two changes are one change.**

### A job the wipe was doing silently

Denylist containment relied on the wholesale reset to drop a quarantined discussion's metadata row. So the wipe served two unrelated purposes and only one was documented. Containment must clear file, index entry and metadata row **explicitly**, independently of how the cache is rebuilt.

## The Fix

1. All **three** producers emit `updatedAt`.
2. `metadata.discussions` is **merged**, never replaced — required in the same change as (1).
3. Denylist containment removes the metadata row explicitly.
4. **Page size unchanged.** With the delta engaged a normal run fetches a handful of discussions.

## Acceptance Criteria

**Delivered — each with a mutation-discriminating witness:**

- [x] A persisted discussion entry carries `updatedAt`, asserted against the written file. RED when the prune omits it.
- [x] `updatedAt` survives the **force-refetch overwrite**, and the LIVE value replaces a stale cached one. RED when the recovery writer omits it.
- [x] All three producers emit the field.
- [x] A delta run does **not** shrink `metadata.discussions` — untouched entries keep `path` and `contentHash`. RED when the wholesale wipe is restored.
- [x] Denylist containment still clears file, index entry **and** metadata row.

**Live-only residuals — `L3`, unobtainable from any unmerged head:**

- [ ] `sinceCutoff` is non-zero on a real run and the paging loop breaks early. Needs a populated post-merge cache; a fixture can only prove the field is readable, not that the live corpus yields a usable high-water mark.
- [ ] Two consecutive syncs over an unchanged corpus produce **no** generated-content diff — the churn witness. Needs two real runs.
- [ ] Point cost of a **delta** run measured via `rateLimit` and recorded beside the ~105-point full-traversal figure.

**Evidence: achieved `L1`; required for closure `L3`.** The code path is proven; the corpus behaviour is not, and this ticket does not close until it is.

## Out of Scope

- **Adaptive page-size degradation — WITHDRAWN.** It was priced against the hourly rate limit, which is not the binding constraint (~105 points against 5,000/hour). The binding limit was the per-query cost ceiling, and the delta fix removes the reason it is reached.
- **Comment/reply pagination to completeness → `#16016`.** No code path fetches past 50 comments / 20 replies, so a long thread's 51st comment has never been in the corpus and the recovery path re-truncates it. That is **data loss**, a different failure mode from fetch cost, and it was mis-filed here.
- **`#16002` / `#16010`** — facet isolation and within-facet resume.
- **Ruleset / credential work** — `#15972`, `#16007`.

## Avoided Traps

- **Treating the page size as the defect.** It is the surface the failure appears on. A smaller page would have made the symptom intermittent and left ~210 discussions re-fetched hourly forever.
- **Persisting `updatedAt` without the merge.** Trades a loud failure for permanent silent churn in a tracked generated corpus — strictly worse, and it would look like a fix.
- **Stopping at the producers you found.** I wrote "two omission sites" twice; there are three. The inventory above exists so the next person reads the set rather than re-deriving it.
- **Assuming the recovery path recovers.** It overwrites the row, so omitting the field there undoes the fix after a repair.
- **Reading a green unit suite as a green corpus.** The three residuals above are live-only by construction.

## Fix shape withdrawn and replaced. The real defect is that comments and replies never paginate at all — and completeness is measurably affordable.

Operator correction, in his words: *"we MUST GET ALL COMMENTS … FETCH LESS ITEMS PER HOUR / TIMEFRAME. NEVER EVER EVER EVER drop content."* He is right about the requirement, and following it exposed something worse than the cost ceiling this ticket was filed for.

### First, what my original proposal got wrong and right

**Right:** halving `discussions(first:)` and retrying the same cursor drops nothing — the same discussions arrive across more pages. The outer axis paginates correctly (`DiscussionSyncer.mjs:401/416/439`).

**Wrong:** I proposed a degradation strategy without ever pricing it, and I described it in language ("halve … and retry") that reads as reduced coverage. The fix shape in the body above is withdrawn.

### The budget premise, measured rather than assumed

GraphQL bills **points**, not requests, so page size and spend are not proportional. Same query, `rateLimit(dryRun:true)`:

| `discussions(first:)` | cost | pages for 30 | total points |
|---|---|---|---|
| 30 | **15** | 1 | **15** |
| 15 | **8** | 2 | **16** |
| 10 | **5** | 3 | **15** |

**Total cost is flat** — ~15 points per 30 discussions however it is paginated. At roughly 165 discussions in the corpus that is **~80 points for a complete pass, against 5,000/hour** (live: `4473/5000` remaining). **≈1.6% of the hourly budget.**

So the hourly rate limit is **not** the binding constraint on this facet. The binding constraint is the **per-query cost ceiling** — a single query being too large — which is a different limit and is exactly what the `Resource limits` error reports. Recording this because a fix designed against the wrong limit will trade away completeness it never needed to.

### The real content drop: the inner connections have no cursor anywhere

**Comments and replies are fetched once, capped, and truncated.** Evidence:

- **All five** exported queries in `discussionQueries.mjs` — `GET_REPO_AND_DISCUSSION_CATEGORIES`, `GET_DISCUSSION_ID`, `GET_DISCUSSION_CONVERSATION`, `FETCH_DISCUSSIONS_FOR_SYNC`, `FETCH_SINGLE_DISCUSSION_FOR_SYNC` — contain **zero** comment-level or reply-level cursors. Grep for `commentCursor|commentsAfter|after: $comment|replyCursor|$after`: **no hits.**
- `DiscussionSyncer.mjs` has exactly **one** `while (hasNextPage)` loop, at `:416`, over `discussions`. The comment/reply `hasNextPage` reads at `:281`, `:285`, `:290`, `:292` are used **only** to compute a `complete` boolean and the `conversationCommentCountObserved` / `…Total` metadata — **they never drive a fetch.**
- The recovery path passes the **same caps**: `:609-610` → `maxComments: 50, maxReplies: 20`, identical to `:422-423`. So a force-refetch of a truncated discussion re-truncates it.

**Net: a discussion with more than 50 comments has never had its 51st comment in the corpus, and no code path can retrieve it.** The syncer records that this happened (`complete: false`) and moves on. That is the "never drop content" violation, and it predates the cost ceiling entirely.

Same shape for replies beyond 20 per comment.

### Revised Fix

1. **Paginate comments and replies to completion.** Add cursors to the sync queries and drive them from the `hasNextPage` values already being read for the completeness flag. The flag stops being a record of loss and becomes an invariant: `complete: false` should be unreachable at the end of a successful sync.
2. **Keep the per-query size under the cost ceiling** by pagination, not by dropping — measured headroom above means completeness costs ~1.6% of the hourly budget, so there is no trade to make.
3. **Spread across time if a full pass ever does approach the budget**, with a persisted cursor so a run resumes where the last one stopped. Fewer items *per run*, never fewer items *in total* — this is the operator's "less per timeframe", and it is a scheduling property rather than a coverage one.
4. **Never a bare retry.** The same query at the same size fails deterministically.

- [ ] **No discussion in the corpus ends with `complete: false`** after a successful full sync. This is the completeness invariant and it is the whole ticket.
- [ ] Unit witness on a discussion whose `comments.totalCount` **exceeds** the per-page value: every comment is present in the rendered Markdown, and the reply chains under them are complete. RED before the change.
- [ ] Same witness for `replies.totalCount` exceeding the per-reply page size.

- [ ] If a resumable cursor is introduced, a run interrupted mid-pass resumes without re-fetching completed pages **and without skipping any** — assert both directions.

### Corrected Avoided Traps

- **Designing against the hourly rate limit when the failure is a per-query ceiling.** Measured: they are different limits, and only one of them is being hit. Optimising the wrong one is how a completeness regression gets justified.
- **Reading `complete: false` as a health signal.** It is a record that content was already lost. Treating it as acceptable telemetry is what let a truncating sync look like a working one.
- **Assuming the recovery path recovers.** It passes the identical caps (`:609-610`), so it re-truncates. Verified, not assumed.
- **My own first shape** — a degradation strategy proposed with no cost measurement, in language that read as reduced coverage. Priced afterwards, it turned out completeness was never the expensive option.

## Root cause found, and it is not the page size: the delta cutoff has never engaged, so every run pages the ENTIRE discussion history

My earlier comment replaced the fix with comment/reply pagination. That still stands as a completeness requirement, but it is not why the query is too big. **The query is too big because the sync re-fetches all ~210 discussions on every single run**, and it has done so since the field its delta depends on was never persisted.

### Measured, not inferred

`resources/content/.sync-metadata.json`, live:

| facet | entries | carrying `updatedAt` |
|---|---|---|
| **discussions** | 210 | **0** |
| issues | 10,380 | **10,380** |

The issue syncer persists `updatedAt` and its delta works. The discussion syncer does not, and its own cutoff logic reads exactly that field:

```js
const cachedDiscDates = Object.values(metadata.discussions || {})
    .map(d => Date.parse(d.updatedAt)).filter(t => !isNaN(t));
const sinceCutoff = (metadata.lastSync == null || cachedDiscDates.length === 0) ? 0 : …
```

`Date.parse(undefined)` → `NaN` → filtered out → `cachedDiscDates.length === 0` → **`sinceCutoff` is always `0`** → the `updatedAt`-descending early-break never fires → full traversal, every run. The cost ceiling is the *consequence*, not the cause.

### Two omission sites, and the prune is only one of them

- **`DiscussionSyncer` `:541-547`** builds the cache entry as `{number, closed, closedAt, contentHash, path}` — `updatedAt` never enters the object.
- **`MetadataManager.save`** prunes discussions to the same five fields, so it could not persist what it was never given.

Fixing only the prune changes nothing. Both need the field.

### The matched-pair hazard — fixing the delta ALONE makes things worse

`DiscussionSyncer:537` does `metadata.discussions = {}` and repopulates **only from `allDiscussions`**, the subset fetched this run. Today that is harmless *because* the cutoff is 0 and the subset is everything.

The moment the delta engages, `allDiscussions` becomes a small recent subset — and that wipe would discard the `path` / `contentHash` of every untouched discussion. They would then be re-rendered and rewritten on every subsequent run: not data loss, but permanent churn in a generated corpus, and a diff that is never empty.

**So the wipe must be converted to a merge in the same change.** Same shape as the accumulator fix in `SyncService` (#16010): merge into the cache rather than replacing it, so a syncer that touches a subset cannot drop the rest.

### Revised Fix

1. **`DiscussionSyncer` writes `updatedAt: d.updatedAt`** into the cache entry, and **`MetadataManager.save` persists it** — symmetric with the issue prune that already does.
2. **`metadata.discussions` is MERGED, not replaced** (`:537`). Required in the same commit as (1), never after.
3. **Comment/reply pagination to completeness** — the previous comment's requirement, unchanged: no discussion may end a successful sync with `complete: false`.
4. **Page size stays as it is** unless a single *delta* batch is ever measured over the ceiling. With the delta engaged a normal run fetches a handful of discussions, so lowering the constant would be optimising a path that no longer runs. That is why the adaptive-degradation shape I originally proposed is withdrawn rather than merely deprioritised.

### Acceptance Criteria (superseding the previous set)

- [ ] A persisted discussion entry carries `updatedAt`; assert against the written file, not the in-memory object.
- [ ] With a populated cache, `sinceCutoff` is **non-zero** and the paging loop breaks early. RED today, because it cannot be non-zero.
- [ ] **A run that fetches a subset does not shrink `metadata.discussions`** — entry count is non-decreasing across a delta run, and an untouched entry keeps its `path` and `contentHash` byte-identical. This is the matched-pair guard and it must fail if (2) is reverted while (1) stands.
- [ ] Second consecutive run over an unchanged corpus produces **no** generated-content diff — the churn witness.
- [ ] No discussion ends a successful sync with `complete: false`.
- [ ] Point cost of a delta run is measured via `rateLimit` and recorded next to the full-traversal figure, so the reduction is a number rather than a claim.

### Corrected Avoided Traps

- **Treating the page size as the defect.** It is the surface the failure appears on. A smaller page would have made the symptom intermittent and left ~210 discussions being re-fetched hourly forever.
- **Persisting `updatedAt` without converting the wipe to a merge.** That trades a loud failure for permanent silent churn in a tracked generated corpus — strictly worse, and it would look like a successful fix.
- **My own first two shapes**: adaptive page-size degradation (priced against the wrong limit), then comment pagination alone (necessary, but not why the query is oversized). Both are now recorded above rather than quietly dropped.
