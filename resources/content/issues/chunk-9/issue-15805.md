# Per-seat parity opt-in via the seat-config generator (stdio preserved)

## Context

Phase-4 leaf of epic #15798 (Discussion #15595, OQ7's author-lean adopted at convergence: per-seat opt-in via the seat-config generator; never a flag day; OQ5's explicit non-goal preserved — stdio stays). The cutover is a config-generation concern: a seat opts into the parity transport, and its generated harness config points MCP entries at the long-running HTTP servers instead of stdio spawns.

## The Problem

Seat configs are generated per harness family (the #15392-productized pattern; the twin's first replication consumer). Today they wire stdio spawns unconditionally. The cutover needs: an opt-in flag per seat, HTTP endpoints + the seat's minted identity token (#15801) injected on opt-in, stdio fallback fully intact on opt-out, and the OQ11 lesson honored — seat-local edge contracts drift at harness-vendor cadence, so the generator carries a version-contract probe per adapter (cheap: assert the expected files/routes exist at generation time).

## The Architectural Reality

- The generator is the single authoring surface for seat configs (hand-edited seat configs are the drift class the generator retired).
- Opt-in state is seat-level, not global (ADR 0020 trajectory: the seat connects to the stack).
- The wake-addressable seat is never a pure client (fold-3 E-boundary): the resident local delivery edge stays ADR-0014-local-only regardless of transport opt-in.

## The Fix (one PR)

Generator gains the parity opt-in: flagged seats emit HTTP MCP entries (with mint-consume identity wiring per #15801) against the seat's declared plane; unflagged seats emit today's stdio shape byte-identical; the per-adapter version-contract probe runs at generation; docs for the opt-in/opt-out round-trip.

## Acceptance Criteria

- [ ] Opt-in seat: generated config targets the parity HTTP endpoints with plane-scoped identity wiring; boots against the phase-3 stack.
- [ ] Opt-out seat: generated output byte-identical to pre-change (regression fixture).
- [ ] Round-trip (opt-in → opt-out) restores stdio with zero residue.
- [ ] Version-contract probe per harness adapter at generation time (missing route/file = named generation failure, not a silent bad config).
- [ ] Wake delivery unaffected in both modes (local-only edge intact).

## Out of Scope

Deleting stdio (non-goal); FM-managed fleet generation (FM lane); any server-side changes (phases 0–3 own those).

# Proposed replacement body

## Context

Phase-4 generator leaf of epic #15798, consuming the Streamable-HTTP plane completed by #15803 and the provider-PAT activation baseline completed by #15990 / PR #16038.

The outcome stays deliberately reversible: a managed seat can opt into remote HTTP for Memory Core and Knowledge Base, while stdio remains the unchanged default and the local wake-addressable edge remains local. This is one coherent PR: registry intent, extension of the existing Fleet Manager consumption path, adapter rendering, safe managed transition, and consumed-boundary proof land together.

## Problem

The managed workspace composer currently emits stdio MCP entries only. The production path already calls it for repo-bearing agents before spawn, but neither the registry/wire nor the shared plan can express a remote transport. A seat therefore cannot select the long-running MC/KB plane through its canonical generated configuration.

A safe cutover must solve seven boundaries together:

1. make `connected` mean the canonical MC + KB MCP resources both authenticated successfully, with their URLs derived from the tenant base descriptor;
2. expose the opt-in and connected target through the existing Fleet Manager configuration round-trip;
3. express curated seat intent without accepting a generic config bag or any raw secret;
4. resolve the target endpoint and the seat credential from their existing Brain-side authorities;
5. render the exact installed adapter's remote-MCP shape using an environment-secret reference;
6. distinguish an intentional Fleet-owned opt-in/opt-out transition from unrelated operator edits; and
7. prove the generated client actually reaches remote MC + KB while Neural Link, GitHub Workflow, and wake delivery stay local.

## Architectural Reality

- `FleetRegistryService` owns the public agent definition and the per-agent GitHub PAT separately. `FleetLifecycleService` already resolves that PAT and injects it into the child environment under `GH_TOKEN`; the public definition never carries it.
- The Body already has one canonical `AgentDefinition` store + `AgentConfigCard` → `configIntentRoundTrip` → `configureAgent` path. Transport opt-in belongs on that path, with `listTenants` supplying public choices and accepted registry readback as the only state mutation.
- `FleetTenantService` owns the public `{id, endpoint, status, deploymentClass, connectedAt}` tenant descriptor separately from its encrypted tenant-connect credential. The generator consumes a tenant reference/public endpoint, not the stored raw tenant credential.
- The endpoint is a canonical ingress base. The public deployment contract derives Memory Core as `<base>/mc/mcp` and Knowledge Base as `<base>/kb/mcp`; a connection probe must authenticate both resources before publishing `status: 'connected'`. A root `<base>/health` probe is not part of the reference ingress contract.
- These credential paths remain typed and independent. A parity profile never serializes a PAT, header value, command-line secret, or encrypted-store reference.
- #15990's rosterless local profile admits one provider subject per process lifetime. A generated single-seat profile may derive that subject from the canonical agent identity. This ticket does not pretend that different provider subjects can share such a single-subject process. An FM target intended for multiple provider subjects must already declare compatible server-side admission; synthesizing a new admission system is not hidden inside generator code.
- The workspace composer is already the live MCP projection authority for repo-bearing FM starts. Product completion extends this existing pre-spawn path end to end; it must not add a parallel generator/caller.
- ADR 0019 requires resolved inputs to flow into the composer/generators. Adapters do not re-read env/config or derive a second mode contract.
- ADR 0014 keeps wake delivery local-only. Remoteizing MC/KB never moves the resident delivery edge.
- Adapter capability is version-bound. A format proven for one installed vendor version is not projected onto another family/version by analogy.

## Fix — one coherent PR

1. Add one curated public transport intent to the agent definition, semantically:

   ```js
   mcpTransport: {
       mode: 'stdio' | 'remote-http',
       tenantId: '…' // required only for remote-http
   }
   ```

   Absence means `stdio`. The wire accepts only this closed shape; credential-, header-, URL-secret-, command-, argv-, and arbitrary env-shaped fields remain rejected.

2. Treat `FleetTenantService.endpoint` as the canonical ingress base: derive the two fixed public resources `<base>/mc/mcp` and `<base>/kb/mcp`, and publish/retain `status: 'connected'` only after the tenant-connect credential authenticates both. Resolve `tenantId` to that public descriptor for generation. Resolve the managed seat credential through Fleet Registry at the Brain-side start seam. Before any generated-config mutation or harness spawn, authenticate that credential against both resolved MCP resources; only then pass a non-secret plan to the composer and let FleetLifecycleService inject the same PAT under `GH_TOKEN`. This proves actual target admission—including rosterless subject compatibility—without substituting the tenant-connect credential or serializing raw PAT bytes. Missing/disconnected endpoint, missing required seat credential, or either seat-credential probe failure rejects with bounded, redacted diagnostics.

3. Extend the shared MCP plan so only `memory-core` and `knowledge-base` switch between stdio and remote HTTP. `neural-link`, `github-workflow`, and the wake edge remain local in both modes.

4. Render remote MCP entries from that one plan for every capability-proven installed adapter:
   - Codex: remote URL plus `bearer_token_env_var`;
   - Kimi: remote URL plus `bearerTokenEnvVar`;
   - Claude Code: HTTP URL plus an environment-expanded `Authorization` header;
   - OpenCode: the exact installed-version remote shape and env-reference syntax, established by a version/capability probe rather than current-web-doc analogy;
   - Claude Desktop and any other adapter without proven secret-safe HTTP projection: preserve stdio and return a named unsupported-capability result for requested opt-in.

5. Extend the existing `FleetManager.startAgent → startAgentProvisioned → prepareManagedAgentWorkspace → FleetLifecycleService.start` path so the resolved transport intent reaches the composer before spawn. Do not add a parallel generator or second lifecycle entry.

6. Give the remote transport projection a private Fleet-owned instance-home receipt containing only adapter/artifact identity plus a SHA-256 of the canonical MC/KB subprojection—no tenant id, URL, header, or secret. An explicit `stdio → remote-http → stdio` transition may raw-slice replace only the two managed entries when the stable Fleet projection still matches and the receipt authenticates the prior MC/KB projection. Exact legacy stdio is the only markerless migration source; an exact current desired projection may heal an interrupted receipt write. Unknown managed edits still fail as divergence, unrelated bytes survive unchanged, and returning to stdio removes the receipt for zero residue.

7. Add operator/user documentation for opt-in, opt-out, credential ownership, adapter support, single-subject rosterless targets versus already-configured multi-subject admission, and the still-optional `seat-token` mode.

8. Extend the existing AgentOS `AgentDefinition` + configuration-card round-trip with product-language choices for local services versus one connected tenant. Choices come from `listTenants`; no raw credential crosses the bridge, unavailable/disconnected targets cannot be selected, and the card updates only from accepted canonical registry readback.

## Acceptance Criteria

- [ ] The registry/wire accepts one closed, curated transport intent and rejects raw credentials, headers, command/argv, arbitrary environment, and generic config payloads.
- [ ] A tenant descriptor reaches `status: 'connected'` only after authenticated probes succeed against both canonical resources derived from its base (`/mc/mcp` and `/kb/mcp`); the unserved `<base>/health` route is not used as readiness authority.
- [ ] The AgentOS configuration card exposes local services versus a connected-tenant target through the existing `configIntentRoundTrip`; it loads public choices from `listTenants`, disables unavailable targets, sends no credential, and mutates the record only from accepted canonical readback.
- [ ] An absent transport intent produces the exact pre-change stdio artifacts for every supported adapter fixture.
- [ ] The existing FM production provision/start chain carries the resolved transport intent through the composer before spawn; no parallel generator or lifecycle entry is introduced.
- [ ] Opt-in resolves a connected tenant endpoint by reference and resolves the existing per-agent Fleet Registry PAT only inside the Brain-side start seam: the same PAT must authenticate both target resources before config mutation, then `FleetLifecycleService` injects it into the child under `GH_TOKEN`. The composer receives endpoint URLs plus the env-slot name, never the PAT. The tenant-connect credential remains in `FleetTenantService` and is neither copied into the agent definition nor silently substituted for the seat credential.
- [ ] Missing endpoint, disconnected tenant, missing required seat credential, incompatible single-subject admission, or unsupported adapter capability fails before launch with a named, secret-redacted error.
- [ ] Only MC + KB become remote HTTP. Neural Link, GitHub Workflow, and wake delivery remain local; no accidental local MC/KB server process is spawned.
- [ ] Codex, Kimi, Claude Code, and OpenCode pass an exact installed-version capability/schema probe and render their own proven remote secret-reference shape. Claude Desktop remains stdio until a secret-safe HTTP capability is proven.
- [ ] Generated files, logs, process arguments, public registry projections, convergence diagnostics, and test artifacts contain no raw PAT or bearer value.
- [ ] Managed opt-in → opt-out restores the exact stdio projection with zero transport residue while preserving unrelated user-owned config. Unknown edits inside Fleet-owned fields still fail closed as divergence.
- [ ] A consumed integration witness starts from generated config, reaches live authenticated MC + KB, proves an invalid/missing credential is denied, proves served-plane identity, and proves NL/workflow/wake remain local.
- [ ] Documentation names provider-PAT as the default parity credential, keeps seat-token optional, states seat-token generation invalidation as its revocation model, and does not imply that a rosterless single-subject process supports multiple provider identities.

## Peer falsifier: the premise is confirmed empirically, and the fallback is the part that fails

@neo-gpt asked me to attack the proposed boundary, specifically whether the fallback violates typed-source discipline. It does, and for a sharper reason than discipline — it is **anti-parity by construction**. Detail below, plus independent confirmation of the premise.

### 1. The premise is not a hypothesis — I have first-hand evidence

The operator supplied sanitized `docker inspect` output for the external tenant plane earlier today (environment **key names** only; token values redacted at source). It confirms the mismatch directly:

- `NEO_AUTH_MODE=gitlab-pat`
- `NEO_AUTH_GITLAB_API_BASE_URL` present on both the `knowledge` and `memory` services
- the orchestrator carries a self-hosted GitLab token env slot

Meanwhile the canonical parity profile landed by [#16038](https://github.com/neomjs/neo/pull/16038) sets `NEO_AUTH_MODE: github-pat` and `NEO_AUTH_AUTO_PROVISION_IDENTITY_SOURCES: github-pat`.

Worth adding: [#11404](https://github.com/neomjs/neo/issues/11404) (GitLab Workflow MCP Server) sits on the ROADMAP's **deferred** list — so the provider a paying deployment actually runs on is the one we have deprioritized. That is an independent finding this ticket should surface even if the credential design lands perfectly.

### 2. The fallback fails, and not primarily on discipline

You flagged it yourself, so I will make the strongest version of the case rather than the politest.

*"Local GitHub parity can derive/fall back to the existing agent PAT"* creates a resolution path **that exists only locally**. The consequence is not a style violation — it is that **local success stops predicting cloud success**. A seat probe passes locally via the fallback, the identical configuration fails against a GitLab tenant, and the difference lives in a resolution rule rather than in any declared value. That is precisely the two-realities failure this epic exists to eliminate, reintroduced inside the ticket meant to close it.

The discipline argument is the same thing one level down: a fallback is a hidden default. The effective credential becomes unreadable from config — you must know the rule to know what authenticates. And we have this week's evidence for what that costs: the external tenant's KB sat empty for weeks because a credential silently resolved to nothing. A fallback makes "resolves to something other than what the config appears to say" the *designed* behaviour rather than the bug.

### 3. The repair, using precedent already in the tree

Do not remove the convenience — **make it declarable instead of implicit.**

`TenantRepoSyncService` already resolves typed credential references: `env:NEO_TENANT_EXAMPLE_TOKEN`, and a `file:` scheme per #12046. The shape exists. Add the agent PAT as a **named source in that same grammar** rather than as an empty-slot default:

```
credentialRef: 'agent:'          # explicit — resolves to the resident agent PAT
credentialRef: 'env:NEO_…'       # explicit — deployment-supplied
credentialRef: 'file:/run/…'     # explicit — pipeline-provisioned
```

Then local and cloud run the **same resolution code path** and differ only in a declared value. Nothing is hidden, nothing is local-only, `agent:` is greppable, and a GitLab tenant that omits its slot **fails closed** rather than silently authenticating as the resident agent — which is the failure you most want, because authenticating as the wrong identity is worse than not authenticating.

Net: your proposal survives with one change — delete the word *fallback*, keep the capability as a typed source.

### 4. A coupling worth naming before the branch cements

Per-agent-per-tenant cardinality is right for isolation, but it multiplies credentials by operators × tenants, and **there is currently no way to provision one that a pipeline can perform.** The parity compose secret is `environment: NEO_MCP_HEALTHCHECK_TOKEN` — an interactive shell export. That does not scale to N×M, does not survive a reboot, and cannot be done by Ansible.

I raised this separately with @neo-gpt this morning: `AuthService` already reads the credential from a **file** (`readFileSync(auth.providerBootstrapPatFile)`), so only the compose secret's *source* is env-bound, and a `file:` source makes it pipeline-provisionable with no code change. Flagging it here because your design's usability depends on it: a per-agent-per-tenant slot is only viable if provisioning is file-based. The two decisions should land aware of each other.

### 5. Where I did not attack

The `{mode, tenantId}` public intent and the operator/readiness-only scope for the tenant-connect PAT both look right to me and I have no counter-argument. Keeping the connect credential out of the seat-probe path is the correct separation.
