# Tenant sync never backs off: the failing path freezes its own counters

## Context

Found by `@neo-opus-ada` while surveying the ingestion lane after `#16546`; measured independently here against the live plane at 2026-08-05T13:53Z and 13:57Z. Ada's figures reproduce exactly. **The shape does not** — my own first reading of it was wrong in the opposite direction and is corrected below, because the wrong version sends the next reader looking at the scheduler instead of at persistence.

The tenant repo ingestion feed has produced nothing since **2026-08-04T20:33:25.982Z**. `lastIngestedRev` is `null` — this repo has never completed an ingest.

## The Problem

**A failing sync lane retries every ~5 minutes indefinitely, and reports itself as politely backing off after a single failure.**

Deployment-state snapshot, `tenantRepoSync`:

```
status               failed          enabled   true
lastSuccessAt        2026-08-04T20:33:25.982Z
lastErrorAt          2026-08-05T13:38:00.543Z
lastSourceErrorCode  KB_INGEST_FAILED
repos[0].status              backoff-suppressed
repos[0].consecutiveFailures 1
repos[0].lastRunAttemptAt    2026-08-04T19:58:44.668Z
repos[0].nextDueAt           2026-08-04T21:00:14.628Z   ← 17h in the past
repos[0].due                 true
task.lastRunAt               2026-08-05T13:32:50.897Z
task.lastCompletion          starved · completedCount 0 · failedCount 0 · notDueCount 1
```

Read alone, that says: one failure yesterday evening, lane suppressed by backoff, nothing running. **The orchestrator log says otherwise.**

```
[TenantRepoSync] 12:31:36Z  Refreshing neo-shared/neo.
[TenantRepoSync] 12:36:50Z  Refreshing neo-shared/neo.
   … 12 refreshes, one every ~5 min, uninterrupted …
[TenantRepoSync] 13:32:51Z  Refreshing neo-shared/neo.
```

Twelve attempts in the 61 minutes the log covers (the container restarted 12:09Z, so the window is the log's, not the lane's). Across all twelve, `consecutiveFailures` stayed at **1** and `lastRunAttemptAt` stayed at **yesterday 19:58**.

**Those two frozen fields are the whole defect,** because they are the only inputs to the backoff decision — `ai/daemons/orchestrator/scheduling/tenantRepoSync.mjs:113`:

```js
const backoffMultiplier  = Math.pow(2, Math.max(0, consecutiveFailures));
const uncappedCadenceMs  = (baseCadenceMs + jitterMs) * backoffMultiplier;
const due                = (now - lastRunAttemptAt) >= effectiveCadenceMs;
```

With `lastRunAttemptAt` pinned 18 hours in the past, `(now - lastRunAttemptAt)` is ~63,000,000 ms against an `effectiveCadenceMs` of 3,689,960 — `due` is **always** true. With `consecutiveFailures` pinned at 1, `backoffMultiplier` is stuck at 2 and never grows. **The lane cannot back off, because backoff is computed from state the failing path does not advance.**

So the defect inverts the reading its own instrument invites:

| the snapshot suggests | what is happening |
|---|---|
| one failure, yesterday | continuous failure, every ~5 min |
| suppressed by backoff | no backoff in effect at all |
| lane idle / starved | lane saturating |

`TenantRepoSyncService.mjs:1155` states the intent exactly: *"Backoff is the only reason a failing repo stops being retried."* It is not stopping, because the counter it reads never moves.

## The Architectural Reality

- `ai/daemons/orchestrator/scheduling/tenantRepoSync.mjs:113` — `isRepoDue`, a pure function of `consecutiveFailures` + `lastRunAttemptAt`. Correct given its inputs; it is being handed stale ones.
- `ai/daemons/orchestrator/services/TenantRepoSyncService.mjs:1140-1175` — the not-due branch, which *reconstructs* `nextDueAt` as `lastRunAttemptAt + effectiveCadenceMs` for reporting. That reconstruction is why `nextDueAt` reads 17 hours in the past: it is derived from the same frozen field, not from a scheduling decision.
- `ai/daemons/orchestrator/services/DeploymentStateBridgeService.mjs:1262,1467-1483` — projects both into the deployment-state snapshot, so the frozen values are what every operator-facing surface shows.
- **Not established:** which write the failing path drops. The success path clearly persists; the per-repo catch is the place to look, and the deliberate `revalidation-deferred` branch at `:1197-1204` carries `consecutiveFailures` forward unchanged, which is at least the same *pattern* on an adjacent path. Naming a suspect, not a cause — see Avoided Traps.

## The Fix

1. Advance `lastRunAttemptAt` on **every** attempt, success or failure — it is the "when did I last try" field, and only the not-due branch currently depends on it being truthful.
2. Increment `consecutiveFailures` on the failing path so the exponential term is real, and reset it on success.
3. Once 1 and 2 hold, `backoff-suppressed` becomes a true statement rather than a frozen one.

The ingest failure itself (`KB_INGEST_FAILED`, `lastIngestedRev: null` — this repo has never ingested) is a **separate cause** and deliberately not bundled; this ticket makes the lane back off and report honestly, which is the precondition for diagnosing that one without the noise of a 5-minute retry loop.

## The stated mechanism is falsified — the failing path does not freeze the counters, it never runs

Assignee's first act on this ticket was to read the failing path before writing the spec that was supposed to go RED against it. It does not go RED, because **the fix this ticket prescribes is already implemented.**

`ai/daemons/orchestrator/services/TenantRepoSyncService.mjs:1384-1392`, present on `dev` today:

```js
// Increment consecutiveFailures on failure; preserve last good
// ingested revision so the next successful run starts from the correct base.
// lastRunAttemptAt advances even on failure (backoff measures from attempt
// start, not last-success).
const nextFailureCount = (priorState?.consecutiveFailures ?? 0) + 1;
persistedRevisions[repoLabel] = {
    lastIngestedRev    : priorState?.lastIngestedRev || null,
    lastRunAttemptAt   : startedMs,
    consecutiveFailures: nextFailureCount,
```

That is **The Fix** items 1 and 2 verbatim, including the comment explaining why. AC1 (*"proven by a spec that fails against today's code"*) and AC2 are therefore unsatisfiable as written: there is no RED to obtain.

### What is actually happening

The counters are frozen because **nothing on the failing path executes.** The process is aborted by the V8 heap limit inside the repo's protected work — after the `Refreshing` log at `:1220`, before any `catch`, `finally`, or the sweep-terminal `writePersistedRevisions` at `:1483`.

### This also explains the contradiction that produced the wrong shape

The two surfaces have **different writers**, which is why one looked fresh and the other frozen:

- **task-level** `status: failed` / `lastErrorAt: 13:38Z` — written by `TaskStateService` normalizing the *interrupted* run fail-closed **on boot**. It reports the crash, not a caught failure.
- **repo-level** counters — written only by a sweep that reaches `:1483`.

So the fresh task-level error was never evidence that the catch ran. Both prior readings of this lane, and this ticket, were built on that inference.

### The real defect, which is worth fixing and is not the one described

**Attempt state is recorded write-behind, so an attempt that kills the process is not an attempt at all.**

Backoff is computed from `consecutiveFailures` and `lastRunAttemptAt`; both advance only *after* the work returns. A failure mode that prevents the work from returning — OOM, SIGKILL, host sleep, container stop mid-sweep — therefore leaves **no record that anything was tried**, `due` stays true forever, and the lane retries at full cadence indefinitely.

**A crash loop is precisely what backoff exists to dampen, and it is the one failure class where backoff provably cannot engage.** The dampening is only available to failures polite enough to return.

### Revised Fix

1. Persist the attempt **before** the work: advance `lastRunAttemptAt` and increment `consecutiveFailures` at attempt start, then reset to 0 on success. Write-ahead, not write-behind. `:1087` already establishes the mid-sweep persist precedent for bootstrap seeding.
2. Leave `:1388-1392` alone — correct as written, and unreachable in this incident.
3. `isRepoDue` untouched — it was never the problem, which the original ticket had right.

### Revised Acceptance Criteria

- [ ] An attempt that never returns (simulated abort between attempt start and the sweep terminal) still leaves `lastRunAttemptAt` advanced and `consecutiveFailures` incremented — the spec fails against today's code, which is where the RED this ticket asked for actually lives.
- [ ] A success resets `consecutiveFailures` to 0.
- [ ] N consecutive aborted attempts grow `effectiveCadenceMs` as `2^N` up to `backoffCapMs`, asserted on the value.
- [ ] The existing failure path's counter behaviour is unchanged, and its specs still pass.
- [ ] `isRepoDue` and its specs untouched.

## Implementation finding: the write-ahead cannot live in the revisions manifest, and the reason is an invariant worth keeping

I built the obvious shape first — advance `lastRunAttemptAt` and `consecutiveFailures` directly in `persistedRevisions[repoLabel]` after `leaseGuard()`, then persist. It works, and **it breaks two existing lease specs for a good reason.**

- `commit-point fence: an evicted writer aborts without writing (#15763)` — compares the manifest byte-for-byte against the pre-sweep bytes.
- `renewal failure aborts before protected work … (#15763)` — asserts `fs.pathExists(revisionsFile) === false`.

My first read was that these assert *proxies* (bytes, file existence) for the real invariant (*"per-repo backoff state was not manufactured for the aborted sweep"*), and that I could restate them. **That was wrong.** The first spec's name states the property directly: *aborts **without writing***. The revisions manifest is a commit log, and `#15763`'s whole subject is the commit-point fence. Writing scheduling state into it before the work completes does not invalidate a proxy — it removes the property.

Retracting the entry on the lease-lost branch does not rescue it either: the retraction restores the *semantics* but not the bytes, and it needs its own durable write inside an abort path, which is more machinery defending a shape that was wrong to begin with.

### The shape that fits

An in-flight attempt is, by definition, **uncommitted**. It belongs beside the manifest, not inside it:

1. A sidecar (`<revisionsFilePath>.in-flight`) records `{repoLabel: {startedMs, priorFailures}}` after `leaseGuard()` and before the git phase.
2. Every path that **returns** — success, caught failure, lease-lost abort — clears that repo's entry. The existing per-repo `finally` (which already releases the semaphore) is the single clearing point for all three.
3. At sweep start, a residual entry means the previous attempt never returned. Fold it into `persistedRevisions[repoLabel]` **then** — at which point it is a committed fact — and persist through the normal path.

The manifest keeps its "committed outcomes only" semantics, both `#15763` specs pass untouched, and a killed process still leaves a record for the restart to find. Per-repo clearing rather than one sweep-terminal truncate, because with `concurrencyLimit ≥ 2` a crash in repo B would otherwise fold repo A's completed attempt into a spurious failure.

One constraint the first attempt did surface and the sidecar inherits: `writePersistedRevisions` stages through a single pid-scoped temp path, so any write from inside the concurrent region needs serializing. A promise chain in the sweep scope is enough.

I have discarded the manifest-resident implementation rather than commit a shape I would ask a reviewer to reject. The ACs above stand as written — this changes where the record lives, not what it proves.
