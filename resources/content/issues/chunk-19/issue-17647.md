# healthcheck cannot tell a disabled wake plane from an unreadable one

## Context

Surfaced while investigating #17646. The operator raised heartbeat delivery as a possible cause of A2A wake noise and flagged the guess as uncertain — *"absolutely NOT sure here, because we previously disabled it on purpose."*

**That uncertainty is the defect.** No live surface can answer it, and the one that looks like it can gives the same answer either way.

## The Problem

`healthcheck` returns:

```json
"wake": {
    "gateState": "unknown", "gateTrippedAt": null, "gateTrippedBy": null,
    "daemonRunning": false, "lastPulseAt": null, "secondsSinceLastPulse": null,
    "subscription": {"armed": true, "reason": "deliverable"}
}
```

`HealthService.mjs:422-437` documents `daemonRunning` as a heuristic over a **heartbeat-liveness file's mtime**, and states that the block degrades to *exactly* `gateState: 'unknown', daemonRunning: false, lastPulseAt: null` **without throwing** when that file cannot be read.

So one payload means all three of:

1. the heartbeat is **deliberately disabled** (`swarmHeartbeatEnabled` defaults `false` — `configBase.mjs:1987`);
2. the heartbeat is **enabled and dead**;
3. the heartbeat's liveness file is **unreadable from the reader's realm** — the MC server runs in its own container and the file is the orchestrator's.

A reader chasing wake noise cannot distinguish "off on purpose" from "silently broken", which is the difference between *not the cause* and *the whole cause*.

**It cost this investigation its first wrong turn.** I read `daemonRunning: false` as evidence the heartbeat was not involved and nearly stopped there. It was the right conclusion reached from an instrument that would have reported identically had the heartbeat been the culprit — a green that means nothing. The real answer came from `configBase.mjs` defaults, `docker inspect` on the orchestrator's env, and its logs showing zero pulse lines.

**And the same payload is actively misleading in the other direction.** `subscription: {armed: true, reason: "deliverable"}` sits beside `daemonRunning: false`, which reads as *"you are subscribed but nothing is running"*. Wakes were in fact being delivered continuously throughout, because `WakeSubscriptionService.mjs:111` supports three routes — `mcp-notifications`, `a2a-webhook`, `bridge-daemon` — and this block reports the liveness of one of them while the live route is another.

## The Architectural Reality

- `WakeSubscriptionService.mjs:111` — `validHarnessTargets = ['mcp-notifications', 'a2a-webhook', 'bridge-daemon', 'disabled', 'none']`.
- `configBase.mjs:1968` / `:1987` — `bridgeDaemonEnabled` and `swarmHeartbeatEnabled` both default `false`, deliberately: *"because the Stop hook makes wake + heartbeat redundant."*
- `HealthService.mjs:480-481` — the degraded defaults are literals in the failure path, indistinguishable from measured values.

The block is not wrong about what it measures. It is **scoped to one route and reports as if it described the wake plane**, and it cannot signal its own blindness.

## The Fix

Make the payload answer the question a reader actually has: *is a wake going to reach me, and if not, why not.*

- **Distinguish disabled from unreadable.** `gateState` should carry a third value — the current `'unknown'` conflates them. A configured-off plane is a *known* state and should say so.
- **Report the configured route.** The subscription already knows its `harnessTarget`; surfacing it turns `daemonRunning` from a bare boolean into a scoped one (`bridge-daemon: false` is unremarkable when the target is `mcp-notifications`).
- **Report liveness for the route in use**, or state explicitly that it is not observable from this realm — an unobservable value must never be rendered as a measured `false`.
- Include the effective `swarmHeartbeatEnabled` / `bridgeDaemonEnabled` values, so "disabled on purpose" is readable without a container `inspect`.

## Acceptance Criteria

- [ ] With the heartbeat **configured off**, `healthcheck` says so distinguishably — a reader can tell it from a heartbeat that is enabled and dead, without reading `configBase.mjs` or inspecting a container.
- [ ] With the liveness file **unreadable**, the payload reports the value as unobservable rather than as `false`. Verified by making it unreadable, not by reading the code path — an unobservable-vs-false distinction asserted only in prose is the defect restated.
- [ ] The `wake` block names the **route** its liveness figure describes, and that route matches the subscription's `harnessTarget`.
- [ ] A control proves the block is not vacuous: with the heartbeat **enabled and pulsing**, `daemonRunning` reads `true` and `lastPulseAt` advances. Without this, every arm above passes on a payload that is permanently and uninformatively "off".

## Out of Scope

- **The wake-noise defect itself** — that is #17646, whose causal chain contains no heartbeat. This ticket is about the instrument that made the heartbeat a plausible suspect.
- Changing any default. `swarmHeartbeatEnabled: false` and `bridgeDaemonEnabled: false` are deliberate and correct; this ticket makes them *legible*, not different.
- The coalescing digest's own opacity — a wake naming only the latest of N events hides how many suppressible broadcasts it carried. Real, adjacent, and separable.

## Avoided Traps

- **"It reports `false` and the thing is `false`, so it is correct."** It is accidentally correct today, for a reason unrelated to what it measures, and would be identically `false` if the heartbeat were enabled and broken. A value that cannot be wrong cannot be evidence.
- **Adding a new health field and leaving the old one.** `daemonRunning` is the field readers already consult; a truer sibling beside a misleading incumbent means the misleading one keeps being read.
- **Fixing this by documenting it.** The conflation is *already documented* at `HealthService.mjs:437` — I read that docblock and still had to go to the config and the container logs to answer the question. Prose that accurately describes an ambiguous value does not disambiguate it.
