# Data Sync exhausts its stale-head budget on an active merge day

## Context

Observed on the first scheduled run after `#17148` merged — [run 31877195197](https://github.com/neomjs/neo/actions/runs/31877195197), which **did** publish (`f87cff0c5e`, ending a ~22h corpus freeze). It published on **attempt 2 of 2**, the last available attempt.

This is a second-order consequence of `#17148`, not a defect in it: that fix lengthened emission by running the stages the pipeline used to skip by aborting at stage 3 of 7. A longer emission window is more likely to be overtaken by `dev`.

## The Problem

`runDataSyncPipeline` defaults `maxAttempts = 2` (`buildScripts/dataSyncPipeline.mjs`). When `origin/dev` advances during emission, the attempt is discarded and re-emitted from the new head; exhausting both attempts throws *"Data Sync stopped cleanly because dev advanced during all 2 emission attempts"* — **and publishes nothing.**

Measured on the run above:

| | window | `dev` activity |
|---|---|---|
| attempt 1 | 09:35:15 → 09:53:18 (18m03s) | `#17152` merged 09:32:33, `#17154` merged 09:50:05 → **discarded** |
| attempt 2 | 09:53:20 → 10:11:22 (18m02s) | quiet → **published** |

Emission is ~18 minutes and the budget is 2. On a morning where merges land every ~18 minutes, the pipeline can burn both attempts and freeze the corpus again — for a reason unrelated to any credential or stage failure. One more merge during attempt 2 and this run would have published nothing.

## The Architectural Reality — measured, because the obvious mitigation is wrong

My first instinct was "publish the corpus before the slow DevIndex enrichment, shrinking the window to minutes". **The measurement falsifies that.** Per-stage decomposition of attempt 1:

| stage | duration | share |
|---|---|---|
| install dependencies | 0m13s | 1% |
| **GitHub Workflow corpus** | **12m54s** | **71%** |
| DevIndex Opt-In | 0m08s | — |
| DevIndex Opt-Out | 0m09s | — |
| DevIndex Spider | 0m45s | — |
| DevIndex Updater | 2m34s | — |
| content indexes and SEO | 1m20s | 7% |
| **total** | **18m03s** | |

**The DevIndex enrichment is only 20% of the window.** The corpus stage alone is 71%, and it *must* precede any publish — it generates the thing being published. So reordering to publish before enrichment saves at most ~3m36s of 18m, roughly a 20% narrowing. Worth having, nowhere near "shrink to minutes".

Recording this because the intuition is attractive and wrong, and the next person will have it too.

## The Fix — candidates, none obviously dominant

1. **Raise `maxAttempts`.** Simplest and directly targets the observed exhaustion. Cost: each extra attempt is ~18 minutes of runner time on a pipeline that runs hourly, so 3 attempts can approach the schedule interval.
2. **Publish corpus + content-indexes before the intake stages.** Measured ~20% window reduction. Also makes publication structurally independent of enrichment, which is the same separation `#17148` established at the failure axis. Requires confirming `content indexes and SEO` does not consume DevIndex output.
3. **Re-emit only what the new head invalidated** rather than the whole corpus. Largest win — it attacks the 71% — and by far the most complex; needs a per-facet dependency on the diff between heads.
4. **Accept it and monitor.** The watchdog already alarms on corpus staleness, and a stale-head exhaustion is self-correcting on the next hourly run. This is a legitimate answer if exhaustion turns out to be rare.

Deciding between these needs a frequency measurement nobody has: how often does `dev` advance twice inside 18 minutes? One observation is not a rate.

## Acceptance Criteria

- [ ] The `dev`-advance rate during emission windows is measured over a representative period (a merge-heavy weekday and a quiet one), not inferred from this single run.
- [ ] A decision between candidates 1–4 is recorded with that rate as its basis, including an explicit "accept and monitor" option.
- [ ] If a code change lands, a stale-head exhaustion no longer silently publishes nothing: the failure names `dev`-advance as the cause distinctly from a stage or credential failure.
- [ ] Any claimed window reduction is stated as a **measured** figure with its per-stage decomposition, not a nominal one.

## Out of Scope

- `#17148` / `#17150` / `#17162` — the failure-isolation work. This is a timing interaction, not a failure path.
- Making the corpus stage itself faster. That is the 71% and the real prize, but it is a different investigation with a different risk profile.

## Avoided Traps

- **"Publish before enrichment shrinks the window to minutes."** Falsified above: enrichment is 20%, the corpus stage is 71% and is unavoidable pre-publish. I proposed this before measuring and it was wrong.
- **Treating one observation as a rate.** This run exhausted attempt 1 on a morning with unusually dense merges. That is an existence proof, not a frequency.
- **Reading the publish as a clean success.** It landed on the last available attempt; a single additional merge would have produced a silent no-publish.

## Related

- `#17148` / PR #17149 — lengthened emission by removing the early abort; the cause of the widened window.
- `#17131` — the standing alarm; a stale-head exhaustion presents there as continued corpus staleness with no failing stage.

## AC-1 measured: exhaustion is a ~1-in-7 event overall and ~1-in-3.5 in peak hours

This ticket's first AC asked for the `dev`-advance rate rather than an inference from the single observed run. Measured over **277 commits across 6.9 days** (2026-08-08 → 2026-08-15), mean merge rate **39.9/day, one every 36 minutes**.

Simulating run starts against the real 18m03s emission window:

| run-start sampling | n | attempt 1 discarded | **budget exhausted → no publish** |
|---|---|---|---|
| hourly (the actual schedule) | 167 | 42% | **11%** |
| every 10 min | 997 | 36% | **14%** |
| every minute | 9962 | 36% | **15%** |

**Roughly one scheduled run in seven publishes nothing** because `dev` advanced during both attempts. That is not rare enough to ignore and not frequent enough to be the dominant failure mode.

**It is strongly hour-dependent**, which matters more than the average:

| UTC hour | exhaustion rate |
|---|---|
| 13h | 29% |
| 17h | 29% |
| 19h | 29% |
| 15h | 26% |

**In peak hours it is closer to one run in three.** The observed near-miss (run 31877195197 publishing on attempt 2 of 2 at ~09:31Z) was not unlucky — it was a typical outcome for a busy window.

### A sampling correction, recorded because it changes the number

My first pass sampled every commit as a hypothetical run start and reported **38%** exhaustion. That is biased: anchoring on commit times conditions on a merge having just occurred, and commits cluster. Scheduled runs start hourly, independent of merge activity. Sampling independently of commits gives **11–15%**. The biased figure was ~2.5× too high and I would have filed it as the answer.

### What this does to the four candidates

- **(4) Accept and monitor** — weakened. 11–15% of runs publishing nothing, concentrated in working hours, is a real staleness contribution rather than noise. The watchdog would surface it as corpus staleness with no failing stage, which is exactly the hard-to-diagnose shape.
- **(1) Raise `maxAttempts`** — quantifiable now. Each attempt is ~18 min, and a third attempt would cut exhaustion to roughly the cube of the per-window advance rate (~5%) at the cost of up to 54 min of runner time on an hourly schedule. That is a real collision risk with the next scheduled run.
- **(2) Publish before enrichment** — still only ~20% window reduction (enrichment is 3m36s of 18m03s; the corpus stage is 12m54s and must precede publish). Narrowing 18m → ~14.5m moves exhaustion from ~14% to roughly ~9% on the same data. Helps, does not solve.
- **(3) Incremental re-emission** — attacks the 71%. Still the largest win and the most complex.

**No recommendation from me yet**, because the honest read is that (1) and (2) are complementary and neither alone is decisive, and (3) is a different-sized project. What the data does settle is that AC-1's question is answered and "accept and monitor" is now the weakest option rather than a reasonable default.

Method: `git log origin/dev --since=2026-08-08 --format=%ct --no-merges`, windows fixed at the measured 18m03s emission time from run 31877195197.

## AC-2 decision: none of the four, because `maxAttempts` is the wrong *kind* of budget

AC-1 is answered (11–15% overall, ~29% in peak UTC hours). AC-2 asks for a decision on that basis. Taking it rather than leaving it open — it is my ticket and the choice is reversible in one commit.

**The decision is a fifth option, and it comes from noticing what the count is a proxy for.**

`maxAttempts = 2` is not really a retry budget. It is a **time** budget wearing a count's clothes: 2 × ~18m ≈ 36m, chosen so a run finishes inside its hourly slot. The count only tracks that constraint while emission duration is stable — and `#17148` changed emission duration, which is precisely why this ticket exists.

That makes the count a **fixed budget standing in for a condition**, and it fails the same way every such budget does: it cannot distinguish *"we are out of attempts"* from *"we are out of time."* Today those coincide by accident. They will separate again the next time a stage gets slower or faster, and the failure will be silent in both directions — either publishing nothing while an hour of slot remained, or overrunning the slot on a fast day and never noticing.

**Recommendation: replace the attempt count with a wall-clock deadline** derived from the schedule interval, retrying while there is time for another emission rather than while a counter is unspent. On a quiet fast day that yields more than two attempts for free; on a slow day it stops before overrunning, which the count cannot do at all.

### Why the deadline matters more than I first thought — verified, not assumed

```yaml
schedule:  - cron: '0 * * * *'      # hourly
concurrency:
  group             : data-sync-pipeline
  cancel-in-progress: false
```

`cancel-in-progress: false` means an overrunning run is **not** cancelled by the next scheduled one — the next run queues behind it, and further pending runs supersede each other. So overrun does not present as a failure; it presents as **the schedule quietly slipping**, with scheduled runs effectively skipped while one long run holds the group.

This is the fact that decides between the candidates, and I had it backwards before checking: I assumed a long run would be cancelled and framed candidate (1) as risking a *collision*. It does not collide — it **delays**, which is harder to see and therefore worse.

### The four candidates, re-scored against that

- **(1) Raise `maxAttempts` to 3** — **reject as a standalone.** ~5% exhaustion, but 3 × 18m = 54m against a 60m interval, and with no cancellation the overrun silently eats the following slot. It buys a better publish rate by spending schedule reliability, and the payment is invisible.
- **(2) Publish before enrichment** — **accept as complementary.** ~20% window reduction (18m03s → ~14.5m) moves exhaustion ~14% → ~9%. Modest alone, but it shortens *every* attempt, so it compounds with a deadline: at 14.5m a 45m deadline affords three attempts inside the slot where 18m affords two. It also carries the same structural separation `#17148` established at the failure axis.
- **(3) Incremental re-emission** — **defer, not reject.** It attacks the 71% and remains the largest available win. Different-sized project, different risk profile; it should be its own leaf once (2) and the deadline are in.
- **(4) Accept and monitor** — **reject.** 11–15% of runs publishing nothing, concentrated in working hours, presents at `#17131` as corpus staleness with no failing stage. That is the hardest shape to diagnose, and I spent most of yesterday proving it.

### Ordering

The deadline first — it is small, it removes the proxy, and it makes the system honest about which resource it is actually spending. Then (2), measured rather than nominal per AC-4. Then re-measure before deciding whether (3) is still worth its complexity.

### One thing I want on the record

This is the second fixed budget standing in for a condition that I have handled today — the other being a test's 50-turn spin (`#17186`), where the same shape produced a defect that shipped *inside a green CI verdict*. Different substrate, milliseconds versus event-loop turns versus retry counts, identical failure: **a number chosen against one machine's behaviour, standing in for the constraint that actually matters, and going quiet when the two drift apart.** Worth naming as a class rather than fixing three times without connecting them.

## Revising my own decision from two comments ago — (2) goes first, not the deadline

I recorded "deadline first, then (2)" earlier today. **Reversing that order.** Recording the change rather than quietly switching, because the reasoning is the useful part and my first pass priced two things wrong.

The deadline argument still stands *as an argument* — `maxAttempts` genuinely is a time budget wearing a count's clothes. What changed is its cost and its urgency, both measured after I wrote the recommendation.

### Fact 1 — a wall-clock deadline needs a clock seam, and the test cost is the punchline

`maxAttempts` is a **tested contract**, not an incidental default: `DataSyncPipeline.spec.mjs:192` pins `attempts: 2`, and `:234` pins `/dev advanced during all 2 emission attempts/` plus `attempt=2/2` in the logs. Both run against a real git fixture.

Converting to a wall-clock budget means those tests either inject a clock, or depend on real elapsed time. **The second option is the exact defect class I spent today removing** — a fixed duration standing in for a condition, which is `#17186`'s whole subject. Choosing a design whose tests reintroduce it, on the same day, would be an unusually direct way to not learn the lesson.

The seam is buildable. It is just no longer the *cheap* option, and I recommended it as if it were.

### Fact 2 — exhaustion is loud, not silent, and I scored candidate (4) against a symptom it does not have

I twice described the failure as "silently publishes nothing." **Checked, and that is wrong:**

- `dataSyncPipeline.mjs:580-585` **throws** on exhaustion, with a message naming `dev`-advance distinctly from any stage or credential failure.
- `.github/workflows/data-sync-pipeline.yml:213` runs it with **no `continue-on-error`**. The only `continue-on-error` in that workflow is line 109, the intake mint, scoped deliberately in `#17165`.

So exhaustion presents as a **red workflow run with an accurate distinct cause**, self-correcting on the next hourly schedule. That is materially less severe than the framing I used, and I should not have used it twice without checking — especially having spent yesterday proving that a step's status can lie.

**This partially rehabilitates candidate (4)** and, more importantly, removes the urgency I was using to justify the more invasive change first. The residual cost is real but different: 11–15% of hourly runs going red trains people to ignore red on this workflow, which is its own hazard — just not the *silent* one.

**AC-3 is therefore already satisfied by current behaviour** for the naming half, independent of any code change.

### Fact 3 — candidate (2)'s precondition is VERIFIED, so it is executable now

The ticket flagged this as unconfirmed: *"Requires confirming `content indexes and SEO` does not consume DevIndex output."*

**Confirmed, transitively.** `rebuildContentIndexesAndSeo.mjs` imports only `./index/{release,discussions,pulls,tickets}.mjs`, `./seo/generate.mjs`, and `reconcileActiveChunks.mjs`. Neither the entry script nor any of those modules contains a `devindex` reference, and they read `resources/content/**` — the **stage-2 corpus**, not DevIndex output.

So the reorder is sound:

| | stage | cumulative |
|---|---|---|
| 1 | install dependencies | 0m13s |
| 2 | GitHub Workflow corpus | 13m07s |
| 3 | content indexes and SEO | 14m27s |
| — | **← publish here** | **~14.5m window** |
| 4–7 | DevIndex Opt-In / Opt-Out / Spider / Updater | +3m36s |

18m03s → ~14.5m moves exhaustion from ~14% to roughly ~9% on the measured data, and it makes publication structurally independent of enrichment — the same separation `#17148` established at the failure axis.

### Revised decision

1. **(2) first.** No clock seam, no retry-semantics change on a pipeline that stabilised today, precondition verified, and it shortens *every* attempt so it compounds with anything later.
2. **Then re-measure**, and decide whether the deadline is still worth its seam. At a ~14.5m window a 45m budget affords three attempts where 18m afforded two — so (2) may deliver most of what the deadline was for.
3. **(3) incremental re-emission** stays the largest available win and stays deferred.

### The general note, since I have now made this mistake in both directions today

I recommended the more invasive change first on a symptom I had not verified, and I did it in a comment that opened by insisting on measurement over inference. **The measurement discipline does not automatically extend to the framing you use to motivate the measurement** — "silently publishes nothing" was doing real argumentative work, and it went unchecked precisely because it was a premise rather than a claim.
