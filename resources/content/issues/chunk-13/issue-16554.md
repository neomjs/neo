# Five orchestrator lanes have no owner: both roles decline them

## Context

Found by `@neo-opus-vega` from the live host-edge runtime state and handed to me as orchestrator surface; the enablement half is measured here. Both halves are first-hand.

The Knowledge Base holds **0 documents**. Per ADR-0027 (`:112`, `:117`, `:189`) that is by design outside the autonomous recovery target set, because *"Knowledge Base rebuilds from source"* — so `kbSync` **is** the KB's sanctioned recovery path. It has never run.

## The Problem

**Five lanes are declined by the container plane on the grounds that host-edge owns them, and declined by the host-edge profile on the grounds that host-edge does not own them.** Both statements are internally coherent. Together they leave the lanes with no owner, and every health surface reads green.

**Container orchestrator, on every boot:**

```
[Orchestrator] Not running 5 lane(s) this role does not own — host-edge owns
githubWorkflowSync, kbSync, primary-dev-sync, swarm-heartbeat, temporal-summary.
This process does not verify that the owning role is live.
```

**`ai/deploy/hostEdgeProfile.mjs:107-117`**, under the literal comment *"Host-edge-class lanes this topology does not elect for the host edge:"*

```js
NEO_ORCHESTRATOR_GITHUB_WORKFLOW_SYNC_ENABLED: 'false',
NEO_ORCHESTRATOR_KB_SYNC_ENABLED             : 'false',
NEO_ORCHESTRATOR_PRIMARY_DEV_SYNC_ENABLED    : 'false',
NEO_ORCHESTRATOR_SWARM_HEARTBEAT_ENABLED     : 'false',
NEO_ORCHESTRATOR_TEMPORAL_SUMMARY_ENABLED    : 'false'
```

**Five for five, exactly** — the same lanes on both sides.

**Observed consequence**, host-edge `orchestrator-state.json` (measured by `@neo-opus-vega`, host-edge live at PID 99868, up 2d 4h): all five report `lastRunAt = NEVER`. Only `lms` has ever run — and `lms` is the one flag the same profile sets `'true'` at `:100`, which is the positive control that the field is written at all and that the profile's declarations are what decide.

`registry.mjs:93` reads `state.kbSync?.lastRunAt ?? 0`, so NEVER means due-immediately. This is not a not-yet-due artefact.

**A live owner running none of its lanes is worse than a dead one.** A dead host-edge would fail a liveness probe. A live one running nothing satisfies every check, and the container's warning naming it as owner reads as reassurance.

## The Architectural Reality

`#16166` ("Split host-edge and container orchestrator task authority", closed) created this topology, and its own AC-3 is the invariant now violated:

> *"The combined host-edge + container-plane matrix has exactly one owner for every required lane; duplicates and gaps fail before work starts."*

and its Fix section:

> *"Add a startup/preflight receipt that reports the resolved owner of every task and rejects an incomplete or double-owned required lane before either supervisor begins work."*

**The reject half is what is missing.** The two halves are derived from different substrates and nothing reconciles them:

- `ai/daemons/orchestrator/Orchestrator.mjs:1125-1150` — `buildDisabledLaneAnnouncement` maps each declined lane through `resolveAuthorityClassOwner({authorityClass})`. The owner is derived from the lane's **authority class**, a static classification. Its JSDoc is explicit and correct about its own boundary (`:1116-1121`): *"it does NOT claim the owning role is running"* — a graphless host edge cannot probe the container plane, so honesty was chosen over a guess.
- `ai/deploy/hostEdgeProfile.mjs:92-118` — `buildHostEdgeEnv` is a **hand-written env fragment** declaring which lanes host-edge elects. Its own JSDoc (`:78-81`) calls this the "lane closure" and says *"stating the closure makes the elected lane set legible in one place."*

Both are well-documented and each is right about itself. **Neither reads the other.** The class table says "host-edge's class"; the profile says "not elected here". The announcement is a **statement**, not a **check** — the gap is named in prose at the exact moment it opens, and then both supervisors start anyway.

`ai/daemons/orchestrator/scheduling/registry.mjs:93` — the due-computation that makes NEVER mean due-immediately, so the lanes are not merely idle; they are permanently due and never offered.

## The Fix

Make the reconciliation mechanical rather than editorial, per `#16166`'s undelivered half.

1. Derive the host-edge lane closure from the **same** authority classification the container uses (`resolveAuthorityClassOwner`), instead of a hand-maintained parallel env fragment. A lane classified host-edge-owned must be enabled by the host-edge profile by construction, not by a second author agreeing.
2. Where a declared owner declines a lane, that is an **unowned required lane** and must fail at boot, not log. The honest-boundary reasoning in `Orchestrator.mjs:1116-1121` stays intact: this check does not require probing the other plane, only comparing two local declarations.
3. Decide and record the disposition of each of the five. `kbSync` self-evidently needs an owner. The other four (`githubWorkflowSync`, `primary-dev-sync`, `swarm-heartbeat`, `temporal-summary`) may be intentionally retired — if so, they must be removed from the classification rather than left orphaned, because an orphan is indistinguishable from a gap.

## Avoided Traps

- **Reading the container's warning as reassurance.** *"host-edge owns kbSync"* is a true statement about a class table and says nothing about whether host-edge runs it. The line even says so. It was read as coverage for 2d 4h.
- **Asserting the enablement branch from the symptom.** `@neo-opus-vega` left this branch explicitly open — *"`enables.kbSync` false versus the scheduling pipeline not running on host-edge at all"* — rather than inferring it from five NEVERs. The profile read settles it; the five-for-five correspondence plus `lms: 'true'` running is the discriminator, and neither is available from the symptom alone.
- **Fixing `buildDisabledLaneAnnouncement`.** It is correct and its boundary is deliberate. The defect is that nothing compares its output against the other role's declaration.
- **A census instead of a predicate.** Enumerating today's five lanes in a doc or a test fixture would go stale the first time a lane is added. The check has to be a derivation, so a new lane is classified as a side effect of existing.

## Correcting my own framing: `#16166`'s reject half WAS delivered. The gap is one level down, and it is sharper.

I wrote above that *"the reject half was never delivered."* **That is false**, and I found it by reading the module I should have read before filing.

`ai/daemons/orchestrator/taskAuthority.mjs:394-425` — `auditAuthorityTopology` is exactly `#16166`'s preflight receipt, and it throws:

```js
if (owners.length !== 1) {
    const failure = owners.length === 0 ? 'ownership gap' : 'double ownership';
    throw new Error(
        `[orchestrator-authority] ${failure} for task "${lane.task}" ` +
        `(class="${lane.authorityClass}", owners=${JSON.stringify(owners)}).`
    );
}
```

It runs from `buildAuthorityReceipt` over an inventory that `buildAuthorityLaneInventory` proves exhaustive — an unclassified task throws at construction (`getTaskAuthorityClass:172`), a duplicate task name throws, and registry metadata disagreeing with the canonical map throws. That is a genuinely well-built gate and it holds today: `kbSync` → class `host-edge` → owned by profile `host-edge`, exactly one owner. **The audit passes, and it is right to pass.**

### The actual gap: ownership and enablement are different axes, and only one is audited

`TASK_AUTHORITY_BY_NAME` (`:41-46`) states the intended relationship in its own JSDoc:

> *"Profile-to-class ownership is the single routing rule. **Per-lane enable flags may disable configured work, but they cannot move a lane to a different authority.**"*

That is precisely correct, and it is precisely the loophole. `NEO_ORCHESTRATOR_KB_SYNC_ENABLED: 'false'` does not move `kbSync` to another authority — it leaves it owned by `host-edge` and simply off. The audit asks *"does this lane have exactly one owner?"* (yes) and never asks *"does its owner actually turn it on?"* (no).

So the two halves are:

| | substrate | asserts |
|---|---|---|
| `auditAuthorityTopology` | `AUTHORITY_CLASSES_BY_PROFILE` × `TASK_AUTHORITY_BY_NAME` | every lane has exactly one owning **profile** |
| `buildHostEdgeEnv` | hand-written env fragment, `hostEdgeProfile.mjs:92-118` | which lanes that profile actually **enables** |

**Nothing reconciles them.** A lane can be owned-by-construction and disabled-by-hand, and every gate in the system reports healthy. Five lanes currently are.

### What changes in The Fix

Item 2 above — *"where a declared owner declines a lane, that is an unowned required lane and must fail at boot"* — stands, but it is now specific: the check belongs **beside `auditAuthorityTopology`, extending it from class-ownership to effective-ownership**, not as a new subsystem. The audit already has the lane inventory and the owning profile per lane; what it lacks is the owner's enablement view.

Item 1 gets stronger and cheaper for the same reason: `buildHostEdgeEnv`'s closure should be **derived** from the same two maps the audit reads, so a `host-edge`-class lane cannot be hand-written `false`. Today the closure is a second, independent authoring of a fact the classification already owns — and its own JSDoc (`:78-81`) says the closure exists to make the elected set *"legible in one place"*, which is the right goal reached by the wrong mechanism: a second place.

ACs are unchanged in substance; AC-1 and AC-2 now name `auditAuthorityTopology` as the extension point rather than implying a missing gate.

### Why I got it wrong, since the ticket asks others to trust its reads

I inferred *"the reject half was never built"* from a grep for `resolvedOwner|resolved-owner|ownerReceipt|laneOwner|unowned` that returned nothing relevant. The function is called `auditAuthorityTopology` and the receipt is `buildAuthorityReceipt` — **my alternation was built from `#16166`'s prose, not from the code's vocabulary**, so the zero it returned described my guess at the naming, not the absence of the thing. The same failure mode, in the same hour, as my `churn-baselines` claim: I searched one spelling of an absence and published the result.

The finding survives both corrections, and is now better specified than when filed. That is the part worth keeping.

* fix(ai): the corpus lanes move to the plane that can run them (#16554)

Supersedes the two earlier shapes on this branch. Both were caught by guards
that predate this work, and both corrections came from @neo-opus-grace.

WHAT THE FIX IS

`kbSync` and `temporal-summary` reclassify host-edge -> container-plane, and
their enable leaves move `localOnly` -> `cloudOnly` so the default resolves
enabled on the role that now owns them.

ADR-0014 §2.1 classed both local-only because they scan the Neo repo's own
corpus "from the local checkout". True when written, and its premise expired:
the non-dockerized local Agent OS was retired deliberately. The checkout did
not disappear, it MOVED -- the container is built from the repo and carries
learn/ (4.3M), src/ (5.7M), resources/content/ (168.7M) and .git (89M),
measured in the running container. Not §5.2's anti-pattern: tenant content
stays with `tenant-repo-sync` on its own GitMirror primitive.

WHAT I GOT WRONG TWICE, AND WHAT THE GUARDS SAID

1. Removing both keys from `hostEdgeProfile`'s closure. `ParityPlaneVolume-
   Scoping` pins that key set as "the graphless closure". The refutation was
   inside the list: CHROMA_DAEMON and EMBED_DAEMON are container-plane too and
   have always been listed. The closure declares what a GRAPHLESS process must
   not start -- a capability claim, not an ownership one -- so it survives any
   reclassification. Both keys restored.

2. Pinning the enablement in docker-compose instead of moving the leaves.
   `mcpHealthcheck.spec.mjs:379` refuses a production compose that sets
   NEO_ORCHESTRATOR_KB_SYNC_ENABLED: "duplicates an AiConfig default". Compose
   must inherit, so the default has to be right. Reverted; the leaf move is
   the correct change and its cost is real.

THAT COST, MEASURED

`kbSync` is the canonical "schedulable heavy lane" across the orchestrator
fixtures, so flipping its default group inverts it for every local-mode case
using it as a stand-in. Against a clean-`dev` control: 13 specs. Paid rather
than dodged -- one shared fixture line (`savedCloudOnly` already existed),
the two localOnly-mechanics specs re-based onto `primaryDevSyncEnabled`
(still localOnly, mutates a working tree), and #16166's authority spec
updated on BOTH sides.

Both sides on purpose: a reclassification that only removes a lane from one
role leaves it owned by nobody, which is this ticket's own defect and is
invisible from either role alone. Line 307 asserted the container does NOT
schedule kbSync and never surfaced -- the earlier assertion failed first and
blinded it.

New coverage for the property the whole change rests on: `cloudOnly` + null
resolves the OPPOSITE way (cloud enables, local opts in). Ownership and
enablement are separate axes and no ownership spec can see that one.

EVIDENCE

  this branch: 5 failed / 11556 passed
Identical failure sets; zero regressions attributable here. The 5 are
pre-existing and order-dependent.

ADR-0014 carries a dated amendment recording why the leaves live in
`cloudOnly`, why compose stays silent, why the closure keeps both keys, and
a revalidation trigger for the container-as-checkout premise.
