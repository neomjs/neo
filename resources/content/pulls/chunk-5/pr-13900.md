Resolves #13882
Refs #13874

Detects and recovers a **stuck Ollama runner** — a model that is resident (residency probes pass, `/api/tags` answers) yet pegged at ~100%×N-cores grinding one pathological request while serving nothing, because `OLLAMA_NUM_PARALLEL=1` queues everything behind it.

**Empirical anchor:** a `gemma4` runner pegged at 399.7% for **58h of CPU-time** on a live deployment with an **idle orchestrator and zero users** — the residency-only `livenessProbe` treated it as healthy, so the supervisor never restarted it and the cores never recovered. This is the *recovery* half; the *prevention* root-cause (un-chunked lossless session summarization shipping a 131K-token context to a CPU model) is tracked separately (#12073 + a CPU context cap).

The fix extends the orchestrator's existing `ollama serve` supervision: the `livenessProbe` now runs a real inference **canary** and flips to unhealthy only after N **consecutive** sustained canary failures, so `ProcessSupervisorService.gateRestartOnLivenessProbe` restarts the runner — bounded by its existing restart cooldown (no thrash). A *single* canary failure stays advisory — the **false-positive guard**: a legitimately-long request must not be restarted, the line between recovery and a self-inflicted outage / restart-loop. The actuator is privilege-free (the orchestrator already supervises `ollama serve` via #13868); inherits the detect≠actuator + bounded-anti-thrash framing of ADR-0025.

Evidence: L2 (11 focused unit tests on the pure stuck-classifier + the canary, including the false-positive guard) -> L4 required (live deploy: a stuck runner restarts unattended and the box recovers). Residual: live restart validation on the deployment.

## Deltas

- New `ai/services/graph/ollamaStuckRunnerLiveness.mjs`: `classifyStuckRunner` (pure — sustained-failure → stuck, single-failure advisory, reset-on-served / reset-after-stuck) + `probeOllamaServing` (a tiny `/api/chat` canary, `num_predict:1`, real `AbortController`, `fetchFn`-injectable for tests).
- `ai/daemons/orchestrator/Orchestrator.mjs`: the `ollama` `livenessProbe` consumes the detector after the residency check — per-task `_ollamaStuckFailures` counter, defensive `try/catch` fallback to "alive" so a detector fault never restarts a healthy runner; both imports stay dynamic, matching the existing probe.
- `ai/config.template.mjs`: `orchestrator.providerReadiness.stuckRunner` leaves (`enabled` / `consecutiveFailures` / `canaryTimeoutMs`) — on in a fresh deploy, off under a stale local config (no surprise restarts).

## Test Evidence

- `node --check` on all three touched source files — clean.
- `npm run test-unit -- test/playwright/unit/ai/services/graph/ollamaStuckRunnerLiveness.spec.mjs` -> **11 passed** (the false-positive guard, the threshold incl. `threshold=1`, the canary timeout/abort/trailing-slash/validation).
- The orchestrator change is additive + multiply-gated (`orchestrator.ollama.enabled` AND `stuckRunner.enabled`), so existing supervision behavior is unchanged when the model task or the detector is off.
