## The Problem

The workstation dock document stages `right-top-tabs: [metrics, audit]`. When `metrics` tears out into a vessel, `audit` becomes the region's remaining/active item — but on camera the region renders the tab header with a black void where the Evidence Audit card should be. A region whose sibling departed must present its surviving pane, not an empty body. The state persists across multiple frames (not a single staging frame), so this is not FLIP-transient.

## The Architectural Reality

- The pane factory (`apps/workstation/view/Workspace.mjs` `resolvePane`) returns cached LIVE instances to preserve identity across re-projection; the audit pane is one of the resident placeholder panes (`.workstation-placeholder` hosting `.workstation-resident-card`).
- Candidate seams, in classification order: (1) tab `activeIndex`/`removeDom` reconciliation when the sibling item leaves the collection (the hidden/removeDom repair patterns in `Neo.tab.plugin.Overflow.applySplit` document the two-surface trap: config says visible while a stale `removeDom` keeps the DOM absent); (2) dock projection re-parenting during the transfer leaving the surviving pane unmounted; (3) the pane instance surviving with `mounted: false` after the region churn (the `#16434` re-arm class, but for panes rather than the overflow control).
- Reproduction stage: the five-beat film run (`NEO_FILM_TAKE=1 … --headed`) or the plain headed scene-2 tear-out; observe the right-top region's DOM while the metrics vessel exists.

## Static classification — seam named, and a falsifiable prediction posted BEFORE the repro

Candidate seam **(1)** in your classification order, and the mechanism is sharper than "removeDom gets set": the survivor's **stale** `removeDom` is never cleared.

Posting the prediction first deliberately. If the headed run contradicts any step below, the reading is wrong and I would rather that be visible than quietly reconciled afterwards.

### The trigger condition is staged, not incidental

`apps/workstation/tour/denseWorkstation.mjs:48`

```js
'right-top-tabs': {type: 'tabs', items: ['metrics', 'audit'], activeItemId: 'metrics'}
```

**`metrics` is index 0 AND the active item.** That conjunction is what arms the defect — a tear-out of a *non-zero* or *inactive* index would not reproduce it.

### The chain

1. `removeInactiveCards: true` is the **default** on both `tab.Container:97` and `layout.Card:63`. So `audit`, being inactive, is sitting on `vdom.removeDom = true`.

2. `metrics` tears out → `TabContainer.removeAt(0, …, silent=true, keepMounted=true)` — the atomic cross-parent move path (`Container.mjs:636-637` documents exactly this transaction).

3. `Container.mjs:631-634` — `index (0) === activeIndex (0)`, so:

   ```js
   cardContainer.layout._activeIndex = activeIndex - 1;   // 0 - 1 === -1
   ```

   **There is no clamp.** Removing the active item at index 0 yields `-1`, not `0`.

4. `Container.mjs:638-640` then calls `applyChildAttributes(audit, 0, /* keepInDom */ true)`.

5. `layout/Card.mjs:151` — `isActiveIndex = (me.activeIndex === index)` → `(-1 === 0)` → **false**.

6. `layout/Card.mjs:160-167` — the `delete vdom.removeDom` on line 164 lives **only** in the `isActiveIndex` branch. The survivor fails that test, so its **pre-existing** `removeDom: true` is never cleared. `keepInDom` correctly stops line 166 from setting it again — but it was already set, and nothing removes it.

7. **Result:** `tabBar` holds the `audit` button (it renders), the card's DOM is absent. Header over black void.

### Why it persists across frames rather than self-healing

`Container.mjs:156` — `afterSetActiveIndex` is guarded by `Neo.isNumber(value) && value > -1`. At `-1` the entire body is skipped: no `cardContainer.layout` update, no `updateTabButtons()`, no `activeIndexChange` event.

So `-1` is a **silent no-op at the reconciliation layer**. Nothing re-arms the region until something else sets a valid index — which matches "the pane content returns in later frames" and confirms this is not FLIP-transient.

The guard reads as defensive and is doing the opposite: it converts an out-of-range index into *no reconciliation at all*, which is how the state gets to be both wrong and stable.

### Prediction to falsify at the empty moment

- `tabContainer.activeIndex === -1`
- `cardContainer.layout.activeIndex === -1`
- `auditCard.vdom.removeDom === true` while the card instance is alive and its config reads visible
- `tabBar.items.length === 1` (the audit button present — which is why the header renders)

That is the config/vdom/DOM triplet AC-1 asks for.

### Fix direction

`activeIndex - 1` must clamp while items remain — removing the active item at index 0 should activate the **new** index 0, not `-1`. Both branches need it (`:633-634` silent and `:643` non-silent); `-1`/null stays correct only when the container is genuinely empty.

Owner is `src/tab/Container.mjs`, not the app layer — consistent with your "no cosmetic patch at the app layer" instruction. I will check whether `layout/Card.mjs:164`'s clear-on-activate also wants to be unconditional, but the index clamp looks like the single root rather than two independent bugs.

## Correcting myself: I fixed a covering seam, not the firing one

My previous comment named `TabContainer.removeAt`'s missing clamp and called it *"the single root rather than two independent bugs."* **That claim is wrong**, and I found it by asking the question I should have asked before writing it: does the tear-out actually *call* the seam I repaired?

It does not.

### The firing path bypasses `TabContainer` entirely

`DockProjectionReconciler.mjs:667`:

```js
state.body.removeAt(state.index, false, true, true);
```

That is aimed at the **BodyContainer**. And `Neo.tab.BodyContainer` (40 lines, whole file) overrides **only** `remove(component, …)` — and even then only delegates to the parent `TabContainer` when `component?.isTab`. It does **not** override `removeAt`.

So the call lands on `Neo.container.Base.removeAt`, which:

- splices `items` and the vdom child
- calls `me.layout?.removeChildAttributes(item)` — for the **removed** item only
- reconciles **nothing else**: not `activeIndex`, not the surviving items' attributes

And `layout/Base.removeChildAttributes(item, index) {}` is an empty no-op that `layout/Card` never overrides. So on the path that actually fires, **nothing reconciles the survivor at all.**

### Proven, not reasoned

I added a case exercising the reconciler's exact call. With my clamp applied:

```
removing the active card via the BODY container leaves the survivor presentable
  Error: the only remaining card must not stay DOM-removed
  Received: true
```

**Still red.** The clamp cannot reach it.

### What that means for each claim

- **The symptom description stands** — survivor stranded with `removeDom: true` while the region renders its header. The two-surface trap is real and it is what the camera caught.
- **The mechanism I published was for the wrong caller.** `activeIndex → -1` is a genuine latent defect (its witness and three controls are green, commit `f04c30fa1a`), but it requires someone calling `TabContainer.removeAt` directly. The dock tear-out does not.
- **On the firing path the failure is worse, not different in kind:** `activeIndex` is never reconciled *at all*. A splice invalidates every index above the removal point, so an index-addressed layout is left pointing at whatever now occupies that slot — while the survivor keeps the removal marker it earned as the inactive sibling.

### Where the real owner probably sits, and the open question

`layout/Card` owns the meaning of "index N is active" and is therefore the thing a splice invalidates. The candidates:

1. `layout/Card` overrides `removeChildAttributes` to reconcile `activeIndex` and re-apply attributes to survivors (the removal hook already exists and is empty).
2. `container.Base.removeAt` re-applies child attributes generically after a splice.
3. `tab/BodyContainer` overrides `removeAt` to delegate upward, mirroring what `remove` already does.

I lean (1): it is the layout's own invariant, the hook exists, and it repairs every container using a card layout rather than only tab-owned ones. But `src/layout/Card.mjs` is shared surface with real blast radius, so I am not landing it at the end of a long session on my own read — I would rather have a second opinion on the owner than be fast and wrong twice in one ticket.

Keeping the clamp: it is a real fix with its own red-proof, and it is not made redundant by whatever lands for the firing path.
