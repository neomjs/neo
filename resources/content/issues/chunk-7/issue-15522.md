## The partition templates — bootstrap-ready content (drop-in for the storefront repo's `.github/ISSUE_TEMPLATE/`)

**`00-route.yml` (the chooser — the partition happens at filing time, not triage time):**

```yaml
name: Route my report
description: Engine-layer or product-layer? The template files it for you.
title: "[route]: "
labels: [needs-triage]
body:
  - type: dropdown
    id: layer
    attributes:
      label: What is this about?
      description: The partition question. Answer it once and your report lands in the right tracker.
      options:
        - "The product I downloaded (the cockpit, the cards, the app itself)"
        - "The engine it runs on (Neo.mjs — docking, harness shell, brain services)"
    validations: {required: true}
  - type: markdown
    attributes:
      value: |
        **Product-layer reports** (you picked the first option): stay here — file the rest of this template.
        **Engine-layer reports** (you picked the second): you're in the product's tracker; the engine lives at `neomjs/neo` — file there: https://github.com/neomjs/neo/issues/new/choose. This template closes itself.
```

**`10-product-bug.yml`** (the product-layer form — cockpit UX, cards, surfaces, first-run):
```yaml
name: Product bug
description: Something in the downloaded product misbehaves or reads wrong.
title: "[bug]: "
labels: [bug, product-layer]
body:
  - type: textarea
    id: seen
    attributes: {label: What did you see? (screenshots welcome; the cockpit's own surfaces in view if you can)}
    validations: {required: true}
  - type: input
    id: build
    attributes: {label: Version + install source (the zip you downloaded, or the storefront release tag)}
  - type: textarea
    id: expected
    attributes: {label: What should it have done instead?}
```

**`20-product-want.yml`** (the product-layer wish form): same shape, `labels: [enhancement, product-layer]`, with a "what task were you trying to do?" field (task-first framing — the addressee's workflow, not our internals).

**`99-engine-pointer.yml`** (the redirect stub): a one-field template that says "this belongs to the engine — file at `neomjs/neo`" and auto-labels `routed-to-engine` so the disposition metric (how many misrouted filings land here) stays measurable.

The anti-recurrence property: the blend never re-forms because filing IS the partition. The disposition table's 8 migrations move with their full history links into this template family. — Phoebe 🔆

## The release-receipt config — bootstrap-ready (consumes receipts, never mints authority)

The storefront's release surface is a **consumer of the monorepo's release receipts**, never a mint. The shape (drop-in when the repo exists):

**`release/RECEIPTS.md`** (the storefront's one release authority file, regenerated per monorepo release — a pointer, not a changelog):

```markdown
# {{PRODUCT}} — release receipts

{{PRODUCT}}'s installers are cut from the Neo.mjs organism's release line. This file records
WHERE the truth lives; it never re-mints version, notes, or hashes.

## Current: v13.x.x

- **Organism release notes:** [v13.x.x](https://github.com/neomjs/neo/blob/main/resources/content/release-notes/v13.x.x.md)
- **Atomic release hash:** `<the hash publish.mjs embeds in the notes — cite it, never restate it>`
- **Installers (macOS arm64, macOS x64, Windows, Linux):** attached to the organism's GitHub Release `v13.x.x` → https://github.com/neomjs/neo/releases/tag/v13.x.x
- **Provenance:** this product consumes `neomjs/neo` as a dependency (the published `neo.mjs` package); the FM wrapper/packaging is ADR-0034's own cadence, cut from the same release line.

## Update rule (mechanical, no authority)

On each organism release: update the version line + the two links. The hash is copied from the
release notes, never recomputed. If this file and the organism's notes disagree, **the organism
is right** — edit this file, never the notes.
```

**The config invariants (the receipt-consumption contract):**

1. **One authority:** `buildScripts/release/publish.mjs` in the monorepo is the ONLY release pipeline — the storefront has no release workflow of its own (no `release.yml` minting versions, tags, or notes).
2. **Receipts, not restatement:** the storefront's release page/artifacts LINK to the organism's release notes + artifacts; it may embed the atomic hash for verification but never recomputes or rewords it.
3. **Disagreement rule:** if the storefront's pointer and the organism's notes disagree, the organism is right — always.
4. **The download button's receipts:** when row 3 walks, the storefront's download button links to the organism's GitHub Release artifacts directly (or a CDN mirror of those exact artifacts with the hash shown beside the link) — never a re-packaged copy.
5. **The coherence obligation:** version mentions on the site/README/release page are `neo-identity-update` governed FACTS (single-source-derived from the organism's version), per the epic's AC.
