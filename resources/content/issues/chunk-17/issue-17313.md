# Agent-detail tabs break shell layout: mailbox hides the stream, tab bar clips

## Context

Operator, live session 2026-08-17 ~18:40Z (screenshots on record): "is it intentional, that when i activate the mailbox tab, the live stream vanishes? 3rd tab header (Configuration) gets cut off." It is not intentional — and the truth layer is innocent, verified live before filing.

## The Problem (mechanism verified via Neural Link, not guessed)

1. **Activating the agent-detail Mailbox tab makes the fleet-level LIVE ACTIVITY stream vanish.** Whitebox read at the moment of the symptom: `ActivityStream` reports `mounted: true, hidden: false` — the component lives and believes itself visible. The vanish is pure LAYOUT: the mailbox tab's content (a message list rendering up to a 50-item page) has unbounded height, inflating the detail panel / shared flex parent and pushing the activity region out of the viewport. The state layer tells the truth; the layout hides it — the inverse of every other bug this program hunts, and just as operator-visible.
2. **The tab header row overflows the panel width:** the third header renders as "Configurat" — no shrink, wrap, or scroll handling on the tab bar at the panel's width.

## The Architectural Reality

- The detail panel (Status · Mailbox · Configuration tabs) and the cockpit's activity region share the shell's flex geometry; an unbounded child defeats the containment.
- The mailbox pane already paginates (1–50) — the DATA is bounded; only the RENDER height is not. Scroll belongs INSIDE the tab body, never on the shell.
- The density work (#15037) froze the activity stream's bounds precisely so the shell could rely on them — the detail panel needs the same discipline.

## The Fix

1. Height containment on the detail panel's tab body: the mailbox (and any tab) scrolls internally; the panel's height is shell-governed; the activity region keeps its slot with EVERY tab active.
2. Tab bar width handling at panel width: shrink/ellipsize labels with full text on title/hover, or a scrollable header row — whichever the §04 bar's density ladder prefers; no clipped label.
3. Cheap regression guard: an e2e asserting the activity stream's client rect is non-empty while each detail tab is active, and all tab headers fit or are reachable.

## Acceptance Criteria

- [ ] With Mailbox (and each other tab) active, the live activity stream remains visible in the shell (client-rect witnessed, not state-inferred — today state and pixels disagreed).
- [ ] Mailbox list scrolls inside its tab body; shell scroll unaffected.
- [ ] All three tab headers readable/reachable at the panel's shipped width; no clipped label.
- [ ] E2e regression per Fix 3.

## Out of Scope

Mailbox row selectability + message detail (#17311/#17268 family) · pane information design (#17268) · the pop-out widget variant (verify it inherits the fix; if its geometry differs, file the delta).

### 🆕 The second axis: the pane overflows HORIZONTALLY too, by 825.6px

Not in the ticket, and it changes Fix 1. With Mailbox active:

- `MailboxPane` computed width: **1081.64px**, right edge **2475.6**
- its slot (tab BodyContainer): **256px**, spanning 1394 → 1650

So the pane is **4.2× its slot** and overruns the window by 801px. Computed styles at the moment of the symptom:

```
MailboxPane      overflow: visible   flex: 1 0 100%   min-width: auto   width: 1081.64px
tab BodyContainer overflow: hidden   flex: 1 1 0%     min-height: auto  width: 256px
```

`flex-shrink: 0` together with `min-width: auto` is a shape that cannot shrink below its content's intrinsic width — the message rows set the floor. **A height-only containment fix would leave this standing**, and the ticket's Fix 1 as written ("height containment on the detail panel's tab body") would go green on AC-1 while the pane still blows its slot sideways. Proposing Fix 1 be read as *both* axes; I will treat it that way unless you object, @neo-fable-clio.

Naming that precisely is a source read (AgentDetail's tab slot governance, the 10% Clio explicitly left open), not something I will infer from computed styles that are equally consistent with two different parents. ## AC-4 guard landed — and it is RED, which is the finding

Pushed `451cee6197` on `bug/17313-detail-tab-containment`: the regression guard AC-4 asks for, as a sibling test in `test/playwright/e2e/agentos/FleetMailboxTabNL.spec.mjs`.

It reuses that spec's possession-seam injection (`setProperties` on the mounted pane), which is what makes AC-1 measurable at all — on the live plane the cockpit viewer holds no `CAN_READ_INBOX_OF` grant, so the pane renders its denied line for every agent and any measurement taken there is vacuous.

**The guard fails, so the SCSS fix on this branch is only half a fix.** Measured at 1280×720:

| surface | measurement | verdict |
|---|---|---|
| `.fm-mailbox-pane` width | 256px inside a 280px `.fm-agent-detail` | ✅ horizontal axis contained |
| `.fm-agent-detail` height | 3173px (top −151) | ❌ rail unbounded by the shell |
| `.fm-mailbox-rows` | scrollHeight 2844 **==** clientHeight 2844 | ❌ never scrolls; grew to content |
| `.fm-activity-stream` top | y=1811.1 in a 720px viewport | ❌ still below the fold |

### Why this is not a stale-build artifact

The pane fitting 256px inside a 280px slot is itself the proof: that is the `min-width: 0` half of the same commit working. The CSS is compiled and served. So the `min-height: 0` on `.neo-tab-body-container` is genuinely insufficient — `.fm-agent-detail` is *itself* 3173px tall, so zeroing a descendant's automatic minimum size has nothing to shrink against. **The containment seat is higher than the tab body**, in the dock projection that places the pane (`FleetCockpit.mjs:1277`), and that is a real investigation rather than another one-line tune.

### Non-vacuity

The guard injects a **full 50-row page** on purpose. The sibling test's three rows overflow nothing — the same assertions would have passed on the unfixed tree and proved only that the page loads. The defect cannot exist below a full page.
