# Arm the plane-bearer alias teeth on the host dev journey (`NEO_MCP_HEALTHCHECK_TOKEN_FILE` host-side)

**Follow-up to #17286 (dormancy recorded [here](https://github.com/neomjs/neo/issues/17286#issuecomment-5314047209), surfacing in @neo-opus-vega's APPROVED review of PR #17287).** The assert variant now guards the dev entry's plane credential, but its alias *teeth* are host-side dormant: nothing on the host launch path exports `NEO_MCP_HEALTHCHECK_TOKEN_FILE`, so the admission-token comparison skips and the assert behaves like the bare resolver on the stock dev journey.

## Context

`fleet.admissionTokenFile` binds `NEO_MCP_HEALTHCHECK_TOKEN_FILE`. Every setting in the tree is a Compose file with a container path (`docker-compose.yml:618`, `local-agent-os.yml:15`, `parity-capture.yml:58/90`, `dev.yml:125`); the bootstrap/healthcheck PAT is provisioned at deploy time as a file-backed Compose secret. Meanwhile the host-side diagnostics (`ai/scripts/diagnostics/mcpHealthcheck.mjs`, `fleetHealthcheck.mjs`) already accept the same env var / `--bearer-token-file` as a HOST path — so a host-readable reference to the token is an established pattern, not a new custody class in principle.

## The Problem

The credential-class ledger's alias refusal (a plane bearer that IS the deployment's admission token fails boot) is proven in Compose profiles and dormant on the exact journey where aliasing is most plausible by hand: the operator's host dev journey targeting the containerized plane (#17276's `cockpit:live` / `ai:fleet-server`). A deployment copied together carelessly — same token exported into both roles on the host — boots clean today on that journey while production would refuse it.

## The Fix (investigation first, then the smallest honest wiring)

1. **Answer the custody question:** does a host-readable copy or reference of the admission token legitimately exist post-provisioning (the deploy reads it from somewhere — `ai/deploy` env handling)? If the design answer is *the host must never hold it*, record that as the disposition and close — dormancy then becomes a documented design property, not a gap.
2. **If provisionable:** the dev launch path (the `cockpit:live` composition and/or the standalone `ai:fleet-server` journey) exports `NEO_MCP_HEALTHCHECK_TOKEN_FILE` pointing at the host-readable copy when — and only when — the journey targets a containerized plane. No copying the secret into a new location; the export names the existing custody home. The assert then self-arms with zero code change (`assertFleetPlaneBearerClass` already reads the leaf).
3. Witness: a host boot with the file exported + an aliased plane bearer fails with the named ledger refusal; with distinct credentials, boots plane-side.

## Decision Record impact

`aligned-with ADR 0019` (the leaf already exists and binds the env var; this is consumption, not new config) · may cite ADR 0038 §2.5.1 (the S6 credential ledger) for the custody ruling.

**AC-1 custody ruling: PROVISIONABLE — the host-readable home already exists as the SOURCE of the container secret, not a copy.**

**Evidence (live `dev`, verified this session):**
- `ai/deploy/docker-compose.local-agent-os.yml:149` sources the secret: `${NEO_MCP_AUTH_TOKEN_FILE:-${HOME}/.neo-ai/secrets/mcp-auth-token}` — the host path is the custody origin; Compose mounts it into containers as `/run/secrets/mcp-auth-token`.
- The documented provisioning flow (`ai/scripts/lifecycle/local-agent-os/README.md:96-112`) materializes exactly that host path.
- Host-side consumers accepting the same env var as a HOST path already exist (`ai/scripts/diagnostics/mcpHealthcheck.mjs`, `fleetHealthcheck.mjs`), so naming the home is an established pattern.
- Design-constraint precedent: host-source vs container-target are separately named contracts (the backup-root shape, ADR 0038 §10.9's paired-rule); here the host-source contract name already exists: `NEO_MCP_AUTH_TOKEN_FILE`.

**Design (smallest honest wiring — AC-2 path):**
1. `devCockpit.mjs` (launcher = deployment-input territory, same family as `resolveLivePlaneConfig`) gains a pure resolver with precedence mirroring the Compose interpolation exactly: operator-pinned `NEO_MCP_HEALTHCHECK_TOKEN_FILE` wins untouched → else `NEO_MCP_AUTH_TOKEN_FILE` (the deployment override) → else the canonical home `${HOME}/.neo-ai/secrets/mcp-auth-token`.
2. In live mode only — after the plane-identity probe succeeds, i.e. when AND ONLY WHEN the journey targets a containerized plane — `buildFleetChildEnv` sets `NEO_MCP_HEALTHCHECK_TOKEN_FILE` in the fleet child's env alongside the plane binding. Webpack child untouched; in-process journeys untouched; no secret material copied anywhere.
3. Zero changes to `devFleetServer.mjs`/`fleetServer.mjs`: the assert at the entry's credential site self-arms from the leaf it already reads.
4. Boot log names the source (pinned / compose-override / canonical-home) and warns named when the file is unreadable — matching the assert's documented degrade-only semantics for an unreadable comparison file.
5. Witness: spawned dev-entry boot with an aliased bearer + armed binding refuses pre-network with the ledger's named error; distinct credentials pass through. Rendering ratchet spec pins the JS default and the Compose default to the same string so they cannot drift.

Standalone `ai:fleet-server` journey: documented export guidance in RunningTheFleetCockpit.md (no launcher owns that path).

ADR-0019 re-read done: the literal lives outside any leaf because it is a deployment-edge constant consumed at the spawn boundary (the `CANONICAL_LOCAL_PLANE_BASE` precedent), never a competing resolver for leaf-bound config.
