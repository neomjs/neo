Resolves #16290

Related: #16267

The receiver route probe is now a runnable command with a required negative control, instead of prose that returns a false negative for every input.

Evidence: L3 (the literal documented command run against two live receivers, with held-route, absent-route, and control cases all confirmed) → L2 required (the close-target ACs are documentation content). Residual: none [#16290].

## Deltas from ticket

None. The one judgement call the ticket left open — whether to also lint runbooks for runnable-command coverage — stayed Out of Scope: it is a different substrate and should not ride a doc fix.

## The defect, briefly

`receiver.mjs:236` reads the subscription id from the `x-neo-wake-subscription-id` **header**. The runbook said only *"POST with a deliberately wrong signature: `401` means the receiver holds the route, `404` means it does not"* — no command, no header. Following it keys the lookup on `undefined`, so the receiver answers `404 unknown-subscription`, which is byte-identical to a genuinely absent route.

I wrote that prose this afternoon and it misled the first person to use it, four hours later, which was me. I probed two live receivers, got `404` for every id including a route that was actively delivering wakes to my own seat, and was one step from reporting "neither receiver holds any routes."

The **bogus-id control** is what caught it: it also returned `404`, which proves the probe is not discriminating rather than that the route is absent. That is why the control is documented as required rather than suggested — it is the only thing that separates a broken probe from a broken receiver, and its absence is invisible.

## Test Evidence

**Live receipt (L3) — the literal block from the runbook, copied verbatim and run:**

```
held route   (ada  on :3199)  -> 401
absent route (iris on :3199)  -> 404
REQUIRED control              -> 404
```

That is the ticket's final AC discharged directly: `401` for a held route, `404` for both an absent route and the control. The same command against `:47101` returns `401` for both real ids, which is how the two-receiver topology was established in the first place.

## Post-Merge Validation

- [ ] Next peer who needs the probe uses it from the runbook without asking. That is the only real test of whether the header requirement is now discoverable, and it is unobservable from CI.

## Evolution

This exists because a self-check I published as prose failed the first person who followed it. The repo's own executable knowledge was already correct — `receiver.spec.mjs`'s reload specs drive the proper header form — so the human-facing copy had silently diverged from the tests beside it.

The generalisable part is not the header. It is that **a diagnostic published without its negative control is not a diagnostic**: a probe that answers `404` for everything looks exactly like a correct probe reporting absence, and nothing in the output distinguishes them. I had documented the interpretation (`401` holds, `404` does not) without documenting the check that makes the interpretation trustworthy.

What I would defend: keeping the control mandatory rather than "recommended". The failure it catches is silent and confident, which is the class that costs the most.
