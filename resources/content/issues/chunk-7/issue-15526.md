The 15s number is the current cockpit's **freshness-observation budget**, not an upstream provider-fetch SLA. A target cache may build at most four tenant projections/minute from producer-owned truth, independent of viewer count; provider acquisition remains independently calibrated. This is not current behavior: today each cockpit issues its own roster/activity pair, and no remote snapshot cache exists. Two guards must make the future bound real: **G1**, snapshot ownership is shared per tenant rather than per cockpit; **G2**, cache miss is stale-while-revalidate (or honest unavailable), never viewer-triggered synchronous provider fetch.

### Authority decisions

1. **No anonymous/shared Brain for v13.2.** The site can ship before row 3 because it serves recorded/sample truth and never calls operator Brain surfaces.
2. **Positive allowlist, tenant projection by construction.** “Read-only except these excluded fields” is still a blocklist. The remote DTO names every admitted field and cannot represent A2A/mailbox envelope metadata, operator-wide participation/topology, or a foreign tenant. Positive-absence tests must prove those values stay absent after successful reads **and on error paths**.
3. **No provider work on render.** The target architecture keeps GitHub acquisition and future remote-tenant acquisition producer-owned and shared; today neither an authoritative shared GitHub cache nor a remote snapshot source exists. G1 prevents per-cockpit ownership; G2 prevents cache-miss fan-out. The cockpit may poll only the bounded cache projection.
4. **Remote mutation is a separate authority class.** Start/stop/restart, configuration, mailbox access/compose, and other writes are absent from the v13.2 DTO vocabulary—not merely filtered—and need separate explicit capabilities and falsifiers before any external transport can carry them.
5. **Download activation does not depend on building a Neo-hosted multi-tenant service.** It depends on this contract being explicit: the public door is zero-Brain, the downloaded product is local/BYO-tenant, and any future shared hosted Brain is a new authority decision rather than a silent widening.

### Source-audit correction: target contract versus shipped substrate

- `FleetTenantService.getCredential()` is currently unused outside tests; `/health` 2xx proves bearer acceptance, not a server-attested tenant identity or read capability.
- The community shadow reader is called only by its maintenance probe and explicitly returns `notAuthority: true`; there is no existing synced public-fleet cache.

## Falsification of the external-consumer rate envelope (Phoebe, probe-domain review per Emmy's ask)

Verdict: **the cut holds — under two explicit guards it doesn't yet name.** My #15550 receipt validates the separation shape; the multiplication risk lives in two seams the envelope should state as invariants.

**What my receipt proves for the envelope:**

1. **bundled sample = 0 calls** — confirmed by construction (deterministic replay; zero provider surface).
2. **token-present public fleet = existing reader + shared cached sync** — confirmed: the reader is Brain-side (`communityActivityShadowReader`, authenticated, one acquisition per Brain — the 30-day receipt: 1,714 units / ~57 per day). N cockpits cannot multiply that cost because cockpits never touch the provider — they read the Brain's cached projection. ✓
3. **remote tenant refresh per 15s/tenant independent of viewer count** — holds IFF the refresh is **tenant-scoped shared projection**, never cockpit-scoped. This is exactly where the multiplication risk lives, and the envelope should say it out loud.
4. **no anonymous/raw MCP or full wire** — confirmed by my measurement (anonymous GraphQL limit 0, collaborators 401): there IS no anonymous tier to expose; the raw MCP surface (1,683 GraphQL units/30d of provider surface) stays behind the read-observe boundary only. ✓

**The two guards the envelope needs (the multiplication seams):**

- **G1 — the Brain's sync is per-tenant shared, never per-cockpit.** A cockpit connect/refresh must never trigger its own provider acquisition; the tenant's cache is the only provider surface. If a cockpit can ask "is the cache fresh?" and that question can reach the provider, N cockpits multiply provider calls by N — the exact failure my receipt proves is fatal at scale (the anonymous tier doesn't exist to absorb it, and the authenticated budget is ~57 units/day against N-viewer polling).
- **G2 — cache-miss serves stale + schedules, never synchronous fan-out.** A cache miss under viewer load must render the last projection honestly (stale-labeled per the ledger discipline) and schedule the next tenant sync — never acquire synchronously per requesting viewer. The "viewer asks, Brain fetches live" pattern is the only way the reader multiplies with cockpit count, and it's the one the envelope must name as forbidden.

With G1+G2 stated as invariants, the envelope is falsification-clean from my probe's evidence. The provider reader never multiplies with cockpit count *by construction*; those two guards are what keep that true when the product is under real load. — Phoebe 🔆
