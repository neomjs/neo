## The defect

**An empty tenant repo could never sync, and could never recover.** `IngestionService` mints a materialization receipt only on positive effect, so for `ingested: 0, deleted: 0` the `provesUncommittedRetry` escape needs a receipt that will never exist:

```js
provesUncommittedRetry = validReceipt && …          // validReceipt is false: no receipt was minted
if (!hasEffect && !provesUncommittedRetry) throw …EMPTY_MATERIALIZATION
```

The guard throws → the checkpoint never commits → `lastCommittedMaterializationAttemptId` is never recorded → **the escape can never engage on any later attempt either.** The loop has no exit, and the population is **new tenant onboarding**.

## The discriminator was already on the envelope

`manifestSnapshot.pathsAfterPush` is what the repo carries after the push, so an **empty array is a positive statement** that there is nothing to ingest — not a proxy for one.

Evidence: L1 structural + unit achieved (1,395 passed across `ai/daemons/orchestrator/`, three RED→GREEN witnesses, positive control preserved) → no L3 receipt outstanding; the guard is pure and driven through the real `runTask` seam.

**It is trustworthy at this guard, and that is checkable rather than assumed:**

```js
// tenantRepoIngestEnvelopeBuilder.mjs:186
async function listRevisionPaths({gitMirror, identity, revision}) {
    try { return await gitMirror.listRevisionPaths({...identity, revision}) }
    catch (error) { throw createIngestEnvelopeError('KB_INGEST_ENVELOPE_LIST_FAILED', …) }
}
```

Enumeration failure **throws**; it never degrades to `[]`. Without that, "empty manifest" and "broken clone" would be indistinguishable and this repair would be unsafe.

## A third case surfaced while verifying the second

`summary.ingested` counts **embeddable** chunks only, and an oversized chunk increments `skippedOversized` instead of joining that array (`IngestionService.mjs:257`, `:1411`). So a repo whose every chunk exceeds the safe band reported *"produced no durable positive-effect proof"* — telling an operator **nothing arrived, look at the embed stage**. Everything arrived, the embed stage never saw it, and re-ingesting cannot help because the chunks are the same size next time.

That is the same mislabelling #16863's split was filed to end, one case over. It now carries **`KB_TENANT_REPO_SYNC_CONTENT_NOT_EMBEDDABLE`** and **still fails closed** — a repo whose content cannot be embedded is not synced, and calling it `completed` would make a broken tenant read as healthy. Whether it should instead commit is a product judgement, recorded as open on the ticket rather than decided here.

| 1 | **empty** | 0 | 0 | `EMPTY_MATERIALIZATION`, permanent backoff | **`completed` + commits** |

| 3 | non-empty | 0 | > 0 | `EMPTY_MATERIALIZATION` (wrong instruction) | `CONTENT_NOT_EMBEDDABLE`, still fails |

**Two conditions on the new arm are load-bearing, and a red test found each of them — not reasoning:**

- `!provesUncommittedRetry` — a delete-only repo also declares no content, and on a retry after a checkpoint-write failure its effect is already applied, so `hasEffect` is false while a valid unacknowledged receipt waits to be settled **exactly once**. Returning early dropped the receipt the caller records. Without this condition, #16045's settle-once test goes red.
- `!priorState?.lastCommittedMaterializationAttemptId` — narrows the arm to a repo that has **never** committed an attempt, which is precisely the state AC-2 describes. A repo that has committed one and later reports no content is a different question; a replay with an already-committed receipt is refused today and stays refused. Without this condition, the stale-receipt replay arm goes red.

I found both by running the suite rather than by inspection, and both would have been silent contract breaks.

## One existing scenario changed deliberately

The `bootstrap` row of the fails-closed table carried `manifestPaths: []` — the **only** row that did not match the table's own fixture (`'source exists but parser materialized nothing'`), and it asserted exactly the behaviour #16577 calls a defect.
