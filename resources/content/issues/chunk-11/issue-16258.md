# Wake webhook routes go silent after Memory Core restart

## Context

During the Docker-canonical cutover in #16167, signed <code>a2a-webhook</code> delivery worked before the Memory Core stop/start: the host receiver recorded and visibly delivered a wake. After Memory Core restarted at 2026-08-01T12:04Z, high-priority A2A sends continued to return <code>status: sent</code> and their <code>MESSAGE</code> / <code>SENT_TO</code> / <code>DELIVERED_TO</code> facts appeared in GraphLog, but:

- Memory Core emitted no coalescing or webhook-delivery log for those events.
- The host receiver recorded nothing newer than the pre-restart delivery.
- The durable SQLite <code>WAKE_SUBSCRIPTION</code> row remained active with the same webhook route.

This separates mailbox persistence from last-mile wake delivery. No container mutation was used to diagnose it.

Live latest-open sweep: checked the newest 20 open issues at 2026-08-01T12:43Z; no equivalent current ticket exists. Semantic and historical sweeps found closed <code>#10717</code> and <code>#11182</code>, which repaired the opposite API/cache split and earlier zero-delivery recurrences. This is a new restart-boundary successor, not a reopening.

## The Problem

<code>WakeSubscriptionService.pump()</code> promises to evaluate every active Shape A/B route after a mailbox projection. It calls <code>_warmPushSubscriptions()</code> before selecting active subscriptions, but that helper iterates only <code>GraphService.db.nodes.items</code>.

After a Memory Core restart or restore, durable <code>WAKE_SUBSCRIPTION</code> rows can exist in SQLite without being present in that in-memory graph collection. The pump then sees zero active push routes and advances its live GraphLog cursor past the event. A later caller-owned <code>manage_wake_subscription({action: 'list'})</code> can hydrate the row, but cannot restore an already-consumed event without an explicit replay.

The result is a healthy mailbox with silently dead webhook wakes precisely after the restart boundary where durable subscriptions are meant to survive.

## The Architectural Reality

- <code>ai/services/memory-core/WakeSubscriptionService.mjs#pump</code> is the low-latency Shape A/B consumer.
- <code>_warmPushSubscriptions()</code> currently reads the hot graph collection only.
- <code>_listDurableSubscriptionsForOwner()</code> already demonstrates the SQLite-first parse/hydrate pattern for the public list path.
- <code>MailboxService._projectMessageWalRecord()</code> invokes the pump only after the durable projection, so the event source is present.
- Shape C bridge daemons independently tail durable GraphLog/SQLite state and are not the owning substrate for this defect.

The Agent OS structure-map gate was attempted with <code>--files --loc</code> and hit its existing maximum-string failure. The targeted source census still identifies <code>ai/services/memory-core/WakeSubscriptionService.mjs</code> and its existing durable hydration helpers as the owning sibling pattern.

## The Fix

Make <code>_warmPushSubscriptions()</code> enumerate active <code>mcp-notifications</code> and <code>a2a-webhook</code> subscriptions from durable SQLite first, hydrate/refresh the hot caches, and invalidate cached push routes whose durable status or target changed. Preserve the current in-memory fallback for isolated tests without raw SQLite storage.

Do this before the pump decides that no active push subscriptions exist or advances its cursor.

## 2. My row cannot produce a route at all — no `signingKey`, and no repair path

Confirmed in production rather than inferred:

```
13:11:33.116Z [ERROR] WebhookDeliveryService: Subscription WAKE_SUB:84dfc4da-… is missing signing key; refusing unsigned Shape-B delivery.
```

The absence is real, not a projection artifact — `list` does not redact, it spreads verbatim (`{id: node.id, ...props}`). And three repair doors are closed:

- The key is minted **only** in `subscribe()` on the **new-row** branch (`crypto.randomBytes(32)`, `WakeSubscriptionService.mjs:975-979`).
- `subscribe()` with a matching existing route returns `{status:'existing'}` at `:963-966` — **before** the mint. `_refreshExistingSubscriptionRoute` merges filters/metadata only, so re-subscribing does not restore a key.
- `update()` cannot mint one, and a client-minted key defeats the property the generator depends on: it reads the *server-issued* key and fails closed on disagreement.

Short of unsubscribe + re-subscribe — which mints a **new subscription id**, and the id is what the manifest, delivery receipts and `#16246`'s degrade all key on — a Shape-B row lacking its key is permanently undeliverable.

**This is a distinct silent mode, and the most complete one.** `deliver()` refuses unsigned Shape-B and returns `'skipped'` **before** `_recordConsecutiveFailure`. So no attempt is recorded, no failure counted, no threshold reached, and **no degrade ever fires** — my own `#16246`/`#16253` work never engages. The row reads `status: 'active'` everywhere, `checkSunsetted` calls it active, and the heartbeat exclusion never triggers.
