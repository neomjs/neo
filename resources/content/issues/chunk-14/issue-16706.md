# Root cause — `[MEASURED]` 2026-08-11 13:40Z from the orchestrator container log

**A single KB tenant-ingestion embedding batch exceeds the 30-minute provider timeout and retries 5×. That is the 400%.**

1. One batch ("batch 7") takes >1,800,000 ms; retried 5× ⇒ ~2.5 h continuous embedding for one batch.
2. Every retry re-buys the identical work (#16963 → fixed by #16964).
3. It holds the single `OLLAMA_NUM_PARALLEL=1` slot, so the KB canary's 30-second probe can never acquire it ⇒ probe-timeout streak 27 ⇒ the KB is health-gated out of its own tools.
4. The two waiting repos die at the concurrency gate (39 and 46 consecutive failures).
5. A warm loop fires into the saturated slot every ~5–11 min at `num_ctx 32768`.

**Why a batch takes >30 minutes when one embed takes 150 ms: batch size, not hardware.** `[SOURCE-READ]` The running host resolves the batch size **empty → shipped default 50**; measured on comparable CPU inference, a 14-chunk batch took 8m25s — 50 puts a single batch at the ceiling, and **a batch that cannot finish stores nothing**. The release compose defaults it to **5**.

# The upstream anchor — `ollama/ollama#11889`, with its honest bounds

`[MEASURED]` **The provider does not observe cancellation while it waits: abandoned work keeps computing.** The frozen witness aborted a `node:http.request({signal})` — socket already destroyed — and the runner still held 397–400% CPU with **zero established sockets**. At `NUM_PARALLEL=1` the runner slot is then dead to all work. Live confirmation from host telemetry 2026-08-12 09:19Z: the pinned task is the **embedding runner at 401% CPU with 101h50m accumulated CPU time over a ~25h container life** — four cores for its entire life — while the chat runner idles at 0%.

> ### 📐 READ THE 400 % CORRECTLY — added 2026-08-10 08:2xZ, and it changes which lever you reach for
>
> **`~400 %` is almost certainly your container's CPU *cap*, not a measure of how much work is happening.** The shipped model service is capped at:
>
> ```yaml
> cpus:   "${OLLAMA_CPU_LIMIT:-4.0}"
> memory: "${OLLAMA_MEMORY_LIMIT:-48g}"
> ```
>
> `4.0` CPUs is exactly `400 %` in `docker stats` / `glances`. **So "400 %" means "pinned at its ceiling" and tells you nothing about whether the work is real.** Two very different states produce the identical number, and the discriminator is *duration*, not magnitude:
>
> - **legitimately busy** — a runner at the cap that returns to ~0 % between requests;
> - **stuck** — a runner at the cap **continuously**. Re-measure with `TIME+` from `top`/`glances` rather than the instantaneous percentage: divide accumulated CPU-time by the percentage to get wall-time, and compare that against container uptime. On the observed plane this was **185:56:12 of CPU time at ~398 %, i.e. 46.7 wall-hours out of a ~48-hour uptime — pegged for 97 % of its life**, while the KB container sat at **0 % CPU** with an **empty** corpus. Nothing was asking it to work, and it never stopped.
>
> **The second thing the cap tells you, and it is the actionable one: your embeddings are slow by CONFIGURATION, not by hardware.** A 64-thread host running at 7 % is giving the model **four** of those threads — and with `OLLAMA_MAX_LOADED_MODELS=2` plus `OLLAMA_KEEP_ALIVE=-1`, a chat model and an embedding model are both resident and **competing for the same four**.
>
> **That single fact drives the timeout problem underneath everything else.** Every deadline in Neo's embedding path is sized for a model that answers in seconds. On four shared CPU threads a cold embed can take tens of seconds — and **an embedding request that is abandoned mid-flight is what strands the runner in the first place** (`#16853`). So the cap does not merely make things slow; **it manufactures the aborts that cause the wedge, and the wedge then holds the cap at 100 % forever.**
>
> **Three levers, in the order that gives the most relief per unit of risk:**
>
> | lever | what to do | why it is first/second/third |
> |---|---|---|
> | ~~**1. Raise the CPU cap**~~ | **RETRACTED — do not.** | See the correction box; on a plane with no embedding work to speed up, this enlarges the freeze instead of removing it. |
> | **2. Raise the embedding deadline** | `NEO_OLLAMA_EMBEDDING_TIMEOUT_MS` (default `300000`) | Headroom while the cap change takes effect. **Note it only became settable on a containerized plane very recently** — before that fix it could not reach the container at all, so if you tried to set it previously and saw no effect, that is why. |

>

And **verify the parallelism knobs are actually applied** — the profile pins `OLLAMA_NUM_PARALLEL=1`, but a deployment running an un-recreated container can be on ollama's auto-default instead, which multiplies both threads and KV cache:

> ```
>

|---|---|
| ~4 cores pinned for days | the runner itself |
| the corpus never ingests | every embed request is sent to a runner that never answers |
| Memory Core `unhealthy` while its process is alive | its provider-dependent canary fails, because the provider is the stuck runner |

## Measured receipt — CPU-only plane, revision `3f9f8343a8`, 2026-08-10 15:15–15:39Z

Recording this on the Epic because it lives in a container log tail that does not survive the next recreate, and it is the evidence base for the whole deadline/batch family. All of it read from the provider's own access log and the deployment-state snapshot.

### The provider completes the work. We throw it away.

```
15:24:25 | 200 | 8m23s | POST /api/embed
15:24:26 | 200 | 4m59s | POST /api/embed     <- succeeded by ONE second
15:24:26 | 200 | 3m24s | POST /api/embed
15:32:46 | 200 | 8m19s | POST /api/embed
15:35:26 | 400 | 5m0s  | POST /api/embed     <- aborted at exactly the 300000ms default
```

**Four of five returned `200`, and both stores still read `0`.** The server finishes at 8m23s and returns success into a connection the consumer abandoned at 5m00s. The record stays pending, the repo's `consecutiveFailures` increments, the backoff doubles. Completed provider work is discarded on every cycle.

This is the concrete shape of "an abort leaves work stranded": not only does the runner keep computing, the *result* is produced and dropped.

### The unit cost is per chunk, not per byte

Memory Core's WAL batch of **14 records took 503s** → **≈36 s per chunk** on this hardware, with a 31b chat model resident alongside the embedder under a 4.0-CPU ceiling.

That single number reframes the family:

| batch size | projected | vs ceiling |
|---|---|---|
| 5 | ~3 min | fits comfortably |
| 14 (measured) | 8m23s | fits only above 300s |
