# Repeated splitter drags desynchronize grid headers and cells

## Context

Repeated real horizontal DockSplitter drags in Workstation produced a 100k Matrix state where the grid still paints, but its header and body no longer share column geometry. The captured frame shows a common outer left edge while the internal boundaries diverge progressively: header columns are narrower than their body cells, and the final body column is clipped at the common right edge.

This is a follow-up to the `#16353` investigation, not scope for PR #16370. It is also distinct from the drag-start wedge in `#16365`.

## The Problem

After several committed splitter resizes, header labels can stop sitting above their corresponding cells. The screenshot proves rendered disagreement; it does **not** prove whether the stale surface is the header, the body, or an upstream width generation.

A grid that continues repainting with mismatched column geometry is both visually broken and dangerous for interaction: users can read or target the wrong apparent column.

## The Architectural Reality

- `src/grid/Container.mjs:1182` handles resize by updating mounted body columns and the header toolbar in separate phases.
- `src/grid/header/Wrapper.mjs` owns header-region projection; `src/grid/Body.mjs` owns body-cell geometry and caches.
- `#12955` has a similar visible header/cell mismatch after **column drag**, while `#12929` covers a uniform scroll-offset mismatch. Neither establishes the cause of this splitter-resize case.

## The Fix

1. Reproduce with a bounded series of real splitter drags, waiting for committed document and FLIP settlement after each drag.
2. Capture a dataField-keyed geometry matrix after every commit: worker column width/x, header DOM left/width, first visible body-cell DOM left/width, container width, and scrollLeft.
3. Identify the first divergent owner/generation and repair that grid resize-propagation seam. Do not add Workstation-specific offsets or timing delays.
4. Retain a regression witness at the owning grid layer and at the headed Workstation surface.

## Acceptance Criteria

- [ ] A bounded repeated-splitter-drag sequence reproduces the pre-fix mismatch.
- [ ] After every settled drag, each visible header and corresponding body cell agree on left position and width within 1 CSS pixel.
- [ ] The witness records worker, header, and body geometry so the first divergence is attributable.
- [ ] Both drag directions and repeated cycles are covered without fixed-delay settlement.
- [ ] The `#16353` repaint witness remains green.

## Out of Scope

- Repaint liveness tracked by `#16353` / PR #16370.
- Intermittent drag-start failure tracked by `#16365`.
- Text selection during splitter drags tracked by `#16362`.
- Reopening historical column-drag fixes unless evidence proves the same mechanism.

Instrument discipline adopted for every run since: a positive-control observed element that must deliver at every phase, or the run aborts.

**The headed re-run (real Chromium, positive control green throughout) shows a per-spec pipeline:** one committed +160 drag → the deferred projection lands as plain flex-basis mutations (`neo-tab-container-2` flex `0.6 → 0.847724`, frame 83) → **the ResizeObserver delivers on that exact frame** (content 545.52 / border 547.52) → DockFlip plays entirely afterwards (invert f100, 280ms play, cleanup f102–103). No node replacement, no reparent, no fixed-stage, no inline width. Four consecutive committed drags (+160/−160/+120/−120, two launched deliberately inside the presentation window): **4/4 engaged, 4/4 committed, 4/4 RO-delivered correctly** (545.52/385.52/505.52/385.52).

**And yet the worker ends up poisoned — the REAL mechanism, witnessed:** at settled net-zero rest (page-side layout box back at 388, header toolbar 386), the worker holds `neo-grid-body-1.containerWidth = 476.77` and `availableWidth = 1328.72`. Both are impossible as layout values (1328 > the 1280 viewport; boot values 387.52/1080-class) — but both are exact **mid-FLIP transformed rects**: 476.77 ∈ (388, 508) = the final drag's scale-transition range, and 1328.72 / 1.3093 (that drag's inverse-scale at play start) = 1014.8 = a sane real column span. In-run control group: `neo-grid-body-2` (outside the FLIP'd panes) reads a clean 1256/1254.

**The writer, in source:**
- `grid.Container#onResize` (`src/grid/Container.mjs:1182`) receives the CORRECT transform-immune RO payload — and ignores its geometry, calling `passSizeToBody()` instead.
- `passSizeToBody` (`src/grid/Container.mjs:1262`) issues `getDomRect([container, header, footer])` — an async worker→main round-trip that reads `getBoundingClientRect` — and writes `containerWidth: containerRect.width` (`:1281`).
- `header.Toolbar#passSizeToBody` (`src/grid/header/Toolbar.mjs:336`) does the same per header BUTTON when any column width is dynamic, summing `rects[i].width` into `currentX` → writes `availableWidth` (`:381`) **and the per-column `columnPositions`** (`:354-361`) — the arrays both header buttons and body cells ride.
- These round-trips queue behind the commit's re-projection traffic (plus the 10/sec feed) and can land anywhere inside the ~660–950ms presentation window. When they land mid-transform, every rect is scaled fiction; the values overwrite the correct RO-delivered geometry and **persist** — the layout box never changes again, so RO stays rightly silent, and nothing re-measures at motion end.
- Downstream: `Body.mjs:1416` paints `vdom.width = availableWidth + 'px'` (body surface wider than the header element), mounted/visible column sets derive from poisoned `containerWidth` (my end-state grew a phantom 10th mounted column, cells to x=1624.8 in a 388px container), and scrollport math (`Toolbar.mjs:420-422`) mixes the two independently-poisoned values. That is the ticket's screenshot, derived: **header narrower than its cells, last column past the shared edge, worsening with repetition** — each commit re-rolls the race; some land in the safe exposed-Last phase (my drags 1–3 stayed visually coherent), some land mid-play and poison (drag 4).

**Companion defect exposed by the same timeline (DockFlip's own, widens the race window):** `hasPreservedMarkerSet` (`src/main/addon/DockFlip.mjs:136`) requires an ancestor-lineage CHANGE, which a same-node splitter resize never produces — so `play()` takes the replacement-tree branch and burns its full `maxFrames=15` rAF poll (~300ms) waiting for a detach that never comes, **exposing the committed Last layout for ~300ms, then visually snapping back to First and animating forward** (a visible double-take on every committed splitter drag, and +300ms of race window). A play-time discriminator exists: preserved node-identity set + geometry already changed ⇒ in-place re-layout ⇒ invert immediately.

**Fix-seam analysis (the seam is now chooseable):**
1. **Owning seam (grid measurement path): layout-size measurements must be transform-immune.** `offsetWidth/offsetHeight` read the layout box and ignore transforms by construction. `passSizeToBody`/header measurement want layout-size semantics exclusively (nothing here needs viewport-space coords) — a box-model option on the measurement primitive (or passing the already-delivered RO payload where available, with offset-metrics for the header buttons) removes the race for every present and future consumer. Vertical splitter commits poison heights identically (`scale(1, sy)` vs `availableHeight` at `Container.mjs:1280`) — same seam covers both axes.
2. **Companion (DockFlip):** the same-node-resize classification above — independent visual value (kills the double-take) and shrinks the window ~40%.
3. **Rejected:** gating grid measurement on the dock-motion signal — couples grid to dock, adds latency to every resize, and leaves any non-dock transform equally poisonous.

## Probe round 5 — the complete mechanism (two stacked defects), one round-4 claim corrected, and the repair: PR #16390

**Correction to round 4 first:** I attributed M1's minutes-long worker staleness to the hidden-pane rendering artifact. That was an overclaim, and the full-chain trace falsified it. The artifact was real — it explains why MY page-side observers went silent in rounds 2–3 — but the worker staleness has its own, environment-independent cause. Round 4's poison finding stands unchanged; its staleness attribution was wrong.

**The full-chain instrumentation** (temporary tagged logging across `main.addon.ResizeObserver` register/deliver + `grid.Container` onResize/passSizeToBody, main logs via page console, worker logs via Neural Link) produced the decisive trace on one boot + one bare flex re-layout + one committed drag:

1. Boot: mount arm registers the observer and measures 387.523 — but the register-time initial RO delivery **never reaches `Container.onResize`** (it races the worker-side listener routing; the addon fired main-side, no worker log).
2. First real re-layout: `onResize initialResizeEvent: true, width 546.98` → **the armed swallow consumed a real resize** — flag flipped, no measure, worker frozen at 387.5 while layout sat at 549 indefinitely.
3. Second re-layout: flag consumed → measured correctly.
4. Committed drag: `captureFirst` → `play` → onResize measure lands at **+293ms — deep inside the FLIP play window** — and (with the round-4 fix) returns layout truth 547.523. Pre-fix, this exact measurement was the gBCR poison writer (476.77 / 1328.72).

**So the ticket's mechanism is TWO stacked defects:**
- **D1 — the swallow (primary staleness, = M1):** `initialResizeEvent` unconditionally consumes the first post-(re)mount delivery, but the echo it exists to skip can lose its race and never arrive — so the flag eats the first REAL resize (the committed drag), and `containerWidth` freezes at the mount-time value until an unrelated resize. Environment-independent; also reproduces on `examples/grid/bigData` with a plain viewport resize (no dock, no transform — witnessed red pre-fix, green post-fix).
- **D2 — the poison (round 4, confirmed):** post-swallow drag deliveries DO measure — via async gBCR round-trips that land inside DockFlip's presentation window, persisting transform-scaled fiction into `containerWidth`/`availableWidth`/`columnPositions`.
- Repeated drags compound both: first drag swallowed-stale, later drags race-poisoned, every generation of column math riding corrupted geometry → the screenshot.

**The repair (PR #16390), both seams:** D1 → `onResize` classifies the first delivery against the mount-measured size and only skips a true echo. D2 → both `passSizeToBody` variants measure through a new transform-immune layout-box primitive (`DomAccess#getLayoutRect` / `component.Base#getLayoutRect`; computed used sizes normalized to border-box — additive, `getBoundingClientRect` untouched for viewport-space consumers).

**Witness receipts (two-sided):** new spec `WorkstationSplitterGridGeometryNL` — a deterministic race-free reproducer (static ancestor scale + the projection's own flex-pair mutation as trigger, premise self-validating) + the ticket's own recipe (4 committed real drags, both directions, per-settled-drag worker↔header↔cell attribution matrix, zero fixed delays). Pre-fix: 3 targeted reds (deterministic + drag-1 swallow + bigData). Post-fix: all green; coupled regression set green (`HeaderCellRectSync`, `BigDataNL`, `WorkstationNL` drag test; the zero-rect staged-frame failure in `WorkstationNL`'s second test reproduces identically with the fix stashed — pre-existing `#16356`-class).
