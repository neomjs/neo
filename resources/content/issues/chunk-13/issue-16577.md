# An empty first materialization is indistinguishable from a broken one, and backs off forever

## Problem

A tenant repo whose first materialization yields zero chunks **can never reach a completed state**. It fails, backs off exponentially, and retries forever — and nothing in the logs says why it produced nothing.

Observed live on the canonical plane, first sync of a freshly registered tenant (`neo-shared/create-app`, #16573):

```
00:53:45  Refreshing neo-shared/create-app
          ...99 seconds, no output...
00:55:24  ERROR create-app failed: KB_TENANT_REPO_SYNC_EMPTY_MATERIALIZATION
          ("Tenant-repo full materialization produced no durable positive-effect proof.")
```

### Defect 1 — the guard cannot distinguish "nothing to ingest" from "the pipeline did nothing"

`TenantRepoSyncService.assertFullMaterializationEffect` (`:294-317`):

```js
hasEffect = [summary.ingested, summary.deleted].some(v => Number.isSafeInteger(v) && v > 0),
provesUncommittedRetry = validReceipt
    && receipt.attemptId !== materializationAttempt?.attemptId
    && receipt.attemptId !== priorState?.lastCommittedMaterializationAttemptId;

if ((hasEffect && !provesCurrentAttempt) || (!hasEffect && !provesUncommittedRetry)) throw
```

On a **first** sync there is no prior receipt, so `validReceipt` is false and `provesUncommittedRetry` is **structurally false**. Therefore `!hasEffect` alone throws. Any repo whose first materialization legitimately produces zero chunks — an empty repo, a scaffolding repo, one whose content matches no configured Source/Parser — is treated identically to a silently-broken pipeline.

The guard's intent is sound: catch a full materialization that claimed success while doing nothing. But it conflates two states that need opposite responses:

| state | correct response | current response |
|---|---|---|
| repo has no ingestable content | completed no-op, or a distinct "nothing matched" signal; checkpoint advances | **failure + exponential backoff, forever** |
| pipeline silently did nothing | failure — the guard's real purpose | failure ✅ |

Because the checkpoint never advances, the repo also never acquires the receipt that `provesUncommittedRetry` needs. **The failure state is self-perpetuating by construction.**

### Defect 2 — the materialization phase reports nothing about what it materialized

99 seconds elapsed between `Refreshing` and the error, with no intermediate log line. Nothing states how many files the envelope carried, how many chunks were produced, or which sources ran. So the operator cannot tell whether:

- the envelope was empty (a config/source-matching problem), or
- the envelope had files and ingestion dropped them all (a code problem).

Both produce the identical error and the identical silence. This is what made the live diagnosis stop at "unknown" instead of a cause.

## Acceptance criteria

- [ ] A first materialization that legitimately yields zero chunks is distinguishable from one that silently did nothing, and does not enter permanent exponential backoff. Whether that is a `completed` no-op, a distinct `KB_TENANT_REPO_SYNC_NO_MATCHING_CONTENT` code, or an advancing checkpoint is the design call this ticket makes — record which and why.
- [ ] The self-perpetuation is broken: a repo in this state can reach a terminal, non-retrying disposition without manual intervention.
- [ ] The materialization phase logs its inputs and outputs — at minimum envelope file count and chunk count — so an empty envelope is distinguishable from a dropped ingest **from the log alone**.
- [ ] `assertFullMaterializationEffect`'s existing purpose is preserved: a claimed-success materialization with no durable effect and no valid retry receipt still fails. Coverage for that path must not be weakened.
- [ ] Reproduction: registering any repo with no matching content reproduces the loop today; a spec pins the corrected disposition.

## Out of scope

- **The embed-stage failure — #16566.** `neo-shared/neo` fails at a different stage (`KB_VECTOR_EMBED_FAILED`, and later `KB_INGEST_FAILED`). Different defect, different repo, different phase. These two must not be merged into one lane.
- Why `create-app` specifically produced zero chunks. That is currently **undiagnosable** — AC 3 is the prerequisite for answering it. A leading hypothesis, untested: the `neo-shared` tenant entries declare only `cloneUrl` / `credentialRef` / `branchRef`, while other deployments' entries carry `useDefaultSources`, `rawRepoSource`, and `sourcePaths`. If a source-config gap is confirmed after AC 3 lands, that is a config fix and belongs in its own ticket.
