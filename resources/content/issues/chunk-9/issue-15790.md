# Make unit-suite profiling budgets parallel-compatible

## Context

The #15783 workers:4 measurement proved a ~2.7× unit-suite wall-clock win (3.6m vs 9:56/10:36 single-worker baselines, 9099 passed) but was blocked from merge-handoff by one deterministic failure: `unit/app/devindex/StoreFilterProfile.spec.mjs:54` asserts `expect(duration).toBeLessThan(400)` — an ABSOLUTE wall-clock budget encoding "shallow-clone filter < 400ms vs deep-clone's ~800-1000ms". Under 4-way CPU contention the shallow path measured 748ms across all retries in BOTH run attempts — inside the old deep-clone band, so the assertion can no longer discriminate the regression it exists to catch.

## The Problem

Absolute wall-clock budgets assume an idle runner. Any parallelism (workers > 1, co-tenant CI load) shifts the measurement without shifting the property under test. The probe (PR #15784) was closed unmerged per the #15783 protocol; this ticket is the named enabler for re-landing the ~2.7× win.

## The Architectural Reality

- `test/playwright/unit/app/devindex/StoreFilterProfile.spec.mjs:21-57` — the profiling spec with the absolute budget (`< 400` ms) and its rationale comment (deep-clone was ~800-1000ms).
- The unit config (`test/playwright/playwright.config.unit.mjs`) already has a projects mechanism (`unit` / `unit-brain` / chroma setup) — a serial `unit-profiling` project (its own `workers: 1` + `fullyParallel: false`) is the structural slot if isolation is chosen.
- Sweep scope: `grep -rn "toBeLessThan(" test/playwright/unit/ | grep -iE "duration|elapsed|ms|time"` to enumerate every absolute-time assertion in the suite (StoreFilterProfile is the proven one; the census decides how many need treatment).

## The Fix (either lever per spec, chosen at implementation)

1. **Ratio/relative assertion:** measure the deep-clone control in the same test run and assert `shallow < deep * 0.6` — contention cancels out; the discriminated property survives any load.
2. **Serial isolation:** move profiling specs into a `unit-profiling` project pinned to `workers: 1`, dependency-free, so they measure on a quiet worker while the bulk suite parallelizes.

### Foundational falsifier — `workers: 1` is not a quiet CPU

Current `origin/dev` confirms the stated starting point: `playwright.config.unit.mjs` has global CI `workers: 1`, while `StoreFilterProfile.spec.mjs` carries the absolute `< 400ms` assertion. The installed/current declared Playwright version is `1.61.1`.

Playwright does support project-level `workers`, but that property only caps workers **for that project**. Independent projects run together in parallel, subject to the global worker maximum. Therefore a `unit-profiling` project with `workers: 1` and `fullyParallel: false` serializes its own files; it does **not** make that worker quiet while the bulk `unit` / `unit-brain` projects use the other workers. That is the same CPU-contention premise this ticket must eliminate, not a solution to it. See the official [TestProject `workers` contract](https://playwright.dev/docs/api/class-testproject#test-project-workers) and [project running order](https://playwright.dev/docs/test-projects#running-sequence).

If isolation remains an option, the body must name a real exclusivity mechanism—for example, an ordering dependency/barrier that completes profiling before the bulk projects, or a separate invocation/job—not merely a per-project worker cap. Otherwise narrow the ticket to the relative-control approach.

### The census is not one contract class

The proposed grep is a useful candidate generator, not a finished census. Current `origin/dev` contains at least these distinct live wall-clock shapes:

- `StoreFilterProfile`: optimization discrimination (`duration < 400`);
- `GridScrollProfile`: UI/VDOM performance discrimination (`duration < 200`);
- `PhoneInputPatternReDoS`: algorithmic-complexity guard (`elapsed < 100`);
- `offHostSync`: process timeout/kill-grace behavior (`elapsed < 800`); and
- `offHostSync`: local-backup receipt duration (`durationMs < 5000`).

The same textual sweep also returns semantic millisecond values that are not measured wall-clock budgets (cadence, age, margin, ordering). Treating every hit with one ratio or one serial project would weaken different properties for different reasons.

For `StoreFilterProfile`, the ratio option is still plausible, but the body must first pin how the deep-clone control is instantiated from current source; the present spec only cites the historical 800–1000ms band and does not construct that control.
