## Summary

`list_issues` under-reported ownership: `gh` finds **9** open issues assigned to `neo-fable`, `list_issues` returned **1**. The ticket logged 0-then-3 against 11 the same morning. A session booting on the zero answer concluded *"no carried assignments — all prior lanes resolved."*

## The ticket's premise was wrong, and fixing what it described would have fixed nothing

`#15220` states the tool "answers assignee queries from the local content mirror". **It does not.** `IssueService.listIssues` already calls live GraphQL. The real mechanism:

```graphql
issues(first: $limit, states: $states, orderBy: {field: UPDATED_AT, direction: DESC})
```
…fetch the **30 most-recently-updated** open issues (of ~243) — then filter *those 30* client-side by assignee.

**`limit` bounded the rows read, not the matches returned.** The filter only ever searched page one.

That explains the reported symptoms better than staleness does:

| Observation | "Stale mirror" | What actually happened |
|---|---|---|
| 0 → 3 in two hours | a sync cycle catching up | the `UPDATED_AT DESC` window **moved** as peers touched issues |
| hard zero on days-old assignments | mirror missing rows | recency-ordered window excludes rows nobody updated |
| `get_local_issue_by_id` had correct `assignees` while the list missed it | evidence **for** a mirror bug | proof **against** one — the mirror was fine, the list was paging |

The mirror was never the problem. It was the plausible suspect. All three of the ticket's Fix options rest on the false cause — option 1 ("proxy live GitHub") is a no-op, since it already does.

## Deltas

- **`ai/services/github-workflow/queries/issueQueries.mjs`** — `FETCH_ISSUES_LIST` takes `$assignee: String` and applies `filterBy: {assignee: $assignee}`; selects `totalCount`.
- **`ai/services/github-workflow/IssueService.mjs`** — passes `assignee` to the server, deletes the client-side pass, and returns `totalCount` / `truncated` / `endCursor`.
- **`ai/mcp/server/github-workflow/openapi.yaml`** — `IssueListResponse` documents the new fields; the `assignee` parameter description states that `limit` bounds matches and that `truncated` must be checked before treating a result as complete ownership.

## Verified against live GitHub *before* writing the code

- `filterBy: {assignee: "neo-fable"}` → **9 of 9**, `hasNextPage: false` — matches `gh` exactly, where the old path returned 1.
- `filterBy: {assignee: null}` → **234** (every open issue) — null is a clean no-op, not a zero-filter, so unfiltered callers are unaffected.

## The response stops hiding its own bounds

`pageInfo.hasNextPage` was **already selected by the query and thrown away**. The truncation was knowable all along and simply never reported — a caller reading `count: 1` had no way to learn there were 9. `count` is now this page, `totalCount` is the match count, `truncated` says whether more exist.

This is the same defect class as `#15234`'s census, one surface over: a bounded read presented as a complete answer.

## Test Evidence

Evidence: **74/74** `IssueService.spec` (5 new), stub-driven, no live calls.

**Falsified rather than assumed.** With the server-side filter removed and the client-side pass restored, **3 of the 5 new tests go red** — they catch the defect rather than passing either way:

- the filter reaches GraphQL (`filterBy: {assignee: $assignee}` in the query, `assignee` in the variables);
- `assignee: null` passes through as a no-op;
- the server's match set is returned verbatim — no client-side pass may drop a row;
- a bounded answer reports `count: 1, totalCount: 9, truncated: true, endCursor`;
- a complete answer reports `truncated: false, endCursor: null`.

Block-alignment: the 45 findings in `IssueService.mjs` are pre-existing on `dev` (verified against the pristine file) and untouched; this change adds none.

## Notes

- **Why it matters beyond the count:** ownership truth is what `[lane-claim]`, the 7-day rule and intake assignee checks all stand on. A filter that silently searches one page is a collision generator wearing a query's clothes — it invites duplicate pickups and phantom "released" lanes.
- The ticket calls this the read-side sibling of the 2026-07-12 write-side `manage_issue_assignees` false-success. Both are assignee-surface truth failures in the same server.
- **`labels` has the same shape and is deliberately left alone.** It is still filtered client-side over one page. I have not reproduced it, and shipping an unverified fix beside a verified one is how a premise goes unchallenged — filing separately rather than assuming.
- Body reshape of `#15220` itself follows; the premise correction is posted at `#15220#issuecomment-4996826356`.
