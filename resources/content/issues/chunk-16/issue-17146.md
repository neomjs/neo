# No-LMS hosts lack an independent wake startup path

## Context

During the same 2026-08-15 reboot incident, the installed host-edge configuration contained `NEO_ORCHESTRATOR_LMS_ENABLED=false`. The wake receiver was nevertheless running independently, and a POST to `127.0.0.1:3199/wake` reached it. Removing the stale override restored LM Studio supervision; it did not change wake ownership.

The runtime separation is correct. The documented startup contract is not.

## The Problem

The local guide's topology correctly names host-edge and the signed wake receiver as separate processes, but its portable platform table tells macOS, Linux, and Windows users to run only `npm run ai:host-edge`. The Day-0 guide also says host-edge owns wake delivery.

A host that intentionally has no LM Studio can therefore follow the documented portable path, disable LMS correctly, and still never start the actual wake receiver.

## The Architectural Reality

- `package.json` exposes separate `ai:host-edge` and `ai:wake-receiver` commands.
- `ai/deploy/hostEdgeProfile.mjs` defines `NEO_ORCHESTRATOR_LMS_ENABLED=false` as a valid one-variable provider opt-out.
- `ai/deploy/com.neomjs.agent-os-wake.plist` launches `ai/daemons/wake/receiver.mjs` with manifest, state, host, and port arguments.
- The host-edge plist launches a different entrypoint and contains no wake receiver.

Structure-map gate: `ai/daemons/wake/` is the existing receiver owner; this ticket proposes documentation/receipt repair, not a new runtime module.

## The Fix

Document wake as its own portable capability: add a complete `ai:wake-receiver` invocation and platform row, correct the Day-0 ownership text, and state explicitly that the LMS flag controls only LM Studio.

## Contract Ledger

| Target Surface | Source of Authority | Proposed Behavior | Fallback | Docs | Evidence |
|---|---|---|---|---|---|
| Portable host capability matrix | separate runtime entrypoints | host-edge and wake are independent rows | no-LMS disables provider only | local + Day-0 guides | command/source assertions |
| No-LMS wake path | wake receiver CLI/plist | receiver starts with manifest, state, host, and port while LMS is disabled | missing manifest fails loud; no coupling fallback | local guide | real signed wake with LMS off |

## Decision Record impact

`none` — runtime authority is unchanged.

## Acceptance Criteria

- [ ] The portable platform matrix lists `ai:wake-receiver` independently from `ai:host-edge`.
- [ ] The guide provides the receiver's complete manifest/state/host/port invocation.
- [ ] Day-0 no longer claims host-edge owns or starts wake delivery.
- [ ] `NEO_ORCHESTRATOR_LMS_ENABLED=false` remains valid and is documented as affecting LMS only.
- [ ] A no-LMS witness proves a signed wake reaches the receiver with host-edge absent or its LMS lane disabled.

## Out of Scope

Wake-subscription auto-registration (#16991), receiver/host-edge process merging, and generic systemd or Windows-service packaging.
