# Elect the smallest provider-lane envelope that meets the joint SLO

Sub of epic #17018 (Row F, OQ4/OQ6/OQ7, and AC-D validation/election stage). This ticket is intentionally unassigned for peer self-selection and is blocked by #17021's canonical two-lane profile.

## Context

D#17015 r6 converged on an Ollama chat lane and OpenAI-compatible embedding lane under one fixed total CPU/memory envelope. The embedding slot count is not prescribed: candidates `{1,2,4}` must be elected empirically, and the smallest candidate meeting the joint service-level objective wins.

Live duplicate sweep (2026-08-12T12:16Z): open searches for `joint load resource election` and `embedding slot election` found only parent #17018 and its composition leaves. No implementation ticket owns this outcome.

## The Problem

A two-engine topology can preserve the original contention class if each service independently requests the whole machine. Conversely, choosing four embedding slots because it was the day-one wish can oversubscribe CPU or divide the model context below the required per-slot ceiling.

The relevant knobs are not comparable in isolation:

- llama.cpp-style `--ctx-size` is total across `-np` slots; slot truth must be observed at runtime.
- Ollama chat remains parallelism 1 and must retain bounded progress during embedding load.
- Neo's KB, MC, and orchestrator processes create the production concurrency, so a single synthetic caller is not representative.
- queue latency, provider wall time, CPU, memory, and refusal behavior answer different questions.

## The Architectural Reality

The election consumes #17021's stable service identities and explicit envelope inputs. It does not create another runtime policy layer. Candidate values are proposed, validated, and either elected or refused; they are never silently clamped or adapted after deployment.

Evidence is generated only on Neo's canonical/disposable plane. No external endpoint, corpus, token, or deployment mutation belongs in this ticket.

## The Fix

Build one reproducible election protocol:

1. hold the total CPU and memory envelope fixed,
2. evaluate embedding slot candidates `1`, `2`, and `4` with chat parallelism `1`,
3. allocate lane resources explicitly for every candidate,
4. verify observed per-slot context and refuse a candidate whose slot truth is below the embedding contract,
5. drive production-shaped concurrent embedding callers representing KB, MC, and orchestrator while overlapping a bounded chat workload,
6. record queue wait, provider duration, throughput, CPU, RSS, errors/refusals, and bounded-progress/starvation outcomes per lane,
7. repeat/interleave candidates sufficiently to expose warm-order and model-residency effects,
8. elect the smallest passing candidate and emit its values as immutable declarative deployment inputs.

The runner may reuse existing benchmark primitives, but any new module placement must pass structural pre-flight before implementation.

## Contract Ledger

| Producer | Consumer | Contract | Failure semantics |
|---|---|---|---|
| #17021 canonical profile | election runner | stable service identities, resource-envelope coordinates, immutable model/image digests | profile mismatch aborts the run |
| candidate matrix | both provider lanes | same total CPU/memory budget for every candidate | budget drift invalidates the candidate |
| runtime receipts | election rule | observed per-slot context plus joint-load metrics | knob-only evidence is invalid |
| election rule | deployment profile | smallest candidate satisfying every joint SLO becomes the immutable input | no passing candidate means no election, never fallback/clamp |

## Acceptance Criteria

- [ ] Candidates `{1,2,4}` run under one identical declared total CPU/memory envelope with chat parallelism fixed at `1`.
- [ ] Every candidate records its explicit per-lane resource allocation and immutable image/model digests.
- [ ] Runtime evidence verifies per-slot embedding context; one over-limit request per lane proves refusal rather than silent truncation.
- [ ] Workload composition includes concurrent KB-, MC-, and orchestrator-shaped embedding demand plus overlapping chat demand.
- [ ] Receipt separates Neo queue wait, provider duration, throughput, CPU, RSS, and errors/refusals; it never labels summed request wall time as CPU utilization.
- [ ] Both lanes must make bounded progress with no starvation under the declared joint SLO.
- [ ] Candidate order is interleaved/counterbalanced and repeated enough to expose warm-order/residency effects; sample count and uncertainty are reported.
- [ ] The smallest fully passing candidate is elected. If none pass, the output is `NO_ELECTION`.
- [ ] Elected values are emitted as immutable declarative inputs consumed by the canonical profile; there is no runtime adaptation or silent clamp.
- [ ] All execution is restricted to Neo's canonical/disposable plane; no external-plane probe or data access exists.

## Avoided Traps

- Benchmarking one caller against a multi-process production topology.
- Comparing candidates under different total resources.
- Reading configured total context as per-slot context.
- Choosing four because it is the largest candidate.
- Calling request wall time CPU time.
- Hiding a failed matrix behind an automatic fallback.

### Joint SLO

Both lanes require:

- CPU high-water no greater than their 2-CPU allocation (`200%` Docker CPU convention);
- aggregate process RSS no greater than their declared memory allocation;
- zero caller-visible errors and zero unexpected refusals;
- Neo queue wait at most 60 seconds;
- provider duration and caller-visible progress gap at most 300 seconds;
- at least 90% resource-sample coverage with zero detected gaps;
- throughput at least 0.001 completed source calls/second;
- queue disposition `queued`.

Cardinality/context floors are source-specific: chat completes both bounded KB-ask calls and proves 131072 context; embedding completes all four production-shaped source calls and proves 8192 context per slot.

Context/first-activation timeout is 900 seconds; each trial timeout is 900 seconds. The shared activation/probe bound is intentionally higher than the 300-second provider-duration SLO because the first disposable candidate must cold-hydrate 23.7 GiB of exact pinned model artifacts. No passing candidate yields `NO_ELECTION`; there is no fallback or clamp.

### Challenge / execution gate

Named-authority review was requested from the graduated Discussion author and the #17022 downstream consumer. Exact pinned images may hydrate in parallel, but model workload does not begin until the proposal receives a clean review or a concrete correction is folded. The final report must independently pass `validateProviderLaneElectionReport(..., {requireElected:false})`; only an `ELECTED` report is admissible to #17022.

The worker first reads runtime `/slots` truth. `createProviderLaneSupportedLimitRequest()` refuses to construct a request unless the observed per-slot limit fits the receipt's context requirement, model ceiling, logical batch, and physical ubatch. It then sends exactly 8192 tokens and requires a completed embedding. The subsequent 8193-token request must be refused without output or silent truncation; the pinned adapter keeps physical-batch refusal distinct from context-limit refusal.

The 32768 Qwen coordinate is a **per-request ceiling**, not the per-slot floor. This plan uses 8192 per slot so candidate 4 preserves the 32768 total model envelope while every production-shaped request remains bounded below the model ceiling.
