## Summary

All four long-lived daemons — orchestrator, embed, message, wake — routed their `uncaughtException` handler into the same `cleanup()` their signal handlers use, and that `cleanup()` called a **bare `process.exit()`**. Node exits **0** with no argument. So a crash was reported to the container runtime as **success**.

A restart policy brings the daemon back either way, which is exactly why this survived: **the loss is not availability, it is attribution.**

Resolves #16882.

## Why it mattered, with numbers

An external CPU-only plane, read live 2026-08-10:

- `restartCount: 12`, `exitCode: 0`, `oomKilled: false`, `error: null` — readings that say *"somebody stopped it twelve times"*
- self-heal ledger: `total: 0`, **no events ever recorded**
- the stack traces were written to the daemon's own log seconds before each exit

Twelve probable crashes, invisible to everything keyed on a non-zero exit, next to a healer that never fired — because the exit code said there was nothing to look at. That plane's operators were told to investigate *who was restarting the service*. The evidence was in the log the whole time and the exit code pointed away from it.

## The change

| file | change |
|---|---|
| `ai/daemons/shared/daemonExit.mjs` | **new** — `DAEMON_EXIT_OK = 0`, `DAEMON_EXIT_CRASH = 1`, single-sourced |
| `orchestrator/daemon.mjs` | `cleanup(exitCode)`; crash arm passes `DAEMON_EXIT_CRASH` |
| `embed` · `message` · `wake` | same, plus `releasePidFile` split out of `cleanup` |

**The signal path deliberately still exits `0`.** An operator stopping a daemon *is* success. A repair that set every exit non-zero would satisfy the obvious test and make every graceful shutdown look like a crash — strictly worse than the defect, because it trains operators to ignore the signal this PR builds.

**Every registration passes its code explicitly, and that is load-bearing rather than stylistic.** `process.on('SIGINT', cleanup)` invokes the listener with the **signal name** — a positional `cleanup(exitCode = 0)` wired directly would hand `'SIGTERM'` to `process.exit`. This is the trap that would have made a naive version of this fix wrong, and the spec asserts the wrapped shape in both directions.

**Second defect found while fixing the first.** Three daemons registered the whole of `cleanup` on `process.on('exit', ...)`. Since `cleanup` calls `process.exit`, that listener could re-enter during a *non-zero* exit and reset the code to 0 — the same class of bug arriving by another door. `releasePidFile` is now separated and registered release-only, which is what the orchestrator already did. All four now agree.

## Evidence

**Mutation conviction — run, not asserted.** Two independent mutations, each caught surgically:

| mutation | result |
|---|---|
| crash arm reverted to bare `cleanup()` | **1 failed** — `orchestrator — the crash path exits NON-ZERO`; 13 passed |
| `process.on('SIGTERM', cleanup)` restored | **failed** — `orchestrator — the SIGNAL path still exits 0`; crash arms unaffected |

Each mutation fails exactly the arm that owns it and nothing else.

**Blast radius:** full `test/playwright/unit/ai/daemons/` suite — **1772 passed, 0 failed**.

## Honest limit on the instrument

The per-daemon tests are **structural** — they read source and assert how handlers are *wired*. They do not prove runtime behaviour, and the spec's docblock says so rather than implying otherwise. Proving the runtime path would mean spawning each daemon and inducing a real uncaught exception, which needs their config, PID locks and stores.

The wiring **is** the defect here — a bare `process.exit()` and a directly-registered listener — so a structural assertion has the right subject. **Retirement condition is stated in the spec:** if handler installation is ever extracted behind an injectable `exit` port, these become behavioural and the source-reading versions should go. The `DAEMON_EXIT_*` tests themselves are behavioural.

## Scope

Makes crashes **visible**. Diagnoses none of them. No restart-policy, backoff or supervision changes. No new config leaf — an exit code is a contract with the supervisor, not a deployment preference, and the module says why.
