# Component cells keep their first record's content when rows recycle

## Context

Reported by the operator against `apps/devindex`: scrolling into new row ranges leaves the User and Impact columns showing the values from the first page. Reproduced in the GPU e2e harness on 2026-08-19.

Live latest-open sweep: latest 20 open issues checked at 20:56Z, no equivalent. A2A claim sweep over the last 12 messages: no overlapping lane.

## The Problem

One row, read at three scroll positions, in the same run:

| position | `rank` | `total` | `login` |
|---|---|---|---|
| page 1 | 1 | 19,876,461 | `laciferin2024Hiro` |
| +100 rows | 105 | 214,342 | `laciferin2024Hiro` |
| bottom | 2263 | 37,236 | `laciferin2024Hiro` |

`rank` and `total` track the scroll exactly. `login` never changes. Rows 2–5 behave identically — the same five logins appear at rank 1, rank 105 and rank 2263.

**The control is inside the row.** Because `rank` and `total` update in the very same recycled row, this cannot be a scroll that did not happen or a store that did not page. Only some cells are stale.

**The split is by column KIND, not by column.** `rank` and `total` are plain/renderer columns and are correct. `login` is `type: 'githubUser'`, which extends `Neo.grid.column.Component`. The operator also names Impact (`type: 'component'`); the sparkline, iconLink and countryFlag columns share the same base and should be assumed affected until measured.

Reproduction: load `/apps/devindex/`, read the first rows, wheel-scroll over `.neo-grid-view` (native `scrollTop` assignment is inert — the grid virtualizes by transform), read again. A diagnostic spec was used and deliberately not committed; the app is leaving this repository and its tests go with it.

## The Architectural Reality

- `src/grid/column/Component.mjs#cellRenderer` — produces or recycles the cell component. It opens with a short-circuit that returns the pooled component untouched when `component[recordProperty] === record && component.lastRecordVersion === record.version`. The reuse branch below it deletes `className`/`module`/`ntype`, maps `undefined` to `null` and calls `component.set(...)`.
- `src/grid/Body.mjs` — owns row pooling and the mounted range.
- `src/grid/column/GitHubUser.mjs`, `Sparkline.mjs`, `IconLink.mjs`, `CountryFlag.mjs`, `Progress.mjs` — all extend the component column and inherit the path.
- Plain and renderer columns take a different, string-producing path and are correct, which is what makes the failure invisible in any grid without a component column.

**Not yet established:** whether the short-circuit fires wrongly, whether `cellRenderer` is reached at all on recycle, or whether the row hands the wrong component instance. The measurement above locates the class; it does not name the line. That work belongs to whoever takes this.

## The Fix

Determine which of the three candidates above holds before changing anything, then make component-backed cells re-bind to the row's current record on recycle.

Note that `useBindings` is **not** the lever: `Component.mjs` documents those bindings as evaluated exactly once at instantiation and explicitly forbids reading record data through them, so enabling it would freeze values rather than refresh them.

## Test Coverage Gap

No spec at any level exercised a component column under recycling, and none resized one either — `test/playwright/unit/grid/ComponentColumnResizeSync.spec.mjs` was added today to close the resize half. The scroll half is still open, and it is why this reached an operator: `ColumnResizeCellSync` and `HeaderResizeRectSync` both drive plain-column grids only.

## Root cause — measured end to end

`src/grid/Body.mjs:799` updates rows during scroll with `silent: true`:

```js
item.updateContent({record: store.getAt(i), rowIndex: i, silent: true})
```

That flag is threaded straight through to the cell components:

`updateContent({silent})` → `createVdom(silent)` → `applyRendererOutput({silent})` → `column.renderer(...)` → `grid.column.Component#cellRenderer` → `component.set(componentConfig, silent)`

`silent: true` applies the new config to the component and **suppresses its vdom update**. Body then flushes its own tree — but a component cell's node is only a reference:

```json
{"data":{"field":"login","recordId":"neo-record-121"},
 "id":"neo-grid-body-1__row-0__login",
 "cn":[{"componentId":"neo-component-1"}]}
```

Re-rendering the row or the body does not re-render the referenced component's subtree, so the suppressed update is never flushed and the cell keeps its first-rendered DOM.

**Why only component columns.** Plain and renderer cells carry their content inline in the row vdom, so the batched row flush repaints them. Component cells carry theirs in a separate tree that the row flush does not reach.

## Evidence

Live, `apps/devindex` in the GPU e2e harness, first row across one wheel scroll:

| | before | after |
|---|---|---|
| row `data-record-id` | `neo-record-754` | `neo-record-910` |
| `rank` cell text | 1 | 157 |
| login cell inner element id | `neo-component-8` | `neo-component-8` |
| login cell text | `laciferin2024Hiro` | `laciferin2024Hiro` |

The row rebound and the plain cell followed it, in the same row — so this is not a scroll that did not happen. The component instance is correctly reused; only its DOM is stale.

At unit level the binding is *correct* — `test/playwright/unit/grid/ComponentCellRecycle.spec.mjs` shows the recycled row rebinding `components.login` to the new record, with the cell node carrying the new `recordId`. That is why the defect needs the batched scroll path to reproduce: the unit path calls `updateContent` without `silent`.

## Fix direction

The silenced component updates have to be flushed when the batch flushes. Dropping `silent` at the `component.set()` call would fix correctness at the cost of one update per component cell per scroll frame, which is the wrong trade in the hot path — the batching exists for a reason. Collecting the silenced components and flushing them once with the body update keeps both.

Whoever takes it should benchmark against `examples/grid/bigData` and the DevIndex grid, since this is the scroll hot path.

The short-circuit at the top of `cellRenderer` is **not** implicated — it is bypassed correctly, since the recycled row does carry a different record.

## It is a regression, and it is one line

`0053bda5ef` — 2026-04-02, "fix(grid): Optimize syncBodies to use updateDepth: 3 to eliminate scroll VDOM backpressure (#9632)":

```diff
-            me.view.updateDepth = -1;
+            me.view.updateDepth = 3;
```

`-1` is unlimited: the scroll flush descended into the cell components and repainted them. `3` reaches View → Body → Row and stops. A row's own vdom renders — which is why plain and renderer cells still track the scroll — but a cell **component** is a separate component one level further down, so it is never reached and keeps its first-rendered DOM.

That is the whole mechanism, and it explains the split by column kind exactly.

## Why it survived four months

No spec at any level exercised a component column under recycling — `ColumnResizeCellSync` and `HeaderResizeRectSync` both drive plain-column grids. A depth cap that only affects child components cannot fail a suite that has none.

## What this means for the fix

`updateDepth: 4` is the minimal change, but #9632 exists to kill scroll backpressure and raising the cap gives that back — it must be benchmarked, not assumed. The narrower option is to keep the cap and flush only the components that were silently updated, which is O(visible component cells) rather than full depth. Either way the benchmark is `examples/grid/bigData` plus the DevIndex grid, since this is the scroll hot path.

## Measured: the two strategies are not equivalent, and only one is atomic

Operator framing: `silent` + a deeper `updateDepth` forces the cell change into the **same update cycle and rAF** as the row geometry; non-silent means the component updates on its own schedule. Under rapid scrolling that difference is visible.

Tearing detector — 60 rapid wheel steps on `apps/devindex`, sampling `(rank, login)` from the top 6 rows each step. `rank` comes from the row, `login` from a component cell. A login observed under two different ranks means the two disagree:

| configuration | torn logins | staleness fixed | atomic |
|---|---|---|---|
| `updateDepth: 3` + silent — **current** | n/a | ✗ never updates | — |
| `updateDepth: 4` + silent | **0 / 266** | ✓ | ✓ |
| `updateDepth: 3` + non-silent | **7 / 292** | ✓ | ✗ |
| `updateDepth: 3` + non-silent + View marked `needsVdomUpdate` before the bodies update | **10 / 303** | ✓ | ✗ |

Example of a torn sample: `laciferin2024Hiro` observed at rank 1 and at rank 14 — the row advanced while its component cell still showed the previous record.

The third row was my attempt to get atomicity without the depth bump, on the theory that `mergeIntoParentUpdate` would attach the cell updates to the View's cycle as disjoint Teleportation payloads. **It is falsified** — marking the ancestor early made tearing worse, not better.

Scroll cost, same rig (`ThumbDragDevIndex` telemetry, frames measured over a fixed 7-profile sequence):

| configuration | frames | blank | jitter |
|---|---|---|---|
| depth 3 + silent | 1921 | 0 | 0 |
| depth 4 + silent | 1912, 1916, 1916 | 0 | 0 |
| depth 3 + non-silent | 1916, 1917 | 0 | 0 |
| depth −1 + silent | 1897 | 0 | 0 |

All within ~1% of each other and of the broken baseline, with no blank frames or jitter anywhere. **The perf rig does not choose between the candidates** — atomicity does.

## The remaining problem with a hardcoded 4

`updateDepth` is 1-based: depth N covers distances 0..N−1. From the View: Body 1, Row 2, cell component 3. So depth 4 reaches the cell component and stops there.

A cell component may be a **Container**, whose children sit at distance 4+. Depth 4 fixes today's built-ins — `GitHubUser`, `IconLink`, `CountryFlag`, `GitHubOrgs`, `Progress` all extend `component/Base.mjs`, and `Sparkline` extends Canvas — and would silently fail for the first nested one. `column.Component` places no constraint on the `module`, so nothing prevents it.

The framework already expresses the right arithmetic in `VDomUpdate#getAdjustedUpdateDepth`: a merged child raises the parent to `distance + childUpdateDepth`, collapsing to −1 when the child needs its full subtree. Deriving the View's scroll depth the same way — `3 + max(cell component updateDepth)`, −1 if any cell needs a full subtree — gives depth 4 for the current flat components and adapts for a container, instead of encoding today's component shapes as a literal.

**Not yet verified:** that a Container cell component actually breaks at depth 4. That is the discriminating fixture and it should exist before either fix lands, otherwise the same class returns the first time someone nests a cell.
