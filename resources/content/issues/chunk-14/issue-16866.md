# Nothing measures how much embedding work is spent re-embedding the same content

## Context

#16780 needs a bounded observation of repeated batch-embedding work. Provider activity says which stage consumes inference and WAL drain says how much work remains; neither records content identity. This ticket adds that identity dimension without storing corpus text or turning the observation into an alarm.

## Architectural Reality

Knowledge Base and Memory Core run in separate processes, so a `TextEmbeddingService`-local window cannot be read by the Memory Core metrics observer. Both recorder services already open the same plane-anchored graph SQLite. The identity observation therefore belongs in that shared artifact.

The producer is `TextEmbeddingService.embedTexts()`, not interactive `embedText()`. It records logical batch-input admissions only after provider and abort validation and before provider settlement. Pre-aborted, unsupported, empty, yielded-before-next-chunk, and locally invalid work records nothing; work that fails after admission remains observable. Transport retry attempts are not multiplied into new logical submissions.

## Fix

- Replace the process-local window with shared `embedding_identity_log` and `embedding_identity_state` tables.
- Store only a recorder-owned source, timestamp, opaque id, and 128-bit SHA-256 fingerprint; never raw input.
- Bound retention to 2,048 rows and preserve durable `coverage_started_at` and `evicted_through` boundaries.
- Read watermark, retained boundary, and counts in one SQLite snapshot so concurrent eviction cannot create a partial-as-total result.
- Query the exact `get_memory_core_tool_metrics().sinceMs` interval; old repeats cannot contaminate a current interval.
- Publish `status`, `reason`, `coverageStartedAt`, `oldestRetainedAt`, `distinct`, `ratio`, `submissions`, and `truncated` on every response arm.
- Keep the ratio observational: `submissions / distinct`, and `null` for an observed interval with no batch submissions. A value above 1 may be legitimate and neither proves a loop nor disproves convergence.

* test(knowledge-base): pin that zero chunks issues zero provider submissions (#16780)

AC-1 is a control, not a repair — embedChunks already returns early on an empty
input. Pinning it is the point.

The ticket observed ~4 cores of continuous inference against an EMPTY corpus. That
observation only becomes attributable if 'Neo submits nothing when there is
nothing to embed' is a guaranteed property rather than a current one. With it
pinned, sustained provider load beside zero pending work cannot be our
submissions — it is a stranded or wedged runner, which is a different ticket and
a different fix. Without it, an operator cannot rule us out, and every such
incident starts by re-deriving whether the loop is looping.

Asserted at the PROVIDER boundary, not on the return value: a function can report
embedded:0 while still having called out, and it is the call that burns the core.

The WAL drain half of this AC was already covered — drainCycle's AC1 spec asserts
collection.addCalls stays at 1 across a second, zero-pending cycle.

* feat(memory-core): expose the re-embed ratio over a bounded window (#16780)

The discriminator between 'the loop does not converge' and 'the load is
legitimate'. Provider load alone cannot tell them apart, and the attribution
ledger answers WHICH stage is calling, never whether it should still be calling.
Identity is what separates them: 500 submissions of 100 distinct texts is not
busy, it is repeating.

Recorded at embedTexts — the one point every submission passes through regardless
of provider or caller. Per-caller recording would answer 'does this sweep repeat
itself', which is the wrong question: a plane whose KB sync and WAL drain each
converge can still re-embed the same content between them.

Recorded on SUBMISSION, not on success. A sweep that re-submits the same content
and fails every time is exactly the non-convergence this surfaces, and counting
completions would hide the loop behind its own failures.

A ratio above 1 is NOT a defect and the tests pin that it reaches no verdict. Real
corpora duplicate content honestly; an alarm keyed on ratio>1 fires on correct
work and is switched off within a week, leaving neither an alarm nor the option of
one. The negative control asserts the reported key set to keep it a denominator
rather than a judgement.

Carries the coverage discipline the WAL drain receipt already needed: ratio is
null — never 1 — for an unobserved window, because 'nothing observed' and 'nothing
repeated' are different facts, and truncation is reported so a bounded window
cannot claim a total. The eviction control has its own negative control, or
'always truncated' would satisfy it.

Fingerprint is truncated sha1: the window must never become a second copy of the
corpus. Collisions understate repetition, which is the safe direction for an
instrument whose failure mode is being disabled after a false alarm.

* feat(memory-core): publish the re-embed ratio on the metrics observer (#16780)

Closes the hop I had scoped OUT of this PR an hour ago, because scoping it out was
the wrong call under a two-reviewer queue: one complete PR beats two partial ones
when reviewers are the bottleneck.

The reason it was scoped out stands and is why it is injected rather than
imported: TextEmbeddingService owns the window and already imports the recorder,
so the recorder reaching back would be a cycle. Same provider injection the WAL
drain projection uses.

`walDrain` answers how much work was PENDING. This answers how much of the work
done was REPEATED. Neither alone separates a converging sweep from a loop, which
is why they belong on one reading rather than in two places an operator has to
know to look.

Fails closed exactly like the drain projection. A process that does not host the
window reports `unavailable`, never a ratio of 1 — one is the value of a
CONVERGING run, so a defaulted 1 would report a healthy corpus for every process
that never embeds. `ratio` stays null on every empty arm.

Every status arm carries the field. That is not tidiness: a required field omitted
on a status branch is a wire break a schema check cannot see, because the schema
validates the declaration and not the runtime branch. That exact break was caught
on this response once already.

The declared key set is EXTENDED, not loosened — the pin records the addition so a
future field cannot arrive unannounced.

Adopting the lesson rather than restating it: a diagnostic without a production
reader is not an instrument. The window existed, was tested, and no operator could
read it. That is the same shape as shipping a field no consumer consumes.
