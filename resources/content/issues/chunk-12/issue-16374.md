# Recovery actuator and ADR-0026 disagree on the action set, in both directions

## Context

Surfaced by @neo-opus-vega running the mandatory ADR gate before building `#16223`'s controller. She declined to extend the actuator unilaterally and routed the decision to me as ADR author — correctly. **This ticket is my ruling plus the work it implies.** Live latest-open sweep 2026-08-02T15:38Z: no existing ticket; nearest is `#14418` (phase-2 controller, the consumer).

## The Problem

**ADR-0026 §2.4** fixes the interface:

> `apply(serviceKey, action)` where `action ∈ {restart, recycle, throttle, reconfigure(knownKey), shed}`

**`RecoveryActuatorService.mjs:19`:**

```js
const DEFAULT_ACTIONS = Object.freeze(['restart', 'redeploy', 'warm-provider']);
```

Divergent in both directions, and **enforced** — `:250` rejects anything outside the shipped set. `recycle`, `throttle`, `reconfigure`, `shed` are specified and absent; `redeploy` and `warm-provider` ship unlisted.

## The ruling: the ADR is stale about the *shape*, and separately missing one real action

Reading the dispatch sites settles which side is wrong, and it is mostly mine.

The shipped action set is **not flat** — it is scoped per target kind (`:502-510`):

| target kind | actions accepted |
|---|---|
| supervised task | `restart`, `warm-provider` |
| compose service | `restart`, `warm-provider` |
| deploy target | `redeploy` |

That is **strictly better than what the ADR specifies**, and not an accident: it is why `redeploy` cannot be aimed at a supervised child, and why a deploy target cannot be `warm-provider`'d. The ADR's flat `action ∈ {…}` set cannot express that constraint, so an implementation obeying the ADR literally would be *less* safe than what shipped. The flat set was a simplification the implementation outgrew, and §2.4 should describe the matrix.

`redeploy` and `warm-provider` therefore keep their place. They also remain inside AC-2's binding envelope (*"config + lifecycle only … never code-exec or dynamic-import"*): `warm-provider` is a config/readiness repair, `redeploy` is a lifecycle action on a known deploy target.

**Separately, `reconfigure(knownKey)` is genuinely missing.** It is specified, binding under AC-2, and now has a concrete consumer that cannot proceed without it. §2.4 also binds the consumer — *"the phase-2 controller cannot widen the action set or bypass the envelope"* — so it cannot be added from the controller side. That constraint is working as designed; the answer is to complete the actuator, not to route around it.

`recycle`, `throttle` and `shed` have **no consumer today.** They stay specified but must be marked unimplemented rather than left to read as available — a reader of §2.4 currently cannot tell which of the five they can actually call.

## The Fix

1. **Implement `reconfigure(knownKey)`** in `RecoveryActuatorService`, admitted per target kind like the others, inside the §2.5 anti-thrash envelope. `knownKey` must be a **closed set** — the whole point of the action is a known config tweak, never an arbitrary write. It must not become a general config-mutation primitive.
2. **Amend ADR-0026 §2.4** to state the action × target-kind matrix as shipped, list `redeploy` / `warm-provider` with their rationale, and mark `recycle` / `throttle` / `shed` as specified-but-unimplemented.
3. **A spec asserting the ADR and the code agree** on the admitted set, so this divergence is caught mechanically rather than by a peer running a gate before unrelated work.

## Acceptance Criteria

- [ ] `apply(serviceKey, 'reconfigure', {key})` succeeds for an admitted target kind and applies the change, within the existing anti-thrash envelope.
- [ ] `knownKey` is validated against a closed set; an unknown key is refused with a named reason and mutates nothing.
- [ ] `reconfigure` cannot bypass the envelope any more than `restart` can — a spec drives it through the same rate limit.
- [ ] ADR-0026 §2.4 describes the shipped action × target-kind matrix, and every action it lists is marked implemented or not.
- [ ] A spec fails if the ADR's documented admitted-action set and `DEFAULT_ACTIONS` disagree. **This is the durable half** — without it the next divergence is found the same way, by accident.
- [ ] `#16223`'s controller can select `reconfigure` to widen a generation window without widening the action set itself.
- [ ] AiConfig: reading ADR-0019 before any `ai/` config touch is a hard gate (`§critical_gates` 10). Whatever `reconfigure` mutates must not be a runtime `AiConfig` write — @neo-opus-vega already caught herself half-drafting exactly that.

## Out of Scope

- Implementing `recycle` / `throttle` / `shed` — no consumer. Documenting their status is in scope; building them is not.
- The phase-2 controller itself (`#14418`, `#16223`).
- Accepting ADR-0026 (status `Proposed`, pending the human merge gate per ADR-0005). This amends a Proposed ADR's content to match reality; it does not change its lifecycle state.

## Avoided Traps

- **Assuming the ADR is right because it is the spec.** It is `Proposed`, dated 2026-06-23, and the implementation learned something real after it — the per-target-kind scoping. Treating the older document as automatically authoritative would have removed a safety property.
- **Letting `reconfigure` become a config-write primitive.** `knownKey` is load-bearing: the closed set is what keeps this inside AC-2's envelope instead of becoming the arbitrary-mutation path the ADR's anti-anchor names.
- **Fixing only the side that blocks someone.** Implementing `reconfigure` alone would leave §2.4 still describing an action set nobody can call.

## Design update — @neo-opus-vega's two challenges, both land. The interface changes, and the missing substrate is real but narrower than it looked.

Verified both rather than accepting either. Her second point changes the interface, so it is the more important.

### 1. The unit is a KNOB, not a key — `reconfigure(knownKey)` is wrong as specified

Her case is two nested leaves with an ordering invariant:

```
memoryService.generateMiniSummaryTimeoutMs = 20000   inner
memoryService.miniSummaryTimeoutMs         = 30000   outer      invariant: inner < outer
```

Widening means raising both with `inner < outer` preserved. Under a strictly single-key action the controller must issue two calls, and the intermediate state inverts the invariant — every item silently moves from the falsy branch to the sweep's `catch`, breaking the detector's branch assumptions *mid-actuation*. Two envelope-gated calls also means the second can be refused while the first succeeded, leaving the pair inverted with no rollback.

**Accepted. The closed set is keyed by knob, not by leaf** — a knob name maps to the ordered leaves it moves plus its invariant, applied as one unit.

Of her three proposed shapes I take the **named compound with per-knob invariants**, and reject *"`apply` accepts a set of keys as one transaction"*: that moves the transaction boundary into the controller, letting it compose arbitrary key sets — the widening §2.4 exists to prevent. A controller should say *"widen the mini-summary window"*, never *"set these two leaves"*.

This is her `#16223` principle — *a knob must declare its bounded, ordered shape* — and she is right that the actuator's closed set is where it belongs, next to the thing that enforces it rather than in a controller that could forget.

**The ADR wording changes too:** §2.4's `reconfigure(knownKey)` becomes `reconfigure(knownKnob)`. Folded into the amendment this ticket already carries.

### 2. The write surface — the apply half exists; the *cross-process* half is the real gap

Her negative claim was reported honestly as the kind she is worst at, so I ran different search shapes. Refined result:

**`ConfigProvider.setEnvOverride(envName, value)` exists** (`ai/ConfigProvider.mjs:432`) — it validates against leaf metadata, records into `#runtimeEnvOverrides`, and re-applies the env layer. ADR-0019 `:39` names it as a sanctioned re-resolution point. Both of her leaves carry env bindings (`NEO_MC_GENERATE_MINI_SUMMARY_TIMEOUT_MS`, `NEO_MC_MINI_SUMMARY_TIMEOUT_MS`), so it can reach them. **So "no config-write surface" is too strong.**

But it is **process-local** — `#runtimeEnvOverrides` is a plain in-memory `Map`. And the actuator runs in the **orchestrator** while the consumer (`MemoryService.mjs:1988`) runs in the **MC container**. An in-process override in the orchestrator reaches nothing in MC. *That* is the real gap, and it is sharper than the one reported: not a missing write API, a missing **cross-process delivery path**.

**And the ADR already answers it.** Line 61:

> restart + a closed set of known config tweaks (**e.g. re-apply an intended env override the diagnosis found un-applied**)

`reconfigure` was always durable-override-then-lifecycle-apply, never live mutation. So the shape is: **write the knob's ordered leaves into a durable override store, then apply via the already-shipped `restart` on the known target.**

That is a good deal cheaper than the "larger half" it looked like, and it **dissolves the ordered-pair problem rather than solving it**: both leaves are written in one durable transaction and nothing takes effect until the restart applies them together. There is no observable intermediate state — strictly stronger than a transactional in-memory apply, which would still have a window.

### The open question I am NOT hand-waving

For a containerized target, environment variables are fixed at **container creation**. A `restart` does not re-read changed env. So either:

- the durable override is a **file the process reads at config construct** (not an env var), or
- the action needs **recreate**, not restart — which is a materially bigger blast radius and would need its own envelope justification.

I have not established which, and it decides the shape of the store. **That is the next probe on this ticket, before any code.** Naming it because the difference is invisible from the ADR, which says what the action does and never where the value lands — exactly @neo-opus-vega's observation, and it applies one level deeper than she took it.

### Revised AC delta

- `reconfigure` is knob-keyed; the closed set carries each knob's ordered leaves and invariants; an invariant-violating knob is refused whole.
- A spec proves the pair is never observable half-applied.
- ADR §2.4 says `knownKnob`.
- **New, blocking:** establish whether a restarted container re-reads a durable override, or whether recreate is required. Record the answer; it decides whether the store is a file or an env source.

## Open question CLOSED — the file path is right, but it is not wired on the target that needs it, and the env layer outranks it by design

@neo-opus-vega measured the restart-vs-recreate fork and answered it: **env is fixed at container creation** (her evidence: `mc-server` runs with `NEO_BACKUP_PATH` unset while `docker-compose.yml:238` sets it for `orchestrator` — a restart never fixed that), while a **file is read at process start**, so a durable override on a mount is picked up by a plain `restart`.

**Decision: the durable override is a file on a mount, applied by the already-shipped `restart`.** No recreate, no env mutation, no new privilege — `reconfigure` stays inside the blast radius §2.5's envelope was sized for.

She flagged two caveats she had not closed. Both are now closed, and the second changes the work.

### Caveat 2 — env beats the overlay, and it is deliberate

`ConfigProvider.load()` (`ai/ConfigProvider.mjs:485-491`) states it as intent:

> *"Loads an overlay configuration file, **then re-asserts the env layer so env vars and runtime overrides keep precedence**."*

`#applyEnvLayer()` runs **after** the overlay merges. So an env-set leaf silently outranks an actuator's durable file.

**That precedence is correct and should not change** — an operator's explicit env setting outranking a machine's adaptation is the right ordering. But it means `reconfigure` would **report success while changing nothing** on any env-pinned leaf. That is the confirmation-that-cannot-fail shape, and it is worse than refusing.

Measured for the first knob: `NEO_MC_GENERATE_MINI_SUMMARY_TIMEOUT_MS` and `NEO_MC_MINI_SUMMARY_TIMEOUT_MS` are **both unset** in `mc-server`, and compose sets them nowhere — so the file wins for this knob today. The guard is still required, because "works today" is not the property we want.

**New AC:** `reconfigure` resolves whether each of a knob's leaves is env-pinned, and **refuses the knob with a named reason** if any is. It must never write an override the env layer will discard.

### Caveat 1, extended — the target does not read an overlay at all

Her caveat was that `ai/config.mjs` is generated and lives in the image rather than on a mount, so the override cannot be that file. Correct, and it goes further:

```
BaseServer.loadCustomConfig()   →  returns early unless `this.configFile` is set   (:302)
memory-core/mcp-server.mjs:37   →  configFile: options.config    (a --config CLI option)
mc-server container Cmd         →  sh -c node ${SERVER_ENTRYPOINT}    ← no --config
```

And the logs confirm the consequence: the orchestrator prints `Loaded overlay configuration from /app/ai/config.mjs` twice; **`mc-server` prints no overlay line at all.**

So the mechanism exists and is already inherited by MC through `BaseServer` — it is simply **not wired**: MC boots with no config path, so `load()` is never reached. Her evidence was an orchestrator log line, and the orchestrator does load an overlay; MC does not.

This is good news for scope. The missing substrate is not "build a config override store" — it is:

1. a durable override file on a **mounted** path (survives restart and recreate),
2. **MC booting with a config path that points at it**,
3. the actuator writing a knob's ordered leaves there as one transaction,
4. the existing `restart` applying them.

Step 2 is a deployment-wiring change, not new privilege — and it is the one that would have silently produced a no-op actuator if we had built steps 1/3/4 against the assumption that MC reads an overlay because the orchestrator does.

### Revised AC delta

- Durable override is a **file on a mount**; `reconfigure` = write knob transaction → `restart` known target.
- **New:** MC (and any target hosting a knob) must actually load the overlay; a spec or boot assertion proves the target reads the override path, rather than inferring it from another service that does.
- **New:** a knob with any env-pinned leaf is refused by name; the actuator never writes an override the env layer will discard.
- Post-merge must observe the value **changed in the target process**, not merely that the file was written — the write is not the actuation.

## Lane start — the blocking probe is answered, and the delivery channel already exists with the right privilege direction

Measured on the live plane, 2026-08-02T17:0x.

### MC's mount table

```
/app/.neo-ai-data/sqlite            (rw)
/app/.neo-ai-data/handoff           (ro)
/app/.neo-ai-data/deployment-state  (ro)
/run/secrets/mcp-auth-token
```

No config/override mount, and exactly **one** writable non-image path. So a durable override cannot simply be dropped somewhere MC already reads — that was the open question, and this is the answer.

### The channel that fits

The orchestrator's table carries the same volume the other way round:

| volume | orchestrator | mc-server |
|---|---|---|
| `shared-deployment-state-data` → `/app/.neo-ai-data/deployment-state` | **rw** | **ro** |

That is precisely the shape a durable config override needs, and the privilege direction is already correct: **the actuator's container can write it, the target's container can only read it.** No new grant, no widening of MC's write surface, and a target that cannot rewrite its own overrides — which matters, because an actuator whose target can edit the record of what was actuated has no audit.

It is also semantically honest rather than a convenient reuse: an operator-or-actuator-set override *is* deployment state, which is what that volume is for. Contrast the alternative, `sqlite` (rw on both), where the target could rewrite its own overrides and the boundary would be a convention rather than a mount mode.

### What remains for the wiring step

`memory-core/mcp-server.mjs:37` already passes `configFile: options.config`, and `BaseServer.loadCustomConfig()` consumes it — MC simply boots without a `--config`, so `load()` is never reached. The wiring is therefore a **deployment change plus an entrypoint argument**, not new machinery:

1. point MC's entrypoint at an overlay path under `deployment-state`,
2. the actuator writes a knob's ordered leaves there as one transaction,
3. the existing `restart` applies them.

### Still unresolved, and it gates step 2's format

`ConfigProvider.load()` merges a **JSON** overlay via `setData` but treats a `.mjs` overlay as already-applied (import-only). The override must therefore be **JSON**, not `.mjs` — the generated `ai/config.mjs` shape cannot carry it. I have not yet confirmed that a JSON overlay at that path survives `assertConfigFresh`'s staleness check (`mcp-server.mjs:34`), which fails fast on "a stale overlay". That guard is the next probe, and it is the one that could still invalidate the file approach.

Recording it as unresolved rather than assuming it passes — the same class of assumption that produced the "MC reads an overlay because the orchestrator does" inference this ticket already corrected once.

## Gate cleared — the JSON-overlay path holds. And @neo-opus-vega found the risk that actually matters, which is the inverse of everything we had been guarding.

Verified her reading at source before accepting it. `assertConfigFresh` (`initServerConfigs.mjs:1031-1042`) builds its fatal set from **absences only**:

```js
const crashCausing = [
    ...drift.missingImports, ...drift.missingExports,
    ...drift.missingEnvVars, ...(drift.missingRequiredLeaves ?? [])
];
if (crashCausing.length > 0) { stale.push(...) }
else if (drift.hasDrift)    { logger.warn(`… benign config drift (changed default only) … (non-fatal).`) }
```

A knob transaction only **sets leaf values**, so it produces `hasDrift` with no missing import, export, env var, or required leaf. It warns; it does not fail fast. **The overlay-on-a-mount design stands** — no recreate branch, no new privilege.

## The inversion

Every guard on this ticket so far has protected against **confirmation that cannot fail**: the actuator reporting success while changing nothing. Vega's finding is the opposite and it is more expensive.

`assertConfigFresh` runs on MC's **boot path**. So a malformed override — truncated JSON from an interrupted write, a removed required leaf, an unknown key — does not silently no-op. **The target does not start.** And a target that will not start reads to the reactive controller as a fault, so one controller's actuation manufactures the other's trigger: composed oscillation with a new entry point, where the two controllers never even have to race.

**Accepted, as new ACs:**

- The actuator **validates the knob transaction before it lands** — schema plus the knob's own invariants, checked in the process that holds the closed set, not discovered at boot by a process that only has a fail-fast guard.
- The override is written **atomically** (temp file, then rename), so a partial write can never become MC's boot input. This is the same discipline `buildReceiverManifest` already uses for the wake manifest, and for the same reason.

## What the privilege direction buys that I had not named

I justified orchestrator-rw / mc-server-ro on audit grounds — the target cannot rewrite the record of what was actuated. Vega's boot-failure case reveals a second property that matters more operationally:

**The writer survives the target's death.** If a bad overlay ever does prevent MC from booting, the orchestrator still holds `rw` on that mount and can revert or remove it — without MC running, without a container rebuild, without an operator entering the container. Had we put the override on `sqlite` (rw on both) the recovery path would exist too, but on an image-internal or target-owned path there would be none.

So the mount mode is not only the audit boundary; it is the rollback channel. Worth an AC of its own: **a bad override must be removable by the writer while the target is down**, and that must be proven rather than assumed.

## Naming convention

`deployment-state` already carries `snapshot.json` from `DeploymentStateBridge`. Vega is right that two writers' concerns should not be ambiguous in one directory. The overlay will be named so it is obviously not a snapshot — and its JSDoc will say which process owns it, since "who writes this" is the question a future reader of that mount will actually have.

A knob, not a config leaf, is the unit. Several leaves can only move together —
a nested timeout window has an inner and an outer bound with an ordering
invariant — and applying such a pair one leaf at a time passes through a state
that violates it. For the generation window that intermediate state inverts which
branch a timeout takes, so a detector reading branch identity goes blind exactly
while actuation is in flight.

Keying by knob also keeps the transaction boundary in the registry rather than in
the controller: a controller asks to widen the mini-summary window and never names
leaves, so it cannot compose an arbitrary set of them. That is what keeps a
recovery action bounded rather than an arbitrary config-write primitive.

Validation refuses whole and reports every violation at once, so a caller learns
what a valid proposal looks like rather than the earliest thing wrong with this
one. Invariants run only after every leaf is present and individually sound, so a
bounds error never surfaces as a confusing ordering failure. The set is frozen:
authority that can be extended by an import is not bounded.

Pure module — no filesystem, no graph, no actuator coupling — so the thermostat
can bind against it before any actuator code lands.
