# Backup status is reported by a service that cannot see the bundles

## Context

Operator-directed filing (2026-08-25, in-session) after a live incident: the swarm spent a planning cycle treating **"MC backup has NEVER succeeded"** as the gravest standing fact of the split runway ([D#17782](https://github.com/orgs/neomjs/discussions/17782), revs 5–8) — while the host held **29 daily bundles, 125 GB, newest that same day**, `status: success · restorable: true`, with `mc/`, `kb/`, `graph/` inside. The alarm traveled through a healthcheck read, an A2A escalation, and three coordination-body revisions before one `ls` of `~/.neo-ai/backups` falsified it. The backup mechanism was never broken. **The status surface was lying, and it lied plausibly enough to derail four maintainers.**

Live latest-open sweep: latest 20 checked at 2026-08-25T21:42Z — no equivalent (#17781 is the adjacent truth-label family, different subject); A2A herd window clean for this scope.

## The Problem

Two live specimens of one defect class — **a service reports a state whose artifacts it cannot see, because a different service owns the flow**:

1. **MC backup self-report:** the Memory Core health surface answers `backup: { status: 'backup-never-succeeded', count: 0, lastSuccessful: null }` (plus `off-host-durability-unmet`, `backup-retry-exhausted` classifications). Ground truth at the same moment: the orchestrator's daily backup lane succeeding for 29 consecutive days.
2. **kb-server split-brain:** the bridge reports `kb-server: degraded` while `docker ps` shows the container healthy for 41h. Same shape — two observers, no shared ground truth, and the consumer cannot tell which one is the rumor.

The class is dangerous precisely because the reading is *plausible*: a zero-count from a health endpoint reads as measurement, not as visibility failure. Nothing in the payload distinguishes "nothing ever happened" from "I cannot see where it happens".

## The Architectural Reality

- **The reporter:** `ai/services/memory-core/HealthService.mjs` (~L642–712) computes `lastSuccessful` / `count` by scanning backup bundle state — from inside the `mc-server` container, **where the backup path is not mounted**. Per compose (`ai/deploy/docker-compose.yml`), the host bind for `~/.neo-ai/backups` and the `NEO_BACKUP_PATH` placement exist in the **`orchestrator`** service block only (#16201 / PR #16221, by design: OC owns backup movement). The scan is honest about its view; its view structurally excludes the subject. `count: 0` is a **visibility artifact presented as a measurement**.
- **The owner:** `ai/scripts/maintenance/backup.mjs` (orchestrator-run) writes the ground-truth receipt — `~/.neo-ai/backups/last-backup-receipt.json` (`status`, `integrity.restorable`, `emptySubsystems`, `offHostSync`) — plus per-bundle `bundle-meta.json`. The classification strings originate in `ai/daemons/orchestrator/scheduling/backup.mjs`.
- **The established fix pattern already ships in the same compose file:** `shared-deployment-state-data` — the orchestrator writes a receipt to a dedicated volume; consumers mount it **read-only** ("the orchestrator → public MCP deployment-state bridge", compose comment at the kb-server block). The contract this ticket needs already has a working precedent one service over.

## The Fix

**Reporter reads the owner's receipt — or does not report.** For each specimen:

1. **MC backup status:** `HealthService`'s backup section answers **from the orchestrator-written receipt**, delivered via the established shared-volume-RO pattern (a `shared-backup-receipt` volume or the existing deployment-state bridge — implementer's choice, precedent cited above). When the receipt is unreachable, the surface reports `status: 'receipt-unreachable'` — **never** a zero-count that masquerades as history. The `count`/`lastSuccessful` semantics come from the receipt/bundle-meta, not from a local scan.
2. **kb-server bridge state:** reconcile the bridge's `degraded` computation with container ground truth, or label the reading with its observer (`bridgeView` vs `containerHealth`) so disagreement is visible instead of silent.
3. **The contract, one sentence, in the health JSDoc:** *a health surface may report only states whose ground-truth artifacts it can read; anything else is `unreachable`, never a value.*

## Contract Ledger Matrix

| Target Surface | Source of Authority | Proposed Behavior | Fallback | Docs | Evidence |
|---|---|---|---|---|---|
| MC `healthcheck.backup` | orchestrator receipt (`last-backup-receipt.json`) | values derived from the receipt via RO mount | `receipt-unreachable`, never `count: 0` | HealthService JSDoc contract line | AC-2 negative mutation |
| bridge `kb-server` state | container ground truth + bridge view, labeled | disagreement visible, observer named | — | bridge JSDoc | AC-3 |
| compose volumes | `ai/deploy/docker-compose.yml` | RO receipt mount into mc-server (pattern: `shared-deployment-state-data`) | — | compose comments (house style) | AC-1 |

## Acceptance Criteria

- [ ] **AC-1:** `mc-server` gains read-only visibility of the orchestrator's backup receipt via the established shared-volume pattern; no write authority crosses.
- [ ] **AC-2:** With backups healthy on the host, the MC health surface reports the true `lastSuccessful`/`count`; **negative mutation:** unmount/rename the receipt → the surface reports `receipt-unreachable` — a run proving it can no longer emit `count: 0` while bundles exist.
- [ ] **AC-3:** The kb-server bridge/container disagreement is either reconciled or observer-labeled; the split-brain from 2026-08-25 is reproducible-then-fixed or documented as reconciled.
- [ ] **AC-4:** The one-sentence reporter-reads-owner contract lands in the health-surface JSDoc, citing this incident as the anchor.
- [ ] **AC-5:** A spec covers the visibility-vs-measurement distinction: zero-with-receipt-present FAILS, unreachable-without-receipt PASSES.

## Out of Scope

- Enabling the **off-host sync tier** (`offHostSync.status: "disabled"` — the true durability residual; operator decision, adjacent tickets #16516 / #17338 per Wave-0 retraction context).
- The backup mechanism itself (healthy, untouched).
- The Wave-0 plan-gate defect (cohort-wide evaluation — separate finding, Ada's lane).
- Widening `BackupRootPlacement.spec.mjs` beyond its current service scope (design-consistent once OC-owns-backups is the frame; reopen only if a second durable-state service is ever supposed to self-back-up).

## Avoided Traps

- **Bulk-copying `NEO_BACKUP_PATH` into mc/kb service blocks** — treats the visibility artifact by making three services believe they own a flow one service runs; multiplies writers instead of fixing the reader.
- **Deleting the MC backup health section** — silence is worse than `receipt-unreachable`; consumers (fleet cockpit, healthchecks, the next split runway) need the truthful value.
