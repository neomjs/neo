# The ingest receipt names the stage that failed and drops why

## Context

Diagnosing a live external deployment on 2026-08-07, the only thing readable about its embed failure was:

```
lastErrorCode       = KB_TENANT_REPO_SYNC_SYNC_FAILED
lastSourceErrorCode = KB_VECTOR_EMBED_FAILED
lastIngestedRev     = null
```

That is the whole receipt, and it names a **stage**. Hours went into deciding whether it was the same defect as `#16566`, which had been diagnosed on a different plane — a question the receipt could not answer either way, because the code it carries is the same regardless of cause.

## The Problem

`ai/services/knowledge-base/IngestionService.mjs:388` and `:406`:

```js
code: result.code || 'KB_VECTOR_EMBED_FAILED',
```

**`KB_VECTOR_EMBED_FAILED` is a fallback.** It fires precisely when the underlying error carried no code of its own — so the receipt is at its least informative exactly when the failure is least understood. A provider error that *does* carry a code surfaces it; the unrecognised ones, which are the interesting ones, all collapse to one string.

The `message` and `details` are attached at the throw site. They do not reach the surface a remote diagnostician reads: `snapshot.tenantRepoSync.repos[]` carries `lastSourceErrorCode` and no message field. So the detail exists in the process and is absent from the artifact.

**Why that is expensive rather than untidy.** The code spans providers that share no implementation. `TextEmbeddingService` branches at `:1043` / `:1059`:

| deployment | `NEO_EMBEDDING_PROVIDER` | transport | branch |
|---|---|---|---|
| external | `ollama` | in-compose container | `#embedOllama` |
| this plane | `openAiCompatible` | host process | the openAiCompatible request queue |

Two deployments reporting `KB_VECTOR_EMBED_FAILED` may share nothing but the stage at which they stopped. Treating the match as a shared defect is the natural reading and it is unsupported — I made exactly that inference and stated it in a deployment guide before checking the branch.

## The Architectural Reality

- `ai/services/knowledge-base/IngestionService.mjs:388,406` — the fallback, with `message` and `details` populated but not carried.
- `ai/services/memory-core/TextEmbeddingService.mjs:1043,1059` — the provider split the single code sits above.
- `snapshot.tenantRepoSync.repos[]` — the remote-readable surface; `lastSourceErrorCode` only.
- `#16568` is the neighbouring gap on the revision axis: a deployment could not report which commit it runs. Same family — a fact the process holds and the artifact drops.

## The Fix

Direction, not prescription.

**Carry a bounded cause alongside the code.** The receipt already has `message` and `details` at the throw site; the surface needs a redacted, length-capped `lastSourceErrorMessage` (or a provider-plus-reason pair) so a reader can tell two different faults apart without shell access to the box.

**And make the fallback rarer.** A provider error reaching this point without a code is itself the defect — the ollama and openAiCompatible branches should classify their own failures, so `KB_VECTOR_EMBED_FAILED` means "unclassified" rather than "embedding, cause unrecorded".

Redaction is a live constraint, not an afterthought: provider errors can echo request content. Whatever surfaces must be bounded and scrubbed by construction rather than by hoping the message is short.

## Acceptance Criteria

- [ ] Two embed failures with different underlying causes are distinguishable **from the deployment-state snapshot alone**, with no shell access to the host.
- [ ] Coverage that fails on today's shape: a spec asserting the surfaced receipt differs between two distinct injected provider errors. A spec asserting the code is present passes today and proves nothing.
- [ ] Whatever is surfaced is length-capped and redacted at the boundary, with a test that a provider error echoing request content does not leak it.
- [ ] `KB_VECTOR_EMBED_FAILED`'s meaning is documented at the throw site as *unclassified*, so a future reader does not repeat the "same code, same defect" inference.

## Out of Scope

- `#16566` — the embed-stage failure on this plane. This ticket is why that one is hard to compare against any other deployment, not the failure itself.
- Fixing any particular provider's error classification. Naming the gap is enough here; the branches can be done as they are touched.
- The tenant-sync error taxonomy above the ingest layer.

## Avoided Traps

- **Reading a shared error code as a shared fault.** It is the intuitive inference and the code's construction makes it wrong: a fallback string says the most when the cause is known and the least when it is not.
- **Assuming the detail is lost because it was never captured.** It is captured — `message` and `details` are both populated at the throw. Only the surface drops them, which makes this a plumbing fix rather than an instrumentation project.
- **Surfacing the raw message.** Provider errors can quote the input. The fix is a bounded, redacted field, not a passthrough.

Durable tenant-repo state admits only codes matching `^KB_[A-Z0-9_]{1,120}$` — a
credential boundary, since such a code cannot carry a clone URL, a token or stderr.
Embed failures arrive in the provider's vocabulary (`EMBEDDING_PROBE_TIMEOUT`,
`ABORT_ERR`). Those are truthy, so `error.code || 'KB_VECTOR_EMBED_FAILED'` never
fired for one: the provider code was recorded, then dropped by the `^KB_` filter,
landing `lastSourceErrorCode` as null.

The result was backwards. A provider that classified its failure well produced a
receipt with no cause; one that threw a bare Error produced at least a stage name.
Better upstream classification made the observable strictly worse, which is why
widening the filter is the wrong fix and translating at the boundary is the right one.

`classifyEmbedFailureCode` maps provider codes into the bounded namespace by
allow-list, so every returned value is either a literal declared in the module or a
string that already satisfied the pattern — provider-controlled text cannot reach
durable state by construction rather than by escaping. An unrecognised code is
reported as unclassified, and `KB_VECTOR_EMBED_FAILED` is documented as meaning
exactly that, so two deployments sharing it are not read as sharing a defect.

The bounded pattern moves to the module that produces codes for the boundary; the
orchestrator's sync service imports it instead of re-declaring the literal, so
producer and filter cannot drift into a pair that separately look correct.

Coverage is red on the defect: under the pre-fix shape 6 of 7 specs fail, including
distinctness, boundedness and the leak guard. The survivor is correct — an
already-bounded code passes through in both shapes.

## Scope amendment — this ticket now covers the *coded* half; the codeless half is #16658

Recording this on the ticket rather than only in the PR, because the body above frames the problem from an observation that **PR #16657 does not fix**, and a future reader mining this ticket would otherwise conclude the wrong thing.

**What #16657 actually delivers.** Not what I filed this for. The defect it found is an *inversion*: provider-classified failures (`EMBEDDING_PROBE_TIMEOUT`, `ABORT_ERR`) are **truthy**, so `error.code || 'KB_VECTOR_EMBED_FAILED'` never fired for them — the provider's own code was recorded, then discarded by the writer-side `^KB_` namespace filter, landing `lastSourceErrorCode` as `null`. A well-classified failure produced a receipt with *no* cause while a bare `Error` produced at least a stage name.

**What it does not deliver.** The receipt quoted in the body above — `lastSourceErrorCode = KB_VECTOR_EMBED_FAILED` on a live deployment — came from a failure carrying **no code at all**. That took the fallback before and takes it now. The string is unchanged; what changed is that it is now accurate and documented as *unclassified* rather than silently standing in for "embedding, cause unrecorded".

So the AC *"two embed failures with different causes are distinguishable from the snapshot alone"* is met for **classified** causes only. #16658 carries the uncoded case, where the real gap sits upstream: `VectorService` sets a code on exactly one path, so the classifier downstream has nothing to translate.

**Why the split rather than leaving this open.** @neo-gpt raised it in review — closing a ticket whose motivating observation is untouched marks the wrong thing fixed. My first remedy was `Refs` instead of `Resolves`; `lint-pr-body` rejects that, and I read the conflict as substrate friction. He then checked and falsified me: **#12367 already defines the mechanism** — a partial PR resolves its own fully-delivered scope and the remainder gets a named successor. The representation existed; I did not know it. No template gap.

Correction filed as a constraint rather than a note: **a `Resolves` on a ticket whose framing observation is untouched is an over-claim even when the ACs technically read as met.** The check is whether the *reported symptom* changed, not whether the checklist can be ticked.

distinct non-null `details.repos[].lastSourceErrorCode`. No `KB_*` literal appears
between the provider error and the assertion, so producer, filter and projection all
have to agree.

Proved against both failure directions rather than one: mutating the classifier back
to `code || KB_VECTOR_EMBED_UNCLASSIFIED` reddens it, and so does dropping
`error.sourceErrorCode` in the middle — the case the earlier witness could not see.

The read-boundary block is kept but renamed and re-scoped to what it proves, since
presenting it as the end-to-end witness was the actual defect. It still carries the
control that the raw provider code is refused by that reader.
