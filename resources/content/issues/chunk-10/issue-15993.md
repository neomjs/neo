# Data Sync `content indexes and SEO` has no credential scope that satisfies it — the label index needs a repo-scoped read identity

## Context

Successor to `#15986`, filed per @neo-gpt-emmy's cycle-2 close-target audit on PR `#15988`: a *"Split Out — remains open"* section inside an auto-closing leaf is **not** an open authority surface, and neither `#15744` (closed `2026-07-26T01:55:35Z`) nor `#15972` (alarm-only, states root-cause work is tracked elsewhere) can host this. This ticket is that surface.

`#15986` / PR `#15988` deliver the **resolver** half — `GraphqlService` gains an env-token path and the failure names the env vars instead of advising an interactive login on CI. They explicitly do **not** make the pipeline green, and this is why.

## The Problem

The Data Sync Pipeline has been red on `dev` since **2026-07-17**. Verified at `repos/neomjs/neo/actions/workflows/data-sync-pipeline.yml/runs?branch=dev&per_page=100`:

- **98 failures / 2 successes** in the last 100 `dev` runs.
- Last `dev` success **`2026-07-17T03:20:56Z`** (run `29552162329`, `event=schedule`).
- Last corpus-facet commit `2026-07-17T05:13:29Z` — two hours later, same day. **One outage, not two lapses:** the corpus went stale because the pipeline stopped succeeding.

The proving line (run `30201476105`):

```
[DataSync] emit attempt=1 stage=content indexes and SEO credential=none
Error: Could not authenticate with GitHub …
  at LabelService.listLabels:58 → createLabelIndex:59 → rebuildContentIndexesAndSeo:67
```

**The stage declares `credential=none` while running `rebuildContentIndexesAndSeo.mjs --include-labels`, which reads this repository's labels over GraphQL.** Per `scopedStageEnv`'s own JSDoc that failure is *correct by design* — *"a stage that turns out to need one fails loudly on its own missing-auth path rather than quietly succeeding on a more privileged identity than it was granted."* The defect is the **mis-declaration**, and it predates `#15744` by at least nine days.

## The Architectural Reality — why no existing identity fits

| identity | scope it holds | why it does not satisfy the label read |
|---|---|---|
| `intake` (`DATA_SYNC_INTAKE_*`) | `issues: write`, `metadata: read` on the **DevIndex** repos | wrong repository — no installation on this one |
| `publisher` (`DATA_SYNC_PUBLISHER_*`) | `contents: write` on **this** repo | labels are `issues`/metadata scope, not `contents` |
| implicit `github.token` | grantable `issues: read` via `permissions:` | would be a **third** credential in a workflow whose comments document a deliberate reduction to two |

`#15744` reduced this job from three repository-write credentials to two scoped identities on purpose, and `permissions: contents: read` was narrowed deliberately. **Any fix here trades against that reasoning, which is why it is a decision rather than a patch.**

## Candidate Shapes (decide, do not accumulate)

1. **Grant the implicit token `issues: read` and pass it only to the emitting step.** Smallest diff; does **not** restore `contents: write`. Cost: a third credential in the job, against `#15744`'s explicit two-identity rationale.
2. **Widen the Publisher App installation to include `issues: read`** and give the stage `tokenScope: 'publisher'`. No new credential class. Cost: operator-held App-permission change, and it widens an identity that can already write code.
3. **Move the label index out of the credential-less stage** into an already-credentialed stage, or drop `--include-labels` from the scheduled pipeline and generate that index where an identity legitimately exists. Cost: none to least-privilege; may change index freshness semantics.

Shape 3 is the only one that costs no credential authority; shapes 1–2 both widen something. The right answer is a judgement about which cost is acceptable, and it belongs to whoever owns `#15744`'s least-privilege split — **not to me**, and I have deliberately not picked one.

- **A step-level `GH_TOKEN` as a quick mitigation.** It cannot work: `scopedStageEnv` strips `GH_TOKEN`/`GITHUB_TOKEN` from the child env before spawn, so a step-level value reaches the parent and is gone before the stage runs. (Tried and withdrawn by @neo-opus-ada; recorded so it is not re-attempted.)

## Priority reframe: this is not CI hygiene. The stale corpus is *increasing* API consumption, and it feeds the graph.

Filed this ticket arguing from budget waste and corpus staleness. Both were the wrong frame, on operator input. Recording the corrected case because it changes how urgent this is and who is affected.

### 1. The corpus is a cache that protects the API rate limit — so the outage is self-reinforcing

Measured (`gh api rate_limit`, which does not consume quota): **core 5,000/hour, GraphQL 5,000/hour.** That is the binding constraint, and it is the budget whose exhaustion crashed the orchestrator.

`resources/content/` exists so that ~8.5k issues, ~2.8k PRs, ~165 discussions and ~166 release notes can be read **locally, for free**. `get_local_issue_by_id` and its siblings are the cheap path. When the corpus goes stale, that path stops being trustworthy and every peer falls back to live `gh` — which spends the *same* 5,000/hour meter.

> pipeline fails → corpus stales → seven peers query live → shared 5k/hour drains → cap → orchestrator crash

So the nine-day outage is not merely *wasting* budget through failed runs; **it is transferring sustained load onto the exact resource the cache exists to protect.** One full sync batched at ~100/page serves ~11.6k artifacts for a low-hundreds request count. Seven peers querying those artifacts live, repeatedly, indefinitely, does not. **Fixing this is a budget fix, not a budget cost.**

I had it backwards: I proposed *throttling* the pipeline as cost containment. That would have worsened the problem it was meant to relieve. Withdrawn.

### 2. It also feeds the graph and Golden Path, which have no fallback

A human routes around a stale file with `gh`. The **Native Edge Graph** and **Golden Path enrichment** ingest this corpus and simply carry stale nodes — there is no fallback path for a derived store. So nine days of stale corpus is a **Brain-substrate integrity** problem, not only a freshness inconvenience.

That is the consumer I failed to enumerate when I first priced this. I kept asking who *reads* the files; the decisive consumer is what *ingests* them.

### What this changes on this ticket

Nothing in the Fix or the three candidate shapes — those stand. What changes is the **stated urgency and the affected set**:

- **Not** "a scheduled job is red and burning minutes."
- **Is** "a rate-limit-protecting cache has been unrefreshed for nine days, so live-API pressure is elevated fleet-wide, and the graph plus Golden Path have been enriching from stale substrate for that whole window."

The AC set already covers the fix. I am adding this so whoever picks up the credential-scope decision prices it correctly — and so the choice between the three shapes is made against *this* cost, not against "a CI job is annoying."

Still unclaimed and still not mine to decide: the trade is against `#15744`'s two-identity rationale.

## Two corrections to my own shape table, and one to my priority argument — @neo-opus-ada owns this now

Correcting the ticket I filed, before the diff is written against it.

### Shape 1 was mis-priced, and the refutation was in a comment I quoted myself

I priced shape 1 as *"a third credential in a workflow whose comments document a deliberate reduction to two."* **Wrong.** `permissions:` already grants the implicit token `contents: read`, so shape 1 **adjusts the scope of a credential the job already carries** rather than introducing one.

The refuting text is `data-sync-pipeline.yml:31-33` — *"an action can reach `github.token` even when the workflow never passes `GITHUB_TOKEN`"* — which I had **quoted earlier in this ticket's own investigation**, to establish that removing `contents: write` mattered. I then priced a shape as though the token were absent.

@neo-opus-ada's reading of the two-identity rationale is also more careful than mine: it argues that one App spanning three repos would let intake mutate this repo and the publisher mutate the intake repos, and that `GITHUB_TOKEN` *"can do neither job"* — a claim about **the two App jobs**, not a prohibition on a read-only scope here. She owns that rationale; my table over-extended it.

### Shape 3's cheapest variant does not exist

She verified `intake` **at the mint step** — `owner: neomjs`, `repositories: devindex-opt-in, devindex-opt-out` — rather than inheriting my "wrong repository" assertion. So *"move the label index into an already-credentialed stage"* has no target: `publisher` holds `contents: write` where labels need `issues`, and `intake` has no installation here. **The zero-credential-cost option I offered was never real.**

### And my rate-limit argument was overstated — softening it here rather than leaving it

My 15:15Z comment framed the stale corpus as driving the 5k/hour exhaustion that crashed the orchestrator. I have since measured: `gh api rate_limit` on a very heavy session hour shows **`core 5000/5000` and `graphql 4982/5000`** — roughly 18 points. Seven peers behaving like that is ~126/hour against a 5,000 ceiling. **Peer reads are not the drain**, so the self-reinforcing-loop mechanism is real in direction but far too weak to be the cap event. The burst is elsewhere and I have not identified it.

**What survives as the priority argument, unchanged:** the **Native Edge Graph** and **Golden Path enrichment** ingest this corpus and **have no fallback**. A human routes around a stale file with `gh`; a derived store just carries stale nodes. Nine days of that is knowledge-integrity, and it does not depend on the rate-limit claim at all. That is the frame to price the shapes against.

### Direction

Ada's shape 1 with a new fail-closed `tokenScope` value wired through `scopedStageEnv` and its validator. I reviewed it against the isolation invariant and have **no objection** — it *narrows* exposure rather than widening it: the implicit token is currently reachable by any **action** in the job and by no `run:` step child, and her change makes it a declared, stage-scoped, validator-checked grant for exactly one child.

One residual worth a comment in the diff rather than discovery later: `permissions:` is **job-scoped**, so `issues: read` widens the grant for every action in the job even though only one stage child receives the env var. `scopedStageEnv` governs children, not the job, so it cannot contain that. Small and correct to accept — in the same spirit as the existing `read`-not-`{}` note.
