# KB class-hierarchy metadata degrades silently on cloud deployments: the image never builds the artifact and nothing fetches it

## Context

Observed in a live cloud deployment's kb-server logs, as the **only** application-level line in the tail:

```
[ApiSource] Class hierarchy file not found at /app/docs/output/class-hierarchy.json.
'extends' metadata will be incomplete.
```

The server reports `status: "healthy"` and `"All features are operational"` alongside it.

## The Problem

`docs/output/class-hierarchy.json` is a **generated** artifact — produced by `buildScripts/docs/generateDocsJson.mjs` — and the Knowledge Base treats it as a first-class input: it is a config leaf (`hierarchyPath` in `ai/mcp/server/knowledge-base/configBase.mjs:266`) and is listed among the files `PrimaryRepoSyncService` keeps in sync.

On a cloud deployment neither producer runs:

1. The deploy image build has **no docs-generation step**, so the artifact is absent from the image.
2. Primary-dev-sync — which would fetch it — is **disabled** in the cloud profile (`NEO_ORCHESTRATOR_PRIMARY_DEV_SYNC_ENABLED=false`), correctly, since a client deployment should not sync our dev repo.

So there is no path by which the file can exist on such a deployment, and `get_class_hierarchy` plus every `extends`-bearing answer is quietly incomplete. **Health stays green**, because a missing optional input degrades rather than fails.

**Not a regression** — no cloud deployment has ever had this artifact.

## The Architectural Reality

Degrading rather than crashing on a missing enrichment input is the right call; a KB that refuses to start because `extends` metadata is unavailable would be worse. The gap is that the degradation is reported **only** as a log line, in a component whose logs an operator has no reason to read while `healthcheck` says healthy — so the deployment is permanently and invisibly less capable than intended.

This is the same shape as two siblings filed today: the system knows something the operator cannot see. Here it is even quieter, because nothing failed.

Two candidate fixes, and the choice is a real decision rather than an implementation detail:

- **Build it into the image** — the artifact is derived from source already present at build time, so this is the self-contained option and needs no runtime fetch.
- **Declare it optional and surface the degradation** — if cloud deployments are not expected to carry it, `healthcheck` should say so instead of claiming all features operational.

These are not exclusive; the first makes the capability whole, the second makes any future absence visible. My read is that both belong, with the build step as the primary.

## Acceptance Criteria

- [ ] Decide and record whether cloud deployments are expected to carry class-hierarchy metadata. Everything else follows from that; the ticket should not proceed on an assumed answer.
- [ ] If expected: the deploy image generates `docs/output/class-hierarchy.json` at build time, verified by asserting the file exists in a built image.
- [ ] Either way: `healthcheck` reports the degradation instead of `"All features are operational"` while an input it depends on is absent — a green health check must not coexist with a known-incomplete capability.
- [ ] `get_class_hierarchy` states that its answer is incomplete when the artifact is missing, rather than returning a partial result indistinguishable from a complete one.
- [ ] A fixture pins the degraded path, so the honest-reporting behaviour cannot regress once the file is present in CI.

## Out of Scope

- Changing what `ApiSource` extracts, or the hierarchy format.
- Re-enabling primary-dev-sync on client deployments — correctly disabled.

Operator-supplied architecture that the original body did not have. Recording it here so the next reader does not re-derive it from two build scripts, which is what I had to do.

### What this artifact actually is

`class-hierarchy.json` backs a **neo-code-only KB tool** — `get_class_hierarchy` answers questions about *neo's own* class hierarchy. It is read **directly from disk**, not embedded into Chroma. Early on the full docs output *was* dumped into Chroma; **that part was removed.** The direct-read hierarchy path remains.

Three corrections to the original framing follow:

1. **This is not an ingestion dependency.** It cannot block KB ingestion, and does not contribute to the empty-corpus problem in #16057. The two are unrelated failures that happened to surface in the same log tail.
2. **The producer is confirmed and live.** `buildScripts/docs/generateDocsJson.mjs:470-475` is an explicit `writeJSON({path: './docs/output/class-hierarchy.json', force: true}, …)` — the sole writer. `package.json:109` still exposes `generate-docs-json`, refactored nine days ago in `acbdfd8360`. Worth stating because the pipeline's status was genuinely ambiguous from the outside; the operator's initial read was that this had been dead for 6+ months, and the file's own history is what settled it.
3. **The real prerequisite is heavier than "add a build step."** Producing this artifact on a client deployment requires `npm i` **plus** the docs build (or `build-all`) against the neo repo in use. That is a substantial addition to image build time and size — not a one-line Dockerfile change.

### Which makes the first AC a genuine product decision, not a formality

**Does a client deployment need `get_class_hierarchy` at all?** It answers questions about *neo's* internals. For a tenant whose KB is ingesting *their own* repositories, that may be of no value — or it may matter precisely because they build on neo. That is a customer-facing scope call, and it determines the fix:

- **Yes, clients need it** → the image must run `npm i` + docs build. Accept the build-time and size cost, and state it, because someone will later ask why the image grew.
- **No, clients do not need it** → the tool should not be *exposed* on those deployments at all.

### The concrete defect either way

`get_class_hierarchy` **is currently advertised in `tools/list` on a deployment where it cannot work.** A user can discover it, call it, and receive a degraded answer, while `healthcheck` reports `"All features are operational"`. An exposed tool with an unsatisfiable dependency is worse than an absent one: absence is self-explanatory, degradation is not.

So regardless of which way the scope decision goes, the honest-reporting ACs stand, and one is now sharper:

- [ ] A tool whose backing artifact is absent must not appear in `tools/list` as though usable, **or** must state its degraded state in its own response — not only in a log line and not while health claims full operation.

### Revised root cause

The original body pointed at "the image lacks a build step," which is the symptom. The root cause is that **the coupling is undeclared**: a live KB source consumes a build artifact with no declared dependency on the step that produces it — no manifest entry, no build-order assertion, nothing that fails when the producer never ran. That is why it degrades to an unread log line rather than a startup refusal, and it is why the dependency's very existence was arguable between two maintainers who both know this codebase.

Fixing the declaration is what prevents the next instance of this class; fixing the image only fixes this one.

### What this tool actually is

`class-hierarchy.json` backs a **Neo.mjs-code-only** tool. In the early days the full docs output was dumped into Chroma; **that was removed.** What remains is a direct-from-disk read serving Neo.mjs hierarchy queries — no embedding, no corpus participation.

So producing it on a client deployment requires `npm i` **plus** the docs build (or `build-all`) against the Neo.mjs repo in use. That is a heavy image-build addition for a tool that answers questions about *our* framework's internals.

### Priority: low. A tenant has no near-term need for this.

The realistic horizon for a tenant needing Neo.mjs hierarchy queries is **months**, not weeks. So the expensive limb — running the docs build in the deploy image — should not be scheduled against this ticket now.

**Hard constraint on whatever is eventually done here: it must not touch any ingestion path.** This tool is corpus-independent by design, and coupling it to ingestion to "fix" its absence would trade a cosmetic gap for a real outage.

### Already shipped: the description fix

`get_class_hierarchy`'s description now states the scope explicitly — **Neo.mjs framework code only**, with a not-covered clause routing non-Neo.mjs code questions to `query_documents` / `ask_knowledge_base`, and a note that it reads a generated build artifact so its answer is independent of ingestion state and empty/partial without the docs build.

Description-only; no ingestion path touched. 915 chars against the 1024 cap; `McpServerToolLimits` green.

That was the acute problem — the tool was **advertised in `tools/list`** on a deployment where it cannot work, describing itself as "the static class hierarchy from the knowledge base," which a caller reasonably reads as covering whatever that knowledge base ingested. On a tenant plane holding their own repositories, that reading is wrong in the most misleading possible direction.

### One correction to my own earlier analysis, and it matters elsewhere

My previous comment asserted this and the empty-corpus failure were "two unrelated failures that happened to surface in the same log tail." **The second half of that is wrong in a way that affects #16057's priority.** `IngestionService` resolves `useDefaultSources` defaulting to **`true`**, imports `SourceRegistry`, and a tenant config that does not disable it inherits the full default Source set — including `PullRequestSource`, which throws on our duplicated corpus artifacts.

If that inheritance holds on the pull path, **our corpus defect blocks a tenant's ability to ingest their own repositories**, which would explain the otherwise-unexplained `consecutiveFailures: 3` carrying null error codes: a thrown Source error, uncaptured. That elevates #16057 from internal hygiene to the thing standing between a deployment and any KB value at all, and it should be confirmed as #16057's first move.
