# Cockpit layout ergonomics: the grid/timeline splitter is invisible, the left rail oversizes its tabs, the right rail undersizes its panels

## Context

Operator UX escalation (screenshots, 2026-08-15, same session as #17209/#17210 — this ticket owns the LAYOUT AFFORDANCE half; #17209 owns skins/shell):

1. **The splitter between the agent-card grid and the activity timeline is invisible.** A resizable boundary exists functionally but carries no visual affordance — no handle, no hover state, no cursor hint. Operators cannot discover it.
2. **Proportion imbalance between the two rails.** The left navigation rail (Home / Fleet / Accounts / Chat) renders large — possibly too large — while the right side-tab rail (Agent detail / Perspectives / Add agent / Catch up / Memories / Wake routes / Operator) renders as cramped rotated text, and the panels it opens use their width poorly (small content in a large drawer).
3. **Side-panel content density**: the drawer content sits small inside its area — the space is claimed but not used.

## Acceptance Criteria

- [ ] The grid/timeline splitter is a designed, discoverable affordance: visible divider, hover/active states, resize cursor — consistent with the fleet look (SCSS token/skin layers only, zero CSS-in-JS).
- [ ] Rail proportions rebalanced: left-rail tab sizing reviewed against its information density; right-rail tabs legible without squinting (size, spacing, active state) — one deliberate proportion decision, documented in the PR body.
- [ ] Drawer content uses its width: pane content lays out to the drawer's actual measure (no fixed narrow column floating in dead space) — verified on the panes that already have skins; the skinless panes inherit this via #17209's shell contract.
- [ ] Acceptance surface: the offline topology (first-run view), light and dark themes.

## Sequencing

Independent of #17209's shell/skin work at the splitter + rails level; the drawer-density AC lands cleanest AFTER #17209's shell contract exists — slice accordingly.

### ⚠️ Correcting myself before it propagates

Earlier today I broadcast — and nearly wrote here — that *"the engine owns the drawer's motion and not its measure."* **That is false**, and I withdraw it. The engine owns the measure:

- `src/dashboard/Container.scss:373-387` — `position`, `z-index: 20`, hidden-state, and per-edge `inset` (`0 auto 0 14px` left, `0 14px 0 auto` right).
- **`src/dashboard/DockRevealOverlay.mjs:412-432`** — the free dimension: `fraction = revealExtent ?? defaultRevealFraction` → `style.width` (left/right) or `style.height` (top/bottom), as a percentage.
- `DockRail.mjs:83-86,633-636` · `DockLayoutAdapter.mjs:387,516` — `defaultRevealFraction` threaded per consumer through projection options.

I got it by grepping `dock-reveal` in the engine, reading the first block (the animation keyframes at `:88-106`), and stopping — while the refuting block sat at `:373` **in the same grep output I was quoting from**.

**This changes the diagnosis, and in the direction that keeps this ticket small.** AC-3 does *not* need an engine promotion, so **no third leaf on #17241** and that parent's remaining scope is unchanged. Measured instead:

- `DockRevealOverlay.defaultRevealFraction_ = 0.25` — drawers open at 25% of workspace extent.
- **No app anywhere sets `defaultRevealFraction`** (`grep -rn 'defaultRevealFraction' apps/` → zero hits). Every consumer takes the engine default.
- In the cockpit's `.neo-dashboard-dock-reveal-pane-slot`, only **`.fm-add-agent-form`** carries `width: 100%` (it needs it — it also sets `align-self: flex-start`, which drops the column-flex cross-axis stretch). Every other hosted pane root gets `gap` + `min-height: 0` and **no width rule**.

So AC-3's "space claimed but not used" is one of: the fraction is wrong for this surface, or the panes do not fill the width they are handed. That is a **number**, and the two answers take opposite fixes.

### Instrument — and an honest negative result

I tried to settle it live. Started the dev server, loaded `/apps/agentos/index.html`, confirmed the cockpit mounts (`.agent-shell`, `.fm-fleet-grid`, one `edge-rail`, four rail-tabs, one reveal-overlay). Then the geometry came back **`innerWidth/innerHeight` 0×0, `documentElement.client*` 0×0, `body` 0×0** — while a child rail-tab still reported `h: 98`. `resize_window` did not move it.

**So the numbers this harness gives me for this surface are not real geometry, and I am not building a verdict on them.** Recording that as a negative result rather than quietly switching instruments: the first partial read (rail `w: 14`, tabs `w: 14 × h: 76–98`) is *consistent* with AC-2's "cramped rotated text", but consistent-with is not measured, and a 0×0 document can produce a plausible-looking number.

The real instrument already exists and is where this ticket's acceptance evidence has to live anyway:

- `test/playwright/e2e/agentos/FleetCockpitDockGeometryNL.spec.mjs`
- `test/playwright/e2e/agentos/FleetCockpitAutoHideRailNL.spec.mjs`

**First implementation step**, before any fix: extend the geometry spec to record, at a real viewport, the reveal overlay's box against its hosted pane root's box, and the two rails' measures. That number chooses the fix instead of me choosing it.
