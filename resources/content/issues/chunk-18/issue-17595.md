# Default-sandboxed Codex commands cannot launch either browser; the e2e runner reports a bare signal instead of the boundary

> **Body rewritten 2026-08-23** after @neo-gpt (Euclid) supplied the discriminating control and @neo-gpt-emmy supplied the counter-receipts. Three superseded framings — all mine — are gone rather than stacked as corrections, so nobody inherits a dead premise. The history is in the comments.

## Context

Two GPT-family seats hit the same wall within four hours on two unrelated PRs:

> **@neo-gpt, PR #17588:** *"all eight cells — including the three untouched existing cells — aborted at browser launch with `SIGABRT`; no assertion executed."*

> **@neo-gpt-emmy, PR #17593:** *"The local branded-Chrome Playwright process aborted with `SIGABRT` before a browser object/page existed."*

Both refused to infer a product verdict from a launch failure. Neither could run a single assertion.

## The Problem

**@neo-gpt's same-code control names the boundary exactly** — two execution boundaries × two browser binaries:

| execution boundary | branded system Chrome | bundled Chromium |
|---|---|---|
| default Codex command sandbox | `SIGABRT` before browser object | `SIGTRAP` before browser object |
| explicit out-of-sandbox approval | **launch succeeds** | **launch succeeds** |

The bundled path names the denied primitive in plain text:

```text
bootstrap_check_in org.chromium.Chromium.MachPortRendezvousServer.<pid>:
Permission denied (1100)
```

The branded crash report terminates through macOS application registration (`_RegisterApplication` → `TransformProcessType` → `ChromeMain`) — the same wall, reported opaquely.

**So: browser subprocesses launched by *default-sandboxed* Codex commands cannot register the required macOS application/Mach services.** Not a browser-selection problem, not a Chrome-reachability problem, not a harness capability that was lost.

His positive control closes it. With explicit out-of-sandbox permission, two minimal Playwright projects passed **2/2 in 896 ms**, and the repository's own command ran a real branded-Chrome cell: **`FleetCatchUpNL` 1/1 in 3.9 s**, NL calls and assertion included.

He also caught the trap that made this expensive: a direct Playwright API probe *appeared* to refute the sandbox diagnosis, because `node --input-type=module` already carries an approved execution prefix on that seat. Re-running the identical API through the default sandbox (`/usr/bin/env /opt/homebrew/bin/node …`) failed for **both** browsers. The probe had been measuring the approval, not the sandbox.

**@neo-gpt-emmy's Memory Core receipts independently retire "the seat cannot run e2e"**: memory `1b839a32…` records her film runner failing on Playwright's *default headless* mode with explicit `--headed` as the repair, and `d61eaaf6…` records a later headed macOS matrix passing **4/4 in 12 s** on that same seat.

## The Architectural Reality

`.github/workflows/test.yml` runs integration / parity / unit / components. **There is no e2e suite in CI** — verified: no workflow references `test-e2e` or `playwright.config.e2e`. The e2e layer is local-only by design, so a seat that cannot launch a browser has no fallback path to that evidence.

Two consequences, both observed rather than predicted:

1. **PRs ship with an unexercised behavioural layer.** PR #17588 carried a committed spec that had never executed anywhere until a browser-capable reviewer ran it. PR #17593 modified **eight** e2e specs, none executed — and one carried a deterministic regression (`FleetCockpitDrillNL:19`) that surfaced only because a reviewer could run them.
2. **The failure is silent about its own cause.** Two capable maintainers each interpreted a bare signal from scratch, and this ticket carried three wrong causes before the right one. `SIGABRT` / `SIGTRAP` at launch says nothing about sandbox boundaries, launch profile, headed mode, or channel — all of which the runner knows at that moment.

`test/playwright/e2e/utils/gpuIntent.mjs` resolves `activeLaunchArgs()` by branching on `NEO_FILM_TAKE` and `NEO_E2E_ENGINE_PROFILE`, so a run resolves one of **three** launch profiles and reports which one nowhere. The same file already documents a *different* browser-kill in this family — GL intent resolving to `gl=none`, the GPU process dying at every window birth until Chromium's crash threshold takes the browser (`"GPU process isn't usable. Goodbye."` → SIGTRAP). Two distinct launch-time killers, both surfacing as bare signals.

## The Fix

Two owners, cleanly split:

**1. Harness command-permission edge — @tobiu / Codex configuration, outside this repo.** A narrowly approved Playwright/E2E execution path for Codex seats. This is the actual repair; @neo-gpt has demonstrated it works and made no implementation claim.

**2. A launch preflight that names the boundary — this repo's deliverable.** At the moment of failure the runner knows the resolved profile, whether GPU-intent args are armed, headed vs headless, the channel, and which binary it tried. It reports none of it. Per @neo-gpt, the preflight must detect the sandbox boundary **for both binaries** — falling back from branded Chrome to bundled Chromium would only trade an opaque `SIGABRT` for an explicit `Permission denied (1100)`, which is a better message but not a working run.

Bundled-Chromium fallback is **rejected as a repair** on his evidence, and retained only as a diagnostic distinction the preflight may report.

## Acceptance Criteria

- [ ] A launch preflight distinguishes, in its message, "this environment cannot launch a browser" from "this spec failed" — and names the resolved launch profile, the headed/headless mode, the channel and the binary.
- [ ] The preflight detects the boundary for **both** the branded channel and bundled Chromium; a green preflight on one binary must not imply the other.
- [ ] A control proves the preflight can fire: it must produce its diagnostic under a deliberately denied launch, so "no preflight error" is not "the check never ran".
- [ ] The e2e evidence contract is written down: what a PR touching e2e owes when its author's seat cannot execute it, and what the reviewer must then run.

## Out of Scope

- **Changing Neo's browser selection.** `channel: 'chrome'` is not the cause; both binaries fail identically at the sandbox boundary.
- **Fixing any red e2e spec** — #17596 owns the pre-existing cockpit set.
- **Adding e2e to CI** — a separate decision with its own cost.
- **The Codex sandbox policy itself** — operator/harness-owned, tracked here only as fix (1).

## Avoided Traps

- **A probe that measured the approval, not the sandbox.** @neo-gpt's `node --input-type=module` prefix was already approved on his seat, so the API probe passed and appeared to refute the diagnosis. The discriminating re-run through the default sandbox is what settled it — the control had to exercise the *boundary*, not the API.
- **Reading a launch signal as a product verdict.** Zero assertions executed means zero information about the specs, and both authors said so.
- **Stacking corrections.** This body has been wrong three times (harness capability lost · system-Chrome reachability · launch-profile divergence). Superseded framings are deleted rather than appended, because the next reader inherits a body, not a thread.
