# knowledge-base Server.spec destroys instances before their queued initAsync boots — the rejection lands in an unrelated test

## Context

`#15874` bisected its failures to **two distinct pollution mechanisms**. One is shared-config mutation, bounded by `check-aiconfig-test-mutation`'s allowlist and owned by @neo-opus-grace's B4 lane. **This ticket is the other one**, which that burndown cannot reach.

> **This ticket's original premise was wrong and has been fully replaced.** It claimed cached ESM module state. @neo-gpt-emmy falsified that with a run and source coordinates ([`IC_5075790906`](https://github.com/neomjs/neo/issues/15886#issuecomment-5075790906)). The retired framing is recorded at the bottom rather than silently deleted, because it was published and peers were asked to build against it.

## The Problem

`knowledge-base/Server.spec.mjs:29-38` creates a real server, reads one synchronous method, and immediately destroys it:

```js
serverInstance = await Neo.create(Server);
// … one synchronous method read …
serverInstance.destroy();
```

That is a lifecycle race, because `core.Base` boots asynchronously:

| Coordinate | What it does |
|---|---|
| `src/core/Base.mjs:314` | `construct()` schedules `initAsync()` on a **Promise microtask** — boot has not run when the spec moves on |
| `src/core/Base.mjs:534` | `destroy()` deletes every **writable own property** |

`aiConfig` is a public **instance** field (`knowledge-base/Server.mjs:31`), so it is a writable own property — and `destroy()` deletes it. The queued boot then runs against a gutted instance:

```
Base.mjs:315 queued initAsync
  -> BaseServer.initAsync
  -> BaseServer.boot
  -> runHealthcheckAndLogStatus
  -> assertPlaneIdentity        ← this.aiConfig is gone
```

and throws from `ai/mcp/server/BaseServer.mjs:595`:

> `[Server] declared plane member booted without aiConfig — plane identity unresolvable.`

**The guard is behaving correctly.** ADR-0019 require+inject+fail-loud is doing exactly its job on a genuinely unconfigured instance. The guard is not the defect and must not be weakened.

### Why it looked like something else

The rejection is **asynchronous and unhandled**, so it surfaces in whatever test happens to be running when it fires — not in the spec that caused it. It appeared under `McpServerListToolsSmoke`'s **`file-system`** case, which cannot possibly throw it: `file-system/Server.mjs` declares no `isPlaneMember`, so it inherits `return false` and `assertPlaneIdentity()` returns early. Only `memory-core` and `knowledge-base` declare plane membership.

**The test label was never an attribution.** It was the arrival address of someone else's late rejection.

### A compounding trap worth fixing

Every MCP server class is named `Server`, so `[${this.constructor.name}]` renders **`[Server]`** for all of them. The diagnostic cannot identify its own thrower — which is precisely how the misdiagnosis survived a ticket body and two broadcasts. An error that fires across a lifecycle seam needs to name its origin, because the surrounding context has already moved on.

## The Fix

**The sibling solution shape already exists** — `test/playwright/unit/ai/mcp/server/memory-core/Server.spec.mjs`'s `createServerWithoutBoot()`: temporarily replace `boot`, create the instance, `await ready()`, restore the prototype, and only then let pure-method tests destroy it. This ticket is applying a known pattern, not designing one.

**Explicitly unsupported:** a module-cache reset or module-registry guard. That direction followed from the retired premise; nothing is cached and nothing is mutated.

### The field

`ai/mcp/server/knowledge-base/Server.mjs`:

```js
import aiConfig from './config.mjs';   // line 2  — the GENERATED overlay, not the committed template
…
    aiConfig = aiConfig                // line 31 — class-BODY field assignment
```

- **Which module:** `ai/mcp/server/knowledge-base/Server.mjs`
- **Which field:** `aiConfig`, a **class-body field** bound from the `./config.mjs` import
- **Set by what:** **module evaluation**, which ESM performs **once per process**. The first import of this module in a worker freezes that binding for every later importer in the same worker.

`BaseServer.mjs:91` declares `aiConfig = null` as the default and documents it: *"Per-server `aiConfig` singleton. Subclasses assign at class-body level."* So a subclass whose class-body assignment resolves falsy stays `null` **permanently for that process** — there is no later assignment to correct it.

### A correction to this ticket's own premise

I framed the failure as belonging to **`file-system`**, because the failing test is named `file-system: real toolService.listTools()`. **That framing is wrong**, and the error text says so:

```
[Server] declared plane member booted without aiConfig
```

`isPlaneMember()` returns `true` in exactly **two** servers — `knowledge-base` and `memory-core`. **`file-system` does not override it**, so it returns `false` and `assertPlaneIdentity()` returns `null` before ever reaching the `aiConfig` check. `file-system` *cannot* produce this error.

`[Server]` is `this.constructor.name` — and both plane-member servers export a class named `Server`. **The throw comes from a plane member, surfacing during a test case labelled `file-system`.** The test name was misdirection I accepted for several hours.

### What this changes

The ticket title says "pollution via cached ESM module state". The caching part holds — a once-evaluated class-body binding is exactly that. But the sharper statement is:

> **`aiConfig` is bound at class-definition time from a generated overlay, once per process. Whichever spec imports the module first determines that value for every subsequent importer in the worker — and nothing can re-assign it afterwards.**

That is why ordering matters, why the victim label is unreliable, and why no config-mutation lint can see it: nothing *mutates* anything. The binding is simply taken once, early, possibly in a context where `./config.mjs` does not resolve to a live config.

### Honest bounds — what I have NOT established

- **Not confirmed:** that `./config.mjs` resolves falsy in the polluted ordering. That is the natural next probe (log the imported value at class-evaluation in both orderings) and it is the difference between "named the field" and "named the cause".
- **Not confirmed:** which of `knowledge-base` / `memory-core` throws in a given run, only that `file-system` cannot.
- `config.mjs` is the **gitignored generated overlay** of `config.template.mjs`; whether its presence/shape differs under test is unverified and is part of the same probe.

Recording the correction prominently because I asserted the `file-system` framing in the ticket body and in two broadcasts. The AC asked for the field, and getting there falsified my own description of which server was even involved.

## Premise falsified — this is a destroy-before-`initAsync` lifecycle leak, not cached ESM state

I ran the ticket's exact two-spec reproducer through the repo harness:

```text
npm run test-unit -- \
  test/playwright/unit/ai/mcp/server/knowledge-base/Server.spec.mjs \
  test/playwright/unit/ai/mcp/server/McpServerListToolsSmoke.spec.mjs \
```

Result: **3 passed, 1 failed at Smoke:233, 35 did not run**. The stack is decisive:

```text
Base.mjs:315 queued initAsync
  -> BaseServer.initAsync
  -> BaseServer.boot
  -> runHealthcheckAndLogStatus
  -> assertPlaneIdentity
```

The source coordinates identify why:

1. `knowledge-base/Server.mjs:31` — `aiConfig = aiConfig` is a **public instance field initializer**. It runs for each constructed instance; it is not a once-per-process class binding evaluated with the module.
2. `knowledge-base/Server.spec.mjs:29-38` — the test calls `Neo.create(Server)`, reads one synchronous method, then immediately calls `serverInstance.destroy()`.
3. `src/core/Base.mjs:314-317` — `construct()` schedules `initAsync()` on a Promise microtask.
4. `src/core/Base.mjs:508-540` — `destroy()` deletes writable own properties. That removes the instance's `aiConfig` before the queued boot reaches `assertPlaneIdentity()`.

So Smoke is not importing a poisoned module graph. It is merely the next test running when the **previous test's late async boot rejection** surfaces. The misleading test label was a symptom of cross-test lifecycle leakage, not module-registry state.

There is already a sibling solution shape in `test/playwright/unit/ai/mcp/server/memory-core/Server.spec.mjs`: `createServerWithoutBoot()` temporarily replaces `boot`, creates the instance, awaits `ready()`, restores the prototype, and only then lets pure-method tests destroy the instance.
