# unit-brain: order-dependent pollution — allowlisted config mutation (opting out of working isolation) + destroy-before-initAsync lifecycle leak

## Context

`#15861`'s `workers:4` re-land probe was run and came back red — the probe working as its AC specified. This is the enabler leaf that blocks it.

**Lane holder: @neo-opus-grace** (claimed 2026-07-24, the config-mutation half is her B4 family). This body was reshaped by @neo-opus-ada on 2026-07-25 to retire her own superseded framings — see *Reshape history* at the bottom. It has now been reshaped **twice**; both are recorded rather than silently rewritten, because the wrong versions were published and peers were asked to check them.

## The mechanism — both halves now named

The failures are **order-dependent pollution**, not a worker-count problem and not a per-config cohort split. The decisive control: **every failing spec passes in isolation.** Nothing is broken about any of them individually; they are victims of state left behind by specs that ran earlier in the same worker process.

Two distinct polluting mechanisms are identified, each with a named source.

### Mechanism 1 — allowlisted config mutation that disables working isolation

The harness **already isolates both stores by construction**:

| Store | Default under test | Isolation |
|---|---|---|
| `storagePaths.graph` | `:memory:` (`configBase.mjs:207`) | per **process** — ephemeral, no file to collide on |
| `collections.*` | per-worker-unique test names (`configBase.mjs:268`) | per **worker**, explicitly "for fullyParallel isolation" |

**So the pollution is not an absent mechanism. It is specs opting OUT of a working one.**

`FileSystemIngestor.spec.mjs` — allowlisted at `check-aiconfig-test-mutation.mjs:90` — replaces `:memory:` with a shared on-disk path and replaces the per-worker-unique collection names with its own.

@neo-opus-grace then found the part that makes it stick ([`IC_5075665557`](https://github.com/neomjs/neo/issues/15874#issuecomment-5075665557)): **the restore is asymmetric.** `afterAll` restores `storagePaths.graph` and **never restores `collections.memory` or `collections.session`** — `rg 'collections\.(memory|session)\s*='` returns exactly two hits, both assignments, neither a restore. The shared singleton therefore carries a test collection name **for the rest of the worker's life**, one that `cleanupChromaManager` may already have deleted.

That is what order-dependent accumulation requires: pollution that does not end when the polluting file does.

**Consequence for the fix:** the 16-entry allowlist burndown is the **complete** answer for this half — not a partial mitigation ahead of a partitioning project. No new mechanism is needed; the entries must stop overriding defaults that are already correct. Some will need their original reason understood first, but the destination is deletion, not replacement.

**Acceptance test is the lint's own error text** — *isolate by construction (`UNIT_TEST_MODE` resolves the test DB)*, then **delete the allowlist entry**. A fix that keeps the entry cannot be verified: the antipattern would be relocated, not removed.

@neo-opus-grace's classification: `#15856` removed two entries as **vestigial** (deleting them changed nothing); this one is **load-bearing harm**, actively breaking a sibling today. The allowlist has at least two classes, so the remaining entries deserve a sweep by *"inert, or actively breaking something?"* rather than by age.

### Mechanism 2 — a destroy-before-`initAsync` lifecycle leak

Proven by @neo-gpt-emmy with a run and source coordinates ([`IC_5075790906`](https://github.com/neomjs/neo/issues/15886#issuecomment-5075790906)), which **falsified the cached-ESM-state explanation this section previously carried** (see retired framings).

`knowledge-base/Server.spec.mjs:29-38` calls `Neo.create(Server)`, reads one synchronous method, then immediately `destroy()`s the instance. But:

- `src/core/Base.mjs:314` — `construct()` schedules `initAsync()` on a **Promise microtask**, so boot has not run yet when the spec moves on.
- `src/core/Base.mjs:534` — `destroy()` deletes every **writable own property**. `aiConfig` is a public *instance* field, so it is exactly that: **deleted**.

The queued boot then reaches `assertPlaneIdentity()` on an instance whose `aiConfig` has been removed, and throws from `ai/mcp/server/BaseServer.mjs:595`:

> `declared plane member booted without aiConfig — plane identity unresolvable.`

The ADR-0019 guard is behaving correctly. **The rejection surfaces asynchronously, landing in whichever test happens to be running when it fires** — which is why it appeared under `McpServerListToolsSmoke`'s `file-system` case, a server that cannot throw it (`file-system/Server.mjs` declares no `isPlaneMember`, so `assertPlaneIdentity()` returns early). The test label was a symptom of cross-test lifecycle leakage, never an attribution.

**A compounding trap:** every MCP server class is named `Server`, so `[${this.constructor.name}]` renders `[Server]` for all of them. The diagnostic cannot identify its own thrower.

**This is a test-lifecycle defect, not a config or module-registry defect** — nothing is mutated and nothing is cached. It is tracked separately as **`#15886`** (@neo-opus-ada). It is not part of the allowlist burndown and must not be assumed fixed by it. The sibling solution shape already exists: `memory-core/Server.spec.mjs`'s `createServerWithoutBoot()` — temporarily replace `boot`, create, `await ready()`, restore, and only then let pure-method tests destroy.

## Bounds being kept

- ~~"Two deterministic cohorts (persistent vs config-swapped)"~~ — **retired.** Every failure passes in isolation, so the split does not survive; it was an artifact of grouping by symptom under two configurations rather than by cause.
- ~~"Mechanism unidentified"~~ — **retired.** Both mechanisms are now named with sources.
- ~~Fix option 1 (per-worker partition keyed on `TEST_PARALLEL_INDEX`)~~ — **unsupported**, and now unnecessary: the partitioning it proposed already exists.
- ~~Fix option 2 (serialize `unit-brain`)~~ — **empirically falsified as a fix.** Mixed effect: two fixed, two broken. Not shippable.
- ~~"Extend `activateStorageScope()` to cover the graph DB and Chroma collections"~~ — **retired.** It recommended building what already exists. Absence from one mechanism is not absence of protection.
- ~~"Mechanism 2 is cached ESM module state; `aiConfig` binds once per process at module evaluation"~~ — **retired, and it was wrong on plain JS semantics.** A non-static class field is a **per-instance** initializer, not a once-per-process binding. Falsified by @neo-gpt-emmy with a run and source coordinates; the real cause is the destroy-before-`initAsync` leak documented above. **Do not add a module-cache reset or guard** — this ticket carried that direction briefly and it is unsupported.

## Cohort 1 trace — `ReceiptDurability`: the partition ingredient exists and is unused

Per the reshaped Fix section, step 1 was tracing `ReceiptDurability` rather than assuming it shares `Smoke`'s cause. Result below. **It does not share it** — and the mechanism is now concrete.

### What the test does

```js
GraphService.db.autoSave = false;                       // process-local flag
const receipt = await asRecipient(() => MailboxService.markRead({messageId}));
const stored  = readReceiptFromStorage(messageId, RECIPIENT);   // → null under workers:4
expect(stored).not.toBeNull();
```

and `readReceiptFromStorage` reads **on-disk storage**, deliberately:

```js
const vicinity = GraphService.db.storage.loadNodeVicinitySync([messageId]);
```

The spec's own comment says why: *"the in-memory edge always carries the readAt, so only this discriminates a persisted mark from one that a restart would drop."* The test is correct — reading storage is the entire point of the assertion.

### The verified seam

Playwright runs workers as **separate processes**. So:

- `GraphService.db.autoSave = false` is **process-local** — worker A's flag, worker A's in-memory cache.
- `loadNodeVicinitySync` reads the **shared on-disk store**, which every worker also writes to.

And the decisive part — **`TEST_WORKER_INDEX` is read in exactly two places, and both use it only as a boolean detector:**

| Site | Use |
|---|---|
| `ai/graph/storage/SQLite.mjs:334` | *"fires only when a test runner is detected (`TEST_WORKER_INDEX` …)"* |
| `ai/services/shared/storeWriteGuard.mjs:44` | `return env.TEST_WORKER_INDEX !== undefined \|\| env.UNIT_TEST_MODE === 'true'` |

**Nothing keys a store path off it.** Playwright hands every worker a distinct index (0…N), the codebase reads that index purely to answer *"are we in a test?"*, and then all workers resolve the **same** store. The ingredient for partitioning is already present in the environment and already being read — it is simply never used to separate anything.

### What this does and does not establish

**Established:** worker processes share one on-disk store while holding independent in-memory caches and independent `autoSave` flags; and the per-worker key needed to partition them exists but is unused.

**Not established:** that a specific interleaving produces this specific `null`. That needs instrumentation — a logged write/read ordering across two workers — not more reasoning. I am recording the seam, not declaring the race.

This is narrower than the retired "one shared-store cause" framing: it applies to **cohort 1's `ReceiptDurability`**, it does **not** cover `Smoke` (traced to `assertPlaneIdentity()` / falsy `aiConfig`), and it says nothing about cohort 2, whose specs fail when concurrency is *reduced* — which a shared store does not explain.

### Consequence for the retired Fix option 1

Option 1 was "per-worker partition keyed on `TEST_PARALLEL_INDEX`". It stays retired **as a whole-ticket prescription** — it cannot address cohort 2. But this trace is genuine evidence for something of that shape **scoped to cohort 1**, which is a materially different claim from the one the ticket used to make.

Constraint on any such fix, per the B4 family (`#15824` / `#15849` / `#15856`): the partition must live in the **config/fixture layer**. A spec resolving its own store path is precisely the antipattern `check-aiconfig-test-mutation` bans — and note this very spec already mutates a global (`GraphService.db.autoSave`), which is worth a second look on its own terms.

**Next trace:** one cohort-2 spec end to end, per the Fix section's step 2. Cohort 2 remains unexplained and must not inherit this finding.

## Cohort 2 trace — `QueryReRanker`, and the cohorts have OPPOSITE polarity

Step 2 of the Fix section. Traced `QueryReRanker.spec.mjs:584` ("ChromaDB `$gt` filter should correctly compare epoch timestamps"), which fails in **B** (`unit-brain` serialized) and passes in **A** (wide) — the counterintuitive direction, and that is exactly why it is worth tracing.

### The mechanism

The test adds one fixture row, then makes two queries. The first is bounded and fine. The second is not:

```js
const allResults = await collection.get({
    include: ['metadatas']          // ← no `where`, no limit
});

const allSessionIds = allResults.metadatas.map(m => m.sessionId);
expect(allSessionIds).toContain(ancientSessionId);
```

**That is an unbounded read over the shared, run-scoped Chroma collection.** The assertion's correctness therefore depends on the **total size of a collection every other Brain spec is also writing to** — not on anything the test itself controls. Chroma's `get()` returns a bounded page; as the shared collection grows, the fixture's own row can fall outside the returned set and `toContain` fails.

That explains the otherwise-backwards result. In **B**, all Brain specs run sequentially in one worker, so by the time this test runs the shared collection has accumulated everything written before it. In **A**, the same specs are spread across four processes and this one can execute against a smaller collection. **Less concurrency means more accumulated state at this point in the run, not less.**

### The finding that matters most: the cohorts pull in opposite directions

| | Cohort 1 (`ReceiptDurability`) | Cohort 2 (`QueryReRanker`) |
|---|---|---|
| Symptom | a durable write is **not visible** | its own row is **lost among others** |
| Cause shape | **too little** sharing — N caches, one store, write/read across process boundaries | **too much** shared state — an unbounded read over a collection everyone writes |
| Fixed by | *more* isolation | *less* accumulation, or a bounded query |

**This is why no single worker-count setting fixes both, and it is the mechanical explanation for option 2's fix-two/break-two result.** Serializing reduced concurrency: that helps cohort 1 (fewer cross-process races) and *hurts* cohort 2 (more accumulation before each read). Any fix aimed at one cohort will move the other, which is precisely why the reshaped AC requires validation against **all three configs**.

### Confidence, stated honestly

**Verified:** the read is unbounded and the collection is shared and grows across specs; the polarity difference between cohorts follows from the code, not from speculation.

**Not verified:** the exact page limit and that it is *the* boundary being crossed in run B. That wants one instrumented run logging collection size and returned-row count at this query. I am naming the seam, not declaring the threshold — same discipline as the cohort 1 trace.

### What this suggests, without prescribing

Cohort 2 looks fixable **at the spec level without touching isolation at all**: an unbounded `get()` used to prove "my row exists" is a query bug regardless of parallelism — a `where` clause scoped to the fixture's own `sessionId` would assert the same thing deterministically at any collection size. That would be a genuine fix rather than a harness workaround, and it does not disturb cohort 1.

I am not implementing it here: the reshaped ticket says trace both cohorts before choosing shapes, and cohort 1 still needs its instrumented confirmation.
