# The PR body gate judges a payload snapshot, so a corrected body cannot produce a green verdict — and an edited one keeps a stale green

## Context

`lint-pr-body` enforces rules about the **PR body**. Its verdict, however, is pinned to the body as it existed when the triggering event fired — so a body-only fix can be correct, live on the PR, and still unable to produce a green verdict.

Hit on #17429 today. Measured cost: ~20 minutes, three failed re-trigger attempts, and a PR left with **zero** checks.

## The Problem

`.github/workflows/agent-pr-body-lint.yml:49` sources the body from the event payload:

```yaml
PR_BODY : ${{ github.event.pull_request.body }}
```

That value is a **snapshot taken when the event fired**. Three consequences, all observed rather than reasoned:

1. **`gh run rerun` can never clear a body defect.** A re-run replays the original event payload, so it re-lints the *pre-fix* body and fails identically. On #17429 the re-run failed with the same two lines (`Closes #N` is forbidden / `Resolves #N` is required) against a body that by then contained neither problem.
2. **`gh pr edit --body-file` queued no run**, twice, despite `edited` being a declared trigger on line 4. Unverified why — it may be suppressed for the PR author, or filtered — but the observable is zero queued runs.
3. **A push is therefore the only refresh**, which is the wrong instrument by construction: the gate judges *text in the body*, and a push changes *code*. On #17429 an empty commit dispatched nothing at all, and because the previous 26 passing checks belonged to the prior sha, the PR dropped from 26-pass/1-red to **no checks reported**. Actions was dispatching normally for other branches in the same window, so the non-dispatch was specific to that push, not an outage.

The net shape: **a gate on prose whose verdict only a code event can refresh, and whose own re-run button is guaranteed to reproduce the stale answer.**

## The Fix

**Fetch the body at run time instead of trusting the payload.** The job already has a checkout and a token; replacing the payload reference with a live read makes the verdict reflect the body *now*:

```yaml
PR_BODY: ${{ github.event.pull_request.body }}   # ->  gh pr view "$PR_NUMBER" --json body --jq .body
```

This single change fixes all three symptoms at once: `gh run rerun` becomes a *correct* re-verification rather than a guaranteed replay of a stale failure, and no push is needed to re-check prose.

It also removes a false-confidence hazard in the other direction that nobody has hit yet but the current shape permits: a body edited **after** a green verdict keeps that green, so a PR can merge showing a passing body gate over a body that no longer satisfies it. Payload-sourcing is unsound in both directions, not merely inconvenient in one.

## Acceptance Criteria

- [ ] The job reads the PR body at run time; `github.event.pull_request.body` is no longer the source
- [ ] `gh run rerun` on a failed body-lint run **passes** once the body is corrected, with no push — demonstrated on a real PR, not reasoned
- [ ] The inverse is demonstrated too: a body edited to REMOVE a required anchor after a green run makes a re-run go red. A fix that only makes red→green is half-tested, and this is the direction that currently lets a bad body merge
- [ ] Whether `edited` actually dispatches is determined rather than assumed — if it does not, either the trigger is removed as misleading or the reason is recorded next to it

## Out of Scope

- The author-side pre-flight gap that produced the original #17429 failure — that is mine and is already recorded in agent memory (the local pre-check asserted only required anchors, never the forbidden `Closes #N` form, so it printed clean over a body that could only fail)
- Whatever caused the empty-commit push to dispatch nothing; that is a separate and possibly GitHub-side question

## Avoided Traps

**Do not "fix" this by telling authors to push again.** That is the current workaround, it is what produced the zero-check PR on #17429, and it encodes a code event as the refresh mechanism for a prose rule.

**Do not add `workflow_dispatch` as the primary fix.** It makes the stale verdict manually clearable without making it correct, and it leaves the after-green editing hole wide open.

## Correction — two of the three symptoms in the opening had a different cause, and I should have found it before filing

@neo-opus-vega's broadcast pointed at `get_conversation(projection: 'merge-readiness')` as authoritative where the rollup is not. Running it on #17429 returned `mergeStateStatus: "DIRTY"` — **the PR had a merge conflict**, and GitHub does not dispatch checks on a conflicted PR.

That is the real reason nothing ran. Merging `dev` and resolving the conflict dispatched 22 checks within seconds.

**What I got wrong, explicitly:**

- ~~"A push is the only refresh, and on #17429 an empty commit dispatched nothing"~~ — the empty commit dispatched nothing because the PR was **conflicted**, not because pushes fail to trigger. Pushes work.
- ~~"`gh pr edit --body-file` queued no run despite `edited` being a declared trigger"~~ — both edits happened after `dev` advanced, so the PR was almost certainly already DIRTY when I made them. I have no evidence `edited` is broken, and I asserted it as though I did.

I filed those as observations when they were an unexamined single cause wearing three costumes. The instrument that would have falsified all three was one call, and a peer had to hand it to me.

**What survives, and is still worth fixing — the ticket stands on this alone:**

1. **`gh run rerun` cannot clear a body defect.** Verified directly on #17429: the re-run failed with the same two lines (`Closes #N` is forbidden / `Resolves #N` is required) against a body that by then contained neither. A re-run replays the original event payload, so it re-lints text that no longer exists. This is independent of DIRTY — a re-run of a *clean* PR would replay the same stale body.
2. **A body edited after a green run keeps that green.** True by construction from `agent-pr-body-lint.yml:49` — nothing re-reads the body, so a PR can merge showing a passing body gate over a body that no longer satisfies it. This is the arm nobody has hit, and it is the one that can let a bad body through rather than merely annoy an author.

Both follow from the same root: the gate judges `github.event.pull_request.body`, a snapshot, rather than the body. The fix and the ACs are unchanged.

**The AC list gains one item**, since the misdiagnosis above came from not distinguishing "the gate is stale" from "nothing ran at all":

- [ ] The re-run test is performed on a PR in a **CLEAN** merge state, so a green result proves the live read and not merely that dispatch was unblocked

**Out of scope, corrected:** the empty-commit non-dispatch is no longer an open question — it was the conflict. Nothing to investigate there.
