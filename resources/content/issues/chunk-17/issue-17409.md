# Header buttons stay at their pre-drag positions for the whole resize drag

## Context

Operator report, 2026-08-19: column drag-and-drop and resizing break in the DevIndex app as it runs inside `neomjs/neo`. This is an investigation ticket — the observation is the operator's own, and the mechanism is not yet known.

It is filed with **negative results attached** so whoever picks it up starts from a narrowed search space rather than repeating the gestures already measured. `neomjs/neo#17401` fixed a different DevIndex grid defect (component cells not following their record on scroll); this one is separate and survives that fix.

Live latest-open sweep: latest 20 open issues at 2026-08-19T22:04Z, no equivalent. A2A claim sweep: no overlapping lane.

## What was measured and did NOT reproduce

All in the GPU e2e harness (`playwright.config.e2e.mjs`, 1920x1080 Chromium, ANGLE Metal), driving `/apps/devindex/` from the neo checkout, comparing visible header rects against first-row cell rects with the off-screen columns clipped out:

| gesture | result |
|---|---|
| Resize each of `User`, `Total`, `Rank`, `Impact`, `Activity`, `Top Repo` via the right-edge handle | widths applied (e.g. `User` 250→387); header/cell mismatches `[]` before and after, every column |
| Column reorder — drag `Total` onto `Rank` at button centre | order changed `#, Rank, User, Total…` → `#, Total, Rank, User…`; mismatches `[]` |
| Reorder, then resize `User` | `User` 250→397, order preserved; mismatches `[]` at baseline, after the drag, and after the resize |

So the plain single-body reorder and resize paths are not broken on this checkout, and neither is their composition in that order.

**A measurement caveat worth inheriting:** the in-app browser pane runs at a 0x0 hidden viewport, so a grid renders no rows there and every reading taken through it is an artifact — the working `examples/grid/bigData` reads identically to a broken grid. Use the e2e harness. Likewise, off-screen columns legitimately have no rendered cell under column virtualization; a rect comparison without a viewport clip reports ~25 false mismatches.

## Candidate directions, none yet tested

1. **Cross-body / locked-region drag.** DevIndex declares no `locked` columns, so it starts single-body, but dragging a column into the start/end region creates one. `ColumnCrossBodyDnD.spec.mjs` and `LockedDnDDuplication.spec.mjs` exist and drive other apps. Resizing *after* a column has been locked is untested here.
2. **Resizing a locked column**, or one adjacent to a region boundary.
3. **Overdrag scroll** — `ColumnOverdragScroll.spec.mjs` covers the gesture elsewhere; dragging past the viewport edge with DevIndex's ~30 columns and horizontal virtualization is untested.
4. **After a horizontal scroll**, when the mounted column range no longer starts at 0.
5. **The dynamic column set.** `GridContainer#buildDynamicColumns` assigns `this.columns` after `super.construct()`, and `afterSetDataMode` rewrites every year column's `dataField` in place. A drag or resize interleaved with a data-mode switch is untested.

## The Architectural Reality

- `apps/devindex/view/home/GridContainer.mjs` — columns assigned post-construct; `bufferColumnRange: 1`, `bufferRowRange: 1`; ~30 columns including 17 year columns
- `src/grid/header/plugin/Resizable.mjs` — resize is armed only from `.neo-resizable`; the handle is injected on hover
- `src/grid/header/Toolbar.mjs` — `createSortZone` sets `ignoreDragSelector: '.neo-resizable'`, so reorder and resize provably never share a gesture
- `src/grid/View.mjs` — the multi-body orchestrator; `syncBodies` drives `bodyStart` / `body` / `bodyEnd`

Existing coverage drives `examples/grid/bigData` and `examples/grid/lockedColumns`, never DevIndex's column shape.

## Reproduced — and it is not a neo defect

The operator named the two behaviours precisely: during a drag-resize the body cells update in real time, and on drop the following columns' positions adjust. Both fail in the DevIndex app. That gave the gesture my earlier probes were missing — I had only measured the end state after drop, never the live path, and never the *neighbouring* columns.

With the same probe, same column, same gesture, run against three targets:

| target | engine | resized cell, mid-drag | neighbours, mid-drag | after drop |
|---|---|---|---|---|
| `examples/grid/bigData` (neo) | this checkout | `Firstname` 150→307 | 211→368, 361→518, 511→668 | settled |
| `apps/devindex` (neo) | this checkout | `User` 250→407 | 387→544, 487→644, 577→734 | settled |
| **DevIndex app from the `neomjs/devindex` repo** | **published `neo.mjs@13.1.0`** | **250 → 250, no change** | **387, 487, 577 — no movement** | **unchanged** |

The third row is the report, reproduced exactly: nothing moves during the drag, and nothing settles on drop.

## Why

That repository consumes the published package rather than this checkout's `src/`, and the published engine predates both resize fixes:

| symbol | origin | `neomjs/devindex` @13.1.0 | neo `src/` |
|---|---|---|---|
| `refreshColumns` | neomjs/neo#17289 — explicit repaint after a pure width change | **0** | 4 |
| `isMeasuredWidth` | neomjs/neo#17327 — width comes from config unless layout owns it | **0** | 3 |

`refreshColumns` is exactly the live-repaint half: without it a pure width change leaves `[startIndex, endIndex]` unchanged, the config never notifies, and the cells keep the geometry that was just replaced. That is the "no real-time update" symptom, and its absence also explains the drop.

## Disposition

Closing as not-a-defect in this repository. The neo-side code is correct and measurably so — `apps/devindex` here behaves identically to `examples/grid/bigData` on both behaviours.

The `neomjs/devindex` repository needs a `neo.mjs` release carrying neomjs/neo#17289 and neomjs/neo#17327, then a dependency bump. Nothing to fix in `neomjs/neo`.

## Two measurement traps recorded, because they cost real time

- **The in-app browser pane runs at a 0x0 hidden viewport.** A grid renders no rows there, so a working grid reads identically to a broken one. Use the e2e harness.
- **Comparing arms requires the same column position.** Resizing a late column while sampling only the leading cells reports "nothing moved" — correctly, since columns *before* the resized one never shift. That produced a false negative here before the arms were aligned.

## Reopening — my not-a-defect closure was wrong, and the reason is worth more than the verdict

I closed this saying the neo-side code was correct because `apps/devindex` in this checkout "behaves identically to `examples/grid/bigData`". That sentence is **true**. The conclusion I drew from it is **false**: they behave identically because **both are broken**, and I used one as the healthy control for the other.

A control that shares the defect reports every subject as healthy. That is the whole failure.

The second half was also a measurement gap: I sampled the **end state**, after drop, where everything is aligned again. The defect exists only while the mouse button is down.

## The defect, measured

Header-vs-cell x-offset for every visible column, sampled **while the drag is still held**, resizing one column by +200px. Chrome, 1920×1080, `dev` @ `4d89ed9b21`.

**`examples/grid/bigData`** — a neo-owned fixture with a clean baseline:

| phase | visible columns | misaligned |
|---|---|---|
| at rest | 15 | **0** |
| **during the drag** | 15 | **12** |
| after drop | 13 | **0** |

```
DURING DRAG
  [1] Firstname   header x=  61 w=150 | cell x=  61 w=150 | dx=0
  [2] Lastname    header x= 211 w=150 | cell x= 211 w=350 | dx=0     <- resized column: cell already 350, header still 150
  [5] Counter     header x= 661 w=100 | cell x= 861 w=100 | dx=200
  [7] Number 7    header x= 911 w=100 | cell x=1111 w=100 | dx=200
  [8] Number 8    header x=1011 w=100 | cell x=1211 w=100 | dx=200
```

`apps/devindex` in this checkout reproduces it identically — 5 of 7 visible columns at `dx=200` during the drag, 0 after drop.

Columns **before** the resized one stay correct. Every column **after** it has its cells moved by the drag delta while its header has not. The whole header row is offset from its own columns for the entire gesture, then snaps back on mouseup.

## The Architectural Reality

`src/grid/header/plugin/Resizable.mjs`:

- **`onDragMove` (:38)** moves the **body** immediately — `owner.width = newWidth` then `body.updateCellPositions(owner.dataField, newWidth)`. That live cell update is neomjs/neo#17289's fix and it is working exactly as intended.
- The **header** does not follow in the same handler. The rendered button keeps its old width for the whole drag — measured above, `w=150` while its own cell is already `w=350` — so the following buttons never reflow.
- **`onDragEnd` (:77)** is where the header catches up: it nulls the proxy-copied `position` / `left` / `top` / `transform` off the owner, sets `owner.width = newWidth`, and calls `toolbar.passSizeToBody()`.

So the asymmetry is the defect: the body has a live path, the header has a drop-only path. neomjs/neo#17289 fixed "header moves, cells do not" — this is the same split surviving in the opposite direction, and only while the gesture is open.

## Why the earlier evidence missed it

Recorded so the next probe is not built the same way:

- **The control was defective.** `examples/grid/bigData` was treated as known-good. It tears the same way. Any "matches the reference" reading was vacuous.
- **Only the end state was sampled.** The gesture has to be *held open* — mouse down, move, read, then up. Reading after `mouse.up()` shows an aligned grid every time.
- **Only the resized column was watched.** The original probe checked that the dragged column's own cell moved. It does. The damage is to every column *after* it.
- **A screenshot found in one look what four numeric probes missed.** The tearing is obvious visually and invisible to a probe aimed at the wrong columns at the wrong instant.

## Implementation note: the header's width update is *swallowed* during the drag, not merely untriggered

Recording one eliminated hypothesis so the next pass does not re-spend it.

`afterSetWidth` → `changeVdomRootKey('width', value)` → **`me.update()`** (`src/component/Base.mjs:1113-1124`). So `owner.width = newWidth` in `onDragMove` already issues an update on the button. The update is issued and does not reach the DOM.

Measured mid-drag on `examples/grid/bigData`, resized column:

| | at rest | during drag | after drop |
|---|---|---|---|
| button inline `style.width` | `150px` | **`150px`** | `350px` |
| `.neo-dragproxy` width | — | **350** | — |
| button `opacity` | 1 | 0.3 (`neo-is-resizing`) | 1 |
| sibling button x positions | 1, 61, 211, 361, 511, 661 | **unchanged** | reflowed |

**Eliminated:** adding an explicit `owner.parent?.update()` alongside the existing `owner.width = newWidth` in `onDragMove` changes nothing — still 12 of 15 columns misaligned, button still `150px`. So the fix is not a missing update call; something is suppressing the button's update while the DragZone is active. That is where the next pass should start — the in-flight/merge path around `DragZone`, not `Resizable` itself.

Also worth noting for whoever takes it: the header's drag-time presentation looks deliberate — `neo-is-resizing` dims every button to `opacity: 0.3` (`resources/scss/src/grid/header/Toolbar.scss:7`) while a `.neo-dragproxy` shows the prospective width. That is a coherent "not committed yet" design **on its own**. It stopped being coherent when neomjs/neo#17289 gave the body a live path, so the two halves now disagree for the whole gesture. Deciding which half moves is a design call, not just a bug fix:

- make the header reflow live so it pairs with the body, or
- keep the header's proxy presentation and stop the body reflowing until drop — which would revert neomjs/neo#17289's live cell tracking, and the operator has asked for live cell tracking explicitly

I read it as the first, but it is worth stating rather than assuming.
