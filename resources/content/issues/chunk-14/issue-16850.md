# Five of six ollama env vars never reach the containers, so ollama-native embedding cannot work in any deployment

## Context

Found by re-framing the reproduction: instead of scripting against a provider, configure **our own containers** the way an external plane configures theirs and exercise the real MCP tools. The change turned out to be impossible to make — which is the finding.

## The Problem

`ai/configBase.mjs` declares **six** ollama env leaves. `ai/deploy/docker-compose.yml` passes **one**.

| declared leaf | reaches the containers? |
|---|---|
| `NEO_OLLAMA_KEEP_ALIVE` | ✅ |
| **`NEO_OLLAMA_HOST`** | ❌ |
| **`NEO_OLLAMA_MODEL`** | ❌ |
| **`NEO_OLLAMA_EMBEDDING_MODEL`** | ❌ |
| **`NEO_OLLAMA_EMBEDDING_TIMEOUT_MS`** | ❌ |
| **`NEO_OLLAMA_REQUIRE_PARALLEL_MODELS`** | ❌ |

`NEO_OLLAMA_HOST` appears **zero times** across *every* compose variant in `ai/deploy/` (`docker-compose.yml`, `.dev`, `.local-agent-os`, `.parity-capture`, `.parity-ci`, `.test`).

**So a deployment that sets `NEO_EMBEDDING_PROVIDER=ollama` gets `ollama.host` resolved to its leaf default, `http://127.0.0.1:11434`.** Inside the `kb-server` container that address is the kb-server itself. Nothing listens on it. **Every native ollama embed fails with connection-refused, on every containerized plane, permanently.** The model service is reachable at `http://local-model:11434` on the compose network, and no configuration path can point the provider at it.

The other four missing leaves compound it: the operator's chosen chat model, embedding model and timeout are all silently ignored in favour of leaf defaults.

**The contrast is what makes this an omission rather than a policy.** The sibling provider is fully wired — `NEO_OPENAI_COMPATIBLE_HOST`, `_MODEL`, `_EMBEDDING_MODEL`, `_API_KEY`, `_KEEP_ALIVE` all pass through. And `NEO_OLLAMA_KEEP_ALIVE` **is** passed: **nobody wires a keep-alive for a provider they intend to exclude.** The intent to support ollama is in the file; the host never followed.

## Why it is worse than a missing variable

`embeddingProvider: leaf('openAiCompatible', 'NEO_EMBEDDING_PROVIDER', 'string')` presents `ollama` as a first-class choice, and the code backs that up completely: `ai/provider/Ollama.mjs` is a full provider, `TextEmbeddingService` has a native embed path, `providerReadinessHelper` carries a whole ollama branch keyed on `role === 'embedding' ? '/api/embed' : '/api/chat'`.

**Everything an operator can read says ollama is supported. The deployment layer cannot deliver it.** Someone reading our config and setting the obvious value gets a plane whose corpus never fills, with no error naming the cause — the failure is a connection refused to localhost, which reads as "the provider is down" rather than "the host was never configured".

## The Architectural Reality

- `ai/deploy/docker-compose.yml` — the three service env blocks (`kb-server` ~`:88`, `mc-server` ~`:210`, `orchestrator` ~`:308`). Each passes `NEO_EMBEDDING_PROVIDER` and the full `NEO_OPENAI_COMPATIBLE_*` set, plus `NEO_OLLAMA_KEEP_ALIVE` alone.
- Same file, `local-model` service — `ollama/ollama:latest`, `OLLAMA_HOST=0.0.0.0:11434`, reachable on the network as `local-model:11434`, gated behind `--profile local-model`. The target exists; nothing can be pointed at it.
- `ai/configBase.mjs:654` — `host: leaf('http://127.0.0.1:11434', 'NEO_OLLAMA_HOST', 'string')`.

## The Fix

Pass the five missing leaves through to the three services that consume them, mirroring the `NEO_OPENAI_COMPATIBLE_*` block that already sits beside them, and default `NEO_OLLAMA_HOST` to the compose-internal service address so the profile works without operator ceremony:

```yaml
- NEO_OLLAMA_HOST=${NEO_OLLAMA_HOST:-}
- NEO_OLLAMA_MODEL=${NEO_OLLAMA_MODEL:-}
- NEO_OLLAMA_EMBEDDING_MODEL=${NEO_OLLAMA_EMBEDDING_MODEL:-}
- NEO_OLLAMA_EMBEDDING_TIMEOUT_MS=${NEO_OLLAMA_EMBEDDING_TIMEOUT_MS:-}
- NEO_OLLAMA_REQUIRE_PARALLEL_MODELS=${NEO_OLLAMA_REQUIRE_PARALLEL_MODELS:-}
```

## Contract Ledger Matrix

| Target Surface | Source of Authority | Proposed Behavior | Fallback | Docs | Evidence |
|---|---|---|---|---|---|
| `kb-server` / `mc-server` / `orchestrator` env | `docker-compose.yml` | the five ollama leaves pass through, matching the openAiCompatible block | unset ⇒ leaf defaults, identical to today | compose comment beside the `local-model` profile note | spec/assertion: declared `NEO_OLLAMA_*` leaves ⊆ compose-passed vars |
| `NEO_OLLAMA_HOST` on a `--profile local-model` plane | operator `.env` | can be set to `http://local-model:11434` and take effect | unset ⇒ `127.0.0.1:11434` leaf default (today's behaviour) | same | plane check: native embed reaches the model service |

**Decision Record impact:** `aligned-with ADR 0019` — the leaves already own env-override-with-default; this is the deployment layer failing to deliver the env, not a config-resolution change. No leaf definitions are touched.

## Acceptance Criteria

- [x] All six declared `NEO_OLLAMA_*` leaves are passed to every service that consumes them. **Receipt:** structural parse — `kb-server`, `mc-server`, `orchestrator` each carry 6.
- [x] ~~A mechanical check asserts declared-`NEO_OLLAMA_*`-leaves ⊆ compose-passed-vars … the same check applied to `NEO_OPENAI_COMPATIBLE_*` must pass on the current tree.~~ **This AC was WRONG and implementing it is what proved so.** The invariant is false by design: **8 of 14** declared `NEO_OPENAI_COMPATIBLE_*` leaves legitimately never reach Compose (`BATCH_EMBEDDING_*`, `CONTENTION_*`, `UNLOAD_RETRY_*`, `REQUIRE_PARALLEL_MODELS`), because most leaves are tunables whose defaults are authoritative and no deployment needs to override them. The required positive control would have **failed**, so this could not have been delivered as written — and had I written the guard without the control, it would have passed vacuously on the one arm being fixed.

  **Replaced by the invariant that is actually true and actually catches this defect:** *a leaf whose default is a **loopback address** must be overridable through the deployment profile.* Inside a container `127.0.0.1`/`localhost` name the container itself, so such a default is not a sensible fallback — it is unconditionally pointed at the wrong process with no configuration path to correct it. **Receipt:** `test/playwright/unit/ai/deploy/LoopbackDefaultReachability.spec.mjs`. `NEO_CHROMA_HOST` and `NEO_OPENAI_COMPATIBLE_HOST` are the positive controls — both carry loopback defaults and both already pass, proving the rule is satisfiable rather than merely unviolated. Two non-vacuity controls cover the silent-failure halves (a regex matching nothing; an env reader returning garbage), and exemptions must carry prose reasons. **Mutation-convicted:** removing `NEO_OLLAMA_HOST` from Compose reddens it by name.
- [x] Defaults unchanged: a deployment setting none of them behaves exactly as today. **Receipt:** every entry is `${VAR:-}`, so an unset var yields an empty value and the leaf default stands; `408 passed` across `ai/deploy/` and `ai/scripts/lint/`.
- [x] On a `--profile local-model` plane with `NEO_EMBEDDING_PROVIDER=ollama` and `NEO_OLLAMA_HOST=http://local-model:11434`, a native embed reaches the model service instead of container-localhost. **`[L3-deferred — operator handoff needed]`** — a running compose plane is not reachable from unit CI, so this is carried as Post-Merge Validation on the PR rather than gating merge.

  **Partial receipt already in hand, stated as partial:** a CPU-only `ollama/ollama:0.23.1` container mounted on the canonical `local-model-data` volume served `POST /api/embed` for `qwen3-embedding` — `http=200`, 4096 dims, runner CPU returning to `0.00 %` after the call. That proves the **model and the wire** work in a container. It does **not** prove the env reaches `kb-server`, which is the actual claim here and needs the plane. The operator-directed reproduction run covers it end to end.

## Out of Scope

- Changing the default provider. `openAiCompatible` stays the default.
- Whether ollama-native or openAiCompatible-against-ollama is the *recommended* path — this ticket makes the declared choice work; it does not re-open which choice to prefer.
- `#16849` (`Ollama.stream()` timeout), `#16846` (embedding batch env overrides) — same neighbourhood, separate defects.

## Avoided Traps

- **Reading the omission as policy.** The wired `NEO_OLLAMA_KEEP_ALIVE` and the fully-implemented provider, readiness-probe and embed paths all say ollama is meant to work. One passed variable out of six is an oversight with a long blast radius, not a decision.
- **A one-sided guard.** An assertion that only checks the ollama arm would pass trivially once this ships and never protect the sibling; the AC requires it to hold for `NEO_OPENAI_COMPATIBLE_*` on the current tree too.
- **Claiming this explains a specific plane's empty corpus.** It explains *any* containerized plane set to `NEO_EMBEDDING_PROVIDER=ollama`. Whether a given deployment is in that state is a one-command check (`docker exec <kb-container> printenv NEO_EMBEDDING_PROVIDER NEO_OLLAMA_HOST`), not something this ticket may assume.
