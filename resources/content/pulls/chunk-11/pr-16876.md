Resolves #16875

Refs #16780

A persistence failure in `embedChunks` is an **unbounded re-embed loop**, and this pins it as a property with its converging control. Verified empirically rather than reasoned from the code shape: three sweeps against a failing collection re-submit the same three distinct texts. All four #16875 acceptance criteria are ticked with receipts.

**The loop is not the finding — its invisibility is.** From provider load alone it is indistinguishable from an ingestion making progress: continuous inference, a corpus that does not grow, and every per-sweep receipt honestly reporting a handled failure. Nothing lies. There is simply no surface at which *"this sweep did the same work as the last one"* is expressible.

Evidence: L2 (spec-driven, real `embedChunks` against an injected failing collection) → L2 required (all four #16875 ACs are unit-verifiable; none names a host-observable effect). No residuals.

## Deltas from ticket

**Asserted at the submission boundary, not on `embedded` counts.** A sweep can report `embedded: 0` while still having paid for every provider call, and the call is the cost. Counting outcomes would measure the wrong thing precisely when the loop is most expensive.

**The converging control is the load-bearing half.** Without it, the loop spec is satisfied by any implementation that embeds at all — *"re-submitted"* is meaningless without a case that does not. The control asserts each text is submitted exactly once and the next sweep has nothing to do.

**The failing collection throws rather than silently accepting.** A permissive double would exercise a path production does not have. That is the exact defect corrected on #16870 hours earlier, where a spy that accepted any `{ids, embeddings}` pair deleted ChromaDB's mandatory refusal and made a spec prove the opposite of its claim. Applying the lesson rather than restating it.

**What this deliberately does not change.** `embedChunks` computes the embedding and upserts inside one `try`, so a failed write discards a paid-for vector. Retaining vectors across a failed write is a different design with its own cost, and AC-2 asks for *detection*, not *survival*.

**The two specs are each other's falsifier**, which is the whole design: the loop case fails against a converging implementation, and the control fails against one that re-submits. Neither alone distinguishes a working sweep from a looping one.

Serial marking is deliberate — these mutate shared `KB_Config.data` batch leaves and the `TextEmbeddingService.embedTexts` singleton, restored in cleanup.
