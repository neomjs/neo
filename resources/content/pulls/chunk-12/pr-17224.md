Resolves #17146

A host with no LM Studio could follow the documented portable path exactly, correctly set `NEO_ORCHESTRATOR_LMS_ENABLED=false`, and never start the wake receiver — then go permanently deaf while every surface reported healthy. The runtime separation was already correct; three documents disagreed with it. The platform matrix now carries both processes and says neither starts the other, the portable `ai:wake-receiver` invocation exists for the first time outside a macOS-only plist, and Day-0 stops pairing its wake-delivery claim with the one command that does not provide it.

Evidence: L3 (a receiver started with `NEO_ORCHESTRATOR_LMS_ENABLED=false` on its own port, probed with positive, negative and malformed controls) → L3 required (AC-5's no-LMS witness). Residual: none — every AC is discharged pre-merge.

## Deltas from ticket

**Two ACs pointed at the wrong file, and one would have introduced an error. Re-aimings were posted on the ticket before any edit ([`issuecomment-5304565748`](https://github.com/neomjs/neo/issues/17146#issuecomment-5304565748)) for @neo-gpt-emmy to overturn; he is dark until the weekly reset, so this proceeds under my own authority rather than waiting on a veto that cannot arrive.**

- **AC-2 as written was dischargeable without an edit.** `learn/agentos/wake-substrate/PersistentProcessManagement.md:217-221` already carries the complete invocation. The real gap was that `ai:wake-receiver` appeared **nowhere** in the local guide AC-1 targets. What was there is `ai:wake-manifest` — the manifest *generator*, which also takes `--manifest`, as an **output** path rather than an input — plus the arguments inside a macOS-only launchd plist. I read the generator as satisfying AC-2 on my first pass and corrected myself; the shared flag name is the trap, so the new section calls the collision out explicitly.
- **AC-3 would have deleted a true sentence.** `Day0Tutorial.md:782` said the host edge owns "wake delivery among them". That is **correct** — the receiver is host-side. The defect is a scope conflation: the same table used `host-edge` for the host half while `:789` handed the reader `npm run ai:host-edge`, which does not start the receiver. Implementing the AC literally would have swung into an untruth in the other direction. The table now carries the receiver as a third role and the text states outright that `ai:host-edge` does not give you wake delivery.
- **Structural fix beyond the ACs, in scope because it is the same defect.** The new section was initially nested under `## Install the host edge (macOS, supervised)` — reproducing the exact discoverability problem being fixed. It is promoted to a top-level `##`, which also splits the pre-existing mis-nesting where receiver material lived under a host-edge heading.
- **Observation, not fixed here.** The running receiver's startup banner reads *"manifest changes reload automatically (watch + 30s sweep); SIGHUP still forces one"*, while the guide says *"A restart is the only safe adoption step."* The guide is not wrong — its caution is explicitly about processes started **before** the reload handler existed, which cannot be distinguished from outside — but the two now read as contradictory to anyone who starts a receiver and sees the banner. Left alone deliberately: reconciling it needs the reload-authority question settled at the running process, which is a different lane.

## Test Evidence

Docs-only diff; no unit surface. The claims were verified against source and against a live process rather than asserted.

**Source verification, every structural claim in the ticket:**

| Claim | Verified at |
|---|---|
| Separate npm commands | `package.json:87` (`ai:host-edge` → `hostEdge.mjs`), `:90` (`ai:wake-receiver` → `wake/receiver.mjs`) |
| LMS one-variable opt-out | `ai/deploy/hostEdgeProfile.mjs:85`, `:100` |
| Wake plist launches the receiver with full args | `com.neomjs.agent-os-wake.plist:17-24` |
| Host-edge plist contains no receiver | its only "wake" mention is a comment at `:13` calling the receiver "a separate final-mile security boundary" |
| Matrix listed only host-edge | `local-agent-os/README.md:41-45` before this diff — three rows, no receiver row |

**AC-5 witness — a receiver started with LMS disabled, probed with all three controls:**

```bash
NEO_ORCHESTRATOR_LMS_ENABLED=false node ai/daemons/wake/receiver.mjs \
  --manifest <fixture>/routes.json --state-dir <fixture>/state --host 127.0.0.1 --port 3198
```

| probe | result | meaning |
|---|---|---|
| positive control — a route the receiver holds | `401` | request reached it; route resolved; signature validation ran |
| negative control — bogus subscription id | `404` | absent route |
| malformed control — subscription header omitted | `404` | indistinguishable from absent, matching the response table this guide already documents |

`NEO_ORCHESTRATOR_LMS_ENABLED=false` was read back from the process's **actual** environment via `ps -Eww`, not merely passed at launch, and the process showed `PPID 1` — no host-edge anywhere in its ancestry.

**What the witness proves and what it does not.** It proves the receiver's startup and route-serving path is independent of the LMS flag and of the host edge — which is the ticket's subject. It does **not** prove end-to-end harness dispatch: the probe carries a deliberately wrong signature precisely so nothing is delivered to a live seat. It is also honest to say LM Studio *was* running on this host; what was disabled is the receiver's LMS lane, not the machine's LM Studio, because stopping the operator's provider mid-session would disrupt other seats for no additional evidence — the receiver imports no provider path at all.

**A first attempt failed loud, which is itself a receipt.** The fixture initially omitted `adapterConfig.codexBinary` and the receiver refused to start with `fatal: … requires Codex app metadata and adapterConfig.codexBinary`. That confirms the ticket's Contract Ledger row "missing manifest fails loud; no coupling fallback".

**Non-destructive throughout.** The witness ran on port 3198 against a throwaway fixture, then was killed and the fixture removed. The operator's live receiver (PID 1383, port 3199) and host edge (PID 19562) were verified still running afterwards and were never touched.
