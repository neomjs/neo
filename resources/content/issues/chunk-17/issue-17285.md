# Cloud-plane `mc-server` imports a HOST-EDGE server's config at module scope — a plane violation, not a domain preference

## Context

Raised by @tobiu against PR #17280: *"why are there 'assigned' and 'unassigned' flags inside the memory core? this is NOT the github workflow server."*

The question is about `explore_lane_landscape`'s response schema, but the schema is downstream of a placement decision.

## The Problem

`explore_lane_landscape` is registered on the **Memory Core** MCP server (`ai/mcp/server/memory-core/toolService.mjs:374`). To serve it, that file imports:

| import | from | what it is |
|---|---|---|
| `GraphqlService` | `services/github-workflow/` | the GitHub transport |
| `PullRequestHistoryService` | `services/github-workflow/` | PR history reads |
| `makeOpenWorkCensusReader` | `services/github-workflow/` | the open-issue / open-PR page readers |
| **`GitHubWorkflowConfig`** | **`../github-workflow/config.mjs`** | **the sibling MCP server's config module** |

The last row is the one that is structurally distinct from the others. A service import is ordinary reuse; reaching into another *server's* config is not.

**Measured, not asserted:** grepping every `ai/mcp/server/*/toolService.mjs` for a sibling-server config import (`from '../<server>/config.mjs'`) returns **exactly one hit** — this one. It is not an established pattern in the tree. It is used at `:111-114` for `owner`, `repo`, `maxAssigneesPerIssue`, `maxLabelsPerIssue`.

The published response schema then carries the consequence: `authorityCoverage.assignedCount` / `unassignedCount` / `unassignedIds` are **pure GitHub issue-assignee facts** with no Memory Core content in them. Memory Core's genuine contribution to the landscape is the other half — the Native Edge Graph relation edges.

## The crossing is deliberate and documented — which is why this is a design question, not a bug report

`toolService.mjs` states the split explicitly:

> *"GitHub repository/query fan-out belongs to the GitHub Workflow child; census traversal bounds belong to the Memory Core child. Reading both at call time preserves reactive overlay/env resolution and fails loud when either provider is not wired."*

and frames the tool as *"the CURRENT-STATE Bird View, the third self-awareness context slot beside the two historical views."*

That reasoning is sound **about config resolution** — each leaf is read from the child Provider that owns it, at call time, per ADR-0019. It does not address **where the tool should live**. "This tool is about agent self-awareness" is a claim about purpose; "this tool's data is GitHub's" is a claim about domain. The current placement optimises the first and pays for it in the second.

No ADR governs MCP tool domain ownership. The two decision records touching `github-workflow` — `0004-github-content-architecture` and `0039-two-plane-sdk-barrel-boundary` — settle neither.

## The Fork

This ticket does not presume the answer; the tool genuinely joins two domains and reasonable people place it differently.

1. **Move the tool to the GitHub Workflow server.** The census, the readers and the config already live there. Cost: it loses cheap access to the Native Edge Graph edges, which is the half that makes it a *landscape* rather than a list.
2. **Keep it on Memory Core, but consume the sibling as a service rather than importing its config.** The self-awareness framing survives; the cross-server config reach — the part with no precedent — does not. Requires deciding how one server asks another for `owner`/`repo`/fan-out bounds.
3. **Split the composition.** The GitHub Workflow server owns and exposes the open-work census; Memory Core joins it with graph edges. Two tools, each in its own domain, at the cost of a round trip.

Whichever is chosen, the sibling-config import at `:33` should not survive as the mechanism — it is the concrete anomaly regardless of where the tool lands.

## Acceptance Criteria

- [ ] The fork is decided and recorded where a reader of either server will find it — the absence of a rule is why this drifted.
- [ ] `ai/mcp/server/memory-core/toolService.mjs` no longer imports `../github-workflow/config.mjs`; whatever replaces it is a mechanism the tree can have more than one of.
- [ ] The response schema's GitHub-domain fields are served by whichever server the fork assigns the domain to — a consumer should not have to know that assignee facts arrive from the memory server.
- [ ] If the tool stays on Memory Core: the reason is written at the tool boundary as a domain decision, not only as a config-resolution note.

## Out of Scope

- The degraded-count honesty fix (PR #17280 / #17278). It adds no import and creates none of this coupling; it stops an already-published schema from declaring `integer` for a field that returns `null`, and that correction travels with the tool wherever it lands.
- `explore_pull_request_history` and the other historical views, unless the fork's answer implicates them — `PullRequestHistoryService` is imported on the same line family and may share the question. Worth checking once the rule exists rather than assuming it does.

## Avoided Traps

- **Reading the documented rationale as a decision.** The comment explains config resolution correctly and was never a placement ruling; treating it as one is how the anomaly kept its cover.
- **Moving the tool to make the import go away.** The import is the symptom that made this visible; the domain question is the thing to settle, and a relocation that leaves the domains still mixed has spent the churn for nothing.

**@tobiu, escalating the original finding:** *"ADA! MC => INSIDE DOCKER, cloud plane. github and gitlab mcp servers => HOST EDGE. local."*

He is right, and it invalidates the framing this ticket opened with. I filed it as "which server should own this domain" — a design preference with three defensible shapes. It is not that. The two servers **run in different runtime planes by construction**, so the import is not a boundary someone chose loosely; it is a boundary that cannot hold.

| MCP server | compose files | plane |
|---|---|---|

| `knowledge-base` | 4 | cloud (`kb-server`) |
| **`github-workflow`** | **0** | **host edge** |
| **`gitlab-workflow`** | **0** | **host edge** |

So `ai/mcp/server/memory-core/toolService.mjs:33` —

```js
import GitHubWorkflowConfig from '../github-workflow/config.mjs';   // module scope
```

— is a **cloud-plane container reaching into a host-edge server's config module, at module load**. Not a service it could call over a boundary: a filesystem import across a plane split.

### What this explains that the original framing missed

**#17283 is not a fork, and I filed it as one.** I wrote that ticket as *"the plane may be deliberately credential-free — both readings are defensible"* and asked someone to decide. The topology already decided: the container holds no GitHub credential **because git-provider access is a host-edge concern by design**. That ticket's option 2 is not one candidate among two — it is the answer, and I did not know the topology well enough to see it. Correcting it there.

**The census is permanently degraded in the cloud plane, by construction.** Not a transient GitHub outage — the steady state for a containerized MC. That makes the honesty fix in PR #17280 load-bearing rather than cosmetic: without it, every containerized Memory Core reports `totalOpenItems: 0` forever and every seat reading it concludes the backlog is empty.

**Why I could not see it, which is the part worth keeping.** I measured everything in a single dev checkout, where the cloud plane and the host edge sit in one filesystem and every cross-plane import resolves cleanly. A dev checkout **collapses the plane distinction**, so a plane violation is indistinguishable from an ordinary relative import — it type-checks, it lints, it boots, and the specifier looks like every other sibling reference in the file. The empirical test I ran (remove the file → `ERR_MODULE_NOT_FOUND`) proved the coupling was hard, but it could not tell me the two ends live in different runtimes.

### The fork is narrower than this ticket first claimed

Option 1 as originally written — *"move the tool to the GitHub Workflow server"* — now reads differently: it means moving a self-awareness tool out of the cloud plane and onto the host edge, which is a topology decision about where lane-awareness lives, not a file relocation.

What survives unchanged: **the `:33` import cannot be the mechanism**. A cloud-plane service that needs host-edge facts asks for them across a boundary or does not have them.

### Unchanged

PR #17280 stays merge-eligible and is now *more* clearly correct: it adds no import, creates none of this coupling, and it is what stops a permanently-degraded cloud-plane census from reading as an empty backlog.

## Plane-crossing census — measured, whole tree. The mixture is **one line**.

@tobiu asked whether to dive into the cloud/host-edge mixture ahead of a refactor. Measured first, and the answer changes the plan: **there is no mixture to refactor.** There is one import.

### The oracle, read from deployment rather than from directory names

A server is container-plane iff a `docker-compose*.yml` builds it via `TARGET_SERVER: <name>`. Grepping every compose file yields exactly two:

| plane | servers |
|---|---|
| **container** | `memory-core`, `knowledge-base` |
| **host edge** | `github-workflow`, `gitlab-workflow`, `file-system`, `neural-link` |

`neural-link`'s compose mentions are config plane-member references, not a build — so it is host-edge, which fits a browser driver.

### Result: 748 tracked `.mjs` under `ai/`, 1 crossing

AST-based (static + dynamic imports), whole tree rather than entrypoint closures:

```
scanned 748 tracked .mjs files under ai/
server-to-server PLANE CROSSINGS: 1
  [container -> host-edge] ai/mcp/server/memory-core/toolService.mjs:33
      -> ai/mcp/server/github-workflow/config.mjs
```

That is the line this ticket already names. Nothing else in `ai/` crosses.

### What the surrounding structure actually looks like

Because "one crossing" invites the question *"then why did it feel systemic?"*:

| pattern | count | verdict |
|---|---|---|
| Service reads **its own** domain's server config (`ai/services/github-workflow/*` → `github-workflow/config.mjs`) | **58 files** | **cohesion, not mixture** |
| **Barrels** wiring several domains | 4 sites | **already plane-correct** — see below |
| Cross-domain config bindings, **container → container** | 6 | domain coupling, **no plane issue** |
| Cross-**plane** server-to-server | **1** | the defect |

**The barrels are the finding I did not expect.** `ai/services.mjs` reads only `knowledge-base/config.mjs` and `memory-core/config.mjs` — both container. `ai/services.host.mjs` reads only `github-workflow/config.mjs` and `neural-link/config.mjs` — both host-edge. The plane split is already encoded in *which barrel* a service is published through, and it holds perfectly. Whoever drew that line drew it correctly; `toolService.mjs:33` is the single place that bypasses it.

The 6 remaining cross-domain bindings are `knowledge-base` ×3, `graph` ×2 and `shared/vector` ×1 all reading `memory-core/config.mjs` — container→container, so plane-clean. Worth knowing for a domain refactor, irrelevant to this one.

### Correcting my own numbers, because the first one would have justified the wrong plan

This census read **182 → 134 → 68 → 10 → 1** as I fixed the unit three times:

1. **182** — I keyed the crossing's plane on *the entrypoint the walk started from* instead of *the importing file*, so `memory-core/logger.mjs → memory-core/config.mjs` counted as a crossing whenever the walk had entered via a host-edge server. That measured **reachability**, not adjacency.
2. **134** — plane-neutral shared code importing a server's private surface, which is a different smell entirely and had no business in a plane count.
3. **68** — config-only, still counting `ai/services/github-workflow/*` reading its own `github-workflow/config.mjs`, which is cohesion.
4. **10** → **1** — separating barrels and same-plane domain coupling from actual cross-plane adjacency.

**182 would have justified a refactor. 1 justifies a three-line change.** Recording the sequence because the first number was the one that felt actionable, and it was measuring something else — the same wrong-unit failure I hit twice earlier today on this branch.

### What this means for the fork above

The three options in this ticket were sized for a systemic problem. At n=1 the question narrows to: **what should `toolService.mjs:111-114` do instead**, given it needs `owner` / `repo` / `maxAssigneesPerIssue` / `maxLabelsPerIssue` for the lane-landscape census?

And #17283's correction answers it — the container should not be running that census at all, because git-provider access is host-edge by construction. So the likely shape is *not* "get the config another way", it is "the container-side path reports the capability unavailable and needs no provider config", which removes the import by removing the reason for it.

That is a behaviour change to a published tool, so it stays a decision rather than something I take unilaterally. But it is a small one, and it is the same disposition #17283 already landed on.

**Bound on this census, stated:** it covers static and dynamic relative imports across tracked `.mjs` under `ai/`. It does not cover runtime-assembled paths (`path.join(root, 'ai/mcp/server/...')`), which is the variant that bit me twice today and which no import-graph sweep can see. A literal-string grep is a separate pass if someone wants that closed.

## ⚠️ Third correction — do NOT strip the tools. The logic belongs in the cloud plane; the *import* was the miss.

**@tobiu, reframing again:** *"PullRequestHistoryService in general sounds useful, for github workflow mcp server tool… we can keep logic inside the cloud plane, just the github workflow service import was a miss."* Plus: this is the **Bird Views** topic, it wants to **embed PR conversation bodies**, and that connects to **multi-tenant repository ingestion**.

My previous disposition — remove `explore_pull_request_history` from MC, strip `explore_lane_landscape`'s census — was **wrong**, and wrong in the expensive direction: it would have deleted capability to fix an import.

### What the code actually shows

`PullRequestHistoryService.explorePullRequestHistory` has **two data legs**, not one:

| leg | source | works in a container? |
|---|---|---|
| `query` = `GraphqlService.query`, `rest` = `GraphqlService.rest` | **live GitHub API** | **No.** No container holds a git-provider credential (#17283) — this leg is dead in every deployment |
| `scanCorpus` = `scanPullRequestCorpus({pullsDir, archiveRoot})` | **the synced corpus on disk** | **Yes.** The corpus ships in the repo and needs no credential |

So the cloud-plane-legal path **already exists in the service**. The live-API leg is the miss, and the `aiConfig` defaults (`owner`, `repo`, `pullsDir`, `archiveRoot`, `productNameDenylist`) resolve through `github-workflow/config.mjs` — correct for a github-workflow service, wrong the instant `memory-core/toolService.mjs` imports it.

### Nothing operational regresses, which is what makes the narrow fix safe

Both GitHub-reaching legs are **already non-functional in the cloud plane**. The live symptom is the one that opened this whole thread: `explore_lane_landscape` returning `totalOpenItems: 0, degraded: true` with `Could not authenticate with GitHub`. Removing a credential-dependent leg from a container removes code that cannot run there — it is not a capability loss, it is deleting a path that only ever returned a degraded envelope.

### The ingestion connection, and a correction to the recollection

The operator's memory was *"blocked until neo itself becomes an ingestion tenant."* Measured, that is close but not the blocker:

- **Neo is already a tenant.** #16566: all three configured repos `checkpointStatus: complete`, one tenant (`tenantHash cf744f16ee7f`). The live problems there are a **starved lane** (`nextDueAt` ~11h past) and `KB_TENANT_REPO_ACCESS_EVIDENCE_EXPIRED` — not absence.
- **`tenant-repo-mirrors` is mounted by `orchestrator`** — cloud plane. So the ingested material is already on the right side of the boundary.
- **The real blocker is #17260** (unassigned epic): mirrors materialize **one envelope per file**, whole files run past the 14,336-token safe band, and *"the dispatch mechanism already exists end-to-end — what is missing is anything production-grade to dispatch to."*

So embedding PR conversation bodies is blocked on **chunking parsers (#17260)**, not tenant onboarding. Worth having precisely, because "onboard neo as a tenant" is work nobody needs to do.

### Corrected disposition — narrow

1. **Remove the four `github-workflow` imports from `ai/mcp/server/memory-core/toolService.mjs`** (`GraphqlService`, `PullRequestHistoryService`, `makeOpenWorkCensusReader`, `GitHubWorkflowConfig`). That is the whole plane violation and the whole of this ticket.
2. **Both tools stay on MC.** Synthesis stays cloud-plane, where the model is (`local-model`, Ollama on `neo-mcp-network`, allowlisted to `chroma, kb-server, mc-server, orchestrator` — nothing host-edge).
3. **The cloud-plane source is the corpus leg**, already implemented, plus the graph edges MC owns.
4. The live-API legs go host-edge with the service, where a credential exists — the service is already correctly homed in `ai/services/github-workflow/`; only MC's reach into it is wrong.
5. Quality of the corpus path improves via **#17260**; not a blocker for this ticket, and this ticket is not a blocker for it.
