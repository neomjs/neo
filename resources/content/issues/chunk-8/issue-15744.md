# Give Data Sync a dedicated GitHub App identity

## Context

The scheduled Data Sync Pipeline is currently failing for more than one reason. A census of its latest 100 runs through 2026-07-23 07:37 UTC found 67 failures and 33 successes. Two authorization boundaries account for 52 of those 67 failures:

- 39 generated-data pushes rejected by the active [`code scanning merge protection` ruleset](https://github.com/neomjs/neo/rules/19087298)
- 13 DevIndex OptIn reads rejected with `Resource not accessible by integration`

Representative evidence: [ruleset rejection](https://github.com/neomjs/neo/actions/runs/29559832086), [current failing run](https://github.com/neomjs/neo/actions/runs/29988762639).

## Problem

The workflow passes the repository-scoped `GITHUB_TOKEN` through all DevIndex stages, including the cross-repository OptIn read from `neomjs/devindex-opt-in`. It then creates a fresh local commit and pushes it directly to `dev` with the same identity.

These are different authorization contracts, but today they share one token:

1. The repository token is not an explicit cross-repository identity for the OptIn repository.
2. A new generated commit cannot already carry target-branch CodeQL evidence, while the active code-scanning ruleset has no permitted bypass actor for this pipeline.

The retry work in #15359 remains useful for genuinely transient reads. Its conclusion that the current integration denial can be treated as transient is no longer sufficient for this persistent configuration boundary. Closed historical tickets remain immutable; this ticket supersedes only that diagnosis.

## Architectural Reality

- The workflow grants `contents: write`, passes `secrets.GITHUB_TOKEN` into every data stage, then runs a direct rebase/push sequence: [`data-sync-pipeline.yml`](https://github.com/neomjs/neo/blob/f1a8013b01488e05445888470ad21a439704b230/.github/workflows/data-sync-pipeline.yml#L16-L81).
- OptIn targets a separate repository: [`OptIn.mjs`](https://github.com/neomjs/neo/blob/f1a8013b01488e05445888470ad21a439704b230/apps/devindex/services/OptIn.mjs#L29-L76).
- The GitHub service currently classifies `Resource not accessible by integration` inside its retry path: [`GitHub.mjs`](https://github.com/neomjs/neo/blob/f1a8013b01488e05445888470ad21a439704b230/apps/devindex/services/GitHub.mjs#L325-L434).
- GitHub documents `GITHUB_TOKEN` as scoped to the workflow repository and documents installation-token creation for GitHub Apps in Actions: [token scope](https://docs.github.com/en/actions/concepts/security/github_token), [GitHub App authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow).

## Fix

Create **two** dedicated, least-privilege GitHub App identities for Data Sync and install each only on the repositories it must reach.

> **Amended 2026-07-26.** This section originally prescribed **one** App. The two-identity split was raised in @neo-gpt-emmy's intake delta and shipped in PR #15953; the body is corrected here rather than left contradicting the implementation. `actions/create-github-app-token@v3` scopes ONE permission set across a whole repository set, so a single App spanning all three repos would give the ruleset-bypass identity write access to the intake repositories **and** let the intake identity publish to `neo`. For an actor that bypasses a security ruleset, that coupling is the wrong trade.

| Identity | Installed on | Permissions | Role |
|---|---|---|---|
| **Publisher** | `neomjs/neo` | `contents: write` | supplies the checkout/push credential; **sole** ruleset-bypass actor |
| **Intake** | `neomjs/devindex-opt-in`, `neomjs/devindex-opt-out` | `issues: write`, `metadata: read`, explicitly **no** `contents` | injected only into the OptIn/OptOut collection stages |

- Mint short-lived installation tokens near workflow start from each App's credentials.
- Pass each token only to the stages entitled to it — never one token for both boundaries.
- Request the permissions **explicitly** on the token, not only on the installation: without `permission-*` inputs the action mints a token carrying every permission the installation holds, so least-privilege would live in a settings page nobody reads at review time.
- Add that specific App as the code-scanning-ruleset bypass actor; do not grant a blanket GitHub Actions bypass and do not disable the rule.
- Probe both target repositories before expensive data collection begins. Distinguish persistent installation/permission denial from transient server or transport failure.
- Preserve bounded retries for replay-safe reads. Do not replay mutations unless their idempotency is explicit.
- Document credential rotation and installation expectations without exposing secret values.

## Contract Ledger

| Surface | Current contract | Required contract | Verification |
| --- | --- | --- | --- |
| Workflow credential boundary | Repository `GITHUB_TOKEN` is reused across repositories and publish | **Two** short-lived App tokens with explicit installations and explicit permission requests: Publisher (`contents: write`, `neo`) and Intake (`issues: write` + `metadata: read`, both DevIndex repos) | Focused workflow test plus permission preflight |
| Per-stage credential scope | Every stage inherits `process.env` wholesale | Each emission stage declares a `tokenScope`; the child env carries at most the one credential it is entitled to, and an undeclared scope fails closed | Unit assertions by VALUE across the whole child env |
| Git-layer credential | `persist-credentials` leaves the token in `.git/config` for the whole job | Checkout persists nothing; publisher auth supplied per-invocation via `GIT_CONFIG_*` in the child env, never argv | Argv witness at the `gitAuthenticated` boundary |
| `GitHub.query()` error classification | Integration denial enters the transient retry path | Persistent installation/permission denial fails fast; genuine transient reads remain bounded | Unit coverage for both classes |
| Ruleset `19087298` | No Data Sync bypass actor | Only the **Publisher** App may bypass for generated-data publication; the Intake identity cannot publish at all | Ruleset inspection plus controlled publish |

- [ ] Only the **Publisher** App is granted the narrow code-scanning-ruleset bypass needed for generated-data publication.

## Intake delta — live premise survives; one permission-topology fork precedes implementation

Fresh checks against current `dev`, the live ruleset, both DevIndex intake services, Neo KB, and GitHub’s current App-token contract preserve #15744’s core diagnosis after #15750:

- The workflow still passes the repository `GITHUB_TOKEN` through Data Sync, and the bounded publisher still performs `git push origin HEAD:dev` through the checkout credential.
- Ruleset `19087298` remains active with CodeQL protection and no bypass actor.
- #15750 moved publication out of inline YAML, but did not change either authorization boundary.

One required repository is missing from the ticket’s current framing: the scheduled sequence runs both OptIn **and OptOut**. `OptOut.mjs` reads `neomjs/devindex-opt-out` and mutates its issues by adding comments and closing processed requests, just as OptIn mutates `neomjs/devindex-opt-in`. A token installed only on `neo` plus `devindex-opt-in` would merely expose the next persistent integration denial later in the sequence.

There is also a real least-privilege fork. GitHub’s official `actions/create-github-app-token@v3` contract scopes a token with one repository set and one explicit permission set; it does not define a different permission map per selected repository. Therefore a single token spanning `neo`, `devindex-opt-in`, and `devindex-opt-out` would carry its aggregate `contents: write` and `issues: write` permissions across all three repositories. That is the minimum *aggregate* permission set for one App, but not strict per-repository least privilege. References: [official action token/repository/permission inputs](https://github.com/actions/create-github-app-token#inputs), [GitHub App installation permissions and selected repositories](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party).

### Recommendation

Use two purpose-scoped App identities/tokens within this same ticket:

1. **Publisher App** — installed only on `neomjs/neo`; owns the required Neo read permissions plus `contents: write`, supplies the checkout/push credential, and is the sole ruleset-bypass actor.
2. **Intake App** — installed only on `neomjs/devindex-opt-in` and `neomjs/devindex-opt-out`; owns `issues: write` and is injected only into the OptIn/OptOut child processes.

This keeps the ruleset-bypass identity unable to mutate the intake repositories and keeps the intake identity unable to publish to `neo`. The bounded publisher will need per-command environment injection rather than one global `GITHUB_TOKEN`; that is testable without exposing either secret.

Operator-owned decision before tracked implementation: accept the recommended two-App split, or explicitly accept the cross-repository overgrant of one aggregate-permission App. Once chosen, the open ticket can absorb the body delta; no new ticket or historical reopen is needed.

Architecture route: continue under #15744 ticket intake rather than an Ideation Sandbox, because this is a reversible workflow/credential split rather than a new subsystem. Blast class remains high operational/security due to secrets, three repository installations, and the ruleset bypass.
