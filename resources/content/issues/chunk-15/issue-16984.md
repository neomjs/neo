# Planned-restart completeness skips corrupt and uncertain runs

## Context

Approve+Follow-Up successor from the exact-head review of PR #16974 at `a27c14c697a7d2598ba7ed5770fef7d74ff1cca7`, which resolves #16482.

That PR repairs the principal production defect: planned-restart subtraction moves from the data-heal ledger to the recovery-run ledger, and the published service record now exposes baseline/read/write degradation. The remaining gaps are bounded because restart churn stays non-authoritative with `actionClass: record`; they do not authorize a lifecycle effect. They still need a new ticket so the conditions survive #16482 closing.

Independent exact-head falsifier: one corrupt retained `.jsonl` artifact passed through the real `readRecentRecoveryRunStates` and `collectPlannedRestarts` returned:

```json
{"count":0,"reason":null,"status":"available"}
```

The reader catches JSON parse failures and skips the artifact. The bridge therefore cannot distinguish a complete empty ledger from an incomplete one and can certify a detector healthy while under-subtracting a restart we initiated.

The PR's new tests have a second, related bound: they drive `DeploymentRuntimeAccessService.restartTarget()`, then hand-build a recovery-run entry with `createRecoveryRunStateEntry()` and inject an in-memory reader. They do not execute the canonical `RecoveryActuatorService → appendRecoveryRunState → readRecentRecoveryRunStates → DeploymentStateBridgeService` chain.

## The Problem

### 1. Corrupt retained artifacts become a false complete read

`readRecentRecoveryRunStates()` deliberately catches a JSON parse failure and continues. That behavior made sense for a best-effort health listing, but it is not sufficient for a consumer that claims its planned-restart count is provably complete. A skipped artifact may be the exact lifecycle proof that must be subtracted.

With a valid churn baseline, the bridge sees fewer than the retention limit, publishes `plannedRestarts.status: available`, and leaves `restartChurn.detecting: true`. This is not an unavailable marker; it is a false healthy detector.

### 2. The regression proof stops below the canonical producer/store boundary

The tests validate the low-level lifecycle proof shape and several useful predicates, but the most load-bearing composition is reconstructed by the fixture. These regressions remain invisible:

- `RecoveryActuatorService.finishAction()` stops carrying `runtimeAccess`;
- `reconfigure` stops forwarding the restart proof;
- the store's latest-row/read behavior changes;
- an uncertain post-dispatch terminal is treated as definitely not applied.

### 3. An uncertain dispatched effect cannot certify zero planned restarts

The actuator can persist `status: failed` with `effectDisposition: uncertain` when an effect was dispatched and authority moved before its outcome became knowable. Such an entry has no successful lifecycle proof, so the current predicate counts zero. It also cannot honestly prove that no restart occurred. The safe result for that window is degraded/suppressed detection, not an available zero.

### 4. The proof window is stamped later than the Docker observation it bounds

The bridge reads Docker `RestartCount` near the start of the service snapshot, but a new baseline is stamped with the later diagnosis time. `DeploymentRuntimeAccessService` creates the lifecycle proof only after the awaited Docker restart response, despite the PR JSDoc calling it a dispatch-time stamp.

On a first observation or window re-anchor, a planned restart can begin after inspect and complete before the later baseline stamp. The stored baseline then carries the pre-restart count with a post-restart timestamp; the next snapshot excludes the proof as older than the baseline and can classify our restart as unplanned. Both window ends must derive from observation coordinates that actually bound the Docker count.

## The Architectural Reality

- `ai/daemons/orchestrator/services/RecoveryActuatorService.mjs` owns lifecycle execution and the durable run outcome.
- `ai/services/memory-core/helpers/recoveryRunStateStore.mjs` owns retained recovery-run artifacts and their read-completeness semantics.
- `ai/daemons/orchestrator/services/DeploymentStateBridgeService.mjs` consumes that store to publish planned-restart detector health.
- `ContainerHealthDiagnosisService` keeps restart churn non-authoritative and record-only; this successor must not move that boundary.
- ADR-0025 owns restart-churn detection; ADR-0026 owns lifecycle-actuator receipts and uncertainty.

The correct composition is producer → durable store → strict/completeness-aware reader → bridge. A hand-built DTO or an array injection is useful for predicate units, but it cannot be the sole proof of that composition.

## The Fix

1. Give the recovery-run read used for planned-restart subtraction explicit completeness semantics. A retained empty, corrupt, or unparsable latest artifact must either throw into the bridge's existing degraded path or return structured completeness metadata that the bridge must reject as unavailable.
2. Add one production-bound composition control that executes an actual restart and reconfigure through `RecoveryActuatorService`, persists through `appendRecoveryRunState` in a temporary directory, and lets the bridge use the default reader.
3. Add actual-writer negative controls for a no-restart lifecycle operation, wrong service, definite not-applied/declined outcomes, and a retained corrupt artifact.
4. Treat a within-window post-dispatch uncertain outcome as degraded unless a lifecycle restart proof establishes the result. Do not guess either applied or not-applied.
5. Bind the baseline and proof-count window to the actual prior/current Docker inspect-proof observation coordinates; add an interleaving restart control that begins after inspect and completes before diagnosis.
6. Correct durable prose that says `runtimeAccess.observedAt` is stamped at dispatch: the current proof is created after the Docker request returns.

## Decision Record impact

`aligned-with ADR 0025 and ADR 0026` — no authority or action-class change. The successor tightens evidence completeness at their existing detect/actuator boundary.

## Acceptance Criteria

- [ ] A retained corrupt, empty, or unparsable recovery-run artifact cannot yield `plannedRestarts.status: available`.
- [ ] A complete empty store still yields an available count of zero.
- [ ] A production-bound test executes actual restart and reconfigure outcomes through `RecoveryActuatorService`, persists them via the real store, and reads them through the bridge's default reader.
- [ ] Removing `runtimeAccess` propagation from `finishAction` or reconfigure makes the production-bound test red.
- [ ] Actual-writer controls prove update-memory-limit, wrong-service, definite not-applied, and declined/no-action entries are not subtracted.
- [ ] A within-window `effectDisposition: uncertain` entry degrades planned-restart detection rather than certifying zero.
- [ ] The restart-churn fact remains `authoritative: false`, `actionClass: record`, and last in classification order.
- [ ] A planned restart that begins after inspect and completes before diagnosis cannot fall below the next baseline window.
- [ ] JSDoc states the actual proof timestamp boundary without calling a post-response stamp a dispatch stamp.

## Out of Scope

- Reopening #16482 after PR #16974 merges.
- Making restart churn authoritative or allowing it to actuate recovery.
- Combining the heal-event and recovery-run ledgers.
- Redesigning the recovery-run retention policy beyond exposing whether the retained read is complete.

## Avoided Traps

- **Treating skipped corruption as resilience.** Best-effort listing and evidence-complete counting have different fallback contracts.
- **Counting uncertain as applied.** That can hide real churn. The honest answer is that the subtraction is unavailable.
- **Counting uncertain as not applied.** That can raise false churn for an effect that landed.
- **Replacing focused predicate tests.** Keep them; add the missing production composition proof rather than turning every unit into an integration test.
