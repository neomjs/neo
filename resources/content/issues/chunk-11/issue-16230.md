# Authority lease: refuse a second live same-role orchestrator per machine

## Context

`#16229`'s OQ1 answer proved empirically that a bare host `npm run ai:orchestrator` claims `container-plane` beside the container that owns it, writes authority state, and starts heavy lanes within seconds. That ticket's entrypoint fix (leaf-owned requiredness) closes the **accidental** path: an *undeclared* role now refuses at boot. This ticket closes the residual named in its OQ1 thread: the **deliberate-but-wrong** path — an explicit `container-plane` declaration on a host where the container already runs that role. Split decision recorded on `#16229` (different surface, different threat model, separately PR-able).

Verified from source: nothing in the tree does cross-process role exclusion. `taskAuthority.mjs` audits are intra-process registry coherence (unknown profile, duplicate *task registration*, empty topology); the authority receipt (`orchestrator-authority.json`) is a receipt written by the boot path, not a lock — a second declarer overwrites it.

Live latest-open sweep: latest 20 open issues at 2026-07-31T16:40Z; no equivalent (`#16229` = the entrypoint/discoverability fix; `#16210` = the host-edge runtime that shipped the receipt). A2A herd-window sweep clean; the filing itself was requested by the `#16229` author.

## The Problem

Role ownership is per-machine single-owner by design (the single-explicit-role rule), but the invariant is enforced nowhere across processes. Two orchestrators declaring the same role on one machine both boot, both write the receipt (last writer wins), and both run mutually-exclusive maintenance lanes against the same substrate and the same scarce inference provider.

## The Architectural Reality

- `ai/daemons/embed/drainLock.mjs` is the in-tree precedent primitive: a pid-liveness file lock — `process.kill(pid, 0)` (`ESRCH` → dead, reclaimable; `EPERM` → alive, must not displace), `DrainLockHeldError` with **refuse, no takeover** semantics, acquired at daemon start.
- The orchestrator boot path already writes `orchestrator-authority.json` (receipt) and logs `authorityProfile=... authorityReceipt=...` at start; the lease belongs immediately before that write.
- `ai/mcp/server/memory-core/Server.mjs` shows the shutdown-release idiom (`process.on('exit', () => lock?.release())`).

## The Fix

1. **Generalize the existing primitive, do not duplicate it**: move/extend `drainLock.mjs` into a shared location (candidates: `ai/services/shared/` — sibling precedent for shared primitives — or a daemon-shared module; implementer's structural pre-flight decides) so embed drain and authority lease use ONE implementation.
2. **Acquire a role-scoped lease at orchestrator boot**, before the authority receipt write: lock file beside the receipt, content `{pid, profile, startedAt}`.
3. **Refusal semantics**: same role held by a DIFFERENT live pid on this machine → structured, fail-closed refusal naming the holder pid, the role, and both entrypoints; non-zero exit. Dead-pid stale lease → reclaim (drainLock semantics). Different roles (host-edge beside container-plane) → no conflict, by design.
4. **Release on clean shutdown** (exit hook, per the existing idiom).

## Decision Record impact

`aligned-with ADR 0019` §10.8 — makes the single-owner rule mechanically enforced across processes on one machine, instead of true only inside each process's own topology audit.

## Acceptance Criteria

- [ ] A second orchestrator boot declaring a role held by a LIVE pid on the same machine refuses with a structured error naming holder pid, role, and both entrypoints, and exits non-zero.
- [ ] A dead-pid stale lease is reclaimed without manual cleanup.
- [ ] Different roles on one machine never conflict.
- [ ] Clean shutdown releases the lease.
- [ ] Unit spec with an injected liveness probe covers held-live, held-dead, different-role, and release paths.
- [ ] One shared lock implementation (embed drain callers unchanged and green) — no second bespoke lock.

## Out of Scope

- Cross-MACHINE exclusion (pid-liveness is machine-local by construction; a distributed lease is a different problem).
- `#16229`'s entrypoint, documentation, and discoverability fixes.
- Wake protocol and receiver supervision (`#16180`).
- Container-internal replica prevention (the container runtime owns replica counts).

## Avoided Traps

- **A second lock implementation beside `drainLock`** — two liveness-lock mechanisms is the same class of drift as two config-requiredness mechanisms; generalize the one that exists.
- **Treating the authority receipt as the lock** — it is written post-boot and races; the lease must be acquired first.
- **A pid file without liveness** — stale files would block forever; `process.kill(pid, 0)` reclaim is the point of the precedent.

### Fact 1 — the collision surface exists as specced

The container's plane root `/app/.neo-ai-data` is the canonical checkout's `.neo-ai-data` bind-mounted, so a bare host process from the canonical checkout and the container orchestrator write their authority receipts to the **same physical directory**. A lease file beside the receipt is mutually visible. ✓

### Fact 2 — the pid-liveness probe is namespace-blind, verified on this machine

```
$ docker inspect neo-local-agent-os-orchestrator-1 --format '{{.State.Pid}}'
335860
$ ps -p 335860 -o pid,comm
(no such process)
```

Docker Desktop on macOS runs containers in a VM: the container holder's pid is **not a live pid in the host namespace**. So when a bare host process reads the container's lease and runs `process.kill(containerPid, 0)` it gets `ESRCH` → "dead holder" → **reclaims the lock and starts the duplicate anyway**. The lease fails *open* in exactly the deliberate-but-wrong case this ticket exists to close (Context: "an explicit `container-plane` declaration on a host where the container already runs that role"). The reverse direction fails identically: a container probing a host holder's pid sees nothing.

Worse than useless in one sub-case: if the container's in-namespace pid (e.g. 7) collides with an *unrelated live host pid*, the probe returns EPERM/alive and the refusal names a wrong holder.

### What still works

Two bare **host** processes (terminal + LaunchAgent, two terminals) share the pid namespace — the drainLock probe is correct there, and for its current consumers (embed daemon vs in-process server loop) it stays correct: those contenders are always same-namespace.

### Options

- **(a) Namespace-aware probe** (`docker inspect` from host): couples the primitive to the Docker CLI, is unavailable in the container→host direction entirely. **Reject.**
- **(b) Heartbeat/TTL lease:** the holder refreshes the lease file on its poll cadence (the orchestrator polls every 3s; refresh is nearly free). A contender reads `lastPulse`: fresher than TTL → refuse (holder verifiably live, any namespace); older than TTL → stale → reclaim. Uniform across host-host, host-container, and container-host with no namespace reasoning at all.
- **(c) Hybrid:** same-namespace pid probe for instant dead-detection + TTL as the cross-namespace authority. More precise, more machinery.

### Recommendation: (b), with the generalization seam preserved

Pure TTL heartbeat is the simplest mechanism that actually covers the named case both directions. The shared-primitive plan survives unchanged in shape: one atomic claim/refuse/reclaim/release core with the **liveness strategy injected** (drainLock already takes `isAlive` — the seam exists). The authority lease injects TTL-liveness; the drain lock keeps pid-liveness. One implementation, no second bespoke lock — the avoided trap stays avoided.

Trade-off to name honestly: a live-but-wedged holder whose pulse lapses past TTL gets reclaimed (a TTL of ~60s against a 3s poll makes that a genuine-wedge signal, and the failure it unlocks is the rare one; the failure it prevents is the daily one).
