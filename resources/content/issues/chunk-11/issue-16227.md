# Vector rebuild failure receipts and bounded embed retry

## Context

The `#16208` cross-store rebuild's memory leg reported `unrecoverable=7562` (~24% of 31,202 rows). Verified in-session: the exact source→target diff is 7,562, and a 400-row sample spread across that population returned **400/400 rows with full documents and metadata**. The rows are per-pass embed-call failures under provider saturation (48 docs in flight against a parallel-4 embedder sharing one inference queue with generation lanes) — not content loss. The flat `unrecoverable` count forced a store-diff investigation that one histogram line would have answered.

## The Problem

Two defects on one surface:

1. **The receipt collapses two opposite fates into one number.** Content problems (`document-empty/missing/invalid`, `metadata-row-missing`) are terminal — retry never helps; the remedy is source-side repair or explicit acceptance. Embed failures (`embedding-provider-error`, `embedding-result-malformed`) are transient — a resume sweep fixes them. Opposite remedies, one indistinguishable count.
2. **The embed path has no retry.** `embedRecoverableDocuments` binary-splits a failed batch to isolate failing docs, and at `slice.length === 1` a single failed attempt permanently records the row for the pass. Under saturation this classified ~7.5k healthy rows as failures — the missing bounded-retry primitive of the `#16222` family, in the rebuild path.

## The Architectural Reality

- `ai/scripts/maintenance/repairMemoryCoreStoredEmbeddings.mjs` owns classification (`getDocumentProblem`, `getEmbeddingFailureReason`, `recordUnrecoverable`) and the binary-split embed (`embedRecoverableDocuments`). Its result is consumed by three surfaces: `defragChromaDB.mjs` (entry array + previews), `ai/services/memory-core/helpers/reEmbedMissingHeal.mjs` (`counts.unrecoverable`, `unrecoverableIds`), and the rebuild runner. Changes must be additive.
- `ai/scripts/maintenance/rebuildMemoryCoreVectorStore.mjs` (branch `agent/16208-mc-vector-store-rebuild`, pre-PR) builds the receipt: currently a fate-less count in the done-line plus the full per-row entry list in the receipt JSON (~750KB at 7.5k rows). Resume-by-diff (target ids as skipIds) makes full id lists redundant.

## The Fix

Converged design (operator dialogue, this session): **one reason-code family, an array of receipts**.

1. **Extractor — classifier-stamped fate:** every unrecoverable entry gains `retryable: Boolean` at classification time (`true` for `embedding-*`, `false` for `document-*`/`metadata-row-missing`). The reason→fate mapping lives in exactly one place; consumers never pattern-match reason strings.
2. **Extractor — bounded retry:** `embedRange` retries the same slice `attempts` times (default 3) with backoff before binary-split descent; a single-doc failure records only after its attempts are exhausted. Whole-slice retry first absorbs transient storms at the widest (cheapest) range. `attempts`/backoff/clock injectable for tests.
3. **Runner — receipt reshape:** replace the flat per-row dump with `failed` = per-reason array `{reason, count, retryable, sampleIds}` (sampleIds capped ~10). Reconciliation becomes `targetAfter + sum(failed[].count) === planned`. Done-line prints the derived rollup: `failed=N (X resumable, Y terminal)`.
4. **Specs** for both: retry exhaustion + retryable stamping + backoff bounds (extractor); grouping + rollup + reconciliation (runner).

## Acceptance Criteria

- [ ] Every unrecoverable entry carries classifier-stamped `retryable`; no consumer derives fate from reason strings.
- [ ] `embedRange` retries a failing slice `attempts` times with backoff before splitting; single-doc failures record only after exhaustion; injectable and spec'd without real timers.
- [ ] Runner receipt: `failed` per-reason array with capped `sampleIds`; full per-row dump removed; reconciliation sums `failed[].count`.
- [ ] Done-line prints `failed=N (X resumable, Y terminal)`.
- [ ] Extractor, heal, and runner specs green (additive-safety witnessed by unchanged consumer specs).
- [ ] Post-merge-only: the resume sweep after the active `#16208` run exercises the new receipt on real data; reconciliation receipt lands on `#16208`.

## Out of Scope

- A shared `ai/`-wide retry primitive (consolidation is the `#16224`-family decision).
- MC service canary/gate semantics (shipped for `#16222` via its own PR).
- Renaming existing reason codes or the extractor's `unrecoverable`/`unrecoverableIds` return fields (consumer compatibility).

## Avoided Traps

- **Two named top-level fate fields** (`contentUnrecoverable`/`failedThisPass`): rejected during convergence — every new fate would be a schema change; the receipt array keeps schema stable and reconciliation a single sum, with the binary verdict as a log-line projection.
- **Retry only at the single-doc level:** splitting a transient whole-batch failure multiplies calls against an already-saturated provider; retrying the intact slice first is strictly cheaper.
