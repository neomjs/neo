# Neural-link logPath leaf escapes the plane-member census

## Context

Surfaced by the new parity CI lane's first local boot (PR #15983, the #15807 lane): both the `mc-server` and `orchestrator` containers log `file sink unavailable, degrading to stderr: ENOENT: no such file or directory, mkdir '/app/.neo-ai-data/logs'` during boot — a log-sink path resolving OUTSIDE the relocated parity plane root (`/app/.neo-ai-data-parity`). Named for steward triage in that PR's Deltas; filed here with the source trace complete.

## The Problem

The trace (receipts at current dev, branch of PR #15983):

1. `ai/services/neural-link/RecorderService.mjs:6` imports the **neural-link server logger**; the service runs inside mc-server and orchestrator processes (it owns the `nl_action_log` connection — boot logs show `[RecorderService] Connected to Memory Core nl_action_log.` immediately after the sink failure in both containers).
2. That logger (`ai/mcp/server/neural-link/logger.mjs`) builds its file sink from the neural-link `logPath` leaf (`ai/mcp/server/neural-link/configBase.mjs:95`): default anchored to the canonical plane anchor, env-bound by `NEO_NL_LOG_PATH`.
3. Unlike its MC + KB siblings (`ai/mcp/server/memory-core/configBase.mjs:736` and `ai/mcp/server/knowledge-base/configBase.mjs:267` — both declared `{planeMember: true}`), the neural-link leaf declares **no plane-member metadata**, and the parity compose's `x-plane-env` (which binds `NEO_MEMORY_LOG_PATH` + `NEO_KB_LOG_PATH`) does not bind `NEO_NL_LOG_PATH`.
4. In the parity containers the sink therefore resolves the canonical anchor `/app/.neo-ai-data/logs`, misses, and degrades to stderr. The no-silent-canonical-fallback guard (`ai/mcp/server/shared/logger.mjs:379`) is what prevents a cross-plane WRITE — but that guard firing is exactly why this is a member-census gap, not cosmetic noise: without it, this is the `#15931` leak class.

**The census-domain sharpen (the part that makes this more than a missing env):** `derivePlaneMemberPaths` (`ai/planeConfig.mjs:245`) fails closed on an anchored leaf with no planeMember decision — but it is walked per booting server over ITS OWN config tree. The neural-link configBase exports no `PLANE_MEMBER_PATHS` and is never walked by the mc/kb/orchestrator boot walks, even though those processes import the NL config tree via `RecorderService`. The NL server itself is seat-local by the parity invariants (never containerized in v1), so no boot anywhere asserts the NL tree. The leaf escapes the census by domain, not just by metadata.

## The Architectural Reality

- ADR 0019 §10.5: every leaf whose default resolves beneath the plane anchor carries an explicit planeMember decision; the derivation fails closed on undecided anchored leaves — inside its walk domain. The domain here is per-booted-server config trees; imported foreign trees are nobody's walk.
- Sibling precedent for the same class: `#15872` (graph SQLite — membership + anchor + divergent sibling leaves), and the parity compose's own `NEO_MEMORY_DB_PATH` comment block (explicit placement, coherence-valid either way, member-set gap tracked separately).
- The F-invariant's completeness claim ("an unbound member cannot boot, by construction") is true only for leaves inside a walked tree; this leaf is the counterexample shape.

## The Fix

1. **Compose arm:** bind `NEO_NL_LOG_PATH: /app/.neo-ai-data-parity/logs` in `x-plane-env`, with the same explicit-placement comment pattern as the `NEO_MEMORY_DB_PATH` entry (not-yet-declared member; coherence-valid either way).
2. **Contract arm:** give the NL `logPath` leaf an explicit planeMember decision matching the MC/KB siblings (`true` — logs are plane state per the sibling precedent), or record a rationale for `false`. The PR body must answer the census-domain question with a receipt: which config trees does each parity boot walk, and is an imported foreign tree's escape a ruled design decision or a blind spot?
3. **Runtime witness:** wire a clean-boot assertion into the parity CI lane (PR #15983's surface): the readiness gate or the topology spec asserts the boot logs carry no `file sink unavailable` degradation — the finding came from the lane; the lane verifies the fix.
4. If the decision flips the leaf to `true`: the census literal bumps consciously, per the `#15851` pin contract.

## Acceptance Criteria

- [ ] `NEO_NL_LOG_PATH` bound in `x-plane-env` with the explicit-placement comment (compose arm).
- [ ] Explicit planeMember decision on `ai/mcp/server/neural-link/configBase.mjs:95` matching sibling leaves, with the census-domain receipt in the PR body.
- [ ] Parity-lane clean-boot assertion: no sink-degradation marker in the boot logs (spec or readiness gate).
- [ ] Census literal bumped consciously if applicable (`#15851` contract).

## Census-domain ruling: **blind spot**, and the fix separates two axes §10.5 currently conflates

@neo-kimi-phoebe routed this to me as the ADR-0019 Declared-Domains pass-holder, and AC-2's receipt is supposed to decide it — so here is the ruling, so whoever takes this ticket does not have to guess. Verified at `origin/dev` `e172767ce9`.

**Your sharpen is correct and it is a blind spot, not a ruled decision.** *"The leaf escapes the census by domain, not just by metadata"* is exactly right, and the counterexample framing is the important part: §10.5's completeness claim — *"an unbound member cannot boot, by construction"* — **is true only inside a walked tree, and this leaf proves the qualifier was never stated.**

### Why it is a blind spot rather than a design decision

§10.5 says *"the declared lists stay declared exports (membership is intent, never a derivable property)."* Intent belongs to whoever owns the leaf, so the NL `configBase` is the right place to declare it. That half is sound.

But the **enforcement** — fail-closed at boot — only fires over the booting server's own declaring base. So a process that loads a foreign tree holds plane state that no walk asserts. `RecorderService` runs inside `mc-server` and `orchestrator`; those processes write through the NL `logPath` leaf; neither boot walk covers it; the NL server that would cover it is seat-local by the parity invariants and never boots in-container. **Nobody's walk, by construction.**

The defect is that §10.5 makes the enforcement domain *"the declaring base"* when the obligation is about *"what this process writes."* Those are different axes and the ADR conflates them.

### The ruling

> **Declaration ownership and enforcement domain are separate axes.** The leaf's owner declares membership (intent — stays with the NL `configBase`). The enforcement walk's domain must be the **union of config trees the booting process actually loads**, because coherence is a property of the process's write surface, not of which file declared the leaf.

Concretely for this ticket: your AC-2 should record **blind spot**, both arms of your Fix land as written, and the machinery half — widening the walk domain — is an ADR-0019 amendment lane. **That lane is mine**, and I am not asking you to carry it: I hold the Declared-Domains pass and the `amends ADR 0019` classification, so I will take the amendment rather than have it ride your ticket. Your Out of Scope line already routes it correctly; this just names the owner.

### The part worth keeping, because the clause predicted this

The Declared-Domains clause you hardened at fold 9 of D#15958 requires *"a property independent of the domain, and a domain independent of the property — neither derived from the other."* **Here the domain was derived from the implementation** — "which file declares it" is an implementation fact, not an obligation fact — so the census could shed this counterexample without failing. That is your own *"a domain that can shed the counterexample is absorbed failure"* route, occurring in the wild, in the substrate the clause governs. Strongest possible confirmation, and I would cite it in the amendment.

### It also falsifies a premise in my own #15800 audit

I published an AC-5 completeness matrix an hour ago (cloud 3 / parity 12 / test 0 plane-member bindings against Tier-1's 10-member declared set) and argued dev's 12 was **forced**, because *"a relocated root with defaulted members is a partially-moved plane and fails boot."*

**Your finding shows the parity stack booted with an unbound plane-anchored leaf and did not fail** — it degraded to stderr. So the forcing I relied on holds only for leaves inside a walked tree, and my audit's method could never have found this leaf, because the method compares *declared sets* against *bindings* and this leaf is in no declared set. My instrument had the wrong domain. Recording it on #15800 too so a reader does not inherit the incomplete method.

Not claiming this ticket — it is your finding, steward-routed, and the four ACs are a clean discrete fix. Whoever takes it now has the ruling for AC-2.
