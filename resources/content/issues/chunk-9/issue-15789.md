# SortZone spec leaks a global Neo.applyDeltas override across spec files

## Context

Discovered by the #15783 workers:4 measurement (PR #15784, run 30081818399 attempt 1): `unit/selection/GalleryInternalId.spec.mjs:88` flaked, and its retry trace shows a foreign fixture executing inside it —

```
at Object.applyDeltas (test/playwright/unit/draggable/dashboard/SortZone.spec.mjs:281:27)
at Gallery.onSelectionChange (src/component/Gallery.mjs:642:13)
at test/playwright/unit/selection/GalleryInternalId.spec.mjs:106:23
```

`SortZone.spec.mjs` assigns `Neo.applyDeltas = (windowId, deltas) => {…}` (line ~280) capturing its local `appliedDeltas` array, and never restores the original. Playwright reuses a worker process across spec files, so any later spec in the same worker that triggers `Neo.applyDeltas` executes SortZone's override against SortZone's dead fixture state.

## The Problem

This is a correctness defect independent of the workers decision: the bleed exists under `workers: 1` too — it is merely masked by the stable single-worker file ordering. Any reordering (new specs, sharding, parallelism, `--grep` runs) can re-pair the leak with a victim. Under `workers: 4` it surfaced immediately as a retry-healed flake.

## The Architectural Reality

- `test/playwright/unit/draggable/dashboard/SortZone.spec.mjs:280-284` — the unrestored global override (module/worker-scoped mutation of the `Neo` namespace).
- Victim class: any spec sharing the worker afterwards whose components call `Neo.applyDeltas` (e.g. `unit/selection/GalleryInternalId.spec.mjs`).
- House rule elsewhere in the suite is fixture-scoped seams (injected `fsModule`, injected services) — a global namespace patch without `finally`-restore is the anti-pattern.

## The Fix

In `SortZone.spec.mjs`: capture the original `Neo.applyDeltas` before override and restore it in `test.afterEach`/`afterAll` (or wrap per-test with try/finally). Sweep the unit tree for the same pattern while there: `grep -rn "Neo\.applyDeltas\s*=" test/playwright/unit/` plus any other `Neo.<fn> =` assignments without a paired restore.

## Acceptance Criteria

- [ ] `SortZone.spec.mjs` restores the original `Neo.applyDeltas` after each test (or its describe block).
- [ ] A sweep of `test/playwright/unit/**` for unrestored `Neo.*` global assignments is recorded on this ticket (fix-in-place any further instances found).
- [ ] `GalleryInternalId.spec.mjs` no longer shows the foreign stack under a reordered/parallel run (verifiable locally with `--workers=4`).

### The gradient

**Confirmed harmful — 1 file.** `draggable/dashboard/SortZone.spec.mjs` overrides `Neo.applyDeltas` with closures **capturing local fixture state** (`appliedDeltas`). A leaked override does not merely no-op a victim — it runs *this file's fixture against the victim's components*. That is the foreign frame in your `GalleryInternalId` trace.

**False-green risk — 10 files.** `component/WrapperLifecycle`, `draggable/container/SortZone`, `functional/Button`, `vdom/AsymmetricMerging`, `vdom/HiddenChildren`, `vdom/ParentIdChange`, `vdom/RaceCondition`, `vdom/SparseUpdates`, `vdom/UpdateWedge`, `vdom/VdomLifecycle` install **stateless** overrides (`async () => {}` / `() => Promise.resolve()`). Leaked, they do not crash a victim — they make a later spec's deltas **silently not apply**, so VDOM assertions can pass against work that never happened. Quieter, and arguably the worse failure mode.

**Verified, not inferred:** each of these files *has* a `test.afterEach`; those blocks destroy components and **none restores `Neo.applyDeltas`**. So this is not an oversight in one file — the suite has no convention for restoring a global `Neo.*` patch.

Also surfaced, **not** touched here (different properties, different blast radii, several already restore correctly): `Neo.get`, `Neo.apps`, `Neo.worker`, `Neo.currentWorker`, `Neo.ai`, `Neo.insideWorker`, `Neo.Main`, `Neo.Xhr`, `Neo.windowConfigs`. Two hours ago I closed my corrected sweep by proposing a lint — *no `Neo.*` assignment in a spec without a paired restore* — and wrote that the classifier above "is most of the implementation." @neo-opus-grace measured a structurally identical proposal of her own this morning and it came back **1 true positive, 5 false**. **False-positive rate: 12/33 = 36%.**

### The restores it is blind to

The classifier's rule is *"a restore is an assignment whose RHS is a bare captured identifier."* Every one of these is a correct restore that is not an assignment of that shape:

```js
Object.assign(Neo.Main, previous);        // fleetCockpitPopOut:63, TearOut:52, dashboard/Container:50
delete Neo.main;                          // CircleAsync:26 — restores to ABSENT, the true prior state
if (hadDragDrop) { Neo.main.addon.DragDrop = original }
else             { delete Neo.main.addon.DragDrop }   // DockTabSortZone:547
```

That last one is **more careful than the fix I shipped in this PR**. It restores a pre-existing value *or* removes the key it created, which is the correct behavior for a namespace that may not have existed. My lint would have flagged it as a violation.

### Why this is a refutation and not a tuning problem

`Object.assign(Neo.Main, previous)` is **the codebase's own idiom for restoring a multi-key namespace patch.** It is what you write when you patch six `Neo.Main.*` methods and want them all back — exactly the case the lint exists to protect. So the instrument is blind to the correct pattern, and by symmetry it is blind to `Object.assign`-shaped *patches* too: those produce **invisible false negatives**, the failure mode nobody reports because nothing appears.

This is precisely the defect class this PR spent all day on, one level up — **an instrument that reports a confident number when it cannot see.** I extended the rule to count `Object.assign` and `delete` (that is where the 21 comes from), but that is patching known holes in a grep, not closing the class. The next idiom — a restore helper, a `for…of` over a saved map, a `Proxy` — is invisible again. Real detection needs dataflow, not pattern-matching. Grace reached the identical verdict from the mechanism side; two independent measurements of two different grep-lints, both refuted by the same structural fact.
