# Deployment config defaults absorb the env-override surface: policy becomes AiConfig, env keeps only secrets and choices

**Blocked until local/cloud runtime parity ([#15798](https://github.com/neomjs/neo/issues/15798)) completes.** Filed now so the decision is captured while the evidence is fresh; the work must not start before parity lands, because parity is what makes the correct defaults knowable.

## The problem

Every deployment-touching PR currently grows the environment-variable surface instead of moving a default. The surface is now the dominant cost of standing Neo up.

Measured against a live external-tenant deployment (sanitized `docker inspect` across its three services): **33 of 45 `NEO_*` keys the deployment sets are already declared config leaves with defaults.** The pipeline sets them anyway. Of the 12 that are not leaves, only 2 belong in the environment at all:

| group | keys | disposition |
|---|---|---|
| auto-* toggles | `NEO_AUTO_SYNC`, `NEO_AUTO_DREAM`, `NEO_AUTO_GOLDEN_PATH`, `NEO_AUTO_INGEST_FS`, `NEO_AUTO_SUMMARIZE`, `NEO_KB_AUTO_START_DATABASE`, `NEO_MEM_AUTO_START_DATABASE`, `NEO_MEM_AUTO_START_INFERENCE` | 8 — should become leaves |
| behavior flags | `NEO_MC_PRIMARY`, `NEO_REAL_TIME_MEMORY_PARSING` | 2 — should become leaves |
| secrets | `NEO_MCP_HEALTHCHECK_TOKEN`, provider PAT | 2 — **correctly** env-side, keep |

## The ratchet, caught live

[PR #16038](https://github.com/neomjs/neo/pull/16038) is well-built work that still adds six `NEO_AUTH_*` overrides to the canonical parity profile:

```yaml
NEO_AUTH_MODE: github-pat
NEO_AUTH_TRUST_PROXY_IDENTITY: "false"
NEO_AUTH_PIN_FIRST_PROVIDER_SUBJECT: "true"
NEO_AUTH_AUTO_PROVISION_IDENTITY_SOURCES: github-pat
NEO_AUTH_PROVIDER_BOOTSTRAP_PAT_FILE: /run/secrets/mcp-auth-token
NEO_MCP_HEALTHCHECK_TOKEN_FILE: *provider-bootstrap-pat-file
```

Exactly one is a genuine deployment decision — where the secret file lives. `TRUST_PROXY_IDENTITY: false` and `PIN_FIRST_PROVIDER_SUBJECT: true` are **security posture that should be the default**; `AUTO_PROVISION_IDENTITY_SOURCES` is derivable from the auth mode. Nothing is wrong with that PR — the ratchet is structural, and no individual PR is where it should be stopped.

## Why this blocks on parity

Today local and deployed run differently, so no one can know which value is *the* default versus a local accommodation. Once the same topology runs both places, the default is observable rather than argued. Doing this first would encode today's divergence as tomorrow's defaults.

## Target posture

A deployment supplies: **tenant repos · GitLab or GitHub · chat + embedding model (only if changing) · secrets.** Everything else is a default, overridable but not required.

## Acceptance Criteria

- [ ] Every non-secret key in the census above is either a config leaf with a defensible default, or has a recorded reason it must stay deployment-supplied.
- [ ] Security-posture leaves default to the safe value (`trustProxyIdentity` false, `pinFirstProviderSubject` true) so a deployment opts *out*, never in.
- [ ] Values derivable from another leaf are derived, not restated — `autoProvisionIdentitySources` from auth mode is the worked example.
- [ ] A mechanical check fails when a compose profile sets a key whose declared default already matches the set value — the ratchet cannot silently resume. Extends the existing `ai/scripts/lint/config-leaf-parity.json` surface rather than adding a lane.
- [ ] The census re-run against the same external-tenant inspect shows the required-key count reduced to secrets + tenant/provider choices.
- [ ] ADR-0019 records the boundary rule: **policy and posture are config; secrets and per-deployment identity are environment.**

## Evidence

Census method is re-runnable: each key greps against `ai/configBase.mjs`, `ai/mcp/server/memory-core/configBase.mjs`, `ai/mcp/server/knowledge-base/configBase.mjs` for a leaf declaration. Baseline recorded on [#15798](https://github.com/neomjs/neo/issues/15798#issuecomment-5085967828).

## Empirical addition: an `environment:`-sourced compose secret is a precondition of `up`, not of the consumer

Measured on a live parity stack at `62e5669c0f`, and it sharpens this ticket's argument beyond "too many env vars."

### What I ran

Brought up `kb-server` in the parity project under a throwaway override that swaps the canonical `github-pat` auth for trusted-proxy-header identity — a mode that reads **no** credential — with both PAT-file leaves blanked. No credential set anywhere.

### What happened

```
environment variable "NEO_MCP_HEALTHCHECK_TOKEN" required by
secret "neo-local-parity_mcp-auth-token" is not set
```

Compose refused at **secret materialization**, before the service started, in a configuration where nothing would ever have read the value.

### Why this matters more than the count

Earlier I framed this ticket around volume — 33 of 45 keys already carry defaults. That is true and still the headline. This is a different and harder property:

**An `environment:`-sourced secret is a precondition of `docker compose up` itself, not of the service that consumes it.** Consequences, all verified by the above rather than reasoned:

1. **No service in the project can start without it** — not the ones that use it, not the ones that don't. `chroma` came up fine alone earlier precisely because it carries no `secrets:` reference; the moment `kb-server` enters the up-set, the whole invocation is gated.
2. **Every future `up` is interactive.** Not just first boot — every restart, every `up -d <one-service>`, every recreate after an edit, every CI invocation. The credential must be present in the *invoking shell* each time.
3. **Auth mode is irrelevant to the gate.** A deployment that authenticates by proxy header still cannot start without a provider PAT in its environment. The requirement is structural, not functional.

### The repair, and why it is not merely cosmetic

Compose supports a `file:` secret source. `AuthService` **already** reads the credential from a file (`readFileSync(auth.providerBootstrapPatFile)`), so the container-side contract at `/run/secrets/mcp-auth-token` is unchanged — this is a source swap with **no application change**.

With `file:`, the credential is provisioned **once, on disk**, by whatever mechanism the deployment already trusts — Ansible, a k8s Secret, SOPS, `/run/secrets`. Restarts and CI stop needing a human in the loop. Precedent exists in-tree: `TenantRepoSyncService` resolves typed `credentialRef`s including a `file:` scheme.

The distinction worth carrying into this ticket's AC set: **secrets belong in the environment as *values*, but not as *startup preconditions*.** The two current secret slots — `NEO_MCP_HEALTHCHECK_TOKEN` and the `NEO_MCP_REMOTE_TOKEN` landing via #15805 — should both be decided once, together, rather than each inheriting the env-source default.

### Scope note

This does **not** change my recommendation that the 2 secrets stay env-side rather than becoming config leaves — that part of the census stands. The question here is *how a secret reaches the container*, not *whether it is config*. A secret sourced from a file is still a secret; it is simply one a pipeline can deliver.
