## Root cause: #15744's permission tightening met a stage declared `credential=none` that needs a credential — and `GraphqlService` has no env-token path at all

The alarm says root-cause work is tracked elsewhere; there was no elsewhere, so here is the diagnosis. **Claiming the fix.** Traced to the proving line rather than log substrings.

### Timeline — clean regression

| event | time |
|---|---|
| last pipeline success | **2026-07-26T00:17:01Z** |
| `b901103ae5` — #15744 two least-privilege identities | **2026-07-26T01:55:33Z** |
| 4 consecutive failures since | through 12:08Z |

The regression window contains exactly one pipeline commit.

### The proving line

Failing step `Run bounded Data Sync emission and publish`, run `30201476105`:

```
[DataSync] emit attempt=1 stage=content indexes and SEO credential=none
[ERROR] Failed to get GitHub auth token from `gh` CLI. Error: Command failed: gh auth token
no oauth token found for github.com
Error generating label index: Could not authenticate with GitHub. Please ensure you have run `gh auth login`.
  at #getAuthToken (ai/services/github-workflow/GraphqlService.mjs:114)
  at LabelService.listLabels (…/LabelService.mjs:58)
  at createLabelIndex (buildScripts/docs/index/labels.mjs:59)
  at rebuildContentIndexesAndSeo (…:67)
```

### It is doubly determined, which is why an env line will not fix it

**1. The stage is *declared* credential-free.** `dataSyncPipeline.mjs`'s `scopedStageEnv(tokenScope)` (~`:107-119`) **strips** `GH_TOKEN`, `GITHUB_TOKEN`, `DATA_SYNC_INTAKE_TOKEN`, `DATA_SYNC_PUBLISHER_TOKEN` from the child env, then re-adds `GH_TOKEN`/`GITHUB_TOKEN` only for `intake` or `publisher` scope. `credential=none` at `:432` is a **deliberate scope value** — so the stage strips tokens by design, while invoking `rebuildContentIndexesAndSeo.mjs --include-labels`, which reads this repo's labels over GraphQL. **The declared scope contradicts the stage's actual requirement.**

**2. `GraphqlService` cannot consume an env token even when one is present.** `#getAuthToken` (`:99-116`) resolves in exactly three steps: `authTokenOverride` → cached `#authToken` → `execAsync('gh auth token')`. **There is no `GH_TOKEN`/`GITHUB_TOKEN` env path.** So every CI consumer of this service silently depends on an authenticated `gh` CLI on the runner, and the failure surfaces as advice to run `gh auth login` — on a GitHub Actions runner.

Worth naming against #15744's own title: it shipped *"a preflight that names the failure,"* and this failure was **not named** — it arrived as a `gh` CLI error four scheduled runs in a row. The permission work was right; `contents: write` genuinely should have gone. What went unnoticed is that the comment at `.github/workflows/data-sync-pipeline.yml:31-33` reasons the implicit token stays *"reachable"* even when unpassed — true for an **action**, false for a `node` **run step**, which sees only what `env:` gives it.

### Fix shape

Root-cause, not symptom, and no operator action required — no new secret, no App-permission widening:

1. **`GraphqlService#getAuthToken` reads `GH_TOKEN` then `GITHUB_TOKEN` from env before the `gh` fallback.** Standard order, matches what the DevIndex service already prefers (`dataSyncPipeline.mjs:79` documents that preference), and makes the "run `gh auth login`" error structurally impossible in CI. Fixes the whole class, not this one caller.
2. **Give the label-index work a truthful credential scope** — either move it into a credentialed stage, or grant the stage a narrow read scope. `permissions: issues: read` on the implicit token is sufficient for labels and preserves #15744's win, since it does not restore `contents: write`.
3. **A named failure when a stage's declared scope cannot satisfy its requirement** — the preflight #15744 promised, applied to the credential axis, so scope/requirement drift fails loudly instead of four silent scheduled runs.

Filing one narrow bug ticket for this and shipping the fix — justified against the live regression per the current direction, and it is one ticket to one PR, not backlog.

**Adjacent, not absorbed:** #15977 (generator scheduled / publisher unowned) is a different defect, and #15963/PR #15964 lands the ISSUE facet's *data*. Neither fixes why the pipeline exits 1. The 223h facet staleness is downstream of this failure.

* test(ai): prove the cache-dependent credential branches in an isolated child (#15986)

Cycle-3. The cached and CLI-success branches were uncovered, and cycle-2 claimed
they needed a production cache-reset seam. That was wrong: a child process cannot
leak cache state, so the seam is process isolation, lifted from the repository's

One child proves all three orderings because the `gh` stub emits a different token
per invocation: call 1 resolves through the CLI and caches, call 2 returns the same

case is the one the in-worker suite structurally cannot reach, since every case there
starts from an empty cache and so cannot distinguish env-over-cache from
env-when-empty.

## Why "Breach continues: 0 consecutive failures" reads as incoherent — and why the breach is real

The operator flagged the contradiction. It is not a false alarm; the breach is real and the number beside it is irrelevant to it. Two separate defects, both in the reporting rather than the detection.

### 1. The continuation message reports a counter that is not the breach reason

`evaluateBreach` collects the actual reasons (`buildScripts/dataSyncWatchdog.mjs:136-160`) and breaches on **either** `consecutiveFailures >= 3` **or** a `resources/content/**` commit older than `WATCHDOG_MAX_CORPUS_AGE_HOURS` (48). This episode is the second condition — 255.5h against a 48h threshold.

But the continuation comment is hardcoded to the first condition:

```js
// dataSyncWatchdog.mjs:383
return `Breach continues: ${consecutiveFailures} consecutive failures`
```

So a corpus-age breach announces itself with a failure streak of 0. `reasons` is already computed and carries the truthful text; the continuation just does not use it.

### 2. The failure counter watches a producer that cannot cause this breach

`DEFAULT_WORKFLOW = 'data-sync-pipeline.yml'` (line 53). That workflow's staged set is `GENERATED_DATA_PATHS` — devindex data, portal data, `sitemap.xml`, `llms.txt`. **It never writes `resources/content/**`.** Its most recent delivery, `0d59da39f9` at 2026-07-27 21:25 UTC, changed exactly one file: `apps/portal/sitemap.xml`, 5 lines.

The corpus is written by a different producer entirely: the orchestrator's `githubWorkflowSync` lane (`ai/daemons/orchestrator/taskDefinitions.mjs:427`, default 2h, `localOnly` so it is enabled on local deployments and correctly disabled on cloud). **That producer is not monitored here at all.**

So `consecutiveFailures` is structurally incapable of ever explaining a corpus-staleness breach: the workflow it counts is healthy every hour, by design, no matter how stale the corpus gets. The alarm's two halves have different subjects.

### The breach itself, measured

Last commit that actually delivered the content corpus:

```
b1028184e9  2026-07-17 05:13:29 UTC  Ada  chore: ticket sync [skip ci]
```

`#15319` merged at **2026-07-17T05:57:38Z** — **44 minutes later**, and nothing has delivered the corpus since.

That PR added `PullRequestSource`'s fail-closed embed refusal *and* stage 7-d's terminal integrity verdict, while leaving 27 divergent duplicate artifacts in place. The verdict throws while the corpus is unclean and the aggregate verdict fails the run before the generated-content commit — so the corpus could not be committed until it was clean, and could not become clean on `dev` until it was committed. A deadlock by construction, and the 255.5h is exactly its age.

Confirmed by comparing clones: the canonical checkout's working tree held **0** duplicates while committed `dev` held **27**, alongside 488 uncommitted files under `resources/content`. The repair had been succeeding every couple of hours and failing to deliver, for ten days.

PR #16067 breaks the deadlock by committing the repaired corpus directly, which is what restores tenant KB ingestion. It does not fix the publisher; that is #15977 (*"The corpus generator is scheduled; the publisher has no owner"*), with #16002 and #15993 alongside.

### Suggested narrow fixes here

Both are small and independent of the publisher work:

- Compose the continuation comment from `reasons` instead of `consecutiveFailures`, so a corpus-age breach says so. One line.
- Either monitor the lane that writes the corpus, or omit the failure counter when the breach reason is corpus age — a counter that cannot move for the breach in question is worse than absent, because a reader spends their attention reconciling it.

Filing no ticket for this: it belongs to whoever owns this alarm, and the operator has this deprioritised behind deployment stability. Recorded so the next reader does not re-derive it.
