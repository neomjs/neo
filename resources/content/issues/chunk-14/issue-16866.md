# Nothing measures how much embedding work is spent re-embedding the same content

## Context

`#16780` observed a plane holding ~4 cores of continuous inference against an empty Knowledge Base. Its AC-3 names the discriminator: *"re-embed ratio over a bounded window ... a fixture with deliberately repeated content moves it above 1 while a clean run holds it at 1."*

Provider load alone cannot separate a converging ingestion from a loop — both are sustained inference. The attribution ledger (`provider_activity_log`) answers *which stage* is calling and has **no content-identity column**, deliberately: every current consumer asks volume questions. So this is a new dimension, not the plumbing change AC-7 turned out to be.

Live latest-open sweep at 2026-08-10T08:33:41Z plus an A2A claim sweep over the herd window; no equivalent found. Design posted on `#16780` (comment `5238196149`) with three options and the reason for choosing the narrow one.

## The Problem

`submissions ÷ distinct` is the whole instrument, and two failure modes make a naive version worse than nothing:

**A ratio above 1 is NOT a defect.** Real corpora duplicate content honestly — two guides quoting one snippet embed the same text twice, correctly. An alarm keyed on `ratio > 1` fires on healthy ingestion and is switched off within a week, leaving neither an alarm nor the option of one. `#16780` AC-6 says this in those words.

**An unobserved window is not a clean one.** A fresh process, or a window whose oldest entries were evicted, has "no repeats to report" — and reporting that as a ratio of 1 tells an operator "no repetition" for a process that has not looked. That is the same false zero `#16835` had to fix one layer down, and the fix there is the precedent: report `coverageStartedAt` and `truncated` rather than a confident number.

## The Architectural Reality

`ai/services/shared/embeddingIdentityWindow.mjs` (new) — sibling of `providerActivityLedger.mjs`, which is the volume half of the same question. Pure and clock-injectable, matching `ai/daemons/shared/drainDisposition.mjs`'s bounded-window discipline.

Recorded at `TextEmbeddingService.embedTexts` — the one point every embedding submission passes through regardless of provider or caller. Per-caller recording answers *"does this sweep repeat itself"*, which is the wrong question: a plane whose KB sync and WAL drain each converge can still re-embed the same content between them.

**The recorder cannot import `TextEmbeddingService`** — `TextEmbeddingService` already imports `MemoryCoreRecorderService`, so the metrics surface needs the same provider-injection the walDrain projection uses. That hop is deliberately **not** in this ticket; see Out of Scope.

## The Fix

- A bounded window of submission fingerprints (truncated sha1 — the window must never become a second copy of the corpus).
- `ratio` = `submissions / distinct`, `null` when nothing was observed.
- `coverageStartedAt` + `truncated` so a partial answer cannot present as a total.
- Recorded on **submission**, not success: a sweep that re-submits and fails every time is exactly the non-convergence this surfaces, and counting completions would hide the loop behind its own failures.
- Plus `#16780` AC-1's control: zero chunks issues zero provider submissions, asserted at the provider boundary.

## Acceptance Criteria

- [x] A clean run holds the ratio at exactly 1. — *"a clean run holds the ratio at exactly 1"*.
- [x] Deliberately repeated content moves it above 1. — *"repeated content moves the ratio ABOVE 1"*: two sweeps over the identical set give 4 submissions / 2 distinct.
- [x] **The ratio reaches no verdict of its own** (`#16780` AC-6's negative control). — *"a ratio above 1 is NOT by itself a defect"*: a 500-document ingest with one honestly-duplicated snippet lands just above 1, and the test pins the reported key set so the module cannot start adjudicating.
- [x] An unobserved window reports `null`, never the value of a clean run. — *"an UNOBSERVED window reports null"*.
- [x] Eviction is reported so a bounded window cannot claim a total. — *"eviction is reported"*, **plus** a never-evicted control, without which "always truncated" satisfies it.
- [x] Identity is content, not position or object. — two sweeps over one corpus must not read as distinct work.
- [x] **The ratio is readable from the metrics observer.** *(Was scoped out; now delivered — see below.)* — `getMemoryCoreToolMetrics().reembedRatio`, injected from `TextEmbeddingService` the same way the WAL drain projection is. Fails closed: a process that does not host the window reports `unavailable`, never a ratio of 1. Every status arm carries the field, and the declared key set is **extended, not loosened**.

  > **Scope corrected.** This was deliberately excluded and named in Out of Scope, on the reasoning that a leaf's every criterion should be met. That reasoning was right in general and wrong here: under a two-reviewer queue, one complete PR beats two partial ones, and the honest objection — *why merge an instrument nobody can read?* — is one a reviewer would rightly raise. The cycle that motivated the exclusion is real and is why the provider is **injected rather than imported**.

- [x] **`#16780` AC-1:** zero chunks issues zero provider submissions, asserted at the **provider boundary** rather than the return value — a function can report `embedded: 0` while still having called out, and it is the call that burns the core.

## Out of Scope

> **The metrics-surface hop WAS scoped out here and has since been delivered** — see the last
> acceptance criterion. The principle that led to excluding it still holds: an unmet criterion on a
> close-target means the merge closes over it. What changed is that the hop was buildable in the
> same cycle, so `#16780` AC-3 is now fully delivered rather than partial.

**The metrics-surface hop.** `TextEmbeddingService` exposes `getEmbeddingIdentityWindow()`, and that is *not* the same as `#16780` AC-3's *"exposed on the existing observer"*. `MemoryCoreRecorderService` cannot import `TextEmbeddingService` (the dependency already runs the other way), so the surface needs the same provider-injection the walDrain projection uses, plus its OpenAPI schema and the response-key pin.

Stated as an open criterion rather than quietly claimed: an instrument an operator cannot read is not an instrument — the lesson `@neo-gpt-emmy` taught on `#16854` this morning, and I would rather carry it as an unticked box than have it found in review. `#16780` AC-3 therefore remains **partial** and is not ticked on the parent.

## Avoided Traps

- **Alarming on the ratio.** The module reports and never adjudicates; the negative control pins that by asserting the key set.
- **Returning 1 for an empty window.** Would make "has not looked" indistinguishable from "converged".
- **Storing the text.** The window would become a second copy of the corpus. Fingerprint collisions understate repetition, which is the safe direction for an instrument whose failure mode is being switched off after a false alarm.
- **A content column on `provider_activity_log`.** Considered and rejected as over-build: it forces an identity concept onto roles that have none (a chat call has no "content identity" in this sense) for a question that is specifically about embedding.
