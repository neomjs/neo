# A zero-row export cannot say whether the corpus was empty or gone

## Context

Narrow leaf carved out of `#16348` (@neo-opus-grace), whose selection half already shipped as `#16384` / PR `#16385`. `#16348` stays open for the two acceptance criteria neither leaf delivers — see **Out of Scope**.

The mechanism below was **read out of source, not inferred from the specimens**. My first shape on `#16348` named `backup.mjs:227`'s `?? 0` as the conflation; reading the producer falsified that and two other assertions, and the correction is on the ticket ([the correction](https://github.com/neomjs/neo/issues/16348#issuecomment-5159420838), [the corrected shape](https://github.com/neomjs/neo/issues/16348#issuecomment-5159954428)). This leaf carries the corrected version.

Live latest-open sweep: checked the latest 20 open issues at `2026-08-02T20:15:51Z`; no equivalent found. A2A in-flight claim sweep at the same minute (30 messages, all read-states): no overlapping `[lane-claim]`.

## The Problem

**A backup's row count answers "how many rows did I write". It has never answered "was there a corpus here" — and the two questions have the same answer shape: `0`.**

Measured on the live corpus: **4 of 36 bundles** in `.neo-ai-data/backups` carry `mc.count == 0 && kb.count == 0` with the message `"Export complete."` — on **four separate dates** (Jul 10, 14, 18, 19), with healthy bundles in between. The condition is recurrent, not a single cutover artifact. A fifth, older shape exists too: a May-2026 recovery set with memories and **no summaries file at all**, i.e. one subsystem captured and another absent inside the same bundle.

The receipt cannot say which happened, so a dependency outage and a legitimately empty deployment are byte-identical:

```json
"mc": { "message": "Export complete. Exported 0 memories, 0 summaries, 0 temporal summaries",
        "count": 0, "memories": { "expected": 0, "exported": 0 } }
```

**The behavioural tell is stronger than the content evidence.** During the May-2026 Memory Core wipe recovery, an experienced peer bypassed the receipts entirely and counted JSONL lines by hand across five backup sets. That is what a receipt nobody trusts looks like from the outside.

## The Architectural Reality

**The truth is destroyed before `backup.mjs` runs.** The vector-store resolvers convert *absent* into *empty*:

| subsystem | site | spelling |
|---|---|---|
| KB | `ai/services/knowledge-base/ChromaManager.mjs:154-184` | `getCollection` → catch not-found → `createCollection` |
| MC | `ai/services/memory-core/managers/ChromaManager.mjs:238,257,276,295` | `getOrCreateCollection` ×4 — create-on-missing **by construction**, no not-found branch at all |

A deleted or missing collection is silently recreated **empty**; `#exportCollection` then reads `collection.count() === 0` and reports it honestly. Every layer above is telling the truth about a store that was replaced by an empty one during the very read meant to capture it. A grep for `createCollection` alone finds the KB half and misses all four MC sites.

**The same defect exists in a second store, in a different spelling.** `ai/services/memory-core/DatabaseService.mjs#exportGraph` returns a bare `0` when the SQLite graph database is not initialized **and** when the table count query throws — both indistinguishable from a genuinely empty graph, and `graph` is one of the three subsystems `verifyBundleIntegrity` checks.

What already works and must not be rebuilt: `verifyBundleIntegrity` (`ai/scripts/maintenance/backup.mjs:431-485`) already separates `empty` from `pass` with a reason, persists it into both `bundle-meta.integrity` and the receipt, and `runBackup` already warns. A genuinely unreachable source already throws `DATABASE_EXPORT_ERROR` and `runBackupWithOffHostSync` writes a `status: 'failed'` receipt.

## The Fix

**Do not change the resolvers.** Their auto-create is load-bearing for first-run bootstrap and is shared by every reader in the system. Risking the vector store's hot path to improve a backup receipt is the wrong trade.

**Ask the question upstream instead, in the export path, before resolution can create anything.**

1. `chromaListCollectionNames({client})` in `ai/services/shared/vector/chromaClientPrimitives.mjs` — paginated, non-mutating enumeration. `listCollections` never creates; `getCollection` throws not-found without creating. Both `ChromaManager`s expose `listCollectionNames()` over it (the KB swap-collection scan already had this page loop and now shares it).
2. A `captured` / `empty` / `unavailable` verdict per subsystem receipt, classified by an **allowlist of positively-established states**: only `sourceExisted === true` earns `empty`; anything else — absent, or a probe that could not answer — lands on `unavailable`.
3. `verifyBundleIntegrity` maps `unavailable` to its own status, **not gated on `sourceCount === 0`**: a subsystem can capture its memories and find its summaries collection absent, giving positive row parity on a bundle that is useless for half of what it claims to hold.

**The probe is genuinely first in this lane, and that is a property of the lane rather than an assumption.** `backup.mjs` is a standalone script (`import.meta.url === process.argv[1]`, run via `npm run ai:backup`), and neither `KB_LifecycleService.ready()` nor `Memory_LifecycleService.ready()` resolves a collection. In a long-lived MCP process an earlier reader would already have created the collection and the probe would say `true` — correctly, but uselessly. This is scoped to the backup process.

**A race exists and is named rather than hidden:** another process could create a collection between probe and export. The window is small and the failure is benign — a concurrently-created collection *was* absent when the backup started, which is exactly what the verdict says.

## Decision Record impact

`none`. No `ai/` config leaf is introduced, modified, or read here — no `AiConfig` surface is touched, so the ADR-0019 gate does not fire on this diff. The verdict vocabulary is structural, with no tunable.

## Acceptance Criteria

- [ ] A subsystem whose collection did **not** pre-exist the read reports `unavailable`, never `empty`.
- [ ] A subsystem whose collection **did** pre-exist and returned zero rows still reports `empty` — asserted with a control that pre-existence was positively established, so `empty` is a finding rather than a default.
- [ ] A populated subsystem reports `captured` / integrity `pass` in the same bundle as an `unavailable` one, so a probe that condemned everything cannot satisfy the suite.
- [ ] A subsystem with **positive** row parity and one absent collection reports `unavailable` — the May-2026 partial specimen, which a `sourceCount === 0` gate would miss.
- [ ] `unavailable` is **non-fatal**: `bundle-meta.json` is still written. Routing it through integrity `fail` would throw before the receipt is written and manufacture the aborted-run specimen `#16348` exists to eliminate.
- [ ] `#exportGraph` distinguishes an uninitialized/unreadable graph store from a genuinely empty one.
- [ ] A receipt carrying **no** `captureOutcome` classifies exactly as it did before — every bundle already on disk predates the verdict, and treating an absent verdict as `unavailable` would retroactively condemn the archive.
- [ ] Post-merge: with a deliberately absent MC collection, a real backup run records `unavailable` and the previous good bundle remains the verified one.

## Out of Scope

These stay on `#16348`, which remains open:

- **The abort-mid-write artifact** (`#16348` AC3) — a run that dies mid-write still leaves a bundle-shaped directory with no `bundle-meta.json`. That needs atomic bundle assembly or a sentinel; a different mechanism.
- **Retry / cadence policy** (`#16348` AC5) — a failed run forfeiting its daily slot is orchestrator scheduling, a different subsystem.
- **Retroactive classification of the bundles already on disk.** That information was destroyed at write time and cannot be recovered. Stating it rather than implying the migration is lossless.
- **Why the sources were unreachable** on four separate dates. A different question.
- **Restore-side selection.** An all-`unavailable` bundle already yields `rowTotal === 0` and is refused as `BUNDLE_EMPTY` by the guard merged in `#16384`. A partially-`unavailable` bundle stays restorable, which is correct — it IS restorable for the subsystems that captured, and the receipt now names which. A second refusal would duplicate a working guard.

## Avoided Traps

- **Changing the resolvers.** The obvious fix — make `getOrCreateCollection` report whether it created — puts the vector store's shared hot path at risk to improve a backup receipt, and first-run bootstrap depends on the auto-create.
- **Routing `unavailable` through integrity `fail`.** `runBackup` throws on `fail` and writes `bundle-meta.json` *after* the integrity check, so failing the bundle produces a receipt-less directory — the exact specimen class this work eliminates.
- **A denylist of known-bad states.** The classifier is an allowlist: only a positively-established pre-existing source earns `empty`, so cases nobody enumerated fail toward "I cannot vouch for this" by construction.
- **A bundle-level flag instead of per-subsystem verdicts.** The May-2026 specimen is a bundle simultaneously useful for memories and useless for summaries; subsystems fail independently.
- **Testing through a seam below the resolver.** A test that injects beneath the resolver cannot observe the conversion that causes the defect — the mistake caught in review on PR `#16385`, where three green specs proved nothing about the production path.
- **`?? 0` at `backup.mjs:227` as the cause.** It feeds only `embedding.counts`; the raw SDK return is written verbatim to `bundle-meta.json` and the integrity check reads `raw?.count` directly. This was my own first answer and the source falsified it.
