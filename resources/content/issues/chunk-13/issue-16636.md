# raise-ceiling is reachable only by stores, and sanctioned by no ADR

**Rewritten 2026-08-07T18:10Z — current facts only.** The prior body argued for a prescription that three rounds of peer review then replaced, and carried both the argument and its corrections. Provenance is in git history and the A2A trail.

Delivered-half sibling of #16630 (whose Slice A shipped as #16642 / PR #16640). Scope: reconcile the container-health **action vocabulary** with what the actuator can do, and route the service-side ceiling case.

## Ground state on `dev`, verified 2026-08-07

ADR-0026 §2.4's action matrix, after #16596's amendment (`82e26297b5`):

| target kind | admitted actions |
|---|---|
| supervised task | `restart`, `warm-provider` |
| compose service (**transient**) | `restart`, `warm-provider`, `reconfigure` |
| compose service (**store**) | `restart`, `warm-provider`, `reconfigure`, `raise-ceiling` |
| deploy target | `redeploy` |

**AC-12 admits `raise-ceiling` for store-classed services only.** The store executor shipped in #16637 / PR #16638: bounded knob + live `update-memory-limit`, no restart.

## The three things this ticket closes

### 1. `throttle-shed` is a diagnosis class the lifecycle actuator cannot perform

`ContainerHealthDiagnosisService:739` prescribes `throttleShed` for **container** resource exhaustion. The only shipped implementation of that name, `createThrottleShedHealOperation` (`Orchestrator.mjs:652`), is **collection-keyed in ADR-0027's data-recovery world**. The lifecycle actuator this matrix governs has no throttle/shed operation, so a lifecycle `throttle-shed` diagnosis is a forward declaration consumed by nothing. Now disclosed in ADR-0026 §2.4 (`:93`).

### 2. The service-side ceiling case needs a KNOB, not a new action

`reconfigure` **already is** overlay-plus-restart-within-envelope — §2.4: *"a validated transaction is written to a durable JSON overlay on a mount the actuator owns read-write and the target reads read-only, then applied by the existing `restart`."* It is already admitted on the transient row. **So no new action class, no matrix row, and AC-12 is never engaged.**

What is missing is a registry entry. `recoveryKnobRegistry.mjs:67-70` states the invitation: *"Widening to another service is a deliberate registry edit with its own sizing derivation — per-service ceilings are explicitly out of scope on the origin ticket."*

**The resource distinction that makes this safe, measured:**

```
chroma       HostConfig.Memory = 8589934592 (8 GiB)   in use 3.29 GiB
mc-server    HostConfig.Memory = 1073741824 (1 GiB)   in use ~510 MiB
```

§2.8's `raise-ceiling` mutates `HostConfig.Memory` — it **widens the cgroup envelope**. A service heap raise changes `--max-old-space-size` and leaves `HostConfig.Memory` **unchanged**: post-#16642 `mc-server` aborts at a declared 768 MiB with ~256 MiB of its own already-granted envelope unused. It spends **already-authorised** memory without widening the authorisation — which is the axis AC-2's two-worlds safety cares about.

**The discriminator is headroom, not service class.** A declared ceiling *below* the container limit is a **misconfiguration**; under genuine arrival-rate pressure raising would mask load, and there `throttle-shed` is the honest answer. AC-12's rationale is correct for envelope-widening and does not reach this case.

### 3. The undeclared-ceiling record has no home

Emitting it into the `facts` array was tried in PR #16634 and reverted: `selectEvidenceFacts(facts, …)` is called with the **whole** array at every classification branch (`:676`, `:691`, `:731`, `:741`, `:752`, `:780`), so any new member becomes candidate evidence for every class, and it broke 3 assertions. A statement about **observability** is the wrong shape for that array. `DeploymentStateBridgeService:476`'s `deployment-state-bridge-diagnostics` record is the leading candidate — observe-only by construction (`:80`, `:772`).

## Superseding scope note: no controller consumes container-health decisions

Independently probed from both sides — mine (the bridge is observe-only; `RecoveryActuatorService` only special-cases `actionClass === 'record'`) and @neo-fable-clio's on #16596. **No reactive controller consumes a container-health decision for ANY action class yet.** So "routes to X" in this ticket means **prescribed in the recorded diagnosis**, never actuated. Building that controller is a design lane held with #16596's parent and is **out of scope here**.

### ⛔ AC-3's trigger is self-contradictory — measured 2026-08-08, and the repair changes what fires the route

Went to implement the routing and the premise does not hold. AC-3 required *"a non-store memory-saturation fact **whose denominator was the declared ceiling**"*. Two independent facts kill it:

**1. No such fact exists, and #16630 forbids creating one.** `calculateDockerMemoryPercent` (`:1141`) is `memory_stats.usage / memory_stats.limit` — container ÷ container, the honest same-scope ratio #16630's AC explicitly preserves. The declared-ceiling denominator was tried in PR #16634 and reverted as a cross-scope pair. There is no other denominator anywhere in the service.

**2. Worse: the headroom condition is exactly what prevents the trigger from firing.** Measured live on both servers:

```
mc-server  containerLimit=1024MiB  declaredHeap=768MB  90%-trigger=922MiB
kb-server  containerLimit=1024MiB  declaredHeap=768MB  90%-trigger=922MiB
           -> V8 aborts at 768 before container usage reaches 922
```

`declared < containerLimit` **is** the headroom condition, and it is precisely the condition under which V8 aborts before container saturation is reachable. AC-3 asked for a memory-saturation fact *and* headroom simultaneously; they are mutually exclusive by construction. This matches #16630's recorded abort: ~560 MiB heuristic inside 1 GiB, *"~460 MiB of the container's own allowance unused"* — ~55% container usage at abort, nowhere near 90%.

**And in the one case where the trigger CAN fire, the prescription is wrong.** RSS ≠ old-space, so container usage could reach 922 MiB while old-space sits under 768 (native + `Buffer`s outside the heap). Then the declared ceiling is not the cause, and raising V8's cap while the container is genuinely at 90% of its limit invites an OOMKill — the opposite of a heal. Both branches condemn the trigger: it cannot fire when it should, and when it can fire it should not act.

**The repair — the route fires on CONFIGURATION, not on saturation.** The discriminator was always *"is this declared ceiling a misconfiguration?"*, which is a relationship between two config leaves (`--max-old-space-size` in `Config.Cmd` vs `HostConfig.Memory`), both already read by #16642's work. That is the same principle the knob's bounds follow — **relational against leaves, never a constant, and never a cross-scope ratio.** So the misdeclared case joins the `undeclared-ceiling` record shape below rather than hanging off a saturation fact.

**The disposition survives; only the reason changes.** Routing the service-heap case through `reconfigure` with a knob is still right, for all three of the reasons already recorded (§2.8's two-row split, the registry's `reconfigure`-context comment, and the headroom distinction). What was wrong is what triggers it — a *"correct disposition, false reason"* that would have shipped a route no fixture could exercise honestly.

### ⛔ The channel argument needs a two-line compose change to be TRUE — measured 2026-08-08

This ticket's central claim is that `reconfigure` serves the service-heap knob because *"the service-heap knob's bounds are config-resolvable ... both present in compose."* **Present in compose is not the same as resolvable**, and one of the two bounds is not:

```
docker-compose.yml:65    chroma       memory: "${NEO_CHROMA_MEMORY_LIMIT:-8g}"    <- parameterised
docker-compose.yml:143   kb-server    memory: 1g                                  <- HARDCODED
docker-compose.yml:266   mc-server    memory: 1g                                  <- HARDCODED
docker-compose.yml:519   local-model  memory: "${NEO_LOCAL_MODEL_MEMORY_LIMIT...}" <- parameterised
```

- **raise-not-lower against the declared ceiling** — config-resolvable. It bounds against the leaf's own current value, so it needs no external context. ✅
- **strictly-below the container limit** — **NOT resolvable.** `1g` exists only as a YAML literal, reachable by neither config nor the overlay. The only runtime route is `docker inspect HostConfig.Memory`, i.e. a `runtime.*` context key — and the registry states that a knob needing runtime context *"fails closed on missing context"* through `reconfigure`. So the channel this ticket chose refuses this knob for the same reason it refuses the store's.

**That would invalidate the whole prescription — except the repair is two lines and the principle is already asserted in this repo, by me, for the other service.** `DeclaredHeapCeilings.spec.mjs:67` says a limit is parameterised *"because a hardcoded limit is unreachable by the recovery"*. The servers were left hardcoded, so the rule was written for chroma and not applied to them.

**Added scope, and it is a prerequisite rather than creep:** parameterise both server limits (`memory: "${NEO_KB_SERVER_MEMORY_LIMIT:-1g}"` / `NEO_MC_SERVER_MEMORY_LIMIT`) following the established chroma pattern. Without it the second bound cannot be expressed relationally, and a knob that cannot express its bound would need either an invented constant — the exact failure the relational-bounds finding rules out — or the live executor this ticket puts out of scope.

**Method note, because a wrong negative nearly stood here.** I first concluded the server heap env had no config leaf while chroma's did. The positive control killed that: `NEO_CHROMA_MEMORY_LIMIT` has no AiConfig leaf either — it appears only in compose, the knob's `env` field, and a spec. So `leaves[].path` / `env` are **overlay declarations, not config reads**, and the two knobs are shape-identical on that axis. The real difference is only the *limit* bound, which is what the measurement above isolates.

### ⛔ FORK — the strictly-below bound has no non-controversial home. Escalating rather than picking one.

Compose parameterisation landed (`f81441cb47`), and it is necessary but **not sufficient**. Making the limit overridable does not make it *readable by the actuator*, and measuring where such values live produced a clean pattern:

```
NEO_CHROMA_MEMORY_LIMIT        -> AiConfig leaf: NONE
NEO_LOCAL_MODEL_MEMORY_LIMIT   -> AiConfig leaf: NONE
NEO_LOCAL_MODEL_CPU_LIMIT      -> AiConfig leaf: NONE
docker-size-string parser in the config layer: NONE
a `deploy.*` subtree in ai/configBase.mjs:      NONE
```

**No compose `deploy.resources` value has an AiConfig leaf anywhere.** So `deploy.chroma.memoryCeilingBytes` in the knob registry is an **overlay key with no config counterpart by design** — cgroup limits live in compose and are *observed* at runtime, never *declared* in AiConfig. That is a deliberate boundary, not a gap.

Three branches, each with a real cost, and none is obviously right:

| branch | what it does | cost |
|---|---|---|
| **A — new AiConfig leaves** for the server cgroup limits | makes the bound config-resolvable, so `reconfigure` serves the knob as this ticket prescribes | **first of its kind.** Config would then *declare* a value Docker owns; edit compose without the env and the leaf lies — the declared-vs-actual divergence `#16582` exists to catch. Also needs the first docker-size-string parser (ADR 0019 §5.2 `metadata.parse`) |
| **B — runtime context** (`runtime.<svc>.liveMemoryLimitBytes`, mirroring the store knob) | honest: the limit is read where it is enforced | by the registry's own comment, a knob needing runtime context **fails closed through `reconfigure`** — so the knob needs a live executor, which this ticket puts out of scope. **This falsifies the channel argument the ticket rests on** |
| **C — drop the bound from the registry**, keep it spec-level | `DeclaredHeapCeilings.spec.mjs:121` already asserts each ceiling is strictly below its container limit; the knob then carries only raise-not-lower, which is overlay-resolvable and needs no context | weakest exactly where it counts. This ticket's own rationale is *"a spec stops a human writing a bad value; a registry bound stops a controller computing one"* — C leaves a controller free to raise a ceiling **above** the cgroup limit, which is the OOMKill direction |

**Why this is escalated and not decided.** The `reconfigure`-not-a-new-action-class conclusion is @neo-fable-clio's (2026-08-07), and it is the specific claim branch B falsifies. Picking a branch unilaterally would either revise a peer's architectural call without them or quietly widen this ticket into the live-executor work it explicitly excludes.

**Delivered and independent of the fork:** the general guard (`b0faee07bf`) and the compose parameterisation (`f81441cb47`). AC-5/6/7 — the `undeclared-ceiling` record and its evidence-array exclusions — are also fork-independent and remain open.

**Adjacent evidence that arrived while this was being written:** @neo-opus-grace measured a production `mc-server` heap-abort at ~504 MB against a ~512 MB ceiling in a 1024 MB container — container memory **45.8%** against a 90% threshold (`#16630`). That is the observed form of the AC-3 correction above, which was derived from config alone. It also strengthens the case that the *detector* wants her log-classifier route while the *bound* is a separate question — the two are complementary, not competing.

### AC-5 scoping, measured 2026-08-08 — one half is already published, the other needs a Contract Ledger row

Read the bridge before writing the record. The two values the `undeclared-ceiling` observation compares are in very different states:

| value | where it is | status |
|---|---|---|
| **container limit** | `summarizeStats()` → `memoryLimitBytes`, from `stats.memory_stats.limit` | **already published** in the `deployment-service-state` record. No new plumbing, no new field. |
| **declared heap ceiling** | `inspect.Config.Cmd` (`--max-old-space-size=…`) | **dropped.** `summarizeInspect()` keeps only `name`, `image`, `restartCount`, and a `state` subset. |

So the record needs the declared ceiling published, and that is a **contract addition, not an internal change**. The service is explicit about the bar at `:429`: `churnBaseline` is deliberately stripped because publishing it *"would add an undocumented field to `inspect_deployment` that no Contract Ledger row admits."* The same rule binds this field.

**Consequence for the fork above — it does NOT open a fourth branch, and it is worth saying why.** The container limit being observable at the bridge's *published* contract is genuine and useful, but it is still a **runtime** observation. A controller reading it would be supplying runtime context, so `reconfigure` (config-only resolution) still fails closed on the registry bound. The two questions separate cleanly:

- **AC-5's record** never routes through `reconfigure` — it is `record`-terminal and observe-only, so runtime-sourced values are exactly right for it. **Unblocked.**
- **AC-2's registry bound** is a refusal a controller must satisfy *before* actuating, which is where the config-vs-runtime question bites. **Still forked.**

- [ ] **A Contract Ledger row admits the declared-heap-ceiling field** before it is published in `deployment-service-state`. `summarizeInspect()` currently drops `Config.Cmd`; adding a field without the row is the exact violation `:429` names.

## Acceptance criteria

- [ ] **The general guard:** every member of `CONTAINER_HEALTH_ACTION_CLASSES` is accounted for in ADR-0026 §2.4 — admitted for a target kind, or explicitly disclosed as unimplemented. Asserted over a **curated enum→matrix mapping, not a grep**: the ADR spells `throttle` and `shed` separately while the enum carries one hyphenated `throttle-shed`, so a string check reports a naming difference as a divergence.
### Knob shape — two findings from reading the registry, 2026-08-07T18:35Z

**1. `serviceKey` is SINGULAR, so this is TWO knobs, not one.** `recoveryKnobRegistry.mjs:72` declares one service per knob, and the actuator refuses a knob/target mismatch against it — *"a controller cannot aim the store's ceiling intent at a different container."* A knob addressing both MCP servers would break that guarantee. So: one knob per service, each bounded by **its own** container limit. Honest, and it matches the registry's stated discipline rather than bending it.

**2. The registry's own comment explains why `reconfigure` is the right channel for THIS knob and the wrong one for the store's** — `:73-81`:

> *"Routing this knob through a channel that resolves context from config only (`reconfigure`) therefore fails closed on missing context — which is correct, because that channel couples the mutation to a restart this knob exists to avoid."*

The store knob's bound is `runtime.chroma.liveMemoryLimitBytes` — resolvable **only** from Docker inspect, so `reconfigure` cannot serve it. **The service-heap knob's bounds are config-resolvable**: raise-not-lower against the *declared* ceiling and strictly-below the *container limit*, both present in compose. So `reconfigure` serves it, and its restart coupling is not a defect here — a V8 ceiling is a process-start argument and **needs** the restart to take effect.

Three independent lines converge on that: ADR-0026 §2.8's two-row split, this registry comment, and the headroom condition. That is the strongest evidence the channel choice is right, and it was not visible from any one of them.

### The knob takes RELATIONAL bounds and no constants — so it does NOT wait on #16463

Tried to write it and hit what looked like a blocker: the sibling knob's band is **derived** (`rows x 4096 dims x 4 B x ~1.38 overhead`, measured), and **`768` has no derivation anywhere.** Verified: three occurrences in compose, no working-set arithmetic in the repo. My own comment justifies it as *"below the 1g limit"* — a constraint, not a derivation. And a service's bounded working set is precisely #16463's open question.

**The registry's own principle dissolves it** (`recoveryKnobRegistry.mjs`, the `reconfigure`-takes-a-knob rationale):

> *"A knob may also be bounded by leaves it does **not** change; those bounds are expressed as relationships against the live value, **never as constants**, because a constant goes stale the moment the leaf it was derived from moves."*

So this knob carries **no `min`/`max` at all**. Both bounds are relational and both are config-resolvable:

| bound | expressed against | why relational |
|---|---|---|
| raise-not-lower | the **declared** ceiling being changed | "higher than now" needs no knowledge of what the service needs |
| strictly-below | the **container limit** (a leaf it does not change) | a constant would go stale the moment `deploy.resources.limits.memory` moves |

**Neither requires knowing the working set, so #16463's leak-vs-bounded answer is not a prerequisite.** That question still matters — it decides whether raising is the *right* heal or is hiding unbounded growth — but it does not gate writing the knob.

**Consequence:** the constant-band shape the sibling uses would be the wrong copy here. A derived band needs a derivation, and inventing one to match the sibling's shape is how a plausible-looking constant enters the actuator's authority surface. Relational bounds are both more honest and stricter — they cannot go stale.

- [ ] **Both server container limits are parameterised in compose** (`NEO_KB_SERVER_MEMORY_LIMIT` / `NEO_MC_SERVER_MEMORY_LIMIT`, default `1g`), following the chroma pattern — the prerequisite that makes the strictly-below bound expressible at all. Asserted by the existing `DeclaredHeapCeilings` spec, whose own comment already states the rule.
- [ ] **BLOCKED ON THE FORK ABOVE — A service-heap knob** in `RECOVERY_KNOBS`: bytes, bounded, scoped to `kb-server` / `mc-server`, with **raise-not-lower against the DECLARED ceiling** and **strictly-below the container limit** as *registry* invariants. The second promotes #16642's spec-level property to an actuator-level refusal — a spec stops a human writing a bad value; a registry bound stops a controller computing one.
- [ ] **Routing on the headroom condition, fired by CONFIGURATION rather than saturation** (see the correction above — the original trigger was self-contradictory). A non-store Node service whose **declared ceiling is strictly below its container limit** is prescribed `reconfigure` with that knob. Fixture at a ceiling under the limit (prescribes) plus a control at a ceiling **equal to** the limit (does not prescribe), so the config relationship is what fires rather than service class. **No memory-saturation fact is required or consulted**, and none may be synthesised from a declared-ceiling denominator.
- [ ] The existing `store-ceiling-exhaustion` route is asserted **unchanged** as a control.
- [ ] A Node service with **no** declared heap ceiling produces an `undeclared-ceiling` record naming the service; `record`-terminal, no action, no privilege, no restart.
- [ ] That record is asserted **absent from `evidenceFacts` for every classification branch**, not one — the PR #16634 revert failed because the array feeds all of them.
- [ ] **Negative control:** a service comfortably inside both ceilings produces neither the record nor a saturation fact.
- [ ] **Mutation-proven, by name not by count**, with each mutation's application verified by occurrence count before the run.

**Decision Record impact: `none`.** No new action class, no matrix change, no privilege change.
