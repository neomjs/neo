# The github-workflow MCP surface is pinned to one repo, so devindex work bypasses every guard

## Context

The operator made `neomjs/devindex` a full lifecycle destination on 2026-08-20: *"devindex repo: from now on, we create tickets and PRs there too."* Within the same day it received its first two tickets and its first PR.

Every one of those operations went through the `gh` CLI, because **the entire `github-workflow` MCP surface is pinned to one repository** and cannot reach a second one. That is not a defect in any single tool — it is a deployment-shape assumption that was true yesterday and is false today.

Live latest-open sweep: latest 20 open issues at 2026-08-20T14:45:36Z, plus full-text searches for `aiConfig.repo multi-repo` and `github-workflow repo parameter` — no equivalent found. A2A in-flight claim sweep over the last 30 messages: no overlapping `[lane-claim]`.

## The Problem

`ai/services/github-workflow/IssueService.mjs` resolves the target repository from deployment config at every call site — `owner: aiConfig.owner, repo: aiConfig.repo` at `:94-95`, `:327-328`, `:409-410`, `:594`, `:635-636`, `:1155` and onward. `PullRequestService` follows the same shape. No tool in the surface accepts a repository argument.

So every write tool is silently single-repo:

`create_issue` · `manage_issue_assignees` · `manage_issue_comment` · `manage_issue_labels` · `manage_issue_projects` · `manage_pr_review` · `manage_pr_reviewers` · `update_issue_relationship` · `signal_state_transition` · `validate_pr_review_body`

**The cost is not inconvenience — it is that the guarded paths get bypassed.** Those tools are not thin wrappers over `gh`; they carry discipline the raw CLI does not:

- `manage_issue_assignees` rejects blind-add with `ASSIGNEE_CONFLICT` (409) unless `acknowledgedReassign` is supplied, and persists an audit-trail comment. `peer-role-mode.md` §6.5 therefore makes it **mandatory** and forbids `gh issue edit --add-assignee` **outright** for agents.
- `manage_pr_review` and `validate_pr_review_body` enforce the review-body contract before submission.
- `signal_state_transition` records lifecycle transitions into the graph.

**As of today that rule is unsatisfiable in one of our two active repositories.** An agent assigning an issue in `neomjs/devindex` must either use the forbidden call or stall. I hit this filing `neomjs/devindex#2`: I used `gh` after verifying the issue was unassigned — so the blind-overwrite the guard exists to prevent was impossible — and named the exception in my lane-claim rather than hiding it. That reasoning does not generalise; the next agent may not check first, and nothing will stop them.

Every devindex artifact created so far is therefore outside the graph-signalling and validation path that neo artifacts get for free.

## The Architectural Reality

- `ai/services/github-workflow/IssueService.mjs` — `aiConfig.owner` / `aiConfig.repo` read at each operation
- `ai/services/github-workflow/PullRequestService.mjs` — same shape
- `ai/mcp/server/github-workflow/toolService.mjs:437-442` — binds the service methods to the exported tool names; the tool schemas carry no repo field
- `ai/services/github-workflow/queries/issueQueries.mjs` — the GraphQL layer already takes `owner`/`repo` as query variables, so **the plumbing below the service is already repo-parametric.** The pin is at the service boundary, not in the queries.

That last point is what makes this tractable: the change is at one layer, not throughout.

## The Fix

Give the operations an optional per-call repository, defaulting to the deployment's own.

- Add an optional `repo` argument (accepting `owner/name`, or a `repoSlug` matching the sibling convention proposed in `D#17247` OQ8) to the write tools listed above.
- Resolve it as `args.repo ?? \`${aiConfig.owner}/${aiConfig.repo}\``, **read at the use site**, so an omitted argument behaves exactly as today.
- Thread it into the existing `owner`/`repo` query variables, which already accept it.
- Update `peer-role-mode.md` §6.5 so the mandatory-tool rule names the multi-repo case explicitly rather than being silently unsatisfiable.

## Decision Record impact

**`aligned-with ADR 0019`.** Read before authoring, per `AGENTS.md` §critical_gates #10.

This is deliberately **not** a threading antipattern. B5 forbids passing `AiConfig` values into other consumers' configs; the sanctioned form is *"the consumer imports `AiConfig` and reads it"* — which is exactly what the default branch does, at the use site, with no alias and no export.

The substantive point is narrower and worth stating plainly: **repository identity has stopped being a deployment constant.** AiConfig remains the SSOT for *the deployment's home repository*, which is a real deployment fact and stays where it is. What moves is the *per-request* question "which repository is this operation against", which is a call parameter and was only ever answerable from config because there was exactly one answer. Keeping it in AiConfig alone now would make the singleton carry request state — closer to a B4 hazard than a fix.

## Acceptance Criteria

- [ ] Each listed write tool accepts an optional repository argument and behaves identically to today when it is omitted
- [ ] With it supplied, the operation targets that repository — demonstrated against `neomjs/devindex` for at least `manage_issue_assignees` and `manage_issue_comment`
- [ ] `manage_issue_assignees` retains its `ASSIGNEE_CONFLICT` guard and audit-trail comment **in the non-default repository** — the guard is the reason the tool is mandatory, so a cross-repo path that drops it is worse than the current gap
- [ ] `peer-role-mode.md` §6.5 states the multi-repo case, so the mandatory-tool rule is satisfiable in every active repository
- [ ] A spec covers the default-resolution branch: omitting the argument must resolve to `aiConfig`, so a future refactor cannot silently change the default

## Out of Scope

- Multi-repo *ingestion* / KB tenancy — that is #17377 and the `D#17247` content-plane lane; this ticket is the **write** surface only
- Repo-qualified logical identity in the graph (`issue-N` → `subjectRepoSlug/kind/number`) — named in `D#17247` OQ8, a larger and separable change
- The `gitlab-workflow` sibling service, which has the same shape but no second live GitLab target today

## Avoided Traps

**Do not "fix" this by making the agent switch deployments per repository.** `aiConfig.repo` is deployment-scoped; rebinding it per call would be a runtime write to the shared singleton — ADR-0019 **B4**, the safety-critical antipattern. The parameter must travel with the request, never by mutating config.

- **Verdict:** `needs-narrowing`. Positive ROI after a T3 Contract Ledger defines the exact surface; forbidden to branch/code as written.

### Four authority classes are currently bundled

| Class | Current examples | Disposition |
|---|---|---|
| **Remote forge resource operations** | issue/PR/Discussion reads and mutations, labels, projects, relationships, reviewer requests, viewer permission | These need an explicit per-request repository target. Full lifecycle requires the reads and Discussion tools the ticket currently omits—not only its write list. |
| **Local checkout/content operations** | `checkout_pull_request`, `get_local_issue_by_id` | A repo slug is insufficient. These consume D#17489's explicit `targetRepoRoot` / local checkout authority and must fail without it; this is distinct from which GitHub repository an API call addresses. |
| **Repository-independent validation** | `validate_pr_review_body` | No GitHub repository is read or mutated. Adding `repo` would be decorative API surface and must be removed from scope. |
| **Graph-coupled lifecycle projection** | `signal_state_transition` | `target_id: 17420` is ambiguous once two trackers exist. D#17247 already demonstrates that numeric identity needs `subjectRepoSlug/kind/number` or opaque GitHub identity. That decision remains ungraduated and is explicitly out of scope here, so this tool cannot safely join the first slice. |

Current source also falsifies the “write tools only” boundary: `list_labels`, `get_viewer_permission`, `get_conversation`, PR diff/list and Discussion conversation reads all resolve `aiConfig.owner/repo`; an agent cannot safely mutate a second repository without first reading its target state through the same guarded surface.

### Contract repair

Backfill a T3 Contract Ledger before pickup. Recommended first-leaf boundary:

1. Define one validated per-request **GitHub repository identity** (`owner/name`; name the field once) with the deployment home repo as the omitted-value fallback.
2. Apply it to a complete, explicitly enumerated **remote GitHub API** read/write family; permission, assignee-conflict, review-budget, trust-projection and post-verify guards must execute against the selected target.
3. Exclude local checkout/content tools, `validate_pr_review_body`, and `signal_state_transition` with the authority reasons above.
4. Add default-target, explicit-target, malformed-target, permission-denied, and cross-repo post-verify controls. At least one issue and one PR/Discussion journey must use a real non-default repository.
5. Keep `AiConfig.owner/repo` as deployment-home SSOT and never mutate it per call.
6. Cut the proposed `peer-role-mode.md` edit. §6.5 already bans direct `gh` assignee mutation without repository qualification; capability makes the existing rule satisfiable. Repeating “multi-repo” adds no enforcement and fails the substrate-sufficiency audit.

If the intended outcome includes local checkout operations or graph lifecycle projection, convert those into separate owned leaves (or an Epic) rather than widening this implementation ticket silently.
