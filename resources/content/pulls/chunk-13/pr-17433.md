Resolves #17412

> 🌿 A lane could declare four slots and use one, and every layer that caused it had a docblock explaining why it was careful — so what this makes unsayable is "the parallelism is honoured" as a thing you can believe without watching two requests overlap.

Two bounds held this path to one request at a time. The ticket named one. Removing it alone would have changed nothing.

Evidence: L2 (isolated-process probes against a real loopback HTTP server exercising the real transport, with the provider stubbed; plus pure plan arithmetic with its own fixtures) → L2 required (every AC on this leaf is unit-reachable). Residual: the plane-observable throughput change, Residual-Owner: #17411.

## The two bounds

**Named:** `slotHeadroomWidth = parallel - 1` spent the declared parallelism on request **width**, to reserve a provider slot. A client cannot reserve a slot — the server assigns them from its own queue — so it only guaranteed one idled. At four slots it reserved 25%, at two 50%, at sixteen 6%, and it only ever clamped downward. Deleted: width comes from its own leaf, concurrency from the parallelism.

**Unnamed, and the reason the first removal is insufficient:** `#drainOpenAiCompatiblePostQueue` drained with a **single worker** behind a boolean re-entrancy guard, its docblock stating it runs posts *"one at a time"*. My dispatch loop could issue four requests and they queued behind one drain.

It is now N bounded workers, N = the declared parallelism, each selecting through the same `#getNextOpenAiCompatiblePostQueueIndex`. **Interactive latency improves rather than degrades** — an interactive item waits for the first of N workers instead of the only one — which is the concern the deleted clamp was clumsily reaching for, handled where the queue actually admits.

## The carry had to change representation, not merely survive

```js
const completedTextCount = completedChunkCount * chunkSize,   // a count times a width
```

Valid only while completions arrive in order; the production comment said so. Under fan-out a span can land after a hole, and the product then claims a range containing inputs that never completed.

**The consequence was never a corrupt vector.** `toOrderedEmbeddings` fails closed, the `catch` swallows, and the error travels uncarried — so concurrency would have **silently switched work conservation off**, with the lane re-purchasing the same vectors on every retry and nothing in the logs. On a lane measured at ~0.19 chunks/min that is indistinguishable from the problem this ticket exists to fix.

`resolveCompletedPrefix` now measures the real carryable prefix and **reports** the completed-but-unbindable remainder. A sparse carry is not expressible: the consumer binds by position (`batchToEmbed.slice(0, err.completedTextCount)`), so the longest contiguous prefix is the most any caller can bind — and the dropped count makes the residue observable instead of silent.

## Deltas from ticket

**The ticket's Architectural Reality named one bound; I amended it before implementing** with the five prefix-dependent properties fan-out breaks, and three ACs including the one that matters: *the red-proof must fail by carrying nothing, not by mis-binding.* An arm checking only "no wrong vectors" passes on the broken shape, because the guard already prevents wrong vectors — and that is exactly what hides the defect.

**The second bound was not in the ticket at all.** Found by the overlap arm failing after the clamp was gone. It is in scope: the ticket's prescription is *"bound in-flight requests by `localModels.embedding.parallel` and let the provider schedule"*, and this is where in-flight requests were actually bounded.

**Not done, deliberately:** a sparse carry. It would conserve the out-of-order remainder too, and it changes the consumer's positional binding contract — a separate leaf if the dropped fraction proves material. The count is now reported so that question becomes measurable rather than speculative.

## Test Evidence

`ai/services/memory-core/**`: new `test/playwright/unit/ai/services/memory-core/embeddingDispatchPlan.spec.mjs` (11 arms over the pure plan), plus the rewritten concurrency arm in `TextEmbeddingService.spec.mjs`.

**Mutation-verified.** Reverting `resolveCompletedPrefix` to the predecessor's `count × width` reddens **4 of 11** arms — all four `resolveCompletedPrefix` arms — and leaves the seven `planEmbeddingSpans` / `resolveEmbeddingConcurrency` arms green.

**A bug of mine caught by a pre-existing arm, which earned its keep.** `a prefix that cannot prove positional binding leaves the failure UNCARRIED` went red: I decorated the error field by field, so an unprovable prefix escaped with `completedTextCount` set and `embeddings` undefined — a count with no vectors, which the consumer slices onto ids anyway. The original computed both before assigning either; that ordering was load-bearing and undocumented. Restored, with the atomicity now stated as the reason rather than implied by expression order.

**The overlap instrument took three attempts and the first two lied.**

1. A macrotask deferral resolved each response before the next request's `end` fired, so a genuinely concurrent client read `maxConcurrent: 1`. I briefly concluded from that reading that a *fourth* serialisation layer existed. **It does not** — a standalone event-log probe showed `arrive#1(open=1) | arrive#2(open=2)`, real overlap, and the collapse was mine.
2. Holding until two are open fixed the concurrent run and **deadlocked the sequential one**, where request N+1 cannot arrive until N answers.
3. The two runs now use instruments matched to what each can observe: the concurrent run holds until it sees real overlap, the sequential run resolves immediately and asserts `maxConcurrent === 1` as the silent arm.

Concurrency is asserted by **overlap, never by call count** — a sequential loop makes the same number of calls, which the ticket names as a trap.

**Both bounds are mutation-verified, and one of the two reds is ugly — stating it rather than letting the table imply otherwise.** Restoring the width clamp reddens the arm by assertion (`width must not vary with parallelism`). Restoring the single-worker drain, with the clamp still deleted, reddens it **by deadlock at the 10s probe timeout** rather than by a `maxConcurrent` assertion: the probe's release condition is the overlap it measures, so a serialised client holds the first response forever. That is a genuine falsifier and it proves the queue conversion is load-bearing rather than incidental, but a timeout has many possible causes and an assertion has one. If a reviewer wants that red to name its cause, the probe needs a release rule that reports serialisation instead of waiting through it, and I have not found one that does not reintroduce the timing fragility of attempt 1.

**Regression check by SET, not by count.** The memory-core suite reports 28–30 failures on both this branch and a stashed clean tree; the counts vary between runs because that suite has flaky arms. The failing **sets** are identical in both directions (`comm -23` and `comm -13` both empty), which is the claim that matters. Consumer suite `ai/services/knowledge-base/`: **720 passed, 1 failed** — `ChromaManager.spec.mjs:51`, pre-existing and baselined earlier today.

`check-fixed-sleeps`: OK, 0 new. `check-ticket-archaeology`: 0 violations.
