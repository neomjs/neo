## Summary

Implements the ADR 0035 §2.6 projection writer — **the missing critical-path leaf of Epic #15100**, which was producer-complete and consumer-empty. The typed route (#15087, merged), both historical Bird Views (#14435, #15088, shipped), the current-state landscape (#15234, approved), and the lifecycle frontier (#15267, PR #15295) all exist, and **not one of them reached a hook.** This is the transport that carries them.

The leaf had no ticket. That gap was invisible because nothing was *wrong* with any existing ticket — the missing one simply did not exist. An epic can look healthy leaf-by-leaf and still have no path to a consumer.

## The property: the guarded resource is not the file

Several MCP and service processes can race one projection target. **Epic #15100 explicitly rejected atomic-rename-alone**, and the reason is worth restating because the rejected option is the intuitive one:

> a rename prevents a **torn read**, but not a **lost update** — two writers can each complete a rename, and the later one silently wins carrying older content.

So the guarded resource is the **serialized SQLite write transaction** that revalidates the holder's token and epoch and then performs the rename *without releasing*. Nothing can commit a takeover in between.

The near-miss worth naming: **revalidate-then-rename is the bug.** It is the obvious shape, it reads as correct, and it leaves a window where a successor acquires the lease while the old holder is already past its check and still about to write. Equally, **a fencing epoch carried in the payload is diagnostic, never a guard** — a reader can see it; it cannot stop the write.

The two mechanisms solve different problems and both are needed:

| Failure | Prevented by |
|---|---|
| A reader sees a half-written projection | the atomic rename (same-dir temp → rename) |
| A stale holder overwrites its successor | the serialized transaction wrapping that rename |

## Deltas

- **`ai/services/memory-core/hookProjectionLease.mjs`** — the two operational tables (deliberately **not** Native Edge Graph nodes: a projection is transport state with an expiry, not knowledge, and an ontology would invite readers to treat a stale render as a fact), plus acquisition, the fenced publication, and token+epoch-checked release. Acquisition is `IMMEDIATE`, not deferred — a deferred transaction takes its write lock only on first write, which is exactly the window where two acquirers both read "unheld" and both believe they won. Only the token **hash** is stored: the lease row is what a competing writer reads, so a raw token there would let any reader impersonate its holder.
- **`ai/services/memory-core/hookProjectionSubmission.mjs`** — producer submission. The three watermark cases are different facts and collapsing any two is the defect class: a **regressed** watermark is rejected (a slow in-flight read must not move the projection backwards); an **equal watermark + identical payload** is idempotent (replay is normal — treating it as an error makes every transient failure a false conflict); an **equal watermark + different payload** is a source conflict, so the prior is kept and the channel degrades, because two payloads claiming one instant cannot both be true and guessing would publish a coherent-looking lie.
- **`ai/services/memory-core/hookProjectionTransport.mjs`** — the atomic write. The path is **derived** from the server-derived target id under the Memory-Core-owned root, never supplied: a caller-chosen path would make every producer a potential arbitrary-write primitive. Flush precedes rename, because a rename that beats its own data to disk publishes a complete-*looking* file with a torn body after a crash — the one outcome a reader (no lock, no retry) cannot detect.
- **`ai/mcp/server/memory-core/config.template.mjs`** — `hookProjectionLeaseTtlMs` + `hookProjectionRoot` as leaves with **no primitive-local default**. The TTL is a real operational dial, not a magic number: it doubles as the worst-case wait before a crashed holder's target frees itself.

## Test Evidence

Evidence: **25 green**, against a **real SQLite store** rather than a stub — a stub cannot prove serialization, which is the entire mechanism under test.

| Suite | | Pins |
|---|---|---|
| `hookProjectionLease` | 9/9 | acquisition, contention, takeover, fencing, release |
| `hookProjectionSubmission` | 8/8 | the three watermark cases, admission, identity |
| `hookProjectionTransport` | 8/8 | derived path, flush-before-rename, cleanup |

Pinned per defect, not asserted in prose:

- **The fencing property is proven by absence, not by output.** After a takeover, the stale holder's transport is asserted **never reached** (`writes === 0`) — an output-only assertion would pass against an implementation that wrote and merely *looked* wrong afterwards.
- **Ordering is asserted as a sequence** (`['mkdir','write','open','fsync','close','rename']`) — an fs double recording only final state could not distinguish flush-then-rename from the reverse, which is the exact crash-safety property.
- **Contention performs no write** — the losing acquirer's row is compared before/after.
- **Replay ≠ conflict** — identical payload at an equal watermark is accepted; a different one degrades the channel *and records why*.
- **A newer watermark clears an earlier conflict** — the contested instant is no longer what the channel describes.
- **A cleanup failure never masks the original error** — the caller needs the cause, not the janitor's complaint.
- **Path traversal is refused at the filesystem boundary** — the id is server-derived, but this is where it *becomes* a path, so it is re-checked rather than trusted.
- Fail-loud on every unbound injection: an un-materialized `leaseTtlMs` must never become a guessed lease window.

## Notes — one deliberate extension, flagged for review

**`conflict_reason` is a column the ADR's shown schema does not carry.** I added it, and this is the one place this PR extends §2.6's literal text, so it deserves the reviewer's attention rather than a quiet pass.

Reasoning: §2.6.1 says an equal-watermark different payload *"degrades that channel"*. The channel row is the only thing the writer reads at publish time, so a conflict living only in a return value would vanish the moment the producer moved on — and the next publication would render a contested channel as though it were clean. A degradation the reader cannot see is not a degradation; it is a silent wrong answer. If the reviewer reads §2.6's `text` block as exhaustive rather than indicative, the alternative is a **separate** conflict table, and I would rather be told than guess.

- **Producer-side only reaches `HookProjectionChannels`.** Producers never read or write `current.json` and never merge another producer's channel — a producer knows one truth and cannot see the composed picture.
- **Wave 1 is bounded single-publication with NO renewal.** A render that cannot finish inside its window aborts loudly rather than quietly holding a target. **Adding renewal is an ADR revalidation, not a review nit** — flagging so it is not proposed as one.
- Not wired into `toolService` yet: the reader cutover (§2.11 Ph3–4) is downstream and out of scope. This PR makes publication *possible* and correct; it does not yet publish on a schedule.
- Whoever takes the §2.11 reader leaf: this is your input — ping me and I will shape the seam with you rather than hand over a fait accompli.
