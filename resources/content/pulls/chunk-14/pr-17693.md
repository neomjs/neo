Resolves #17691

Evidence: L2 (pure arms over the published block with an injected `fs` and an injected clock; the runner's two repairs are source-verified) → L2 required (every AC governs a projected shape or a control-flow guarantee, decidable offline). Residual: none.

> 🌿 The operator asked the question that opened this: **"e2e runner => how would our ai team know in case it fails?"**

The honest answer was: probably not. Three independent silences, none ever observed — because the runner has never run on any host.

## AC Evidence

| AC | Proof |
|---|---|
| AC-1 | **the RED digest opts out of suppression explicitly.** `AGENT:*` resolves `wakeSuppressed` to `true` by default (`MailboxService.mjs:2446`) and `isAllowedWakeSuppression` returns `true` unconditionally for it, so nothing objected. A red suite is action-required by definition; it now passes `wakeSuppressed: false` |
| AC-2 | **green stays silent and wakes nobody.** The early `if (!red) return` is untouched — the change lives strictly on the red path, so routine success generates no traffic |
| AC-3 | **never-ran is distinguishable from all-green.** Three arms: no receipt → `unavailable` with every field `null`; a green receipt → `observed`/`red: false`; a red receipt → `observed`/`red: true` with its failing count. One arm asserts the two `observationStatus` values differ directly, so the distinction cannot regress to a shared shape |
| AC-4 | **a stale receipt reports its age, an unreadable one reports unavailable.** `ageMs` rides beside the verdict (a 23-day-old green asserts `23 * 24 * 60 * 60 * 1000`), a receipt with no parseable `at` is `unreadable` rather than a verdict, and a throwing read is `unreadable` with its message — never green |
| AC-5 | **a throwing digest send does not lose the red.** The send is wrapped; on failure the receipt is rewritten with `digest: 'failed'` and the error, then rethrown so the process exits non-zero. The block carries `digest` forward, so a failed delivery cannot read as an ordinary red |
| AC-6 | **the lock is still always released.** The new `catch` sits INSIDE the existing `try`, so the `finally { fs.remove(LOCK_PATH) }` runs on the new path exactly as before — verified by reading the nesting, not by assuming it |
| AC-7 | **red-proof** — see the mutation table |

## The three silences, and why each was invisible

**Wake.** The digest was a `AGENT:*` broadcast with no explicit wake tier, so it inherited suppression. It landed drain-class in mailboxes routinely carrying 2,000+ unread. Nothing was misconfigured; the *default* was doing it.

**Liveness.** `last-run.json` was already written on **every** run, red or green, carrying `{at, red, configs}` — and nothing in `ai/`, `src/` or `apps/` read it. So absence of a digest meant all-green **or** never-ran **or** crashed-before-reporting, and a reader could not tell which. **This was not a missing measurement; it was a measurement that never reached a decision.** The healthcheck now publishes it as `whiteboxE2e`.

**Delivery.** The send had no `catch` — only a `finally` releasing the lock. A throw from `ready()` or `addMessage` lost the detected red entirely and left the next run with no record. The reporter's failure mode was identical to its success mode. Not hypothetical: `healthcheck` on this host reported `identity.bound: false` on 2026-08-24.

## Deltas from ticket

- **`unavailable` deliberately means "no run recorded", never "nothing wrong."** A plane where the LaunchAgent was never installed reports absence. That is the entire point — the layer sat in exactly that state with 17 red specs, reading as healthy.
- **The clock is injected.** `buildE2eRunStateBlock(statePath, fs, now = Date.now())`. Every arm passes a pinned `now`, so they assert a decision rather than a date. I fixed a wall-clock time bomb of exactly this shape on #17672 this morning and had no interest in shipping another.
- **Vocabulary reused, not invented.** `observed | unavailable | unreadable` already exists on the backup census and `maintenance.*`; a fourth spelling would make the payload harder to read, not richer.
- **`digest` is carried forward rather than recomputed.** A red whose digest failed is the failure mode that most resembles a normal red, so the block reports what the runner recorded instead of inferring `sent` from `red`.

## The anchor question the lint settled — and the design question it opens

I got this wrong once and the tooling corrected me, which is worth recording because the reasoning is the interesting part.

The plane-literal lint convicted the reader's `.neo-ai-data/nightly-e2e/last-run.json`, so I anchored **both** sides on `AiConfig.plane.dataRoot`. That broke the ledger's own `LIVE-ANCHOR` arm, and reading the ledger showed why: the runner's cwd-relative root carries a **permanent exact-site acquittal**, with the rule stated in the checker's docblock — *"Ownership decides, not shape."* The runner is bound to one checkout by its LaunchAgent plist; two checkouts hold different code and therefore different e2e results, so a shared plane root would **couple independent test runs across revisions**.

I had read the lint's generic remediation text rather than the rule governing the line I was changing — and that acquittal names this exact file.

So the writer keeps the acquitted literal and the reader takes the **same** checkout-relative path. A plane-anchored reader beside a checkout-anchored writer would address different state on any host running two checkouts: the same fork this rule prevents, expressed as reader/writer divergence rather than a forked root. The reader carries its own exact-site entry recording that it **inherits** the writer's ownership and must be retired with it, never separately.

**The design question this opens, which I want a reviewer's judgment on rather than my own:** the receipt is checkout-owned, and the Memory Core healthcheck is plane-owned. Publishing there means the field reports the e2e state of *the checkout that plane serves* — well-defined and useful on a one-checkout host, ambiguous on a host running several. The alternative surfaces are worse in different ways (a digest cannot report a run that never happened; a log nobody is told to read is where this started). I think plane-publishes-its-own-checkout is right and the ledger entry makes the coupling explicit rather than silent, but it is a judgment call and the ownership tension is real.
