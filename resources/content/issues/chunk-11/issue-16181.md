# Bridge Claude Desktop seats to remote MC/KB without local servers

## Context

The #16167 hard cut must stop resident Memory Core and Knowledge Base stdio servers before the canonical container plane becomes the only writer. The existing remote-seat work from #15805 / PR #16053 deliberately left Claude Desktop on stdio until a secret-safe adapter was proven.

That proof now has a concrete, bounded shape:

- `learn/agentos/cloud-deployment/ClientAuthentication.md:136-137` already names `mcp-remote` as the Claude Desktop stdio-to-HTTP bridge.
- The upstream bridge documents `${ENV}` expansion for authorization headers, so the generated artifact can reference a credential slot without serializing its value: https://github.com/geelen/mcp-remote#custom-headers
- Anthropic's current contract says Claude Desktop can consume remote MCP through Connectors, but remote servers cannot be configured directly in `claude_desktop_config.json`: https://support.anthropic.com/en/articles/11503834-building-custom-connectors-via-remote-mcp-servers. The same-machine loopback cutover therefore still needs the committed local bridge path rather than a public Connector deployment.
- A live-machine census on 2026-07-30 found the current Neo Claude Desktop configs still launch MC and KB as local `command` entries.

Live latest-open sweep: checked the latest 20 open issues at 2026-07-30T16:32Z; no equivalent found. The closest predecessor is closed #15805, whose accepted contract explicitly deferred Claude Desktop until this proof existed. The A2A in-flight sweep found no competing claim.

## The Problem

`src/ai/fleet/mcpServers.mjs:24-35` excludes `claude-desktop` from `REMOTE_HTTP_HARNESS_TYPES`. `ai/services/fleet/prepareManagedAgentWorkspace.mjs` owns the contained `claude_desktop_config.json`, but rejects every remote plan for that harness before hydration. `test/playwright/unit/ai/services/fleet/prepareManagedAgentWorkspace.spec.mjs` makes the refusal explicit.

As a result, #16167 cannot truthfully satisfy both of these properties for current Claude Desktop residents:

1. MC and KB are served only by the canonical container plane; and
2. the residents retain MC and KB tool access.

Keeping the full local MC/KB servers alive for one harness would preserve the second runtime. Exposing the loopback deployment publicly merely to use Claude's remote Connector plane would widen the security and deployment surface. A small generated transport adapter is the narrower boundary.

## The Architectural Reality

- `prepareManagedAgentWorkspace` is already the single Fleet author of Claude Desktop's Neo MCP entries and already owns local-to-remote transition receipts. Extend that path; do not add another config writer.
- The remote plan already limits HTTP projection to Memory Core and Knowledge Base. Neural Link and other machine-local servers stay local.
- `FleetLifecycleService` already resolves the selected plane credential and injects it into the child under `NEO_MCP_REMOTE_TOKEN`. The bridge must consume that inherited slot; raw credentials must not enter generated files, argv, receipts, logs, or public agent state.
- Claude Desktop's config grammar remains command-based. For this harness, remote MC/KB therefore render as a pinned stdio bridge command, not as an unsupported `{type:'http'}` entry.
- The bridge dependency is transition-independent runtime capability for a named current consumer. It remains only while Claude Desktop cannot directly consume the loopback HTTP plane through its managed artifact.

Owning folder/sibling precedent: `ai/services/fleet/prepareManagedAgentWorkspace.mjs` and its direct unit spec. `npm run --silent ai:structure-map -- --files --loc` confirms `ai/services/fleet/` is the existing workspace-projection owner; no new service folder or daemon is needed.

## The Fix

1. Add `claude-desktop` remote support only behind an exact bridge capability/admission proof.
2. Render remote MC/KB entries in `claude_desktop_config.json` as a mechanically pinned `mcp-remote` invocation targeting the two canonical HTTP resources. Never use an unpinned `@latest` or a floating runtime install.
3. Pass only the literal `NEO_MCP_REMOTE_TOKEN` reference in the authorization-header argument; the bridge resolves it from the inherited child environment. Keep Neural Link and any other enabled local server byte-for-byte in their local command shape.
4. Extend the existing transport convergence/receipt path so local → remote → local remains surgical, preserves operator-owned JSON keys, and leaves no remote residue on reversal.
5. Prove the generated bridge against an ephemeral Streamable-HTTP MC/KB fixture, then add one bounded live cutover witness: a Claude Desktop resident lists/calls MC and KB through the container endpoints while no resident MC/KB server child exists.
6. Add an explicit retirement trigger: remove this bridge projection when the managed Claude Desktop artifact can encode the same loopback HTTP + secret-reference contract directly.

## Decision Record impact

Aligned with ADR 0014: the wake and Neural Link host edges remain local. Depends on ADR 0019: resolved transport and credential inputs flow into the generator; the adapter does not re-read policy. No ADR amendment is required unless implementation changes either boundary.

## Acceptance Criteria

- [ ] Claude Desktop remote MC/KB admission is version/capability-gated before any workspace mutation.
- [ ] Generated MC/KB entries use a mechanically pinned `mcp-remote` bridge to the canonical `/mc/mcp` and `/kb/mcp` resources.
- [ ] Generated artifacts, argv, receipts, logs, and public state contain no raw plane credential; only the fixed environment-slot reference is present.
- [ ] Neural Link and every non-MC/KB local entry remain local and unchanged.
- [ ] Local → remote → local round-trip restores the prior MC/KB stdio projection, preserves unrelated operator keys, and removes the transition receipt.
- [ ] Missing bridge, wrong bridge version, missing credential, malformed endpoint, and divergent operator projection all fail closed before launch.
- [ ] An ephemeral HTTP fixture proves both generated MC and KB paths can list/call tools through the bridge.
- [ ] A bounded live witness proves one Claude Desktop resident consumes container MC/KB while no resident MC/KB server process is running.
- [ ] The docs name the retirement trigger for deleting the bridge projection.

## Out of Scope

- Claude's public remote Connector/OAuth product path.
- Exposing the same-machine loopback ingress publicly.
- Antigravity's distinct global/per-resident config-root problem.
- Changing MC/KB server implementations or authentication modes.
- The signed host wake dispatcher from #16180.
- Remoteizing Neural Link, GitHub Workflow, GitLab Workflow, or file-system MCP.

## Avoided Traps

- **Floating `npx` dependency:** `mcp-remote@latest` makes every seat boot consume an unreviewed moving target.
- **Secret in JSON or argv:** a working bridge that persists the bearer violates the existing Fleet credential boundary.
- **Direct-HTTP fiction:** Claude Desktop's managed JSON is command-based; render the bridge contract it actually consumes.
- **Broad Fleet redesign:** this is one adapter completion for named current residents, not a new transport framework.
- **Preserving local MC/KB by association:** the bridge retains protocol access without retaining the local servers.
