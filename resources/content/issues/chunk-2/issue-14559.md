# KB release artifact: binary (fp16) vector encoding to cut the JSON-float text tax (low-pri, before v13.2)

**Priority: LOW** — look into before the next release, not now. fp16 alone buys years and the GitHub cap is soft (below); no urgency.

## Context
v13.1.0's KB release artifact (`chroma-neo-knowledge-base.zip`, via `ai/scripts/maintenance/uploadKnowledgeBase.mjs`) hit **1009.91 MB** — 49,283 chunks, dim 4096. ~97% is embedding vectors serialized as **JSON-float TEXT**; the source conversations are only ~28 MB. Growth driver = chunk count (tickets + PR conversations, intense).

## Invariant (do not break)
The artifact ships raw vectors precisely so adopters never re-embed 49k×4k on boot. Any fix MUST preserve raw-vectors / no-re-embed. "Ship text, re-embed on download" is out.

## Lever — binary encoding (the waste is encoding, not vectors)
Verified arithmetic: fp32 binary uncompressed = **770 MB** (already < the current 1010 MB zip); fp16 = **385 MB**.
- **fp16 binary ≈ 2.6× smaller**, minor precision drift, no re-embed → the KISS win.
- fp32 ≈ 1.4×, lossless. **fp16-vs-fp32 is a recall-vs-size trade-off worth a quick measurement before committing.**
- Impl: export schema v1→v2 (packed/binary vectors), decode download-side, keep the `meta.json` drift-check.

## Secondary (defer)
- **Shard past 2 GiB** — GitHub allows 1000 assets/release, no total-size/bandwidth cap → sharding is a trivial runway; size never blocks. Safety net only.
- **Baseline scope** — the real growth lever: does the shipped KB need the whole ever-growing dev-conversation corpus, or durable knowledge + a separate conversation sync? Product decision.

Refs: `ai/config.mjs:372` (dim 4096), `uploadKnowledgeBase.mjs`, v13.1.0 cut. Analysis persisted; owner @neo-opus-grace.

### Reading this honestly — two things it does NOT say

1. **My 6.36× is not comparable to the ticket's 2.6×, and I am not claiming I beat the estimate.** The ticket compares fp16 binary against the **zipped** 1010 MB artifact; mine compares against **uncompressed** JSON text. Zip already recovers much of the float-text redundancy, so the shipped-artifact ratio stays the ticket's arithmetic (≈385 MB from fp16), not this table's. Different denominators.
2. **100% recall on a 2000-vector pool is easier than on 49,283.** Near-ties grow with corpus size, so degradation that cannot appear in a 4% slice may appear at full scale. My sample is also the **first** N records, i.e. a contiguous slice — likely correlated (adjacent chunks from the same documents) rather than a random draw.

**So the defensible claim:** fp16 quantisation is **lossless for retrieval at k=10 on a 4% contiguous sample of the real corpus** — the "minor precision drift" the ticket anticipated did not materialise at all, in either recall or top-1. That is strong evidence for fp16 over fp32, and it removes the reason to hedge toward the lossless-but-only-1.4× option.

**What would settle it fully** (cheap, and the right gate before implementing schema v1→v2): rerun over a **random** 10–20% sample of all 49,283 chunks at k=10 **and** k=50. If recall stays ≥99% at k=50 on a random draw, fp16 is settled and the remaining work is purely the export/decode schema. If it drops at k=50, the fp32 fallback is there and still buys 3.18× on the text tax.

Measurement script kept out of the repo deliberately — it is a decision probe, not substrate, and belongs in the PR that implements the schema if it earns a regression test.

**Unchanged premise, now confirmed from the artifact itself:** the KB backup JSONL is **2.8 GB** of `{"id":…,"embedding":[0.018881595,…]}` JSON-float text. The waste is the encoding, exactly as the ticket says.

## v2 Contract Ledger (RA4 from @neo-gpt-emmy's review of PR #15822)

The release-artifact format is a **consumed T3 surface** — an external adopter's `npm install` decodes it — but this ticket defined only the *lever* ("export schema v1→v2"), never the wire semantics. #12157's ledger covers collection-only export/import and never-clobber; it does not define version, sidecar, encoding, digest, row-set, byte order, or compatibility states. Recording them here, at the source of authority, so the contract outlives the PR that implemented it.

### Wire contract

| field | type | required | semantics | on mismatch |
|---|---|---|---|---|
| `artifactVersion` | Number | **yes** for v2 | Schema state. **Authoritative** — never inferred from sidecar presence. Absent ⇒ treated as 1. | unknown/newer ⇒ **abort** (no half-decode) |
| `vectorEncoding` | String | **yes** for v2 | `'fp16'` only | any other value ⇒ **abort** |
| `vectorDigest` | String | **yes** for v2 | FNV-1a over the newline-joined record-id sequence. The only proof of the row order that positional re-attachment assumes. | absent ⇒ **abort**; mismatch ⇒ **abort** |
| `byteOrder` | String | **yes** — never defaulted | Canonical wire order, always `little-endian`. `Float16Array` writes the **agent's** native order and Node ships a big-endian s390x build, so an absent stamp cannot be assumed to match the consumer's host. | **absent ⇒ abort**; any other value ⇒ **abort** |
| `dimension` · `recordCount` | Number | **yes** for v2 | Sidecar geometry; `recordCount × dimension × 2` must equal the sidecar's byte length exactly. | mismatch ⇒ **abort** |
| `embeddingProvider` | String | yes | Provenance for the recall-drift check | mismatch ⇒ **warn** (never abort — recall degrades, install must not break) |
| sidecar `kb-vectors-fp16.bin` | file | **yes** for v2 | Row-major packed fp16, one row per JSONL line, paired **by index** | missing under a v2 stamp ⇒ **abort** |
| KB `*.jsonl` | file | exactly **one** | The row-set the sidecar describes | 0 or ≥2 ⇒ **abort** (not a tie-break — a silent choice of pairing) |

### Compatibility states

| producer | consumer sees | outcome |
|---|---|---|
| v1 (no meta, no sidecar) | no meta, no sidecar | import unchanged (no-op) |
| v1 (meta, `artifactVersion` absent/1) | no sidecar | import unchanged (no-op) |
| v2 | full stamp + sidecar | re-attach, then import |
| v2 with sidecar lost | v2 stamp, no sidecar | **abort** — would otherwise import every record with no embedding |
| v1 stamp + stray sidecar | contradiction | **abort** |
| v3+ (future) | newer version | **abort** — upgrade, never guess |

### Invariants that are NOT negotiable

1. **Raw vectors ship; nobody re-embeds on boot.** fp16 is an encoding change, not a lossy-transport decision. Retiring this would invalidate the ticket's premise, not just an AC.

3. **The SDK export/import boundary keeps consuming v1-shaped JSONL.** v2 is post-processing on both ends; the SDK is not taught the format.
4. **Bounded memory.** Both paths must stream. The corpus is 5.62× Node's `MAX_STRING_LENGTH`, so any whole-file materialization is broken by construction and no small fixture reveals it.
