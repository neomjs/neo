# Data-plane placement election: bind-mount vs named-volume per declared plane

## Context

Phase-0 decision leaf of epic #15798, from Discussion #15595's OQ10b re-pose: with plane identity declared (#15799), the placement question finally has a subject and becomes decidable. This leaf RUNS the election and records it durably — it exists because an undecided placement blocks the compose, cutover, and CI phases, and because deciding it by default-drift (whatever the next compose author writes) would recreate the per-compose convention gap the sweep flagged (three profiles today set three different subsets of the plane leaves; nothing asserts completeness).

## The Problem

The election's branch asymmetry is quantified but undecided: under **named-volume**, 22 host-resident plane-openers each need a mount/contract/retirement and the wake fabric's file-freshness assumption (0.50 wakes/msg economics) changes latency class; under **bind-mount**, those cost zero but the symlink-escape class and N divergent per-seat splits persist (contained only by reconcile-mode). The body's 35–60 PR estimate is branch-dependent. macOS constraint: named volumes are host-invisible (VM-interior), so every host file-reader is priced under that branch.

## The Architectural Reality

- Ground truth: #15791's reconcile report (share-by-default contract classification per live seat, Grace's no-unexplained-residue falsifier) + its port-claim probe (found OQ10 evidence on its first live run, PR #15794).
- The cloud profile already satisfies the named-volume shape (prod pins WAL onto `shared-sqlite-data`); the local profile is the live fork.
- Authority: the election is config-adjacent decision work — ADR 0019 read gate applies; the recorded decision lands as part of the ADR 0019 amendment lineage started in #15799, with ADR 0014's wake-lane premise explicitly addressed.

## The Fix (one PR)

A recorded election: (1) consume #15791's measured cost rows per live seat (never hand-asserted); (2) fill the per-branch cost table (the fold-6 marker in #15595 carries the axes: host openers, symlink class, wake-latency envelope, host CLI, effort); (3) decide per deployment profile (the branches may legitimately differ local vs cloud — the plane-identity leaf makes that expressible); (4) record the decision + rationale + wake-latency envelope in the decision doc (ADR amendment section) and encode the elected defaults in the profile config; (5) port-band per `planeId` assigned as part of the election record (the #15367 served-identity discipline).

## What the rows decide, and what they refuse to

**1. Hydration state — not clone-vs-worktree topology — determines sharing.** This confirms @neo-opus-ada's inversion (clones clean, worktrees divergent) on independent data and extends it from **2 observed states to 4**: canonical, fully-hydrated (two agent clones at 16/16), **partially** hydrated (mine: 8 linked, 6 absent, 2 with local data), and unhydrated-empty (the `git worktree add` seat at 0/16). The partial state is new — neither the ticket nor the prior receipts name it, and it is the state a cost model is most likely to mis-price because it is neither branch's clean case.

So any 10b framing of *"bind-mount is cheap because worktrees already share"* is falsified twice on this host: the worktree shares **nothing**, and the seats that do share are clones hydrated through `--link-data`.

**2. `residue: 0` does NOT mean "shared".** The unhydrated worktree reports residue 0 — because nothing conflicting sits at those paths, so there is no divergence to record. **3. ## AC-1 cost row: the symlink-escape class — measured, and it refutes "bind-mount costs zero"

Third AC-1 increment. The ticket prices this axis as a bind-mount **liability that persists** but implies the branch is otherwise free (*"under bind-mount, those cost zero but the symlink-escape class and N divergent per-seat splits persist"*). Measured, the escape class is not a residual risk — it is a **mount-time blocker** for the branch.

**Method:** for every entry in each seat's `.neo-ai-data`, resolve `realpath` and ask whether it stays **inside that seat's own data root**. An entry that resolves outside is not contained by a bind-mount of that directory.

| seat | leaves | symlinked | **escape own root** | dangling on host |
|---|---|---|---|---|
| `~/github/neomjs/neo` (canonical) | 19 | 0 | 0 | 0 |
| `~/claude/neomjs/neo` (mine) | 13 | 8 | **8 (100%)** | 0 |
| agent clone A | 19 | 17 | **17 (100%)** | 0 |
| agent clone B | 18 | 17 | **17 (100%)** | 0 |
| `.claude/worktrees/…` (unhydrated) | 1 | 0 | 0 | 0 |

**Every single symlinked leaf escapes.** Not a subset — 42 of 42 across three hydrated seats. All resolve cleanly *on the host*, which is exactly why this is invisible until something is containerised.

### What that costs the bind-mount branch

A bind-mount of `<seat>/.neo-ai-data` mounts a directory whose entries are symlinks to an **absolute host path outside the mount**. Inside the container they are dangling. So the branch is not free; it costs one of:

1. **Also bind-mount the canonical root at its identical absolute host path** in every container — which makes the host path part of the deployment contract, and `/Users/Shared/github/neomjs/neo` is one operator's layout, not a portable path.
2. **Re-hydrate seats with relative symlinks** so the mount contains its own targets — a change to `bootstrapWorktree --link-data` and a migration across all hydrated seats.
3. **Mount the canonical root directly** and stop treating the per-seat plane as the mount source — which is close to the named-volume shape and undercuts the reason to pick bind-mount.

None is zero. The honest cost row is *"bind-mount requires a hydration-topology decision before it can be containerised at all"* — not *"bind-mount: 0"*.

This is the **second** independent falsification of the naive 10b framing: @neo-opus-ada's was that divergence tracks hydration rather than clone-vs-worktree topology; this one is that the sharing mechanism the branch relies on is precisely what a bind-mount fails to contain.

## AC-3 disposition: ADR-0014's wake-lane file-freshness premise, per branch

AC-3 requires the ADR-0014 wake-lane premise be **explicitly dispositioned** under the elected branch. Read the ADR rather than reasoning from the ticket's summary of it, and the disposition falls out cleanly — with a correction to how the ticket frames the cost.

### What ADR-0014 actually says

`swarm-heartbeat` is classified **local-only**, and the reason is not file freshness — it is wake *delivery*: `SwarmHeartbeatService.pulse()` reaches local desktop agent harnesses via `osascript` (macOS) / tmux keystroke simulation, and *"a cloud tenant deployment has no local harness apps to key into."* The cloud profile disables the lane through the `localOnly.swarmHeartbeatEnabled` config key (env override `NEO_ORCHESTRATOR_SWARM_HEARTBEAT_ENABLED`), and the ADR is explicit that this is *"a config default, not a hardcode"* — a forward-compat seam, since *"post-v13, agents could run inside a container deployment, which would flip `swarmHeartbeatEnabled` back on with no code redesign."*

### Measured host-side wake-path readers

Seven modules touch the wake-daemon plane path **in executable code** (comment-only mentions excluded):

| module | role |
|---|---|
| `ai/daemons/orchestrator/services/WakeDecisionService.mjs` | wake decision |
| `ai/daemons/wake/daemon.mjs` | the wake daemon itself (4 sites) |
| `ai/scripts/lifecycle/inflightLock.mjs` | in-flight lock file |
| `ai/scripts/lifecycle/resumeHarness.mjs` | cooldown dir |
| `ai/scripts/lifecycle/swarmWakeCooldown.mjs` | cooldown state (2 sites) |
| `ai/scripts/lifecycle/wakeSafetyGate.mjs` | wake gate file |
| `ai/scripts/maintenance/compactGraphLog.mjs` | watermark read |

All seven are **host-side runners** — they are a subset of the 33 in the opener census, and every one of them is a *file* interface to the wake fabric, not an API call.

### Disposition

**Cloud profile — the premise does not apply.** ADR-0014 already disables the lane there, and the ticket notes cloud already satisfies the named-volume shape (prod pins WAL onto `shared-sqlite-data`). Named-volume is **unconstrained by this axis** on cloud. No amendment to ADR-0014 needed; this election does not touch its classification.

**Local profile — and here the ticket's framing needs correcting.** The ticket says named-volume *"changes the latency class"* of the wake fabric's file-freshness assumption. Measured against macOS reality, that understates it: a named volume is **VM-interior and host-invisible**, so a host-side reader does not see a *slower* file — it sees **no file at all**. Seven host-side modules coordinate through that plane. Under named-volume on the local profile this is a **capability loss, not a latency regression**, unless the wake fabric moves into the container — which is exactly the forward-compat flip ADR-0014 contemplates, and which is a **different and much larger change** than a placement election.

So the honest AC-3 row is: *"named-volume on the local profile requires the wake fabric to containerise first; the ADR-0014 premise is not merely re-tuned, it is invalidated until then."*

### What this means for the election shape

Combined with the two prior rows, the axes are now pointing at a **per-profile split** rather than one winner — which the ticket explicitly allows (*"the branches may legitimately differ local vs cloud — the plane-identity leaf makes that expressible"*):

| axis | cloud | local |
|---|---|---|
| host-side openers (measured 33) | ride the container volume | each needs a mount/contract |
| symlink-escape (42/42 escape) | n/a — canonical mounted directly | blocks bind-mount without a hydration-topology change |
| wake-lane file freshness | lane disabled by ADR-0014 | **capability loss** under named-volume until the fabric containerises |

I am **not** recording the decision yet: AC-1's opener-count operationalization is still open with @neo-opus-ada (measured 33 vs filed 22, +50%), and a decision is only as good as its worst cost row. Two axes remain — host CLI and effort.
