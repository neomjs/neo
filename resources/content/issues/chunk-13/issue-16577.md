# A successful materialization is rejected: producer and consumer digest different snapshot shapes

## ⚠️ CORRECTED 2026-08-06 — the premise of this ticket was wrong, and the news is good

**Tenant ingestion works.** `create-app` is in the Knowledge Base right now: **50 chunks, embedded**, queryable. The original framing here — *"an empty first materialization"* — described a failure that never happened.

The diagnostic from #16580 produced the inversion in one line:

```
07:50:51 [INFO]  neo-shared/create-app materialized: envelopeFiles=50 envelopeDeleted=0
                 ingested=50 deleted=0 embeddings=50 errors=0
07:50:51 [ERROR] neo-shared/create-app failed: KB_TENANT_REPO_SYNC_EMPTY_MATERIALIZATION
                 ("Tenant-repo full materialization produced no durable positive-effect proof.")
```

Confirmed in the corpus:

```
neo-knowledge-base total : 17600
  repoSlug=create-app    : 50
  repoSlug=neo           : 17550
```

**A completely successful materialization is being reported as an empty one.** 50 files matched, 50 ingested, 50 embeddings, zero errors — then rejected.

### What is falsified

- **The empty-materialization premise.** Nothing was empty.
- **The source-config hypothesis** (`useDefaultSources` / `rawRepoSource` / `sourcePaths`) that this ticket carried as its leading candidate. The envelope had 50 files. Source matching was never the problem.
- **The "first sync can never earn a receipt" reasoning.** The receipt path runs; it produces a receipt that fails to *validate*.

## The actual defect: two digests over differently-shaped inputs

`assertFullMaterializationEffect` (`TenantRepoSyncService.mjs:294-317`) throws on `(hasEffect && !provesCurrentAttempt)`. With `ingested=50`, `hasEffect` is **true** — so the throw is the *receipt* arm, not the effect arm. The message says "no durable positive-effect proof": the **effect** is real, the **proof** does not validate. That reads as the exact opposite of what occurred.

Both sides compute an envelope digest, over different inputs:

| side | call | `manifestSnapshot` passed |
|---|---|---|
| **producer** — `IngestionService.persistManifestSnapshot:978` | `createTenantRepoMaterializationDigest({repoSlug: normalized.repoSlug, headRevision, manifestSnapshot: normalized, files})` | **`normalized`** |
| **consumer** — `TenantRepoSyncService:300` | `createTenantRepoMaterializationDigest(envelope)` | **`envelope.manifestSnapshot`** (raw) |

`normalizeManifestSnapshot` (`IngestionService.mjs:1086`) does not pass the snapshot through — it rebuilds it, running `pathsAfterPush` through `normalizeManifestPaths`, documented as *"a stable unique string set"*: **sorted and deduplicated**. The digest hashes `manifestSnapshot.pathsAfterPush` directly.

So whenever a repo's tracked paths are not already in sorted-unique order, the two digests differ, `isMatchingMaterializationReceipt` returns false, `provesCurrentAttempt` is false, and a fully successful ingest is discarded.

**Consequence:** the checkpoint never commits, `lastIngestedRev` stays `null`, and the lane re-ingests the same content every cycle — succeeding each time and being told it failed. The corpus grows correct while the state machine believes nothing happened.

Confidence: the input asymmetry is **read directly from source** and is not in question. That it is the *sole* cause is inferred from `hasEffect` being provably true; a digest-equality probe on the live envelope would settle it outright and is the first task.

## Revised acceptance criteria

- [ ] **Prove the digest mismatch** — compute both digests for one live `create-app` envelope and diff them. If they match, the receipt fails for another reason and this AC set is re-derived before any fix.
- [ ] One digest input shape, not two. Either both sides normalize, or the producer records the digest it actually used and the consumer compares against that recorded value rather than recomputing.
- [ ] A successful materialization commits its checkpoint: `lastIngestedRev` non-null, lane reports `completed`, and the next sweep is a no-op diff rather than a full re-ingest.
- [ ] `KB_TENANT_REPO_SYNC_EMPTY_MATERIALIZATION` is only raised when the materialization was genuinely empty. A receipt-validation failure gets its own code — the current message actively misleads.
- [ ] Regression spec: an ingest whose `pathsAfterPush` arrive unsorted or with duplicates still validates its receipt.
- [ ] Re-check the sibling: `neo-shared/neo` shows 17,550 chunks and also fails to complete. Confirm whether it is the same digest defect or a second cause.

## Still true, still out of scope

The self-perpetuation observation stands and is *worsened* by this finding: because the checkpoint never commits, the repo never records a `lastCommittedMaterializationAttemptId`, so the `provesUncommittedRetry` escape can never engage either. Both arms of the guard are unreachable — but the fix is the digest, not the disposition. **This ticket is no longer about backoff disposition.**

## ROOT CAUSE FOUND — and it is not in either service

The digest-mismatch diagnosis in the body above is **falsified**. Both digests match; the digest normalizes `pathsAfterPush` internally. Correcting it here rather than editing the body, so the reasoning trail survives.

### The cause

`ai/services.mjs:139` parses every Knowledge Base service call through a Zod schema built from the OpenAPI contract:

```js
const parsedArgs = zodSchema.parse(args || {});   // Zod DROPS undeclared keys, silently
```

`ingestSourceFiles` documents `materializationAttempt` and `viaMcp` as params, and its in-process callers pass both. **Neither was declared in any spec.** Both were deleted from the payload before the method ran — no error, no log, no summary entry.

Measured in the running orchestrator against the real `create-app` envelope:

```
attempt sent in payload : {"attemptId":"a7a07f76601f638c0af6286dfcaaa85d","ingestContractVersion":2}
producer received       : materializationAttempt: undefined
                          manifestSnapshot: present paths=50
                          summary.ingested: 50   summary.errors: 0
```

`manifestSnapshot` **is** declared, so it survives. That asymmetry is the entire signature: the manifest persists with 50 correct paths while the receipt never appears.

### One cause, both repos, two symptoms

- **create-app** — attempt stripped → `attempt` is null → the receipt block never runs → a successful materialization persists no proof → `EMPTY_MATERIALIZATION`.
- **neo** — `viaMcp` stripped → `payload.viaMcp !== false` re-reads as `true` → `VectorService.mjs:1098` (`if (viaMcp && workVolume > mcpThreshold)`) throws → `KB_VECTOR_EMBED_FAILED`. `create-app` sits at exactly the 50-chunk `mcpSyncMaxChunks` default and slips under; `neo` at 24,590 does not.

AC-6 asked whether the sibling repo was the same defect or a second cause. **Answer: same cause, different symptom** — the two params were dropped by the same mechanism.

Corroborating: **no receipt has ever existed** in this deployment — zero across every graph node and the full `GraphLog`. The feature has never once produced its proof since it landed in #16047.

### What this retires

- **AC-1 / AC-2** (prove the digest mismatch; unify the digest input shape) — void. The digests were never the problem; there is nothing to unify.
- **AC-5** (regression spec for unsorted/duplicate `pathsAfterPush`) — void for the same reason.
- **AC-3** (a successful materialization commits its checkpoint) — stands, and is the post-merge proof.
- **AC-4** (`EMPTY_MATERIALIZATION` only when genuinely empty) — stands as a **separate** concern. The message still reads as the opposite of what happened whenever a receipt fails to validate for any reason. Not fixed by the contract change; worth its own narrow ticket rather than widening this one.
- **AC-6** — answered above.

### Fix

PR #16583 — two properties declared on `IngestSourceFilesRequest`, no code change. Declaring them cannot widen the agent surface: the MCP push path already deletes `materializationAttempt` inbound and `materializationReceipt` outbound, and forces `viaMcp: true`.

RED-proven regression spec, and verified end-to-end against the live orchestrator with both write points stubbed — receipt minted, `attemptId` matches the attempt sent.

### The lesson worth keeping

Three hypotheses died here (digest, ordering, early-return) and all three were guesses at *which branch inside the producer* skipped receipt creation. They were unfalsifiable-by-reading because the branch was selected by an input that had already been deleted one layer up. Reading the producer could never have found it; measuring what the producer *received* found it in one call.

**The defect class has no mechanical guard.** Any service param added without a matching spec property is silently stripped — two live instances in one contract, one undetected since #16047. Filing the parity check (service JSDoc `@param payload.X` vs declared properties) separately.
