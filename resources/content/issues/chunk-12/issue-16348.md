# A backup that captured nothing must not report success

## Context

Operator direction 2026-08-02, after a live incident. Two bundles produced today prove the same defect from opposite ends, and the second one blocked the deploy guard until I removed it by hand.

Live latest-open sweep 2026-08-02T12:31:54Z. Neighbours checked: `#15641` (CLOSED — built the off-host sync hook), `#16055` (CLOSED — the survivability incident), `#16208` (Chroma persist path). None owns the success/failure verdict of a capture.

## The Problem

**The backup lane can write a bundle that captured nothing and record it as a success.**

Specimen 1 — `backup-2026-07-31T04-57-18.233Z`, 64K, still on disk:

```json
"mc": { "message": "Export complete. Exported 0 memories, 0 summaries, 0 temporal summaries", "count": 0,
        "memories": { "backupFile": null, "expected": 0, "exported": 0 } }
"kb": { "message": "Export complete. Exported 0 knowledge base chunks.", "count": 0 }
```

It ran mid-cutover while the Chroma re-embed was still in flight, found an empty plane, and reported **`"Export complete."`** The subsystem contract has no way to say *"the source was unavailable"* — `expected: 0, exported: 0` is byte-identical to a genuinely empty corpus, so a dependency outage and a legitimately empty plane produce the same receipt.

Specimen 2 — `backup-2026-08-02T05-12-55.917Z`, deleted 12:30Z under operator authorization:

```
7 empty directories + kb/knowledge-base-backup-…jsonl  (0 bytes)   NO bundle-meta.json
directory mtime 05-12-55.917Z   file mtime 05-12-55.930Z    (13 ms apart)
```

The orchestrator was crash-looping (325 restarts, deadlocked on its own authority lease — see `#16230` / `#16242`). The lane opened the KB output stream and died before the first byte. It left a bundle-shaped directory behind.

**Both then compound with newest-only selection.** `verifyLatestBackupRestorable` (`ai/scripts/maintenance/restore.mjs:750-760`) sorts bundle names reverse-lexically and inspects **only `bundleNames[0]`**. Specimen 2 was the newest, so the guard reported no verified bundle while a complete 5.0 GB bundle sat directly beside it:

```
before  →  (guard blocked by the 0-byte artifact)
after   →  restorable: true   code: RESTORABLE   rowTotal: 94325
           bundleRoot: backup-2026-08-01T12-13-23.398Z
```

One aborted run made 94,325 recoverable rows invisible, and the repair was `rm -rf` on a directory.

## The Architectural Reality

- `ai/scripts/maintenance/backup.mjs` — writes per-subsystem receipts into `bundle-meta.json`. The receipt records what was exported; it does not record what *should* have been exportable, so shortfall is unrepresentable.
- `ai/scripts/maintenance/restore.mjs` — `verifyLatestBackupRestorable` already rejects a zero-row bundle with `BUNDLE_EMPTY`, and its comment names this exact incident class. **That guard is correct and is not the gap.** It runs at *restore/preflight* time; nothing applies the same standard at *capture* time, and nothing looks past the newest bundle.
- `backup` is a priority-zero orchestrator lane (`ai/daemons/orchestrator/scheduling/pipeline.mjs:13`), cadence `backupMs = DAY_MS`. A failed run therefore costs a full day by default.

## The Fix

*(Prescription — the operator named several viable options; this ticket should choose one deliberately, not fold them together.)*

**A capture that cannot reach its sources is a failure, not an empty success.** Options, with trade-offs:

1. **Refuse to finalize.** If a subsystem's source is unreachable, do not write a bundle directory at all. Cleanest invariant — every directory under the backup root is then a real attempt — but it discards partial captures that might still have value.
2. **Wait for the dependency, then proceed.** Chroma down ⇒ block and retry within the run. Keeps the daily slot, but an unbounded wait inside a priority-zero lane is its own hazard and needs a cap.
3. **Raise scheduler priority and re-try.** Record the failure, promote the lane so the next attempt is soon rather than in `DAY_MS`. Best fit for the crash-loop specimen, where the dependency was fine and the *process* died.
4. **Mark the bundle failed and keep it.** Write `bundle-meta.json` with an explicit failure verdict so the artifact is self-describing rather than merely thin.

Option 3 plus the failure receipt from 4 is my read — a lane that dies should not surrender its daily slot, and a bundle that failed should say so rather than be inferred from its size. But 1 has the cleanest invariant and the choice belongs in this ticket.

**Independent of which is chosen:** selection must fall back past an unusable newest bundle to the newest *valid* one, or a single bad run keeps hiding good history.

## Acceptance Criteria

- [ ] A capture whose source is unreachable does not produce an artifact that reads as a successful backup.
- [ ] `expected` vs `exported` can express shortfall — an unreachable source is distinguishable from a legitimately empty corpus in the receipt.
- [ ] A run that dies mid-write leaves either nothing or a self-describing failed artifact; never a bundle-shaped directory with no `bundle-meta.json`.
- [ ] Restorability selection falls back to the newest **valid** bundle rather than stopping at the newest. A spec covers: valid bundle + newer invalid bundle ⇒ `RESTORABLE` against the valid one.
- [ ] A failed run does not silently forfeit its cadence slot — retry policy is explicit and bounded.
- [ ] Spec coverage for both live specimens: source-unreachable (zero rows exported) and abort-mid-write (no meta).
- [ ] Post-merge: with a deliberately unreachable Chroma, the lane reports failure and the previous good bundle remains the verified one.

## Out of Scope

## Avoided Traps

- **Treating the guard as the defect.** `verifyLatestBackupRestorable` correctly rejects zero-row bundles and its comment already names this incident class. The gap is that capture applies no equivalent standard, and that selection stops at the newest.
- **Reading "Export complete" as a lie.** It is not — it accurately reports that the export finished. The contract simply cannot express *"finished having found nothing because the source was gone."*
- **Fixing this by deleting bad bundles.** That is what I did by hand today, under operator authorization, to unblock the guard. It restored `rowTotal: 94325` in seconds — which is precisely why it must not be the standing remedy.

## The contract shape, posted before implementing as promised

Two source-level mechanisms, both found by reading rather than inferring from the specimens.

### Mechanism 1 — the conflation is in code, not just in prose

`ai/scripts/maintenance/backup.mjs:227`:

```js
const countOf = value => typeof value === 'number' ? value : value?.count ?? value?.exported ?? 0;
```

**`?? 0` is where "unavailable" becomes "empty".** A subsystem that returned no count at all — because it could not be reached — is folded into the same `0` as a subsystem that was reached and genuinely held nothing. By the time `buildEmbeddingContract` writes the receipt the distinction is already destroyed, so no downstream reader can recover it. The ticket's `expected: 0, exported: 0` is the *symptom*; this line is the cause.

### Mechanism 2 — a missing receipt is a warning, not a failure

`ai/scripts/maintenance/restore.mjs:59`: *"Bundles without `bundle-meta.json` skip this check with a console warning."*

So specimen 2 (aborted before the receipt) does not fail verification — it **skips** it. Combined with newest-only selection, a bundle that never got far enough to describe itself is treated as unverifiable-but-acceptable rather than unusable.

### The shape

**1. A capture outcome is a verdict, not a number.** Each subsystem receipt carries an explicit outcome alongside its count:

- `captured` — the source was reached and returned rows
- `empty` — the source was reached and genuinely held nothing
- `unavailable` — the source could not be reached

`empty` and `unavailable` are both `count: 0` and must never again be inferred from that. **Absence of a count means `unavailable`** — the `?? 0` default is deleted, not re-defaulted, because a default is exactly what erased the distinction.

**2. A bundle's restorability is the conjunction of its subsystem verdicts.** Any `unavailable` makes the bundle non-restorable and says which subsystem. A bundle of all-`empty` is restorable and honest — that is a real state, just not a useful one.

**3. A missing `bundle-meta.json` is `unavailable`, not "skip".** A bundle that cannot describe itself cannot be verified, and unverified is not a pass. This is the specimen-2 repair and it is one branch.

**4. Selection consumes the verdict.** `verifyLatestBackupRestorable` already sorts reverse-lexically and inspects `bundleNames[0]`. It keeps doing that — but a non-restorable newest bundle no longer ends the search. **Deliberately NOT a fallback that hides the problem:** it reports the newest restorable bundle *and* names every non-restorable one it passed over, so `rm -rf` is never the repair again.

### What this does and does not fix

**Repairs the 7 already on disk** — they become classifiable rather than indistinguishable. It cannot retroactively tell which of the 4 zero-capture bundles were `empty` versus `unavailable`; that information was destroyed at write time. They will classify as `unavailable` (absent verdict ⇒ unavailable), which is the safe reading and may over-condemn a genuinely-empty bundle. **Stating that rather than pretending the migration is lossless.**

**Does not address why the sources were unreachable** on four separate dates. That is a different question and I am not folding it in.

### Falsifier

A stub subsystem that throws on read must produce `unavailable` and a non-restorable bundle, while a stub that returns zero rows must produce `empty` and a restorable one — **both asserted, because either alone passes against a contract that answers only one way.** Plus a fixture control that the `unavailable` specimen genuinely lacks a count rather than carrying `0`, since a hand-built fixture usually fails to produce the real specimen.

Proceeding to implement unless someone reads this differently — @neo-opus-grace especially, since the incident was yours.

### The shape

**Do not change the resolvers.** Their auto-create is load-bearing for first-run bootstrap, and it is shared by every reader in the system — not just backup. Changing it to serve the backup lane would put the hot path of the vector store at risk for a reporting improvement. That is the wrong trade.

**Probe pre-existence in the export path instead**, before resolution can create anything:

- Both managers expose `this.client`; `listCollections` already has a caller (`knowledge-base/ChromaManager.mjs:337`) and never creates, and `getCollection` throws not-found without creating. So the export can ask *"did this collection exist before I touched it?"* with one non-mutating call.

- `verifyBundleIntegrity` maps `unavailable` to its own status instead of folding it into `empty`. It **already** separates `empty` from `pass` and persists that into both `bundle-meta.integrity` and the receipt — that machinery exists and works, which is one of the things I got wrong the first time.

**A race exists and I am naming it rather than hiding it:** another process could create the collection between probe and export. The window is small and the failure is benign — a concurrently-created collection *was* absent when the backup started, which is exactly what the verdict says.

### What this deliberately does NOT do

- **It does not fail the bundle.** `runBackup` throws on integrity `fail` and writes `bundle-meta.json` *after* the integrity check — so routing `unavailable` through `fail` would produce a bundle-shaped directory with no receipt, manufacturing the specimen-2 class this ticket exists to eliminate. - **It does not retroactively classify the 7 unusable bundles already on disk.** That information was destroyed at write time and cannot be recovered. Stating that rather than implying the migration is lossless.
- **It does not address why the sources were unreachable** on four separate dates. Different question, not folded in.

A stub collection that does not pre-exist must produce `unavailable` with a non-restorable-flagged receipt, while a stub that pre-exists and returns zero rows must produce `empty` — **both asserted, because either alone passes against a contract that answers only one way.** Plus a fixture control that the `unavailable` specimen genuinely lacks a pre-existing collection rather than carrying a hand-set flag, and a positive control that a populated collection still reports `captured`.

The lesson from the last two rounds applies directly here: the probe must enter **upstream of the resolver**, because a test that injects below it cannot see the very conversion that causes the defect.
