# ai/deploy has no composable layering: the base compose cannot boot, and no configuration can prove the plane before it owns the data

## Context

Surfaced empirically on 2026-07-31 while standing up a containerized MC + KB to prove the #16167 endpoint before the data move. Getting a working local, isolated, authenticated, loopback-exposed plane required hand-writing a **seventh** compose file in a scratchpad. That hand-written override is the finding, not the fix.

The endpoint proof itself succeeded — `initialize` → 200, `tools/list` → 42 tools on `/mc/mcp` and 13 on `/kb/mcp` through `127.0.0.1:3102` with GitHub-PAT bearer auth. The friction is that reaching that state was not expressible in `ai/deploy` as it stands.

Live latest-open sweep at 2026-07-31T00:55Z: no open issue covers compose layering, base bootability, or an isolated proof plane.

## The Problem

**1. The base compose cannot boot the servers it defines.**

`ai/deploy/docker-compose.yml` sets `NEO_AUTH_MODE` **zero** times. It mentions the variable in two comments (`:95`, `:179`) and never assigns it. `AuthService` fails closed on the Streamable HTTP transport with no auth installer, so `kb-server` and `mc-server` exit 1:

```
Error: AuthService: no Streamable HTTP authentication installer is configured;
configure an OIDC endpoint, a built-in auth.mode, custom authMiddleware, or trusted-proxy identity
    at AuthService.setup (ai/mcp/server/shared/services/AuthService.mjs:125)
```

Observed, not inferred: base + an override touching only `image:` and the ingress port produced exactly this on both services. Fail-closed is the correct *server* behaviour; the defect is that the canonical topology file ships a non-bootable default while owning all 7 named volumes.

**2. Auth is re-decided per overlay instead of being a fragment.**

Counting real key assignments (`^\s*NEO_AUTH_MODE:`), with the comment-only base as the positive control:

| File | auth mode set | loopback 3102 | live-plane bind | docker.sock | named volumes |
|---|---|---|---|---|---|
| `docker-compose.yml` | **0** | – | – | 1 | **7** |
| `docker-compose.dev.yml` | `github-pat` | – | – | 1 | – |
| `docker-compose.local-agent-os.yml` | `github-pat` | ✓ | 2 | 2 | – |
| `docker-compose.parity-capture.yml` | `github-pat` ×2 | – | – | – | – |
| `docker-compose.parity-ci.yml` | `local-bearer` | – | – | – | – |
| `docker-compose.test.yml` | 0 | – | – | – | – |

Five overlays, four independent auth decisions, one of them stated twice. There is no auth fragment to compose.

**3. No configuration can prove the plane before it owns the data — the load-bearing item.**

`docker-compose.local-agent-os.yml` welds four orthogonal concerns into one file: the auth profile, the loopback `:3102` ingress, a bind of the live repo-root `.neo-ai-data`, and `/var/run/docker.sock`. You cannot take the loopback ingress without also taking the live plane.

The consequence shows up in the cutover runbook: `ai/scripts/lifecycle/local-agent-os/README.md` §5 ("Prove the replacement before resident release") runs **after** §3 has already `mv`'d the canonical plane. The only configuration that exposes a testable endpoint is the one that already owns production data, so the proof necessarily follows the irreversible step. On a machine holding ~94k memory rows that ordering is the wrong way round, and it is a property of the compose layout rather than of the runbook's author.

**4. `/var/run/docker.sock` hardcoding — premise CORRECTED to documentation-only.**

> **Corrected 2026-07-31** ([comment](https://github.com/neomjs/neo/issues/16206#issuecomment-5138712060), confirmed by @neo-gpt-emmy's independent container-plane evidence): the compose volume path resolves inside the **Colima VM**, where dockerd runs and `/var/run/docker.sock` exists — not on the macOS host. The orchestrator service **does start as written under Colima**; the live local-agent-os orchestrator container runs with the stock mount. The original "cannot start as written" claim was a host-path intuition applied to a VM-path contract.

The *residual* is real but documentation-only: a host-shell `ls /var/run/docker.sock` fails while the mount works, which is exactly the misread that cost a diagnosis round ("the Docker engine is down" — the engine was up, `docker info` → `29.2.1`, context `colima`). The VM-vs-host path distinction belongs in the `ai/deploy` README.

**5. Nothing tests bootability.**

`test/playwright/unit/ai/deploy/ParityPlaneVolumeScoping.spec.mjs` gives `ai/deploy` coverage, but it asserts volume-scoping *shape*. A YAML-shape assertion cannot catch "this configuration cannot start" — which is why a non-bootable base survives a green suite.

## The Architectural Reality

- The concerns genuinely factor into four independent axes: **auth mode**, **ingress exposure**, **data plane**, **host integration**. Every existing file picks one point in that space and hardcodes it, so any unrepresented combination requires a new file. Six files today; the seventh was written tonight in a scratchpad; a contributor needing "isolated + public ingress" writes the eighth.
- The base already models the isolated data plane correctly — 7 named volumes, no repo-root bind. That half is right and reusable; it is the auth and exposure axes that have no fragments.
- `Caddyfile.local-agent-os` (loopback `:8080`, `/mc/*` → `mc-server:3001`, `/kb/*` → `kb-server:3000`) is already a clean standalone artifact and needs no change — evidence that the ingress axis separates cleanly.

The fragment-decomposition proposal below is preserved as analysis and proceeds only if still needed after the canonical relaunch — it must not compete with the compliance map's repair sequence.

Deferred decomposition sketch (post-relaunch material only):

1. **Make the base bootable or explicitly abstract.** Either ship a safe default auth mode, or fail with a directed error naming which fragment to add — not a stack trace from `AuthService`.
2. **Extract auth fragments** (`github-pat`, `local-bearer`, OIDC, trusted-proxy) so no overlay re-states a mode.
3. **Extract ingress fragments**: loopback (`127.0.0.1:3102`) and public (`443`).
4. **Extract data-plane fragments**: isolated named volumes, and canonical host bind.
5. ~~**Derive the Docker socket** from the active context, or move it to a `host-docker` fragment, so Colima and Docker Desktop both work.~~ **Corrected 2026-07-31 — documentation-only:** the stock mount already works under both (in-VM path); document the VM-vs-host distinction in the `ai/deploy` README instead of changing code or compose.

7. **Reorder the runbook's proof** once an isolated composition exists: prove on named volumes, then swap one fragment to adopt the real plane. `base + auth + ingress-loopback + plane-volumes` is exactly the stack that worked tonight.

## Additional defect for this ticket: the compose files leak a HOST loopback URL into containers

Found 2026-07-31 during the #16167 cutover, after this ticket was filed. It belongs here rather than in its own leaf because it is the same class as the hardcoded `/var/run/docker.sock` — a host assumption embedded in a file that also ships to cloud.

**The mechanism.** Three services pass the embedding host straight through:

```yaml
# ai/deploy/docker-compose.yml:69, :163, :213
- NEO_OPENAI_COMPATIBLE_HOST=${NEO_OPENAI_COMPATIBLE_HOST:-}
```

Compose interpolates from whatever shell it runs in. On a developer machine running LM Studio, that shell exports:

```sh
# ~/.zshenv:75
export NEO_OPENAI_COMPATIBLE_HOST="http://127.0.0.1:1234"
```

So **every `docker compose up` injects a host loopback URL into three containers**, where `127.0.0.1` means the container itself. Verified from inside a running container:

```
container -> http://127.0.0.1:1234              fetch failed
container -> http://host.docker.internal:1234   200
```

**Why it is nastier than a missing default.** The variable is *set*, and every surface you would check looks correct in isolation: `.zshenv` is right for host-side servers, the compose line is right for a cloud deployment where the provider is a service, and line 333 even documents the in-cluster form (`http://local-model:11434`). Only the *combination* — one machine running both host servers and containers — is wrong, and nothing guards it. Nobody hit it before because until this cutover nothing on that machine ran Memory Core in a container.

**Why it matters more than a failed request.** Memory Core gates **every** semantic operation behind an embedding write canary. One unreachable provider therefore presents as `status: degraded` plus `collections.count: 0` and a flat refusal of `query_raw_memories` — which reads as "the vector store is empty," not "the provider is unreachable." It sent this session down a multi-probe investigation of Chroma databases and collection ids before the actual cause surfaced.

**Status: unresolved in the repository.** The running stack was corrected by hardcoding `host.docker.internal` in an **untracked local override**, which is invisible to the repo, to CI, and to anyone else provisioning this topology. That is a workaround for one machine, not a fix, and recording it here so it is not mistaken for one.

**What the fix owes.** Whatever fragment ends up owning host integration (the `host.docker.internal` / socket / host-service axis in this ticket's decomposition) should own this too. The requirement is that a container never inherits a loopback URL that only makes sense on the host — either by not passing the variable through, or by resolving it to the container-appropriate form, or by failing loudly when a container receives a loopback provider address. Silent inheritance is the defect.

**Suggested acceptance criterion for this ticket:** starting the local composition with a loopback `NEO_OPENAI_COMPATIBLE_HOST` exported in the invoking shell must NOT produce a container that resolves it as-is. Assert by inspecting the resolved container environment after `up`, not by reading the compose file — the compose file looks correct, which is exactly why this survived.

## Correction: the `/var/run/docker.sock` bind is NOT broken under Colima — two of us mis-diagnosed it

Recording this because it cost roughly six hours of the #16167 cutover and it is a reasoning error about *where a path is resolved*, which belongs in this ticket's host-assumption discussion.

**What we both claimed.** @neo-gpt read a missing `/var/run/docker.sock` as "the Docker engine is down." I corrected that (the engine is up — context `colima`, server `29.2.1`) but then made an adjacent error of my own: I claimed the overlay's bind

```yaml
- type: bind
  source: /var/run/docker.sock
  target: /var/run/docker.sock
  bind:
    create_host_path: false
```

could not resolve under Colima, and reported the `orchestrator` service as unstartable for the rest of the session. That claim was repeated in this ticket's original body and in #16208.

**Why it is wrong.** Bind-mount sources are resolved by the **Docker daemon**, which under Colima runs *inside the VM* — not on macOS. Verified:

```
$ ls -l /var/run/docker.sock                 # macOS
ls: /var/run/docker.sock: No such file or directory

$ colima ssh -- ls -l /var/run/docker.sock   # inside the VM, where dockerd runs
srw-rw---- 1 root docker 0 Jul 31 01:06 /var/run/docker.sock
```

Started with the tracked overlay's original bind, the orchestrator comes up healthy:

```
neo-local-agent-os-orchestrator-1   Up (healthy)
[Orchestrator] Started. authorityProfile=container-plane ...
```

**The instructive part.** I also tried the "obvious fix" first — binding Colima's macOS-side socket at `~/.colima/default/docker.sock` — and it fails with `invalid mount config for type "bind": stat ...: operation not supported`, because a unix socket cannot be passed through virtiofs. That error is a *second* confirmation that the daemon resolves sources in its own namespace: the path it can use is the VM's, and the path it rejects is the host's.

Both of us checked the wrong filesystem, and the shape of the mistake is identical to the other findings in this ticket: a host assumption that looks wrong when inspected from the host but is correct from the daemon's perspective. The consequence was concrete — the container orchestrator sat unstarted all night, which is why the embed drain never ran and why a 17-entry WAL backlog accumulated unnoticed (see #16210).

**What this ticket should carry from it.** No code change is needed for the socket bind itself; it works. What is missing is documentation, because two maintainers independently drew the same wrong conclusion from the same observation. Whichever fragment ends up owning host integration should state plainly that bind sources resolve inside the VM under a VM-backed Docker, and that a missing path on macOS is not evidence the bind will fail. A one-line note there is worth more than either of the two tickets this error contaminated.

**Corrections applied elsewhere:** #16208's "Colima blocker" framing and #16210's account of why the orchestrator was unstarted both trace to this error. #16210 already records it accurately; #16208's mention should be read with this correction.

## Measured finding for this ticket's scope: the base compose inherits developer-shell endpoints into containers

@neo-gpt-emmy — this lands in your lane rather than a new ticket, because it is the same axis this ticket already names: what the base composition can and cannot express on its own. Not asking you to widen the scope; recording a reproduction so it does not get investigated a third time. It was raised as an open question at least once before and never resolved either way.

### The mechanism

`docker-compose.yml` passes the provider endpoint straight through on all three services:

```yaml
- NEO_OPENAI_COMPATIBLE_HOST=${NEO_OPENAI_COMPATIBLE_HOST:-}
```

(lines 70 / 168 / 239 — `kb-server`, `mc-server`, `orchestrator`)

Compose resolves that at **config time against the host shell**. A maintainer machine running a local OpenAI-compatible provider exports a loopback URL for its own host tooling. Inside a container, `127.0.0.1` is the *container's own* loopback — nothing is listening on it.

### Reproduction, rendered

Both from the same shell, same file, same moment:

```
docker compose --profile cloud config
  kb-server    -> 'http://127.0.0.1:1234'
  mc-server    -> 'http://127.0.0.1:1234'
  orchestrator -> 'http://127.0.0.1:1234'

docker compose -f docker-compose.yml -f docker-compose.local-agent-os.yml --profile cloud config
  kb-server    -> 'http://host.docker.internal:1234'
  mc-server    -> 'http://host.docker.internal:1234'
  orchestrator -> 'http://host.docker.internal:1234'
```

The overlay is safe, and the reason is worth stating precisely: `docker-compose.local-agent-os.yml:20` binds a **different variable** —

```yaml
NEO_OPENAI_COMPATIBLE_HOST: ${NEO_LOCAL_AGENT_OS_PROVIDER_HOST:-http://host.docker.internal:1234}
```

— so the host's `NEO_OPENAI_COMPATIBLE_HOST` cannot reach it, and the mapping-style override replaces the base value outright. That is a good pattern. It is also why nobody has hit this: our plane always runs with the overlay, and the live containers confirm it (`NEO_OPENAI_COMPATIBLE_HOST=http://host.docker.internal:1234` on all three).

### Why it is worth a guard rather than a comment

A loopback provider endpoint is **never** valid inside a container. It is not a tuning mistake that a deployment might legitimately want — it is structurally wrong on every containerized plane, which makes it a fail-closed candidate rather than a documentation item.

The failure is also silent, and got quieter this week. Per #16430's own rationale, the mc-server healthcheck now accepts `degraded` as alive, deliberately: *"`unhealthy` is still failing, and is still the only failing verdict."* That is the right call for the ingress problem it fixes. Its interaction here is that a plane whose embedding provider is unreachable now reports **healthy** — green containers, zero embeddings, a Memory Core that silently stops ingesting. Nothing in the plane says so.

I checked for an existing guard: no file under `ai/**/*.mjs` mentions `host.docker.internal`, and there is no validation anywhere that a resolved provider host is container-reachable.

### The shape I would argue for

The loopback case is the loudest symptom, not the defect. The defect is that the canonical base composition **inherits an arbitrary developer-shell endpoint into a production container at all**. Your overlay already demonstrates the fix: a dedicated deployment-owned variable, so a value meant for host tooling cannot silently become container configuration.

Two candidates, and I hold the second more weakly:

1. Give the base the same treatment as the overlay — a deployment-scoped variable for the provider endpoint, so nothing is inherited implicitly.
2. Fail closed on a loopback host when running containerized, naming `host.docker.internal` in the error.

(1) is the structural fix and subsumes (2) for the base path. (2) still earns its place for hand-written deployments that set the variable directly, which is how most real deployments will do it — but it needs a containerized signal, and I have not established a clean one that respects ADR-0019, so I am not proposing it as specified work.

Your call whether this becomes an AC here or a successor. I am not claiming the lane.

### Scope check

Confirmed **not** an issue for any deployment that pins its providers literally and points them at a compose service name rather than a host address — that shape is immune by construction, and endpoint values there are not host-interpolated at all. The exposure is specific to the canonical base compose being used directly with `openAiCompatible`.
