Resolves #16895

`HealthService.mjs` froze five embedding-probe numerics as module-level literals. All five were **byte-identical to Memory Core's leaf defaults** — the same policy, configurable on one side of the plane and unreachable on the other. On CPU-only hardware the 30s deadline sits below the observed completion time of a single embed, so the probe fails permanently while the embedder is working, and no deployment can reach the number to fix it.

Evidence: L4 (three source mutations executed against the suite; full KB + MCP suites run) → L4 required (#16895's ACs are declaration-and-use-site properties, both reachable in-suite). Residual: none for the delivered ACs; the resolver-honours-env behaviour belongs to `ConfigProvider`'s own contract and is stated as out of scope in the spec docblock rather than left implied.

## Deltas from ticket

Two beyond the ticket text, both found while implementing:

- **The frozen block was itself an ADR-0019 A1 antipattern** — module-level re-derivation of values that belong in leaves. So this diff *removes* config surface rather than adding it, which changes how it should be reviewed: the question is not "is a new leaf justified" but "why did this one live in a service".
- **Use-site reads are load-bearing, not stylistic.** Memory Core's sibling docblock requires these numerics to re-resolve *at arm time*. A hoisted `const` would bind once at module load, so a deployment change would need a process restart to take effect — most of this defect arriving by a different door. There is an explicit spec arm for it (ADR-0019 B2).

**Mutation conviction — run, not asserted.** Three mutations, each caught by exactly one arm:

| mutation | result |
|---|---|
| restore the frozen literal in `HealthService` | 1 failed (`no frozen probe-policy object survives`), 6 passed |
| **drop the env binding, keep the value at 30000** | 1 failed (the binding arm), 6 passed |
| hoist `const … = aiConfig.healthcheck…` to module scope | 1 failed (the use-site arm), 6 passed |

The middle one is the one that matters. **The defaults are unchanged by this repair**, so the obvious assertion — "the resolved value equals the config value" — passes identically against the defect and is worthless. Mutation 2 proves the suite discriminates on the *binding* rather than the number: same value, no env name, still caught.

## Evolution

First version imported `config.template.mjs` to assert the resolved tree. It would not load (Neo bootstrap), and removing it cost the suite nothing — that arm was the vacuous one by the suite's own analysis, since the leaf default and the old literal are the same number. The docblock now records why there is no runtime read rather than leaving it as an apparent omission.
