# Dense tour leaves the 100k Matrix update stream dead while the feed keeps streaming

## Context

Operator-observed during headed dense-tour runs (2026-08-02): after roughly the second tour step, the 100k Matrix stops updating cells for good, while the rest of the app stays visibly alive. Reproduced same-hour with a measuring probe (receipts below). This is the film-critical surface: a frozen Matrix during tour choreography falsifies the "content never stops living" thesis on camera — the same stake `#16353` carried for the splitter trigger.

## The Problem

The Matrix and the Feed grid have different liveness signatures, and the defect separates them cleanly:

Headed probe (1280×720, dev head `47d998f1f6`-era tree, `apps/workstation`, per-2s MutationObserver windows over each grid body — childList + characterData; feed grid as in-run control; zero pageerrors):

```
[t+4s]  matrix: 122   feed: 50   "Audit crosses the matrix split preview…"
[t+10s] matrix: 116   feed: 50   "…Sparkline receives a new values array…"
[t+12s] matrix: 115   feed: 50   "light mode…"
[t+16s]              (tour reports complete — 11 beats)
[t+20s] matrix: 104   feed: 50
[t+26s] matrix:  78   feed: 50
[t+36s] matrix:  78   feed: 50   ← last Matrix burst, ever
[t+38s…t+90s] matrix: 0 × 27 consecutive windows   feed: 50 in EVERY window
```

- Baseline: the Matrix updates in bursts (~78–122 mutations every ~8–12s — its natural pulse), the Feed streams continuously (50/2s, the 10 events/sec feed).
- After the tour, the Matrix bursts cease permanently (54+ seconds of zero across 27 windows) while the Feed never misses a window.
- The operator's observation places the freeze earlier (mid-tour, around step 2); the probe run froze after completion. Both fit "a tour beat boundary kills the Matrix update stream"; which beat varies between runs.

## The Architectural Reality

- The page is healthy at freeze time: the Feed grid's mutation stream, timers, vdom delta pipeline, and rendering all run uninterrupted; no page errors.
- The grid's layout width never changed across the run (336px constant) — no dock resize committed. This measured fact DOWNGRADES the `#16375` geometry family (echo-swallow / transform-poison, repaired in PR #16390) as the prime suspect for this trigger: the freeze is update-SOURCE-shaped, not geometry-shaped.
- The tour is deterministic by design ("11 deterministic beats"); at least one beat interacts with Matrix content directly (the Sparkline values-array beat), and beats touching the Matrix pane (split preview crossing) may pause, redirect, or take ownership of the Matrix churn generator for determinism. The prime suspect class is the tour↔churn lifecycle seam: a pause-for-determinism whose resume leg is conditional/broken, a generator ownership handoff that never hands back, or a tour-end state flip the Matrix scheduler reads as terminal.
- `#16353` (closed) proved repaint truth for the SPLITTER trigger: store-accepts + identity-survives + exact-cell-repaints all hold across committed drags. This ticket's trigger is tour choreography; the closed witness does not cover it.
- Relevant surfaces to read first: the workstation tour script (`apps/workstation/tour/denseWorkstation.mjs`) for beats that touch the Matrix pane or its stores; the Matrix churn/update scheduler (whatever drives the ~10s burst pulse — follow the store/interval ownership from `apps/workstation`); `TourRunner` step settlement (`#16359` landed injected-callback settlement — check what tour start/finish toggles app-side).

## The Fix

1. Instrument the Matrix update chain across one tour run: who fires the burst pulse (worker interval / store task), and what state does each tour beat toggle on it (pause flags, generator swaps, store references).
2. Identify the first beat boundary after which the pulse owner never fires again (or fires into a dead store/component reference).
3. Repair at the owning seam — likely the tour's pause/resume contract or the churn generator's ownership handoff — never by adding screenplay delays (the `#16353` wall applies unchanged).
4. Regression witness: a headed spec that runs the full dense tour and asserts the Matrix mutation pulse RESUMES within one pulse period after tour completion (feed-grid control included), plus a mid-tour liveness floor if the operator-observed mid-tour variant reproduces under instrumentation.

## The mechanism (all measured today at dev head `63149823e2`, both #16390 and #16403 in-tree)

`grid.Container` acquires geometry through exactly two channels: a **one-shot** mount-time `passSizeToBody()` (paint-independent `getLayoutRect` round-trip, `Container.mjs#addResizeObserver`) and, forever after, **ResizeObserver deliveries only** (`#onResize`). RO callbacks ride rendering opportunities — so in any rendering-starved window (hidden browser pane, occluded/backgrounded window), the carrier simply never delivers. Everything else in the stack is paint-independent and keeps flowing: vdom style writes, store streams, semantic dock ops. That asymmetry is the entire ticket.

## Receipts

**1. Boot leg (hidden pane, `document.hidden=true`, rAF ticks = 0 measured):** the matrix booted with a 1-row pool, 0 canvases, empty cells — mount-time measure caught a mid-projection box; the correcting RO delivery starved forever. Worker table at that moment — three of four live grid bodies degenerate:

| body | grid | containerWidth | availableHeight | pool |
|---|---|---|---|---|
| body-3 (pane matrix, post-heal) | scale | 335.85 | 320.56 | 26 |
| body-4 (pane feed) | feed | **2** | **58** | 5 |
| body-1 (older window matrix) | scale | **2** | **-28** | null |

The feed *looks* healthy at `containerWidth: 2` because store-adds re-render whatever pool exists — geometry-independent. The matrix has no store churn; it *is* its geometry. Hence the exact reported split: matrix dead, feed streaming.

**2. Tour leg (hidden, at head):** beats advance worker-paced (pips 4/11 → …), semantic geometry applies (document sizes updated; DOM box 388→336 via vdom writes), matrix takes ZERO DOM mutations through the resizeSplit AND scroll-to-50000 beats (headed control: 122 mutations at the scroll beat). Feed control: 205 mutations/5s throughout. Then the tour **halts fail-closed**: `pulseScaleSparkline`'s bounded wait finds no registered sparkline in an empty pool → *"Tour stopped — canvas-update: canvas-update returned no observable receipt"*. The screenshot at that moment is the operator's screenshot: an empty 100k Matrix, full progress bar, live feed row beside it.

**3. Step-2 leg, isolated (the operator's exact variant):** with the pane healed (worker 335.85), applied semantic `resizeSplit split-main [0.35, 0.65]` while starved (rAF = 0):
- DOM truth: grid container → **226.05px** (vdom write, flows hidden)
- Worker truth: `containerWidth` → **335.85, STALE** — the RO delivery carrying the new geometry never arrived
- One forced-frame burst later: worker → **226.05, healed**; pool rebuilt 1→27 rows earlier the same way; even the starved scroll materialized (rows 50001+ on screen).

This is the #16375 M1 signature with the carrier finally named: not a swallow this time — the carrier itself is paint-gated, and in a starved window there is no later repair. `resizeSplit` is the tour's **first geometry-invalidating beat** — that is why the freeze onsets "after the second step". In partially-starved windows (watched pane screencasts, part-occluded headed windows on a shared display) it is race-dependent: boot happens under frames → matrix lives; the step-2 delivery lands in a frame gap → permanently stale. In fully-starved windows it is deterministic (this run).

**4. Headed control (v2 + v3 receipts, JSONs archived):** 11/11 beats + 6 cues settled, matrix bursts exactly at its beats (122 scroll / 115 splitNode / 114 sparkline+addTab), zero errors, post-tour wheel-poke alive (78–80 mutations/window). No freeze exists headed at head.

## Retired premises (mine, from the filing)

- **"The Matrix's natural ~78–122/10s burst pulse"** — there is no pulse. Census receipt: no interval/timeout/rAF driver touches the scale store anywhere in `apps/workstation/` (`appendFeedBatch` is feed-only), and no timer exists in any `src/grid/column/*` class. Every matrix mutation is beat-driven or interaction-driven; post-tour zero is BY DESIGN. The filing's t+20..36s "bursts" were trailing settles of the pre-#16403 tree; "the last burst, ever" was the end of trailing work, not a death.
- **AC2 as written** ("resumes its update pulse within one pulse period") is unsatisfiable against a pulse that does not exist — restating it in the body (ticket author edit, same protocol as #16391's AC1 restatement) to bind the real invariant: worker geometry must converge to the DOM box without requiring rendering opportunities.
- #16403 is orthogonal to this defect (measured still-reproducing at head with it merged); it narrowed stage-A exposure headed, and nothing here.

## The owning seam and the fix shape (next block)

The seam is `grid.Container` geometry acquisition: it must not depend EXCLUSIVELY on a paint-gated carrier. The paint-independent channel is already shipped and proven by these very receipts (#16390's `getLayoutRect` round-trip — it performed both the mount measure and every heal read above). Candidate repair, additive (RO stays the fast path):

1. **Self-healing pull:** when `Body.createViewData` short-circuits on degenerate geometry while the store has data, request a bounded `passSizeToBody` re-measure through `getLayoutRect`. Covers the boot-empty class.
2. **Geometry-invalidation push:** semantic dock/layout operations that change pane boxes nudge affected grids to re-measure through the same channel. Covers the step-2 class. Since #16390, `onResize` re-processing is idempotent by design — a later duplicate RO delivery is a silent no-op, so double-measurement is safe by construction.

Witness shape (per AC5, no fixed delays): a spec that drives geometry changes under a rendering-starved page state and asserts worker↔DOM geometry convergence via the paint-independent read, feed control uninterrupted; plus the headed tour witness asserting zero cue failures end-to-end.
