# Memory Core stays alive while its MCP surface wedges

## Context

At 2026-08-08T11:16Z, the Docker-canonical Memory Core process was alive but its MCP surface was not reachable.

Measured on the same machine and revision cohort:

~~~
container state     running; RestartCount=0; OOMKilled=false
server command      node --max-old-space-size=768 ai/mcp/server/memory-core/mcp-server.mjs
Docker health       unhealthy; failing streak 23
last five probes    MCP healthcheck connect timed out after 8000ms
stats sample        99.43% CPU; 859.7 MiB / 1 GiB
docker top sample   44.1% CPU several seconds later; one long-lived Node server
remote reads        list_messages and query_raw_memories -> MCP -32001 after 60000ms
control             authenticated Knowledge Base query succeeded; KB container healthy
~~~

The Memory Core healthcheck had succeeded earlier in the same hour and reported the canonical plane with its WAL caught up. This is therefore a liveness deterioration, not evidence of data loss and not an authorization failure.

This is the second recorded instance of the same shape. The earlier occurrence is preserved on #16463: the server process remained present while ingress and the in-container MCP healthcheck both timed out.

The latest server-log tail contained only the three boot lines from process start. It supplied no GC, fatal-heap, blocked-operation, or recovery marker that could classify the wedge.

## The Problem

A live Memory Core process can stop accepting or completing MCP connections while Docker keeps the process running.

That removes A2A, semantic recall, and turn persistence from every seat at once. The existing probe eventually marks the container unhealthy, but the process does not exit, no restart occurs, and callers wait until their own transport deadline. Operators can see that the plane is unavailable but cannot tell why it stopped serving or whether it can recover without mutation.

The current evidence does not distinguish among event-loop starvation, GC pressure, a synchronous SQLite/Chroma/model path, request accumulation, or another process-local stall. The issue is the unclassified liveness failure, not a guessed cause.

## Architectural Reality

The targeted structure map keeps the existing ownership boundaries:

- ai/mcp/server/memory-core/Server.mjs and toolService.mjs own the MCP server and dispatch boundary.
- ai/services/memory-core/ owns the SQLite, Chroma, model, mailbox, WAL, and health operations that can execute behind that boundary.
- ai/scripts/diagnostics/mcpHealthcheck.mjs already bounds connect and healthcheck calls at 8000ms and aborts the transport.
- ai/deploy/docker-compose.yml owns the container health contract.
- ai/mcp/client/Client.mjs delegates ordinary calls to the MCP SDK; the observed SDK deadline was 60000ms.

Because list_messages and query_raw_memories both timed out while the in-container probe could not connect, this is not yet a MailboxService-specific bug. Because the KB control succeeded through the same authenticated ingress, it is not a generic credential or Caddy failure.

Discussion #15820 proposes a broader degraded-but-reachable support tier, but explicitly targets post-v13.2 and remains ungraduated. This ticket does not import that architecture. It owns the narrower current-release invariant: the canonical MC process must not remain alive indefinitely while its entire MCP surface is unreachable and causally opaque.

## The Fix

Direction, not premature mechanism:

1. Add enough process-local evidence to classify a live MCP wedge: event-loop delay, V8 heap/GC state, active request/operation identity, and the last completed server pulse, with bounded collection that still works under stress.
2. Reproduce the failure under a controlled workload or capture the next live recurrence with that evidence.
3. Remove or bound the blocking mechanism once identified.
4. Make the terminal posture explicit: the server either remains responsive with backpressure/degraded errors, or fails in a way the deployment can detect and recover. A permanently live-but-unreachable process is not an accepted state.
5. Preserve WAL/data safety; do not turn a liveness fix into an implicit restore or replay policy.

## Contract Ledger

| Target Surface | Authority | Required Behavior | Failure Posture | Evidence |
|---|---|---|---|---|
| MC MCP accept/dispatch loop | Memory Core server | Connections and health calls remain schedulable during bounded subsystem pressure | Explicit degraded/error result or observable process failure; never an indefinite live wedge | Controlled stress receipt plus live recurrence receipt |
| Long-running MC operations | Owning Memory Core service | Yield, isolate, or bound work so the server control path remains reachable | Operation-specific timeout/cancellation with identity and duration | Regression test at the identified causal boundary |
| Container health | mcpHealthcheck + Compose | Detect actual unreachability without claiming its cause | Preserve the current nonzero failure and expose enough causal context for diagnosis | Five-probe sequence and deployment snapshot |
| A2A/WAL durability | Mailbox/WAL contracts | No message/data loss introduced by recovery | Ambiguous timed-out writes are never blindly retried | Write/read receipt across the repaired failure mode |

## Decision Record Impact

No ADR amendment is justified before the mechanism is classified. If the fix adds a new deployment diagnosis/action class, ADR 0025/0026 alignment must be reviewed. If it becomes a new bootstrap/support tier, it must return to Discussion #15820 and its graduation criteria.

## Acceptance Criteria

- [ ] A deterministic stress harness or a captured live recurrence identifies what owns the server stall; root cause is not inferred from RSS or CPU alone.
- [ ] While that workload runs, the MCP health/control path either answers within its declared bound or the process terminates into an observable, recoverable failure.
- [ ] The repaired path cannot leave the container running with five consecutive in-container MCP connect timeouts and no causal receipt.
- [ ] list_messages and a semantically backed read both complete or return explicit bounded errors under the reproduced pressure.
- [ ] Knowledge Base and ingress controls remain green, proving the test targets Memory Core rather than generic remote transport.
- [ ] WAL caught-up state and a message write/read receipt are proven after recovery; no restore, replay, or retry is assumed from a timeout.
- [ ] Coverage fails against the identified pre-fix mechanism and passes against the repair.
- [ ] Any new diagnosis/action class is reconciled with ADR 0025/0026; otherwise the ticket records that no ADR change was needed.

## Out of Scope

- Restarting, recreating, or restoring the live canonical plane as part of this ticket's diagnosis.
- Treating total container RSS as V8 old-space usage or raising a heap ceiling from that cross-scope ratio.
- The already-shipped canonical client defaults in #16672.
- False health verdicts caused by probe startup under host load (#16646).
- Heap-abort detection and V8-scoped saturation classification (#16630).
- Mailbox read-state semantics or message disappearance.
- The post-v13.2 support-mode architecture from Discussion #15820.

## Avoided Traps

- **Blank mailbox equals no mail.** The call timed out; mailbox state is unknown.
- **Healthy earlier equals healthy now.** The plane changed from answering to unreachable within the same hour.
- **Unhealthy equals dead.** The process is running and has not restarted.
- **High RSS proves a heap leak.** Container RSS and V8 old space are different scopes.
- **A transport timeout is the root cause.** It is the caller's bound on an unresponsive subject.
- **Restart first, explain later.** Mutation would erase the only live recurrence before causal evidence exists.
