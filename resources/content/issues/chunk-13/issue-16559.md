# A component binding Store load and sort does full reorder work in both

## Context

Generalized from `#16538` / PR `#16552`, where Helix was fixed. Found by `@neo-opus-vega` during that review, who ran the consumer census the fix needed and flagged Gallery as a likely second instance while explicitly stating she had not read `Gallery.onStoreLoad`. That read is done below — it is **established**, not suspected.

## The Problem

**`data.Store` fires `load` on a sort, deliberately — and a component that binds both events and does complete reorder work in each pays for the sort twice.**

`Store.onCollectionSort()` (`src/data/Store.mjs:1094`) re-fires a sort as a `load`:

```js
onCollectionSort() {
    if (this.isConstructed) {
        this.fire('load', {items: this.items})
    }
}
```

**This is correct and must not change.** Vega's census of all 14 `src/` consumers binding Store `load` found two that bind `load` and **not** `sort`:

| consumer | `load` | `sort` |
|---|---|---|
| `form/field/ComboBox.mjs:224` | yes | **no** |
| `toolbar/Paging.mjs:174` | yes | **no** |
| `table/Container.mjs` | yes | yes |
| `component/Gallery.mjs:366-367` | yes | yes |

`ComboBox` and `Paging` react to a sort **only** because `onCollectionSort` fires `load`. Making Store suppress it would silently stop both updating — no error, no failing test. So `load` is the coarse change-notification and `sort` the fine-grained one, and each consumer picks its granularity.

**The defect is therefore always consumer-level: binding both and treating each as a complete reorder.**

### Helix — closed, `#16538` / PR `#16552`

`onStoreLoad` rebuilt the item vdom and let the differ reorder, while `onSort` hand-wrote one `moveNode` delta per item straight to `Neo.applyDeltas`. ~1176 moves where 590 suffice on 590 items, and the manual pass bypassed the differ, so the vdom and the real DOM diverged across a sort.

### Gallery — established, and structurally identical

`src/component/Gallery.mjs:366-367` binds both. Then:

```js
onStoreLoad(items) {
    this.getItemsRoot().cn = [];   // silent update
    this.createItems()
}
```

Byte-identical to Helix's — a full teardown and rebuild of every item vdom.

And `onSort()` (`:701`) builds `newCn` from `store.items` against the existing `view.cn`, then:

```js
if (hasChange) {
    view.cn = newCn;
    me.update();
}
```

So one store sort runs **both**: a complete teardown + `createItems()` rebuild, and a separate full reorder of `view.cn` followed by another `update()`.

**One difference from Helix, in Gallery's favour:** both passes go through the differ, so there is no vdom/DOM divergence — the class of bug Helix's `applyDeltas` bypass created does not exist here. **One against it:** Helix's duplicate pass was a reorder; Gallery's `onStoreLoad` half is a full *rebuild* of every item's vdom, which is strictly more work than reordering.

## The Architectural Reality

- `src/data/Store.mjs:1094` — `onCollectionSort` → `fire('load')`. Correct; two consumers depend on it. **Out of scope to change.**
- `src/collection/Base.mjs:786` — fires `sort`. Store registers its own listener in its constructor, before a component binds, so a component's `onStoreLoad` runs before its `onSort` on the same event.
- `src/component/Gallery.mjs:366-367, 701` — the instance this ticket carries.
- `src/component/Helix.mjs` — fixed in PR `#16552`; the pattern to follow is that `onSort` stops reordering and the differ owns it once.

**`Store.onCollectionSort()` carries an empty JSDoc block** and no comment stating the `load` fire is deliberate. Vega logged this as a `[KB_GAP]` on `#16552`, and it is the root of the whole class: with nothing saying the coarse/fine split is intentional, the method reads as a conflation to anyone finding it mid-debug, and the tempting fix is the one that breaks ComboBox and Paging silently. Documenting it is cheap and prevents the dangerous repair.

## The Fix

1. **Gallery:** one reorder pass per sort. Follow `#16552` — the handler that reorders keeps it, the other stops doing complete work.
2. **`Store.onCollectionSort()`:** state in JSDoc that the `load` fire is the deliberate coarse notification, name `ComboBox` and `Paging` as the consumers that depend on it, and say that suppressing it breaks them silently.
3. **Consider a guard for the class**, so a third instance fails rather than ships: a component binding both events and reordering in both is mechanically detectable.

## Acceptance Criteria

- [ ] A Gallery sort issues one reorder pass, asserted on delta or update counts, failing against today's double pass.
- [ ] `ComboBox` and `Paging` still update on a sort — the regression the tempting Store-level fix would cause, pinned so it cannot be introduced later.
- [ ] `Store.onCollectionSort()` documents the coarse/fine split and its dependent consumers.
- [ ] `#16552`'s Helix behaviour is unchanged — no shared refactor regresses the closed instance.
- [ ] If a mechanical guard lands, it fails on a synthetic component that binds both and reorders in both.

## Out of Scope

- **Changing `Store.onCollectionSort`'s `load` fire.** Two consumers depend on it; this is recorded as an Avoided Trap, not a candidate.
- Helix (`#16538`, closed via PR `#16552`).
- `table/Container.mjs` — binds both, but its handlers were not read here. If it is a third instance it belongs in this ticket; that read is part of the work.

## Avoided Traps

- **"`load`-on-sort is a conflation, fix it at the Store."** The obvious repair, and it silently breaks `ComboBox` and `Paging` — no error, no test. Only a consumer census surfaces that, which is why the census is recorded above rather than the conclusion alone.
- **Assuming Gallery is identical to Helix.** It is the same class but not the same shape: Gallery's duplicate work goes through the differ, so the vdom/DOM divergence Helix had does not apply, and a copied fix would be wrong about what it is fixing.
- **Reading a binding and inferring the handler.** Vega flagged Gallery from `:366-367` and explicitly declined to call it established without reading `onStoreLoad`. Reading it is what moved this from "likely" to established — and it also found the rebuild-vs-reorder difference, which a copied conclusion would have missed.

## Correcting my own premise: Gallery does NOT double-reorder — `onSort` is dead code on the sort path

I filed this 20 minutes ago claiming Gallery was "established, not suspected" as a second instance of *"does full reorder work in both handlers."* **That is wrong**, and the ticket is better for it.

### What I actually did wrong

I read `onStoreLoad` and I read `onSort`, saw a rebuild in one and a reorder in the other, and concluded both run. **Reading two handler bodies is not reading their interaction** — and the interaction is the entire question. Vega declined to call Gallery established without reading `onStoreLoad`; I read it and then made the *same* class of leap one level up, from bodies to sequence.

### The sequence, from four independent facts

| fact | source |
|---|---|
| `Store` registers its own `sort` listener in its constructor | `src/data/Store.mjs:220` |
| Gallery binds its listeners later, via `beforeSetStore` | `src/component/Gallery.mjs:359` |
| `createItems` mutates `cn` **synchronously** (`itemsRoot.cn.push`); only `promiseUpdate()` is async | `Gallery.mjs` `createItems` |
| `onStoreLoad` does **not** reset `itemsMounted` — its only writes are `:196` (false) and `:461` (true) | `Gallery.mjs` |

So on one store sort:

1. `Store.onCollectionSort()` fires `load`.
2. Gallery's `onStoreLoad` runs **first** — `view.cn = []`, then `createItems()` pushes every item back **in the new store order**, synchronously.
3. Gallery's `onSort` runs. `itemsMounted` is still `true`, so it proceeds — and reads a `view.cn` that is *already* in the target order. `fromIndex === index` for every item, so `hasChange` stays `false`.
4. `view.cn = newCn` and `me.update()` **never execute**.

**There is no second reorder.** There is one rebuild and one no-op.

### What the real defects are

**1. `onSort` cannot fire its own body on a store sort.** Its `hasChange` guard is unreachable by construction, not by data. That is dead code sitting in the hot path of a component that reads `view.cn`, maps every id, and allocates `newCn` on every sort before discarding all of it.

**2. The repositioning behind that guard never runs.** `afterSetOrderByRow(me.orderByRow, !me.orderByRow)` is inside `if (hasChange)`, so it is unreachable on this path too. `createItems` does set `vdomItem.style.transform = me.getItemTransform(i)` during the rebuild, so the positions are *probably* already correct and the call is redundant — **but I have not established that**, and "unreachable code that might have been load-bearing" is the more expensive half of this ticket.

**3. The sort path is a full teardown and rebuild.** `cn = []` plus `createItems()` reconstructs every item vdom — strictly more work than reordering existing children. That is a real cost and the one thing my original filing got right, for the wrong reason.

### How this differs from Helix, which is the point

Helix genuinely double-reordered: its `onSort` wrote `moveNode` deltas straight to `Neo.applyDeltas`, bypassing the differ, so its work was *invisible* to the rebuild and both passes landed. Gallery's `onSort` operates on the same `view.cn` the rebuild just corrected, so it self-cancels.

**Same binding, opposite outcome.** That is why the class as I stated it — *"binds both and does full reorder work in each"* — does not survive: what matters is not whether both handlers contain reorder logic, but whether the second one can still observe stale order when it runs. Helix's could because it bypassed the vdom; Gallery's cannot because it does not.

The `Store.onCollectionSort()` `[KB_GAP]` (empty JSDoc, no statement that the `load` fire is deliberate) stands unchanged — it is what makes this sequence unreadable without a four-fact trace.

`table/Container.mjs` remains genuinely unread and is now the only open candidate for the original class.
