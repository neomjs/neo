# Blobless tenant mirror turns first ingestion into 23,931 network round trips

## Context

Found on the live plane immediately after deploying `#16547` (`#16546`) and removing the pre-fix 4.9 GB mirror, while verifying the fix did what it claimed.

The disk half worked exactly as designed: **4.9 GB → 36.2 MB**, `remote.origin.promisor=true`, `partialclonefilter=blob:none`, 28 promisor packs, 25,839 commits, 23,931 files at `dev`, tip at the deployed revision. Orchestrator memory went from ~1009 MB at death to **146 MB / 3 GB**, and the OOM loop stopped — 19-for-19 heap FATALs before, zero since.

Then the operator asked the question none of the three reviewers asked: *"`resources/content` alone is 126 MB. OC does not need it, but for tenant repo ingestion, it is crucial."*

## The Problem

**A blobless mirror makes every content read a network round trip, and the ingestion does one `show` per file.**

`gitMirror.mjs` reads content exactly one way — `show <revision>:<sourcePath>` — which on a promisor repo lazily fetches that single blob from the remote.

Measured on the live plane, two independent samples:

| sample | files | wall clock | per file |
|---|---|---|---|
| `resources/content` offsets 101-120 | 20 | 8.17 s | 0.41 s |
| `resources/content` offsets 2001-2030 | 30 | 12.55 s | 0.42 s |

The mirror grew 36.2 MB → 39.8 MB across those fetches, which is the backfill confirming each read hit the network.

**Tracked files at `dev`: 23,931.** The lane's `lastIngestedRev` is `null` — it has never completed an ingest — so the first run reads the whole tree, not a diff:

**23,931 × 0.42 s ≈ 2.8 hours**, and `resources/content` alone (16,674 files) is ≈ 1.9 hours of it.

This is the trade `#16546` explicitly rejected, arriving through a different door. Its Avoided Traps rejected `--depth 1` because it *"trades a disk problem for a throughput problem"* — `--filter=blob:none` preserves the incremental-diff operations `--depth` would have broken (verified: `diff --name-status dev~5 dev` returns 60 paths, `merge-base --is-ancestor` passes) but reintroduces the throughput cost on the read path instead.

The PR body **states** the trade — *"`show` becomes a potentially NETWORKED read … a `show` against an unreachable remote now fails where it previously read from disk"* — and prices it as a failure-mode change. Nobody priced it as a **per-file latency multiplied by the ingestion surface**. I reviewed that PR, required changes on an unrelated scope hole, and missed this.

## The Architectural Reality

- `ai/services/knowledge-base/helpers/gitMirror.mjs` — `readRevisionFile` is the only content read, one `show` per path. On a promisor repo each is a round trip.
- `cloneIfMissing` — `--mirror --filter=blob:none`, with `assertBloblessClone` proving blobs are genuinely absent. Working as intended; the cost is downstream.
- The incremental path is **not** affected in steady state: once `lastIngestedRev` is set, only changed paths are read. The 2.8 hours is a first-ingest / re-clone cost — which is exactly the state this plane is in, and the state any fresh tenant deployment starts in.

## The Fix

Direction, not prescription — the shape is genuinely open and the measurement below is the part I trust.

**Option A — bulk-fetch before ingesting.** Git can fetch many missing objects in one negotiation; the ingestion just never asks for them together. A pre-ingest pass that resolves the target revision's blob OIDs and fetches them in one operation would collapse N round trips into one. **Unverified:** my batch test was invalid — `fetch-pack --stdin` failed and fell through to the same sequential loop, so both arms measured the sequential path. *Batching is untested, not disproven*, and testing it properly is the first task on this ticket.

**Option B — filter by path, not by blob.** `--filter=blob:none` is the wrong axis if the ingestion reads most of the current tree anyway. `--filter=sparse:oid` or a partial clone scoped to the ingested subtree keeps the current tree's blobs local while still dropping history.

**Option C — accept it for the incremental case and pay the first ingest once.** Defensible if first-ingest is genuinely rare, but this plane has done it zero times successfully and any new tenant pays it.

## Decision Record impact

`none` — a read-path change behind the existing helper boundary.

## Acceptance Criteria

- [ ] A full first ingestion of the tenant repo completes in a stated budget, measured on the container plane rather than a fixture.
- [ ] The per-file cold-read cost is asserted against a threshold that **fails at today's 0.42 s/file**, so the regression cannot return silently.
- [ ] Whichever option lands, `assertBloblessClone`'s guarantee is either preserved or its removal is explicit — the 4.9 GB must not come back invisibly.
- [ ] Incremental sync stays untouched: `diff --name-status <base> <head>` and `merge-base --is-ancestor` still operate without fetching blobs.
- [ ] The measurement method is recorded, since the naive one is wrong: a `date +%s%N` timer inside the container returns 0 (busybox has no nanoseconds), which is how the first read of this looked like "0 ms per file."

## Out of Scope

- `#16554` (five unowned lanes, `kbSync` among them) — that lane never runs at all; this one runs and is slow. Different producers, and neither substitutes.
- The orchestrator heap ceiling (`#16463`).
- Reverting `#16547`. The disk and OOM results are real and measured; this is the other half of the same trade.

## Avoided Traps

- **Trusting a container-side timer.** `date +%s%N` under busybox produced "20 files: 0 ms, 6.8 MB" — a result that looked like a triumph and was a broken clock. Timed from the host thereafter.
- **Reporting a failed instrument as a negative result.** My batch-vs-sequential comparison returned 12.42 s vs 12.55 s, which reads as "batching does not help." It fell through to sequential in both arms. A test that did not run is not evidence.
- **Declaring the fix verified on the axis that was easy to measure.** I confirmed size, promisor config, byte-identical content and zero OOMs, and called it done — without measuring the throughput of the thing the mirror exists to serve.
