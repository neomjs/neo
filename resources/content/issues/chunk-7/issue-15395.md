# Dual-window conversion geometry: popup→proxy over a target vessel

## Context

Epic #15239 leaf (G3 family) — operator exploration 2026-07-18: *drag one tab out into a popup, resize it, drag a second tab out — when the second popup crosses the first, at what point does it convert into a semi-transparent drag proxy inside the target? Gut: it should depend on the heights and widths of BOTH windows.* The gut is provably right, and this leaf turns it into a measured contract. #15246 owns G3's claim-arbitration story; **no leaf owns the conversion-entry mechanic** — this one does.

## The Problem

The landed tear-out grammar uses direction-aware intersection-ratio hysteresis against ONE window (`src/draggable/container/SortZone.mjs:270` `checkWindowBoundary`, defaults 0.8 detach / 0.6 reattach, #8160 lineage). **A fixed single-denominator ratio is mathematically broken for popup-over-popup:**

- Denominator = dragged window B: a large B over a small target A caps at `area(A)/area(B)` — for B twice A's size, the ratio can never exceed 0.5, so a 0.8 threshold is **unreachable** and conversion never fires.
- Denominator = target A: a small B can never cover enough of a large A — unreachable in the mirror case.

Both windows are freely resizable mid-session (the operator's scenario resizes A before the second drag), so any creation-time or single-window basis is wrong twice.

## The Architectural Reality

- The conversion is the tear-out's inverse: boundary-exit converts proxy→popup (`src/dashboard/Container.mjs:218` `onDragBoundaryExit` → `:243` `openWidgetInPopup`); this leaf converts popup→proxy on vessel-overlap. Same hysteresis philosophy, new geometry.
- The pointer (not the rect) is the *intent* signal — the dragged window follows the pointer (`main/addon/DragDrop.mjs` pointer-follow), but a large B's rect can overlap A while the pointer is nowhere near it. Claim/menu/preview single-target semantics are #15240's protocol (ADR 0029 amendment, closed) + #15246's arbitration; this leaf feeds them a conversion event, never re-implements claiming.
- The calibration harness already exists in-flight: the #15243 seven-row headed matrix suite — this contract's witness rides the same harness as an extension row (same instrumentation, new cells), so the geometry ships with calibration receipts, never numbers from memory (G1's #15244 discipline).

## The Fix

One PR: the dual-window conversion contract + its headed witness.

1. **Metric:** per-axis overlap ratios normalized by the SMALLER extent per axis — `rx = overlapWidth / min(width(A), width(B))`, `ry = overlapHeight / min(height(A), height(B))` — composed (e.g. `min(rx, ry)` or product; decided empirically), so the threshold is reachable for every size pair in both directions. Computed from LIVE rects every gesture frame.
2. **Hysteresis pair:** convert-in threshold > convert-out threshold (flicker-free at the boundary), calibrated on the workstation density with receipts.
3. **Pointer gate:** conversion arms only while the pointer is inside the target's dock-accepting region — rect overlap alone never converts (intent stays pointer-owned; feeds the #15240 claim protocol unchanged).
4. **Headed witness cells** on the #15243 harness: small-over-large, large-over-small, near-equal, post-resize asymmetric — each asserting reachability, hysteresis stability (no convert/revert oscillation across a slow crossing), and single-claim (at most one target exposes menu+preview, G1 AC parity).

## Acceptance Criteria

- [ ] The conversion metric is reachable for ANY window-size pair in both directions (small↔large), proven by witness cells, computed from live post-resize rects.
- [ ] In/out hysteresis pair calibrated empirically on the workstation density; chosen values carry calibration receipts in the PR.
- [ ] Pointer-inside-target gates arming; rect-overlap alone never converts.
- [ ] Conversion emits through the #15240 outcome machine (a new state, if required, lands as an ADR 0029 amendment in the same PR — see Decision Record impact).
- [ ] A slow boundary-crossing witness proves zero convert/revert flicker.
- [ ] **Flicker ownership (the #15434 review's non-blocking challenge, Ada):** the sensor's pointer gate is deliberately undamped (rect overlap must never pin a conversion), so the wire-in NAMES where `pointerInTarget` stability lives — the #15246 claim feed's expiry/hysteresis semantics or an explicit debounce at the binding site — and witnesses a boundary-flicker sequence producing bounded conversion flips.

## Gate-0 correction — the canonical red is a wrong-owner join in this wire-in seam

To assert the cause rather than repeat the headed symptom, I traced the exact live `origin/dev` source at `65097d75e4a3f6348bad999e1e07d923db609918` and re-fetched draft PR #15552 at exact head `e23406258c074f5eeb7805a1a68c3a3eae62b7a4` (all CI green; deliberately test/ledger-only).

The failure is deterministic in `DemoBWorkspace`:

1. `commitCrossWindowTransfer()` publishes `detachedPanes[workbench] = {windowId: <workspace-popup>, windowName: 'demo-b-cross-window'}` synchronously.
2. The competing G1 vessel connects through `?popout=workbench`.
3. `onWindowConnect()` looks up only `detachedPanes[itemId]`. Because that entry exists, it overwrites `entry.windowId` with the G1 vessel's runtime ID and reparents the live pane there.
4. The intended `?workspaceId=demo-b-popup` target therefore remains connected but loses the CounterPane — exactly Emmy's headed receipt. The narrow drag-only green never checks this competing-owner path.

This corrects the earlier bounded inference on #15396: **the absence of conversion/park composition is still real work, but it is not the proven immediate cause of this red.** This ticket already owns the production wire-in and previously names `onWindowConnect()` as a consumed seam, so the repair belongs here; #15396 retains the async park/re-show lifecycle contract, while #15551 / PR #15552 remains the evidence boundary.

### Required invariant

A physical child window may adopt the live pane only through an exact, generation-bound owner grant. `itemId`, URL shape, arrival order, and “an entry exists” are not ownership. The click-popout fast-connect race must remain valid, which rules out a superficial `entry.windowId === windowId` check while click entries begin at `null`; the wire-in needs an explicit provisional grant that the expected child consumes once. A competing tear-out vessel must never mutate the cross-window target's entry.

Required falsifiers: click popout connect-before-open-settlement, tear-out connect-before-terminal, cross-window target plus competing G1 vessel, stale/reused child connection, and canonical full round-trip. Do not make the canonical test green by suppressing the extra window or loosening its target assertion.
