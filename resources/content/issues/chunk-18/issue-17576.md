# Dock-demo journeys: four pre-existing dev-red cases, one of them a platform golden

## Context

Sibling to #17564, which owns the equivalent set for the Workstation witnesses. This one owns the **dock-demo** journeys.

Surfaced while discharging @neo-gpt-emmy's RA-2 on PR #17562 (#16322, the dockdemo relocation). That review's standard is the reason this ticket exists: *"the same test failing at different assertions cannot be called byte-identical or zero-regression evidence."* Applying it required measuring the relocation branch against a **detached `origin/dev` worktree** rather than against memory — and that measurement showed four journeys already red on `dev`, at assertions the relocation does not touch.

Without a durable owner, four permanently-red journeys become background noise that every future dock PR has to re-triage from scratch.

## The Problem

Eight relocation journeys were run on `origin/dev` and on the relocation branch. Both trees: **12 passed / 4 failed**, the same four specs, and `diff` over the sorted failure messages is **empty**.

The four, enumerated by failed invariant rather than by name — each needs its own diagnosis and none of them share a mechanism:

| # | journey | failed invariant | observed |
|---|---|---|---|
| 1 | `e2e/agentos/DemoBKeyboardDetachNL.spec.mjs:31` | the detach announcement must name the popup surface | `expect(received).toContain(expected)`, expected substring **`"popout"`** — the announcement/URL does not carry it. The file's other two tests pass, **including** the harder popup-origin RETURN at `:122`, so the detach grammar itself works and only this announcement assertion is red |
| 2 | `e2e/agentos/DemoBPerspectivesNL.spec.mjs:53` | *"the real popup hosts the live workbench pane"* | the reparented pane is not found in the popup — the shared-heap handover assertion, not the perspective switching around it |
| 3 | `e2e/dashboard/DemoATourNL.spec.mjs:26` | *"the tucked window must render real DockRail tab buttons"* | `maxRailTabs: **5**`, expected `3`. The scene tucks three residents; five rail tabs are observed, so this is an over-count, not an absence — the rail renders, it renders too many |
| 4 | `e2e/dashboard/PreviewLanguageDragPairNL.spec.mjs:135` | visual golden | `toHaveScreenshot` — **688 pixels, ratio 0.01**. A sub-1% delta on a platform-specific golden; see the instrument caveat below |

## The Architectural Reality

Rows 1–3 are behavioural assertions against live cross-window and rail state; they are real questions about the product, not harness artifacts.

**Row 4 is a different class and should not be triaged with the other three.** The visual suite is a local-harness, platform-specific instrument — `#17518` recorded 8/8 goldens failing on an unmodified tree. A 0.01 ratio on a machine that is not the golden's origin host is exactly what that caveat predicts. Deciding whether row 4 is a product defect requires first deciding whether the golden is authoritative on this host at all.

## The Fix

Diagnose each row independently. They are grouped here for **ownership**, not because they share a cause — a single "fix the dock e2e" commit would be the wrong shape.

Suggested order, cheapest signal first: row 3 (a deterministic over-count, fully observable from one run's `OBSERVED` payload), then row 1 (a string assertion with an obvious candidate surface), then row 2 (genuine cross-window state), and row 4 only after the golden's authority on the running host is settled.

## Acceptance Criteria

- [ ] Each of rows 1–3 is either fixed, or reclassified with a named cause and its own successor ticket. A row closed as "flaky" must carry the evidence that it is timing-dependent — a repeat count, not an adjective.
- [ ] Row 4 carries an explicit verdict on golden authority for the running host before any product diagnosis is attributed to it.
- [ ] `test-e2e` over the eight dock journeys is green on `dev`, **or** the residual set is smaller and each survivor names its own owner.
- [ ] A control proves the suite can fail: the greened set must redden against a deliberate regression, so "green" is not "the assertions stopped running".

## Out of Scope

- The relocation itself (#16322 / PR #17562). It is measured to add nothing to this set; that measurement is the reason this ticket can exist separately.
- The Workstation witnesses (#17564) — same shape, different specs, already owned.
- Retiring any of these journeys. They assert real product invariants; the red is the finding, not the nuisance.

## Avoided Traps

- **Fixing them as a batch.** Four different mechanisms; a single commit that turns the set green would hide which invariant was actually restored and which assertion was merely weakened.
- **Blaming the relocation.** Measured on both trees at assertion level; the messages are byte-identical. Attributing them to the newest PR is the cheapest wrong answer.
- **Treating row 4 like rows 1–3.** A platform-specific golden and a live cross-window invariant fail for unrelated reasons; triaging them together produces a wrong verdict on at least one.

## Row 3 diagnosed — it is a rail-level leak, not a tab-level one

Claimed this ticket and took row 3 first, per its own "cheapest signal" ordering. The `maxRailTabs: 5` assertion is **correct** and the product is leaking. Measured, on `dev` as well as on PR #17562 — this is not relocation fallout.

**The finding:** during the auto-hide wave, **two `DockRail` instances exist in the DOM at once**.

```
neo-dashboard-dock-rail-2[2]   ← STALE — Preview, Terminal
neo-dashboard-dock-rail-3[3]   ← LIVE  — Preview, Terminal, Logs
```

Both carry `.neo-dashboard-dock-edge-rail-right`, both sit under the same `neo-dashboard-dock-edge-row`. The rail is re-projected as a **new instance** and the previous one is never removed, so the document holds five rail tabs where three residents were tucked — with `Preview` and `Terminal` visibly duplicated.

The spec's instrument counts `document.querySelectorAll('.neo-dashboard-dock-rail-tab')` globally and asserts `3`. Given a stale rail survives, `5` is the honest reading of a real defect. **Do not "fix" this by scoping the selector to the live rail** — that would hide a DOM leak behind a narrower query and turn a true red into a false green.

### Two wrong turns recorded, so nobody repeats them

**1. `reconcileTabs()` is not the culprit.** Its reorder path looked conclusive:

```js
me.remove(button, false, true);   // destroyItem:false, silent:true, keepMounted:false
me.insert(targetIndex, button)
```

A silent removal never syncs to the DOM, and `keepMounted:false` marks the component unmounted so `insert` re-renders a fresh node — a textbook stranding. I passed `keepMounted:true` and **the count stayed at 5**. Reverted; an unverified change is not an improvement, and the reasoning was aimed one layer below the defect.

**2. A per-edge breakdown lied to me, and the lie looked like exoneration.** My first probe built `byRail[edgeClass] = tabCount`, which reported `{"…-edge-rail-right": 3}` and made the rail look correct. **Two rails share that edge class, so the second overwrote the first** — the object key collapsed the very duplication I was hunting. Census by element id (`r.id + '[' + count + ']'`) is what exposed it. A census keyed on a non-unique attribute cannot see duplicates by construction.

### Where the fix belongs

Not in `DockRail`. The question is why the edge-row acquires a second rail rather than updating the first — the projection/reconciliation path (`DockLayoutAdapter` → `DockProjectionReconciler`), where an item is matched to an existing component or created anew. `DockRail` already documents in-place reconciliation as its contract; something above it is not reaching that path.

Suggested first probe for whoever takes it: log the reconciler's match decision for the edge rail across the auto-hide wave — whether it fails to match the existing rail (so creates), or matches and creates anyway.

### AC impact

`maxRailTabs` should reach `3` once the stale rail stops surviving; no spec change is required and none should be made. Row 3's AC is met by the leak being fixed or by a named cause, not by adjusting the assertion.

## Correcting my own diagnosis above — the rail is NOT stranded, it is double-mounted

My previous comment said *"the rail is re-projected as a new instance and the previous one is never removed."* **That is wrong and I am retracting it.** The old rail *is* removed; it is just removed **after** the new one mounts.

I only found this by sampling the rail-element count **per tick across the whole tour** instead of taking its maximum. The shape:

```
0000…0000  1111  2221222  1111111111…1111  2
   no rail   one   OVERLAP     one, sustained   (final sample)
```

It settles at one for the overwhelming majority of the tour. The spec records the **max** over the run, so a sub-second overlap window is indistinguishable from a permanent leak in the reported number — which is exactly how I misread it. A max-sampler cannot tell "stranded forever" from "briefly doubled", and I asserted the former from a number that only supports "at some instant, five".

So the defect is an **ordering** one: on a rail re-projection the replacement mounts before the outgoing rail unmounts, and the document transiently holds two rails and five tabs. A user would see a flicker of duplicated tabs, which is real but is a different bug from the one I described.

### Two candidate fixes, both falsified — do not re-try either as written

**1. `DockRail.reconcileTabs()` reorder path, `keepMounted`.** `me.remove(button, false, true)` is `destroyItem:false, silent:true, keepMounted:false`; a silent removal never syncs to the DOM and the unmount makes `insert` render a fresh node. Passed `keepMounted:true` → **still 5**. Reverted.

**2. Adding `edge-rail` to `projectionNodeTypes`.** `DockProjectionReconciler.mjs:4` is `new Set(['edge-zone', 'split', 'tabs'])`, so rails are recreated per projection rather than reconciled in place. Added `'edge-rail'` → **still 5**. Reverted.

Fix 2 failed for a reason worth carrying: the reconciler's structural branch also requires a stable `dockNodeId` (`DockProjectionReconciler.mjs:82` — `if (!node.dockNodeId || …) valid = false`), and `DockLayoutAdapter.createEdgeRail()` does not project one. Membership in the set is necessary but not sufficient; the rail would need a stable identity across projections first.

### What this exposes, and it is the more interesting finding

`DockRail` documents in-place reconciliation as its contract — *"Model flips reconcile the button set IN PLACE (`reconcileTabs()`): surviving items keep their live component instance — object permanence at the affordance level"* — and implements `afterSetRailItems()` → `reconcileTabs()` to honour it.

**The projection layer never gives it the chance.** Rails are outside `projectionNodeTypes` and carry no `dockNodeId`, so each projection builds a new `DockRail` whose `railItems` arrives at construct time. `afterSetRailItems` guards on `oldValue !== undefined`, which a construct-time value never satisfies. That machinery appears to be unreachable from the projection path — worth confirming with a counter before anyone relies on it.

### Revised fix shape

Give the edge rail a stable `dockNodeId` (its edge is already unique per zone) and admit it to `projectionNodeTypes`, so a flip updates `railItems` on the living rail and the swap — with its overlap window — stops happening at all. That is a real engine change with blast radius into the reconciler's staging rules, so it wants its own design pass rather than a third opportunistic patch from me tonight.

Rows 1, 2 and 4 remain untouched.
