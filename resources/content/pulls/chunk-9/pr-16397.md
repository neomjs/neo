Resolves #16388

Related: #16382 (the detector this unblocks), #16223 (the live starvation the chain serves)

`buildMiniSummary` returned a bare `null` for four unrelated reasons — no model, empty output, a caught provider error, and its own swallowed inner timeout. The sweep mapped every falsy result to `failedInner` and every escaped throw to `failedOuter`, so the recorded facts answered *which control-flow branch ran* and nothing answered *why*.

That is what closed PR #16383 unmerged: I read `failedInner` as "the inner timeout is binding". A branch counter cannot carry that fact, and no rewording repairs an input contract that never had it. This adds the missing dimension at the source. `failedInner` / `failedOuter` keep their exact meaning and values.

Evidence: L2 (unit coverage at exact head; every AC is an assertion on a returned value or an emitted log line, and the classifier is fully reachable in-sandbox) → L2 required. Residual: the five causes are proven distinguishable in-sandbox; which cause actually dominates on the CPU-only plane of #16223 is a live-plane observation, listed below.

## Deltas from ticket

**Classification is structural, never textual.** `withTimeout` now sets `code = WITH_TIMEOUT_CODE` plus `label` / `timeoutMs` on its rejection. The ticket asked for `timeout-inner` to be separated from `provider-error` inside the same `catch` but did not say how, and message-matching was the only pre-existing option — unsound twice over: a reworded message silently stops matching, and any downstream error whose prose happens to mention a timeout is misread as one. A spec pins that second failure mode directly.

**`WITH_TIMEOUT_CODE` is re-exported beside `withTimeout` from `MemoryService`.** `withTimeout` was already re-exported there for back-compat; the code was not. An importer on that path could reach the thrower but not its identity, and would have to hardcode the literal to classify a rejection — reintroducing the drift the constant exists to remove.

**The completion log carries the cause tally, on failing runs only.** Not in the ticket. It matters because a starved plane is diagnosed from captured stderr, not by a caller inspecting a return value — a cause that only reaches the return value is invisible where #16223 is actually read. Healthy runs keep their existing line rather than carrying an empty object every sweep.

**A legacy bare return is tallied `unspecified`, never a plausible cause.** The seam accepts a summarizer that returns a bare string / `null`, and that path must not guess. Guessing is the same defect as the one this ticket fixes, one layer down and harder to see.

**One reviewable point I fixed mid-implementation.** The escaped-throw spec first asserted only the negative half — a plain throw is `provider-error`, not `timeout-outer`. That left the classifier's true branch unexercised: a wrong constant would have made `timeout-outer` unreachable with the whole suite green, and `timeout-outer` is the one cause a widening consumer can act on. Added the throw that does carry the code, and verified the assertion is load-bearing by mutation — replacing the compared constant turns exactly that spec red, restoring it turns it green.

Two `SessionSummarization.spec.mjs` tests failed on an early run. I stashed to clean `dev` at `51e5bf429a` and reproduced both there before attributing them, then they passed on both trees on re-run — a local-model availability flake, not this diff.

- `buildMiniSummary` returns `{summary, cause}`. The seam still accepts a bare return.
- `backfillMiniSummaries` returns `failureCauses`; all four return sites carry it.
- Completion log gains a `[causes: …]` suffix on failing runs only. No test pinned that suffix; the cost-ledger parser matches a different line (`completed successfully`).
