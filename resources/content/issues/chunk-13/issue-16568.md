# The deployed revision is a build arg no runtime code reads, so deployment skew is unmeasurable

## Problem

`NEO_REVISION` reaches images as a build arg (`ai/deploy/docker-compose.yml:56-61`, the #16087 single operator pin) and is **never surfaced at runtime**:

```
grep -rl NEO_REVISION ai/services ai/mcp   →   (empty)
```

Exhaustive key dumps of both healthchecks confirm no revision field exists — Knowledge Base 19 keys, Memory Core 60 keys, neither carrying `revision`, `gitSha`, `commit`, or equivalent.

**Consequence: a deployment cannot report what it is running.** A plane hundreds of commits behind is indistinguishable from a current one through any surface we ship.

## Why `runtimeFreshness` does not cover this

It reports `"Runtime source/config identity matches the current checkout."` while a plane is far behind, because `stale.configDigest` / `stale.openApiDigest` are booleans against **the image's own checkout**. It answers *"are my tool schemas stale"* — the #16320 design intent — and structurally cannot answer *"am I current with dev"*. Not a bug in that feature; a different question with no implementation.

This is the signal whose name most implies it would catch drift, which makes its silence actively misleading.

## Why it matters now

Deployment skew is currently discovered during incidents, by hand, from indirect evidence. A long-lived deployment several hundred commits behind will not experience the fixes we ship, and nothing surfaces that — so the symptom gets attributed to product quality rather than to a stale deployment.

## Proposed shape

1. Emit the resolved revision in the healthcheck payload (both MC and KB). Precedent to copy: `snapshot.tenantRepoSync.repos[].lastIngestedRev` already does exactly this for ingested repo content, so the pattern exists in-tree.
2. With that field present, a **skew reporter** is a subtraction: `deployed` vs `origin/dev`, remotely readable over the MCP surface, needing no shell or docker access on the target.

## Acceptance criteria

- [ ] `healthcheck` on both surfaces reports the deployed revision, or an explicit `unknown` when the build arg was not supplied — never a silent omission.
- [ ] A deployment built without `NEO_REVISION` reports `unknown` rather than appearing current.
- [ ] Skew is computable from the MCP surface alone: deployed revision vs a named ref.
- [ ] The distinction is documented so `runtimeFreshness` is not mistaken for a drift signal.

## Related

- #16087 — established `NEO_REVISION` as the single operator-facing pin; this completes it by making the pin observable.
- #16320 — the passive surface-digest decision that `runtimeFreshness` implements.

Evidence: L1 — grep across `ai/services` and `ai/mcp`, plus exhaustive healthcheck key enumeration on two independent planes, 2026-08-06.

- 2026-08-08T03:25:39Z @neo-opus-grace referenced in commit `db2121b` - "fix(ai): require deployedRevision at the top level, and keep it verified (#16568)

Two things from @neo-gpt's cycle-2, and the second is the one that mattered.

`required: [revision, source]` constrains the object only once it EXISTS. The response
could still omit `deployedRevision` entirely — which is precisely the ambiguity this field
removes, since a consumer computing deployment skew reads an absent field as "current". My
own schema description claimed "always present" while the contract permitted omission.
Both HealthCheckResponse schemas now carry `required: [deployedRevision]`, deliberately
narrow: its siblings are emitted in practice but not contractually guaranteed, and widening
that list is a per-field decision rather than a convention this starts.

The second: I verified the first repair with a one-off node probe and shipped no guard, so
nothing kept it verified. That is the defect this ticket is about, for the third time in
one PR — a fact established once and not held. The spec now asserts, per service, that the
field is declared, that its enum and nested required set are right, that the RESPONSE
requires it, and that the emitted object satisfies the declared contract including the
unknown case. Top-level requiredness is a separate assertion from the nested shape because
they fail independently.

Carries a control (`runtimeFreshness` declared) so a mistyped schema path cannot fail every
assertion for the wrong reason and read as a regression.

Mutation-verified: dropping `required: [deployedRevision]` from knowledge-base reddens that
service's assertion and leaves memory-core green.

- 2026-08-08T09:06:35Z @neo-opus-grace referenced in commit `5c4d8f7` - "refactor(ai): one nullable string, not a two-field object (#16568)

Operator review: a token-drain bomb for a tiny "give me the neo sha" flag.
Correct on both counts.

`source` carried ZERO information. It was `revision === null ? 'unknown' : 'packaged'`
— fully derivable from the field beside it. I shipped a two-field object where one
nullable string does the job, then wrote paragraphs explaining how the two fields
interact. Most of the prose existed to justify the redundancy.

`deployedRevision` is now `string | null`: a SHA, the `local-build` marker, or null
when no build wrote one.

The openapi blocks drop 29 lines to 9 each. That is the part that actually costs:
schema descriptions ship in every `tools/list` response, so a seven-line prose
paragraph on a health field is a permanent per-session tax on every agent in the
swarm — unlike JSDoc, which costs only when someone opens the file. The distinction
was worth making and I had not made it.

Kept, because it is load-bearing rather than decorative: top-level `required:
[deployedRevision]` (presence is the contract; `null` is how "unknown" is said, and an
absent field reads as current to a skew consumer), and the memo's two sentinels —
`undefined` is "not read", `null` is "read, nothing there" — so an unbuilt runtime
does not re-read the file on every healthcheck.

- 2026-08-08T09:17:31Z @neo-opus-grace referenced in commit `762bd6c` - "refactor(ai): drop the memo — the goal is one field, not a caching layer (#16568)

The goal is narrow: we could not tell whether an external deployment had applied an
Agent OS update. One healthcheck field answers it.

The memo was premature and I justified it with a false premise — "the hottest endpoint
we serve". A healthcheck runs on a 60s interval; one readFileSync of a 41-byte file is
nothing. It bought no measurable saving and cost two cache sentinels, a reset seam
existing only for tests, and two specs covering the caching rather than the feature.

Removing it collapses the module to a single try/catch.

  module   88 -> 28
  spec    137 -> 40
  openapi  29 ->  9  per server

What survives is what the field is FOR: read the packaged marker rather than the
NEO_REVISION build arg (which records what was requested and no runtime code reads),
never throw, and stay present with a null value — an absent field reads as "current"
to whoever is checking for skew.
