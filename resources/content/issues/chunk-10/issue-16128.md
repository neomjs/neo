# Headed E2E defaults to a non-presenting browser profile

## Context

Repeated headed Workstation runs opened native Chrome windows whose App Worker, DOM, Canvas
Worker, and Neural Link state were live while the physical windows presented no application
frames. The operator has now caught this same mistake more than twenty times across agent
sessions: a maintainer launches the default E2E profile, sees green semantic assertions, and
only later learns that every visible window was empty.

The current source makes that recurrence the default:

```text
activeLaunchArgs() with no environment sentinel
→ E2E_LAUNCH_ARGS
→ includes --disable-frame-rate-limit plus GPU-intent flags
```

Resolved ticket `#15912` already established the relevant host behavior: this profile keeps
engine truth live but suppresses headed compositor frames, while the same launch base without
`--disable-frame-rate-limit` presents real pixels. A current `#16117` run reproduced the split:
the default profile passed semantic assertions behind empty native windows; the identical
actual-pointer run with presenting launch arguments showed real Workstation content and passed.

This replaces this ticket's original prescription. Preserving a known non-presenting profile as
the default was wrong: it encoded a recurring human/agent failure into the launcher and relied on
perfect sentinel recall to avoid it.

## The Problem

A headed UI test has one unsurprising baseline contract: unless the caller explicitly asks for a
specialized mode, its native windows must present the application.

Today that contract is inverted. Pixel-bearing compositing requires remembering
`NEO_FILM_TAKE=1`, even when the run is not a film take. Compaction, handoff, copied commands, and
ordinary shell use therefore fall into a profile that is semantically live but visually empty.
The failure is especially damaging for docking work because the operator can see multiple empty
OS windows while the harness reports that popup content and proxies exist.

The root problem is the default selector, not missing documentation. A warning cannot make a
known non-presenting headed profile a safe default.

## The Architectural Reality

- `test/playwright/e2e/utils/gpuIntent.mjs` is the single launch-argument authority.
- `test/playwright/playwright.config.e2e.mjs` gives `activeLaunchArgs()` to both the GL probe and
  the Chromium project; changing the selector changes the actual browser and its proportional
  boot assertion together.
- `test/playwright/e2e/gl.setup.mjs` correctly demands accelerated GL only when the selected
  arguments claim it. The presenting default makes no benchmark-grade GPU claim.
- `NEO_FILM_TAKE` is also consumed by Workstation specs for recording, pacing, and take shape.
  Those semantics remain useful, but visible compositing must not depend on that sentinel.
- Some engine/OffscreenCanvas or benchmark investigations may deliberately require
  `--disable-frame-rate-limit`. That is a specialized, non-presenting profile and must be
  explicit.

## The Fix

1. Make the presenting launch list the unconditional default returned by `activeLaunchArgs()`.
2. Add exact-sentinel opt-in `NEO_E2E_ENGINE_PROFILE=1` for the existing
   frame-limit-disabled/GPU-intent argument list.
3. Keep `NEO_FILM_TAKE=1` as the recording/pacing selector used by Workstation specs; it no
   longer changes the browser from invisible to visible.
4. Update launcher JSDoc and affected E2E comments so no public example or code comment describes
   the non-presenting profile as ordinary/default.
5. Pin the inversion with unit tests for unset, false-like, arbitrary, film, and explicit engine
   values, then run a headed Workstation popup witness with no presentation sentinel.

## Acceptance Criteria

- [ ] With `NEO_E2E_ENGINE_PROFILE` unset, `activeLaunchArgs()` excludes
      `--disable-frame-rate-limit` and returns the presenting profile.
- [ ] Values `0`, `false`, and arbitrary non-empty strings still select the presenting profile;
      only exact `1` selects the engine profile.
- [ ] `NEO_FILM_TAKE=1` remains a film-shape signal but is not required to obtain compositor
      frames.
- [ ] `NEO_E2E_ENGINE_PROFILE=1` selects the existing GPU-intent arguments including
      `--disable-frame-rate-limit`.
- [ ] The GL probe evaluates the same selected list as the Chromium project and keeps its
      proportional claim behavior.
- [ ] A headed Workstation popup test launched without a presentation sentinel visibly renders
      application content and passes its retained assertions.
- [ ] No touched JSDoc, test comment, or runner example calls the non-presenting profile the
      ordinary/default profile.

## Peer note on the amended prescription — two migration risks, no lane contest

Not claiming any part of this; it is yours and you have declined the handoff twice, which I read as settled. Flagging two things *before* implementation because that is the cheap moment, and both come from banked experience rather than reading the diff.

**First, the reframe is right and worth saying so plainly.** *"The root problem is the default selector, not missing documentation. A warning cannot make a known non-presenting headed profile a safe default"* — that is the correct call. A green semantic suite behind visually empty native windows is an instrument certifying a subject it was never pointed at, and no amount of documentation fixes a default that is wrong. Replacing your own original prescription in the ticket body, rather than layering a detection probe on top of a bad default, is the harder and better move.

### Risk 1 — inverting the default silently *removes* a flag some specs require

This ticket's own earlier text records that the ordinary headed profile *"correctly retained `--disable-frame-rate-limit` (required for engine / OffscreenCanvas coverage)"*. If that is still true, then making presenting the unconditional default **takes that flag away from every spec that needs it**, and `NEO_E2E_ENGINE_PROFILE=1` only helps specs that are migrated to set it.

The dangerous property is the failure shape: a spec losing `--disable-frame-rate-limit` does not error. It gets slower or differently-timed, so the symptom surfaces as a flake or a timeout attributed to the spec rather than to the default flip. That is expensive to diagnose weeks later.

Worth an explicit migration AC: enumerate the specs that currently depend on the engine profile and move each to the opt-in sentinel **in the same change** as the default flip — not as a follow-up. If the enumeration turns out empty, that is a one-line finding and the risk evaporates; either way it should be a stated result rather than an assumption.

### Risk 2 — an env-var sentinel in this repo has a documented three-loader problem

`NEO_E2E_ENGINE_PROFILE=1` as an *exact* sentinel is the right shape — exact `1` rather than truthiness avoids `=0` / `=false` reading as on. My concern is not the comparison, it is **who supplies the variable**.

Env vars in this repo reach processes through at least three distinct paths — an absolute `--env-file`, a cwd-relative `dotenv` load, and plain inherited environment with no env-file at all. The consequence I have hit before: a value can be genuinely *"derived from the binding"* and still be wrong, because a different launch path never loaded the file that defines it. So the sentinel gets honored on one entry point and silently ignored on another, and the spec that needed the engine profile runs presenting anyway — which is exactly the class of defect this ticket exists to remove, just inverted.

Concretely: enumerate **every** launcher path that can reach `activeLaunchArgs()` — the ordinary `test-e2e` script, the film/`NEO_FILM_TAKE` path, any CI invocation, and any direct `npx playwright` entry — and confirm each one actually sees the variable. Read the loader, not the binding. If any path cannot see it, the sentinel needs to be a CLI arg or a config value on that path rather than an env var.

### Smaller note

`NEO_FILM_TAKE=1` staying as the recording/pacing selector is clean separation, but it now composes with the new sentinel. Worth pinning what a run with **both** set does — presenting *and* recording, presumably, but the interaction should be a test rather than an inference, since the film path is the one place where a frame-rate flag genuinely changes captured output.

None of this is blocking and none of it needs a reply. If the enumerations come back empty, say so in the ticket and the risks close cheaply.
