Closes #16951. Second of two root causes behind the month-long frozen-cores deployment; the first is #16950.

## The defect

The embedding write canary's retry gate **single-flights correctly** and its **failure backoff works**. I filed this ticket claiming neither was true and had to correct it — the gate coalesces demand during a flight (`boundedRetryGate.mjs:298`), and a struggling provider does see attempts decrease.

Neither bounds a probe that **succeeds slowly**, because a healthy result carries no suppression at all — which is correct in isolation: a healthy provider *should* be re-probed. The consequence is not:

```
cadence  :  60s      →  a tick fires while the attempt is still running (joins, no new work)
duration : 264s      →  settles, and the next tick starts a fresh run ~36s later
                     →  264 / 300 = 88% provider occupancy, by the liveness check
```

Measured on the affected plane: **208 of 396 provider activities were `embedding-canary`** at ~264s each, while the Knowledge Base container sat at 0.1% CPU and tenant ingestion had made zero attempts. Every projection read green throughout. The probe worked, the gate worked, and the deployment was saturated by its own health check.

## The fix, and the fix it is NOT

A duty-cycle floor. After each attempt the producer stays idle for `charged · (1 - d) / d`, so the effective period is `max(cadence, charged + floor)`.

**Raising the cadence does not work, and this is the part worth checking.** A probe whose duration approaches its cadence runs back-to-back at *any* cadence value — 264s against a 300s cadence is 88% occupancy exactly as 264s against 60s is. Only a duration-derived floor closes it, and it self-scales: a fast probe never reaches the floor and keeps sampling at the cadence, unchanged.

**Putting the deployment's raised timeout back to 30s does not work either.** That raise was solving a real false-unhealthy restart loop. Both obvious levers are wrong in opposite directions, which is why this survived a month of looking at it.

I also reverted my own cadence-default change mid-implementation: I had claimed the 60s default contradicted the leaf's "sample in MINUTES, not seconds" guidance. 60000ms **is** one minute. The comment's actual falsehood was the separate claim that "the probe performs no inference itself" — corrected here. Raising the default would have delayed dead-provider detection 5x for none of the benefit.

## The charge model — @neo-opus-vega's upstream finding

`ollama/ollama#11889` (open) — Ollama does not stop processing a request whose client has terminated. Corroborated by `spring-ai#2944` and `rawveg/ollama-mcp#16`. Vega found it during this incident; nobody had run that search in a month.

So the measured span is not the provider's occupancy, and the discriminator is **whether we gave up**, not healthy-vs-failed:

| outcome | charged | why |
|---|---|---|
| returned inside budget (healthy **or** failed) | measured span | the work is done either way — a connection refused in 5ms cost the provider nothing |
| consumed the whole budget | measured + one further budget | abandoned; it is still running where we cannot observe it |

Charging a fast failure its full budget would slow recovery on exactly the plane we most want to re-probe. The error direction is deliberate: overcharging costs probe frequency, which the projection now reports; undercharging re-issues work onto a provider still executing the last attempt, which is silent — and silent is what froze four cores for a month.

## Second-order breaks this would otherwise have caused

Both found while writing the tests, not after:

1. **Staleness was measured against the configured cadence.** A probe legitimately waiting out its idle window would have reported `loop not running` — the dead-loop guard firing precisely on the deployments the floor exists to protect. Now measured against the effective period.
2. **`nextEligibleAt` is an absolute instant.** A re-arm carrying a fresh clock made it meaningless. It now re-bases the *remaining* idle onto the new source rather than dropping it, so a restart cannot be used to bypass the bound. There is a test for that.

## Reports, never degrades

A probe out of scale with its own schedule emits one details entry and does not change status. Degrading would flip the saturated deployments this detects into `unhealthy`, and the container restarts that follow are the hazard the cadence leaf already warns about — the probe would then be both the load *and* the restart trigger.

## Verification

5 new tests, all green. AC-1 was **mutation-tested**: disabling the tick guard (`if (false)`) makes it fail, so it cannot pass vacuously.

- `AC1` — 17 cadence ticks inside the owed window produce zero attempts; the 18th runs. A guard that permanently suppressed the probe would be a worse defect than the pileup, so non-permanence is asserted in the same test.
- `NON-VACUITY` — a 2s canary at 60s cadence runs on every tick, unchanged, and emits no warning. This one does **not** discriminate the fix; its job is to prove the floor cannot be why a healthy deployment stops being probed.
- abandonment surcharge — three ticks suppressed, the fourth runs. Without the surcharge the *second* would run, so the test distinguishes the surcharge from its absence. Paired with a fast-failure arm proving a cheap failure buys no idle.
- staleness — a slow-but-alive probe does not project `stale`, and the cost **is** reported.
- disabled floor — `maxDutyCycle` outside `(0, 1)` restores pure-cadence scheduling and says so.

Two tests in this spec fail on my machine (`shared-key verdict`, `without mutating the cache`) — both reproduce on clean `dev` and are local Chroma/loopback environment, not this change. CI is the oracle.
