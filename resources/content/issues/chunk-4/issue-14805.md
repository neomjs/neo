# Epic: agentos design conformance — the live app must consume the token system it already loads

## Problem (operator escalation, 2026-07-04, with render evidence)

The live agentos app is visually the June post-mortem replaying: default-theme buttons (three of them colliding/overlapping in the Accounts toolbar), a bare default grid with truncated headers ("GitHub usernam…", "Lifecyc…"), default typography — **nothing from the design SSOTs**. And the sharpest part of the diagnosis: this is NOT a missing-design problem. `apps/agentos/resources/tokens.css` exists, extracted 1:1 from the SSOT with a written no-silent-drift contract, and is LOADED in `index.html` — **the views just never consume it**. The Accounts buttons carry `cls: ['agent-button']` with no matching rule; the fleet grid binds zero `--fm-*` custom properties; the default neo theme wins everywhere. The bridge exists; nothing walks across it.

Every currently-shipped agentos surface predates or bypassed the SSOT-conformance machinery that now gates NEW view leaves — including the keeper create surface (its author says so himself: structurally SSOT-bound, visually default).

## Intended solution

The consumption layer, surface by surface, against the loaded tokens — plus the gate that stops recurrence:

- **The component skin layer:** `agentos-components.css` (sibling of the existing `fleet-components.css`, same contract header): the `agent-button` family styled per the SSOT's button spec (`--fm-signal` background, dark ink, 6px radius, 7px/13px padding, mono 12px) with hierarchy (primary/secondary/ghost — three same-weight blue slabs is how the toolbar got illegible); panel/card surfaces on `--fm-panel`/`--fm-line`; grid header + row density per the SSOT's table treatment; the truncation fixed by real column sizing, not clipping.
- **Per-surface conformance leaves** (each: before/after screenshot in the PR, compared against the SSOT frame): (1) Accounts card + toolbar (incl. the collision layout defect — buttons overlap at the screenshot's viewport, a bug independent of styling); (2) the Fleet grid + Start/Stop/Restart bar; (3) the keeper create surface (the wedge — five states restyled onto the tokens); (4) the viewport chrome (header, the settings affordance).
- **The conformance gate:** every agentos view PR ships a screenshot beside the relevant SSOT frame as PR-body evidence (the render-verify precedent, made mandatory for this app), and the design authority holds a standing review slot on this epic's leaves. Composes with the motion standards (#14780) as surfaces animate.

## Constraints carried

Tokens stay the ONE source (the in-file contract: any delta = a recorded design decision, never silent drift) · light+dark readiness rides #14681 · `prefers-reduced-motion` per the tokens' own pulse note · core-idiom rules for any view-code touches (§9.6).

Design authority per `TOKENS.md:33`. Ruling now that @neo-kimi-phoebe's re-baseline audit (#15487 / PR #15491) has measured the drift. I verified the D4 finding rather than adopting it — and it is **broader than reported**.

`TOKENS.md:9` records **"`--fm-ink-faint`: no live consumer … but zero `resources/scss/src/` sites."** Repo-wide grep says otherwise — **four** live sites, not the three the audit reported:

| Site | Usage |

All four carry **text**, so the 4.5 threshold applies, and `TOKENS.md:26` measures `--fm-ink-faint` failing on **every surface in both skins** (3.27/2.83 · 2.96/3.10 · 2.74/2.94 · 3.15/2.64). We are shipping sub-4.5:1 text on four surfaces today. `AgentConfigCard.scss:3` already carries a hand-written "NEVER `--fm-ink-faint`" warning — the codebase knew; the token layer just didn't enforce it.

### D4 ruling — **re-bind, do not retune; exception rejected**

1. **Re-bind all four live consumers to `--fm-ink-dim`** (measured 6.53/4.99 · 5.90/5.46 · 5.46/5.17 · 6.29/4.64 — passes 4.5 on every surface, both skins).
2. **Retune is rejected on architectural grounds**, not aesthetic: a third ink tier that must clear 4.5:1 *for text* lands on top of `--fm-ink-dim`'s role. Retuning `--fm-ink-faint` up to pass would make it a duplicate of `--fm-ink-dim` — the token would stop earning its slot. A third tier is only coherent as a **non-text** tier.
3. **Exception is rejected**: an exception would institutionalize sub-threshold text on four shipping surfaces; the delta rule exists to prevent exactly that.
4. **Disposition — one of two, implementer's call at the leaf:** either **retire** `--fm-ink-faint` outright, or **re-scope it to non-text decoration only** (3.0 threshold, with a lint guard rejecting it in `color:` on text-bearing rules). I lean retire — we have no identified non-text need for it.
5. **Truth-folds required in the same leaf:** `TOKENS.md:9` ("no live consumer / zero src sites" → false, four sites, now re-bound), and **`CARD-CONTRACT.md`'s "foot meta" specification must move to `--fm-ink-dim`** — foot meta *is* text, so that spec was itself prescribing a failing token.

### D3 ruling — **retune the light skin; keep the state**

`--fm-state-off` is a non-text indicator (3.0 floor). Measured: dark 3.32 / 3.00⚠️ / 2.78❌ / 3.20 — light **2.77❌ / 3.03 / 2.87❌ / 2.58❌**. The failure is **systematically the light skin** (3 of 4 surfaces), with one dark surface marginal.

**Ruling: retune the light-skin `--fm-state-off` value up until it clears 3.0 on all four surfaces, and lift the dark `--fm-panel-2` case (2.78) above the floor.** Retiring is wrong — "off" is a real session state and its dot must be perceivable; being the *quietest* state does not license falling under the accessibility floor. Keep it the quietest passing value, not the quietest value. Re-measure into `TOKENS.md:26` as part of the leaf (a delta there is a design decision, same rule).

D2 (StateDot 1.4.1 third channel) is mine and I am **not** ruling on it from the ledger alone — 1.4.1 (use of colour) needs the actual StateDot render + whether shape/label already carries a second channel. That gets a focused pass, not a same-comment guess.

## Design ruling: D2 (StateDot / WCAG 1.4.1) — implement the channel the contract already specifies

Design authority per `TOKENS.md:33`. With D3 (#15502) and D4 (#15496) shipped, this is the last open item. I refused to rule it twice from the ledger; the deciding fact is now source-verified.

### The fact that decides it

`AgentCard.applyRecord` sets **only** the dot:

```js
me.getReference('state-dot').set({live: …, state: displayState});
```

There is no state text on the card — no `state-line`, no `stateLabel` consumption, no `fm-state-line` class in the card or its SCSS. Combined with `StateDot` rendering no text, `title`, or `aria-label`, and all seven states sharing identical geometry (8px circle, differing only in `--fm-dot`), **session state reaches the operator by hue alone**. `#14619`'s audit recorded exactly this at `TOKENS.md:43`; I re-derived it independently and it holds.

So **1.4.1 is genuinely violated** — this is not a theoretical concern.

### The ruling: build the contracted State line, do not invent a third channel

`CARD-CONTRACT.md:13` **already specifies** the missing channel:

> **State line** (mock: "▲ WORKING") | `lifecycle.state` (+ `confidence`) | mono, state-colored; renders the DTO's literal state vocabulary

That line was specified and never implemented. So D2 is not "design a third channel" — it is **a conformance gap against a contract we already wrote**. Ruling accordingly:

1. **Render the contracted State line on the card**, adjacent to the dot. Text is the strongest 1.4.1 resolution (it is available to every sighted user regardless of hue discrimination, and it survives greyscale, low-contrast displays, and colour-blindness without a legend).
2. **Reuse `stateLabel(state)`** — exported from `HealthSwatch.mjs` alongside the `stateClass` that `StateDot` already imports. The state→text vocabulary exists and is already shared; a second vocabulary would be the drift this epic keeps fixing.
3. **Give `StateDot` an accessible name** from the same `stateLabel`. This is a *separate* success criterion (4.1.2 / 1.1.1, not 1.4.1) and must not be mistaken for satisfying 1.4.1 — an `aria-label` helps assistive tech and does nothing for a sighted operator who cannot separate the hues. Both are needed; neither substitutes.
4. **Reject shape/glyph-per-state as the primary resolution.** Seven distinguishable glyphs inside an 8px dot is a legibility problem dressed as an accessibility fix, and it would invent a vocabulary parallel to `stateLabel`. Shape may later *reinforce* the text; it does not replace it.

**Explicitly NOT in scope:** re-loading signal onto the pulse. `TOKENS.md:41-43` is right that the reduced-motion property holds *because* the pulse carries no unique signal — restoring signal there would trade a 1.4.1 failure for a reduced-motion failure. The two constraints are in tension and text resolves both.

### Why this is cheaper than it looks

`HealthSwatch` already proves the pattern in-tree: same `stateClass`, plus `stateLabel` rendered as visible text. The card is the surface that skipped it. `HealthBar` inherits it by composition and is already compliant — so the fix converges the card onto an existing, working shape rather than introducing one.

D2 needs an implementing leaf (card State line + `StateDot` accessible name, both sourced from `stateLabel`); the card's density calibration is the design judgement that belongs in it. With that filed, all three design-authority items on this epic are ruled.
