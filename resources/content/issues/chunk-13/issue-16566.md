## The lane's presence here is CORRECT — checked against the current authority map, not the stale amendment

Recording this because the obvious ADR read is out of date and would send a reader down a wrong path.

ADR-0014's **2026-05-23 (#11740)** amendment classifies `tenant-repo-sync` as *cloud-deployable*, "config-disabled in the local Neo-maintainer profile (which has no tenant repos)", and marks the path **not blessed production-deployable** pending the #11787 credential contract. Read literally in August 2026 that implies the lane should not be running on this plane at all.

**It is superseded, on both points:**

1. **The topology changed.** That amendment predates the local Agent OS being replaced by the dockerized deployment. The current projection (ADR-0014 amendment **2026-07-30 / #16166**, "exhaustive host-edge / container-plane authority projection") replaces the cloud-vs-local axis with **host-edge vs container-plane** — and `ai/daemons/orchestrator/taskAuthority.mjs:109` reads:

   ```js
   'tenant-repo-sync' : ORCHESTRATOR_AUTHORITY_CLASS.containerPlane,
   ```

   The dockerized local Agent OS **is** the container plane, so the lane running here is correct by construction. "Local" in the May amendment meant a non-containerized maintainer machine, which no longer exists.

2. **Pull mode was promoted to first-class**, so the "not blessed deployable" caveat no longer stands: `#11790` landed the lane, `#11791` its operator docs + health/telemetry, and `#12052`/`#12053` rewrote the Day-0 milestone to *first-class pull mode*.

3. **The §5.2 conflation is already handled in code**, not left to config discipline — `taskAuthority.mjs:81`: *"This does **not** re-point `kbSync` at TENANT content — that remains `tenant-repo-sync`'s job."*

**What remains a real question is the config, not the lane:** `kbSync` and `tenant-repo-sync` are now BOTH container-plane (`kbSync` moved there via #16556), and the single configured tenant entry is `tenantId: neo-shared`, `repoSlug: neo`, `cloneUrl: https://github.com/neomjs/neo.git` — the same corpus `kbSync` already ingests, under a byte-identical `tenantId/repoSlug` identity. Two lanes, two primitives, one corpus, one identity namespace. That overlap is worth a deliberate answer (see question 1 below), but it is a configuration choice, **not** an ADR violation.

⚠️ **Lesson for anyone extending this ticket:** ADR-0014 has five amendments spanning May–July 2026 across a topology replacement. Cite the **latest** amendment plus the runtime authority map, never the original decision table.

## Mechanism for the embed failure: the lease gates admission, not in-flight work

```
19:06:xx  kbSync starts its embedding loop (1281 batches)
20:12:40  TenantRepoSync: "Refreshing neo-shared/neo"
20:12:43  Orchestrator: "Deferring knowledge base sync; heavy maintenance task
                         tenant repo sync (cloud) is active"
20:17:27  ERROR TenantRepoSync failed: KB_TENANT_REPO_SYNC_SYNC_FAILED
                source=KB_VECTOR_EMBED_FAILED
                ("Knowledge Base ingestion returned an error-bearing summary.")
```

Tenant sync acquired heavy-maintenance status at 20:12 **while kbSync's loop from 19:06 was still running**. The `Deferring knowledge base sync` line proves kbSync was blocked from *starting again* — not that its in-flight batches had stopped. Both embedded concurrently.

Corroborating: the embedder degrades measurably under load. Batch pacing inside one kbSync run — 176 at 22:54:02, 177 at 22:54:24 (**22s**), 178 at 22:56:33 (**129s**), 179 at 22:58:44 (**131s**), 181 at 23:02:55 (**166s**). A 4–7x slowdown within a single run; a call taking 7x its baseline is what turns into a timeout-shaped failure for a second concurrent consumer.

Both lanes embed the same corpus under the **same identity** — `defaultTenantId: neo-shared` / `defaultRepoSlug: neo` is byte-identical to this repo entry's `tenantId/repoSlug`.

Also: the real embed error never reaches the log. *"Knowledge Base ingestion returned an error-bearing summary"* is a wrapper; the cause is inside the ingestion summary, so this cannot be diagnosed from logs alone.

## How the polling is actually implemented — two-level scheduling

Verified, because it makes the proof run cheap and it explains the failure accumulation.

**Level 1 — lane sweep.** Registered at `taskDefinitions.mjs:478` (`expectedCommand: 'TenantRepoSyncService'`, `serviceTask: true`, label *"tenant repo sync (cloud)"*), invoked from `pipeline.mjs:407` via `tenantRepoSyncService.runTask({...})`, polled at **`periodic-sweep:60000`** — every 60s. `configBase.mjs:1615` states this is deliberately *"decoupled from per-repo cadence"*.

**Level 2 — per-repo due-ness.** Base cadence `intervals.tenantRepoSyncMs` = **30 min** (`configBase.mjs:1189`), plus deterministic jitter and exponential backoff, computed by the pure helpers in `scheduling/tenantRepoSync.mjs` (`isRepoDue`).

So the sweep runs every minute, selects due repos, and attempts them; each failure increments `consecutiveFailures` and doubles `backoffMultiplier`, growing `effectiveCadenceMs`. That is exactly the observed `3 failures / backoffX=8 / "suppressed by backoff"` state, and why repeated attempts accumulated without a human triggering anything.

Also relevant to any fix:
- Per-repo concurrency is an in-memory semaphore; repos run via `Promise.all(...map(syncRepo))`, **not** sequentially — so a "between iterations" yield has to be placed at the start of `syncRepo`, not in a loop body.
- The service holds its **own** mutual-exclusion lease (`tenant-repo-sync-lease.json`, pid-liveness + TTL). This is **distinct** from the cross-daemon heavy-maintenance gate — yielding on the wrong one is a live trap (it invalidated a first attempt at the #16561 OQ1 adoption).
- `accessReadiness` is cached with expiring evidence, hence `KB_TENANT_REPO_ACCESS_EVIDENCE_EXPIRED` in the snapshot above.

**Consequence for the proof run:** a newly-registered tenant carries **no backoff**, so the 60s sweep picks it up within about a minute. No manual trigger, no waiting on a 2h suppression window. The only precondition is an idle embedder.

**The cadence numbers DO reconcile — and the reason they looked wrong is itself a small reporting gap.** `scheduling/tenantRepoSync.mjs:123-126`:

```js
backoffMultiplier  = Math.pow(2, Math.max(0, consecutiveFailures));   // 2^3 = 8 ✓
uncappedCadenceMs  = (baseCadenceMs + jitterMs) * backoffMultiplier;  // ≈ 4.1h at 30min base
effectiveCadenceMs = backoffCapped ? backoffCapMs : uncappedCadenceMs;
```

The observed `effectiveCadenceMs = 7200000` is exactly 2h because it is the **cap**, not a derivation — so nothing is misconfigured. But the reported per-repo state carries `effectiveCadenceMs`, `jitterMs` and `backoffMultiplier` while **omitting `backoffCapped`**, which `isRepoDue` computes and returns. A reader therefore cannot tell a derived cadence from a capped one, and the correct value reads as a config inconsistency — it did, to me, for long enough to nearly file it as a defect.

Worth surfacing `backoffCapped` (and the cap value when capped) in the reported state. The same file already accepted this exact argument once, at `TenantRepoSyncService.mjs:1172`: *"the reason a lane was wedged existed on disk and vanished from the one surface an operator can read — exactly when it mattered most."* Note the snapshot's `jitterMs` / `backoffMultiplier` fields are assembled on a path distinct from the `repoStates.push` at `:1162`, so the fix needs that path traced first.

## LIVE RESULT 2026-08-06 — the two repos fail at DIFFERENT stages

Executed end to end on the canonical plane after #16574 registered `create-app`. Two findings, and the second splits this ticket.

**First, the blocker was not code — it was a stale bind mount.** `kb-config.yaml` is bind-mounted per file into kb-server and orchestrator. `git merge --ff-only` replaces the file rather than editing in place, so the containers stayed bound to the **old inode**: `ls` showed a phantom entry while `cat` / `grep` / `head` all returned *No such file or directory*. A `restart` reuses the broken bind; only `up -d --force-recreate` rebinds. After recreate both containers read the config (`create-app` hits = 4) and the lane picked it up within ~90 s. **Any file-bind of a git-tracked config has this property** — see the note at the end.

**Second, and this is the split:**

```
00:48:50  Bootstrap-seeding neo-shared/create-app (consecutiveFailures=0, backoffX=1)
00:53:45  Refreshing neo-shared/create-app
00:55:24  ERROR create-app failed: KB_TENANT_REPO_SYNC_EMPTY_MATERIALIZATION
          ("Tenant-repo full materialization produced no durable positive-effect proof.")

          neo suppressed by backoff (consecutiveFailures=4, backoffX=16,
          next ~02:48, lastErrorCode=KB_TENANT_REPO_SYNC_SYNC_FAILED)
```

| repo | fails at | code |
|---|---|---|
| `neo-shared/neo` | **embed** | `KB_VECTOR_EMBED_FAILED` |
| `neo-shared/create-app` | **materialization** — never reaches embed | `KB_TENANT_REPO_SYNC_EMPTY_MATERIALIZATION` |

`TenantRepoSyncService.mjs:714` defines the second as *"full materialization lacks a fresh positive effect or matching unacknowledged retry receipt"* — the clone and materialization ran and produced **zero chunks**.

So "tenant ingestion is broken" is **two distinct defects**, not one. Anything fixing the embed contention will not make `create-app` ingest, and vice versa.

### 2026-08-07 — ⚠️ THE HYPOTHESIS ABOVE IS FALSIFIED. Do not run its experiment; it cannot produce a signal either way.

**The three source keys are inert on the pull path.** They configure the **`kbSync` full-corpus Source build**, not `tenant-repo-sync`. Pull-mode ingestion does not consult the Source registry at all — `ai/services/knowledge-base/helpers/tenantRepoIngestEnvelopeBuilder.mjs:12-19` describes the envelope as built straight from the git mirror: *"Linear history advances emit bounded raw-file deltas plus tombstones; bootstrap, missing-baseline, and force-push cases fall back to a full manifest-carrying snapshot."* The builder imports no `SourceRegistry` and reads no `sourcePaths`. So the repository's *shape* does not gate pull-mode materialization, and a scaffolding repo matching no curated Source is not a possible cause of its failure.

**Therefore the falsifier I prescribed above — "add the raw-repo source keys to the `create-app` entry and re-run" — is a NULL EXPERIMENT.** It changes no input the pull path reads. A still-failing run would have read as confirmation of a false negative; a coincidentally-passing run as confirmation of a false positive. Worse than no experiment, because it produces a result.

**How it was caught, because the method generalises better than the finding:** the operator pointed me at a deployment that already ingests non-Neo-shaped repositories through this exact lane. Its tenant config declares all three keys — so my "other deployments carry them" claim was literally true — and a comment beside them states plainly that on the pull path those keys *"are currently inert"* because the `kbSync` lane they govern is disabled there. The disproof of my hypothesis was sitting in the reference implementation's own comment. I then confirmed it against the envelope builder rather than taking the comment's word for it, since a comment asserting a property the code lacks is the failure mode I hit three times today.

That is the prior-art sweep earning its place for the fourth time this session: **whoever configured the working deployment had already answered the question I was about to spend a config cycle on.**

**What survives:** the *reporting* defect, and it now holds more strongly. `IngestionService.mjs:1016-1046` documents the same error code firing on this lane with `ingested=50, embeddings=50, errors=0` and **no materialization receipt** — materialization that worked, rejected downstream because `assertFullMaterializationEffect` saw a real effect and no proof of it. Its own words: *"a message that reads as the opposite of what happened."* With the shape hypothesis dead, **that is now the leading candidate** rather than one of two.

So `KB_TENANT_REPO_SYNC_EMPTY_MATERIALIZATION` covers at least two distinct causes:

| cause | signature | status |
|---|---|---|
| materialization succeeded, receipt never minted | `ingested > 0`, `receipt` null | **leading** — documented firing on this lane |
| the envelope genuinely carried no files | `ingested = 0` | open, but no longer attributable to repo shape |
| no registered Source matched the repo shape | — | **ruled out**: the pull path reads no Source registry |

The error code is the coarse signal; the discriminator is `ingested`, and **I have not read it for the `create-app` run.** That single field separates a receipt defect from an empty envelope, and it decides the whole half.

**The discriminating fields are already logged, so the next step costs nothing.** `:1037-1046` warns with `attemptPresentAfterValidation`, `attemptAccepted`, `ingested`, `deleted`, `errorCount`, `priorReceiptPresent` whenever a receipt is absent. The real first step is **reading that warn line from the `create-app` run** — no instrumentation, no config change, no experiment.

Note also `:1027-1033`: `attemptPresentAfterValidation` deliberately does not claim caller-omission, because the Zod gate in `ai/services.mjs` strips undeclared keys — *"Reading it as caller-omission is exactly how the first diagnosis on this lane was misrouted to a caller that was passing it correctly."* Second time this lane has been misrouted by reading one field as more specific than it is. Worth the two lines of warning to the next reader.

**What IS a defect, and it now holds more strongly than before:** the error cannot be acted on. *"Tenant-repo full materialization produced no durable positive-effect proof"* is indistinguishable, to an operator or an agent, from a broken clone, an empty envelope, a credential fault — **or a successful materialization whose receipt was never minted**. That last one is not hypothetical; it is the case the code comment records, with 50 files ingested and embedded. One error code, causes with opposite remedies, and nothing in the message narrows them.

The cost is not theoretical: this error sent me to a **wrong cause and a null experiment inside one sitting**, on a lane whose own code comments record a previous misdiagnosis from the same class of ambiguity. The stage holds the discriminating facts at the moment it fails — the `ingested` count and whether a receipt was minted — and the error code discards them.

This is the same shape as the embed half's *"Knowledge Base ingestion returned an error-bearing summary"* (above), and the same shape as the ceiling incident in #16630: **the system detects the condition and names it in a vocabulary that cannot be acted on.** Both halves of this epic reduce to that, which is worth stating because it changes the fix from two mechanisms to one discipline.

**Consequence for the ACs — the decomposition holds even though my cause did not.** The materialization half is workable **now** and does not require an idle embedder, because it fails before reaching embed. Its first step is neither a code change nor a config change: **read the `ingested` count from the `create-app` run's receipt-absence warning.** That decides whether this half is the receipt defect or an empty envelope, and it is the step that replaces the null experiment.

The embed half still requires the idle-embedder precondition and stays blocked while the plane re-embeds (batch 372 of 1121 at `2026-08-07T14:09Z`, ~30h remaining). Splitting on that boundary is what makes the epic half-workable rather than wholly blocked.

**Added AC:** `KB_TENANT_REPO_SYNC_EMPTY_MATERIALIZATION` must distinguish its causes in the error itself — at minimum effect-without-receipt from a genuinely empty envelope — not only in a `warn` line a reader has to know exists. Asserted with a fixture per cause and the error strings shown to differ. The embed half's *"returned an error-bearing summary"* wrapper is the same defect in the same lane, so both get named or neither is fixed.

**Added to Out of Scope by this finding:** tenant **Source/Parser** configuration (`useDefaultSources` / `rawRepoSource` / `sourcePaths`). Those govern the `kbSync` full-corpus build, not this lane, and touching them here would be work on a path this epic does not exercise. Worth its own ticket only if a deployment ever needs both lanes live against the same tenant.

**The cheap-proof property held.** create-app's full attempt took 99 seconds against `neo`'s multi-minute cycles, and it carries no backoff on first registration. The retry loop this ticket needs is now seconds long.

## Ordered questions — these precede code

1. **Is `neo-shared/neo` the right tenant entry?** Both `kbSync` and `tenant-repo-sync` are container-plane and both cover the Neo corpus under the same identity. Either that overlap is intended (and the embed contention below is its predictable cost), or the tenant entry should be a genuinely external repo. A small one is also the cheaper proof, since first-ingest cost scales with file count (#16557).
2. **Are the three configured tenants actually deployed?** Three were set up (`create-app`, `devindex-opt-in`, `devindex-opt-out`) but the snapshot shows **one** repo and `uninitializedCount = 1`. So "is tenant content ingested" is No for a second, independent reason: most configured tenants are absent from the deployed plane.
3. **Then:** root-cause `KB_VECTOR_EMBED_FAILED`.

## Acceptance criteria

- [ ] Questions 1–2 answered and recorded before implementation.
- [ ] A tenant repo ingests end to end: `lastIngestedRev` non-null AND a non-zero `repoSlug` count in `neo-knowledge-base`. **This is the proof artifact — a passing unit test does not close this AC.**
- [ ] The proof run happens against an **idle embedder**. A run concurrent with kbSync reproduces the contention failure and teaches nothing.
- [ ] `KB_VECTOR_EMBED_FAILED` root-caused. Candidates: provider contention (leading, see mechanism above); embedding-dimension mismatch against the tenant collection; an unbounded provider call — `TextEmbeddingService` accepts `options.signal` but it is **optional per caller**, so a caller omitting it has neither timeout nor cancellation.
- [ ] The underlying embed error is surfaced instead of wrapped as "an error-bearing summary".
- [ ] A repo whose embed stage fails reports `failed`, never `uninitialized`, and the lane does not report `status = completed` over a null `lastIngestedRev`.
- [ ] Either the heavy-maintenance lease covers in-flight work, or the embed path tolerates a saturated provider (bounded retry + a caller-supplied AbortSignal). Pick one and record why.
